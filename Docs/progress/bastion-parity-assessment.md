# Vaultix ↔ Bastion 功能对齐评估

> 生成日期：2026-09-09 · 基于批次②–⑥ 落地后的代码现状
> 参照项目：Bastion（GPL-3.0，Copyright 2025 JoyinJoester），位于 `reference/bastion/`
> 评估口径：可比能力点（非 LOC / 非 Screen 数）

## 1. 总评

**Vaultix 当前达成 Bastion 可比能力的约 40%（区间 35%–45%）。**

但这个数字需要正确解读，否则会误导排期：

- **Bastion 约有 1 万行代码是 Vaultix 架构上不需要的**——KeePass 本地库抽象、WebDAV/OneDrive 同步、跨库去重服务。Vaultix 是「Bitwarden canonical + CipherDto 密文存储」单后端架构，这些层**不应照搬**。
- **Bastion 把一个设置项拆成一屏**（78 个设置字段散在 20+ 子屏），所以「Screen 数比值 13%」严重低估真实覆盖。
- **两处 Vaultix 已反超 Bastion**（Bitwarden canonical 架构的直接红利）：
  - 身份条目 17 字段全量（Bastion 静默丢弃 passportNumber / licenseNumber / ssn）；
  - 自定义字段 4 态（含 Linked 指向字段），Bastion 仅 3 态。

**结论**：正确目标不是「逐行追平 Bastion」，而是「在 Bitwarden 密文架构内，追平 Bastion 的**可用操作面**」。剩余差距主要集中在**自动填充、导入导出、生成器独立页、个性化定制**四类，且前两类是架构级工作量。

## 4. 不应照搬（架构差异）

以下 Bastion 能力因 Vaultix 采用 Bitwarden canonical 单后端架构而**不应迁移**：

1. **KeePass 本地库层**——Vaultix 没有 KeePass 抽象，所有数据走 CipherDto 密文；强行引入会与既有 mapper/同步层冲突。
2. **WebDAV / OneDrive 同步**——Vaultix 通过 Bitwarden REST API 同步，这两类是 Bastion 的多后端补丁。
3. **浏览器扩展**——Bastion 的 `ExtensionsScreen` 实为「功能拓展聚合设置页」（剪贴板清理/通知栏验证器等），**并非真正的浏览器插件**；真正的浏览器表单填充由 AutofillService 承担。Vaultix 当前连 AutofillService 都没有，优先级应放在系统级自动填充而非扩展。
4. **跨库去重服务**——Bastion 多后端合并产生的去重需求，Vaultix 单后端不存在。

## 5. 工作量估算与建议路线

按「可用操作面」补齐，建议分三档：

**P0（架构级，先做，决定「能不能用」）**
- 自动填充服务（AutofillService + 凭据提供方 + 浏览器表单解析）：**大，约 5–8 天**。这是与 Bastion「完整操作」差距最大的一项，也是密码管理器的基本盘。
- 数据导入导出（Bitwarden JSON 双向 + 本地备份）：**大，约 4–6 天**。

**P1（中等工作，体验补齐）**
- 独立生成器工具页：**~1.5 天**
- 主密码改密 / 账户管理入口：**~2 天**
- 历史密码合并 / 高级通行密钥管理：**~2 天**
- 布局 / 卡片字段 / favicon 个性化：**~3 天**

**P2（小， polish）**
- 开发者日志与诊断导出：**~0.5 天**
- 自定义主题色、锁定遮罩 / 截图水印：**~1 天**

**合计 M2 待做：约 19–27 人天**（不含 P0 的自动填充/导入导出则可压缩到 ~10 人天）。

> 说明：百分比与工作量均为基于代码通读的估算，非精确度量。其中「主密码改密」「账户管理」两项因未逐文件确认，状态标为「待确认」，落地前需先核对 `UnlockViewModel` / `SettingsViewModel` 现有能力。

---

## 6. 一句话结论

Vaultix 已经把 Bastion 的**核心条目能力 + 验证码 + 回收站 + 外观/安全设置 + 卡片/通行密钥基础**对齐到位（约 40% 可比覆盖、且在身份/自定义字段两项反超）。要「像 Bastion 一样完整可用」，**最大两块缺口是系统自动填充与数据导入导出**——这两项是架构级工作量，建议作为 M2 的 P0 优先攻坚；其余多为中等或较小的体验补齐。
