## 0. 结论先行

**方向对，形态我建议换一个。**

「别为每加一个功能就扩一个 Tab」是对的；但「**互斥替换第 3 槽位**」有三个硬伤：
用户通常**同时**要用卡包和便签，互斥意味着每次换功能都要去设置改一次；
位置 3 语义漂移会毁掉肌肉记忆；而且会撞上项目 `SaveableStateHolder` 的状态契约。

⇒ 我推荐 **方案 A：中央「+」升级为动作菜单 + 便签走密码页已有筛选器**。
三个功能同时可用、Tab 身份恒定、几乎不动导航状态契约。

## 1. 取证：这两个「后续要完善的功能」其实已经有了

| 功能 | 实际状态 | 证据 |
|---|---|---|
| **便签 / 安全笔记** | ✅ **已是五种条目类型之一**，在密码库里 | `VaultItemType.SecureNote`（`core/model/.../VaultItem.kt:262`）；`ItemsQuickFilter.Note` 已能按类型筛选；新建表单 `TypePicker` 已能选「安全笔记」；KDBX mapper 只产 `Login` / `SecureNote` |
| **生成器** | ✅ **已存在**，是表单里的动作 | `PasswordGeneratorDialog.kt`，由 `ItemFormDialog.kt:1115` 的密码字段调用（`onUse` 回填密码） |

⇒ **用户想解的是「入口」问题，不是「功能」问题**。这和 `805b64cc`
「补三处『能力已有、入口没接』的缺口」是同一类：能力都在，缺的是显眼入口。

### 更关键：它们和「卡包」不是同一个层级的东西

| 对象 | 本质 | 该待在哪 |
|---|---|---|
| 卡包 | 一类条目的**集合视图**（`Card`） | 独立 Tab（现状） |
| 便签 | 一种**条目类型**（`SecureNote`） | 密码库里，用筛选器看 |
| 生成器 | 一个**动作 / 工具** | 表单里，或「+」的动作菜单 |

把它们并列成「第 3 槽位的三个候选」，等于把「目的地 / 内容类型 / 动作」混成一层。
**Tab 是导航（去某个地方），生成器没有"地方"可去。**

### 顺带澄清一个数据模型差异

用户说「bitwarden 和 kdbx 都有的便签」，两者其实不同：

- **Bitwarden** 有独立的 `SecureNote` 类型；
- **KDBX / KeePass** 没有独立类型，`notes` 是**条目上的字段**。
  项目 `KdbxItemMapper` 用「无用户名、无密码、有备注 ⇒ SecureNote」推导
  （`ItemTypePolicy.kt:17`），是兼容层的近似。

⇒ 若真做「独立便签页」，两个库后端的行为会不一致，需要在数据层先定口径。
  而放在密码页用筛选器看，这个差异天然被抹平。

| # | 问题 | 代码依据 |
|---|---|---|
| 1 | **互斥 = 不能同时用**。选了便签就没有卡包，银行卡条目得先去设置切回来才能看 | 产品层，非代码 |
| 2 | **肌肉记忆丢失**：位置 3 一会儿卡包一会儿便签，用户每次都要重新找 | 8.4「可点性由不透明 + 恒定在最上层保证」的同族纪律 |

## 4. 三个方案

### A ★ 推荐 · 「+」动作菜单 + 便签走已有筛选器

| 改动 | 内容 |
|---|---|
| 中央「+」 | 从单一动作升级为**动作菜单**（M3E `FloatingActionButtonMenu` 或长按展开）：新建登录 / 安全笔记 / 银行卡 / 身份 / SSH，外加「生成密码」工具（可复制、不强制建条目） |
| 便签 | 密码 Tab 的 `ItemsQuickFilter.Note` 已有，把它做显眼：置顶 chip 或加进 ⋮「前往」组 |
| 生成器 | 保持表单内原位，另从「+」菜单给一个独立入口（纯工具，用完即走） |
| 卡包 | **位置与身份完全不变** |

**收益**：三个功能同时可用；零肌肉记忆损失；`currentTab` / `SaveableStateProvider` /
`contentKey` / `addTarget` 全部不用改；入口放在各功能真正所属的层级。
**代价**：「+」从一次点击变成一次选择（多一步），需要按 8.8 §6④ 判定是否算产品变更 ——
我的判断是**算**，需单独拍板，但比改导航骨架便宜得多。

### B 折中 · 第 3 槽位做成「工具」容器（保留用户精神）

不是替换卡包，而是把该槽位身份**恒定为「工具」**，内部二级切换卡包 / 便签 / 生成器。
Tab 名字不变 ⇒ 状态契约不串台；但卡包从一步变两步，且「工具」这个抽象名不如「卡包」好认。

### C 用户原案 · 互斥替换

技术上可行，但要一次补齐 §3 的六项（尤其 `currentTab` 迁移与状态键设计），
且换来的是「一次只能用一个功能」。**我不推荐**，除非明确目标就是「底栏永远只有 4 格、
且用户愿意为换功能去设置」。

## 5. 我的建议与待拍板

**优先级**：A > B > C。

1. 先确认一件事：**你说的「完善便签 / 生成器」，是想要独立页面（有自己的列表、
   生成器有自己的历史与设置），还是只是想要更显眼的入口？**
   - 若只是入口 ⇒ A 足够，而且今天就能排期，几乎不动架构。
   - 若确实要做独立页面 ⇒ 那是两个新功能，应先各自定数据模型（尤其 §1 的 KDBX 差异），
     再回来谈它们该不该占 Tab；B 是那时的收容所。
2. 若采纳 A，「+」动作菜单算产品变更，需单独拍板（8.8 §6④）。
3. 无论哪种，**`VaultixNavModel.kt` 文件头那句「Send/Notes/Generator 暂不具备」
   应更正**，否则下一个接力者会照着过时结论做判断。
