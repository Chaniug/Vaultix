五、确认的代码缺陷

🔴 S1 · restoreItem 没用原子写 → 恢复操作可静默失效
data/repository/.../ItemRepositoryImpl.kt:360-370 
cipherDao.upsertAll(listOf(existing.copy(deletedDate = null)))   // ① 先改行
pendingOpDao.enqueue(PendingOpEntity(op = OP_RESTORE, ...))       // ② 后入队
项目为「行 + 队列」写专门建了 AtomicWriteDao.upsertCipherAndEnqueue（@Transaction 保证同生共死）， 并在 createItem:250 / updateItem:309 / softDeleteItem:338 全部使用。 唯独 restoreItem 是两个独立的 suspend 调用，且顺序是「先改行、后入队」。

后果：若 ② 失败（进程被杀 / IO 异常），本地行已清 deletedDate（条目重现），但队列里没有 OP_RESTORE ⇒ 下次同步 persistCiphers 用服务端旧版（仍带 deletedDate）覆盖它 ⇒ 条目又回到回收站，用户以为恢复了却"恢复失败"。

这不是我猜的：AtomicWriteDao 的 KDoc 第 22-26 行精确预言了这个症状—— 「软删除的条目则会被服务端版本复活」。

修复：改为 atomicWriteDao.upsertCipherAndEnqueue(row = existing.copy(deletedDate = null), op = ...)。

🟡 M2 · TOTP 生成失败静默返回恒定 000000

core/common/.../Totp.kt:143,163,203,357 —— Base32 解码失败 / 算法缺失时 catch (_: Exception) { "0".repeat(digits) }，用户看到一个恒定不变的 000000 而非错误提示， 会拿它去输入、失败后无法理解原因。属「错误被吞成合法的错误数据」。
⚠️ 但要如实说明：该文件 KDoc 第 57-58 行自己写着「用户看到恒定的 000000 且没有任何提示」 —— 这是作者知情的取舍（避免崩溃），不是疏漏。是否要改成返回 null 由 UI 显示「验证码不可用」，是个产品决策。

⚪ M3 · ParsedCipherString 是含 ByteArray 的 data class

core/crypto/.../CipherString.kt:56-61 —— data class 的 equals/hashCode 对 ByteArray 做引用比较而非内容比较。项目内 SymmetricCryptoKey.kt:15-16 的 KDoc 明说因同样原因它被改成了普通 class —— 同一项目内标准不一致。 当前若无 == 调用则无实际后果，但违反项目自定约定。

⚪ 可疑项（需进一步验证，未当作确定漏洞）

  • Autofill 保存路径用明文 String 密码走 Intent extra（AutofillSaveIntents.kt:17-34）—— 与项目「口令禁止用 String 承载」的核心规范相悖。Intent 会经 Binder 复制到 system_server， 明文密码短暂存在于系统进程内存。属架构取舍，但严格说应至少用 SecureBytes 并在用后清零。
  • CredentialProvider 的 PendingIntent.FLAG_MUTABLE（VaultixCredentialProviderService.kt:232-237）—— CP 场景系统确实需要 mutable（回填结果），但未比对官方 sample 是否同样要求，也未做 Intent 白名单校验。
  • KDBX passkey 写回不保真 —— FLAG_BE/FLAG_BS 因领域模型无此二位取默认值， 第三方写入的 false 会被改写成「可备份且已备份」。W6 真机待验。
✅ 值得肯定的地方（同样是实证）
生产代码（src/main，约 325 文件）： TODO/FIXME/HACK = 0 · GlobalScope = 0 · 空吞异常 = 0 · !! 仅 2 处且均经核实安全（都因 Kotlin 无法智能转换）。

SecureBytes/SymmetricCryptoKey 设计正确、fill(0) 清零真实存在、 toString() 只输出长度；AES-GCM nonce 用 SecureRandom 每次随机、128 位 tag； KeyPermanentlyInvalidatedException 有专门处理且穿透 ProviderException 包装链； FLAG_SECURE 经进程级 ActivityLifecycleCallbacks 全局覆盖全部 10 个 Activity。

这是一个反常态地干净的安全敏感代码库。正因如此，S1 才格外突出 —— 它是同一条写路径家族里唯一被遗漏的一致性保护。

功能路线建议

功能上，P0 的四项（导入器 / 附件 / 安全中心 / 主密码改密）决定了这个项目能否被"非作者本人"使用。 其中安全中心与导入器性价比最高：前者是安全产品的核心价值主张，后者是用户进入的第一道门。 建议把 M3 拆成 M3-a（导入导出矩阵，让它"进得来"）与 M3-b（安全中心，让它"有存在的理由"）。

本报告基于静态代码审查（实际读取代码行、grep 统计、模块结构分析）+ 2025–2026 公开竞品资料。 所有缺陷均附文件路径与行号。标注「需进一步验证」的项未当作确定漏洞。 不引用项目自报的完成度百分比（其 Bastion 对照报告自认「5 条 ❌ 有 4 条是假的」）。
