# 17 · 稳定性与防错规范

> 参照 Bitwarden / Keyguard / Monica / Bastion 的实践与 Android 官方建议，
> 列出 Vaultix **必须具备**的健壮性约束，以及**当前待整改项**。

## 1. 序列化容错（最高优先级）

**风险**：Bitwarden 服务端新增字段时，严格解析会**直接崩溃**——这是第三方客户端最常见的线上事故。

**约束（MUST）**

- `Json { ignoreUnknownKeys = true; explicitNulls = false; coerceInputValues = true }`
- `sync` 响应必须宽松解析，未知字段忽略
- 未知枚举/类型抛**明确异常**，而不是让解析崩在底层

**现状**：`data:bitwarden` 尚未创建 Json 实例 → **待整改（P0）**

## 2. 协程与取消

- `CancellationException` **必须透传**，不得吞掉（否则协程取消失效）
- CPU 密集型（KDF）**必须**走注入的 dispatcher，禁止主线程
- `viewModelScope` 随 ViewModel 自动取消；**禁止** `GlobalScope`
- 需要隔离子协程失败时用 `supervisorScope`

## 3. 敏感数据生命周期

- 明文只在 `useBytes { }` 或详情页短时存在，离开即 `zero()`
- 列表页**只持有密文句柄**（`LoginSecret.Encrypted`），绝不批量解密
- 禁止把密钥 / 口令 / 密文写进日志
- `SecureBytes.toString()` 不得泄露内容（已实现并测试）

## 4. 网络层健壮性（源自 Bastion 的真实事故）

| 项 | 要求 | 说明 |
|---|---|---|
| 超时 | 连接 / 读 / 写 **≤ 30s** | Bastion 原为 60s，用户感知就是"卡死" |
| 死连接 | `retryOnConnectionFailure(true)` + `pingInterval` | 反代（nginx/Cloudflare）会静默关闭空闲连接，复用即挂死 |
| 401 | `Authenticator` 按 host 刷新 token 后**重试一次** | 防死循环：`priorResponse != null` 即停止 |
| 重试 | 仅对**幂等**请求 | 否则可能重复创建条目 |
| 上传/下载 | **解耦** | 新建条目走轻量 `POST`，不等整库下载 |

**现状**：`data:bitwarden` 尚未配置 OkHttp → **待整改（P0）**

> ⚠️ 另注：Vaultwarden 会忽略 `sinceRevisionDate`，增量同步等于空转。
> 必须先用 `GET accounts/revision-date` 预检，再决定是否全量。

## 5. 数据库与并发（M1 引入 Room 时）

- 写操作走事务，避免半写状态
- 同步采用"预检 revision-date → 决定全量 / 增量"
- dirty 队列：本地改动先入队，联网后推送

## 6. 状态管理（MVI）

- `UiState` 不可变，事件用 `Channel` / `SharedFlow`
- 用 `collectAsStateWithLifecycle`（生命周期感知），避免后台无谓收集
- 用 `repeatOnLifecycle(STARTED)`，`launchWhenStarted` 已废弃

## 7. 崩溃与兜底

- 关键路径（解锁、同步、保存）失败**必须**给用户可见提示，**禁止静默失败**
- 全局异常处理器仅记录，不得上报任何明文

## 8. 性能基础设施（必要项）

| 项 | 收益 | 现状 |
|---|---|---|
| **Baseline Profile** | 官方推荐；显著提升启动与首次滚动流畅度 | ⬜ 未配置 |
| R8 全量优化 | 体积 + 运行性能 | ✅ release 已开启 |
| Gradle **配置缓存** | 构建提速 | ⬜ 未开启 |
| **Detekt** | 强制 `Docs/16` 的规模上限（防超大函数） | ⬜ 未接入 |
| 依赖校验 | 防供应链风险 | ⬜ 未接入 |
