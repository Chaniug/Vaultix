| 交付 | 内容 |
|---|---|
| `data:bitwarden` | prelogin / token / refresh / sync / 增删改 / 2FA（TOTP、Email、Remember） |

| UI | 连接 Bitwarden（官方 / 自托管）、顶部胶囊 + 可自定义 Dock、主列表、详情、编辑、验证器页、生成器 |
| 平台 | 生物识别解锁、自动锁定、`FLAG_SECURE`、剪贴板清除 |
| 验收 | 可对 bitwarden.com 与 Vaultwarden 完成登录—同步—写入—离线—重连全流程；抓包无明文；2FA 账号可用；**往返保真度测试通过（见 `Docs/02` 3.4）** |

> **为何改为先做 Bitwarden**（原为 KDBX 优先，已调整）：
> 1. **产品定位**：Vaultix 定位为 **Bitwarden 优先的客户端**（对标 Keyguard 路线），云端同步是主流用户的第一诉求，应最先打通；
> 2. **模型一致**：领域模型以 Bitwarden `Cipher` 为规范模型（见 `Docs/02`），先做 Bitwarden 可让实现与模型同构，避免"先按 KDBX 建模型、后再反向适配"的返工；
> 3. **底座就绪**：`core:crypto`（PBKDF2 / Argon2id / HKDF / EncString）已在 M0 完成，网络层可直接承接，无需额外加密基建。
>
> KDBX 作为第二库后置到 M2，仍保留在 1.0 范围内。

## 风险与对策

| 风险 | 可能性 | 对策 |
|---|---|---|
| **Bitwarden 官方 API 变更（认证流程、新增字段）** | **高**（Bitwarden 优先后由「中」调高：M1 主线强依赖） | `sync` 响应宽松解析（未知字段忽略）；只依赖新版 `userDecryption` 结构并在缺失时给出"服务端过旧"的明确提示；订阅官方客户端变更；**对齐官方客户端的「实际行为」而非仅文档**（已知非标准点：KDF salt 为 UTF-8 编码字符串、`encKeyValidation` 明文为 UUID） |
| 只支持新版导致存量用户被挡 | 中 | KDBX 3.1 / 旧服务端在打开时给出**可执行的**转换与升级指引（含推荐工具与步骤链接），不做静默失败 |
| Argon2 在部分设备上性能/内存问题 | 中 | 设备基准测试自动降配 + 用户可调；提供"低配模式" |
| KDBX 库 License 与兼容性 | 中 | 选型前完成 License 审计；必要时自研 KDBX 解析器（工作量约 +3 周） |
| 自动填充兼容性碎片化 | 高 | 兼容模式白名单 + 用户可反馈"此 App 填充异常"（附带结构化日志，脱敏） |
| 供应链安全 | 低—中 | 依赖最小化 + 校验和锁定 + `dependency-guard` |
| 维护者精力不足 | 中 | 文档先行、良好 first-issue 标记、模块负责人制 |

## 社区治理（建议）

- 采用 **Contributor Covenant** 行为准则。
- 决策记录放 `docs/adr/`（架构决策记录，ADR）：如"为何 Bitwarden 优先（原 KDBX 优先，2026-09 调整）""为何选 GPL-3.0""为何不接 FCM"。
- 安全漏洞披露：`SECURITY.md` 提供加密邮箱，承诺 90 天内修复或公开。
