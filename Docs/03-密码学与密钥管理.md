# 03 · 密码学与密钥管理

> **总原则**：不自研算法。所有原语来自 JDK / Conscrypt / 成熟第三方绑定；所有参数取值对齐 Bitwarden 与 KeePass 官方规范，并附测试向量。

## 1. 密钥层次总览

```
                       ┌─────────────────────────────┐
                       │ 用户主密码 (+ KeyFile / 2FA) │
                       └──────────────┬──────────────┘
        ┌─────────────────────────────┴─────────────────────────────┐
        │ Bitwarden                                                  │ KDBX
        ▼                                                            ▼
  KDF(PBKDF2-SHA256 / Argon2id)                          CompositeKey = SHA256(凭证拼接)
        │ salt = 邮箱（小写）                                          │
        ▼                                                            ▼
    MasterKey (32B)                                        KDF(仅 Argon2id)
        │ HKDF-Expand("enc"/"mac")                                    │ + MasterSeed
        ▼                                                            ▼
 StretchedMasterKey (64B)                                 CipherKey + HMACBaseKey
        │ AES-CBC 解包                                                │
        ▼                                                            ▼
 账号对称密钥 Enc+MAC (64B) ──加密条目──           外层解密 → 内层保护流密钥 ──保护 Password/TOTP 等字段
        │
        └─(可选) Keystore 密钥二次包裹 → 生物识别解锁凭据
```

## 2. Bitwarden 侧

### 2.1 预登录与 KDF 参数

`POST /identity/accounts/prelogin { "email": "..." }` 返回该账号的 KDF 配置。客户端**必须**使用服务端下发的参数，不能自行假设。

| KDF | 参数 | 默认/范围 |
|---|---|---|
| `Argon2id`（KdfType=1，**首选**） | `kdfIterations` / `kdfMemory`(MiB) / `kdfParallelism` | 默认 **3 / 64 MiB / 4**；范围 2–10、16–1024 MiB、1–16 |
| `PBKDF2_SHA256`（KdfType=0） | `kdfIterations` | 默认 600 000（OWASP 推荐下限），范围 600 000 – 2 000 000 |

> KDF 类型由**服务端决定并下发**，客户端无法单方面禁用 PBKDF2（否则旧账号无法登录）。策略：完整支持两种；新建账号与"修改 KDF"流程中**默认并推荐 Argon2id**；服务端下发 PBKDF2 且迭代数低于 600 000 时在 UI 提示"该账号密钥派生参数偏弱，建议上调"。

> 官方说明：客户端登录时还会在服务端配置的迭代数之上再多做一次内层拉伸（默认总计约 700 000 次）。实现时以服务端 `prelogin` 返回值与官方客户端实现为准，不要写死常量。

### 2.2 密钥派生

```
MasterKey        = PBKDF2-HMAC-SHA256(password, salt = email.toLowerCase(), iterations, 32B)
                   或 Argon2id(password, salt = 邮箱派生的盐, m, t, p, 32B)

StretchedMasterKey.enc = HKDF-Expand(MasterKey, info="enc", 32B)
StretchedMasterKey.mac = HKDF-Expand(MasterKey, info="mac", 32B)

MasterPasswordHash = PBKDF2-HMAC-SHA256(StretchedMasterKey, password, 1) → Base64
                    ↑ 这个哈希才是 POST /connect/token 的 password 字段（服务端存其再哈希值）
```

要点：
- **邮箱即盐**，改邮箱会改变 MasterKey；Bitwarden 通过"用新 MasterKey 重新加密同一把对称密钥"来兼容。Vaultix 修改邮箱/密码流程必须实现"重新封装对称密钥"，否则会锁死账号。
- 邮箱在派生前统一 `trim().lowercase()`。

### 2.3 对称密钥解包

登录响应中的 `Key` 字段是 **受保护的对称密钥**（EncString type 2）。用 StretchedMasterKey 解密后得到 **64 字节**账号对称密钥：

```
SymmetricKey[0..31]   = 加密密钥 (AES-256)
SymmetricKey[32..63]  = MAC 密钥 (HMAC-SHA256)
```

**只支持新版协议**：账号对称密钥一律从 `/api/sync` 的 `userDecryption.masterPasswordUnlock` 读取（该结构同时携带 KDF 类型与参数、加密后的主密钥）；**不实现**旧版 `profile.key` / 登录响应 `Key` 字段的回退路径。服务端若未返回 `userDecryption`，视为版本过低，提示用户升级服务端（Vaultwarden 需较新版本）。

### 2.4 EncString 编解码

格式：`<type>.<b64(iv)>|<b64(ciphertext)>|<b64(mac)>`（type 7 为 COSE/CBOR 编码，格式不同）

| type | 含义 | 支持策略 |
|---|---|---|
| `2` | `AesCbc256_HmacSha256_B64`（当前标准） | **读 + 写**（写入恒为此类型） |
| `7` | `CoseEncrypt0`（XChaCha20-Poly1305，COSE 编码） | 只读（新版客户端产出的条目）；V1 不写入 |
| `3` | `Rsa2048_OaepSha256_B64` | 只读，用于组织密钥与用户私钥解包 |
| `5` | `Rsa2048_OaepSha256_HmacSha256_B64` | 只读，同上 |

> 明确**不支持**：`0`（`AesCbc256_B64`，无 MAC 的遗留格式）、`4`/`6`（RSA-OAEP with **SHA-1** 的遗留变体）。遇到即报"数据由过旧版本客户端生成，请升级后重新同步"。

**解密必须遵循 encrypt-then-MAC 顺序**：

```
1. mac' = HMAC-SHA256(macKey, iv ‖ ciphertext)
2. 恒定时间比较 mac' 与 mac —— 不相等立即抛错（禁止"先解密再判断"）
3. plaintext = AES-256-CBC-Decrypt(encKey, iv, ciphertext)，去 PKCS#7 填充
```

**加密**：IV 由 `SecureRandom` 每次生成 16 字节。

### 2.5 非对称（组织/私钥）

- 用户密钥对：**RSA-2048**，私钥用账号对称密钥加密后上传（`PrivateKey` 字段）。
- 组织密钥：512 位对称密钥，用成员公钥 **RSA/ECB/OAEPWithSHA-256AndMGF1Padding** 包裹。
- V1 个人库场景不生成密钥对；仅在读取带组织条目时实现解包路径。

## 3. KDBX 侧

### 3.1 格式版本支持范围

**只支持 KDBX 4.x（major = 4）**，写入恒为 **KDBX 4.1**（`0x00040001`）。

| 版本 | 版本字 | 读取 | 写入 |
|---|---|---|---|
| KDBX 4.1 | `0x00040001` | ✅ | ✅（唯一写入目标） |
| KDBX 4.0 | `0x00040000` | ✅ | 打开后保存即升级为 4.1 |
| KDBX 3.1 及更早 | `0x00030001` / `0x0002000x` | ❌ 拒绝 | — |

拒绝旧版本时的用户提示："该数据库为旧版 KDBX 3.1 格式。请先用 KeePassXC / KeePass 2.x 将其转换为 KDBX 4.x 后再打开（Vaultix 不兼容旧格式）。"

支持的算法组合（4.x 范围内的现代选项，均不做遗留兼容）：

| 组件 | 支持 |
|---|---|
| 外层加密 | AES-256-CBC（默认）、ChaCha20（在无 AES 硬件加速设备上更快） |
| KDF | **仅 Argon2id**（version 0x13） |
| 完整性 | Header SHA-256 + Header HMAC-SHA256 + 分块 HMAC-SHA256 |
| 内层保护流 | **仅 ChaCha20** |
| 压缩 | GZip / 不压缩 |
| 密钥文件 | XML / 32 字节二进制 / 任意文件（SHA-256） |

> 明确**不支持**：Twofish、AES-KDF、Argon2d、Salsa20 与 RC4 保护流。遇到这些参数（通常为旧库或被第三方工具降配）时报错并指明具体项，不做静默降级。

文件头固定签名：`0x9AA2D903`、`0xB54BFB67`。

### 3.2 关键 UUID

```
Cipher:  AES-256-CBC = 31C1F2E6-BF71-4350-BE58-05216AFC5AFF
         ChaCha20    = D6038A2B-8B6F-4CB5-A524-339A31DBB59A
KDF:     Argon2id    = 9E298B19-56DB-4773-B23D-FC3EC6F0A1E6
Inner:   0 = 无保护   3 = ChaCha20
```

外层 header 字段 ID：`0` 结束、`2` CipherID、`3` 压缩(0/1=GZip)、`4` MasterSeed(32B)、`7` IV、`11` KDF 参数（VariantDictionary，`$UUID` 必须为 Argon2id）、`12` 公开自定义数据。
（KDBX 3.1 使用的 `5` TransformSeed、`6` TransformRounds、`8` ProtectedStreamKey、`9` StreamStartBytes、`10` InnerRandomStreamID 均已废弃，本实现不读取。）

### 3.3 解密管道（KDBX 4.x）

```
1. 校验签名与版本（major ≠ 4 → UnsupportedFormat）；逐字段读外层 header
   - `$UUID` 非 Argon2id / CipherID 非 AES 或 ChaCha20 → 明确报错
   - minor 高于支持值（如 4.2）→ 允许打开并提示"存在未知字段，保存可能丢失"
2. CompositeKey = SHA256( SHA256(主密码) ‖ KeyFileKey ‖ 挑战响应 )
3. TransformedKey = Argon2id(CompositeKey, 参数：S / I / M / P / V)
4. MasterKey_cipher = SHA256(MasterSeed ‖ TransformedKey)
   ChaCha20 情形：cipherKey = SHA512(MasterSeed ‖ TransformedKey)[0..32)，nonce 取 header IV(12B)
5. HMACBaseKey = SHA512(MasterSeed ‖ TransformedKey ‖ 0x01)
   hmacKey_i   = SHA512( int64LE(i) ‖ HMACBaseKey )
   header 校验用 i = 0xFFFFFFFF_FFFFFFFF；数据块用块序号（从 0 开始）
6. 校验 header SHA-256（快，先验）→ 再校验 header HMAC（口令正确性在此暴露）
7. 读取 HMAC 块流：每块 = HMAC-SHA256(32B) ‖ length(4B LE) ‖ data
   逐块校验后拼接；length = 0 为终止块
8. 解密（AES-CBC-PKCS7 或 ChaCha20）→ GZip 解压（若 compression = 1）
9. 读内层 header：InnerRandomStreamID、InnerRandomStreamKey(64B)、二进制附件表
10. 解析 XML；Protected 字段保留密文，仅在访问时解密
```

错误定位（用于给用户准确提示）：

| 失败阶段 | 含义 |
|---|---|
| Header SHA-256 不一致 | 文件被截断或损坏 |
| Header HMAC 不一致 | **主密码 / KeyFile 错误**，或 KDF 参数被篡改 |
| 某数据块 HMAC 不一致 | 文件损坏（同步未完成 / 存储介质问题） |
| XML 解析失败 | 结构损坏，建议从备份恢复 |

### 3.4 内层保护流（Protected Value）

```
key    = SHA256(InnerRandomStreamKey)      // 32B
nonce  = 固定 12B 常量 `E830094B97205D2A` + 4B 零扩展（ChaCha20）
cipher = ChaCha20(key, nonce, plaintext) → Base64 存入 XML，属性 Protected="True"
```

- 每个字段**从头开始**用该流加密（不是续接），因此随机访问任意字段都能独立解密。
- 内存中保留流的密钥但不保留明文；详情页/复制时按需解密。
- 读取时若 `InnerRandomStreamID ≠ 3`（ChaCha20）→ 报"数据库使用了不受支持的保护流（Salsa20/RC4），请转换为 KDBX 4.x 标准配置"。

### 3.5 写入与参数默认值

| 项 | 新建库默认 | 说明 |
|---|---|---|
| 格式版本 | KDBX 4.1 | 无兼容模式开关；写入路径唯一 |
| 外层加密 | AES-256-CBC | ChaCha20 在无 AES 硬件加速设备上更快，可在高级设置切换 |
| KDF | Argon2id（唯一） | 目标解锁耗时 **0.5–2 s**（在用户最慢设备上） |
| Argon2 参数 | memory 64 MiB、iterations 3、parallelism = 设备核心数（上限 8）、version 0x13 | 需做设备内存上限保护（低端机降配至 32 MiB，并在 UI 标注"低于推荐值"） |
| 内层保护流 | ChaCha20 | 每次保存生成新的 64B InnerRandomStreamKey |
| 压缩 | GZip | 附件大库可关闭以换取保存速度 |

**原子写入**：写临时文件 → `fsync` → 重命名覆盖目标 → 校验读回。禁用"原地覆盖"。

## 4. 本地密钥存储（Android Keystore）

```kotlin
val spec = KeyGenParameterSpec.Builder(
    "vaultix_biometric_key",
    KeyProperties.PURPOSE_ENCRYPT or KeyProperties.PURPOSE_DECRYPT
).apply {
    setBlockModes(KeyProperties.BLOCK_MODE_GCM)
    setEncryptionPaddings(KeyProperties.ENCRYPTION_PADDING_NONE)
    setKeySize(256)
    setUserAuthenticationRequired(true)
    // 0 = 每次使用都要认证；>0 = 时间窗内免认证
    if (Build.VERSION.SDK_INT >= 30) setUserAuthenticationParameters(0,
        KeyProperties.AUTH_BIOMETRIC_STRONG or KeyProperties.AUTH_DEVICE_CREDENTIAL)
    else setUserAuthenticationValidityDurationSeconds(-1) // 需 CryptoObject 认证
    setInvalidatedByBiometricEnrollment(true)   // 新增/删除指纹即失效
    if (Build.VERSION.SDK_INT >= 28) setIsStrongBoxBacked(true)   // 失败则回落 TEE
}.build()
```

| 存储对象 | 保护方式 |
|---|---|
| 生物识别解锁凭据（包裹后的主密钥/复合密钥） | Keystore AES-GCM（上表 spec）→ `EncryptedSharedPreferences` |
| OAuth access/refresh token | Keystore AES-GCM（**不带**生物识别门禁，便于后台静默续期） |
| 本地密文缓存（Room） | 数据库内已是密文；数据库文件本身不额外加密（避免双重开销），但目录置于 `noBackupFilesDir` |
| KDBX 文件 | 由用户通过 SAF 管理；Vaultix 只在内部缓存区留一份临时副本，锁定即删 |
| 内存中的密钥 | `SecureBytes`（ByteArray 包装，提供 `zero()`）；**禁止**用 `String` 保存 |

**必测异常**：`KeyPermanentlyInvalidatedException`（指纹变更后密钥失效）→ 清除生物识别凭据、提示重新用主密码解锁；`UserNotAuthenticatedException` → 拉起 `BiometricPrompt`。

## 5. 随机数与编码

- 所有 IV / nonce / salt / 主密钥材料一律 `SecureRandom`（Android 上为 `SHA1PRNG`/Conscrypt 提供的实现）；**禁止** `Random`。
- Base64 使用 `Base64.NO_WRAP or Base64.NO_PADDING`（Bitwarden EncString 均为标准 Base64 无换行）。
- 所有比较密钥/MAC 的地方使用 `MessageDigest.isEqual`，避免时序侧信道。

## 6. 密码学清单（自检用）

| 检查项 | 结论 |
|---|---|
| 是否存在自研算法/自研填充 | 否 |
| 是否出现硬编码 IV / salt / 密钥 | 否（KDBX 内层流 nonce 为格式规定的常量，例外并已注明） |
| 是否先解密后验 MAC | 否，统一 encrypt-then-MAC |
| 明文是否落磁盘/日志/备份 | 否（备份目录 `noBackupFilesDir`，release 无日志） |
| 是否可能存在密文降级（type 2 → 0） | 不允许，写入恒为 2（或更高） |
| KDF 参数是否可被服务端单方面下调 | 需在 UI 提示"参数较弱的账号"，并允许手动上调 |
