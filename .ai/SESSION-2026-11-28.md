# SESSION 2026-11-28 · 附件区 UI 务实档改版 + 100MB 前置预检

> 你看一下标准。看看 bitwarden 和 keepass 的规范」。

## 1. 规范调研（官方源，本轮查证）

| | Bitwarden | KeePass / KDBX |
|---|---|---|
| 单附件上限 | 500MB（网页/桌面）；**移动端上传 100MB 硬限** | 格式层 ~4GB（UInt32、不可配置）；第三方服务常 25MB |
| 账户总量 | 5GB（付费用户/付费组织，1GB 增量加购） | 无账户概念，受库文件体积制约 |
| 加密位置 | 本地加解密，服务端只存密文 | 二进制存进 KDBX，随库加密 |
| 依据 | [帮助中心 attachments](https://bitwarden.com/help/attachments)、[Send](https://www.bitwarden.com/help/create-send/) | [作者答复](https://sourceforge.net/p/keepass/discussion/329221/thread/89ff8fb2)、[KDBX 规范](https://keepass.info/help/kb/kdbx.html) |

**判据**：现有 `MAX_ATTACHMENT_BYTES = 100MB` 对齐 Bitwarden 移动端硬限，正确。KDBX 虽能到 4GB，
但附件写库是**整库重写**，手机端 100MB 已是务实上限 —— 两类来源统一用这一个数，
UI 明示「单个附件不超过 100MB」，避免用户误以为是 bug。

## 2. 改了什么（4 文件，+137/-26）

### 2.1 大小预检时序（真问题，不只是观感）
- 原逻辑：选择器回调里先 `readBytes()` 把整份文件读进内存，回到 ViewModel 才判超限 ——
  100MB 白读一遍，低内存机型可能先 OOM。
- 现逻辑：`SafFiles.querySize()` 先查 `OpenableColumns.SIZE`：
  - 超限 → 走 `onTooLarge()` 上报事件，**根本不读字节**；
  - 拿不到 SIZE（虚拟文件/云盘 Provider）→ 返回 null → 退回原路径读出后由 ViewModel 字节级兜底。
- 两端共用 `internal MAX_ATTACHMENT_BYTES`（从 `private` 提升），杜绝「UI 99MB / VM 100MB」漂移。
- ViewModel 新增 `onAttachmentTooLarge()` 作统一事件入口，文案只在 strings.xml 一处。

### 2.2 UI 务实档（结构不变、低风险）
- 入口：标题旁孤零零的小 `+` IconButton → 带文字的「+ 添加附件」`TextButton`。
- 空态：一行灰字 → 卡片内可点区域（图标 + 「点此添加」+ 「单个附件不超过 100MB」）。
- 附件行：文件名直接贴卡片左边 → 加 `secondaryContainer` 淡底圆角类型图标锚点
  （统一 `AttachFile`，不按扩展名分类型，避免 mime→图标映射与未知兜底的复杂度）。
- 大小展示：MB 从整数取整改为 1 位小数（`2.4 MB`），KB/B 仍取整。
- 遵守 M3 视觉方案：分区标题仍 `titleSmall` + `onSurfaceVariant`；同一屏无新增 Filled 按钮
  （`TextButton` 是次要动作）；删除确认仍用 `DialogTextButton`（#284 门禁）。

### 2.3 文案与清理
- `attachment_empty_hint`：「点右上角 + 添加」→「点此添加」（入口已改）。
- 新增 `attachment_limit_hint`；`attachment_too_large` 明确「单个附件」。
- 删除 `attachment_kdbx_readonly`（P1 起已零引用，本想改文案，发现是残留 → 直接删）。
