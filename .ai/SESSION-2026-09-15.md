## 7. 用户报的空白页 bug（提交 `c1ff14a`，问题编号 #99）

### 7.1 现象与复现路径

「设置里当前是 Bitwarden，**选择 KDBX 查看、不点「默认」**，返回到密码条目页是空白的，
验证码页也全白，好像加载不出来。只能通过条目页 ⋮ → 切换密码库 → 进登录界面 →
验证生物解锁，才能顺利看到条目。」

### 7.2 根因：三件各自合理的事叠成死局

| # | 环节 | 行为 |
|---|---|---|
| 1 | `ActiveVaultDialog.onSelect` | 对**未解锁**项也无条件 `select(vaultId)` |
| 2 | `ItemRepositoryImpl.observeItems`（KDBX 分支） | `Kdbx.contentOf(id)?.items.orEmpty()` ⇒ 一个**真实的空列表** |
| 3 | `ItemsScreen` 空态 | 空列表 ⇒ 「还没有保存的密码」 |

单看每一步都对；合起来「库锁着」这个**唯一真正的原因**被 `orEmpty()` 抹掉、
又被空态文案替换成假话 ⇒ 用户看到的只有全白。
再叠加 `ItemsViewModel.init` 的**「切库即锁旧库」**（这条策略用户拍板保留）：
切过去的瞬间原来的 Bitwarden 也被锁 ⇒ **两个库都进不去**，
只剩用户自己摸出来的那条生路。

### 7.3 修法（用户拍板的取向：点未解锁的库 → 直接去解锁页）

- `SettingsScreen` 新增 `onOpenLockedVault(vaultId)`，一路透传到 `VaultixApp`
  的 `UnlockRoute(vaultId)`；两个 `SettingsScreen` 调用点（Tab 内嵌 / 独立路由）都接上。
- `ActiveVaultDialog` / `VaultChoiceRow` 改为传整个 `VaultSummary`：
  `unlocked` → 切活跃库；未解锁 → 去解锁页。
- 未解锁行**不再画 `RadioButton`**（单选语义是"现在看哪个"，它不参与），
  改右侧 `KeyboardArrowRight` + 副标题「未解锁 · 点这里输入主密码」。
- 「设为默认」**保持可用**（正当用途：明知要输密码仍想让它冷启动先开），
  但只对已解锁库同步切活跃库。
- **兜底**：条目页 / 验证码页新增「库未解锁」空态 + 「立即解锁」出口。
  正常路径走不到，但能防住同类静默状态（冷启动恢复 / 未来新入口）。

### 7.4 detekt 逼出来的重构

加了兜底分支后门禁立刻报了三处（说明这轮优化本身在压缩代码余量）：

```
ItemsScreen   LongMethod 152 > 150
TotpCodesScreen LongMethod 153 > 150、CyclomaticComplexMethod 15 > 14
```

⇒ 抽出 `ItemsBody`（空态与列表分流）与 `TotpBody`（四处 `when` 分支）。
⚠️ 教训：**用脚本按行号做大段移动会翻车** —— 删了 import 后行号偏移，

## 8. 收尾：CI 盲区（#100）+ 一个可复用自检脚本（同日追加）

### 8.1 我想"补一次编译验证"，结果撞出一个从未跑过的门禁

推送文档提交后收到 CI 通知，我想着"顺手确认一下"，于是手工触发了一次
`gh workflow run ci-debug.yml`。**这是我第一次用非 push 方式触发这个工作流**，
结果：**`Run lint` 步骤失败，后面 detekt / 编码检查 / Build Debug APK 全部 skipped**，
而这次改动**只是两个 .md**。

查下去发现的原因（见 `issues/01-构建与环境.md` **#100**）：

- lint 步骤带 `if: github.event_name != 'push'` ⇒ **push 链路永远跳过**；
- 本仓库最近 50 次 CI 运行**全是 push** ⇒ 这条步骤**是第一次真正执行**；
- 即：**「push 全绿」这个结论里从来不包含 lint**，这道门**从未被验证过**。

⇒ 这是**盲区**，不是我这轮的回归。但它有两个直接后果：
① 我不能再拿"CI 全绿"当作完整门禁证据（必须说明是哪条链路）；
② lint 一失败就把它后面三条真门禁全 skip 掉 —— 所以先给它加
`continue-on-error: true` **止血**（只报告、不阻断）。

**刻意不做的事**：不删 `if`、不放宽 lint 规则、不压代码。
因为**失败原因还没取证**：可能是「`setup-gradle` 固定的 Gradle 8.11.1 与 AGP 9.3.2
不兼容」，也可能是真有 lint 违例 —— 两者处置完全相反。
沙箱**拿不到 job 原始日志**（`.../logs` 302 到 `blob.core.windows.net`，沙箱不可达，下载 0 字节），
所以留了替代手段在 #100 里（check-run annotations 最有用）。

> 顺带发现：`ci-debug.yml` 把 Gradle 固定为 **8.11.1**，而仓库 wrapper 是 **9.5.1**。
> push 链路的 `./gradlew` 走 wrapper（9.5.1）所以能过；`setup-gradle` 那个 8.11.1
> 只影响它自己的 Gradle 命令。**待确认**这一项是否就是 lint 失败的原因。

### 8.2 把上一轮的教训做成了脚本：`.ai/tools/check_signature_types.py`

上一轮我因为**凭记忆写错类型名**（`ItemGroup` / `ItemsDisplayMode`，真名是
`ItemsGroup` / `ItemsCardDisplayMode`）把 CI 编译搞红，当时说"这类错误本可以本地一次揪出"。
这轮把它真的写出来了。

**它做什么**：扫 `app/src/main/java` 建「全仓库顶层类型定义」表（230 个），
再解析每个函数/Composable **参数列表**里的类型名，检查它是否
「有 import ／ 同包有定义 ／ 是 Kotlin 默认可见类型 ／ 是泛型参数」，
不满足就报出来（含行号与出处）。

**开发它本身踩了三个坑**（都修了，源码注释里写明了原因）：

| 坑 | 现象 | 修法 |
|---|---|---|
| 朴素正则 `标识符 : 类型` 扫整个参数串 | **22 处误报**：`ThemeMode = ThemeMode.SYSTEM` 里的 `SYSTEM`、`String = "Vaultix"` 里的 `Vaultix` 都当成了类型 | 先按**顶层逗号**切参数段，每段只取**第一个 `=` 之前**的部分 |
| 没剥注释 | **29 处误报**：KDoc 里写的 `fun foo(...)` **示例**被当成真定义（本仓库注释密度高，极易中招） | 先做 `strip_comments_and_strings()`（等长空白替换、**保留换行**，行号不错位） |
| 全限定名/嵌套类当成未知 | `android.content.Context` / `PasswordStrength.Level` 被报 | 全限定名整段跳过；嵌套类只查**最左边那段** |

**关键验证（不是"跑通就算"）**：我把当时那个真实错误**注入回去**
（`items Group: List<ItemGroup>`），脚本精确报出 5 处、退出码 1；
恢复后全仓库 158 个文件 **0 报**。⇒ 它是**能抓到目标缺陷**的，不是空转的。

**用法**：`python3 .ai/tools/check_signature_types.py`（默认查最近提交的改动）
`--all`（全仓库）/ 显式传文件名。**抽/改函数签名后跑一遍。**

### 9.2 解锁页 PIN 键盘下移

**根因**：`UnlockScreen` 主列恒 `verticalArrangement = Arrangement.Center`，
整列（头像 64 + 库名 + 账号 + 圆点 + 4×76dp 按键 + 出口 ≈ 520dp）在可用高度里居中
⇒ 键盘落屏幕中部偏上，拇指够不到。

**关键约束**：外层有 `verticalScroll`（小屏 / 横屏必须能滚）⇒ 给子项的是**无界高度**：
- `weight(1f)` 要求有界 ⇒ 直接抛 `IllegalStateException`；
- `Arrangement.Bottom` 只在内容**低于**容器时才推到底，内容一超高就退化成 `Top`
  ⇒ 小屏键盘被推出屏幕（要滚动才够得着，比居中更糟）。

**解法**：顶对齐 + 反推让位。

```
让位 = 屏高 − 顶部信息区高 − 键盘高 − 换库按钮高 − 底距
```

**⚠️ 第一版我写错了**：用「屏高 × 0.35」当目标值。键盘自身就 400dp，
任何 < 0.5 的比例都算出负数 ⇒ **让位恒为 0，等于没改**。
是**写成公式后代入真实尺寸验算**（600/640/720/800/891/915 六档）才发现的。
最终键盘底从改前的 **57%~82%** 稳定落到 **88%~92%**，零溢出。

⚠️ 第二版又漏了「换一个库」按钮的高度：它挂在键盘下方，漏算把整列顶出屏幕，
**唯一的多库出口要滚动才看得见**（多库用户冷启动卡在解锁页时那是唯一出路）。
⇒ 把它算进让位，并让显示条件与 `switchVisible` 同源（两处漂移就会"算进去了却没显示"）。

⚠️ detekt 实测拦了一次：我加的 `if (state.pinMode)` 正好是压垮
`CyclomaticComplexMethod` 的第 15 个分支（上限 14）。⇒ 把「排列方式 + 让位」
折进 `unlockColumnLayout()` 一次返回（`UnlockColumnLayout` 数据类），
主函数里只剩一次解构赋值，零新增分支。

### 11.1 用户驳回的是我的错修 —— 通行密钥「必须点搜索才出现」

用户原话：**「通行密钥界面打开还是没有显示，必须要点一下搜索，才能出现。这样不对吧」**。
上一轮我只**调整了空态分支顺序**，把它当成 #84 的「分支塌陷」来治 —— **方向错了**，
没碰真正的病根。用户说「还是」，就是明确告诉我上一修没生效。

**真正的根因**：`PasskeysScreen` 调的是 `viewModel.passkeyRows()`，
而它内部读 `_state.value` —— **普通函数调用不会订阅 Flow、也不参与重组**。
首帧算出空列表后，**没有任何机制再触发一次重组**，页面就钉死在「还没有通行密钥」。
点搜索会翻转 `searchActive` ⇒ 逼出一次重组 ⇒ 条目才冒出来。
**症状的形状本身就是诊断**：「点一下某个无关按钮才出现」= 数据在、但没有订阅。

**修法**（对齐验证码页 `rememberTotpEntries`，那边早就修过同一个坑）：

```kotlin
@Composable
private fun rememberPasskeyRows(state: PasskeysViewModel.UiState): List<PasskeyRow> =
    remember(state.items, state.query) {
        state.items.toPasskeyRows().filter { it.matches(state.query) }
    }
```

同时把纯逻辑抽成 `List<VaultItem>.toPasskeyRows()` + `PasskeyRow.matches(query)`
（**不读 `_state`**），并删掉 ViewModel 里的 `passkeyRows()`（确认只有一个调用点）。

**链路复核**（不能只看 CI 绿）：`state` 由 `collectAsStateWithLifecycle()` 真订阅；
`UiState.items` 由 `itemRepository.observeItems(vaultId).collect` 驱动，解锁后确实会变；
`remember` 的 key 是 `state.items` ⇒ items 一变即重算。**订阅关系补齐了。**

顺带修两个同源问题：把混在一起的空态拆成 `noPasskeysAtAll` 与 `rows.isEmpty()`；
`state.loading` 分支原先配着硬编码 `0` 计数（自相矛盾）⇒ 改 `title = null` + 新增
`passkeys_loading_body`「正在读取通行密钥…」。

**可复用判据**：**界面要用的任何派生数据，都必须从「已收集的 state 快照」算出来。**
排查启发式：**用户描述里出现「要点一下某个无关按钮才出现」，八成就是漏订阅。**

**重写后的判据**（模拟注解作用域，迭代到不动点）：

1. **自证**：函数自己的注解块覆盖了它用到的全部实验性符号；
2. **继承**：有另一个**已合法**的函数**调用了它** ⇒ 合法。

⚠️ 第 2 条是**反向边**（合法性从「调用方」流向「被调方」）——
实现时我**第一次把方向写反了**，是自测把它抓出来的。

**回归验证**：临时删掉三处 `@OptIn` 后，精确报出且**零噪声**：

### 11.5 结论与本轮教训

**收获不是「修了三个弹窗」，而是承认了两次自己的错**：

第一次写 opt-in 检查器按「文本搜索」写错了判据，被自己的回归测试驳回。
两次的纠正方式是同一条：**回到机制本身**（订阅 / 作用域），别用症状的相似性去套旧结论。

**贯穿两轮的结论**：detekt + 三个自检脚本覆盖的都是**语法层**；
**符号解析层**（包是否存在、注解是否齐、API 是否实验性）**只有真实编译器在看**。
每被炸一次就问一句「这条缝能不能用 20 行 Python 补上？」——
能补就补，补不了就**明确写下漏报边界**，别假装覆盖了。

## 12. 快速解锁对话框「毛坯房」重做（第六十七轮 · 沙箱内，未编译未真机）

> 用户原话：「设置里面的密码库设置，快速解锁设置，看起来很廉价，UI不好看，
> 界面看起来像是毛坯房。有没有办法优化的」

### 12.1 归因：是**三个可量化的结构问题**，不是「不够花哨」

逐行比对截图与 `QuickUnlockManageDialog` / `UnlockOptionRow` 代码后定位：

| # | 用户看到的 | 代码根因 |
|---|---|---|
| 1 | 整屏灰蒙蒙、卡片几乎看不出边界 | 🔴 **卡片与面板同色**：`DialogSurface` 面板底 = `surfaceContainerHigh`，`UnlockOptionRow` 也用 `surfaceContainerHigh @ 55%` ⇒ 同色相叠，层级归零 |
| 2 | 徽标写「已启用」，下面副标题**又**写「已启用」 | `QuickUnlockRow` 启用时 summary 传的就是 `quick_unlock_enabled`（"已启用"）⇒ 一行字说两遍 |
| 3 | 「应用内 PIN：已启用（6 位）」很啰嗦 | `pin_enabled_summary` 把**段落标题**（应用内 PIN）与**徽标**（已启用）都复述了一遍 |
| 4 | 按钮散落在右下角、右边一大片空 | 动作区 `Arrangement.End` 右对齐，每卡只有一个词飘着 |
| 5 | 两段之间只靠一条细线、节奏松垮 | `HorizontalDivider` 分隔，段落标题无锚点、间距各自为政 |

**第 1 条是最致命的** —— 它是「毛坯房」三个字的直接来源，且此前**没人意识到**
（前一轮的 KDoc 还写着「把整行包进 Card，行与行之间有了卡片边界」，
但卡片与背景同色 ⇒ 这句话在真机上并未成立）。

### 12.2 改法（全部在既有视觉语言内，**行为零变化**）

1. 🔴 **卡片底改 `surfaceContainerLowest`**（比面板 `surfaceContainerHigh` **低**一档）
   —— M3 容器色阶梯的标准用法：嵌套内容往**低**走，**不是同色叠 alpha**。
   `VaultChoiceRow` 未选中态同样处理（同一个病）。
2. **去重复文案**：`QuickUnlockRow` 启用后副标题**留空**；
   `PinRow` 启用后只留**位数**（新串 `pin_enabled_digits` = "%1$d 位数字"）。
3. **动作区两端对齐**：新增 `RowScope.ActionSpacer()`（`weight(1f)` 占位），
   主操作推到行尾。PIN 行有「关闭 + 修改」两个按钮时**一左一右**，主次立现。
4. **段落标题带图标锚点**：`DialogSectionTitle` 新增 `icon` / `hint` 参数
   （`hint` 并入是为了让"标题 + 说明"整体参与间距计算，避免两处 padding 不等）。
   两段各配 `Fingerprint` / `Pin` 图标，`HorizontalDivider` 移除。
5. **间距走 `Spacing` 标尺**，卡片行距统一 `Spacing.xs`。

### 12.3 保留的既有告诫（**未被本轮推翻**）

- ⚠️ `UnlockOptionRow` **不得退回** `ListItem` + `trailingContent`（宽度窄、按钮会叠字）；
- ⚠️ 未解锁项**不得**给选中标记；
- ⚠️ 「指纹 / 应用内 PIN」**两段式**结构不动（PIN 不需生物识别，无 `canAuthenticate` 门槛）；
- ⚠️ 形态一致性优先：仍是 `BasicAlertDialog`，**不做** `ModalBottomSheet`。

### 12.4 刻意保留的"僵尸串"（新增 2 条，别当垃圾清掉）

- `pin_enabled_summary`（"应用内 PIN：已启用（%1$d 位）"）—— 暂无引用，但若 PIN 行
  日后**脱离「应用内 PIN」段落**单独出现，这句完整口径仍可用；
- `quick_unlock_enabled`（"已启用"）—— 保留同理，已在 strings.xml 就地加注释。

### 12.6 本轮教训（可复用）

- **「加了 Card 就算有层级」是错的** —— 必须核对**卡片底 vs 容器底是否同色**。
  同色叠 alpha 得到的不是"更浅的卡片"，而是"看不见的卡片"。
  判据：**嵌套容器的色阶必须与父容器不同档**（M3 阶梯 `Lowest < Low < Base < High`）。
- **一个元素只该说一件事**：状态归徽标、身份归标题、补充信息归副标题。
  同一行里出现两个说同一件事的元素（徽标"已启用" + 副标题"已启用"），
  观感上就是"廉价"—— 因为它暴露了**没有人在做信息归属的决策**。

## 13. 快速解锁对话框：合并为「一库一卡」（第六十八轮 · 用户拍板）

> 用户原话：「可以合并设置的。做完推送到github」

### 13.1 改了什么

| 维度 | 三改前 | 三改后 |
|---|---|---|
| 分组方式 | **按手段**：指纹段（列全部库）→ 分隔线 → PIN 段（再列全部库） | **按库**：一个库一张卡，卡内两行（指纹 / 应用内 PIN） |
| 段落标题 | 两个（「指纹解锁」「应用内 PIN」） | 一个（「选择要快速解锁的库」作卡组引导语） |
| 行标题 | 库名 | **手段名**（「指纹解锁」「应用内 PIN」），库名升为**卡头** |
| 结构 | `QuickUnlockRow` / `PinRow` 各自持有一张 Card | 新增 `VaultUnlockCard`（持卡），`UnlockOptionRow` 降级为**卡内行** |
| 删除的函数 | — | `QuickUnlockRow` / `PinRow`（职责并入 `VaultUnlockCard`） |

### 13.2 为什么合并是**对的**，且不违反既有告诫

「按手段分组」有两个实测毛病：
1. **同一个库名在屏幕上出现两次** —— 用户读到第二个「Bitwarden」时必须回头确认
   "这是同一个库吗"；
2. 想给某个库同时配指纹 + PIN，要在两段之间**滚动来回找**。

合并的是**分组维度**，不是两种手段本身。
⚠️ `.ai` 里那条「指纹与应用内 PIN 是两条独立路径、不可合成一个『已启用』」
**依然有效** —— 卡内两行各自带独立徽标，正是为了保住这一点。

⚠️ 另一条既有告诫「`UnlockOptionRow` 不得退回 `ListItem`+`trailingContent`」
**同样保留**：卡内两行仍是「图标 + 标题 + 徽标 / 说明 / 动作」的纵向骨架。
新增的 `icon` 槽位（指纹 / PIN）在"卡内两行标题都很短"的场景下，
是区分二者最快的扫读锚点。

### 13.3 一处刻意的视觉选择：卡内用分隔线

`.ai` 里曾写过「段落之间不该用分隔线」（第 12 轮把 `HorizontalDivider` 去掉了）。
本轮**又加回来**，但位置不同、理由也不同：
- 第 12 轮去掉的是**两个段落之间**的线（那里改用图标锚点做分隔）；
- 本轮加的是**同一张卡内两条并列项之间**的线 —— M3 的 list divider 正用于此，
  它说明的是"这是两件独立的事"（PIN 不需要系统认证，与指纹无依赖），
  不用线反而会让两行糊成"一个开关的两个档位"。
