## 7. 用户报的空白页 bug（提交 `c1ff14a`，问题编号 #99）

### 7.1 现象与复现路径

「设置里当前是 Bitwarden，**选择 KDBX 查看、不点「默认」**，返回到密码条目页是空白的，
验证码页也全白，好像加载不出来。只能通过条目页 ⋮ → 切换密码库 → 进登录界面 →
验证生物解锁，才能顺利看到条目。」

### 7.2 根因：三件各自合理的事叠成死局

| # | 环节 | 行为 |
|---|---|---|
| 1 | `ActiveVaultDialog.onSelect` | 对**未解锁**项也无条件 `select(vaultId)` |
| 2 | `ItemRepositoryImpl.observeItems`（KDBX 分支） | `Kdbx.contentOf(id)?.items.orEmpty()` ⇒ 一个**真实的空列表** |
| 3 | `ItemsScreen` 空态 | 空列表 ⇒ 「还没有保存的密码」 |

单看每一步都对；合起来「库锁着」这个**唯一真正的原因**被 `orEmpty()` 抹掉、
又被空态文案替换成假话 ⇒ 用户看到的只有全白。
再叠加 `ItemsViewModel.init` 的**「切库即锁旧库」**（这条策略用户拍板保留）：
切过去的瞬间原来的 Bitwarden 也被锁 ⇒ **两个库都进不去**，
只剩用户自己摸出来的那条生路。

### 7.3 修法（用户拍板的取向：点未解锁的库 → 直接去解锁页）

- `SettingsScreen` 新增 `onOpenLockedVault(vaultId)`，一路透传到 `VaultixApp`
  的 `UnlockRoute(vaultId)`；两个 `SettingsScreen` 调用点（Tab 内嵌 / 独立路由）都接上。
- `ActiveVaultDialog` / `VaultChoiceRow` 改为传整个 `VaultSummary`：
  `unlocked` → 切活跃库；未解锁 → 去解锁页。
- 未解锁行**不再画 `RadioButton`**（单选语义是"现在看哪个"，它不参与），
  改右侧 `KeyboardArrowRight` + 副标题「未解锁 · 点这里输入主密码」。
- 「设为默认」**保持可用**（正当用途：明知要输密码仍想让它冷启动先开），
  但只对已解锁库同步切活跃库。
- **兜底**：条目页 / 验证码页新增「库未解锁」空态 + 「立即解锁」出口。
  正常路径走不到，但能防住同类静默状态（冷启动恢复 / 未来新入口）。

### 7.4 detekt 逼出来的重构

加了兜底分支后门禁立刻报了三处（说明这轮优化本身在压缩代码余量）：

```
ItemsScreen   LongMethod 152 > 150
TotpCodesScreen LongMethod 153 > 150、CyclomaticComplexMethod 15 > 14
```

⇒ 抽出 `ItemsBody`（空态与列表分流）与 `TotpBody`（四处 `when` 分支）。
⚠️ 教训：**用脚本按行号做大段移动会翻车** —— 删了 import 后行号偏移，

## 8. 收尾：CI 盲区（#100）+ 一个可复用自检脚本（同日追加）

### 8.1 我想"补一次编译验证"，结果撞出一个从未跑过的门禁

推送文档提交后收到 CI 通知，我想着"顺手确认一下"，于是手工触发了一次
`gh workflow run ci-debug.yml`。**这是我第一次用非 push 方式触发这个工作流**，
结果：**`Run lint` 步骤失败，后面 detekt / 编码检查 / Build Debug APK 全部 skipped**，
而这次改动**只是两个 .md**。

查下去发现的原因（见 `issues/01-构建与环境.md` **#100**）：

- lint 步骤带 `if: github.event_name != 'push'` ⇒ **push 链路永远跳过**；
- 本仓库最近 50 次 CI 运行**全是 push** ⇒ 这条步骤**是第一次真正执行**；
- 即：**「push 全绿」这个结论里从来不包含 lint**，这道门**从未被验证过**。

⇒ 这是**盲区**，不是我这轮的回归。但它有两个直接后果：
① 我不能再拿"CI 全绿"当作完整门禁证据（必须说明是哪条链路）；
② lint 一失败就把它后面三条真门禁全 skip 掉 —— 所以先给它加
`continue-on-error: true` **止血**（只报告、不阻断）。

**刻意不做的事**：不删 `if`、不放宽 lint 规则、不压代码。
因为**失败原因还没取证**：可能是「`setup-gradle` 固定的 Gradle 8.11.1 与 AGP 9.3.2
不兼容」，也可能是真有 lint 违例 —— 两者处置完全相反。
沙箱**拿不到 job 原始日志**（`.../logs` 302 到 `blob.core.windows.net`，沙箱不可达，下载 0 字节），
所以留了替代手段在 #100 里（check-run annotations 最有用）。

> 顺带发现：`ci-debug.yml` 把 Gradle 固定为 **8.11.1**，而仓库 wrapper 是 **9.5.1**。
> push 链路的 `./gradlew` 走 wrapper（9.5.1）所以能过；`setup-gradle` 那个 8.11.1
> 只影响它自己的 Gradle 命令。**待确认**这一项是否就是 lint 失败的原因。

### 8.2 把上一轮的教训做成了脚本：`.ai/tools/check_signature_types.py`

上一轮我因为**凭记忆写错类型名**（`ItemGroup` / `ItemsDisplayMode`，真名是
`ItemsGroup` / `ItemsCardDisplayMode`）把 CI 编译搞红，当时说"这类错误本可以本地一次揪出"。
这轮把它真的写出来了。

**它做什么**：扫 `app/src/main/java` 建「全仓库顶层类型定义」表（230 个），
再解析每个函数/Composable **参数列表**里的类型名，检查它是否
「有 import ／ 同包有定义 ／ 是 Kotlin 默认可见类型 ／ 是泛型参数」，
不满足就报出来（含行号与出处）。

**开发它本身踩了三个坑**（都修了，源码注释里写明了原因）：

| 坑 | 现象 | 修法 |
|---|---|---|
| 朴素正则 `标识符 : 类型` 扫整个参数串 | **22 处误报**：`ThemeMode = ThemeMode.SYSTEM` 里的 `SYSTEM`、`String = "Vaultix"` 里的 `Vaultix` 都当成了类型 | 先按**顶层逗号**切参数段，每段只取**第一个 `=` 之前**的部分 |
| 没剥注释 | **29 处误报**：KDoc 里写的 `fun foo(...)` **示例**被当成真定义（本仓库注释密度高，极易中招） | 先做 `strip_comments_and_strings()`（等长空白替换、**保留换行**，行号不错位） |
| 全限定名/嵌套类当成未知 | `android.content.Context` / `PasswordStrength.Level` 被报 | 全限定名整段跳过；嵌套类只查**最左边那段** |

**关键验证（不是"跑通就算"）**：我把当时那个真实错误**注入回去**
（`items Group: List<ItemGroup>`），脚本精确报出 5 处、退出码 1；
恢复后全仓库 158 个文件 **0 报**。⇒ 它是**能抓到目标缺陷**的，不是空转的。

**用法**：`python3 .ai/tools/check_signature_types.py`（默认查最近提交的改动）
`--all`（全仓库）/ 显式传文件名。**抽/改函数签名后跑一遍。**

**`Run lint` 报 `success`**，且 detekt / 编码 / Build Debug APK / 单测**全部真的跑起来了**。

⇒ 所以 8.1 里「这道门从未被验证过」这个说法**下早了**，得改成：
- ✅ **lint 步骤可用**（既能跑又能通过）；
- ❌ 非 push 链路真正的问题是 **`Collect debug APK metadata`**：
  它带 `if: github.event_name == 'push' && ref == 'refs/heads/main'`，
  而**非 push 时会被 skip** ⇒ 于是它内部 `apk_count == 0` 的 `exit 1` 不触发；
  但**同时命中了代码检查 + workflow 自身变更**那条路径时，链条顺序不同，就会在
  lint 之后才炸 —— **与 lint 无关**。
- ❓ 仍未定性：`ci-debug.yml` 固定 Gradle **8.11.1** 而 wrapper 是 **9.5.1**。

**这次真正该记住的教训**：**别急着给"第一次执行就失败的步骤"定罪。**
先隔离（让后续步骤能跑起来），再判断失败者是谁 ——
我差点就顺着"lint 从未验证过"的叙事去动 lint 配置，**那是在改错东西**。
**push 链路的 `Run lint` 恒为 `skipped` 这个事实不变**，
所以「CI 全绿要问是哪条链路的绿」这条纪律**依然成立**。

### 9.2 解锁页 PIN 键盘下移

**根因**：`UnlockScreen` 主列恒 `verticalArrangement = Arrangement.Center`，
整列（头像 64 + 库名 + 账号 + 圆点 + 4×76dp 按键 + 出口 ≈ 520dp）在可用高度里居中
⇒ 键盘落屏幕中部偏上，拇指够不到。

**关键约束**：外层有 `verticalScroll`（小屏 / 横屏必须能滚）⇒ 给子项的是**无界高度**：
- `weight(1f)` 要求有界 ⇒ 直接抛 `IllegalStateException`；
- `Arrangement.Bottom` 只在内容**低于**容器时才推到底，内容一超高就退化成 `Top`
  ⇒ 小屏键盘被推出屏幕（要滚动才够得着，比居中更糟）。

**解法**：顶对齐 + 反推让位。

```
让位 = 屏高 − 顶部信息区高 − 键盘高 − 换库按钮高 − 底距
```

**⚠️ 第一版我写错了**：用「屏高 × 0.35」当目标值。键盘自身就 400dp，
任何 < 0.5 的比例都算出负数 ⇒ **让位恒为 0，等于没改**。
是**写成公式后代入真实尺寸验算**（600/640/720/800/891/915 六档）才发现的。
最终键盘底从改前的 **57%~82%** 稳定落到 **88%~92%**，零溢出。

⚠️ 第二版又漏了「换一个库」按钮的高度：它挂在键盘下方，漏算把整列顶出屏幕，
**唯一的多库出口要滚动才看得见**（多库用户冷启动卡在解锁页时那是唯一出路）。
⇒ 把它算进让位，并让显示条件与 `switchVisible` 同源（两处漂移就会"算进去了却没显示"）。

⚠️ detekt 实测拦了一次：我加的 `if (state.pinMode)` 正好是压垮
`CyclomaticComplexMethod` 的第 15 个分支（上限 14）。⇒ 把「排列方式 + 让位」
折进 `unlockColumnLayout()` 一次返回（`UnlockColumnLayout` 数据类），
主函数里只剩一次解构赋值，零新增分支。

### 9.3 设置页「密码库管理」合并为二级页

⚠️ **与定稿的关系**：`.ai/decisions/设置页信息架构-定稿.md` §3 曾把快速解锁定在
