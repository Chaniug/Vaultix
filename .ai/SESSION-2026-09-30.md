### 2.3 ★ 修一个真实线上 bug（`ISSUES.md` **#135**）

写 W0 的 keyfile 用例时它红了，且红法**自相矛盾**（只给主密码开不了=对；
密码+原样同一份 keyfile 也开不了=错）⇒ 只能是"同一份字节在两次使用之间变了"。
诊断坐实：kotpass 的 `EncryptedValue.fromBinary` **原地 XOR 改写调用方数组**，
而 `parseKeyfile(32 字节)` 是"原样返回同一引用"。

**真实受害点** `LocalUnlockEnrollment`：`readBytes → Kdbx.verify`（改写在此时）
`→ 用同一份数组组装快速解锁信封` ⇒ **带 keyfile 的库启用快速解锁后，指纹再也开不了它**。

修法：只修**唯一那个边界**（`buildCredentialCandidates` 开头 copy，覆盖 unlock/verify
两条入口）+ 新建路径同理；两条回归用例（含"同一份字节连用两次都要成功"）。
★ 判据：**交给第三方库的密钥/凭据字节先 copy**；**同一份密钥被复用两次的流程必须有一条
"连用两次"的用例** —— 只测一次成功永远发现不了这类缺陷。

### 2.4 用户四项 UI 反馈（均已落地）

| 反馈 | 做法 | 关键判据 |
|---|---|---|
| 条目详情要显示**创建 / 最近修改** | BW 侧 `CipherDto` **根本没声明 `creationDate`**（被 `ignoreUnknownKeys` 静默丢弃）；KDBX 侧整块没读 `<Times>` ⇒ 两侧补齐 + 详情页新增「记录」分区 | ★ `lastAccessTime` **不映射**（语义是"上次查看"，上游每次改条目都刷新它 ⇒ 当"最近修改"会每次点开都在变）；取不到时 **null 且不显示该行**（兜"现在"/1970 = 假信息）；格式化必须带本地时区 |
| 条目页加**库状态**（域名 / 路径 + 条目数） | 口径集中在 `ui/common/VaultOriginLabel.kt`：BW → **域名**（保留端口、去 scheme 与路径）；KDBX → 本地文件 / OneDrive 路径 / WebDAV 主机+路径 | **未解锁时不给数字**（条目数不可知，显示 0 就是把"不知道"说成"没有"） |
| ⋮ 菜单**平铺不好看** | 用户选定**方案 B**：顶部当前库卡片 + 按「前往 / 操作」分组 | 平铺的毛病不在"不好看"，而在**四种性质不同的东西混在一起**（换上下文 / 去另一页 / 对库做动作 / 破坏性动作） |
| 左侧标题**超长 + 变大变小** | 旧代码在 `onTextLayout` 里发现溢出就改 state 缩一档、下一帧再量再缩 ⇒ **必然先按满字号画一帧再变小**。改成**组合期一次算好**（`BoxWithConstraints` + `rememberTextMeasurer`），同一帧内定字号 | ★ **"布局后回调改状态"= 必然的视觉跳变**，挪到组合期计算即可根除；兜底 `overflow` 由 `Clip` 改 `Ellipsis` |

长文本的两条规则（**不缩字号**：它是常驻信息，缩字号等于每一眼都在付代价，且小屏缩得最狠）：
**来源走中间省略**（路径头尾最关键、中间目录最不重要；尾部省略会先吃掉"打开的是哪个库"）；
**条目数不参与压缩**（它是这一行的锚点）。菜单卡片里则 `maxLines = 2` **给全** —— 同数据、两种密度。

★ **踩到的 KDoc 坑**：写 `**旧缓存**/旧测试…` ⇒ 粗体闭合的 `**` 紧跟 `/` 构成 **`*/`，
把 KDoc **提前闭合**，后面的中文被当代码解析（报一串 "Expecting a top level declaration"）。
**写 KDoc 时别让粗体紧接斜杠。**

### 2.5 KDBX 阶段 B：W0（部分）→ W1 → W2 → W3

- **只认 4.x（单子 §2.6 = B）**：`KdbxFormat.SUPPORTED_MAJOR` 3 → 4；拒绝文案**唯一化**
  （抽出 `KdbxOpenError.UnsupportedVersion.guidance`）—— 原两处已漂，其中一处还把用户引向
  **刚被拒**的 3.1。不做 `Ver3x→Ver4x` 转换（理由写进代码）。
- **W0 数据层**：`KdbxCreator.createEmpty` + `Kdbx.createVault`。格式选型**逐字节反编译核实**
  = KDBX **4.1** + AES-256 + GZip + Argon2（正是 XC/DX 通用组合）。建库顺手登记会话
  （省一次 Argon2 + 避免"写的凭据≠读的凭据"）；建库即建回收站组。
- **W1 `KdbxItemWriter`**：只覆盖**领域模型承载的字段**，其余交给 `copy` 原样带过
  （`KPEX_*` / 未知自定义字段 / 附件 / 历史）。**禁止"从领域模型重建 Entry"**。
  三个出事点：未变更的字段不重写（TOTP）/ `moveEntry` 是"先删后加"（目标组不存在会**静默丢条目**）
  / 改条目走 `withHistory`。
- **W2 数据层**：`Kdbx.createItem/updateItem/moveItemToRecycleBin/restoreItemFromRecycleBin/purgeItem`
  → `Result<KdbxPendingWrite>`（**公开签名不含 `KeePassDatabase`**，#64 引擎不外泄）。
- **W2 接线 + W3 放闸**：新 `KdbxItemRepository`（本地 SAF 直接写文件；网盘写本地缓存 + 标记待上传）。
  **#106 收口**：五个写方法各自先分流，Room 侧**一个字节都不碰**（用例逐条 `coVerify(exactly = 0)` 钉住），
  UI 的只读闸全部撤掉。

★ **两个测试逼出来的真问题**：
① `OTP_FIELD_NAMES` 是**小写**集合而 `EntryFields.minus` 是**精确匹配** ⇒ 拿它减
`TimeOtp-Secret-Hex` 一个都减不掉（两条测试直接红）。
② **上游 `getGroupBy` 会返回 null，即使谓词对根组恒真、且该组确实是根的直接子项**
（探针实测 `groups.any{}=true` 而 `getGroupBy{}=false`；源码与字节码看着都对）⇒ 不再用它做

★ 判据：**第三方 API 行为与源码不一致时以行为为准；"找不到就返回 null"这种静默失败签名
不能用于数据安全判断**。
