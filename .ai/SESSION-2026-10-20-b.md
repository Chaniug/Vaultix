## 二、真正修掉的三条

### #178 `Kdbx.mutate` 读-改-写不原子 ⇒ 并发编辑静默丢一笔

- **形状**：`KdbxSessionStore.get → 改 → put`，底层是 `ConcurrentHashMap`。
  它只保证**单次 map 操作**安全，不保证这三步合起来原子。
- **为什么本项目真会撞**：五个写入口都在 `Dispatchers.IO`；`KdbxAutoUploader` 自带
  `Dispatchers.IO` 的 scope，上传时 `saveVia` 读同一个 `session.database`。
- **修法**：每库一把 `Mutex`（`writeLocks` + `lockOf`），`mutate` 与 `replaceSession` 共用。
  不用 `synchronized`（临界区有挂起点）；**不**把网络/文件 IO 纳入（会让"上传时保存"卡十几秒，
  那边的正确性由 `expectedVersion` 条件写保证）。

### #179 `writeLocks` 只增不减

- `getOrPut` 建的锁永不释放，而 `removeVault` / `signOut` 都会 `Kdbx.lock(vaultId)`
  却只 `close` 会话。
- **修法**：`lock` / `lockAll` 一并 `remove` / `clear`。⚠️ **顺序**：先 `close` 会话再丢锁。
- **安全性**：等待中的 `Mutex` 被 `remove` 安全（等待者握对象引用不是 map 键）；
  且会话已丢弃 ⇒ `mutateLocked` 直接返回 `NotUnlocked`，不会出现"两把锁同时放行两笔写"。

### #180 `resolveUsingRemote` 下载窗口覆盖本地编辑

- **形状**：`判本地没改 → stat → read(1–10 s)` → `replaceSession` 整体替换 → `markResolved(IN_SYNC)`。
  窗口内的编辑被抹掉，且**再也不会重试**。
- **修法**：`read()` **之前**用最新 `syncStatus` 再判一次 `localChangedSinceLastSync`，
  有改动就返回 `Conflict` 且不下载。
- **两个"不要"**：① 不要用 `markDeferred`（只在已 CONFLICT 时生效，用在这里等于没做）；
  ② 不要把本地改动改写成 `CONFLICT`（伪报"两边都改了"，把用户推向真丢数据的选项）。

## 三、验证纪律（本轮实际做了什么）

每一条都做了**变异验证**，不是"跑绿就算"：

| Bug | 正例 | 反证 | 撤掉修复 |
|---|---|---|---|
| #178 | 并发两线程各改一条，两笔都必须留 | 用**线程**不用协程（`runBlocking` 是单线程事件循环，撞不进窗口） | 5/5 红（`missing (1): 改乙`） |
| #179 | 写一次后计数 > 0 → `lock` 后 == 0 | 反证在**同一用例内**（先证明装置能观测到"有"） | 该用例红 |
| #180 | `coVerify(exactly = 0) { source.read() }` + 不替换会话 | 独立用例：本地没改时必须 read 1 次、替换 1 次 | 正例红、反证仍绿 |

⚠️ 踩到的两个坑：
1. **`read()` 是 `suspend`** ⇒ 必须 `coEvery` / `coVerify`（写成 `every` / `verify` 报
   "Suspension functions can only be called within coroutine body"，位置指向 mockk 块首行，很容易误判成 `coEvery` 用错了）。
2. **反证用例先红在"桩不够"**：`markResolved` 会调 `dao.updateSyncState`，
   没打桩就抛 `MockKException`。但那条报错恰恰证明**它真的走到了 `read()` 与 `replaceSession`**
   —— 于是把 `dao` 改成 `relaxed = true`，只显式钉 `get`。
