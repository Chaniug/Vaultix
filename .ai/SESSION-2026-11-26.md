## #308 填充响应组装切回主线程

**用户指令**：`现在就修并出 preview 验证`；随后追问 `修复后会影响现在的填充吗`。

**起因**：Edge 全链路日志里夹系统警告
`AutofillValue: forText() not called on main thread: Thread[DefaultDispatcher-worker-7,5,main]`。
Edge 上填充、passkey 全部正常，功能未坏。

**根因**：`VaultixAutofillService.scope` 用 `Dispatchers.Default`，`buildResponse()` 整条链
（含 `AutofillValue.forText()` / `Dataset.Builder` / `FillResponse.Builder`）都在后台线程。
framework 契约要求这些 Parcelable 在主线程构造；国产 OEM 的 RemoteViews / Parcelable 实现
差异更大，有偶发填充 UI 异常风险。

**修法（只动线程归属，不动填充语义）**：

| 文件 | 改动 |
|---|---|
| `AutofillDatasets.kt` | 新增 `IconSource`（`FromUrl` / `Ready` / `None`），`build()` 参数维持 8 个过 detekt |
| `AutofillDatasetFactory.kt` | `prepareIcon()` 后台预生成位图；`datasetFor()` 加可选 `icon`（null = 旧行为） |
| `VaultixAutofillService.kt` | 图标先后台算，三条分支（正常 / 锁定 / 无匹配）组装全部 `withContext(Dispatchers.Main)` |

曾误把 `totpTickets` 写成 `null`（会断掉验证码复制），当场改回 `totpTickets`，并在 `.ai`
里留痕——这是本轮唯一一处差点造成的真实回归。

**风险评估（回应用户追问）**：候选匹配、字段映射、认证意图、SaveInfo、TOTP 票据、header
全部沿用原实现；图标在后台先算好，主线程零磁盘 I/O；三条分支全覆盖。预期填充行为不变，
只消掉系统警告。

**门禁**：新增 `.ai/tools/check_autofill_main_thread.py`（剥注释，3 判据 + 4 组变异自测）。
TDD 旧实现在 B 判据红灯，改完转绿；`--selftest` 4/4、`check` 实跑通过。
⚠️ 本轮一度**写完门禁却漏接 CI**，后补进 `ci-debug.yml` 两步（与 #305/#306 同训：

## 线程 / 调度审计（回应用户「快、稳、准、省」，待量化后立项）

**方法**：静态通读 `onFillRequest → buildResponse` 关键路径。不臆测耗时，只标记可测量项。
**结论先行**：#308 只解决「稳」；「准」与调度无关；「快 / 省」要先埋点再动手。

| 优先级 | 发现 | 证据 | 建议 | 风险 |
|---|---|---|---|---|
| P0-快 | `refreshIfStale()` 内联在填充关键路径 | `FillAssistRepository:59` 是 `withContext(IO)` 的**挂起等待**；6h 到期会同步跑两次 OkHttp（manifest + 最多 25KB forms）。用户点密码框时等网络，OkHttp 默认超时可达秒级 | 移出关键路径：进程空闲时预刷新 / 改成「发起即返回」，失败照旧静默退化 | 低——规则只是增益，晚到不影响填充正确性 |
| P1-省 | 图标每次新建 Bitmap | `createAutofillItemIcon()` 每次 `decodeFile` + `createBitmap` + 画圆；10 条 = 10 次磁盘读 + 10 个位图，还经 Binder 传给系统 | 按 `iconUrl ?: title+category` 加小 LRU（如 32），观感不变 | 低——不改图标形态 |
| P1-快 | 冷启动空等 `AUTO_RESTORE_WAIT_MS=1000` | `VaultixAutofillService:279` 无条件等 1 秒自动恢复 | 只在「确实在恢复中」时才等；或缩短 + 复查。**不能一刀切砍**（那是「稳」的取舍） | 中——改错会重新打扰用户解锁 |
| P2-快 | 全量候选映射 | `collectCandidates():58` 对全部条目 `toCredential()`；日志里 `candidates=212` 是匹配前的准备量 | 若埋点证实这里慢，再考虑域名索引缓存 | 高——是「准」的基础，排最后 |
| — 准 | 字段分类 / URI 匹配 | 与调度无关，已对齐 Bitwarden | **不在本审计优化范围** | — |

**立项前置**：加 debug 埋点 `parseMs / candidatesMs / matchMs / iconMs / assembleMs / totalMs`
（无 text、仅元数据），拿真机数字后再决定动哪几项。否则就是 #307 式「诊断加错层级」的白费。
