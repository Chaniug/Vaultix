## 2. 五组 UI 改动（承接 09-16 用户诉求）

用户原话：「我想在这些页面好看一点，不用那么理性和克制」
「弹出的密码条目框好像密码条目显示效果不太好，偏大了」
「按住条目的时候，出现全选的设置，我感觉全选的没必要吧…被底部栏遮住了。所以看不到，也点击不到」
「新建条目的内容里面，上边和下边不是透明的啊…之前是全屏的，沉浸的」

### 2.1 填充建议条目行收窄（`5017029`）

**根因**：填充面板走 **RemoteViews**（`autofill_dataset_item.xml`），而条目行尺寸照
Material 3 列表项规格定（40dp 图标容器 / 16sp 标题 / 16dp 内边距）——
那套规格是按 **360dp+ 的整页宽度**设计的，而填充面板只有约 **240dp** 宽，
同样的绝对尺寸在窄栏里视觉占比被放大 ⇒ 显得臃肿。
⇒ 按窄栏重定：图标 40→32dp、位图 34→26dp、左右内边距 16→12dp、字号 16/14→15/13sp、minHeight 56→52dp。
⚠️ `AutofillItemIcon.ICON_DP` 必须同步（位图尺寸由代码侧决定，与布局里的容器必须一致）。

### 2.2 卡片质感统一（`8654e62`）

- 圆角 `CARD_CORNER` 12dp → **16dp**：**有意偏离**上游 Bastion 的「稀疏列表卡片 = 12dp」。
  12dp 在列表里偏方正显平；16dp 与设置页卡片（20dp）更接近，观感更柔和成套。
- 条目卡片与详情页 `DetailCard` 各加 **0.5dp `outlineVariant` 描边**。
  **原因（可复用）**：M3 filled card 的底色与页面背景明度差本就小，在**动态取色**下更不可靠
  （底色由壁纸派生，可能恰好贴近背景）⇒ 卡片边界只能靠"猜"。描边把边界**说死**，
  且不吃底色、不与动态取色打架 —— 比反复调底色稳。
- 改动落在共用的 `EntryCard` 上 ⇒ 密码 / 验证码 / 卡包三个列表同时生效。

### 2.3 表单改分组卡片（`be8b15e`）

旧方案是一条极淡的 `HorizontalDivider`，它当时的注释写着取舍理由「不像卡片那样需要猜底色」
—— 那是**保守**的选择；用户看过实际效果后明确要求放松克制 ⇒ 把当初排除的卡片方案捡回来。

卡片比分隔线多给三样东西：**边界**（哪里是一个组）、**底色**（组的范围可见）、
**呼吸**（组内紧凑、组间留白）⇒ 结构能一眼读出来。拆成 4 张卡：

1. 基本信息（文件夹 / 类型 / 名称）
2. 类型专属字段（Login / Card / Identity / SshKey）
3. 附加内容（自定义字段 + 备注）
4. 安全选项（主密码二次验证）

⚠️ 第 4 张单独成卡：它回答的是「这个条目**怎么被保护**」，与上面「填了什么内容」不是一回事，
混在一起会让卡的标题失去意义。
⚠️ 底色取 `surfaceContainerLow`，比宿主面板 `surfaceContainerHigh` **低一档** ——
同色相叠会让卡片边界消失（`VaultUnlockCard` 已踩过此坑）。
⚠️ `SecureNote` 分支返回 `Unit`（该类型本就没有专属字段）—— 否则留一张空卡。
⚠️ 类型分支写成**单个 `when`** 而非「先 `if` 再 `when`」：`ItemFormDialog` 的圈复杂度本就顶在
detekt 上限 14，多一个分支就红，用 `when` 聚拢可保持分支数不变。

### 2.4 沉浸外壳（`5b4b41c`）

**排查结论：不是回归。** 此前那次「整页全屏」只做了一半 —— 窗口确实变全屏了
（`decorFitsSystemWindows = false`），但内容层是标题栏 / 正文 / 底部条三者**平铺**
（`Column` + `weight`），从第一天起就没有穿越效果，所以"全屏"体现不出来。

改法：`Column` → `Box` **叠加**。正文铺满并 `verticalScroll`，标题栏与底部条各
`align(TopCenter/BottomCenter)` 叠在最上层、背景为不透明的 `surface` ⇒ 内容从其下方滑过。

⚠️ 正文仍要预留两条的高度（`padding top = TITLE_BAR_HEIGHT` / `bottom = ACTION_BAR_HEIGHT`）：
标题栏与底部条是不透明的（否则内容与按钮叠在一起看不清），内容不预留就会钻到按钮底下。
⚠️ 高度用**常量**（56dp / 80dp）而非 `onGloballyPositioned` 实测：后者首次组合拿不到值，
会先按 0 让位、再跳一次 —— 那一跳比"数值不精确"更难看。

### 2.5 多选操作栏（`5b9ff76`）

**① 摘除「全选」**：密码管理器里批量全选后能做的事只有「删除」，而"全选 + 删除"恰是最危险的
组合（误触一次即整库清空）；真要全选，逐条点的成本远低于误删的代价。
⇒ 摘掉按钮，`selectedCount` 的展示保留。
⇒ `strings.xml` 里的 `action_select_all` **刻意保留但补注释**：它是通用动作词，
日后别处（如导入时选中全部）可直接复用，别当僵尸串删掉。

**② 修复被 Dock 遮挡（真 bug）**：根因是悬浮胶囊底栏（`VaultixBottomDock`）**叠层**画的
—— `AdaptiveMainScaffold` 刻意不走 `Scaffold.bottomBar`，内容一直铺到屏幕底。
所以**页面自己的 `bottomBar` 会落在 Dock 底下**：主 Tab 页（密码条目 / 验证码）里这条操作栏
看不见也点不到，而二级页（通行密钥，无 Dock）却正常 —— 用户反馈的正是这个差异。
本组件原先的注释写着「直接在页面 `Scaffold.bottomBar` 内渲染，省掉跨层回调」——
**省掉的那层跨层正是这个 bug 的来源**（上游 Bastion 是上抛给宿主统一渲染的）。
⇒ 新增 `dockInset` 参数，由调用方告知"我下面有多少被 Dock 占掉"。
⚠️ 让位写在**内容 padding** 里而不是外挂 `Spacer`（本项目 #76「让位必须写在 contentPadding 里」）。

## 3. ★★ KDBX 写入口止血（`ISSUES.md` #106）

### 3.1 怎么发现的

**不是用户报的** —— 是排查「OneDrive / WebDAV 网盘同步」的前置条件时，
顺着「KDBX 到底能不能写」这条线查出来的。

### 3.2 根因：读路径分流了 KDBX，写路径没有

| 环节 | 位置 | 修前现状 |
|---|---|---|
| 读 | `ItemRepositoryImpl.observeItems` | `kind == KDBX ⇒ Kdbx.contentOf(vaultId)?.items.orEmpty()`（**内存，不在 Room**） |
| 写 | `createItem` | **无任何 kind 判断**，无条件 `atomicWriteDao.upsertCipherAndEnqueue(...)` ⇒ 写出 **Room 孤儿行** |
| 写 | `updateItem` | 先 `cipherDao.get(item.id) ?: error("条目不存在")`；KDBX 条目 id 是 `KdbxItemMapper.itemIdOf(uuid)`（:108），**不在 Room** ⇒ 直接抛错 |

⇒ **一隐一显，两个方向都在骗人**：新建 = **静默丢失**（写进 Room，读侧永远看不到，
用户以为存上了）；编辑 = **报出与真实原因无关的错**（「条目不存在」）。
`app` 层对 `VaultKind` 只用于**徽标 / 解锁路由**，全局 grep `canEdit`/`isEditable`/`readOnly`
**无任何 KDBX 命中** ⇒ UI 也没拦。

**危害边界（已查证）**：`flushAfterLocalWrite` 对非 Bitwarden 库不入队推送（`server = null`）
⇒ **不会外泄**，损害限于本地多一条幽灵行。

### 3.3 修法

1. **`domain` 新增 `ReadOnlyVaultException`**：业务层拒绝，`message` 直接给用户看；
   `vaultId` 只作**诊断字段**、刻意不拼进 `message`（UUID 对用户没有意义）。
   用异常而不是给 `VaultSaveOutcome` 加常量：数据层已有同一惯例
   （`error("条目不存在")` / `require(existing.vaultId == vaultId)`），
   且能**零改动**复用现有 `onFailure { error.message }` 链路。
2. **`ItemRepositoryImpl.requireWritable(vaultId)`**，**8 个写方法**各自在 `runCatching` 首行调用：
   `create` / `update` / `softDelete` / `restore` / `permanentDelete` / `cleanupExpiredTrash` /
   `updateFido2Credentials` / `removeFido2Credential`。
   - 闸放在 `runCatching` **内部** ⇒ `Result` 语义与其它业务拒绝完全一致，3 个消费点零改动。
   - **每次现查** `vaultDao.get` 而不是缓存 kind：与读路径「每次订阅重新解析种类」同一取向，
     不引入第二份真相源（缓存过期就会漏闸）。
   - `cleanupExpiredTrash` **也必须拦**：若历史上残留孤儿行，它会查到并给 KDBX 库入队 DELETE
     ⇒ 队列里躺下**永不推送的毒丸**（`flushAfterLocalWrite` 恒返回 `Queued`，没人消费它）。
   - `removeFido2Credential` **单独拦**：否则会先走 `loadItem`（查 Room）而报出
     「条目不存在」这个与真实原因无关的错误。
3. **UI 收起写入口**（不让用户白填一场再被拒）：
   - 详情页 `ItemDetailViewModel` 暴露 `readOnly` ⇒ 收起编辑/删除按钮；
   - 条目页隐藏新建 FAB，并把底部栏「+」的请求拦成 snackbar 提示。
4. **单测**：新增 `writeToKdbxVault_rejectedAndNothingWritten` ——
   锁死「返回 `ReadOnlyVaultException`」+「**一个字节都没落**」（行、队列都不许动），
   后者才是"没有幽灵数据"的真正判据。

### 3.4 判据（写进纪律）

> **读路径按 `kind` 分流了，写路径就必须同时分流。**
> 否则「读 A 存储、写 B 存储」必然产生幽灵数据，且**两个方向都骗人**：
> 新建静默、编辑报错，用户无法从任何一条错误信息推出真实原因。
> **新增任何 `kind ==` 分支时，读/写两侧成对检查。**

## 6. ★ 三条新纪律（都值得记住，代价已经付过）

### 6.1 「任务 UP-TO-DATE」≠「那段代码是好的」

本轮跑 `test` 时炸出 `data:repository` 的单测**编译**错误：
`ItemRepositoryImplTest` 缺 `atomicWriteDao`（由 `d17772b` 加进构造函数）、

已用 `git diff --name-only` 举证）。之所以一直没暴露：那些提交**只跑了 `:app:` 的编译、
没跑 `test`**，而 `:data:repository:compileDebugUnitTestKotlin` 一直是 **UP-TO-DATE**
⇒ 从未被重新编译。本轮改 `ItemRepositoryImpl.kt` 让它失效、重跑，才抖出来。

> ★ **纪律：门禁必须包含 `test`，不能只跑 `compile`。**
> 一个任务只要输入没变过就永远不检查 —— 改了某模块的**生产代码**后，
> 它的**测试编译**才会失效，那时才暴露积压的断链。

### 6.2 给 mock 补桩时要「转发」而不是「mock 掉」

`ItemRepositoryImplTest` 需要 `atomicWriteDao`。**直接 mock 掉
`upsertCipherAndEnqueue` 是错的** —— 那样行不会真落库，
所有「写完再读回来」的断言会一起失效。正解是**匿名子类只转发**：

```kotlin
atomicWriteDao = object : AtomicWriteDao() {
    override suspend fun upsertCipher(row: CipherEntity) = cipherDao.upsertAll(listOf(row))
    override suspend fun upsertPendingOp(op: PendingOpEntity) = pendingOpDao.enqueue(op)
}
```
`@Transaction` 的实体编排照旧执行、两个 `protected` 落点转发到 mock ⇒
原有 `coVerify { cipherDao.upsertAll(...) }` **依然成立**。
（`AtomicWriteDao` 是 `abstract class` 且 `upsertCipherAndEnqueue` **有实体**，所以可行。）

### 6.3 加写闸会改变测试的隐含前提

`requireWritable` 会调**挂起的** `vaultDao.get(vaultId)`。严格 mockk 未打桩 ⇒ 抛
`MockKException` ⇒ 被 `runCatching` 吞掉、**替换掉真正的失败消息**
（`updateItem_serverTypeUnknown_rejectedWithoutWrite` 因此挂掉：它要的是「编辑暂不支持」）。
⇒ **在 `setUp` 里补 `coEvery { vaultDao.get(vaultId) } returns <row>`。**

### 6.4 附：bash 双引号里的反引号会被**命令替换**

写提交信息时用了 `` -m "... 写成 `when` 而非 ..." ``，bash 把 `` `when` `` 当命令执行，
**提交信息里那两处变成空白**，而提交照样 `exit 0` ⇒ 不核验就发现不了。
- **修法**：commit message 里**不要用反引号**；或用 `git commit -F <文件>`。
- ⚠️ `git commit -F` 的路径：**`/c/Users/...` 会被 Windows 版 git 拒绝**
  （`fatal: could not read log file`）—— 必须传 **`C:/Users/...`**。
  与 `adb pull` / `keytool -keystore` 是同一个坑。

### 10.2 数据安全的三道防线（用户硬要求的落点）

> 用户原话（方案 §12）：「**同步不丢，数据不错不漏，同步下来的不损坏不错漏**」

1. **写前往返自检**（`KdbxRoundTrip`）：编码后的字节**立刻用原凭据解回来**，
   比对条目数与关键字段。不自洽就**一个字节都不落盘**。
2. **原子替换 + 备份**（`KdbxAtomicWriter`）：临时文件 → rename，先备份
   `.kdbx.bak` 再动 target。SAF 没有可靠的 rename ⇒ 保障放在**编码层**。
3. **服务端条件写**（`If-Match` / `If-None-Match: *`）：判定权交给服务端，
   客户端「先查再写」的 TOCTOU 窗口因此**不构成风险**。

### 10.3 ★ 本轮踩到并记牢的五个坑

#### ① 🔴 门禁有两种口径，跑错等于没跑

CI 用 `./gradlew detekt`，而根 `build.gradle.kts` 设了
`buildUponDefaultConfig.set(true)` ⇒ **本地必须加 `--build-upon-default-config`**，
否则默认规则（`ThrowsCount` / `CyclomaticComplexMethod` / `MaxLineLength` /
`SwallowedException` / `MatchingDeclarationName` / `MagicNumber` /
`LoopWithTooManyJumpStatements` / `UnusedParameter`）**全不生效**。
我按「仅本项目配置」跑出 **0 findings 的假绿**，CI 上同一批文件报出 **22 处**。

CLI 跑法（jar 名是 `-all.jar`，`--input` 用**冒号**分隔）：
```bash
java -jar /workspace/detekt-cli-2.0.0-alpha.6/lib/detekt-cli-2.0.0-alpha.6-all.jar \
  --build-upon-default-config --config config/detekt/detekt.yml --jvm-target 17 \
  --input "<file1>:<file2>"
```
**修法一律是「拆出纯函数」，不是放宽阈值**（阈值是 `Docs/16` 定的硬上限）：
- `ThrowsCount`（上限 2）⇒ `writeFailureOf` / `sessionFailureOf`：
  **状态码 ⇒ 该抛的异常**的纯映射函数（自己不抛），调用点只抛一次。
- `CyclomaticComplexMethod`（上限 14）⇒ `precheckVersion` / `conditionalHeader` /
  `writeActionLabel` / `classifyWriteResponse` 从 `writeConditionally` 里拆出。
- `SwallowedException` ⇒ 给 `KdbxFileConflictException` 补 `cause` 并传原异常。
  **这条是「顺带修掉两处不是门禁问题、但确实是问题」之一** ——
  为了给用户看一句人话而丢掉原始异常，会让「到底哪个请求 412」失去唯一线索。

#### ② 🔴🔴 「门禁前置项红 = 后面的检查全都没跑」（`272eff8` 的教训）

`classifyKdbxError` 里那个 `when` 漏了 `NotUnlocked` 分支，是**我自己在 `910b571`
里新增分支时忘的同步**。它躲过两轮 CI 的原因很值得记：

- `when` 作为**表达式**才强制穷尽 ⇒ 编译器**一定会报**；
- 但**前两轮的 detekt 步骤先红，`build_gate` 整个被 skip**
  ⇒ 编译错误**从来没被触发过**。

⇒ 教训有两层：
1. 别把「前置步骤红了」当成「后面的都过了」——**恰恰相反，后面的一个都没跑**。
2. 给 `sealed` 类型加分支后，**主动全局搜消费点**，别等编译器告诉你。
   本轮据此排查了 `KdbxOpenError` 的 3 处 `when`
   （`VaultRepositoryImpl.kt` 的 598 / 679 / 908）与 `KdbxWriteFailure` 的 2 处，
   确认穷尽性**只有 908 这一处破**。

映射取舍：归到 `UnlockResult.Unknown("请先解锁该密码库")`，
**不**在 domain 层新增 `UnlockResult` 分支 —— 该函数只服务解锁/添加路径，
那条路径上「未解锁」本就不该出现（你正在解锁它），
为它撑开 domain 分支只会让 UI 多一个永远走不到的 case。

#### ③ 沙箱 GitHub 通道会**再次失效**，且 hosts 记录会丢

本轮开始时 `ssh.github.com` 又被解析到 `198.18.0.39`（保留网段占位）

#### ④ `-Xfriend-paths` 的写法（纯 JVM 验证链）

- 参数名是 **`-Xfriend-paths=<dir1>,<dir2>`**（**逗号**分隔）。
  写成 `-friend-paths=` 会报 `invalid argument: -friend-paths=...`。
- **多文件必须用 `@argfile`**（`-d out @srcs.txt`）；
  `$(cat file | tr '\n' ' ')` 会打乱 `-classpath` 的解析。
- okio 必须用 **`okio-jvm-3.15.0.jar`** —— `okio-3.15.0.jar`（KMP 元数据 jar）里
  **没有** `okio.ByteString`。
- 全模块清单编译会因缺 Compose / Android stub 而失败
  ⇒ **只编译 `data/repository/.../kdbx/` 子包**（8 个文件）。
- 断言套件重跑脚本 `/tmp/kc/reverify.sh`；⚠️ **`VerifyWrite` 会污染
  `/tmp/kc/vt/work/`**，残留的 `vault.kdbx.bak` 会让「第一次 save 不产生备份」
  假失败 ⇒ **重跑前先 `rm -rf /tmp/kc/vt/work`**。
- ⚠️ `reverify.sh` 里 `tail -8` 会把失败行藏掉，用 `tail -60`。

#### ⑤ `force` 与 `expectedVersion = null` 是**两件事**

- `force = true`：**别检查、直接盖**（只在用户确认覆盖后用）。
- `expectedVersion = null`：**我没带基线**（仍是乐观并发，内部自己 stat 一次）。

合并会让「忘了传基线」静默升级成「强写覆盖远端」⇒ 必须分开。
（`VerifySyncOrch` 第 ⑬ 组专门钉死了这个区别。）

### 10.4 关键设计决策

- **冲突第一期只做「拒写 + 用户拍板」**，刻意**不给「合并」**：
  自动合并出错时用户**看不见**；而两个覆盖选项的代价对称、用户能看懂。
  对话框三个选项（`KeepLocalUpload` / `KeepRemoteDownload` / `DecideLater`）都写明
  后果，**刻意不给任何一个标红**。
- **版本令牌选型**：WebDAV / OneDrive 用 ETag；本地 SAF 用**内容 SHA-256** ——
  mtime 精度到秒会漏报冲突，**漏报 = 静默覆盖用户改动**。
- **ETag 必须归一化**（剥 `W/` 与引号），否则弱校验 ETag 会被 412 误拒。
- **命名冲突消歧**：`io.vaultix.domain.VaultSyncStatus`（Bitwarden 运行时状态）
  vs `io.vaultix.model.KdbxCloudSyncStatus`（KDBX 网盘状态枚举）—— 后者加 `Kdbx` 前缀。
- **`VaultRepositoryImpl` 顶格 40 个函数**（detekt `TooManyFunctions` 上限）
  ⇒ KDBX 同步走**独立接口 `KdbxSyncRepository` + 独立实现**，
  `RepositoryModule` 里 `bindKdbxSyncRepository`。
- **DI 构造环用 `Provider` 破**：`KdbxCloudSyncModule` 里
  「协调器 ↔ 编排器 ↔ 来源工厂」构成环 ⇒ 编排器拿
  `Provider<KdbxCloudSyncCoordinator>` 而不是提前捕获 lambda。
- ★ **`VaultixApplication.kdbxCloudSyncInitializer` 看起来没用，但必须存在**：
  `KdbxCloudSyncInitializer` 的全部价值在它的 `init` 块里
  （把 app 侧 OneDrive 工厂注册进协调器）。**不注入 = Hilt 不构造它 = 不注册**

### 11.1 R1 读路径迁移 —— 关键路径已通

**改法**：`Kdbx.kt` 里**删掉** `fun interface KdbxSource` 与两个**非挂起**重载，
换成收 `KdbxFileSource` 的挂起版本：

```kotlin
suspend fun unlock(vaultId, source: KdbxFileSource, password, keyFileBytes = null): Result<KdbxUnlockedContent>
suspend fun verify(source: KdbxFileSource, password, keyFileBytes = null): Boolean
```

★ **为什么是"删"而不是工作单里写的"并存、逐步迁"**：并存的前提是"旧的那条不影响可用性"，
而 §16.1 已经证明**恰恰相反** —— 留一个只认 SAF 的读入口就是留一个**静默失效**的口子
（把 `webdav:` 交给 `Uri.parse` 不报错、只是读不到）。判据同坑 #106：
**读路径分流了，写路径就必须同时分流；反之亦然。**

**新增 `KdbxFileSourceResolver`**（`data:repository/kdbx`）：`origin ⇒ 来源`的**唯一**判别表。
实现**就是** `KdbxCloudSyncCoordinator`（`: KdbxFileSourceResolver`）—— 不另写第二份 `when (prefix)`，
否则必然漂移成"同步找得到来源、解锁却说找不到"（**且没有任何报错**）。
`readBytes(uri)` 做成 interface 的**默认方法**：keyfile 与库文件共用同一套解析，
且将来 keyfile 放到网盘上不用改签名。Hilt 侧用 `Provider<Coordinator>` 打破构造环。

**5 个调用点**全迁。三个类顺手各去掉一个不再需要的构造参数（`Context` / `Uri`）：
`VaultRepositoryImpl`（-`@ApplicationContext context`，正好抵消新增的 resolver）、
`LocalUnlockEnrollment`、`PinEnrollment`。
⇒ 那三份**逐字复制**的 SAF lambda 也没了 —— 它们本来就是同一个坑的三个副本。

**新增测试 `KdbxFileSourceReadTest`（4 例）**：纯内存来源能 `unlock`/`verify`
⇒ **证明**读路径不再依赖 `ContentResolver`（此前 `KdbxReadPathTest` 全部绕过门面直接喂
`ByteArray`，所以"门面收不收得下非 SAF 来源"**没有任何测试覆盖** —— 正是这次的盲区）。
另有一条验"来源抛错 ⇒ 归到 `SourceUnavailable` 且**保留来源原话与原异常**"。

### 12.2 第一层：`RESULT_CANCELED` ⇒ 面板重发 PendingIntent（~2 次/秒）

★ **重发者是凭据面板本身**（`realCallingUid` 就是面板进程），不是我们的代码在循环。
`AutofillActivity` 的解锁路径是"秒创建秒 finish"，配上默认的 `RESULT_CANCELED`

`result.resultCode / result.data` **原样透传**。

**修复**：`AutofillActivity` 的 CP 收尾一律走 `finishCredentialFlowUnlocked()`（`RESULT_OK`）。
顺带把 `unlockAll` 一直**丢弃**的解封结果接了出来（原来"指纹过了但库没打开"是**完全静默**的）。

### 12.3 第二层：结果 Intent 必须**带候选列表**（系统不会回来重查）

  **`CredentialProviderEntryBuilder`**（`@Singleton`，`@RequiresApi(34)`）——
  服务与解锁 Activity **共用同一份**，绝不复制（两份实现必然漂移，而漂移表现为"面板里少几条候选"）。
  搬迁是机械的：`sed` 切 160–443 行 + `this`→`context`、`getString(`→`context.getString(`，
  7 处编译错误全部由编译器兜住（缺 3 个 import、缺 2 个常量、`buildGetResponse` 需放开可见性）。
- 构建器在"因锁定而回解锁动作"时**暂存该份请求**（`pendingUnlockRequest`，只含请求、不含密钥材料）。
- `AutofillActivity` 收尾改为 `finishWithRefreshedEntries()`：取暂存请求 → 构建候选 →
  `setBeginGetCredentialResponse` → `RESULT_OK`。拿不到请求时回**空 OK**（诚实降级，
  用户重触发一次即可）；⚠️ **绝不回 CANCELED**（那会回到第一层的死循环）。
