# SESSION-2026-11-09 · KDBX 写回链路修复 + UI 重排（0.11.3 批次回填）

> 单主题单篇（[8.9](./conventions/8.9-文档分篇.md) §7），本篇两件事（约 255 行 / 16KB，在预算内）：
> **① 0.11.3 那 19 个提交的工程判据回填**（那批只写了 `Docs/release-notes/v0.11.3.md`，
> 用户视角说明，没有根因与「为什么不能改回去」，`.ai` 里 `0.11.3` 出现 **0 次**）；
> **② 11-09 当晚修掉「进条目页闪一帧『此条目不存在或已删除』」**。
> 后者是本篇重点，因为它**推翻了 11-09 早些时候那次修复的写法**（同一现象第二次出现）。

## 0. 一句话结论

**「未知」必须是一种显式状态，而且必须在分支条件里被真正用上。**
11-09 早些时候已经写对了判据（`itemLoaded` 区分"还没解出来"与"确实没有"），
却又把它从分支里拿掉、只留着做转圈延迟的输入 ⇒ 前 120ms 没有一支接住"未知"，
直接落到 `item == null` 的「条目不存在」。判据写进文档、代码没照着写，等于没写。

## 1. 现象 / 需求

用户 11-09 00:46：

> 「不论是 bitwarden 库还是 kdbx 库，点击进入条目页，会发现有一帧有问题，
> 闪烁了一下，眼睛捕捉到：此条目不存在或已删除。」

关键信息：**两种库都中**。这条排除了"KDBX 特有路径"的可能 —— 它与库类型无关，
只能是详情页自己的状态机问题。

## 2. 根因

### 2.1 数据层是干净的，问题全在 UI 分支

`ItemRepositoryImpl.observeItem()` 在 `2347b55c` / `18cec250` 里修过：删掉了
`.onStart { emit(null) }`，流在拿到真实 `kind` 之前**不发射**。所以"假 null"已经不存在。
真正的问题在 `ItemDetailScreen.kt` 的 `DetailBodyContent`：

```kotlin
// ❌ 修之前的 when
when {
    showProgress && item == null -> VaultixWavyProgress(...)   // 要等 120ms 才成立
    deleting -> Unit
    item == null -> Text("条目不存在或已被删除")                 // ← 前 120ms 全落这里
    else -> DetailSections(...)
}
```

`showProgress` 由 `LaunchedEffect` 延迟 120ms 置真；`loading`（= `!itemLoaded`）
虽然作为参数传进来了，**却没出现在任何分支条件里**。于是进入页面的头 120ms：

| 判据 | 值 |
|---|---|
| `itemLoaded` | false（`UiState` 初值） |
| `item` | null（初值） |
| `showProgress` | false（还没到 120ms） |
| `deleting` | false |

四支全不中第一支，直接命中 `item == null` ⇒ 画「此条目不存在或已删除」。
条目从 Room 内存缓存到达通常 50ms 内 ⇒ **正好在那 120ms 窗口里替换掉**，
人类眼睛看到的是一帧闪烁。与库类型无关，这也解释了为什么 Bitwarden 与 KDBX 都复现。

### 2.2 为什么 11-09 早些时候的修复没生效

那次改动做对了两件事：加了 `itemLoaded` 字段、加了 `DETAIL_PROGRESS_DELAY_MS = 120`。
但它把「未知」当成**转圈的触发条件**，而不是**独立的渲染分支**。
转圈延迟的本意是"别为一次 50ms 的读取闪个 spinner"，结果把"未知态"一起延后了 ——
**延迟只该加在视觉信号上，不该加在状态判定上**。

这是本次最值得记的一条：防闪烁的延迟是**表现层**的，状态机不能跟着它延迟。

## 3. 做法

`app/src/main/java/io/vaultix/vaultix/ui/detail/ItemDetailScreen.kt`：

1. 判据提到分支之前，作为**第一支**：
   ```kotlin
   val unknown = item == null && !loaded
   when {
       unknown -> DetailUnknownPlaceholder(...)   // 从第 0 帧起就成立，不吃延迟
       deleting -> Unit
       item == null -> Text(detail_missing)        // 现在这句是真的：流发过了、确实没有
       else -> DetailSections(...)
   }
   ```
2. 新增 `DetailUnknownPlaceholder`：**空白占位**，不画文字、不画骨架屏。
   - 不画「加载中」：一次 50ms 的缓存读取不该被说成"正在加载"；
   - 不画骨架屏：骨架需要知道条目类型 / 字段数，而我们恰恰还不知道，猜错反而更吵；
   - 只做两件事：用 `DETAIL_UNKNOWN_MIN_HEIGHT = 220.dp` 占住内容位（避免内容到达时
     「先缩后撑」），并让顶部让位 `rememberImmersiveBarPadding(...)` 与
     `DetailSections` 里那个可滚动 `Spacer` **同高**（切换时不位移）。
3. 转圈保留 120ms 延迟，但改成**叠在占位上**：`showProgress` 为真才叠 `VaultixWavyProgress`。
   缓存命中 ⇒ 一次都不出现；真慢（冷读盘 / 大库）⇒ 用户确实需要知道在等。
4. 参数 `loading: Boolean` 改名 `loaded: Boolean`，语义方向与字段名一致
   （原先是 `loading = !state.itemLoaded`，调用处与形参方向相反，容易读反）。
5. `LaunchedEffect` 的 key 从 `(loading, item)` 收敛为只 `unknown`：
   条目**内容**变化（编辑后刷新）不该重启延迟，否则每次编辑都要重等 120ms。

### 4.1 KDBX 写回链路（`d9d65b86` → `f9f51604`）

**① 写回闸门从 `persist` 前移到 `mutate` 之前（`d9d65b86`）**

旧闸门长在 `KdbxItemRepository.persist` 里，而 `Kdbx.mutateLocked` **在那之前**
就已经把新会话 `put` 进内存 ⇒ 拒写时"内存已删、磁盘没动"，列表 / 详情 / 回收站
读到三份互相矛盾的真相。修法：

- 新增 `Kdbx.baselineStateOf()`（**只读**：`known` / `aligned` / 两个内容指纹），
  九个写动作入口统一 `assertWritable(vaultId)`；
- `persist` 用 `try/finally` **无条件** bump，任何 throw 都不再让列表停在旧快照。

**② `!aligned` 的两种成因必须分开（同一提交，这是最关键的一条）**

| 成因 | 处理 |
|---|---|
| 远端真变过（状态 `REMOTE_CHANGED` / `CONFLICT`） | 拒写，抛 `StaleBaseline` —— #185 防线原样保留 |
| 本机连续编辑、基线没跟着推进 | `Kdbx.rebaseBaselineOnSession()` 就地重对齐后**放行** |

旧实现一律当"远端变过"，于是「保存被拦 → 点同步判两边都没变 → 仍被拦」成环，
状态还被洗成绿色 `IN_SYNC`，死锁只能靠锁库 / 冷启动清内存基线才解开。
⚠️ **远端是否变过最终仍由条件写兜底**（`If-Match` → 412 → `CONFLICT`），
内容指纹只是"本机这份内容来自哪一版"的辅助判据，**不是唯一防线** ——
所以放宽它不等于放松安全，这一点改动前必须想清楚。

**③ 换文件夹曾经根本没落盘（同一提交）**

`KdbxItemWriter.updateEntry` 原先只改 `folderId` 字段，不在 XML 里真搬组。
补上 `moveEntry`（目标组不存在退回根组），**顺序放在 `withHistory` 之后、
毫秒余数补写之前** —— 搬运会重建条目，放错位置会冲掉刚定稿的字段。

**④ 落盘失败必须回滚会话（`3f4ec7fe`）**

真机现象：删除后「搜索看得到、点不开、回收站有、XC 没删」。根因是 `mutateLocked`
编码完就把新会话放进内存，`persist` 任一步抛异常都留下内存 / 磁盘不一致，
**而失败路径此前完全静默**。修法：`KdbxSessionStore` 按令牌留旧会话快照
（每库只留最新一个，锁库即清），`persist` 成功 `commitMutation` / 失败 `rollbackMutation`；
`try` 扩到整个函数体（原先 `vaultDao.get` / `hasCloudSource` 在 try 外，
抛异常时 `finally` 的 bump 不执行）；补两处静默失败日志，下次一抓即可区分
「目标不存在」与「往返自检失败 / 落盘 IO 失败」。

**⑤ 上传失败要自己重试（`c7d0ba3b` / `f657308d`）**

原 `KdbxAutoUploader.drain()` 一次 `Failed` 就收工，真机一次 72s 超时后状态停在
`FAILED`；而 `enqueue` 只在 `persist` 里调用 ⇒ 用户必须**再编辑一次或手动点同步**
才能把改动推上去。改为：网络 / IO 失败按 **3s → 8s → 20s** 退避，最多 `MAX_RETRIES = 3` 次，
一次 `enqueue` 最多 `MAX_ROUNDS = 6` 轮；**冲突 / 远端有更新 / 无云端仍一次收工**
（这些需要用户决策，重试解决不了）。全程在后台协程，界面一行都不等。
`f657308d` 把重试循环收敛成单一 `break`，过 detekt `LoopWithTooManyJumpStatements`。

**⑥ 读路径不再与 KDF 抢调度器（`f9f51604`）**

真机「点删除等 1–2 秒、进回收站等 2–5 秒」。两个原因叠加：

- 读流只认 `persist` **末尾**的 bump，而它压在编码 / 自检 / 落缓存之后；
- `kdbxItems` / `kdbxTrash` 误挂在 `@CryptoDispatcher`（`Dispatchers.Default
  .limitedParallelism(2)` 的 KDF 车道）上 ⇒ 写回一占用、读就排队。

⇒ 会话在 `mutateLocked` 里提交时**即**自增代次并推给 UI（编码失败就地恢复会话）、
`persist` 开头即 bump，纯内存读改用 `Dispatchers.Default`。

### 4.2 交互反馈（`21406157` / `2347b55c` / `b85ce9b9`）

真机日志（21:47–21:49）：删除与恢复的**本地写回只有约 100ms**，用户感受到的几秒
是 OneDrive 上传 27–34s。也就是说，几秒等待里绝大部分**根本不是本地慢**，
而是 UI 把"后台在上传"表达成了"页面还在等你"。三条同源修法：

- **点完即走**：详情页点删除后立刻清空内容，`UiEvent.Deleted` 用 `trySend`
  提前到附件明文清理之前；清理用 `NonCancellable` 包住（返回列表取消
  `viewModelScope` 也不会留下明文）。修「点了几秒没反应」。
- **不再整页转圈**：详情页移除 `DetailSyncProgress` 进度条 —— 上传是后台行为，
  角标 `DetailSyncIndicator` 足以表达；进度条会把「本地已完成」读成「页面还在等同步」。
- **回收站不再整页变灰**：`UiState` 增 `activeItemId`，`TrashRow` 只禁用被操作那一行
  （全局 `busy` 保留用于防连点）；恢复走**乐观移除**，点下就从列表消失。
- **写回串行闸门**：连续两笔写时旧字节可能后落盘覆盖新内容 ⇒ 加串行。
- **重试要真拉远端**：列表页 `retrySync` 遇 `NeedsReload` 补 `pull()`，
  与「密码库」页"立即同步"一致，不再反复提示重新解锁。

### 4.3 同步状态可视化（`aa48e7e5` / `7ba3e8b1` / `cad2bb6e`）

**常驻横幅只挂"需要用户动手"的三种状态**（`aa48e7e5`）：

| 状态 | 横幅 |
|---|---|
| `FAILED` | 常驻警告 +「重试」，文案说"改动只在本机" |
| `CONFLICT` | 常驻警告，引导去「密码库」页拍板 |
| `REMOTE_CHANGED` | 常驻警告 +「重试」拉取（不用重新解锁） |
| `PENDING_UPLOAD` / `SYNCING` | **不挂** |

⚠️ 上传中不挂横幅是 11-08 早些时候**被用户否掉**的行为，后来补失败提示时
一度连失败一起砍了（只剩 ⋮ 里一个 6dp 红点，菜单不展开根本看不见）。
现在是拆开：**上传中不打扰，异常必须说话**。别为了"补提示"把上传中横幅捡回来。

**⋮ 菜单底部三图标是第 4 轮定稿**（`cad2bb6e`），前面三轮的教训值钱：

| 轮 | 形态 | 用户反馈 |
|---|---|---|
| 1 | 同步整行 + 尾部锁图标 | 挤、怕误触 |
| 2 | 各占一行 | 锁定贴底整行可点，拇指上扫擦到 |
| 3 | 同步只在异常时出现 + 锁定缩成右下角图标 | "孤零零的，也没有颜色灯" |
| 4 **定稿** | `[灯] [同步] ←weight→ [锁定]`，**全部不写字** | — |

⇒ 教训：**"删掉元素"能解决拥挤，但会制造空旷**；真正该做的是"元素保留、文字去掉"。
灯只给颜色（异常原因由顶部横幅说），同步常驻可点，两个动作之间用 `weight` 撑开
不是零间隙相接，锁定仍在最右（低风险在左、高风险在右）。
`7ba3e8b1` 顺手把同步结果改用 `settled` 取失败原因（原写法编译期智能转换丢失）。

### 4.4 详情页与设置页观感（`f3bf5a2e` / `9c6dddf5` / `065f3934`）

- **网址超 3 条折叠**：多数条目 1–2 条不受影响，其余收进「另外 N 个网址」，
  展开态 `rememberSaveable` 保持。渐进披露，**不排序不去重**。
- **时间戳降级为页脚小字**：原先整张卡片 + 分区标题，与「网址」「备注」同等视觉重量，
  而它是整页信息价值最低的内容。字段保留、位置仍在最底，只是不再抢视觉；
  三个不再有调用点的字符串一并删除。
- **设置行图标改为顶对齐标题行**（M3 多行 list item 做法）：原先整行垂直居中，
  副标题一行与两行的行并排时图标上下跳，同一列看起来没对齐。
- **防截屏关闭态文案 33 字 → 25 字**：原先在副标题 2 行上限处被截成「最近任务里也可…」，
  而这是唯一说明关闭后果的句子。
- **组名校准**：「密码库与解锁」→「密码库与安全」（组里防截屏 / 剪贴板 / 权限三项与解锁无关）；
  「显示与填充」→「外观与填充」。措辞改陈述式，不口语化。
- **库管理页行尾星标换成同步**：星标是一次性设置却占最高频位置，同步是改完就想点的动作
  却藏在 ⋮ 里。默认库降级为副标题文字。三处同步入口统一叫「同步」、统一 `Icons.Filled.Sync`。
