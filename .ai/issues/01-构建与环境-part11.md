## 218. 🟡 预览包的「身份」全靠 commit SHA 与日志措辞 —— 装不上时用户无从自查（2026-11-01，用户报告）

**现象**（用户原话）：「最新的安装包与我本机的上一个 dev 包签名不一致」，以及
「Development Preview (dev-341be3a58fb6c248f8f8a935d6fae0b9501ffa4c) …这些表述是否精简优化，
dev 也有版本号之类的」。

**拆开是两件独立的事，但同一个根**：**预览包没有可被验证的身份**。

1. **标题里只有 SHA**：`⚠️ Development Preview (dev-341be3a58fb…)`。
   Releases 列表里会被截断，看不出是哪个版本 —— 而这是用户**唯一**能看到的身份。
   包里其实有正经的 `versionName = 0.10.4-dev-341be3a`，只是没人把它放到页面上。
2. **页面上没有签名指纹**：用户装上提示"签名不一致"时，唯一的取证途径是翻 CI 日志，
   而日志**要认证才能下载**。等于要求用户替我们做一件他做不到的事。
3. **日志措辞与事实矛盾**：`Decode signing keystore` 打「校验通过」，`packageFullDebug`
   却报 `keystore password was incorrect` —— 因为 `keytool -list` **只验 store 密码**。
   这两句把排查引向"代码问题"，连续猜错了四次（#217）。

**修法**（本轮）：

- **标题带版本**：`Vaultix v0.10.4-dev+341be3a · Preview`。版本字段由构建步骤**落盘**
  （`dev-build-info.env`）后再读，不让后面步骤自己重算 —— 重算 = 第二处来源。
- **正文压成一张表**：版本 / 提交 / 构建类型 / 签名，去掉「Debug APK」「debug 构建产物」
  「Generated APKs」三处同义重复；末尾一句"签名一致可直接覆盖，不一致请先备份"。
- **签名指纹如实取自产出的 APK**（`apksigner --print-certs`，兜底从 `META-INF/*.RSA`
  取整张证书 DER 的 SHA-256），两个 workflow 都印。
- **密钥失败分两种病因**：#218.1 见下。
- **Stable 侧不降级**：`release.yml` 验不过 key 密码就 `exit 1`。正式版发一个
  "一次性密钥签的 Stable"，会让所有人下次更新被要求卸载重装（连带 Keystore 里的指纹解锁）。

### 218.1 密钥密码错 ≠ 密钥不对 —— 合并成一句话就修不好

原提示只有「key 密码与 store 密码不一致」，而实际有两种病因、修法完全不同：

| 现象 | 病因 | 修法 |
|---|---|---|
| `keytool -list` 也过不了 | store 密码错 / 密钥文件损坏 | 改 `SIGNING_STORE_PASSWORD` 或重传密钥 |
| `keytool -list` 过了、`-certreq` 过不了 | key 密码与 store 密码不同 | 改 `SIGNING_KEY_PASSWORD` |
| 两者都过、**装的还是盖不上** | Secret 里根本不是原来那把钥匙 | 换密钥；此时指纹会与设备上那个不同 |

⇒ 现场再验一次 `-list`、并把**证书指纹**打进 annotation，就能定性。
最后一个分支尤其重要：**改密码永远修不好它**，而指纹是唯一硬证据。

> **判据**：① **能被用户验证的，才叫"发布物的身份"** —— 只写 SHA 等于没写身份；
> ② **诊断信息必须区分病因而非描述症状**（"密码不一致"听着像一种病，其实是两种）；
> ③ **正式版遇到签名问题宁可红，不可降级** —— 红的代价是一天，降级的代价是所有人的数据。

### 218.2 `versionCode` 的第二份实现（awk）—— 用变异测试证明它没跑偏

页面上写 versionCode 就要在 workflow 里算一遍，于是 `versionCodeOf()` 有了第二份实现。
这不是小事：`.ai/ISSUES.md` #145.1 的规矩就是**版本号只能有一个来源**。

本轮踩到两次（都只在"页面数字"层面，包本身没坏）：

- `${name%%-*}` 把 `-1.0.0` 截成空串（负号被当后缀分隔符）⇒ awk 收到空输入、无输出；
- `isnum` 写成 `^-?[0-9]+$`，而 Kotlin 的 `toIntOrNull()` **接受 `+4`**
  ⇒ `0.10.+4` 两边算出 10000 / 10004。

⚠️ 第二个是**测试抓出来的**，不是我推演出来的。而第一版测试写的 14 条用例里，
有三种改法**故意改坏后照样全绿** —— 说明"有断言"和"断言断到了"是两件事。

⇒ 落地为 `.ai/tools/tests/selftest_version_code.py`：**直接抽 workflow 里那段 awk 跑**
（不抄一份，抄的会和真身分叉），期望值由**真编译器编译 `versionCodeOf()`** 得出，
并已在 CI 里执行。反向验证四种改法全部被抓。

> **判据**：**任何"同一事实的两份实现"都要配一个拿真源对账的测试**；
> 且这个测试必须**先被故意改坏验证过**，否则它只是安慰剂。

### 218.3 🟡 两条语句被写成一行：`bash -n` 判合法、CI 全绿、只有页面内容变怪

**现象**（CI #340 实测）：Release 页面的「签名」一行印出

```
SHA-256 echo signer_subject=unknown
```

**根因**：改 `ci-debug.yml` 时把 `else` 分支的两条 `echo` 写成了同一行：

```bash
echo "signer_fingerprint=" >> "$GITHUB_OUTPUT"            echo "signer_subject=unknown" >> "$GITHUB_OUTPUT"
```

这**不是语法错误** —— `echo` 的参数变成了 `= >> $GITHUB_OUTPUT echo signer_subject=unknown`，
`>>` 只重定向一次。于是：

| 检查项 | 结果 |
|---|---|
| `bash -n` | ✅ 通过 |
| CI 构建 / 单测 / 发布 | ✅ 全绿（APK 正常产出、Release 正常生成） |
| **页面内容** | ❌ 那一行是错的 |

⇒ 这是本项目第一次遇到「**门禁全绿，产物也对，只有内容错**」的组合。
它比编译错误更贵：编译错误十分钟就修好，这个要等人去打开页面才可能发现。

**修法**：新增 `.ai/tools/check_workflow_shell.py` 并接入 CI，查两条：
① `>> "$GITHUB_OUTPUT"` 之后同一行还有内容；② 一行里出现两个 `echo "`。
反向验证：把 bug 原样写回去 → 脚本报 2 处、退出码 1（而 `bash -n` 仍说 OK）。

> **判据**：**语法检查只能证明"能被解析"，不能证明"能按意图执行"**。
> 一类错误如果"不报错、不改产物、只改内容"，就必须有专门的门禁；
> 指望"改完看一眼页面"等于把可靠性押在人的记性上。

⚠️ 刻意**没有**把 `if ...; then X=1; fi` 这类单行写法判红 —— 它是常见合法写法，
误报只会教人加 `# noqa`。只查「两条命令挤一行」这个具体形状。

### 218.4 🟢 「有兜底」不等于「兜底能兜住」：APK v2 签名块解析连错三处

**现象**：修完 218.3 之后，Release 页面「签名」行不再错乱，但指纹仍是空的 ——
显示「未能读取」。也就是说：**这块功能上线了，但没有任何实际作用。**

**为什么读不到**：debug 包用的是 **v2 签名**，证书在 APK Signing Block 里，
`META-INF/` 下根本没有 `.RSA` 文件。而第一版兜底恰恰是去读 `META-INF/*.RSA`。
两条路同时落空：

| 通道 | 结局 |
|---|---|
| `command -v apksigner` | 恒假 —— `apksigner` **不在 runner 的 PATH 上**（在 `$ANDROID_SDK_ROOT/build-tools/<ver>/`） |
| 兜底读 `META-INF/*.RSA` | 恒空 —— v2 签名的包没有这个文件 |

**修的过程中又错三次**（每一处都是静默的，读出来是垃圾而不是报错）：

| # | 错在哪 | 后果 |
|---|---|---|
| 1 | `size` 从 `magic` **之后**读 | 读到的是 zip 数据，块起点算飞 |
| 2 | 少读 signers 序列的 `count` | 整体偏 4 字节，`signed_len` 读成 0 |
| 3 | `digests` / `certificates` 当成 `LP(seq)` 而非 `count + LP(item)*` | 偏 4 字节，读到 536870922 这种荒谬长度 |

APK v2 的真实布局（`size` 指「不含 size head 自身、也不含 size foot+magic」）：

```
<size head:8><pairs…><size foot:8><magic:16>
pair = <len:8><id:4><value>
value(v2) = LP( signers 序列 )        # 序列 = count + LP(item)*
signer    = LP(signed) + 序列(signatures) + LP(publicKey)
signed    = 序列(digests) + 序列(certificates) + 序列(attrs)
```

**最终修法**：
- 解析器独立成 `.ai/tools/read_apk_signer.py`，**两个 workflow 共用同一份**（不再是两份复制）。
- 自检 `.ai/tools/tests/selftest_apk_signer.py` 接入 CI：现场用 `keytool` 生成证书 →
  拼一个结构合法的 v2 APK → 断言解析出的 SHA-256 与证书文件**逐字节相等**；
  并断言未签名文件返回非零（不能把「没签名」说成「签名正常」）。
- 对自检做变异测试 5 组：

| 变异 | 自检 |
|---|---|
| signer 少读 count（就是 bug #2） | ✅ 判红 |
| 证书序列少读 count（bug #3） | ✅ 判红 |
| `size` 读在 magic 之后（bug #1） | ✅ 判红 |
| 未签名时也返回 0 + 空指纹 | ✅ 判红 |
| 去掉「size head == size foot」自校验 | ⚠️ **仍绿，未覆盖**（样本结构本就合法，它是防御性断言） |

> **判据**：兜底路径必须在"兜底的场景"里被验证过。否则你写的不是兜底，
> 是一段**看起来像兜底**的代码 —— 它只在事故发生时才被告知是没用的。
> 所以：**每加一条兜底，就要加一个能让主路径失败的测试**。

最后一组如实标为未覆盖，不假装测到了。

### 218.5 🔴 诊断本身在说谎：`Build Debug APK` 缺 `env:` ⇒ 一条假的「store 密码错」

**现象**（CI #341 实测 annotation）：

```
[error] Keystore store password wrong
        固定密钥库连 store 密码都打不开 ⇒ SIGNING_STORE_PASSWORD 与 keystore 不符。
```

而**同一次 run 的上一步** `Decode signing keystore` 明明打着
`固定密钥签名解码通过（仅 store 密码；key 密码在打包步骤前再验）`。
两句日志互相矛盾 —— **同一个 PR 刚为"消除这种矛盾"写完 #218.1**。

**根因**：`Build Debug APK` 步骤**没有 `env:` 块**。GitHub Secrets 不会自动变成环境变量，
于是该步骤内 `${SIGNING_STORE_PASSWORD}` 恒为空 ⇒ 全部回落 `android` ⇒
`keytool -certreq` 拿 `android` 去开真实密钥库 ⇒ 必然失败 ⇒ 走到「store 密码错」分支。

**这是同一句教训的第二次**：2026-09-08 已在 `Decode signing keystore` 上踩过并写了长注释
（「⚠️ Secrets 不会自动变成环境变量」），同一份文件里又漏了一遍。

| 检查 | 结果 |
|---|---|
| `bash -n` | ✅ 通过（`${VAR:-android}` 语法完美） |
| 同一次 run 的另一步 | ✅ 能用（那步有 `env`） |
| **结论** | ❌ 假的，而且把人引向错误的修复方向 |

**修法（三件）**：
1. 给 `Build Debug APK` 补上 `SIGNING_STORE_PASSWORD` / `SIGNING_KEY_PASSWORD` / `SIGNING_KEY_ALIAS` 三个 env。
2. 告警文案带上「Secret 到底有没有配」——空值导致的误诊不该再靠比对另一条日志才能识破：
   `诊断：SIGNING_STORE_PASSWORD 已配置（N 字符）/ 未配置，已回落 android；…`
3. 新增门禁 `.ai/tools/check_workflow_secret_env.py`（已接入 CI）：扫每个 step 的 `run` 里
   出现的 `${SIGNING_*}`，凡是该 step 与 job 级 `env` 都没注入的就判红。
   反向验证：删掉那三条 env → 报 3 处、退出码 1，而 `bash -n` 仍说 OK。

> **判据**：`${VAR:-default}` 语法永远合法、`bash -n` 永远通过 ——
> 「这个变量是否会被赋值」是 **YAML 层**的缺陷，只能跨 step 比对。
> 更狠的一条：**诊断代码本身也会说谎**。凡是"从某处推断出病因并打印"的代码，
> 必须能区分「输入确实是 A」和「输入根本没送到」，否则它输出的不是诊断，是猜测。

### 218.6 🔴 我的测试是"自测自己"：v2 解析器四版全错，自造样本每次都通过

**背景**：218.4 时写了个 v2 签名块解析器，并配了自检 `selftest_apk_signer.py`。
自检的做法是「手工拼一个 v2 APK → 断言解析出的指纹 == 证书 SHA-256」，结果**一路绿**。
但 CI #341/#342 的实测一直是「apksigner 找到了、执行了、零输出」，指纹读不出来。

**真因**：**样本是我按当时的（错误）理解拼的**。解析器与样本犯了同一个错，
所以断言永远成立 —— 这不是测试，这是**同义反复**。

**用真实产物对账后，三个错误当场全暴露**：

| 版本 | 错在哪 | 表现 |
|---|---|---|
| 1 | `size` 从 `magic` **之后**读 | 块起点算飞 |
| 2 | `head = magic - 16 - size` | 偏 8 字节 |
| 3 | `signed` 里按 `count` 读证书序列 | 偏 4 字节，读到**错误的证书** |
| 4 | `head = magic + 8 - size` | ✅ 与 `apksigner` 逐字节一致 |

第 3 版最阴：它读出来的「证书」也是一段合法字节，`sha256()` 照样算出结果 ——
**指纹看起来完全正常，只是错的**。主语（DN）甚至是对的，因为离得近。

**根因之一**还在于我对结构的假设错了：APK v2 的每一层都是 **length-prefixed（LP）**，
**没有** `count + LP*` 那种带计数的序列。把 LP 的长度字段当 count 用，就整体偏 4 字节。

**修法**：
1. 自检**只用真实 `apksigner` 产物**对账（`apksigner sign` → 两边 SHA-256 逐字节相等）。
2. 本机没有 `apksigner` 时 **SKIP，绝不退回自造样本** —— 并在输出里写明为什么。
3. 解析器顶部写清「这行 `+8` 是实测出来的，不要按推理去'修正'，改之前先跑自检」。

变异测试（真实产物模式）：

| 变异 | 结果 |
|---|---|
| `start` 偏 8 字节 | ✅ 判红 |
| signers 少读一层 LP | ✅ 判红 |
| 未签名也返回成功 | ✅ 判红 |
| 证书序列"按 count 读" | ⚪ 等价变异体（两种写法结果相同，不是缺陷） |
| 去掉 `size head == size foot` 自校验 | ⚠️ 仍绿，如实标为未覆盖 |

> **判据**：**测试的输入如果和被测量由同一个理解生成，那它只能证明"我自己和自己一致"**。
> 唯一可靠的验证是拿**外部的、权威实现**的产物来对账 —— 这里是 `apksigner`。
> 拿不到外部产物时，正确做法是 SKIP 并说明，**不是**自己拼一个样本给自己盖章。

### 218.7 🟡 `paths` 白名单漏了 `.ai/tools/**` ⇒ 改门禁时**整个 CI 不跑**

**现象**：提交 `6bccb9d`（只改了 `read_apk_signer.py`、`selftest_apk_signer.py` 与文档）
之后，等了十分钟，`actions/runs` 里**一条新 run 都没有**。远端 main 确实是 `6bccb9d`。

**根因**：`ci-debug.yml` 的 `on.push.paths` 白名单逐个列了 `*.kt` / `*.xml` / `gradlew` /
`.github/scripts/**` / `.github/workflows/**` … 但**没有 `.ai/tools/**`**。
而 `.ai/tools/` 下放的正是 CI 自己的门禁脚本（`check_workflow_shell.py`、
`check_workflow_secret_env.py`、`selftest_*.py`）。

⇒ **改门禁 → 门禁不跑 → 你以为门禁通过了。**

**修法**：`on.push.paths` 与 `on.pull_request.paths` 都补上 `.ai/tools/**`。

> **判据**：`paths` 白名单是"只在改到这些文件时验证"，所以**它本身就是一张盲区地图** ——
> 凡是"会改变 CI 行为"的文件（脚本、配置、清单）必须在内，否则得到的是**假的绿灯**。
> 这与 #218.5 同源：**假绿灯比没有绿灯更贵**，因为人会据此宣布完成。

顺带把 `.github/scripts/**` 在 `push.paths` 里也补齐（原先只有 `pull_request` 有）。

### 218.8 🔴 workflow 交进来的密钥，gradle 一个都不认 —— 「签名不一致」的真正根因

**现象**（用户）：*「最新的安装包与我本机的上一个 dev 包签名不一致」* —— 下载 CI 的预览包，
装不上手机里已有的包，提示签名不匹配。

**根因**：两套变量名并行，且**互不相认**。

| 位置 | 用的是什么 | gradle 会读吗 |
|---|---|---|
| `.github/workflows/*.yml` | `-Pandroid.injected.signing.{store.file,store.password,key.alias,key.password}` | ❌ **不会** |
| `app/build.gradle.kts` | `System.getenv("VAULTIX_KEYSTORE_PATH")` / `VAULTIX_STORE_PASSWORD` / `keystore.properties` | ✅ 只认这三个 |

于是 CI 上 `hasReleaseSigning == false` ⇒ `debug` 用 `signingConfigs.debug`
（Android 一次性 debug key，**每次 runner 一把新的**）⇒ 与本机包证书不同 ⇒ 盖不上。

**为什么这么久没被发现 —— 三句话全都是对的**：

1. workflow 的 `keytool -certreq` 校验**真的通过**（密钥文件本身没问题）；
2. `./gradlew assembleFullDebug` **真的成功**（debug 签名总会成功）；
3. `Decode signing keystore` 打的「固定密钥解码并校验通过」**也是真的**（它确实解码通过了）。

没有一句错话。缺的那一步是「交给 gradle 之后，gradle 到底用没用」——
而这一步在日志里**不留任何痕迹**，只有把「包里实际的证书」与「本机包的证书」摆在一起才看得出来。

⚠️ 顺带：`app/build.gradle.kts` 里那段注释原话是
「没有则保持『由 CI 通过 `-Pandroid.injected.signing.*` 注入』的旧路径」——
**这句注释本身是错的**：gradle 从未读过那个属性。注释被写下来之后就再没人验证过它。

**修法**（两层，缺一不可）：

1. `app/build.gradle.kts` 的 `signingValue()` 改为 `firstEnv(...)` 逐个尝试
   `VAULTIX_*` → `SIGNING_*`；**两套名字都认**，并把**命中的变量名打进 lifecycle 日志**
   （`keystore←VAULTIX_KEYSTORE_PATH`），下次改名能从日志读出来是走哪条通道。
2. workflow 里把密钥**同时**以环境变量下发（`export VAULTIX_KEYSTORE_PATH=…`、
   `SIGNING_KEYSTORE_PATH=…`）；`-Pandroid.injected.signing.*` 原样保留（AGP 官方通道，
   删它属于"顺手清理"，没有收益只有风险）。
   ⚠️ 密钥只在**已经解过 base64、验过密码**之后以路径形式下发 —— **绝不从 Secret 原文现算密码**：
   Secret 里带 `$` / `\` 时经 YAML → shell → Gradle 的转义会静默变形，
   得到一个"看起来配好了、其实是错密码"的状态（那正是 #218.1 花整轮才定位的病）。

**门禁**：`.ai/tools/check_signing_var_names.py` —— 从 workflow 的 `run:` 里抽它产出的
gradle 参数名与 shell 变量名，与 gradle 真正读取的名字做交集；空交集即判红，接入 CI（第 16 步）。
自检 `.ai/tools/tests/selftest_signing_var_names.py` 造「断链 / 接通」两个临时仓库分别要求
rc=1 / rc=0，另有「只有注释提到变量名」与「仓库不涉及签名变量」两个边界。

写这个门禁时**第一版自己就是假绿**：`shells` 集合里混进了 `KS_OPTS`（它的值是
`-Pandroid.injected...`），于是"有交集"永远成立。抓出来的方式是**先拿真仓库跑一遍**、
看到它对着已知断链报 ✅ —— 门禁写完后必须先在**已知会失败的状态**下验它判红。

> **判据**：**「配置写下来了」不等于「配置被读走了」。** 凡是跨进程/跨工具的协议
> （env 名、属性名、文件名），两端必须各有独立来源，且配一条**能对着已知坏状态判红**的检查；
> 只在注释里写「由 X 注入」的，等于没有约定。
> 补充：**注释会撒谎，而且是最难识破的那种** —— 它不报错、不告警，还会被人当成事实引用。
