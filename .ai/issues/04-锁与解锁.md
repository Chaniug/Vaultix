## 15. 「永不锁定」档位被新规则静默覆盖（2026-09-09）

- **现象**：自动锁定设为「从不 / 永久开启」后，息屏再亮屏仍然被锁
- **根因**：① 策略函数 `neverAutoLock` 写了但控制器没调用，`onStart` 无条件执行
  「keyguard 仍锁即锁」；② 档位缓存在 `@Volatile` 字段（初值默认 5 分钟），
  冷启动首帧 DataStore 首值还没到达 → 按默认档误判
- **解法**：`AutoLockPolicy.shouldLockOnResume(minutes, screenLocked, timedOut)` 让 never
  短路；控制器每次判定现取 `prefs.autoLockMinutes.first()`，删掉缓存字段
- **判据**：① 用户显式档位必须在**策略层**最高优先级并写单测；② 生命周期观察者里
  不要缓存偏好字段（DataStore / Flow 首值异步到达，首帧会用到默认值）

## 53. 快速解锁「覆盖安装 + 重启后不生效」= 三个独立缺陷叠加（2026-09-12，P0，第四十三轮）

用户原话：「新的构建包覆盖安装后会发现，指纹解锁的按钮在重启打开 APP 的时候不生效。
按照逻辑说，这个覆盖安装，应该指纹解锁不会被清除的啊」。
**用户直觉是对的：应用从不因升级/重启清注册**（无 `MY_PACKAGE_REPLACED` / `BOOT_COMPLETED` /
版本号迁移逻辑）。问题在读侧「撒谎」+ 自毁 + 死锁。

### A（最致命）解锁页卡死在 `submitting` → 按钮在、点了完全没反应
`UnlockScreen` 的 `onError` 只处理「用户取消」，`ERROR_TIMEOUT`/`ERROR_CANCELED`/
`ERROR_HW_UNAVAILABLE`/`ERROR_LOCKOUT` 落进来**无人复位** `submitting` ⇒
指纹按钮 + 主密码按钮双双置灰、转圈不散、后续点击被 `startLocalUnlock` 的守卫直接 return
⇒ **整页死锁，只能杀进程**。
**触发放大**：上一轮新增的「进解锁页自动弹一次」若在 Activity 尚未 RESUMED 时发起，
重启后（生物识别 HAL 未就绪）很容易被系统以非取消错误结束。
**修**：任何错误都复位 `submitting`；仅「用户/系统取消」安静（`ERROR_CANCELED` 也算取消）；
其余显示原因；自动弹窗改到 `lifecycle.withResumed { … }` 之后。

### B 一次瞬时失败会**自毁注册**
`isLocalUnlockUnrecoverable` 把 `UserNotAuthenticatedException`（语义 = **本次未认证**）
当成「密钥已废」→ `clearBrokenLocalUnlock` **真删用户的快速解锁注册**。
`Docs/03-密码学与密钥管理.md` 要求相反：「`UserNotAuthenticatedException` → 拉起 BiometricPrompt」。
**修**：移出「不可恢复」集合（回归锁 `userNotAuthenticated_isRecoverable`）。

### C 「钥匙丢了」被设计成「顺手把锁砸了」
`LocalUnlockKeyStore.obtainKey()` 在别名缺失时**静默新建 KEK** ⇒
payload 还在（旧 KEK 密文）→ 新 KEK 下 `Cipher.init`（per-use 认证）不报错 →
BiometricPrompt 认证**成功** → `unwrap` 抛 `AEADBadTagException` → 走自毁分支删注册。
另：`keyAvailable` 用 `containsAlias` 当健康检查 —— 平台在密钥**永久失效**时让
`getKeyMetadata()` 静默返回 null（AOSP `AndroidKeyStoreSpi`），于是「开关在、钥匙废」被当成
「从未启用」→ 按钮消失；且设置页「启用」是 `?: return@launch` 的**静默 no-op** ⇒ 用户无法自愈。
**修**：①`loadKey()`（只读，绝不新建）与 `obtainOrCreateKey()`（仅启用路径，且先删失效别名再建）
拆开；②新增三态 `kekStatus`（LOADABLE / MISSING / INVALIDATED，靠 `getKey` 而非 `containsAlias` 判定）。

### D CI「假覆盖安装」：手动触发的包签不上
`ci-debug.yml` 原先 `if: github.event_name == 'push'` 才解码固定密钥 ⇒
**`workflow_dispatch` 出的包是 runner 现生成的一次性 debug key 签的**（每台 runner 全新），
盖不上 preview 包 ⇒ 只能卸载重装 ⇒ **数据 + AndroidKeyStore 一起没**，
表现恰是「指纹解锁被清除」。**修**：改 `event_name != 'pull_request'`；
构建步骤按磁盘上是否存在 `release.jks` 决定是否注入签名参数（`release.yml` 本来就无此闸门，无需改）。

**真机排障要点（下一步若仍复现）**：应用在快速解锁链路上**没有任何日志**，
但平台会打 `AndroidKeyStoreSpi: Could not get key metadata from Keystore.`
⇒ `adb logcat -s AndroidKeyStoreSpi keystore2 BiometricPrompt Fingerprint` 边点指纹边看；
再用 `run-as` 读 `files/datastore/vaultix_settings.preferences_pb`（开关）与
`shared_prefs/vaultix_secure.xml`（payload）区分「开关丢」/「payload 丢」/「KEK 废」。

## 61. 查看锁 vs 真锁：两条成功分支必须分开写（2026-09-12，第四十八轮）

**用户要求**：「主页密码条目上方的锁按钮应该**只锁生物验证那一层，解锁密钥不应该被清除**」。

**落地**：`VaultSessionManager.viewLock`（只置内存标记）+
`RootNavState.VaultLocked(vaultId)`（携带目标库 id）+ `UnlockScreen` 的
`ViewLockedContent`（**只有**生物识别按钮，不渲染主密码 / 2FA）。

### 三个真实会踩的坑（都已有断言/注释钉住）

**① 根导航判定顺序**：查看锁的库在会话层面**仍是已解锁**（`unlockedIds` 含它），
所以 `viewLocked` 必须排在「已解锁 → 主界面」**之前**。顺序错了的表现不是报错，
而是「按了锁按钮什么都没发生」——最难查的一类。

**② 自动选库顺序**：查看锁的库 `!it.unlocked` 为 false，若解锁页先按「第一个未锁定的库」
选目标，用户在多库场景下会被要求解锁**另一个**库。必须先看 `isViewLocked`。

**③ 标记的清理**：真锁（超时 / 冷启动 / 退出数据库）必须**同时清掉查看锁标记**，
否则密钥都没了、标记还在 → 根导航把界面收在「已解锁但查看锁定」的分支上，
用户输完主密码又被弹回解锁页（死循环的观感）。
清理点放在 `VaultSessionManager.lock / lockAll` 里（一处收口，不散在调用方）。

### 另一个必须分开的点：成功分支不同
- 查看锁认证成功 → **只 `clearViewLock`**，不动密钥（密钥本来就在）；
- 真锁生物解锁成功 → `completeLocalUnlock`（解封 KEK 重建会话）。
合并成一条就会「认证完还得解封一次」——那正是用户抱怨的「解锁完还要再验证一次」。

判据写进了 `UnlockViewModel.completeLocalUnlock(cipher, forViewLock)` 的**显式参数**，
而不是读调用时刻的状态：认证对话框弹出期间状态可能被其它流改写（读状态会走错分支）。

## 73. 覆盖安装后首次解锁慢、指纹弹得晚 —— 密钥运算跑在主线程（2026-09-13）

**现象**：覆盖安装后有时指纹框不能第一时间弹出，「像每次都要重新验证登录密钥链」；
Bitwarden 库同步后本应已缓存在本地，打开却慢。

**根因**：`viewModelScope.launch` **默认跑主线程**，而里面做的是 Keystore 往返、
`prepareLocalUnlock` / `completeLocalUnlock`、PBKDF2 / Argon2 派生 ——
全是毫秒到百毫秒级的阻塞调用；`localUnlockAvailable` 也在主线程做 Keystore 查询。
主线程一卡，BiometricPrompt 的弹出与动画就被推迟。此外 cipher 是**点按钮才创建**的，
用户看到指纹框时密钥还没备好。

**解法**：上述全部 `withContext(Dispatchers.IO)`；`localUnlockAvailable` 加
`flowOn(Dispatchers.IO)`；`localUnlockAvailable` 一到位就后台 `prewarmCipher(id)`
把 BiometricPrompt 需要的 cipher 备好。

**判据**：**`viewModelScope.launch` 的默认调度器是主线程。**
任何 Keystore / 密钥派生 / 数据库 / 文件 IO 都必须显式切走。

## 85. KEK 健康判据：**探测要宽、失败判定要严**（2026-09-13，第五十二轮）

- **现象**：**覆盖安装后**指纹入口整条消失（"生物验证不出现"）。
- **根因**：判据写成了"**不是永久失效就算可用**"，两个方向都过宽：
  ① 把 `UnrecoverableKeyException` 也算"永久失效"——而 OEM（实测华为/荣耀 KeyMint）在
  「覆盖安装后 Keystore 瞬时不可用」「密钥在但本次未认证」这类**可恢复**场景下同样抛它；
  ② `MISSING`（别名根本不存在）也被当成"可用"（`kekStatus != INVALIDATED`）。
- **解法**：**探测**（要不要给用户显示指纹入口）只认 `KeyPermanentlyInvalidatedException`
  （沿 cause 链找），且 `MISSING` **必须算不可用**；
  **失败判定**（失败后要不要清状态，`LocalUnlockFailure`）继续把
  `UnrecoverableKeyException` / `AEADBadTagException` 算不可恢复 —— **这是刻意的**。
  **改任一侧前先想清是哪一侧。**

## 88. debug 包 → release 包**原地覆盖**后，快速解锁（指纹）失效，需重新启用才恢复（2026-09-13，第五十二轮）

> ★ **专项计划：[`Docs/progress/quick-unlock-plan.md`](../../Docs/progress/quick-unlock-plan.md)**
> —— 含复现步骤、埋点清单、观测→根因判据表、以及可先行的 UX 改进。本条目只记结论与已排除项。

> ### ⚡ 勘误 + 结案（2026-09-13 22:45）—— 下面那条"结论"**是错的**，勿再据此排查
>
> **错在哪**：原文断言「**状态（包裹密钥 / KEK）在"原地更新"过程中变成了不可解密**。
> 这是真 bug，会命中每一个升级的用户。」该断言**从未被证实**，本次实测**直接证伪**：
>
> | 实测 | 结果 | 排除了什么 |
> |---|---|---|
> | `local_unlock_enabled_https://pwd.vv1234.cn`（DataStore `.pb` 值字节 `12 02 08 01`） | **true** | 不是"开关被关" |
> | `shared_prefs/vaultix_secure.xml` 含 `local_unlock_key::https://pwd.vv1234.cn` | **payload 在** | **`disableLocalUnlock` / `clearBrokenLocalUnlock` 从未执行**（二者都会删该 payload） |
> | `bw_access::` / `bw_refresh::` / `bw_protected_key::` | 均在 | 与"凭据库密钥"无关，不用重登 |
>
> **决定性反证**：用户原话「**必须清掉后台打开，才能看到指纹解锁**」——
> 若 KEK 真是 `MISSING`/`INVALIDATED`，**重启进程不可能恢复**。⇒ 只能是 **UI 状态被固化成错值**。
>
> **真实根因：`UnlockViewModel` 的 `vaultId` 竞态。**
> "选库"（协程 A，`:140`）与"订阅可用性"（协程 C，`:169`）**并发**收集同一个 `observeVaults()`；
> C 若先处理同一次发射，其 `.map` 读到的 `var vaultId` 仍是空串 ⇒ `return@collectLatest` 跳过，
> 而 `localUnlockAvailable` 的**唯一写入点**（`:179`）正在其后 ⇒ 状态**永久停在初值 `false`**
> ⇒ **指纹入口不渲染、生物识别也不自动弹**（`eligible` 里含同一项）。
> 重建 ViewModel（手动返回 / 清后台重开）才有一次重掷机会 —— 与全部用户观感吻合，
> 也解释了"系统 keystore 日志一条都没有"（压根没读密钥）。
>
> **修复**：`UnlockViewModel` 新增私有 `resolveTargetVaultId(vaults)`，订阅侧改为
> `.map { resolveTargetVaultId(it) }.filter { it.isNotBlank() }.distinctUntilChanged()`，
> **不再读跨协程 `var vaultId`** ⇒ 竞态从根上消失（语义不变：路由带参只认该库；无参才自动选库，
> 且先看查看层锁再看"第一个未锁定"）。
> 门禁：新增 `UnlockViewModelTest`（3 例）**修前精确红 → 修后绿**；全模块 detekt ✓ /
> `:app:compileFullDebugKotlin` ✓ / `:app:assembleFullDebug` ✓ / app 全量单测 ✓。
> 真机已覆盖安装（证书 SHA-256 一致、`firstInstallTime` 未变 ⇒ 数据未丢）。

## 131. 多库「锁」的作用域不一致：四把锁四个答案 + 单库动作带全局副作用（2026-09-29，P0-结构）

- **现象**（用户）：两个库互相解锁/加锁逻辑混乱 —— 手动锁 A，B 的冷启动恢复也没了；
  开 A 再开 B，只有 B 会被计时锁，A 永不自动锁。
- **根因**：四种「锁」作用域互不一致，且存在跨层/跨库副作用：
  1. `lockVault(id)`（`VaultRepositoryImpl.kt:326-341`）锁单库却**删全局 `house_lock_auto`**（`:340`）
     —— 删的本意对（不删则冷启动把刚锁的库悄悄开回来，「锁定」被静默撤销），错在**粒度**
     （auto 信封包的是**全局房钥匙**）与**缺状态**（没有「用户主动锁」的每库持久记录）；
  2. `lockOtherKdbxVaults(keep)`（`:231`）只覆盖 KDBX、不含 Bitwarden 云库，
     且挂在「进入条目页」这个 UI 时机；
  3. 超时定时器只认 `activeVaultId`（`VaultLockManagerImpl.kt:195-198`）；
     `CheckTimeoutReason.UserChanged`（`:271`）**全项目零调用方**（死代码）——
     而 Bitwarden 有 `handleUserSwitch → checkForVaultTimeout(previous, UserChanged)`（`:560-571`）。
- **解法**：[`多库锁模型-定稿`](../decisions/多库锁模型-定稿.md) D1（每库「用户主动锁」标记，
  不删全局信封）+ D2（每库各自计时）+ D3（档位每库一份）。
- **判据**：修完「锁 A」不得改变 B 的任何状态；每个已解锁库各有自己的定时器。

## 132. KDBX 快速解锁比 Bitwarden 慢 100 倍：房间信封包「主密码」而非「派生密钥」（2026-09-29，实测）

- **现象**（用户）：切到 KDBX 库指纹解锁要等好几秒；Bitwarden 库秒开。
- **实测**（同 App、同轮、同指纹弹窗）：BW（`pwd.vv1234.cn`）解锁 **33 ms**；
  KDBX（OneDrive `valkjin.kdbx`）**3.58 s**。指纹认证本身 ~1 s（含按手指），慢在认证之后。
- **根因**：房间信封 payload 不对称 —— BW 侧包**派生 64B full key**
  （`LocalUnlockEnrollment.kt:63-64`，取出即用，零 KDF）；KDBX 侧包**主密码 + keyfile**
  （`KdbxUnlockPayload` 线格式）⇒ 每次解锁都要重跑 Argon2id + 重解密整库。
  Bitwarden 官方同思路（`storeUserAutoUnlockKey(getUserEncryptionKey)` + `DecryptedKey`）。
- **顺带解释**：登记 KDBX 时多输一次主密码是**密码学必然**（解锁后内存只有库明文，
  密码本体不保留）；信封改包派生密钥后「已解锁时登记」即可免输入 —— 一箭双雕。
- **解法**：定稿批次 B —— KDBX 信封改包 KDF 后 masterKey（文件头 HMAC 校验开库，
  校验失败回退主密码重跑并重包裹）。

## 194. 🟡 附件解密后的明文留在 `cacheDir` 里，锁库不清（2026-10-26，对比审计）

- **现象**（用户看不见）：下载一个附件后，`cache/attachments/<itemId>/<id>_<name>` 里躺着
  **解密好的明文**。用户锁库、离开设备、甚至删掉那条密码 —— 文件还在。
- **根因**：`ItemDetailViewModel.downloadAttachment` 落在 `cacheDir` 下就算完事。
  `cacheDir` 只对本应用可读，所以**不是"没风险"，而是"风险窗口可控却没人关窗"**：
  系统只在**存储空间不足时**才回收缓存 —— 一台 512G 的手机可能几个月都不回收一次。
- **修法**：新增 `SensitiveCache`（`util/`）作为**敏感落盘缓存的唯一归口**：
  1. 所有敏感缓存挂在**同一个根** `cache/vaultix-sensitive/` 下
     （`attachments/`、`thumbs/`），`clearAll()` 只需删一次根目录
     ⇒ **将来谁再往根下加第三种敏感缓存，自动被清，不需要回来改 `clearAll`**
     —— "清除的覆盖面不能靠记得"；
  2. `setVaultToLocked` 里 `runCatching { sensitiveCache.clearAll() }`；
  3. `deleteItem` 成功后 `invalidateFor(itemId)`（删条目前清没意义：删可能失败，
     KDBX 写回冲突等，失败时条目还在、缓存还得用）；
  4. `invalidateFor` 按 `CACHE_KINDS` 表逐项清 ⇒ **新增一种缓存必须在这个表里登记**
     （挂在根下只保证 `clearAll` 覆盖，"删单条"要登记）。
- **⚠️ 与 `VaultixClipboard.clearNow()` 的关键区别**：剪贴板是全系统共享的一块地，
  清之前必须确认"是我放的"；`cacheDir` 下这几个子目录**只有本应用会写**，
  所以这里**无条件清** —— 少一层判断，就少一次"判断错了于是没清"。
- **⚠️ 别误伤 `cache/dev_logs/`**：那是用户主动导出的排查日志，与库内容无关，
  保留策略是"只留最近若干个"。把它一起删掉 = 用户刚导出的日志在锁库那一刻消失。
  ⇒ 单测里有一条**反向锁定**（`clearAll_不碰导出日志目录`）。
- **验证**：`SensitiveCacheTest`（6 条，用**真实 TemporaryFolder**，不 mock 文件系统 ——
  本类的全部价值就是"真的删掉了"）+ `VaultLockManagerImplNeverTest` 两条
  （`自动锁定后清明文附件缓存` / `Never档_绝不清明文附件缓存`）。
- **判据**：**"临时文件"不等于"安全文件"**。凡是解密后落盘的明文，都要回答
  "它什么时候消失" —— 如果答案是"系统缺空间的时候"，那就等于没有答案。

  `MainDispatchers.kt:111` / `HandlerDispatcher.kt:51`。**本地同版本绿**，且此前同一文件
  跑过很多次都绿 ⇒ 偶发，不是必现。
- **根因**：`UnlockViewModel` 的三个测试接缝（`testingScope` / `testingIoDispatcher` /
  `testingBlockableIoDispatcher`）只能**构造之后**赋值（Hilt 不许把 `viewModelScope`
  注入构造，#174 已记四种失败尝试）。而观察协程是在 `init { … }` 里 `scope.launch` 起的 ——
  **`init` 在构造期间就跑**，那一刻 `testingScope` 还是 null ⇒ 落在 `viewModelScope`
  （= `Dispatchers.Main.immediate`）。
  单测 `@Before setMain(dispatcher)` 换掉的只是**当时**的 Main；`@After resetMain()` 把
  它卸掉时，仍挂在旧 Main 上的任务一执行就炸。**构造期间与赋值之后用的不是同一个调度器。**
- **修法**（两步，缺一不可）：
  1. 观察协程的启动从 `init` 里抽成 `internal fun startObservers()`，带
     `AtomicBoolean` 幂等守卫；`init` 只在 `testingScope == null`（= 生产）时自启。
  2. 两个测试工厂（`UnlockViewModelTest` / `StaleRoomResealTest`）在**接缝全设完之后**
     调一次 `startObservers()`。
- **判据**：**接缝的生效范围必须覆盖"用到它的第一个协程"**。`init` 天然不满足这一点 ——
  凡是"构造后赋值才生效"的测试接缝，都不能让真实协程在 `init` 里起。
- **为什么这次不是"再加一次 setMain"就能解决**：问题不在 Main 被卸掉，而在**有两个 Main**
  先后存在。把 `setMain` 调两次只会让第二个也变成"旧的"。

## 210. 「从不」档 ≠ 用户以为的「清后台/锁屏后要验证」——开发者设置收纳「保持不锁」（2026-10-30）

### 现象（用户原话）

> 「release 版本在后台清掉 app，再次打开 app 的时候需要指纹解锁，而预览版是不需要的，
> 这样对吗。我感觉 app 清掉后台或者锁屏后，指纹解锁是正确的方案。当然了开发的时候
> 避免 app 频繁上锁，保持不锁状态也有好处，只是开发预览版是否要加一个开发者设置，
> 在里面把日志、上锁的和完全不锁的功能都放到里面。
> 上述的两个环境都是在 app 设置里面锁与安全里面设置了自动锁定时间为**从不**的状态下。」

### 先把两个事实分开（这是本条最容易看错的地方）

| 事实 | 结论 |
|---|---|
| 「从不」档下 `VaultLockManagerImpl` 会不会锁 | **不会**，任何触发源（`AppBackgrounded` / `AppCreated` / `UserChanged`）都 `return@launch` |
| 「从不」档下进程死亡后要不要验证 | **不要**：`AutoRestoreTrigger` 存在信封 ⇒ 免交互恢复（现成的 `Never档_进程创建_不锁定` 用例钉着） |
| 用户想要的「清后台 / 熄屏回来要指纹」是哪一档 | **`OnAppRestart`（重启 App 时）**，不是「从不」 |
| `Immediately`（立即） | 也会锁，但它连「切后台一秒又回来」都锁，太吵 |

⇒ 所以「正式版要指纹、预览版不要」若**两个包都是「从不」**，按代码不可能出现
（两条路径读的是同一个 `VaultTimeoutPreferences`）。**可能的解释只有两类**，且都不需要改锁模型：

| 解释 | 怎么自查（30 秒） |
|---|---|
| ① 两份实际档位不同（预览包覆盖安装后偏好没跟过来，或某一包停在「重启 App 时」/「立即」） | 打开「设置 → 锁与安全」，看**自动锁定**那一行的副标题——它就是当前生效档位，别凭记忆 |
| ② 正式版那次是**手动锁**（主页锁按钮 = 查看层锁）或**指纹门锁待重装**导致的"看起来要验证" | 看解锁页是「只有指纹按钮」（= 查看层锁）还是「主密码 + 指纹」（= 真锁） |

⚠️ **不要**为了"让两版一致"去改 `Never` 的语义：那会推翻 2026-09-29 的二次定稿
（`VaultLockManagerImpl.checkForVaultTimeoutInternal` 的 KDoc「为什么推翻」），
并且让「从不」变成和 Bitwarden 不一致。

### 落地：开发者设置里加一个「保持不锁」

用户明确要的是**开发便利**，不是新产品档位 ⇒ 做成 **debug-only 开关**：

| 层 | 位置 | 做法 |
|---|---|---|
| 偏好 | `VaultixPreferences.DEV_RELAX_SCREEN_LOCK` | `true`（默认）= 照档位执行；`false` = `OnAppRestart` 退化成「不锁」 |
| 消费 | `VaultLockManagerImpl` `OnAppRestart` 分支 | `if (devRelaxScreenLockEnabled()) handleTimeoutAction(vaultId)`，**只**拦这一档 |
| UI | `SettingsScreen.DeveloperSection` | 与「查看与导出日志」同组，整组仍在 `if (BuildConfig.DEBUG)` 内 |

- **⚠️ 读失败按 `true`（锁）**：这是安全判定，宁可多锁一次。与项目里那些
  `runCatching{}.getOrDefault(false)` 的"图省事"兜底**方向相反**，别照抄。
- **⚠️ 不把「自动锁定」整行搬进开发者组**：它已是「锁与安全」页的一等设置
  （2026-09-30 晚用户拍板的位置），搬进 debug-only 组会出现两份入口，而 debug 包
  恰恰是天天在用的那个 ⇒ 两份必然漂移。开发者组里只放这个**辅助开关**，副标题
  直说"正式版没有这一项"。
- **⚠️ `VaultixPreferences` 已顶格 40 个函数**（detekt `TooManyFunctions`）：写口做成
  带 `@set:JvmName("setDevRelaxScreenLock")` 的 write-only 属性，Kotlin 调用方写法
  （`prefs.setDevRelaxScreenLock = false`）与普通 setter 一致，但不占第 41 个名额。
- **⚠️ relaxed mock 的 `Boolean` 恒 `false`** ⇒ 等于"开发者开关关掉了" ⇒ `OnAppRestart`
  用例会**静默变绿**（锁根本没发生）。测试里三处构造都要显式 stub 成 `true`。
- **验证**：`VaultLockManagerImplNeverTest` 新增 3 条 ——
  `OnAppRestart档_进程创建_立即锁`（正向 + 守"生产默认没被改"）、
  `OnAppRestart档_开发者保持不锁开关关掉后_进程创建不锁`、
  `开发者开关关掉后_五分钟档_照旧到点锁`（反向边界：不许把别的档一起关掉）。

## 213. 🔴 用户报「还是点不动」的真因：**两个负号相消**，开关被接成恒等映射（2026-10-30 二次回归）

### 现象

#212 修完命中框后，用户复测：**「好像还是无法点击这个按钮，按钮始终是打开状态的」**。
注意后半句 —— "始终是打开状态"不是"没反应"，是**状态永远不变**。这句话本身就是线索：
如果点击压根没落到控件上，用户通常说"点不动"；说"始终是打开"，说明他看到的是
**一个会回弹/不动的确定状态**。

### 真因：`checked` 与 `onCheckedChange` 的语义不同向

第一版把偏好写成**反义**（`true` = 仍需验证），UI 又在调用点取反了一次：

```kotlin
// 偏好：true = 仍需验证（与开关标题「保持不锁」相反）
SettingsSwitch(
    value = relaxScreenLock,                                   // true → 开关显示 ON
    onCheckedChange = { relax -> setDevRelaxScreenLock(!relax) }, // 又取反一次
)
```

而 Compose 的 `Switch` 内部是 `toggleable(value = checked)`，回调传进来的
**已经是"新值"**（`!checked`）。于是：

| 步 | 值 |
|---|---|
| 偏好 | `true` |
| 开关 `checked` | `true`（ON） |
| 用户点一下 → `onValueChange(!checked)` | 回调收到 `false` |
| 调用点再取反：`setDevRelaxScreenLock(!false)` | 写入 `true` |
| 回流 | `true` → 开关**仍是 ON** |

**`f(!x) = x`**：每次点击都把**当前值**写回去，是恒等映射。而且它是**双向**不动点 ——
初始为 `false` 时同样写回 `false`，开关同样不动。用户看到的就是"永远是打开状态"。

### 为什么上一轮没抓到

- 数据流单测全部通过：**写口确实写成功了**（写的就是那个旧值），只是写的值没变；
- 编译/detekt/单测都看不见：类型完全合法，`!` 是最普通的运算符；
- #212 的命中框问题**也是真的**（52×32dp 确实小于 48dp），修完它之后这个逻辑 bug 才浮出来，
  于是被误读成"上一轮的修复没生效"。

⇒ 这正是 #121 / #212 的同一族：**"点了没反应"至少有两层（命中框 / 状态机），修完第一层要重新复测，
不能假设第二层不存在。**

### 修法：把语义翻正，让"显示的值"和"写入的值"是同一个布尔

| 层 | 改动 |
|---|---|
| 偏好 | 语义改为**与键名同向**：`true` = 保持不锁（不验证），默认 `false`（= 与正式版一致） |
| 键名 | 换成 `dev_relax_screen_lock_v2` —— 旧键存的是反义，复用会让老机器上的 `true` 静默变成"不锁" |
| 锁管理 | `if (!devRelaxScreenLockEnabled()) handleTimeoutAction(vaultId)`；读失败默认 `false`（不放松 = 照常锁） |
| UI | `onCheckedChange = viewModel::setDevRelaxScreenLock` —— **不做任何取反**、不写 lambda |
| 文案 | `desc_normal` / `desc_relaxed` 两个名字按"当前行为"命名，不再用 on/off（on/off 指的是开关，容易再次读反） |

### 判据（三条，都能复用）

1. **布尔控件回调的参数是"新值"**：Compose 的 `Switch` / `Checkbox` / `toggleable` 传
   `!checked`。在调用点再取反，等于把状态机接成 `f(!x)=x` 的**恒等映射** ——
   症状是"点了永远不动"，而不是"点了报错"。
2. **一个布尔偏好的名字必须与真值同向**。`dev_relax_screen_lock = true` 却是"要验证"，
   就是这次双负号的土壤。取名时先问一句："`true` 时开关该是开还是关？"
3. **改语义时要换键，不要复用**。旧键可能已被旧语义写过；复用 = 让旧数据在新语义下被误读，
   而这类误读的方向往往正是"放松安全"（本次是 `true` 从"要验证"变成"不锁"）。

## 214. ✅ 「从不」档对齐 Bitwarden：**两层锁**（密钥层不锁 / 界面层验证指纹）+ 新增「系统锁屏时」档（2026-10-30）

### 现象与用户原话

> 「感觉这一块的逻辑可以直接参考 bitwarden 的，它的保护效果很不错，另外开启了从不锁定的设置，
> 屏幕熄屏或者清除后台后，bitwarden 好像还是会需要指纹解锁生物验证解锁。但是好像填充并不会受影响，
> 意思是开启了从不锁定，自动填充依然是生效的，只是进入 bitwarden 这个软件的时候需要验证指纹，其他的不变。
> 你仔细看一下相关的代码就知道我说的了」

用户描述的是一个**同时成立**的组合，而不是三选一：

| 场景 | 「从不」档下用户期望 | 上一版行为 | 判定 |
|---|---|---|---|
| 熄屏后回到 App | 要指纹 | 直接进去（`Never` 任何触发源都不锁） | ❌ |
| 清后台后重开 | 要指纹 | 信封**免交互**恢复，直接进去 | ❌ |
| 自动填充弹窗 | **不受影响** | 正常 | ✅ |
| 库里密钥 | **不要求重新输主密码** | 在内存里 | ✅ |

关键在**后两行**：如果按最直觉的修法「熄屏就锁库」，虽然第 1、2 行满足了，但第 3 行（填充要重新认证）
和第 4 行（密钥清零、下次要主密码）会被一起破坏 —— **用户明确说了"其他的不变"**。

### 真因：只有一层锁，而用户要的是两层

读代码确认了两处（用户说的"仔细看一下相关的代码"指的就是这里）：

1. `AutoRestoreTrigger`：`Never` + 密钥在内存 ⇒ 注册信封；`Never` + 已锁 + 有信封 ⇒
   **`restore()` 不要求生物识别**（信封用的是不需要认证的 Keystore 密钥）。所以"清后台"这条路
   是**完全静默**的 —— 进程被杀了也能一声不响地开回来。
2. `VaultixApplication` / `AutoLockController` 只调 `onAppCreated` / `onAppBackgrounded`，
   `Never` 分支对两者都直接 `return` ⇒ **没有任何东西去挡界面**。

⇒ 结论：缺的不是"更狠的锁"，而是**把「密钥可见性」和「界面可见性」拆成两个独立开关**。
只加一层（锁得更狠）必然违反"其他的不变"。

### 修法：两层锁（复用已有的 `viewLocked`，不新增锁类型）

第二层其实**项目里早就有** —— `VaultSessionManager.viewLockedIds`（"查看锁"，#61）：
锁住界面但**不动密钥**，`UnlockScreen` 会渲染成"只有一个指纹按钮"的 `ViewLockedContent`。
上一版没用它的原因很单纯：`viewLockedIds` 是**手动**的（用户长按"锁此库"），
没有任何地方在熄屏/恢复后自动给它加标记。于是本轮做的是"给已有机制补一个**自动**入口"：

| 层 | 状态位 | 熄屏/清后台后 | 填充链路 | 谁设置 |
|---|---|---|---|---|
| 密钥层 | `sessions`（已派生密钥） | **保持** | 照常用 | 只有真锁（超时/手动锁库）才清 |
| 界面层 | `viewLockedIdsState`（含 `autoViewLockedIdsState` 子集） | **置位** | 直通（看穿） | `AutoViewGate` |

`viewLocked` 加了 `automatic: Boolean = false` 参数，自动标记放在
`autoViewLockedIdsState` 这个**子集**里，目的是让两件事同时可判定：

- `isViewLocked(id)` —— 界面要不要挡（手动 + 自动都算）；
- `isAutoViewLocked(id)` / `anyManualViewLocked()` —— **这是不是"只是挡住界面"**。

自动标记是**可升级**的：同一库先被自动挡、再被手动锁，`viewLocked(automatic = false)`
会把 `autoViewLockedIdsState` 里的 id **减掉**（手动锁的语义更重，填充要认证）。
`lock()` / `lockAll()` / `clearViewLock()` / `clearAllViewLocks()` 两套标记**一并清**。

### `AutoViewGate`：只有两个触发点，且五个前置条件缺一不可

新增 `security/AutoViewGate.kt`，**只**在这两个时刻被调用：

1. `VaultLockManagerImpl.onScreenOff()`（`ACTION_SCREEN_OFF`）；
2. `AutoRestoreTrigger` 信封恢复**成功且确实开了库**（`report.opened > 0`）之后 ——
   对应"清后台再打开"。注释写在调用点：**恢复 ≠ 免验证**。

⚠️ **普通切后台不触发**。这是刻意的：复制密码→切去粘贴是最高频的操作路径，
如果在 `onAppBackgrounded` 就挡界面，`Never` 会退化成 `Immediately`（用户要的是"其他的不变"）。

五个前置条件（`gateUnlockedVaults()` 依次判，任一不满足就**整体跳过**）：

| 条件 | 不满足时 |
|---|---|
| 有已解锁的库 | 无事可做 |
| 产品开关 `autoViewGateOnNever`（默认 `true`） | 用户主动关掉 |
| 该库档位 == `Never` | 其他档位本来就会真锁，不需要门禁 |
| 指纹门锁可用（`fingerprintLockAvailable`） | **跳过**，否则退化成"每次回来输主密码" |
| 开发者「保持不锁」关 | 开发便利优先 |

⚠️ **指纹可用性这一条是硬要求，不是优化**：没有指纹时"门禁"= 每次回来输主密码，
比不做门禁更糟，而且会被当成 bug 报上来。

⚠️ 这里的读失败全部 **fail-open**（`getOrDefault(false)`），与 `devRelaxScreenLockEnabled()`
的 fail-closed **方向相反**，且是故意的：这一层决定的是「**要不要挡界面**」（可用性问题），
不是「要不要清密钥」（安全问题）。读不到偏好时挡住用户 = 把人关在门外，代价远大于放行。

### 填充为什么不受影响：看穿自动标记

`AutofillActivity` 原本的 `hasViewLockedVault()` 改名为 `hasManualViewLockedVault()`：

```kotlin
if (!sessionRepository.anyManualViewLocked()) return false      // 没有任何手动锁 → 直接放行
val unlocked = vaultRepository.observeUnlockedVaultIds().first()           // 取已解锁库
return unlocked.any { sessionRepository.isViewLocked(it) && !sessionRepository.isAutoViewLocked(it) }
```

即：**手动锁仍然要认证**（安全不能被门禁偷偷削掉），**自动门禁一律看穿**（用户："填充并不会受影响"）。
两个方向都有单测钉住（含"手动锁覆盖自动标记"的那条）。

### 顺手补齐 Bitwarden 的档位：`VaultTimeout.OnSystemLock`

用户说"直接参考 Bitwarden"，而 Bitwarden 2025.11.0 的锁定档位里有 **`On system lock`**。
本轮把它补上（`STORAGE_ON_SYSTEM_LOCK = -3`）：

```kotlin
override fun onScreenOff() {
    onAppBackgrounded()                                  // 原有：分钟档计时
    scope.launch { autoViewGate.gateUnlockedVaults() }    // 新增：从不档界面门禁
    scheduleSystemLockCheck()                            // 新增：系统锁屏档
}
```

- 判定用 **`KeyguardManager.isDeviceLocked()`（严格）**，不是 `isKeyguardLocked`：
  后者在"只滑动解锁"的设备上熄屏即为 `true`，会让这档变成"熄屏即锁"，与文案不符。
- 熄屏瞬间系统**还没**把设备标记为 locked ⇒ 300ms 后**复查一次**；`screenOffToken`
  在 `onScreenOff` / `onScreenOn` 都会自增，用于取消过期复查（亮屏了就不用再锁）。
- 该档在 `CheckTimeoutReason` 里只认 `SystemLocked`：进程创建 (`AppCreated`)、
  切后台、换用户都**不锁**（否则它就跟 `Immediately` 没区别了）。有专门的回归用例。

⚠️ **`-3` 与"负数 = 旧键的 Never"冲突**：`fromLegacyMinutes()` 对 `-3` **仍然返回 `Never`**
（旧版根本没这个档，读出 `-3` 只能是脏数据/被误写），`assertNotEquals` 钉死。
新键 `fromStorageValue` 才认 `-3`。

### 判据（四条）

1. **"锁"至少有两种，先问锁哪一层**。「密钥在不在内存」和「界面要不要验证」是两个独立问题；
   把它们合成一个布尔，就必然要在"填充要重新认证"和"清后台能直接进"之间二选一。
2. **门禁类改动必须先问"退化路径长什么样"**。没有指纹时门禁会退化成主密码门，
   ⇒ 前置条件里必须有"能力可用"，否则安全改动会变成可用性事故。
3. **自动置位的锁态必须是可区分的子集**，不能和手动锁共用同一个标志。
   共用之后，下游（这里是自动填充）只能二选一：要么一律要认证（违反用户），
   要么一律放行（把手动锁废掉）—— 后者是安全倒退。
4. **读失败的默认方向由"代价更大的一侧"决定**：清密钥失败 = 放行（可用性灾难，fail-closed）；
   挡界面失败 = 挡住（把人关在门外，同样灾难）⇒ 同一项目里两种方向可以并存，
   但**每一个都必须写出理由**，否则下一个人会"统一"成一种。

## 215. ✅ 「进 App 要验两次指纹」——认证是全局的，门禁标记却是按库的（2026-10-31，#214 的直接后续）

### 现象与用户原话

> 「进入 app 时候验证指纹怎么需要两次，两个密码库？两个密码库不应该是同一个指纹吗，
> 指纹检验一次就够了啊」

用户有两个密码库。熄屏后重新进 App：验证一次指纹 → 进第一个库 → **切到第二个库又弹一次指纹**。
用户的判断完全正确，这不是"设计如此"，是 bug。

### 真因：认证粒度 ≠ 门禁粒度

#214 加的两层锁，第一层（密钥）是**全局**的（房子化后只有一把门锁 `HouseKeyStore`），
第二层（界面门禁）的标记却是**按库**存的（`viewLockedIdsState: Set<String>`）。
三处一串联就必然出这个症状：

| 环节 | 行为 | 后果 |
|---|---|---|
| `AutoViewGate.gateUnlockedVaults()` | 熄屏时给**每个**已解锁的「从不」库各打一个 `automatic = true` 标记 | 两个库 ⇒ 两个标记 |
| `RootNavViewModel` | 判据是「**任一**库带查看锁 ⇒ 收回解锁页」 | 只要有**一个**标记剩着，整个 UI 就停在解锁页 |
| `UnlockViewModel.completeLocalUnlock(forViewLock = true)` | 只调 `clearViewLock(vaultId)` | **只清了当前库** ⇒ 另一个标记还在 ⇒ 再验一次 |

所以"验几次"= 用户有几个库。库越多越离谱，这不是能用"多点一次"糊过去的量级问题。

> **为什么 Bitwarden 没有这个 bug**：它的锁定态是**账号级**的（一个账号一次认证），
> 「认证粒度」与「门禁粒度」天然一致。#214 把门禁细化到库、却没同步细化认证 —— 错位就出现了。

### 修法：把认证粒度对齐到全局（不是把门禁粗化）

新增 `VaultSessionManager.clearAutoViewLocks()`，**只从 `viewLockedIds` 里减去 `autoViewLockedIds` 子集**：

```kotlin
suspend fun clearAutoViewLocks() {
    mutex.withLock {
        viewLockedIdsState.value = viewLockedIdsState.value - autoViewLockedIdsState.value
        autoViewLockedIdsState.value = emptySet()
    }
}
```

UI 侧只改一行：`clearViewLock(vaultId)` → `clearAutoViewLocks()`。
`VaultSessionRepository` 加同名接口成员（零逻辑直通实现）。

**"一次认证够全部库"的理由**：验的是"你是不是本人"，这件事与"哪个库"无关。
按库的标记只是 UI 的**存储方式**，不该被升格成"每个库各验一次"的**语义**。

### 刻意没选的两个修法（都会被写回来，所以在这里钉死）

| 候选 | 为什么不选 |
|---|---|
| `clearAllViewLocks()` | 会把手动查看锁一起抹掉 —— 用户锁了 A，验个指纹 A 也开了，**安全语义倒退** |
| UI 里 `for (id in ids) clearViewLock(id)` | 绕了一圈还是"逐库清"，且**漏掉之后才出现的库**；把粒度错位固化进 UI 层 |

子集相减是**唯一同时满足两个方向**的写法：自动标记跨库全清、手动锁一个不动。

### 测试：两层各钉一遍（缺一层会假绿）

| 层 | 文件 | 钉的是什么 |
|---|---|---|
| 数据层 | `VaultSessionManagerTest.清自动门禁_跨库一次清干净_手动锁原样保留` | 集合代数：`bw` 自动 → 放行；`kdbx` 自动 + 手动 → 仍锁住；`anyManualViewLocked() == true` |
| UI 层 | `ViewUnlockScopeTest`（新，2 条） | **UI 到底调了哪个方法**：`clearAutoViewLocks()` 恰好 1 次、`clearViewLock` 0 次、`clearAllViewLocks` 0 次；查看锁分支不碰密钥（`viewLock` 0 次） |

⚠️ 只写数据层用例的话，**把 UI 改回 `clearViewLock(vaultId)` 依然全绿** —— 这个 bug 的现场就在
UI 这一行，回归门禁必须钉在调用点上。

|---|---|

| 单测 | ✅ **1422 例，失败 0 例**（含本轮新增 3 例） |

### 判据

1. **认证的粒度必须与门禁的粒度对齐**。要么门禁全局（#214 之前），要么认证全局（本轮）。
   一个全局、一个按库 ⇒ 立刻退化成"每个库各验一次"。
2. **"存储方式"不许升格成"语义"**。按库存标记是为了知道"锁哪几个库"，
   不是为了让用户按库出认证。
3. **收窄清除范围的功能，必须成对思考"扩大清除范围"的风险**。`clearAllViewLocks()` 顺手可取，
   但它会连带手动锁 —— 所以正确解是**新增一个更精确的方法**，而不是放宽已有的那个。
4. **子集标志的第二次回报**。#214 引入 `autoViewLockedIdsState` 时只是为了让自动填充
   能"看穿自动门禁、仍尊重手动锁"；本轮它又正好是"只清自动、不动手动"的现成工具。
   ⇒ 把一个"看起来多余"的区分做出来，往往在下一次改动里就还回来。

### 顺手修的流程问题：Release 说明对用户不友好

自动生成的 changelog 是**提交列表**，里面有「修 CI 红」「补充文档」这类内部账。
v0.10.4 第一次发布就是这样，用户点开 Release 看到的第一条是
「AutoViewGate 从 VaultTimeoutPreferences 读产品开关（f7ac3d2 CI 红）」—— 看不懂，也没意义。

而**改不掉**：`PATCH /releases/{id}` 需要 token，沙箱里只有 SSH key（`ssh -T` 认得出身份，
但推不了 REST）。⇒ 事后修改这条路是死的。

修法（向前兼容，不碰 v0.10.4 已有的 body）：
- 新增 `Docs/release-notes/v<版本>.md`：**人工撰写**的更新内容，正文直接是内容
  （不写标题、不写元说明 —— 多一层剥离逻辑只会多一处出错的地方）；
- `release.yml` 的「Generate changelog」优先读它，**文件不存在时回退提交列表**
  （否则某次忘了写文件就等于发布失败，这条路不能断）。

判据：**自动生成的对外文案要留人工覆盖口，且覆盖必须可回退**。
纯自动 = 内部噪音外泄；纯人工 = 忘写就发不出去。
