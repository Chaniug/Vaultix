## 288. 坚果云 WebDAV 测试连接报「账号或密码不正确（HTTP 403）」

**用户原话**（2026-11-13，附真机截图）：

> 实际中，我发现 webdav 好像登录不上去

截图现场：服务器地址 `https://dav.jianguoyun.com/dav/`、账号 `chaniug@vip.qq.com`、
密码已填，点「测试连接」后红字 **`WebDAV 账号或密码不正确（HTTP 403）`**。

### 现象 → 差分实测 → 定性

先在沙箱对 `dav.jianguoyun.com` 做**匿名 / 假凭据**探测（**不触碰用户真实密码**）：

| 请求 | 结果 |
|---|---|
| 无凭据：`HEAD` / `GET` / `PROPFIND` / `OPTIONS` × `/dav/` 与 `/dav` | 全部 `401`，响应头 `WWW-Authenticate: Basic realm="nutstore"` |
| 假 `Basic` 凭据 × 4 种方法 × 3 种 UA（`curl/8.0` / `Vaultix-WebDAV` / `Mozilla/5.0`） | 12/12 全部 `401` |

⇒ **坚果云把「认证失败」稳定映射为 401**。用户带凭据拿到的是 **403**，说明
**认证已经通过**，是服务端主动拒绝。坚果云官方 FAQ（`content.jianguoyun.com/1112.html`
与 `/29740.html`）对 `403` 的原文解释是：

> 提示"dav.jianguoyun.com 服务器返回 forbidden(403) 以响应 PROPFIND /dav 的请求"
> —— 由于 WebDAV 协议不支持微信二次验证，需要到网页端的账户信息—安全选项中
> 关闭微信二次验证后才能正常使用。

另有官方帮助中心（`help.jianguoyun.com/?p=2064`）要求第三方应用必须用网页端生成的
**「应用授权密码」**而非登录密码，并限制免费版每 30 分钟 600 次请求。

**一句话定性**：这不是「密码错」，是 **App 把 403 谎报成密码错**，用户于是只能
无限重输一个本来正确的密码；同时界面从头到尾没告诉他「要用应用密码 / 要关二次验证」。

### 证伪：上一轮排查的 P0 不是这次的直接原因

上一轮 WebDAV 排查报过一个 P0：全局 `OkHttpClient` 挂的 `BitwardenAuthInterceptor`
会把 `Basic` 覆盖成 `Bearer`。本次先核死 `BitwardenAuthRepository.accessTokenForHost()`：

```kotlin
fun accessTokenForHost(host: String): String? {
    val server = serverByHost[host] ?: return null   // 陌生 host 直接返回 null
    ...
}
```

用户填的是 `dav.jianguoyun.com`，不可能登记为 Bitwarden 服务器 host ⇒ 不会覆盖。
**但 P0 依然真实存在**（同域名不同端口也会命中，因为 `hostOf()` 用 `URL(server).host`
不含端口），所以本轮仍顺手修掉，只是不把它写成这次 403 的根因。

⚠️ 长期教训：**上一轮静态排查的「最严重项」不一定是下一轮真机反馈的根因**。
先做差分实验把现象分层，再决定修哪条，别拿旧结论直接套。

### 修法（四道防线，全部改生产代码）

1. **自检改 `PROPFIND Depth: 0`，HEAD 只作降级。**
   `testConnection()` 旧实现 `HEAD` 一个**目录 URL**；坚果云官方 FAQ 里所有 WebDAV
   报错原文写的都是 `PROPFIND /dav`，且部分实现对目录 HEAD 直接 403/405。更关键的是
   **自检与 `listChildren()` 不同源** ⇒ 账号页显示 OK、添加页却列不出目录（上一轮
   排查里的 P2，被这次真机反馈升级）。现在主探 PROPFIND，`405 / 501` 才降级 HEAD，
   两条路径共用 `probeFailureOf()` **同一张判据表**。
2. **401 / 403 分流，文案收口到两处真源。**
   `credentialsMessage(401)` 说「账号或密码不正确」并点名「应用密码」；
   `forbiddenMessage(403)` 明确写「**认证已通过，不是密码错**」+ 四条可依次排除的原因
   （关微信二次验证 / 应用密码未被撤销 / 访问频率超限 / 目录权限或改子目录）。
   分流不只在 `writeFailureOf()`：**`errorMessage()` 也分流**，因为
   `stat()` / `read()` / `listChildren()` / `forceReplace()` 全走它 —— 只在写入路径
   改会漏掉大半条链路，变成「解锁说密码错、写入说拒绝访问」。
   `404` 也不再当成功：这里传的是 `normalizeServerUrl()` 出来的目录 URL，
   404 只可能是地址填错或目录没建，放行等于让用户带着一个必失败的账号进添加页。
3. **填之前就说清（`strings.xml` + `CloudAccountsScreen`）。**
   密码框下加提示：坚果云 / 群晖等需在网页端生成「应用密码」，登录密码无效；
   坚果云还需先关闭微信二次验证。光靠失败文案补救已经晚了一轮。
4. **隔离 WebDAV 专用 `OkHttpClient`（顺手修 P0）。**
   新增顶层工厂 `webDavProductionClient(shared)`：`shared.newBuilder()` **共享连接池 /
   Dispatcher / 超时**，但 `interceptors().clear()` + `networkInterceptors().clear()` +
   `authenticator(Authenticator { _, _ -> null })`。两个生产构造点
   （`CloudAccountConnector.webDavSource()` 与
   `KdbxCloudSyncCoordinator.fileSourceFor()`）**都**改用它 —— 漏一个就会变成
   「配置页能连上、真正读库被 Bearer 顶掉」的分裂现象。
   ⚠️ 单测直接构造 `WebDavKdbxFileSource(client = 假服务器)`，**不走工厂**，
   否则假服务器的 `Interceptor` 会被一起清掉（这正是上一轮 27 例 WebDAV 单测
   全部绕开 P0 的原因）。同步订正三处过时注释：`CloudAccountConnector` 的 KDoc 原写
   「不要新建、复用带拦截器的单例」、`KdbxCloudSyncAppModule` 头部同款理由、
   `BitwardenAuthInterceptor` 的 KDoc 原称「仅 `/api/` 端点预挂」（实现只跳过
   `/identity/`，注释与实现不符）。

### 6 条坑

1. **403 ≠ 401**：把两者合并成一句「账号或密码不正确」，用户动作就只剩「重输密码」，
   而真因在服务端配置 / 限流上，重输一万次也不会好。
2. **自检与使用的协议方法必须同源**：`HEAD` 探通不代表 `PROPFIND` 能列目录。
3. **错误分类要放在共同出口**：`errorMessage()` 是 stat / read / list / 强写的共同出口，
   只在 `writeFailureOf()` 分流会造出「同一状态码两套解释」。
4. **Kotlin 块注释可嵌套**：在 KDoc 里写出块注释起始符（如 `` `/**` ``）会把后面的
   代码整段吞进注释，表现为 `Unresolved reference` 与一整片 `Expecting member
   declaration`——本轮规则测试第一次编译就是这么红的，第一处错误行号在几十行之后。
5. **`forEach { … }` 要用 `}` 闭合**，写成 `)` 会把后面所有成员函数吞进参数列表
   （`Modifier 'private' is not applicable to 'local function'` 是它的典型症状）。
6. **detekt `ThrowsCount` 上限 2**：`testConnection()` / `probeViaHead()` 原本各有
   3~5 个 `throw`，改成 `probeFailureOf(): String?` 纯判据表 + 调用方各一个
   `?.let { throw IOException(it) }`。同时 KDoc 表格行超 `MaxLineLength` 也要拆。
