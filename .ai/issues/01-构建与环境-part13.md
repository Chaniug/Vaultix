## 227. 🟡 校验和「给了却验不了」：路径带 `./full/release/` 前缀（2026-11-02，v0.11.0 发版后实测）

- **现象**：v0.11.0 的 Release 页有 `checksums-sha256.txt`，内容长这样：

  ```
  626dfaa0b93b248e53720c4433067157c94a0e6d350da7aa96b564dcadc54f3c  ./full/release/app-full-release.apk
  ```

  用户把 `checksums-sha256.txt` 和 `app-full-release.apk` 下到**同一个目录**，
  按惯例执行 `sha256sum -c checksums-sha256.txt`，得到：

  ```
  sha256sum: ./full/release/app-full-release.apk: No such file or directory
  ./full/release/app-full-release.apk: FAILED open or read
  ```

  **哈希值本身完全正确**（已用 GitHub 服务端独立算的 `digest` 交叉验证过），
  但校验**跑不起来** —— 等于没有。

- **根因**：`sha256sum $apk_files`，而 `$apk_files` 是 `find . -type f -iname '*.apk'`
  的输出，天然带 `./` 前缀。CI 里这个相对路径是**构建目录结构**的产物，
  跟"用户下载后的目录"毫无关系 —— 生成端与消费端用了两套路径语义。

- **修法**：用 `basename` 重写成扁平文件名，让校验和只描述"哪个文件的哈希是多少"，
  不携带任何关于构建目录的信息：

  ```bash
  sha256sum $apk_files | while read -r hash apk_path; do
    printf '%s  %s\n' "$hash" "$(basename "$apk_path")"
  done > "$GITHUB_WORKSPACE/checksums-sha256.txt"
  ```

- **⚠️ 顺带踩到的第二个坑：循环变量不能叫 `path`**。
  第一次本地验证时脚本报 `command not found: basename` / `command not found: cat` ——
  看起来像 PATH 坏了，实际是 **zsh 里 `path` 是 `PATH` 的数组别名**：
  `while read -r hash path` 把 `path` 赋成 APK 路径，等价于把 `PATH` 覆盖成一个文件名，
  之后所有外部命令都找不到。
  CI 用的是 `shell: bash`（`path` 只是普通变量）所以不会炸 ——
  但"本地跑一次就中招"的写法不该留在仓库里，改名 `apk_path`。

- **验证**（本地三件事，缺一不算验过）：
  1. 造 7,605,555 字节的 APK 模拟产物，按新逻辑生成 checksums ⇒ 内容是
     `f3acfe92…  app-full-release.apk`（无任何目录前缀）；
  2. **模拟用户场景**：把 apk 与 checksums 一起拷到空目录，`sha256sum -c` ⇒ `OK`；
  3. **证明校验有检出能力**：`dd` 改坏 APK 第 100 字节后再跑 ⇒ `FAILED`。
     第 3 步是关键 —— 只验"通过"无法区分"校验正确"与"校验恒真"。

- **⚠️ 三条教训**：
  1. **「有校验和」≠「校验和能用」**。生成端看到文件里有哈希就以为完事，
     而消费端的路径语义完全不同。**验收要在用户的场景里做**（下载到同一目录、照文档执行），
     不是在生成端 `cat` 一眼。
  2. **只验"通过"是不够的，要验"能失败"**。哈希校验、签名校验、断言这类东西，
     恒真与正确在成功路径上长得一模一样。改坏一个字节看它红不红，成本几秒。
  3. **CI 的 `bash` 与开发机的 `zsh` 有语义差**。`path` / `status` / `pipestatus` / `argv`
     在 zsh 里是特殊变量，赋值会改掉底层状态。这类差异**只在本地跑才炸**，
     CI 永远绿 —— 所以"CI 绿了"不能替代"本地跑过一遍"。

- **顺带确认的事（不是问题，但值得记）**：v0.11.0 的 `Build Release APK` 日志明确写着
  `4 个签名 Secrets 均已配置` → `固定密钥解码通过` → `store 密码与 key 密码均已验证通过`，
  最终指纹 `7e6c8c07…`，DN `CN=Vaultix, O=Vaultix`。
  ⇒ **没有降级成一次性密钥**，用户可覆盖安装升级（#221 那类"盖不上旧包"的情况未发生）。

## 239. 🔴 一进含 `OutlinedTextField` 的页面就闪退 —— `composeBom` 只改了版本号，**没查传递依赖**（2026-11-03 晚，真机日志实证）

- **现象**：从网盘添加 KDBX → 打开「添加账号」表单 → **立刻闪退**。
  真机 荣耀 BKQ-AN00 / Android 17（SDK 37）/ `0.11.0-dev-5a94c29`。清 App 数据无效（与用户数据无关）。
- **日志本体**（异常类就写明了性质，**跟 Compose 的 measure 完全不是一回事**）：

  ```
  FATAL EXCEPTION: main
  java.lang.AbstractMethodError: abstract method
      "void androidx.compose.foundation.style.CustomStyle.applyStyle(
           androidx.compose.foundation.style.CustomStyleScope)"
      on receiver java.lang.Class<androidx.compose.material3.OutlinedTextFieldDefaults$$ExternalSyntheticLambda0>
      at androidx.compose.foundation.style.ResolvedStyle.build$foundation(ResolvedStyle.kt:109)
      at androidx.compose.foundation.style.StyleOuterNode.resolveStyleAndInvalidate(StyleModifier.kt:741)
  ```

- **机制**：`AbstractMethodError` = **实现类没有实现接口里的抽象方法**。
  这不是"代码写错"，而是**编译期接口与运行期接口不是同一个版本**：
  - 运行期 `foundation 1.12.1` 的 `CustomStyle<ScopeT>` 把 `applyStyle(ScopeT)` 定为**抽象方法**；
  - `material3 1.5.0-alpha16` 的字节码编译于 `foundation 1.11.0-beta02`，
    它合成出的 lambda 类**不具备** 1.12 那套实现 ⇒ invokeinterface 落空。
  - **实证**：`grep -rl CustomStyle` 扫 alpha16 的 `classes.jar` → **0 命中**；
    1.11.4 的 foundation 里**根本没有 `CustomStyle.class`**，`ResolvedStyle.kt:109`
    这条调用路径只存在于 1.12.x。⇒ 是 1.12 的新代码路径撞上了 1.11 时代的 material3。

- **根因（两层，第二层才是关键）**：
  1. 11-03 上午 Dependabot 把 `composeBom` 从 `2026.03.00` 拉到 `2026.09.00`，
     而 `material3` 留在 `1.5.0-alpha16`。
  2. **只回退 bom 并不够**。把 bom 改回 `2026.06.01`（请求 foundation `1.11.4`）后，
     解析结果**仍然是 1.12.1** —— `dependencyInsight` 给出的真凶是：

     ```
     androidx.compose.foundation:foundation:1.12.1
     +--- com.mikepenz:multiplatform-markdown-renderer-android:0.46.0
          \--- org.jetbrains.compose.foundation:foundation:1.12.1   ← 传递依赖
     ```

     `markdown-renderer` **0.46.0 恰好是引入 JetBrains Compose 1.12.1 的那一版**
     （0.45.0 及以前只依赖 AndroidX，实测 `.module` 元数据逐个版本比对过）。
     Gradle 冲突仲裁取高版本 ⇒ bom 的约束被一个**UI 库的传递依赖**顶掉了。

- **修法**：
  1. `composeBom = "2026.06.01"`（foundation/ui/runtime → **1.11.4**，与 alpha16 的
     `1.11.0-beta02` 同 minor）；
  2. `markdownRenderer = "0.45.0"`（去掉 1.12.1 来源）。项目只用到
     `Markdown(content = ..., modifier = ...)` 一个 API，降级无感。
  3. 验证方式不是"改完就信"，而是 `:app:dependencies` 实测：
     `foundation 1.11.4 / ui 1.11.4 / runtime 1.11.4`，`org.jetbrains.compose` 残留 **0 条**。

- **★ 教训（比结论更值钱）**：
  | 错法 | 后果 |
  |---|---|
  | 只看 `libs.versions.toml` 的注释（"bom 2026.03.00 锁 1.10.5"）就以为知道实际版本 | 注释是**历史快照**，不是解析结果；实际早已漂到 1.12.1 |
  | 改了 bom 就以为对齐了 | **bom 只是约束，不是命令**。任何传递依赖都能顶上去，必须 `dependencyInsight` 求证 |

  > **依赖"对齐"永远是"解析结果"的属性，不是"声明"的属性。**
  > 判据：`gradle :app:dependencyInsight --dependency <组:工件>` 的输出里，
  > `Selection reasons` 只要出现 `By conflict resolution`，就说明**有人在你背后改版本**。

- **顺带排掉的错误方向**（诚实记账）：
  - 前一版把崩溃归到 `OutlinedTextFieldMeasurePolicy` 的 `fastFirst`（#238）。
    那是**另一个**崩溃（同一个 App、不同入口），本次堆栈里连 `measure` 都没有。
    ⚠️ **同一个 App 可以有多个不相关的闪退，不能拿上一个的结论套下一个。**
  - 一度怀疑 R8 / MSAL：均无关。堆栈里类名完整，且异常是 `AbstractMethodError`
    （运行期链接错误），与混淆无关。

- **验证**：`:app:compileFullDebugKotlin` BUILD SUCCESSFUL；`detekt` 全 10 模块通过；
  9 个脚本门禁全绿。真机复现路径：**进「添加账号」表单**（不用点任何输入框，进页面即验）。
