## 8. 「登录易失效」三根因（2026-09-08，真机驱动，d689a37 修复）

- **现象**：app 高频提示「登录已失效，请重新登录」；重启后快速解锁尤其必现
- **根因（3 条叠加）**：
  1. 网络层从不预挂 `Authorization`——每个请求先 401 → OkHttp Authenticator 刷新 → 重试；每次调用都轮换 token，任何一次刷新失败即误报失效；
  2. `host→server` 映射只在**登录**时登记且仅存内存——进程重启后走快速解锁（不重登）则映射为空，刷新必失败（即使 access token 仍有效）；
  3. 刷新失败不分类——403（CF/WAF）/429/5xx/网络抖动全被当凭据失效（Bastion 明示过此误伤）
- **解法**：① 请求拦截器按 host 预挂 Bearer，expiresIn 落盘、到期前 60s 预刷新；② 解锁路径（含本地快速解锁）`registerServer`；③ 刷新结果三分：400/401=Invalid（重登）/ 其余=Transient（保留登录态，sync 401 按 `refreshFailureOf(server)` 归类）
- **防回退**：任何「请求不带 Bearer 直接发」或「把非 401 失败当登出」的改动都是回归

## 22. Mapper 读写字段不对称 → 静默数据破坏（2026-09-09，通行密钥 P0）

- **现象**：编辑任一条登录条目后，服务端该条通行密钥的密钥材料被清空、计数器归零
- **根因**：`mapFido2` 只读 8 个字段，`mapFido2Request` 却写 13 个 → 没读到的字段用默认值
  覆盖上传（`encryptOpt("")` 返回 null = 服务端字段被置空）
- **解法**：读侧补齐全部字段（照 Bastion `Fido2CredentialCodec` 13 字段）；
  对「写明文、读密文」的 `creationDate` 用 `decryptOrPlain` 兼容
- **判据**：**Mapper 读 N 字段就必须能写回 N 字段**，且要有「往返后逐字段相等」的回归测试；
  读不到就写默认值的写法一定会造成不可逆破坏

## 79. `PendingOp` 表可以当「未同步」判据，但**只能取条目级操作**（2026-09-13，第五十一轮）

**需求**：条目行尾要显示「已同步 / 待推送」的小云图标（参考 Bastion）。

**做法**：新增 `PendingOpDao.observeItemLevelIds(vaultId)` ——
`SELECT DISTINCT cipherId FROM pending_ops WHERE vaultId = :vaultId AND op IN ('CREATE', 'UPDATE')`，
一路经 `ItemRepository.observeSyncStates` 到两个 ViewModel 的 `syncStates: Map<String, Boolean>`，
UI 侧 `synced = syncStates[item.id] ?: true`（键存在 = 已同步；待推送的 id 不入 map）。

**为什么必须过滤 `op`**：`pending_ops` 里还有删除类（`SOFT_DELETE` / `DELETE` / `RESTORE`），
它们对应的条目**在列表里本就不可见**；让它们参与判定，只会把「已经删掉的条目」
标成「待推送」，而用户根本看不到这些行 —— 属于**判定集合与展示集合不一致**。
KDBX 库没有「云端」这一层（文件即存储）⇒ 恒返回空 map ⇒ UI 因而不画云图标。

**为什么用 Flow 不用挂起函数**：推送成功后队列行被删除，图标要**自动**
从「云 + 斜杠」变成「云」，不能要求用户手动刷新。

**接法**：**不要 combine 进主 UiState 的流**（高频小变化会重组整张表），
独立 `viewModelScope.launch { ... .collect { states -> _state.update { it.copy(syncStates = states) } } }`。

**判据**：**队列表当判据时，先问「这张表的哪些行对应用户正在看的东西」。**
判定集合 ≠ 展示集合，就会得到一批用户看不懂的标记。

## 91. 全量拉取无条件 `upsertAll` → 覆盖掉队列里的本地改动（2026-09-14，第五十三轮，4de48f6 修复）

- **现象**：离线改了某条密码 / 备注，恢复网络同步后**变回旧值**；无任何提示，用户只会
  觉得「改的东西自己跑回去了」
- **根因**：`persistCiphers` 对服务端返回的条目无条件 `upsertAll`。而 `pending_ops` 里有
  这条 = 本地有**尚未成功推送**的改动（上一轮 `flushPending` 失败留下的）。服务端那份
  是**旧版本**，无条件落库即用旧版本盖掉用户的最新意图
- **解法**：落库前先取 `pendingOpDao.listByVault(vaultId).map { it.cipherId }.toSet()`，
  `filter { dto -> dto.id !in pendingIds }` 之后再 `upsertAll`
- **与 `pruneRemovedRows` 是同一保护思路的两面**：那里也用 `pendingIds`，防的是
  「被误删」；这里防的是「被覆盖」。**改动同步落库路径时，两处要一起看**
- **代价（有意为之）**：队列条目在推送成功前保持本地版本（对——本地才是用户最新意图）；
  推送成功后队列清空，下一次同步自然取服务端版本收敛
- **判据**：**「服务端数据」不等于「权威数据」。只要本地还有未推送的意图，服务端那份就是旧的。**

## 92. 4xx 弃单只删队列行不删本地行 → 条目「凭空消失」（2026-09-14，第五十三轮，4de48f6 修复）

- **现象**：新建的条目在同步后**凭空消失**，无提示、无日志
- **根因**：`flushPending` 遇确定性 4xx（非 408/429）会「永久弃单」防毒丸卡死队列。
  但**只** `pendingOpDao.remove(op.localId)` 是不够的：这条 op 一旦离开队列，
  紧接着的全量同步里它既不在服务端集合、也不在 `pendingIds` 中
  ⇒ `pruneRemovedRows` 判定为「服务端已删除」⇒ **删掉本地行**
- **解法**：弃单时按 op 类型分流：
  - `OP_CREATE`：服务端**从未**接受它（4xx 即拒绝），本地这行注定同步不了
    ⇒ `cipherDao.deleteByIds(listOf(op.cipherId))` 立即删除。行为由「静默消失」
    变为「即刻、可追溯」
  - 其余（`UPDATE` / `DELETE` / `RESTORE`…）：本地行**是用户数据，不能删**，
    保留它，由正常全量同步按服务端版本收敛（此时服务端版本更权威）
- **★ 一般化判据**：**删掉一个「保护性集合」的成员前，先问「谁在依赖这个集合的存在」。**
  这里 `pendingIds` 同时被 `pruneRemovedRows`（防误删）和 `persistCiphers`（防覆盖）
  依赖，弃单时只想着「清队列」，就把下游两道保护一起撤掉了
- ⚠️ 该模块**没有任何日志设施**（连 `android.util.Log` 都没引）⇒ 想「记一条日志」
  时不要凭空造 `SyncLogger`；当前取舍是纯删除 + 代码注释说明

## 119. 三个「服务端有、领域模型没有」的字段被每次编辑静默抹掉（2026-09-23，第六十六轮，06f0168 修复）

- **现象（推断 + 服务端源码判据）**：在 Vaultix 里改一条条目的标题/密码后，
  - 服务端的**密码历史**（`passwordHistory`）被清空；
  - 组织共享库里的条目**掉出组织**（成员再也看不到）；
  - 多设备并发编辑**静默互相覆盖**，无任何冲突提示。
- **根因**：`VaultItem` 领域模型里没有这三个概念，`CipherRequest` 自然也没有
  ⇒ 每次 `PUT /ciphers/{id}` 的请求体都不带它们。而服务端**不是**「缺省=不改动」：
  - `PasswordHistory = PasswordHistory?.Select(...)` ⇒ 不带即清空
    （且 `Data` 是整块重建的，序列化用 `JsonHelpers.IgnoreWritingNull`，不是 patch 语义）
  - `IsOrganizationCipher => !string.IsNullOrWhiteSpace(OrganizationId)` ⇒ 不带即被当个人条目
  - `LastKnownRevisionDate` 一路传给 `SaveDetailsAsync(...)` ⇒ 不带即放弃冲突检测
- **与 #22 是同一族问题**：**「Mapper 写回的字段集 ⊊ 服务端拥有的字段集」= 静默数据破坏。**
  #22 是通行密钥段，本条是条目级的三个标量/列表字段。判据可复用：
  **任何一次「整条重写」型写入，都要先问「我这次没带上、但服务端有的字段会怎样」。**
- **解法**：**只透传、不建模**——新增三段字段原样装回请求体（**仅更新路径**），
  领域模型保持不动。新建路径不填（那时服务端没有原值，「已知版本」无从谈起）。
- **⚠️ 附件刻意不在透传之列**：服务端 `if (!hasAttachments2 && !hasAttachments) return existingCipher;`
  ⇒ 不带时**原样保留**；而附件的提交语义是「整体替换」，塞回去反而有覆盖风险。
  **「不做什么」也是修复的一部分** —— 盲目对齐字段集同样会破坏数据。
- **防回退**：`.ai/tools/verify_sync_fields.py`
  - 8 组结构检查，其中 [6] 做**构造点双向检查**：
    所有 `CipherRequest(` 构造点里，只有 `toUpdateRequest` 该带这三段，
    `toRequest` 带了就是 bug（新建无原值）。
  - 经 5 组变异确认断言非空：顶层多带 / 顶层少带 / `SerialName` 写错 /
    透传源改成常量 / 声明类型不一致 —— 均被抓。
  - 探针自身踩过的三个坑（子串匹配、注释分隔线误判、嵌套窗口漏开括号）
    都写在函数注释里；另记录一次**「变异逃逸但前提本身是错的」**的复盘：
    往嵌套 lambda 里插字段并不构成泄漏，探针判它「不算透传」是语义正确的。
    ⇒ **变异逃逸时先确认「期望它被抓」这个前提对不对，再怀疑探针。**
- **仍未做的（同族风险，另行处理）**：`attachments` / `collectionIds` / `archivedDate`
  尚未建模 —— 前两者按上面的判据**未必需要**（附件不带更安全），
  `collectionIds` 则需确认服务端是否也是「不带即清空」。

## 139. 「现查」与「快照」各写一个判据 ⇒ 必然漂移（2026-10-01）

- **现象**：`localChangedSinceLastSync` 有两处来源 —— UI 传入的 `VaultSummary` **快照**，
  和 DAO 里 **现查** 的 `vaults.syncStatus`。改 S3 时发现两处各写了一遍"什么算本地有改动"。
- **⚠️ 真正的风险不是"重复"，是漂移**：将来加一种状态（比如 `PENDING_DELETE`），
  只改了一处 ⇒ 界面说"有改动"、上传器说"没有"，而**两边都不报错**。
- **解法**：判据**收敛到类型上**，两处都调它 ——
  `KdbxCloudSyncStatus.hasPendingUpload` / `.impliesLocalChanges`（放在 `VaultSummary.kt`，
  紧挨着枚举本身）。改判据只改一处。
- **判据本身**：`impliesLocalChanges = hasPendingUpload || CONFLICT`。
  ⚠️ `CONFLICT` 也算"有本地改动" —— 它正是"两边都改了"，漏掉它 ⇒
  拉取路径会认为"本地没改"而**丢弃用户未上传的改动**（这是本仓库最不能犯的错，见 #91）。
- **纪律**：**凡"同一语义有两处来源"，先问"判据该放哪"，而不是各写一份再祈祷同步。**

## 140. 异步上传：**失败不重试**，但**必须留下 FAILED**（2026-10-01）

- 触发点在保存路径上（`KdbxItemRepository.persist` ⇒ `autoUploader.enqueue()`），
  ⚠️ **必须排在 `markLocalEdited` 之后** —— 顺序反了就会上传一份**还没标脏**的状态，
  条件写会把它当成"没变过"而跳过 ⇒ 用户以为传了，云端其实没动。
- **失败不重试**：离线时反复重试无意义（网盘一次写 5–60 s），会把 `MAX_ROUNDS` 白烧掉。
- 但 **必须落 `FAILED`** 而不是吞掉：本仓库已有 `SyncBadge` 角标能显示它 ⇒
  "传没传上去"这件事**用户自己看得见**。⚠️ 静默失败在密码管理器里是最坏的一类 bug
  （用户以为备份好了，换机才发现没有）。
- **并发**：每库一把 `Mutex`（`ConcurrentHashMap<String, Mutex>`），
  同一库串行、**不同库互不阻塞**。⚠️ 只做"串行"是不够的 ——
  做成一把全局锁会让"改 A 库"卡住"改 B 库"，而这在多库场景是常态。
- **异常不许逸出**：`SupervisorJob` + 内部 `runCatching`，否则一次失败崩掉整个上传器
  ⇒ 后续所有库的自动上传**静默失效**（又是静默失败）。

## 141. 拉取**不要另写一条路径**：复用 `resolveUsingRemote`（2026-10-01）

- `KdbxCloudSyncCoordinator.resolveUsingRemote` 已经在做「替换已解锁会话 + 落缓存 + 置 `IN_SYNC`」。
- ⚠️ 再写一个 `pull()` 从远端读字节、自己落盘 ⇒ **两条路会漂**：
  将来改了缓存格式 / 会话替换顺序，只改一处，另一条静默用旧逻辑。
- ⇒ `pull()` 的实现就是 `if (localChangedSinceLastSync) return Conflict else resolveUsingRemote(vaultId)`，
  **只在前面加一道闸**，字节处理一行都不自己写。
- ⚠️ **闸的位置对了才有用**：这道闸必须在**拉取之前**，不能在"拉完发现冲突再回滚" ——
  拉完再回滚意味着本地改动**已经先被覆盖过一次**（覆盖了再"恢复"不是恢复，是二次风险）。

## 147. ⭐ 占位实现**假装是兜底**：死类把错误结论写成了定论（2026-10-01）

- 现象：`KdbxCloudSyncModule` 里挂着一个 `RequiresUnlockSessionReplacer`（`@Inject constructor`），
  `replace()` 恒定返回 failure「云端已更新，请先锁定并重新解锁该密码库，再执行同步」。
- **它其实从未被注入过**：`@Inject constructor` 提供的是 `RequiresUnlockSessionReplacer`
  这个**具体类型**，而不是 `KdbxSessionReplacer` ⇒ Hilt 只会去取 app 侧那个 `@Provides`。
  也就是说它是个**死类**，唯一的作用是让人以为"还有个兜底实现"。
- ⚠️ 更贵的代价是它的 **KDoc 把一句错误结论写成了定论**：
  「免密重开需要主密码，而主密码只在 app 侧的快速解锁信封里，`data:repository` 拿不到」。
  这句话让后续每一次接力都默认"这件事做不了"，于是拉取路径一直空着。
- **真相**：已解锁的会话里**本来就存着**打开这个库用的那组 kotpass `Credentials`
  （`KdbxSession.credentials`，写回时 `KdbxRoundTrip` 正用它重编码整库）
  ⇒ 复用它解码远端字节即可，**既不需要信封、也不需要把主密码以明文交回这一层**。
  ⚠️ 复用是安全的：`EncryptedValue` 只在构造时用随机 salt XOR 一次、取值时按 salt 还原，
  同一个对象可反复 decode/encode（已被每次保存验证过）。
- **纪律**：① 别留"恒定失败"的占位实现 —— 它不会兜底，只会让"这条链是通的"这件事
  在代码审查时**看起来成立**；② 真要留，就明写 `@Deprecated` + "尚未接通，别当成兜底"；
  ③ **前提性断言（"X 拿不到 Y"）必须能被一行代码证伪** —— 它在注释里活得越久越像事实。

## 148. ⭐⭐ 同步基线**只在"本机真跟上远端"之后**才推进（2026-10-01）

- `remoteVersionToken` 的语义是**「本机内容 = 远端的哪一版」**（它是条件写 `If-Match` 的基线）。
  ⇒ 推进它的唯一合法时机是：拉取成功（`markResolved`）或强推成功（`resolveUsingLocal`）。
- 踩过的：编排器在「**只有远端变**」的分支里顺手 `markStatus(..., remoteNow)` 推进了基线，
  可本机会话**根本没动过**。于是一条完整的数据丢失链：
  ```
  ① 远端变到 T1 ⇒ 报 REMOTE_CHANGED，基线被记成 T1；
  ② 用户在本机改一笔 ⇒ PENDING_UPLOAD ⇒ 自动上传（#140）；
  ③ 上传拿 T1 当 expectedVersion，服务端当前也正好是 T1 ⇒ 条件写**通过**；
  ④ 而本机会话还是旧的 ⇒ 推上去的是「旧内容 + 新改动」⇒ 远端 T1 的新内容被**静默覆盖**。
  ```
  ⚠️ 这条链在自动上传接上之后才真正兑现 —— 此前第 ② 步需要用户手动点同步，
  所以它在文档里躺了很久都只是"隐患"。**修好一个能力会让别处的隐患变成真事故**。
- 解法就是那一行**不再传** `remoteNow`：基线留在 T0 ⇒ 第 ③ 步 `remoteChanged` 仍为真
  ⇒ 与"本地也改了"合成 `CONFLICT` ⇒ 拒写、交用户拍板。
- **纪律**：凡"记基线"的动作，先问一句"**本机这一刻真的等于远端那一版吗**"。
  答不上来就是不推进。⚠️ 反方向（漏推进）最多多同步一次；正方向（多推进）是丢数据。

## 149. `stat` 必须在 `read` **之前**：令牌偏旧是安全的，偏新是漏改（2026-10-01）

- `resolveUsingRemote` 原先是「read 字节 → 替换会话 → 再 `stat` 拿令牌记基线」。
- ⚠️ 读到字节之后远端可能**又被改了一版**：那时 stat 拿到的是**更新的**令牌，
  而会话里躺的却是**旧一版** ⇒ 把它记成基线，等于宣称"我已经跟上这一版了"
  ⇒ 那一版**再也不会被拉**（静默漏掉别人的改动）。
- ⇒ `stat` 挪到 `read` 之前：拿到的令牌是"读之前那一刻"的，读到的字节**至少**是那一版。
- **纪律**：两个方向不对称 —— **令牌偏旧 = 多拉一次**（无害，用户顶多多点一下）；
  **令牌偏新 = 静默漏改**（有害，且没有任何报错）。凡是"版本令牌"与"内容"分开取的场合，
  一律让令牌**偏旧**。这条与 #148 是同一条纪律的两个方向。

## 150. ★ 新建 KDBX 库的两个 SAF 必做项（少一个就「新建 → 重启 → 打不开」）（2026-10-01）

用户诉求是「在打开 kdbx 文件这里，做一下新建 kdbx 密码库接口」。数据层早就写完了
（`KdbxCreator` + `Kdbx.createVault`，带 11 条单测）—— 缺的一直是**入口**
（`createVault` 在全仓库**零调用点**）。接入口时踩到/绕开的两件事：

- ① **`takePersistableUriPermission` 一定要 `READ | WRITE`**。
  `ActivityResultContracts.CreateDocument` 返回的 URI **没有**持久授权，
  和 `OpenDocument` 一样要自己 take。⚠️ 但标志位**不同**：打开态只要**读**
  （那个文件不归我们写），新建态要**读写** —— 少 WRITE 的表现是
  "改一条"在**下次启动后**失败，与此刻的代码路径相隔十万八千里。
- ② ★ **`origin` 要取来源实际报的（`stat().remoteId`），不是请求时那个 `targetUri`**。
  SAF 的部分文档提供方（Downloads 之类）返回的是**临时** URI，最终路径另有一个。
  拿 `targetUri` 当库 id ⇒ **「库在列表里，却怎么点都打不开」**，
  而且**只在那些 provider 上复现**（AOSP Files 上一切正常）。
  ⇒ 这类"只在部分机型复现"的故障排查起来最贵，必须靠单测钉住
  （`KdbxCreateRepositoryTest` 里让 `targetUri != remoteId`，两个 URI 不同本身也断言）。
- **纪律**：凡是"系统面板给的 URI"要长期持有的场合，都要问两个问题：
  「授权拿了吗？拿的是不是我们要的那些位？」「这个 URI 就是最终身份吗？」

## 151. 落库顺序：**先建文件、后登记**，不是反过来（2026-10-01）

- 新建库做的是「写文件 → 登记 `vaults` 行」。这两步的顺序**不能换**。
- 反过来的话，`Kdbx.createVault` 失败（keyfile 读不到 / 目标不可写 / KDF 参数被拒）
  就会留下**一行指向不存在库的记录**：用户看到列表里多了一项、点进去永远报错，
  而库列表里**没有"删掉它"的入口**（那是另一个功能）。
- 现顺序的最坏情况只是"文件建好了但没登记"—— 用户在文件管理器里看得见、能自己删。
  ⇒ **两种失败的可恢复性差一个数量级**，这才是不换顺序的真正理由。
- ⚠️ 但**别因此说这一步"原子"**：`createVault` 内部是「先编码（纯内存，失败时没文件）
  → 再 write」，真正的写入失败（磁盘满 / 授权被撤）仍可能留下半截文件 ——
  那由 `SafKdbxFileSource.write` 的**写后读回校验**去发现（它会抛），而不是假装不存在。

## 152. 表单校验文案**不要**塞进 `UnlockUiError.Detail`（2026-10-01）

- `UnlockUiError.Detail` 的契约是「**来源层已经翻译好**的一句话」，
  `unlockErrorText` 对它是**原样返回**（绕过资源系统）。
- 把 ViewModel 自己写的校验文案（"请输入密码库名称"）塞进去，会有两个后果：
  ① 文案散在 Kotlin 里，与 `strings.xml` 那批同类文案**分家**，改措辞要找两个地方；
  ② 那种字符串在**孤儿串检查里是隐形的**（它不在 strings.xml）——
  于是"文案该不该翻译"在评审时也没有任何提示。
- ⇒ 新增 `UnlockUiError.Validation`（枚举）+ `ErrorText.validationTextRes`
  （纯函数：错误 → 资源 id，可单测）。分辨标准：**这句话是不是我们 UI 层自己写的**？
- ⚠️ 顺手踩到：加了分支之后 detekt 报 `unlockErrorText` 圈复杂度 **20**（上限 14）。
  两次修：① 把 Validation 的 5 个分支抽成 `validationTextRes`（降到 15）；
  ② 把 `forKdbx` 那句**提前 return** 折进 `when` 的 `InvalidCredentials` 分支 ——
  原来那句 return **本身就是第 15 个分支**。⇒ 降复杂度时，提前 return 要算进去。
