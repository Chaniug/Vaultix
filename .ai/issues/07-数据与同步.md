## 8. 「登录易失效」三根因（2026-09-08，真机驱动，d689a37 修复）

- **现象**：app 高频提示「登录已失效，请重新登录」；重启后快速解锁尤其必现
- **根因（3 条叠加）**：
  1. 网络层从不预挂 `Authorization`——每个请求先 401 → OkHttp Authenticator 刷新 → 重试；每次调用都轮换 token，任何一次刷新失败即误报失效；
  2. `host→server` 映射只在**登录**时登记且仅存内存——进程重启后走快速解锁（不重登）则映射为空，刷新必失败（即使 access token 仍有效）；
  3. 刷新失败不分类——403（CF/WAF）/429/5xx/网络抖动全被当凭据失效（Bastion 明示过此误伤）
- **解法**：① 请求拦截器按 host 预挂 Bearer，expiresIn 落盘、到期前 60s 预刷新；② 解锁路径（含本地快速解锁）`registerServer`；③ 刷新结果三分：400/401=Invalid（重登）/ 其余=Transient（保留登录态，sync 401 按 `refreshFailureOf(server)` 归类）
- **防回退**：任何「请求不带 Bearer 直接发」或「把非 401 失败当登出」的改动都是回归

## 22. Mapper 读写字段不对称 → 静默数据破坏（2026-09-09，通行密钥 P0）

- **现象**：编辑任一条登录条目后，服务端该条通行密钥的密钥材料被清空、计数器归零
- **根因**：`mapFido2` 只读 8 个字段，`mapFido2Request` 却写 13 个 → 没读到的字段用默认值
  覆盖上传（`encryptOpt("")` 返回 null = 服务端字段被置空）
- **解法**：读侧补齐全部字段（照 Bastion `Fido2CredentialCodec` 13 字段）；
  对「写明文、读密文」的 `creationDate` 用 `decryptOrPlain` 兼容
- **判据**：**Mapper 读 N 字段就必须能写回 N 字段**，且要有「往返后逐字段相等」的回归测试；
  读不到就写默认值的写法一定会造成不可逆破坏

## 79. `PendingOp` 表可以当「未同步」判据，但**只能取条目级操作**（2026-09-13，第五十一轮）

**需求**：条目行尾要显示「已同步 / 待推送」的小云图标（参考 Bastion）。

**做法**：新增 `PendingOpDao.observeItemLevelIds(vaultId)` ——
`SELECT DISTINCT cipherId FROM pending_ops WHERE vaultId = :vaultId AND op IN ('CREATE', 'UPDATE')`，
一路经 `ItemRepository.observeSyncStates` 到两个 ViewModel 的 `syncStates: Map<String, Boolean>`，
UI 侧 `synced = syncStates[item.id] ?: true`（键存在 = 已同步；待推送的 id 不入 map）。

**为什么必须过滤 `op`**：`pending_ops` 里还有删除类（`SOFT_DELETE` / `DELETE` / `RESTORE`），
它们对应的条目**在列表里本就不可见**；让它们参与判定，只会把「已经删掉的条目」
标成「待推送」，而用户根本看不到这些行 —— 属于**判定集合与展示集合不一致**。
KDBX 库没有「云端」这一层（文件即存储）⇒ 恒返回空 map ⇒ UI 因而不画云图标。

**为什么用 Flow 不用挂起函数**：推送成功后队列行被删除，图标要**自动**
从「云 + 斜杠」变成「云」，不能要求用户手动刷新。

**接法**：**不要 combine 进主 UiState 的流**（高频小变化会重组整张表），
独立 `viewModelScope.launch { ... .collect { states -> _state.update { it.copy(syncStates = states) } } }`。

**判据**：**队列表当判据时，先问「这张表的哪些行对应用户正在看的东西」。**
判定集合 ≠ 展示集合，就会得到一批用户看不懂的标记。

## 91. 全量拉取无条件 `upsertAll` → 覆盖掉队列里的本地改动（2026-09-14，第五十三轮，4de48f6 修复）

- **现象**：离线改了某条密码 / 备注，恢复网络同步后**变回旧值**；无任何提示，用户只会
  觉得「改的东西自己跑回去了」
- **根因**：`persistCiphers` 对服务端返回的条目无条件 `upsertAll`。而 `pending_ops` 里有
  这条 = 本地有**尚未成功推送**的改动（上一轮 `flushPending` 失败留下的）。服务端那份
  是**旧版本**，无条件落库即用旧版本盖掉用户的最新意图
- **解法**：落库前先取 `pendingOpDao.listByVault(vaultId).map { it.cipherId }.toSet()`，
  `filter { dto -> dto.id !in pendingIds }` 之后再 `upsertAll`
- **与 `pruneRemovedRows` 是同一保护思路的两面**：那里也用 `pendingIds`，防的是
  「被误删」；这里防的是「被覆盖」。**改动同步落库路径时，两处要一起看**
- **代价（有意为之）**：队列条目在推送成功前保持本地版本（对——本地才是用户最新意图）；
  推送成功后队列清空，下一次同步自然取服务端版本收敛
- **判据**：**「服务端数据」不等于「权威数据」。只要本地还有未推送的意图，服务端那份就是旧的。**

## 92. 4xx 弃单只删队列行不删本地行 → 条目「凭空消失」（2026-09-14，第五十三轮，4de48f6 修复）

- **现象**：新建的条目在同步后**凭空消失**，无提示、无日志
- **根因**：`flushPending` 遇确定性 4xx（非 408/429）会「永久弃单」防毒丸卡死队列。
  但**只** `pendingOpDao.remove(op.localId)` 是不够的：这条 op 一旦离开队列，
  紧接着的全量同步里它既不在服务端集合、也不在 `pendingIds` 中
  ⇒ `pruneRemovedRows` 判定为「服务端已删除」⇒ **删掉本地行**
- **解法**：弃单时按 op 类型分流：
  - `OP_CREATE`：服务端**从未**接受它（4xx 即拒绝），本地这行注定同步不了
    ⇒ `cipherDao.deleteByIds(listOf(op.cipherId))` 立即删除。行为由「静默消失」
    变为「即刻、可追溯」
  - 其余（`UPDATE` / `DELETE` / `RESTORE`…）：本地行**是用户数据，不能删**，
    保留它，由正常全量同步按服务端版本收敛（此时服务端版本更权威）
- **★ 一般化判据**：**删掉一个「保护性集合」的成员前，先问「谁在依赖这个集合的存在」。**
  这里 `pendingIds` 同时被 `pruneRemovedRows`（防误删）和 `persistCiphers`（防覆盖）
  依赖，弃单时只想着「清队列」，就把下游两道保护一起撤掉了
- ⚠️ 该模块**没有任何日志设施**（连 `android.util.Log` 都没引）⇒ 想「记一条日志」
  时不要凭空造 `SyncLogger`；当前取舍是纯删除 + 代码注释说明
