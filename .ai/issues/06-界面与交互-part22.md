### 第 1 组：为什么「取消」跟别的按钮长得不一样

#### 取证：先把 #273 / #283 的根因钉死，别再凭猜改宽度

#273 推断 M3 `AlertDialog` 动作槽通过 `indentChar` + `IntrinsicSize.Max` 把裸按钮测成 0 宽，
于是加 `width(IntrinsicSize.Min)` 治「逐字竖排」；#283 又在前面补 `widthIn(min = MinWidth)`。
本轮解包实际依赖 **material3-android:1.5.0-alpha16** 反编译取证：

- `javap` 反编译 `AlertDialogKt.AlertDialogFlowRow` ⇒ 它直接调用
  `androidx.compose.foundation.layout.FlowLayoutKt.FlowRow`，**没有任何 intrinsic 测量**；
- 扫遍全部 Dialog 相关类，**零处 `IntrinsicSize` 引用**；
- `git show d8559668:gradle/libs.versions.toml` 证明 #273 提交时 `composeBom = 2026.06.01` /
  `material3 = 1.5.0-alpha16` 与当前**完全相同** ⇒ 不是版本变化让旧修法失效，是旧根因本来就是错的。

#### 真根因：一套代码里跑着两套宽度规格

```kotlin
// #283 的写法（病因）
private fun Modifier.dialogActionWidth(): Modifier =
    this.widthIn(min = ButtonDefaults.MinWidth)
        .width(IntrinsicSize.Min)   // ← 把宽度钉死成 minIntrinsicWidth
```

`width(IntrinsicSize.Min)` 不是「至少多宽」，而是**固定为最小固有宽度**：中文按单字断行时
「取消」两字的 `minIntrinsicWidth` 只够一个字加内边距；#283 的 `widthIn(min = 64dp)` 只是
把这个小方块**托到 64dp**，结果 **63 处动作槽调用（21 个使用文件）**全是「64dp 固定方块」，
不随文案、字号伸缩。

而用户说的「**其他正常按钮**」是 `DialogShell` 家族：`DialogActions` 用 `FlowRow` + 原生 M3
`Button` / `OutlinedButton`，wrap-content、自带 `MinWidth` 与 `ContentPadding`，额外带
`DIALOG_BUTTON_PADDING = PaddingValues(horizontal = 16.dp, vertical = 8.dp)`。
⇒ 同一个 App 里两套规格并排，长文案 / 2.0x 字号 / 窄屏下差异最明显。

#### 修法：删掉 intrinsic，回归原生 M3

```kotlin
// DialogActionButtons.kt（#284）
private fun Modifier.dialogActionWidth(): Modifier =
    this.widthIn(min = ButtonDefaults.MinWidth)
```

- 删 `IntrinsicSize` / `width` import 与固定宽度，**只保留 M3 宽度下限**；按钮宽度回到
  wrap-content，随文案 / 字号伸缩，与 `DialogShell` 家族一致。
- 两个组件继续**显式**声明 `contentPadding = ButtonDefaults.TextButtonContentPadding` /
  `ButtonDefaults.ContentPadding`（M3 默认值不是随版本不变的契约，显式写才锁得住）。
- 全项目动作槽仍**全部**走这一个共用组件 ⇒ 改一处即全量生效；`DialogShell` 一个不动。
- #282 的边框判据不动；7 处生产注释里的旧「intrinsic 缩进撑宽 / 逐字摞起来」归因统一订正为
  `#284 勘误：旧根因已被反编译证伪，规则仍有效是因为共用组件是规格单点真源`：
  `SettingsScreen.kt` / `SettingsComponents.kt` / `FullScreenDialogShell.kt` /
  `CloudAccountsScreen.kt` / `DeveloperLogsDialog.kt` / `ImportExportScreen.kt` /
  `VaultManagementScreen.kt`。

#### 门禁同步反转

- `DialogStyleRulesTest` 规则 4 → `对话框动作按钮禁止固定宽度只允许原生wrap-content规格`：
  扫 `IntrinsicSize`、`width(`、`height(` 一律红；同时钉住 `widthIn(min = MinWidth)` 与两处
  `contentPadding` 不得丢。KDoc 明写「#273 的 intrinsic 修法已被反编译证伪」。
- `SettingsStyleRulesTest` 规则 2 保留但 KDoc 勘误，失败提示从「两个字会被逐字摞起来」改为
  「会脱离共用组件的 M3 规格（#284）」。

### 第 2 组：KDBX 到底能不能存通行密钥？管理部分正常吗？

#### 结论一：**能存**，链路是通的，不是只读阻断

| 环节 | 实现 | 结论 |
|---|---|---|
| 领域 → KDBX 字段 | `KdbxPasskeyCodec.fromCredential()` 写 `KPEX_PASSKEY_*` + 私有 `VPX_PASSKEY_META` | 有完整编解码 |
| 写回落地 | `KdbxItemWriter.applyPasskeys()` 把 `item.fido2Credentials` 写成字段，私钥 PEM / `credentialId` / `userHandle` 强制 `EntryValue.Encrypted` | 敏感字段受保护写入 |
| 仓储分流 | `ItemRepositoryImpl.updateFido2Credentials()` / `removeFido2Credential()` 解锁门控 `sessions.isUnlocked(vaultId) \|\| Kdbx.isUnlocked(vaultId)`，`updateItem()` 后按 `isKdbx(vaultId)` 分流 | 自 2026-10-13 起对 KDBX 放行，`requireNotKdbx()` 注释已同步 |
| 读取 | `KdbxItemMapper` → `KdbxPasskeyCodec.toCredential()` 读回 | 往返保真有 `KdbxPasskeyWritebackTest` 钉住 |

#### 结论二：管理页**结构完整**，但人工录入路径会让 KDBX「存了却读不回来」

- 模型：通行密钥永远绑定 `VaultItemType.Login`，**不存在独立条目**；
  `PasskeysViewModel.savePasskey()` 追加到登录条目的 `fido2Credentials`，
  `deleteCredential()` 走 `removeFido2Credential()`；`PasskeysScreen` 有列表、搜索、加载 / 锁定 /
  空态区分、多选批量删除、详情、删除二次确认、FAB 打开 `SavePasskeyDialog`。这些都正常。
- **真缺陷**：`KdbxPasskeyCodec.toCredential()` 要求 `rpId`、`credentialId`、
  `privateKeyPem`(keyValue)、`userName`、`userHandle` **五项非空**，缺一返回 `null`。
  而 `SavePasskeyDialog` 旧代码只校验前三项，**不产出 `userHandle`、还允许 `userName` 留空**，
  且 `keyAlgorithm` / `creationDate` 等元数据也没补齐 ⇒ 手工录入的凭证写进 KDBX 后，
  下次打开库会**静默消失**（没有报错、没有日志，最容易误判成「KDBX 不支持」）。
- 系统注册路径 `PasskeyCreateActivity` 把 RP 给的 `user.id` 原样写入 `userHandle`；
  RP 传空时同样是半截凭证。

#### 修法：写入侧必须产出完整凭证（不覆盖真实 `user.id`）

| 文件 | 改动 |
|---|---|
| `core/common/WebAuthn.kt` | 新增 `randomUserHandle()`：32 字节 `SecureRandom` → base64url **无填充**（WebAuthn `user.id` 上限 64 字节）；KDoc 写明**只在 RP 没给 / 手工录入留空时兜底，有真实值不得覆盖** |
| `SavePasskeyDialog.kt` | `userName` 必填校验（新文案 `passkey_error_user_name_required`）；新增选填「用户句柄」输入框（新文案 `passkey_field_user_handle_optional`），留空走 `WebAuthn.randomUserHandle()`；补齐 `keyAlgorithm = PasskeyKeyAlgorithm.DEFAULT` / `keyType` / `keyCurve` / `creationDate = Instant.now().toString()` / `counter` / `discoverable` |
| `PasskeyCreateActivity.kt` | `userHandle = userId ?: WebAuthn.randomUserHandle()`（真实值原样保留） |
| `PasskeysViewModel.kt` | 删零引用死代码 `newPasskeyCredential(...)` —— 它会诱导后来者复用缺 `userHandle` 的半成品；凭证构造真源收敛为上面两条路径 |
| `strings.xml` | 新增两条文案（都已被引用，孤儿字符串基线不增加） |

#### 三层测试闭环（补上「UI 构造路径 ↔ KDBX 读侧契约」之间的缝）

| 层 | 用例 | 作用 |
|---|---|---|
| `core/common` | `WebAuthnTest.randomUserHandle is a valid opaque user id` | 非空 / 两次不相等 / 无 `=` / 解码后 32 字节 |
| `data/kdbx` | `credential with userHandle survives KDBX round trip` | 正向往返保真 |
| `data/kdbx` | `missing userHandle is silently dropped on KDBX read` | **故意钉住失败形态**：`userHandle = null` ⇒ 不写 `FIELD_USER_HANDLE` ⇒ `toCredential()` 返回 `null`，防止有人「贴心地」把必填校验删掉 |
| `app`（新建） | `SavePasskeyDialogRulesTest` 3 条 | ① 手工录入构造块必须带齐读侧必填字段 + `randomUserHandle()` + 元数据；② `userName` 空白校验；③ `PasskeyCreateActivity` 必须有 `userId ?: WebAuthn.randomUserHandle()` |

⚠️ ① 里的 `credentialBlock()` helper 用 `balancedCallEnd()` 从 `VaultFido2Credential(` 起
**只扫构造块**，避免把文件别处的同名字符串算进来 —— 这是源码文本门禁的一贯做法
（另配 `stripComments()`，别把注释当代码扫）。

### 本轮踩的坑（别记成代码红）

1. **凭猜改宽度会连错两轮**：#273 的 intrinsic 根因没有任何反编译依据，#283 在错误前提上
   又加了一层补强。UI 观感问题也应先取证（解包依赖 / 读真实测量代码），别只靠「看起来像」。
2. **`:core:common:test --tests "…"` 不是合法用法**：`Unknown command-line option '--tests'`；
   该模块测试要用模块级任务 `:core:common:test`（`--tests` 只对标准 Test 任务入口生效）。
3. **zsh 下 `PIPESTATUS` 为空**：`cmd | tee …; echo ${PIPESTATUS[0]}` 在 zsh 打印空串
   （zsh 用小写 `pipestatus[1]`）。判退出码请直接 `cmd > log 2>&1; rc=$?`，或显式 `set -o pipefail`
   后用 `$?`，别依赖 bash 专有数组。
4. **源码门禁要扫构造块而非整文件**：整文件 `contains(...)` 会被注释 / 别处同名符号骗过，
   `balancedCallEnd()` + `stripComments()` 是本项目固定套路。
5. **文档里的数量要实测，别沿用上一轮口算**：草稿写「59 个动作槽」，收工前 grep 复核实际是
   **63 处调用 / 21 个使用文件**（#283 记的「22 个文件 60+ 处」是把定义文件也算进去了）。
   这类数字不进编译、不进门禁，却会被下一轮当成事实引用 ⇒ 写进接力文档前先量一遍。
