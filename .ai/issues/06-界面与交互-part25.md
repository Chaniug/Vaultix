## 287. OneDrive KDBX 改完条目立刻返回，改动被云端旧版本覆盖（2026-11-12，用户反馈）

### 用户原话

> 目前我的操作：kdbx 上随便一个条目，我点了修改后，虽然可以立马在本地看到改动的内容，
> 立马退出等待，返回然后去点同步，还是把云端的旧版本的内容同步过了，新修改的并没有生效。

> 一般情况下，修改完成后，点击保存，不操作，停个 5 秒，会发现条目页面底下有提示
> 「已保存到本地 · 正在同步到云端」，这时候才能够保存并且同步上去，但是大部分情况，
> 都是点击修改完成后，大家都是返回的，所以这一步相当于没生效？

**一句话定性**：这不是 #286 修的「同步状态机判据」，而是**更前面的一段**——
保存写回跑在 `viewModelScope` 里，用户点完保存立刻返回 ⇒ `onCleared()` 取消协程 ⇒
写回断在 `Kdbx.verifyWrite()` 那 1~5 s 的 KDF 往返自检里。会话已经换好（所以本地
立刻看得到改动），但脏缓存 / `markLocalEdited` / `autoUploader.enqueue()` 一行都没跑到。
此时 #286 的双真源判据（DB 状态 + 缓存脏标记）**两个都还是干净的**，点同步就放行拉远端
旧字节 `replaceSession()` ⇒ 改动彻底消失。停留 5 秒只是让协程跑完、提示出现、上传排队完成。

> ⚠️ **判据反转（第三次）**：#286 的收尾口径是「改动不丢由双真源闸门保证」。
> 这条只有在**写回已经把脏标记落到缓存**之后才成立。#287 证明存在一条更靠前的路径：
> 写回本身被取消，压根没走到 `fileCache.save`，闸门看的两个真源自然都是干净的。
> ⇒ **先保证「写回必须跑完」，再谈「同步闸门别覆盖」**，两道防线是串联不是并联。

### 真机时序（用户补充的第二段是决定性证据）

| 步骤 | 停留 5 秒（用户说「生效」） | 立刻返回（用户说「没生效」） |
|---|---|---|
| 1 | `mutateLocked` 换内存会话 | 同左（所以两种都能立刻看到改动） |
| 2 | `persist()` 进 `Kdbx.verifyWrite()`，KDF 往返 1~5 s | 同左 |
| 3 | 协程跑完：写脏缓存 → `markLocalEdited` → `enqueue` → 提示出现 | **返回** ⇒ `viewModelScope` 取消，写回断在第 2 步 |
| 4 | 点同步：双真源判据看到脏标记 ⇒ 转冲突 / 上传本地改动 | 点同步：DB 仍 `IN_SYNC`、缓存无脏标记 ⇒ 闸门放行 |
| 5 | 改动上云 | `readRemoteCurrent()` 拉远端旧字节 → `replaceSession` ⇒ 改动消失 |

> 「本地立刻看得到改动」**不是**落盘完成的证据。`Kdbx.mutateLocked` 在 `persist()` 之前
> 就把新会话换进内存，UI 读的是会话；磁盘 / 缓存 / 同步状态是另外三份真相。

### 取证链

1. `ItemDetailScreen.kt` 的保存回调：
   ```kotlin
   onSave = { updated ->
       viewModel.updateItem(updated)
       editOpen = false      // 表单立刻关闭，用户随后系统返回 ⇒ ViewModel.onCleared()
   }
   ```
2. `ItemDetailViewModel.updateItem()` 旧实现是裸 `viewModelScope.launch { ... }`；
   而 `deleteItem()` 早在 11-08 就有注释「页面返回会取消 `viewModelScope` ⇒ 整笔写回
   必须 `NonCancellable`」并用 `launch(NonCancellable)` 修过**同一个坑**——编辑没跟上。
3. `KdbxItemRepository.persist()` 旧顺序：
   ```kotlin
   Kdbx.verifyWrite(vaultId, bytes).getOrElse { throw it.toUserFacing() }   // KDF 1~5 s
   ...
   fileCache.save(origin, CachedKdbxFile(bytes, previousToken, pendingLocalEdits = true))
   cloudSync.markLocalEdited(vaultId)
   autoUploader.enqueue(vaultId)
   ```
   ⇒ 昂贵自检在前、脏标记在后，正是用户「要等 5 秒」的那几秒盲窗。
4. `strings.xml` 里 `item_saved_queued` =「已保存到本地 · 正在同步到云端」，注释明确
   `Queued` 意味着**本地已落盘、上传刚入队** ⇒ 提示出现即写回完成，与用户观察吻合。
5. `ItemRepositoryImpl.updateItem()` 对 KDBX 走 `kdbxItemWrites.update()`，八个写动作
   （create / update / softDelete / restore / permanentDelete / createFolder / renameFolder /
   deleteFolder）全过 `KdbxItemRepository.serialWrite` ⇒ **一处收口即可全覆盖**，
   不需要逐个 ViewModel 打补丁。

### 修法（四道防线，按调用顺序）

| # | 位置 | 改动 |
|---|---|---|
| 1 | `KdbxItemRepository.serialWrite` | 改为 `withContext(Dispatchers.IO + NonCancellable) { writeGate.withLock { block() } }`。⚠️ `withContext` 必须在 `withLock` **外面**：等锁期间也不许取消，否则第二笔写回消失而第一笔已换会话，同样是「UI 说改了、磁盘没改」。八个写动作共用这一处。 |
| 2 | `KdbxItemRepository.persist` | 把 `fileCache.save(... pendingLocalEdits = true)` **提到 `Kdbx.verifyWrite()` 之前**，本地文件 IO 毫秒级，把「本地有未上传改动」尽早变成持久事实，盲窗压到最小。沿用旧 `versionToken` 作条件写基线不变。 |
| 3 | `KdbxItemRepository.persist` catch | 新增 `cacheRestore: (suspend () -> Unit)?`（声明在 try 外）：自检 / 落盘失败时恢复写前缓存快照（原本无缓存则 `fileCache.remove(origin)`），否则一份**没通过往返自检**的字节会留在缓存里，下次解锁直接拿它解密或当成待上传改动推上远端。`CancellationException` 只原样重抛、不记 ERROR、不跑回滚链。 |
| 4 | `ItemDetailViewModel` | `updateItem()` / `deleteItem()` 统一改 `viewModelScope.launch { withContext(NonCancellable) { ... } }`。UI 层是第二层：让 `saving=false`、成功提示、乐观上屏也能正常收口，而不只是保住数据。 |

> ⚠️ **代价与取舍**：点完保存立刻锁库 / 切后台时，写回仍会跑完（几秒）。这是对的——
> 取消一次半途的落盘只会制造「会话 / 缓存 / DB 状态」三份互相矛盾的真相。
> `NonCancellable` 只包住**已经开始的原子写回**，不是把整个 ViewModel 变成不可取消。

### 坑（6 条）

1. **`launch(NonCancellable)` 已 deprecated**：较新协程版本警告
   「Passing a NonCancellable to launch breaks structured concurrency ... will be
   deprecated with an error in the future」。统一改 `launch { withContext(NonCancellable) { } }`，
   语义相同且少一条编译警告；源码门禁追加 `assertFalse(vm.contains("launch(NonCancellable)"))`。
2. **`functionBody()` 必须从签名起点截，不能从第一个 `{` 截**：`serialWrite` 是表达式体
   `= withContext(Dispatchers.IO + NonCancellable) { … }`，第一个 `{` 属于 `withContext`
   的 lambda ⇒ 从那里截会把要判的 `withContext(...)` 本身排除掉，源码门禁**假红**。
   改为 `val start = signature.range.first` 后从 `start` 配平括号。
   （#283 / #285 的坑是「`functionBody()` 不含参数列表」，这次是同一 helper 的另一种形状。）
3. **取消不是失败**：协程已取消时每个挂起点都会立刻再抛 `CancellationException`，
   回滚链跑不完还可能把会话换了一半 ⇒ `CancellationException` 必须**只**重抛，
   不记 ERROR、不动缓存、不动会话（与 `CachedKdbxFileSource` 同款分界）。
4. **detekt `ThrowsCount` 上限 2**：新增 `throw cancellation` 后 `persist()` 达到 3 个
   `throw`（自检的 `throw it.toUserFacing()` + 两个 catch 的重抛）⇒ 合并为
   一个 `catch (error: Exception)` + `if (error !is CancellationException)`。
   门禁判据同步改为查这个条件表达式。
5. **行为测试要用 `runBlocking` 真实时间，不能用 `runTest`**：`serialWrite` 强制切
   `Dispatchers.IO`，虚拟时间调度器会在 test 协程挂起时立刻推进到超时，制造假竞态。
6. **行为测试必须做反证**：用 `CompletableDeferred` 在 `RecordingSource.write()` 处
   停住（确定写回已进入写文件阶段）再取消调用方协程；临时撤掉 `serialWrite` 的
   `NonCancellable` 后该用例必须变红。实测 `9 tests completed, 1 failed`，证明测的
   正是「返回即取消」这条真机链路，不是假绿。源码已恢复。
