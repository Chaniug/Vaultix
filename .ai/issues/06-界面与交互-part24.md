## 286. OneDrive 上的 KDBX 改完条目，刷新后被云端旧内容覆盖（2026-11-12，用户反馈）

### 用户原话

> 目前有几个小瑕疵。比如 onedrive 上的 kdbx，我需要修改其中的条目，修改后，
> 需要等待上传同步才生效，如果同步过程中返回了，或者断网了，那么就相当于没同步，
> 而刷新后则直接被云端覆盖下来，相当于没有上传上去，依然是老内容，相当于修改并未成功。

**一句话定性**：这不是 UI 观感，是**数据完整性 / 同步状态机**缺陷。用户描述的两句话
对应**两个叠加且独立**的缺陷，缺一不可：

| 用户说的 | 缺陷 |
|---|---|
| 「刷新后直接被云端覆盖」 | 刷新闸门用「只读 DB 状态」判「本地有没有未上传改动」，漏掉 `SYNCING` / `FAILED` |
| 「返回 / 断网就相当于没同步」 | 自动上传只在保存那一刻排队，全仓没有冷启动 / 恢复后的补传入口 |

### 根因取证（按链路逐层读，不靠猜）

改动落盘链路（`KdbxItemRepository.persist`）：

```kotlin
fileCache.save(origin, CachedKdbxFile(bytes, previousToken, pendingLocalEdits = true))
cloudSync.markLocalEdited(vaultId)      // DB: PENDING_UPLOAD
autoUploader.enqueue(vaultId)           // 只在这一刻排队
```

`pendingLocalEdits` 是**持久事实**：只在 `CachedKdbxFileSource.write()` 上传成功后
被 `cache.save(...)`（不带该标记）清掉；DB 的 `syncStatus` 则是**展示用的瞬时快照**。

丢改动完整链路：

```
改条目 → 写脏缓存(pendingLocalEdits=true) + markLocalEdited(PENDING_UPLOAD)
       → autoUploader 起跑，KdbxSyncOrchestrator.sync 一开头 markStatus(SYNCING)
       → 用户返回 / 断网 ⇒ 状态停在 SYNCING，失败则写 FAILED
       → 刷新（pull / resolveUsingRemote）：
           KdbxCloudSyncStatus.impliesLocalChanges 只认
           hasPendingUpload / CONFLICT，不认 SYNCING / FAILED / IN_SYNC / REMOTE_CHANGED
       → 闸门误判「本地没改」→ 放行
       → readRemoteCurrent() 拉远端旧字节 → sessionReplacer.replace() 换掉会话
       → markResolved() 记「已同步」→ fileCache.save(远端字节) 顺手清掉脏标记
       ⇒ 那一笔改动永久消失，且界面显示「已同步」，无人提醒
```

同一个仓库里 `KdbxAutoUploader.hasWork()` 与 `KdbxCloudSyncCoordinator.sync()`
早在 11-07 就已经把「缓存脏标记」当作第二真源，**唯独这道刷新闸门漏了** —— 判据
散落两处必然漂移，本项目为此付过多次代价（#233 缓存令牌、#264 来源判据）。

第二个缺陷：`enqueue` 的唯一调用点是 `persist`。上传跑在应用级后台协程，
返回页面不会取消它，但**进程被杀**或**断网后重试到 [MAX_RETRIES] 上限**，
就再没有任何人排第二次队 ⇒ 改动以脏缓存形式一直躺着，本地看得到、云端永远没有。

### 施工一：把「本地有未上传改动」收敛成唯一判据 + 两道闸门

| 文件 | 改动 |
|---|---|
| `KdbxCloudSyncCoordinator.kt` | 新增 `hasUnsyncedLocalEdits(vaultId)` = `persistedStatusSaysLocalChanges() \|\| hasCachedLocalEdits()`；旧只读 DB 判据改名并收成 `private`；`resolveUsingRemote()` 下载**前**与下载**后**各一道闸门都走它 |
| `KdbxSyncRepositoryImpl.kt` | `localChangedSinceLastSync()` 委托协调器双真源判据，删掉本层的 `KdbxCloudSyncStatus.fromName` / `impliesLocalChanges` |
| `CachedKdbxFileSource.kt` | `readRemoteCurrent()` 回写缓存**前现查**脏标记（`dirtyNow` / `loadFailed`），不再用下载前的 `hasLocalEdits` 快照；读缓存失败也 fail-closed |

**为什么必须两道闸门**：旧 KDoc 声称「下载前的闸门已覆盖长窗口」是错的 ——
闸门在 `readRemoteCurrent()` **之前**，而真机下载要 1–10 s，用户完全可能在这几秒
再编辑一笔。旧代码一路 `replaceSession → markResolved → fileCache.save`，会话换成
远端旧版、状态记成已同步、脏缓存被盖掉。第二道闸门在下载之后、替换会话之前，
用同一个判据现查；宁可多报一次冲突，也不静默覆盖。
`discardLocalChanges = true`（用户在冲突对话框明确选「用云端覆盖本地」）跳过两道。

**装饰器那道为什么独立**：协调器的闸门能保住**会话**，但管不到
`CachedKdbxFileSource.readRemoteCurrent()` 内部把远端字节回写进缓存的那一次 `save`。
两处都改才闭环。

### 施工二：冷启动补传，以及它的补正（同一轮第二轮，本轮完成）

第一版在 `KdbxAutoUploader` 加了 `resumePendingUploads()` / `resumePendingUploadsNow()`
（扫 `vaultDao.observeAll().first()`，按 `hasCloudSource` 过滤后逐个 `drain`），
并在 `VaultixApplication.onCreate()` 末尾调用。**局部编译与单测全绿，但收尾复核时
发现它在最常见的场景里是空转的**：

> `KdbxSyncOrchestrator.sync()` 的上传分支（第 ④ 支）走
> `Kdbx.saveVia(vaultId, source, expectedVersion)`，而 `Kdbx.saveVia()` 第一行就是
> `val session = KdbxSessionStore.get(vaultId) ?: return ... NotUnlocked`。
> **冷启动时库通常还锁着** ⇒ 补传必然失败、写假 `FAILED`、再退避空转 3 次，
> 改动一个字节都没上去。

进一步核对：全仓的解锁路径（主密码 `unlockKdbxInternal` / `LocalUnlockFanout` /
autofill / 「从不锁定」自动恢复）**都没有**同步或补传钩子；`ItemsViewModel.init`
只调 `markKdbxActive`，手动同步要点按钮。⇒ 只加「启动扫一次」等于没接上。

补正（不碰 `VaultRepositoryImpl` 构造 —— 它有 3 个手动构造的测试，也不碰 UI 层 DI）：

| 文件 | 改动 |
|---|---|
| `KdbxAutoUploader.kt` | `resumePendingUploadsNow(sessionReady: (String) -> Boolean = Kdbx::isUnlocked)` 只处理**已解锁**的库；新增 `startUnlockObserver()` 订阅 `Kdbx.sessionRevision()`，按 `newlyUnlockedIds(known, now)` 差集只对**新解锁**的库 `drain`；新增可单测纯函数 `newlyUnlockedIds()` |
| `VaultixApplication.kt` | `onCreate()` 末尾**先** `startUnlockObserver()` **再** `resumePendingUploads()`；字段 KDoc 与注释写明两条的顺序与分工 |

**为什么用 `Kdbx` 门面而不是 `KdbxSessionStore`**：后者是 `data:kdbx` 的
`internal object`，`data:repository` 模块访问不到；而 `Kdbx.isUnlocked()` /
`Kdbx.unlockedIds()` / `Kdbx.sessionRevision()` 都是公开门面方法，
repository 已依赖该模块（`KdbxCloudSyncCoordinator` 就 import 了 `Kdbx`）。

**为什么用差集而不是「每次会话变化都扫全表」**：`sessionRevision()` 在
`mutateLocked` 提交新会话时也会发值（11-08 为「点删除等 1~2 秒」加的），
全表扫描会让一次普通编辑把所有已解锁库重排一次队。差集只在「从无到有」时触发；
锁库再解锁会重新进差集，那正是要补传的时刻。

**为什么显式启动而不是放进 `init`**：单测每次 `new KdbxAutoUploader(...)` 都会
挂一条常驻订阅到全局静态流上，别的用例解锁库时会意外打到它的 mock。生产只在
`VaultixApplication.onCreate()` 调一次。

**两行顺序不能反**：先订阅（此刻会话集合作为基线），再扫存量。反过来会在
「订阅刚挂上、会话恰好恢复」这个窗口漏掉一个库；按此顺序，订阅前已解锁的由
存量扫描覆盖，之后解锁的由订阅覆盖，无窗口。

⚠️ **「改动不丢」与「自动收敛」是两件事**：即使补传在锁态下被跳过，
改动也由刷新闸门（双真源）保住 —— 不会被云端覆盖，会转冲突交用户拍板。
补传解决的是「不用用户再点一次同步」。

### 坑（本轮新增 6 条）

1. **「局部验证全绿」不等于链路闭环** —— 补传入口的编译与单测都过了，
   但单测里 `coordinator.sync` 是 mock，真实链路 `saveVia → KdbxSessionStore`
   从没被跑到。凡是「跨模块的启动钩子」，必须把**最后一层真实依赖**读到底。
2. **DB 状态是快照，缓存脏标记才是事实** —— 与 11-07 `hasWork` / `sync` 的教训
   同一条纪律，这次漏在刷新闸门。判据必须**只有一个定义点**，
   旧名字（`localChanged…`）会让人误以为它回答了「本地有没有改动」，
   所以改名 `persistedStatusSaysLocalChanges` 并收成 `private`。
3. **「下载前判一次」覆盖不了下载窗口** —— 旧 KDoc 自己写的「长窗口已被覆盖」
   是错的，闸门位置决定了它只能挡判断之前发生的编辑。文档也会说谎，
   要看代码里的语句顺序。
4. **判参数要能注入** —— `sessionReady` 做成带默认值的参数，生产走
   `Kdbx::isUnlocked`，单测传 `{ true }` / `{ false }`；否则单测会被进程里
   真实的锁态安静地过滤掉，变成**假绿**。
5. **常驻订阅不放 `init`** —— 全局静态流 + 应用级 scope 的组合在单测里会
   跨用例串扰；显式启动既可控，也让源码门禁能钉住「Application 真的调了」。
6. **跨模块访问先看可见性** —— `KdbxSessionStore` 是 `internal`，
   第一反应想直接查它；门面 `Kdbx.isUnlocked()` 才是 repository 能用的入口。
