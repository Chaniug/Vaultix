## 235. 内容指纹漏算分组树：路径集合一样时，"内容没变"是假的（2026-11-03）

- **现象**：在分组树里做某些调整（同一父组下多一个**同名**子组、或把组名里的 `/`
  当作层级分隔符来理解），`KdbxEncoder.contentFingerprint` 算出的值与调整前**一样**。
- **根因**：指纹只喂了 `content.folders`（`VaultFolder(id, name)`），而 `name` 是
  **拼出来的完整路径**（`parentPath/group.name`）。路径相同不等于树相同：
  - 两个不同 `uuid` 的同名分组挂在同一路径下 ⇒ `folders` 里只有**一条**（`id` 相同、`name` 相同）；
  - 组名本身含 `/` ⇒ 一层 `A/B` 与两层 `A` → `B` 拼出同一个字符串。
  `content.groupPaths`（`uuid -> 路径`）里本来就有 uuid，但**没有任何人把它喂进摘要**。
- **为什么这条比"指纹算错"严重**：#185 的写回基线用指纹判"本地内容有没有动过"。
  漏算 ⇒ 动了却被判"没动" ⇒ 基线被推进 ⇒ 下一次写回**放行**一次可能覆盖远端改动的写入。
  指纹的假阳性只是多弹一次「请先同步」，假阴性是**静默丢数据**。
- **修法**：新增 `fingerprintGroupTree(digest, groupPaths, rootGroupUuid)`：
  先把节点数写进摘要（否则"空树"与"没有任何分组信息"撞在一起），
  再按 `uuid` 排序逐条喂 `uuid + path`。排序是为了消除 `Map` 迭代顺序带来的假阳性。

### ⚠️ 必须跳过根分组：否则**用户一条都存不进去**

`KeePassDatabase.Ver4x.create` 每次给根组**随机生成 uuid**。若把根组算进摘要，
"同一份内容建两次库"的指纹就不同 ⇒ 每次保存都判"内容过期" ⇒ **每次写回都被基线拒绝**。

这个坑是被 `KdbxWriteBaselineTest` 当场抓出来的（新用例 `同一份内容建两次库 指纹必须相同`
先红、后加 `rootGroupUuid`）。所以 `KdbxMappedContent` 新增 `rootGroupUuid`，
指纹里 `filterKeys { it != rootGroupUuid }`；`null`（不知道根是谁）时不跳过任何节点 ——
宁可假阳性，不可假阴性。

### 能力边界（写进 KDoc，不假装覆盖）

| 变化 | 能捕获吗 |
|---|---|
| 新建 / 删除分组 | ✅ |
| 分组改名 | ✅ |
| 换父级 | ✅ |
| **同一父组下调整同级顺序** | ❌ —— `groupPaths` 没有"同级第几个"，硬推 index 会制造假阳性 |

排序这一项交给 #185 的 `baselineAligned` 兜底：它比的是条目集合，不是树形。

### 验证

`:data:kdbx` **236 例 0 失败**。两次变异，各自**精确报红**：

| 变异 | 报红用例 |
|---|---|
| 分组树整段不参与摘要（`if (groupPaths.isEmpty()) fingerprintGroupTree(...)`） | `路径集合相同但树结构不同 必须改变指纹` |
| 不跳过根分组 | `同一份内容建两次库 指纹必须相同` |

> ★ **第一版用例是错的，值得记下来**：最初拿"把子组上移一层"当用例（`A/B` → `B`）。
> 那会让**路径字符串**变化，而路径早就在 `folders[i].name` 里 ⇒ 指纹本来就会变。
> 变异把分组树整段停掉，那条用例**依然全绿** —— 它测的是"路径变了"，根本没测分组树。
> 换成"`folders` 完全相同、`groupPaths` 多一个同名节点"才真正报红。
>
> 同批还发现：老夹具用 `UUID.randomUUID()` 当根 uuid，指纹开始读 `groupPaths` 之后，
> `同一份内容反复计算必须相等` 与 `附件换 Map 顺序不该变指纹` **必然失败** ——
> 说明这两条此前**并没有在测它们声称的东西**。改成固定 `ROOT_UUID` 后才成立。

## 236. OneDrive 分片上传没有整次续传：断在 90% 就白传全部（2026-11-03）

- **现象**：几十 MiB 的库在蜂窝网下传到一半断一次，下次同步**从第一个字节重来**。
  用户感受是"同步特别慢、老是失败"，而日志里每一片都"重试过 3 次"。
- **根因**：重试粒度只有**单片**。`putChunkWithRetry` 用尽 3 次就抛，整次上传作废。
  而 Graph 的分片协议本来就给了续传的全部信息：每次 PUT 的响应体（202/200）都带
  `nextExpectedRanges`，`GET <uploadUrl>` 也能随时问。
- **对照**：

  | 实现 | 失败后 |
  |---|---|
  | 我们（#236 之前） | 同片重试 3 次；仍失败 ⇒ **整次作废** |
  | KeePassDX / KeePass2Android | 同款（小分片 / 简单 PUT） |
  | rclone / OneDrive 官方 SDK | 读 `nextExpectedRanges`，**从断点继续** |

- **修法**：`chunkedUpload` 引入 `confirmed`（**已确认写进服务端**的偏移）作为唯一真相，
  循环条件改为 `while (confirmed < bytes.size)`；每片成功后用响应体自带的区间推进，
  失败才 `GET` 一次。判定收在纯函数 `judgeResume` / `confirmedAfterAccepted`
  （本模块单测不跑 Android 运行时，所以判据必须是纯函数）。

### 三条铁律

1. **永远不许"跳跃"**：服务端说从 327680 开始，而我们只确认到 163840 ⇒ **夹回**确认位重发。
   真按服务端说的跳过去，文件中间会**永久缺一段** —— KDBX 错一个字节就整库打不开，
   而报错只会说"密码错误或文件损坏"。这比"上传失败"糟得多。
2. **"没给"与"给了个空的"是两件事**：`null` / 空列表 ⇒ 不知道（原地重发）；
   `[""]` ⇒ 服务端**明确**回了个空值 ⇒ `Restart`（原地重发只会无限对着坏路径重试）。
3. **`0-` 的含义取决于我们确认到哪了**：本地也是 0 ⇒ 原地重发（第一片就没上去，
   会话是好的）；本地 > 0 ⇒ `Restart`（我们确认传过，服务端却说全没了 ⇒ 会话被清）。

### 顺带修掉的三个真缺陷

| 缺陷 | 后果 | 修法 |
|---|---|---|
| 成功分支里 `stalls = 0` 无条件重置，而 `confirmed` 没动 | 服务端 202 却从不推进 ⇒ `while` 永远成立 ⇒ **同一片无限 PUT**，实测 `Java heap space` | 加 `progressed` 判定 + 连续无进展超过 `MAX_STALLS` 抛"上传无进展" |
| 每片都额外 `GET` 一次查进度 | 每片多一个 RTT，几十片就是几十次 | 优先用 PUT 响应体自带的 `nextExpectedRanges`，**只在失败时**才 GET |
| `412` 被当成"这一片没上去"进入续传 | 续传循环会一直重试；一旦条件重新成立就**静默覆盖别人的改动** | `ChunkFailureKind` 三态：412/401/403 = `Fatal`，原样抛穿 |

> ★ 第三条是最危险的一条。412 的语义是"远端不是你以为的那一版"，
> 把它当网络抖动来重试，等于**把并发保护当成一次性障碍**绕过去。
> 现在 `classifyChunkFailure` 显式分三类，`handleChunkFailure` 只对 `Retry` 返回重试。

| 变异 | 报红用例 |

## 两条教训

1. **"算了一部分"比"完全没算"更危险**：指纹喂了 `folders` 就以为覆盖了分组，
   而 `folders[i].name` 是拼出来的路径 —— 它看起来像"完整信息"，实际丢掉了拓扑。
   写摘要/对账这类代码时，要问一句"我喂进去的这层抽象，**丢掉了什么**"。
2. **重试的粒度决定代价的量级**：单片重试把"一次网络抖动"放大成"整库白传"。
   协议既然给了断点信息（`nextExpectedRanges`），不用它就是把成本转嫁给用户。
