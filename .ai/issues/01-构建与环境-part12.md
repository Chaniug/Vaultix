## 220. 🔴 测试接缝「构造后赋值」永远晚于 `init` —— 注入从未生效，CI 偶发红的真正原因（2026-11-01，CI run 41279321669）

**现象**：`Android CI (Debug)` 在 `feat(convert): JSON→KDBX 真正无损` 那次提交上红，
513 条单测里 1 条失败：

```
UnlockViewModelTest > fingerprintEntryStaysHiddenWhenLocalUnlockIsNotEnabledForTheVault FAILED
  java.lang.IllegalStateException at TestMainDispatcherJvm.kt:45
    Caused by: java.lang.IllegalStateException at MainDispatchers.kt:111
      Caused by: java.lang.IllegalStateException at HandlerDispatcher.kt:51
```

完整堆栈（从 CI artifact `debug-unit-test-reports` 里取的）：

```
TestMainDispatcher.isDispatchNeeded
  ← DispatchedContinuation.resumeCancellableWithInternal
  ← DispatchedCoroutine.afterResume            // withContext 结束
  ← DispatchedTask.run
  ← LimitedDispatcher$Worker.run               // ← 真线程池
```

**三个信号同时出现，指向同一个根**：

1. 失败的用例是**最简单**的那条（`flowOf`，没有 `delay`、没有事件）；
2. suite 里 8 条只红 1 条，且每次红的"受害者"会换；
3. 本地 `:app:testFullDebugUnitTest` 513 条全绿。

**根因**：`UnlockViewModel` 的测试接缝是三个「构造后赋值」的 `var`：

```kotlin
internal var testingScope: CoroutineScope? = null   // 测试里 it.testingScope = this

init {
    if (testingScope == null) startObservers()       // ← 构造期间，该字段恒为 null
}
```

`init` 在**构造期间**执行，`.also { it.testingScope = this }` 在构造**之后**执行 ——
所以那句守卫 `恒为真`，`init` 永远抢先用 `viewModelScope`（= `Dispatchers.Main`）启动
4 条观察协程。测试随后那次 `startObservers()` 又被 `observersStarted` 的 CAS
**静默挡回**（`compareAndSet` 已置位），一行日志都不留。

于是：`scope` = `viewModelScope`（Main.immediate），`ioContext` = `Dispatchers.IO`（真线程池）。
`prewarmCipher` 里 `withContext(Dispatchers.IO)` 真的跳了线程，回来时 `@After resetMain()`
已经把 `TestMainDispatcher` 卸下 ⇒ 炸。而这条续体属于**上一条**用例（`available = true`
那条会 prewarm），异常被 JUnit 记到**当前正在跑**的那条头上 —— 所以受害者每次都换。

**为什么修了三轮都没修好（#174 / #176 / 2026-10-28）**：

| 轮次 | 当时的判断 | 为什么没生效 |
|---|---|---|
| #174 | 把 `scope` 换成 `TestScope` | 换的是 getter，不是"谁启动的协程" |
| #176 | 再加 `testingBlockableIoDispatcher` 拦截 IO | 同上：`ioContext` 也是 getter，init 那一刻读到的是 `Dispatchers.IO` |
| 2026-10-28 | 把 `init` 启动拆成显式 `startObservers()` | 守卫条件仍读「构造后赋值的 var」⇒ 恒为真 ⇒ 拆了也白拆 |

**为什么本地一直绿**：`@Before` 里 `Dispatchers.setMain(UnconfinedTestDispatcher())` 让
`flowOf` 那几条**同步跑完就结束**；只有 `prewarmCipher` 的 `withContext(IO)` 会跨线程，
而它是否恰好在 `resetMain()` 之后 resume 取决于真线程调度 —— 典型竞态。

**修法**：把接缝从「构造后赋值的 `var`」改成「**构造参数里的容器对象**」：

```kotlin
class UnlockViewModelSeams @Inject constructor() {
    internal var scope: CoroutineScope? = null
    internal var io: CoroutineDispatcher? = null
    internal var ioContextOverride: CoroutineDispatcher? = null
}

class UnlockViewModel @Inject constructor(
    …,
    private val seams: UnlockViewModelSeams = UnlockViewModelSeams(),
) : ViewModel() {
    init { if (seams.scope == null) startObservers() }   // 构造参数在 init 之前就绪 ✅
}
```

`@Inject constructor()` 无参 ⇒ Dagger 可直接绑定，不需要 `@Provides`；
生产拿到的永远是全 null 实例，行为一字不改。

**变异验证**（证明它不是"看起来修好了"）：把 `init` 改回无条件 `startObservers()`，
`:app:testFullDebugUnitTest --tests UnlockViewModelTest` 只有
`overrideScopeIsActuallyUsedByTheViewModel` 一条红 —— 正是这次新加的断言。
改回来立刻全绿。

**顺带修掉一个空断言**：`probeOwnScope()` 返回的就是 `scope` getter 的值，
测试拿它和 `coroutineContext[Job]` 比，**恒成立** —— 它从来没证明过"协程挂哪"。
新增 `probeObserversStarted()` 作为正面判据：构造刚完成、未调 `startObservers()` 时必须为 `false`。

> **判据**：**接缝的赋值时机必须早于「用到它的第一个协程」。**
> `init` 在构造期间跑，所以任何「构造后赋值」的接缝对它都**等于没设** ——
> 而那种失败不报错、不告警，还会让后面的所有"确定性等待"变成错觉
> （`advanceUntilIdle()` 推的是一条没人用的时钟）。
> 第三类"不报错的错"（#218.8 协议对不上、#219 只接一侧）的又一实例：
> **两端各自都对，中间那根线从来没接上。**

## 221. 🔴 预览包「发布成功」但一个附件都没有 —— `files:` 被粘进了 `body:`（2026-11-01，commit `261c6ee` 引入）

**现象**：用户报「最新的 dev 构建没有出 apk 包」。

查证：

```
$ gh release view preview --json assets --jq '.assets | length'
0
```

而 CI run `41284293711` 的结论是 **success**，`Publish Debug APK to preview Release`
这一步也是 **success**。日志里从头到尾**没有一句 `Uploading asset`**：

```
Getting assets list...
🎉 Release ready at https://github.com/Chaniug/Vaultix/releases/tag/preview
```

**根因**（`.github/workflows/ci-debug.yml`，commit `261c6ee` 引入）：改文案时把
`files: |` 粘在了 `body:` 的**最后一行末尾**：

```yaml
          body: |
            …**下载**

            ${{ steps.apk_meta.outputs.apk_list }}

            > 与上一个预览包**签名一致**时…安装前请先导出备份。          files: |
            app/build/outputs/apk/*/debug/*.apk
            app/build/outputs/apk/*/debug/*.APK
```

YAML **完全接受**这段 —— 它只是一行更长的普通文本。于是：

- `with.body` 末尾多了 `          files: |` 这么一串字（Release 页正文里能看见）；
- `with` 下面**没有 `files` 这个键**；
- `softprops/action-gh-release` 走「没有 files 输入」的分支：建 release、不传文件、返回 0。

**为什么一路绿灯**：

| 环节 | 为什么看不出问题 |
|---|---|
| `bash -n` / yamllint | 语法完全合法，没有任何告警 |
| `Upload APK` 步骤 | 用的是 `actions/upload-artifact` 的 `path:`，和 Release 上传是**两条独立的路径**，它一直正常 |
| `Collect debug APK metadata` | 自己 `find` 目录，也正常（body 里那个「35.8 MB」是真的） |
| Publish 步骤 | 没有 files 不算错误，退出码 0 |
| Release 页 | 确实更新了标题、正文、时间 —— 只有点进 Assets 才看得出是空的 |

**影响面**：从 `261c6ee`（签名修复那次）之后**每一个** preview Release 都是 0 附件。
用户不能下载，但页面看起来一切正常，CI 也一直报 success。

**修法**：

1. 把 `files: |` 拆回独立一行，缩进与 `body:` 同级（10 空格）；
2. 两个 workflow 的 `action-gh-release` 都加 `fail_on_unmatched_files: true`
   —— glob 匹配不到就当场红，别再安静发空包；
3. 新增门禁 `.ai/tools/check_release_assets.py` + 自检 `selftest_release_assets.py`：
   - **结构**：`with` 必须真的解析出非空 `files`；
   - **粘连**：`body` 里不得出现「非空白 + 2 个以上空格 + action 输入键名 + `:`」；
   - **兜底**：必须带 `fail_on_unmatched_files: true`。

自检把**真实事故的 YAML 原样复刻**成 `glued` 用例，要求 rc=1。这样"这条门禁在工作"
可以被证明，而不是靠"真仓库跑出来是绿的"来相信。

> **判据**：**「命令成功」不等于「副作用发生」。** 退出码 0 只说明程序没崩，
> 不说明那个 release 里真的有文件。凡是有外部副作用的步骤（发 Release、上传产物、
> 推送镜像），验收标准必须是**去读副作用的结果**（`assets > 0`），
> 而不是「这一步的结论是绿的」。
>
> 这是第 7 类"不报错的错"：**结构合法、语义丢失**。
> YAML 的缩进被吃掉一个键、JSON 里多一层嵌套让字段名变了、
> protobuf 的字段号被复用 —— 都属于这一类：解析器全部接受，业务层拿到的是空的。

### 221.1 修好 `files:` 之后**立刻**暴露的第二个问题：`*.APK` 大小写

`files:` 拆回独立一行后，新加的 `fail_on_unmatched_files: true` 当场把它顶了出来：

```
##[error]⚠️  Pattern 'app/build/outputs/apk/*/debug/*.APK' does not match any files.
```

runner 是 Ubuntu（ext4，**区分大小写**），Gradle 产出的文件名恒为
`app-full-debug.apk`。`*.APK` 这个 pattern **从来没有匹配到任何东西** ——
它一直躺在那里，因为默认 `fail_on_unmatched_files: false`，
"匹配不到就跳过"，谁也不会去看。

三处同源残留，一并清掉：

| 位置 | 原来 | 现在 |
|---|---|---|
| `Upload APK` 的 `path` | `*.apk` + `*.APK` | 只留 `*.apk` |
| Publish 的 `files` | `*.apk` + `*.APK` | 只留 `*.apk` |
| `Collect debug APK metadata` 的 `find` | `-iname '*.apk' -o -iname '*.APK'` | `-iname '*.apk'`（`-iname` 本来就不区分大小写） |

**这一条的价值在于它验证了上一轮那条修法**：如果没加 `fail_on_unmatched_files`，
`*.APK` 这个死 pattern 会继续躺到下次有人改 flavor 名，然后一起爆。
这次它爆在**发布步骤**、且报错文案是"这个 pattern 没匹配到文件" ——
看起来像"APK 没生成"，极易误导人去查构建，实际是 glob 写错了大小写。

门禁相应加了第 ④ 条：`files` 里不得出现**只差大小写**的重复 pattern。
自检加了 `uppercase_dup` 用例要求 rc=1。

> ⚠️ 加这条检查时**它先抓到了我自己**：`GOOD` 样例是照原文件抄的，
> 里面也带着 `*.APK`，于是"必须判绿"的那条红了。
> 这说明检查在工作 —— 也说明"照抄现状"会把现状的病一起抄进来。
