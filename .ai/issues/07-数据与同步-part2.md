## 149. `stat` 必须在 `read` **之前**：令牌偏旧是安全的，偏新是漏改（2026-10-01）

- `resolveUsingRemote` 原先是「read 字节 → 替换会话 → 再 `stat` 拿令牌记基线」。
- ⚠️ 读到字节之后远端可能**又被改了一版**：那时 stat 拿到的是**更新的**令牌，
  而会话里躺的却是**旧一版** ⇒ 把它记成基线，等于宣称"我已经跟上这一版了"
  ⇒ 那一版**再也不会被拉**（静默漏掉别人的改动）。
- ⇒ `stat` 挪到 `read` 之前：拿到的令牌是"读之前那一刻"的，读到的字节**至少**是那一版。
- **纪律**：两个方向不对称 —— **令牌偏旧 = 多拉一次**（无害，用户顶多多点一下）；
  **令牌偏新 = 静默漏改**（有害，且没有任何报错）。凡是"版本令牌"与"内容"分开取的场合，
  一律让令牌**偏旧**。这条与 #148 是同一条纪律的两个方向。

## 150. ★ 新建 KDBX 库的两个 SAF 必做项（少一个就「新建 → 重启 → 打不开」）（2026-10-01）

用户诉求是「在打开 kdbx 文件这里，做一下新建 kdbx 密码库接口」。数据层早就写完了
（`KdbxCreator` + `Kdbx.createVault`，带 11 条单测）—— 缺的一直是**入口**
（`createVault` 在全仓库**零调用点**）。接入口时踩到/绕开的两件事：

- ① **`takePersistableUriPermission` 一定要 `READ | WRITE`**。
  `ActivityResultContracts.CreateDocument` 返回的 URI **没有**持久授权，
  和 `OpenDocument` 一样要自己 take。⚠️ 但标志位**不同**：打开态只要**读**
  （那个文件不归我们写），新建态要**读写** —— 少 WRITE 的表现是
  "改一条"在**下次启动后**失败，与此刻的代码路径相隔十万八千里。
- ② ★ **`origin` 要取来源实际报的（`stat().remoteId`），不是请求时那个 `targetUri`**。
  SAF 的部分文档提供方（Downloads 之类）返回的是**临时** URI，最终路径另有一个。
  拿 `targetUri` 当库 id ⇒ **「库在列表里，却怎么点都打不开」**，
  而且**只在那些 provider 上复现**（AOSP Files 上一切正常）。
  ⇒ 这类"只在部分机型复现"的故障排查起来最贵，必须靠单测钉住
  （`KdbxCreateRepositoryTest` 里让 `targetUri != remoteId`，两个 URI 不同本身也断言）。
- **纪律**：凡是"系统面板给的 URI"要长期持有的场合，都要问两个问题：
  「授权拿了吗？拿的是不是我们要的那些位？」「这个 URI 就是最终身份吗？」

## 151. 落库顺序：**先建文件、后登记**，不是反过来（2026-10-01）

- 新建库做的是「写文件 → 登记 `vaults` 行」。这两步的顺序**不能换**。
- 反过来的话，`Kdbx.createVault` 失败（keyfile 读不到 / 目标不可写 / KDF 参数被拒）
  就会留下**一行指向不存在库的记录**：用户看到列表里多了一项、点进去永远报错，
  而库列表里**没有"删掉它"的入口**（那是另一个功能）。
- 现顺序的最坏情况只是"文件建好了但没登记"—— 用户在文件管理器里看得见、能自己删。
  ⇒ **两种失败的可恢复性差一个数量级**，这才是不换顺序的真正理由。
- ⚠️ 但**别因此说这一步"原子"**：`createVault` 内部是「先编码（纯内存，失败时没文件）
  → 再 write」，真正的写入失败（磁盘满 / 授权被撤）仍可能留下半截文件 ——
  那由 `SafKdbxFileSource.write` 的**写后读回校验**去发现（它会抛），而不是假装不存在。

## 152. 表单校验文案**不要**塞进 `UnlockUiError.Detail`（2026-10-01）

- `UnlockUiError.Detail` 的契约是「**来源层已经翻译好**的一句话」，
  `unlockErrorText` 对它是**原样返回**（绕过资源系统）。
- 把 ViewModel 自己写的校验文案（"请输入密码库名称"）塞进去，会有两个后果：
  ① 文案散在 Kotlin 里，与 `strings.xml` 那批同类文案**分家**，改措辞要找两个地方；
  ② 那种字符串在**孤儿串检查里是隐形的**（它不在 strings.xml）——
  于是"文案该不该翻译"在评审时也没有任何提示。
- ⇒ 新增 `UnlockUiError.Validation`（枚举）+ `ErrorText.validationTextRes`
  （纯函数：错误 → 资源 id，可单测）。分辨标准：**这句话是不是我们 UI 层自己写的**？
- ⚠️ 顺手踩到：加了分支之后 detekt 报 `unlockErrorText` 圈复杂度 **20**（上限 14）。
  两次修：① 把 Validation 的 5 个分支抽成 `validationTextRes`（降到 15）；
  ② 把 `forKdbx` 那句**提前 return** 折进 `when` 的 `InvalidCredentials` 分支 ——
  原来那句 return **本身就是第 15 个分支**。⇒ 降复杂度时，提前 return 要算进去。

## 153. ⭐ TOTP 算法名不做归一化 ⇒ KeePassXC 的 SHA-256 条目**恒为 `000000`**（2026-10-02，双库健康度审计）

- **现象**：KDBX 库里一条用 KeePassXC 建的 TOTP 条目，在 Vaultix 里验证码永远是 `000000`；
  没有任何报错、没有任何提示。Bitwarden 库里的同类条目却正常。
- **根因**：`generateHmac` 直接拼 `"Hmac$algorithm"`，而算法名是**外部数据**：
  | 来源 | 取值 | 拼出来的名字 |
  |---|---|---|
  | Bitwarden / Google Authenticator | `SHA256` | `HmacSHA256` ✅ |
  | KeePassXC / KeePassOTP 的 `TimeOtp-Algorithm` | **`HMAC-SHA-256`** | `HmacHMAC-SHA-256` 🔴 |
  后者让 `Mac.getInstance` 抛 `NoSuchAlgorithmException`，而上层
  `catch (_: Exception) { "0".repeat(digits) }` 把异常**吞成了全零**。
  `KdbxTotpCodec.resolveSettings` 只做 `trim().uppercase()`，原样透进这一层。
- **解法**：顶层 `normalizeAlgorithm`（去 `HMAC` 前缀与分隔符、只留位数、白名单
  `1/224/256/384/512`、认不出回落 `SHA1`），**咽点设在 `generateHmac` 一处**——
  所有路径（URI / KDBX 独立字段 / 位置式 `30;6;SHA1`）最终都过这里，不可能漏。
- **⚠️ 判据**：**吞异常换成"一个看起来合理的假值"，比崩溃还糟** —— 用户拿着 `000000`
  只会怀疑自己。凡 `catch` 之后返回兜底值的，都要反过来问"这个兜底值能不能被误认成有效结果"。
- **验证**：新建独立 JVM 工程真编译 `Totp.kt` 并跑 RFC 6238 向量（SHA256@T=59 → `46119246`、
  SHA512@T=59 → `90693936`），27 条断言全通过 —— **而非"看着对"就提交**。

## 154. 🔴 `period=0` 是可解析成功的畸形输入 ⇒ 验证码页**整页崩溃**（2026-10-02）

- **现象**：`otpauth://...?period=0`（或负数）在下游 `%` / `/` 上抛
  `ArithmeticException`；`TotpCodesScreen` 在 **Composable 里**直接调
  `remainingSeconds` 算倒计时，重组帧没有 try/catch ⇒ 抛了就是整页崩。
- **为什么躲这么久**：`generateTotp` 里有 `catch (_: Exception)`，所以**生成侧其实不崩**
  （只是出全零）；而 `remainingSeconds`/`progress` 是**无 catch 的纯计算**。
  ⇒ **「有保护的那条路径看起来正常」会掩盖紧邻的真崩溃** —— 这是它藏到今天的原因。
- **解法**：`safePeriod()` 统一兜底，`generateTotp`/`remainingSeconds`/`progress` 三个入口
  全过它；**外加**在解析边界 `parseOtpAuth` 就把 `period` 夹住（`toIntOrNull` 认 `0`）。
- **⚠️ 判据**：**畸形输入的"能解析成功"不等于"能用"**。凡从 URI / 文件 / 外部模型读来的
  数值，在**进入模型那一刻**就要夹到有效区间，别指望每个消费点各自记得兜。

## 155. 🔴 `toStoredCipherDto` 只拷 14 个字段 ⇒ **每次编辑**都抹掉服务端有、请求体没有的字段（2026-10-02）

- **现象**：编辑一次 Bitwarden 条目后，本地行丢掉 `organizationId`（组织成员条目**降级为
  个人条目**＝"共享库里的东西不见了"）、`passwordHistory`、`creationDate`、`attachments`、`key`。
- **根因**：本地落库是从**上传请求体** `CipherRequest` 反推出来的，而请求体**天生不包含**
  这些字段（它们压根不是这次要提交的东西）。`CipherRequest` 那三个透传字段是 2026-09-23
  为了避免「发给服务端时丢」才加的 —— **只修了上行，没修本地**。
- **解法**：加 `previous: CipherDto?` 参数做**顺延**（这些值一次编辑本来就不变），
  更新路径必传；新建路径不传（默认值 null ⇒ 干净）。
- **⚠️ 判据**：**"从 A 还原 B"的方向天然有信息缺口**。凡是"由请求体/领域模型重建本地快照"
  的写法，都要列出"哪些字段 A 里根本没有"，逐个回答"它去哪了" —— 答不上来的就是静默丢弃。
- **注意**：顺延不等于把字段塞进请求体（那会改变提交语义，见 `CipherRequest` 关于附件的注释）。

## 156. 🔴 离线「新建 → 编辑」再联网，那笔编辑被**静默丢弃**（2026-10-02）

- **现象**：离线新建一条、顺手改一笔，联网同步后界面显示"已同步"，编辑却不见了。
- **根因（两个缺陷叠加）**：
  1. `flushPending` 把 `ops` **一次性读进内存**就开循环；CREATE 成功后
     `remapCreatedLocalRow` 把行迁到服务端 id，**内存列表里后续那条 UPDATE 的实体
     仍是离线时的临时 UUID** ⇒ `PUT /ciphers/{旧临时 id}` ⇒ 404 ⇒ 被当自定义失败弃单；
  2. 库里的队列行也因此没改指 ⇒ **下一次** `flushPending` 从库重读后照样 404。
- **解法**：`createdIdRemap` 改指表（管本次循环）+ `pendingOpDao.repointCipherId`（管下一次）
  —— **两处缺一不可**，这正是"同一个事实存两份"最容易修一半的地方。
- **⚠️ 判据**：**凡是"id 会被服务端替换"的流程，都要检查有哪些地方缓存了旧 id**
  （内存快照、队列、索引、UI 状态）。只改数据库那一份，等于修了一半。

## 180. 🔴 `resolveUsingRemote` 的下载窗口：几秒内编辑的一笔被整体替换抹掉，且记成"已同步"（2026-10-20）

- **现象**：「用远端覆盖本地 / 拉取远端更新」过程中用户改了一笔，之后那笔**永久消失**，
  状态还是 `IN_SYNC`，**再也不会重试**。
- **根因（check-then-act）**：形状是
  ```
  调用方判"本地没改" → stat → read(网络，真机 1–10 s) → replaceSession(整体替换会话)
  ```
  调用方的判断在 `read` **之前**就做完了，而 `read` 本身要好几秒。窗口内编辑，
  `replaceSession` 会整体替换会话 ⇒ 抹掉；紧接着 `markResolved` 记 `IN_SYNC` ⇒ 无处再提醒。
- **解法**：`read()` **之前**用最新的 `syncStatus` 再判一次 `localChangedSinceLastSync`
  （判据只此一份：`KdbxCloudSyncStatus.impliesLocalChanges`），有本地改动 ⇒ 返回 `Conflict` 且**不下载**。
- **⚠️ 两处"不要"**（都踩过）：
  1. **不要**用 `markDeferred`：它只在状态已是 `CONFLICT` 时生效（语义是"用户点了稍后"），
     用在这里等于什么都不做，状态会停在 `SYNCING`；
  2. **不要**把本地改动改写成 `CONFLICT`：那会伪报"两边都改了"，把用户推向
     「用本地覆盖远端」这个**真丢数据**的选项。原样保留 `PENDING_UPLOAD` 即可。
- **残留窗口**：判断与 `read` 之间仍有微秒级 gap，但长的那个（下载）已覆盖。
  要彻底消掉得把"编辑"也纳入同一把锁，而那是 UI 线程会等的锁 —— 不值。
  取舍：**宁可多报一次冲突，也不静默覆盖**（报冲突最坏是多点一下）。
- **验证**：`KdbxCloudSyncCoordinatorTest`，`coVerify(exactly = 0) { source.read() }` +
  反证用例（本地没改时必须 `read` 1 次且替换 1 次）。撤掉判据 → 反证仍绿、正例转红。

## 185. 🔴 写回基线盲区：令牌对得上 ≠ 内容来源对得上，远端改动会被静默覆盖（2026-10-25）

- **现象**：另一台设备改了库（远端 v1 → v2）。本机同步时报"云端有更新"，
  用户没去拉，直接在本机改了一笔 ⇒ **远端 v2 被基于 v1 的内容静默覆盖**，
  两边都没有任何提示。这是密码管理器里代价最高的一类错。
- **根因（两道防线缺了第二道）**：
  ```
  远端 v1→v2
  → 同步报 REMOTE_CHANGED（基线令牌仍是 v1 ⇒ 这个判断是对的）
  → 用户在旧会话上编辑并保存
  → 主写路径 saveVia(expectedVersion = 缓存里的 v1)
  → 服务端说"还是 v1" ⇒ 条件写**通过** ⇒ 远端 v2 被盖掉
  ```
  版本令牌（ETag）回答的是「**远端动过没**」，回答不了「**我手里这份是不是它**」。
  而主写路径的 `expectedVersion` 来自**本地缓存里的旧令牌**，它天生不满足
  "内容与令牌配套"这条乐观并发的前提。
- **解法（两道防线，缺一不可）**：
  1. **令牌层**（`KdbxSyncOrchestrator`）："只有远端变"分支**绝不**提前推进基线；
     改为做**内容对账**（`adoptRemoteIfSameContent`）—— 内容相同才降级为 `IN_SYNC`，
     不同则保持 `REMOTE_CHANGED`、一个字节都不写。
  2. **内容指纹层**（`KdbxBaseStore` + `saveVia`）：每条库记一个"写回基线"内容指纹。
     `mutateLocked` 在**改动之前**取指纹并与基线比对，结论随
     `KdbxPendingWrite.baselineAligned` 上浮；`KdbxItemRepository.persist` 见到
     `false` 就**在落任何字节之前**抛 `KdbxWriteFailure.StaleBaseline`。
- **⚠️ 四个坑（都是本轮实测踩到的，写在这里省下一次重踩）**：
  1. **不能拿 `KdbxEncoder.encode` 的字节哈希当指纹**：`encode` 内部 `regenerateVectors`
     每次重派生内容密钥 + 重生成 IV/随机流 ⇒ 同一份库编两次字节**必然不同** ⇒
     "所有库永远算变过"。
  2. **不能为比指纹再 `encode` 一遍**：一次编码 = 一次 KDF 量级（真机数百毫秒）。
     ⇒ 指纹对**明文映射内容**（`KdbxMappedContent`）做 SHA-256。
  3. **不能把 `updatedAt` 算进指纹**：远端那份是别的设备重编码的，`<Times>` 与本地
     完全是两回事 ⇒ "远端只是重新编码、内容一模一样"会被判成"内容变了"，
     本该省掉的一次"请先同步"照样弹（防线变成纯噪音）。覆盖丢的是**字段值**，
     字段值已逐字进摘要 ⇒ 时间戳上宽一点是划算的。
  4. **`saveVia` 里不能"现查会话内容"比基线**：走到那里时 `session.content` 已经是
     **改完之后**的内容，而基线记的是改之前那一版 ⇒ 必然不等 ⇒ **所有正常保存全线误拦**。
     ⇒ 判据必须由 `mutateLocked`（改动之前）算出、随 `KdbxPendingWrite` 递上来。
- **语义选择**：基线**没记录**时放行（交给令牌那层兜底）。理由是解锁后的第一次写
  本来就没有基线，硬拦会让用户"保存不了"且没有出路。基线由两处补：
  `Kdbx.replaceSession`（拉取成功）、`Kdbx.adoptBaselineIfMatches`（对账相同）。
- **⚠️ 闸门只对"有云端来源"的库生效**：本地 SAF 库没有"远端那一版"这个概念，
  基线永远不会登记 ⇒ 无条件判它等于把所有本地保存拦住（实测就是这个后果，
  `KdbxItemRepositoryTest` 直接红了）。
- **⚠️ 同步编排器那条写路径传 `baselineAligned = null`（不表态）**：它推的是
  "会话里的全部改动"，可能是"上次编辑后一直没推上去"的旧货 —— 那时基线本来就对不上。
  这条路径的正解是**条件写**（`lastKnownVersion`）：远端若在期间变过，服务端会拒写
  并转 `CONFLICT`。写回基线只服务于**条目编辑的即时保存**。
- **验证**：`KdbxWriteBaselineTest`（14 条，含"编两次字节必然不同"的反向对照）、
  `KdbxSyncOrchestratorTest.远端只换令牌时对账失败也绝不假定内容相同`、
  `KdbxItemRepositoryTest`（本地库不受影响）。
- **⚠️ 判据**：**凡是"用自己的旧值去写别人也在写的东西"，都要问一句"我这个旧值
  和对方的当前值配套吗"**。版本号/令牌只保证"没人抢先"，不保证"我这内容是那一版的"。
  两层判断不可互相替代：令牌便宜但会误判，内容指纹准但需要提前埋点。
