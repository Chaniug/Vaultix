## 126. ⭐ 新增探针 `check_orphan_strings.py`：834 条字符串里 **126 条零引用**（2026-09-26；数字为当时摸底值，2026-10-02 实测存量 118）

- **起因**：删 `passkeyCount` 死代码时发现，它的**文案留在了 `strings.xml`**
  （`setting_passkey_saved` / `setting_passkey_saved_fmt` / `setting_passkey_saved_locked`
  / `setting_passkey_saved_none` —— 一组 4 条，UI 早没了）。
- **摸底**：本项目 834 条字符串里 **126 条零引用**。
  这类残留**不报错、不变慢、不影响功能**，所以没有任何现有手段会提它，
  只会一轮轮攒下去，最后没人敢动 `strings.xml`。
- **★ 但它是「报告器」不是「删除器」** —— 这是本条最关键的判断。
  零引用 ≠ 该删。本项目 `.ai/` 有一条**既存判据**：
  > **被"搬走"的留，被"取代"的删。**
  实证两例（都在代码注释里写明了的**刻意保留**）：
  - `about_channel`：注释写"渠道用短文案（预览版/正式版），**长解释留在
    `about_channel_preview` 那份里**"；
  - `settings_quick_unlock_desc`：注释写"⛔ **不用** `settings_quick_unlock_desc`
    （那句是首页版的独立入口说明，措辞针对『重新打开』）"。
  ⇒ 自动化手段**无法区分**「功能没了该跟着删」与「表述被取代但刻意留着做对照」。
  若做成"自动清理"，会把第二类一起清掉 ——
  那类删了**没有编译错误**，只会在某天需要它时发现它已经不在了。
- **解法**：工具只列候选集供人逐条判读；`--gate` 用基线
  （`.ai/tools/orphan_strings_baseline.txt`）做**只减不增**约束：
  **新增**零引用会让门禁失败（提醒作者顺手清干净），
  存量慢慢消减、**不阻塞当前工作**。
  ⚠️ **数字更正（2026-10-02）**：本条原文三处写「已生成 126 条 / 存量 126 条」，
  但基线文件**当前是 120 条**（首次生成时确实是 126，`a3d05b2` 有意消减 6 条真孤儿）。
  → 一切以**基线文件实测**为准，正文里的手抄数字会过期，基线文件不会。
  2026-10-02 实测**当前 118 条**（基线 120 − 已清 2），仍满足「只减不增」。
- **自测（7 用例）刻意覆盖的两类误判**：
  1. **前缀撞名**：`a_head` 与 `a_header` ——
     用 `in` 或 `startswith` 匹配会把后者的引用错算到前者头上，
     是本类工具最经典的误判，专门有一条用例钉住它；
  2. **只统计 `<string>`**，不把 `string-array` / `plurals` 的名字算进来
     （引用方式不同，`R.array.` / `R.plurals.`，混进来会误报）。
  另有一条**故意偏向漏报**的断言：字符串字面量里出现 `R.string.xxx` 也算"已引用"。
  ⇒ 方向选择说明：**与其误删在用的（运行时才炸），不如少报几条孤儿的。**
- **验证**：`--gate` 双向闭环 —— 注入一条新孤儿 ⇒ 报错并指名（exit 1）；
  还原 ⇒ 通过（exit 0）。
- **2026-10-04 存量 118 条已按前缀归组判读完毕**（详见下方「判读结论」小节）——
  **本轮仍未删任何一条**，因为判读结论是「这 118 条里绝大多数确实是残留，
  但删除属于独立批次」，混在别处做会看不清是哪件改坏了。
- **⚠️ 待办**：把判读结论里判为「删」的那批**成批删掉**并收窄基线
  （`--update-baseline`），删完必须 CI 真跑一次 `assembleFullDebug`——
  引用可能在 `string-array` / `plurals` / 数据类里，探针扫不到。

1. **`totp_steam_label` 不是"功能没做"** —— Steam Guard 早就做完了。

2. **`add_cloud_onedrive_*` 与 `cloud_accounts_onedrive_*` 只差一个前缀** ——

## 127. 🔴 「以为没新增违例」：我用**逐条对比**才发现自己引入了 `UnusedPrivateProperty`（2026-09-26）

- **现象**：本轮 `06bd5a4` 的提交信息写着「detekt **净 18 → 17**（无新增违例）」。
  收工前按规矩复核，把 origin/main 与当前的违例清单**逐条做集合差**，
  结果：**消除 1 条、新增 2 条** —— 净数从 17 变 19，但**只看净数变化是看不出来的**。
- **真因**：删 `passkeyCount` 时，它订阅的 `itemRepository` 唯一用途随之消失，
  变成 `SettingsViewModel` 上一个**没人用的构造属性** ⇒ `UnusedPrivateProperty`。
  这是**删除代码的典型副产品**：删掉 A，只被 A 用的 B 就成了死代码，
  而 B 在别处看着还挺合理（构造注入一个仓库，谁会怀疑）。
- **为什么"净数"骗人**：净数只回答"总数变了吗"。**抵消**（消 1 增 1）与
  **真的没动**在净数上完全一样。同一个文件里既消又增时尤其危险。
- **解法**：`itemRepository` 与它的 `import` 一并删除。
  ⚠️ 删 import 时我**先加了一行** `import io.vaultix.domain.VaultRepository`，
  而它**本来就在下一行** ⇒ 造出一个重复 import。**改 import 前先 grep 一遍现有 import。**
- **★ 可复用的验证手法**（比"跑一遍看总数"强得多）：
  ```bash
  git worktree add /tmp/base origin/main -f          # 基线单开一个工作区
  # 两边用**同一份** detekt 配置与输入目录各跑一次，再按「文件::规则」去重做集合差
  comm -13 <(基线 | 归一化) <(当前 | 归一化)      # 必须有输出 = 引入新问题
  ```
  - ⚠️ **归一化必须掐掉行号**（`sed 's/:[0-9]*:[0-9]*:/::/'`）：
    行号会随改动漂移，带着行号比会把「同一处违例挪了几行」误判成"消一条 + 增一条"。
  - ⇒ **判据：`comm -13` 的输出必须为空。** 只看总数等于没看。
- **⚠️ 顺带记一条口径**（别被吓到）：沙箱里用 detekt 1.23.8 跑全树会报 **175 条**
  （`MagicNumber` 等），而 CI 跑 `./gradlew detekt`（2.0.0-alpha.6）是**真的全绿**。
  两边的默认规则集不同 ⇒ **本地这套只用来做「相对基线的差值」，不能用来判"是否绿"。**
  1.23.8 在沙箱里的用途是**抓回归**，不是复现 CI。

## 142. 顶栏标题折两行：`softWrap = false` 会让整件事**静默不发生**（2026-10-01）

改 L2（标题过长时"分栏 / 分行"）时踩的：

- 把测量逻辑改成"一行放不下 ⇒ 折两行"、并正确算出 `maxLines = 2` 之后，
  **界面上仍然是一行** —— 因为该 `Text` 上有 `softWrap = false`。
- ⚠️ 这类失败**没有任何信号**：不报错、不崩溃、detekt 不报，
  只是"你算出来的行数被下游忽略了"。组合期测量 + 渲染期参数，两边**各写各的**。
- **纪律**：**凡"算出来的排版结论"，都要回头确认渲染端有对应的开关没被关掉**
  （`softWrap` / `maxLines` / `overflow`）。三个参数任一不对，结论就只是个数字。

**配套的两条（同一次改动）**：

1. **固定栏高下两行有字号预算**：栏高写死 72dp，而列表顶部让位高度也按它算
   ⇒ 26sp 两行 ≈ 62dp + 16dp 内边距 = **78dp，超出 6dp**，表现是"第一条内容被顶栏压住一点点"。
   ⇒ 两行时字号上限压到 **20sp**（48 + 16 = 64dp，留在 72dp 内）。
   ⚠️ **改换行前先算一遍栏高预算**，别等"内容被压住"这种隐蔽反馈。
2. **收起态（16sp）不折两行**：小字号折两行看着像"标题换行了"而不是"分栏"，
   且收起态栏高只有 48dp ⇒ 收起态维持老行为（缩字号）。
   ⚠️ 别让"两行"这个新能力**无条件生效**，它只在展开态才成立。

## 143. 「两栏」在手机上落地应为**两行**（2026-10-01）

- 用户原话是"分成两**栏**显示"，但 6 寸屏左右各占一半 ⇒ **两栏都变窄**，
  结果是两边都读不清 —— 比原来一行缩字号还糟。
- ⇒ 取"两行"。**记录在案的价值**：下次再看到用户说"分栏"，先确认是"分栏"还是"分行"；
  这两个词在本项目里指向**完全不同**的实现。
- 已知近似（写在源码 KDoc 里）：两行判定用「文本总宽 ≤ 可用宽 × 2」= 假设两行都填满。
  真换行是贪心的 ⇒ 理论上存在"实际要 3 行"的边界，后果是**省略号兜底**（不溢出、不崩）。
  没有改成"按 `Constraints(maxWidth)` 真测一次"：会与同项目 `MiddleEllipsizedText`
  的宽度比较写法不一致，而收益只是消掉一个很少命中的边界。

## 144. 拆行之后，**可压缩项要跟着换**（2026-10-01）

- 状态行原为一行：来源（`weight(1f)`、中间省略）+ 角标 + 条目数（**都不压缩**）。
  压缩压力全部由**来源**承担 —— 这正是它能成立的原因。
- 拆成两行后：第一行只剩来源（独占整行），第二行是角标 + 条目数。
  ⇒ 第二行**没有任何一项可压缩**，窄屏 + 长角标时会**溢出**。
- **解法**：把"可压缩"这个责任转给第二行的**角标**（`weight(1f, fill = false)`），
  条目数继续不压缩（它是锚点信息："有多少条"必须完整可读）。
- **纪律**：⚠️ **布局里"谁来吸收挤压"是一项显式设计，不是默认值**。
  任何"把一行拆成两行 / 把两行并成一行"的改动，都要重新回答一遍这个问题 ——
  否则要么溢出，要么某个关键信息被挤成省略号。

## 159. 🔴 防截屏只覆盖了 1 个 Activity，另外 9 个**全裸**（2026-10-02，双库健康度审计）

- **现象**：`FLAG_SECURE` 只挂在 `MainActivity`（经 `ScreenSecurityEffect` 这一个 Composable）。
  而 `AutofillActivity` / `ManualFillActivity` / `AutofillSaveActivity` /
  `AutofillInlinePlaceholderActivity` / `CredentialProviderActivity` /
  `PasskeyGetActivity` / `PasswordGetActivity` / `PasskeyCreateActivity` /
  `CredentialProviderSettingsActivity` 这 9 个**都不走 Compose** ⇒ 挂不上去。
- **为什么这一处尤其严重**：它们恰恰是**用户在第三方 App 里最常看到的那几张**
  （填充候选框、通行密钥选择、解锁后的条目详情），屏上就有条目名与密码。
  自动填充框一弹出，系统截图/录屏/"最近任务"卡片缩略图就能把内容整段录走。
- **解法**：`ScreenSecurityGuard` + `ActivityLifecycleCallbacks` 在 `Application.onCreate()`
  注册（另配 `onActivityPreCreated` 覆盖 API 29+ 的更早时机），
  `VaultixApplication` 调一次 `install`。开关偏好经 `@Volatile` 内存快照同步读取。
- **⚠️ 判据**：**安全属性必须是"跟着载体走"，不能是"每个页面记得写一行"**。
  凡是"要记得做 X 才安全"的模式，都应该换成宿主/生命周期级的统一挂载 ——
  新加一个 Activity 时，**默认就被保护**。
- **附带**：`.bak` 备份那条前提不实（见 [05-KDBX 本地库 #158](../issues/05-KDBX本地库.md)），本次一并更正了注释。
