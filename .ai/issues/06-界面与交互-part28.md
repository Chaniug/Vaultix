### 取证链：0 从哪来

1. `CloudAccountsScreen.kt:154` → `NoticeSnackbar(state.notice, ...)`。
2. `NoticeSnackbar`（:812）`val noticeText = noticeId?.let { stringResource(it) }` —— **变量式**解析。

### 编译期 vs 运行时 R 类（决定性对照）

| | `cloud_msg_probe_ok` | `cloud_msg_removed_onedrive` | `cloud_msg_removed_webdav` |
|---|---|---|---|
| `compile_symbol_list/.../R.txt` | `0x0` | `0x0` | `0x0` |
| `runtime_symbol_list/.../R.txt` | `0x7f0f0133` | `0x7f0f0134` | `0x7f0f0135` |
| 编译期 `R.jar` `javap -constants` | `public static int ... = 0` | 同 | 同 |
| 运行时 `R.jar` | `= 2131689779` | `= 2131689780` | `= 2131689781` |

`javap -constants CloudAccountsViewModel.class` **改前**：

```
public static final int SETTINGS_CLOUD_FIELDS_MISSING = 0;
public static final int SETTINGS_CLOUD_INVALID_SERVER = 0;
public static final int SETTINGS_CLOUD_CREDENTIALS_IN_URL = 0;
public static final int SETTINGS_CLOUD_PROBE_OK = 0;
... 11 条全 = 0 ...
public static final int SETTINGS_CLOUD_REMOVED_WEBDAV = 0;
public static final int SETTINGS_CLOUD_REMOVED_ONEDRIVE = 0;
```

**机理**：AGP 编译期 R 类把资源 id 生成为 `0x0` 占位（**不是**运行时真值），
Kotlin `const val` 要求编译期常量 ⇒ 编译器把 **0 内联进每个调用点**。
运行时才有的 `0x7f0f01xx` 永远没机会被读到。于是 `notice = 0` /
`CloudError.Res(0)` → UI `stringResource(0)` → 崩。

⚠️ 全仓宽松扫描确认：只有 `CloudAccountsViewModel.kt` 这 11 处 `const val = R.*`。

### 四处修法

1. **11 条资源 id 常量一律改普通 `val`**（`private companion object` 内）。
   `val` 不是编译期常量，Kotlin 生成 `<clinit>` 里的
   `getstatic R$string.cloud_msg_xxx → putstatic ...`；运行时 classpath 的 `R$string`
   字段是**非 final** 真值，JVM 不做常量折叠 ⇒ 拿到 `0x7f0f01xx`。
   ⚠️ `const val TAG = "CloudAccounts"` 是普通字符串常量，无害，保留。
2. **两个变量式解析点过统一守卫 `safeStringRes()`**：
   `NoticeSnackbar` 的 `notice`、`CloudError.Res` 的 `id`。
   `internal fun safeStringRes(@StringRes id: Int?): Int? = id?.takeIf { it != Resources.ID_NULL }`。
   无效 id 返回 null 让调用方降级，绝不把 0 交给 `stringResource`。
3. **`NoticeSnackbar` 无效 id 也必须消费掉**：`LaunchedEffect(noticeId, noticeText)`
   里 `noticeId != null -> onConsumed()`，否则 0 会永远挂在 `UiState` 上；
   有效文案弹完照常 `showSnackbar` + `onConsumed()`。
4. **`CloudError.Res` 有可见降级**：无效 id 显示 `error_unknown_no_detail`，不静默吞掉。
   抽成 `@Composable cloudErrorText(error)`（顺带把 `CloudAccountsScreen` 圈复杂度
   从 16 压回 detekt 上限 14 以内）。

### 判据反转：订正 #289

`probeWebDav()` 成功分支同样写 `notice = SETTINGS_CLOUD_PROBE_OK`（也是 0），
且它发生在 `refresh()` **之前** ⇒ **#289「连上 WebDAV 就闪退、重进账号已添加」的真因
极可能就是这个 0，而不是「成功之后某处 IO 抛异常」**。

#289 补的 `launchGuarded` **仍然必要**（无全局兜底时裸 `viewModelScope.launch`
未捕获异常确实会杀进程、凭据写入 / 自检 / 清单读取确实压在主线程），
但它兜的是**协程内部**异常；Compose **重组期**异常不在它的作用域里，两者是不同的边界。
⇒ 结论改写为：#289 修了真实存在的健壮性缺口，但**没有**修掉当时那次闪退；
#290 才是那两次闪退的共同根因。

### 6 条坑

1. **Android 编译期 R 类不是常量真值**：`compile_symbol_list` 全 `0x0`，
   `runtime_symbol_list` 才是 `0x7f...`；把资源 id 写进 `const val` 等于把 0 写死。
2. **`stringResource(0)` 是重组期异常**：栈在 `Recomposer` / `Choreographer`，
   不经过 `viewModelScope`，任何协程异常边界（`runCatching` / `CoroutineExceptionHandler`）
   都兜不住 ⇒ 直接杀进程。
3. **「变量式」资源解析与「字面量式」不同**：`stringResource(R.string.foo)` 永远安全，
   `stringResource(idFromState)` 必须先验 `Resources.ID_NULL`。
4. **`val` 与 `const val` 差一条 `getstatic`**：改完必须 `javap -c` 看 `<clinit>`
   是不是真的读 `R$string.*`，不能只看 `javap -constants` 的字段声明。
5. **detekt 圈复杂度**：页面里塞 `when` + `?.let` + `?:` 会从 14 涨到 16；
   抽独立 Composable 是最省事的降法。
6. **门禁注释也会被别的门禁扫**：`selftest_cross_file_private.py` 把测试注释里
   `R.string.y` 的示例当成悬空资源引用 ⇒ 示例文本不要写成真实可解析的符号。
