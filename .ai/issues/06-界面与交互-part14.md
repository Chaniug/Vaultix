## 266. 上一轮把云图标删过头：OneDrive 上的 KDBX 变得和本地一模一样（2026-11-10 下午，真机反馈 —— #263 的直接后续）

**现象**：OneDrive 上的 KDBX 库，条目行尾**没有**云图标，看起来和本地库完全一样。

用户原话：

> onedrive 上的 kdbx 条目，居然没有小云图标，这样和本地的 kdbx 条目看起来没有区别啊，不对。
> onedrive 上的 kdbx 是必有小云图标，因为它来自云，而本地文件没有云图标，它是来自本地的，这样的才对。

### 这是 #263 的过度修正

#263 修的是「本地库不该有云」，修法是 `cloudSyncBadgeOrNull` 里一句：

```kotlin
if (vaultKind == VaultKind.BITWARDEN) syncedInVault ?: true else null
```

`else null` 把 **所有 KDBX** 一起判成"不画"。判据因此从「这个库有没有云」退化成
「这个库是不是 KDBX」—— 而后者与要回答的问题**无关**。

### 真根因：两个问题被一个答案合并

用户提这两轮反馈时，问的其实是两个不同的问题：

| 问题 | 数据源 | 图标形状 |
|---|---|---|
| **这个库本身在云上吗**（地点） | `VaultSummary.origin` | 裸云（无对勾） |
| **这一条推上云了吗**（状态） | Bitwarden `pending_ops` | 云+对勾 / 云+斜杠 |

#263 之前：两问都用「状态」那一套答 ⇒ 本地 KDBX 被画成「已同步」（假）。
#263 之后：两问都被答成 null ⇒ 云端 KDBX 失去「地点」标记（也是假 —— 少说了实话）。
**两次都不是"画错图标"，是"用一套语义答了两个问题"。**

### 修法：三态而不是二值

```kotlin
internal fun cloudSyncBadgeOrNull(
    vaultKind: VaultKind?,
    vaultOrigin: String?,
    syncedInVault: Boolean?,
): ItemCloudBadge?   // SYNCED / PENDING / CLOUD_VAULT / null
```

| 库 | 行尾 | 回答的是 |
|---|---|---|
| Bitwarden | `SYNCED`（云+对勾）/ `PENDING`（云+斜杠，error 色） | 第二问 |
| KDBX·OneDrive / WebDAV | `CLOUD_VAULT`（**裸云**，弱化色） | 第一问 |
| KDBX·本地 SAF | `null`（不画） | 哪儿都不在 |

两个关键约束：

1. **裸云不带对勾** —— 带了对勾就是在复用 Bitwarden 的条目级语义，而 KDBX 是整文件同步，
   「这一条上云了」这件事**不存在**。形状不同才让两个语义可区分（读屏文案也各自独立）。
2. **KDBX 是否在云上只认 `kdbxSourceTargetOf(origin)`** —— 那是「这个库在哪」的唯一真源
   （`VaultOriginLabel.kt`）。写成 `origin.startsWith("onedrive:")` 会让 **WebDAV 库**又退回
   「和本地一样」，正是 `#264` 那类"来源判据存了两份"的复发。

### 判据

> **一个图标只能回答一个问题。**
>
> 当两次修复分别朝两个方向错（多画 / 少画）时，先别找"哪个分支写错了" ——
> 先问「这个位置到底该由几个问题共同决定」。二值类型答不了两个问题，
> 强行答就必然有一边错。

### 已知边界：TOTP 页**没有**跟着改（是碰巧对，不是判据对）

`TotpCodesScreen` 里也画云，但条件相反 —— 只在 `!synced` 时画（**告警**语义：
"这条待推送"）。而它读的是 `syncStates[itemId] ?: true`，KDBX 的空 map 让这个表达式
恒为 `true`，于是 `!synced` 恒 `false`、**永不绘制**。

⇒ 结果恰好正确（KDBX 不画），但**理由是错的**：一旦哪天有人给 KDBX 也塞条目级
同步状态，TOTP 页会立刻冒出"待推送"的云加斜杠，而 KDBX 根本没有这个状态。

本轮**刻意不动它**，理由是语义不同：TOTP 页的云是告警（异常才出现），
把一个"地点"图标塞进去会让"这里为什么有云"更难读。真要统一，得给它也接
`cloudSyncBadgeOrNull` 并接受"常态也有云"，那是另一个取舍。

⚠️ 记在这里是为了不让人误以为"TOTP 页已经处理过了" —— 它只是没被触发。

### 测试

`CloudSyncBadgeTest` 由 6 条扩到 **12 条**（同一文件，两轮反馈都钉住）：

| 用例 | 守的是 |
|---|---|
| `kdbx local file never draws a cloud` | #263（第一轮）不能因为本轮改动而丢 |
| `kdbx on onedrive shows the cloud vault badge` | 本轮 |
| `kdbx on webdav shows the cloud vault badge` | 判据不是"是不是 OneDrive"，是"来源不是本地文件" |
| `kdbx cloud vault ignores per item sync state` | 第一问不被第二问污染 |
| `kdbx with unknown origin does not draw a cloud` | 加载期不闪假图标 |
| `kdbx with broken cloud origin degrades to local` | 与 `kdbxSourceTargetOf` 的退化口径一致 |
| `bitwarden ignores vault origin` | 反向：第二问不被第一问污染 |
| `only kdbx can return cloud vault…` | 穷举 `VaultKind.entries`，新增库类型时立刻红 |

## 267. 「已对 N 个库生效」把**暂时状态**说成了**配置结果**（2026-11-10 下午，真机反馈）

**现象**：设置 → 锁与安全 →「指纹解锁 / 应用内 PIN」的副标题写着「已对 3 个库生效」，
但用户有 5 个库。

用户原话：

> 这两个开关的下方文案，已对 x 个库生效的文案是否要移除，目前我的想法就是要对所有库都生效。

### 数字本身没错，错在它回答的问题

范围早在 2026-09-30 就固定成「全部库」（逐库勾选 UI 已删除）。所以 `N < 总数`
**不代表**有几个库被排除在范围外，它只表示：

> 那几个库还没被**主密码解锁过一次** —— 房间信封要在解锁时顺手封
> （`LocalUnlockEnrollment.enrollJustAuthenticated`），而 KDBX 还需要主密码在手。

也就是说 N 是个**会自动收敛的暂时值**（用一次主密码就补上），不是用户选出来的配置。
旧文案把这两件事混成一句，用户唯一能读出的意思是「我有库漏了 / 坏了」。

### 修法：分两句，只在**真有缺口**时报数字

| 状态 | 文案 |
|---|---|
| 全覆盖 | 「已对所有密码库生效」 |
| 有缺口 | 「已对 %1$d/%2$d 个库生效」 |

- 全覆盖那句确认的是**用户真正关心的事**（范围），而不是复述一个数字；
- 有缺口时**必须带分母** —— 只给 3 不给 5，用户无法判断"是差 2 个还是差 20 个"；
- 分母用 `rows.size`（用户的全部库），**不是**"可纳入的候选集"：任何过滤都会让缺口凭空消失。

⚠️ 一个库都没有时走不到这里（开关本就该是关的），但仍加了 `rows.isNotEmpty()` 守卫 ——
`0 >= 0` 会在空列表上让「已对所有密码库生效」成立，那是一种 vacuous truth，也是谎。

### 判据

> **给用户看的数字，必须能被用户用来做判断。**
>
> 「已对 3 个库生效」不可判断（3 是全部吗？是选的吗？是坏了吗？）；
> 「已对 3/5 个」可判断（还差 2 个）；「已对所有库」也可判断（没有缺口）。
> 只给一个**孤立分子**，是最省事也最没用的写法。

### 待观察

`readyCount` 的口径与开关状态（`CapabilityState`）共用 `inScope` 判据，
两处漂移会出现「开关说已启用、数字写 5」的自相矛盾 —— 已有注释钉住，但**没有单测**。
真要钉，得把 `readyCount` 提成 internal 纯函数（现在它是 private composable 辅助）。
本轮没做：`QuickUnlockController` 的状态推导已有 20+ 条单测覆盖，
再为一个文案加测试的收益低于改造成本。
