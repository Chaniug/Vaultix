## 292. 🟢 预览包与 Release 名字太长 —— 短命名约定与门禁（2026-11-14）

> **触发**（用户原话）：「`Vaultix-v0.13.1-dev-fcb77f9-preview.apk` 最终生成包的名字
> 偏长了，release 名字也偏长了吧，你看看如何优化。**以后这种名字短一点，简洁一点**。」
>
> ⇒ 不是一次改名，是**长期约定**。约定真源：
> [`../conventions/8.12-发布产物命名.md`](../conventions/8.12-发布产物命名.md)。

**这章回答什么问题**：名字该砍哪一段、哪一段一个字都不能砍，以及怎么让
「以后短一点」变成机器可校验的约束而不是一句口号。

### 292.1 现象与边界

| 项 | 改前 | 字符数 | 改后 | 字符数 |
|---|---|---|---|---|
| preview APK | `Vaultix-v0.13.1-dev-fcb77f9-preview.apk` | 39 | `Vaultix-fcb77f9.apk` | 18 |
| preview Release 标题 | `Vaultix v0.13.1-dev-fcb77f9 · Preview` | 37 | `v0.13.1-dev-fcb77f9 · Preview` | 29 |
| stable APK | `Vaultix-v0.13.1.apk` | 17 | **不动** | 17 |
| stable Release 标题 | `Vaultix v0.13.1` | 15 | **不动** | 15 |

**稳定侧不动**是拍板，不是遗漏：`Vaultix-v0.13.1.apk` 本就够短，版本号是稳定版
唯一身份，没有 `dev` / SHA / 渠道后缀可删；再砍产品名会和 tag 混淆。用户抱怨的
「这种名字」指的是带 `dev` 的预览包。

### 292.2 约束：短不能突破 #218 的身份硬约束

> #218 判据（[`part11.md`](./01-构建与环境-part11.md)，同一位用户 2026-11-01 拍板）：
> **「能被用户验证的，才叫『发布物的身份』—— 只写 SHA 等于没写身份」**。

当时的事故正是标题只有一长串 SHA（`Development Preview (dev-341be3a58fb…)`），
在 Releases 列表里被截断、看不出是哪个版本。所以本轮**先确认哪些不能砍**，再谈短：

1. **标题里的版本 + 7 位短 SHA 一字不砍**，`-` 不换回 `+`（`+` 是 build metadata，
   不参与版本比较）—— 这是 #218 的原判据，不能为了短把用户自己定的规矩推翻。
2. **APK 名保留 7 位 SHA**，不能叫 `Vaultix-preview.apk`：多次下载会互相覆盖、
   也无从把手里的包对应回某次构建。SHA 是短名与可验证之间唯一的连接点。
3. `-preview` 后缀纯冗余：tag 叫 `preview`、有 prerelease 徽标、标题带 `· Preview`。
4. 标题里的 `Vaultix ` 前缀冗余（页面在 Vaultix 仓库下，面包屑已有产品名）；
   **但 APK 名要保留产品名** —— 文件脱离页面后仍要认得出是什么。

⇒ 可删的是**重复**，不是**身份**。身份由 Release 页承载（标题 + 版本/提交/构建/
签名表 + tag），文件名只留能对应回页面的提交标识。

### 292.3 做法（改了什么）

| 文件 | 改动 |
|---|---|
| `.github/workflows/ci-debug.yml` `Collect debug APK metadata` | `_dst` 模板 `Vaultix-v${version_name}-preview.apk` → `Vaultix-${short_sha}.apk`；改名段注释重写 |
| 同上 | 新增 `short_sha` 空值兜底（`dev-build-info.env` 是旧格式时回退 `GITHUB_SHA` 前 7 位），否则会产出 `Vaultix-.apk` |
| `.github/workflows/ci-debug.yml` `Publish Debug APK to preview Release` | `name` 去掉 `Vaultix ` 前缀 → `v${{ …version_name }} · Preview`；补 #292 注释 |
| 同上 | 顺手订正历史注释里「标题前缀沿用 ⚠️」的漂移（实际早就改成字面 `· Preview` 后缀） |
| `.github/workflows/release.yml` `Collect APK + SHA-256` | **只加注释**：说明稳定侧不跟着改、两个模板都由门禁钉住；命名字符串未动 |
| `.github/workflows/ci-debug.yml` `android-ci` | 接 `Check release naming` + `Self-test release naming checker` 两步 |
| `.ai/tools/check_release_naming.py` | 新建：4 模板精确匹配 + 变量数 ≤ 1 + 渲染长度预算 + #218 身份不退化 |
| `.ai/tools/tests/selftest_release_naming.py` | 新建：拿**真实 workflow** 做 11 组变异，逐组判红判绿 |
| `.ai/conventions/8.12-发布产物命名.md` | 新建：长期约定真源（为什么 / 形状表 / 边界） |
| `.ai/conventions/8.10-架构与目录地图.md` | 约定范围 `8.1~8.10` → `8.1~8.12`；§7 速查表加一行指向 8.12 |

**门禁挂 `ci-debug.yml` 而不是 `ci-docs.yml`**：前者 `paths` 含
`.github/workflows/**` 与 `.ai/tools/**`，改命名 / 改门禁都会触发；后者**不含**
workflow —— 挂那边就是 #218.7 的复刻：「改门禁 → 门禁不跑 → 以为通过」，
**假绿灯比没有绿灯更贵**。

### 292.4 门禁设计与两轮反证

门禁刻意不写「禁止某些长名字符串」的黑名单，而钉住**形状**：

- 4 个模板精确匹配（改形状必然红 ⇒ 逼着人回 8.12 重新拍板，而不是加白名单）；
- 一个模板里 `${…}` / `${{ … }}` 占位符 ≤ 1 ⇒ 从结构上挡住「版本 + SHA + 渠道」重新堆叠；
- 按最坏样本渲染后 APK ≤ 24 字符、标题 ≤ 34 字符；
- #218 身份：preview 标题必须含版本变量、正文表必须含 `steps.apk_meta.outputs.short_sha`；
- **找不到被检查的步骤 / 改名语句一律报红**（静默放过 = 门禁失效）。

**第一轮反证（天然）**：先在**未改的长名 workflow** 上跑门禁 ⇒ rc=1，
报出 5 条（两个模板不符、`-preview` 后缀、APK 39 > 24、标题 37 > 34）。
改完 workflow 后复跑 ⇒ rc=0。这证明门禁确实在检查当前文件，不是「写在那里好看」。

**第二轮反证（自测）**：`selftest_release_naming.py` 复制真实两个 workflow
逐项改坏 —— 长名 / 无 SHA / 标题加回 `Vaultix ` / 删版本变量 / 删正文提交行 /
stable 堆长名 / stable 加后缀 / 一个模板塞两变量 / 步骤改名 / 缺文件 —— 10 组
必须红，基线必须绿。每个变异用 `sub()` 断言「原文里确实有这个子串」，
替换失效直接自检失败（不给「看起来全绿」留口子，同 8.11 判据）。

### 292.7 明确不做 / 未决

- **不动签名链路**：`SIGNING_*` Secrets、`Decode signing keystore`、attestation、
  `release.yml` 的命名字符串全部原样（用户 2026-11-14 明确「签名没有疑问」）。
- **不推 `rele`**：本轮只推 `main`，正式 `v0.13.1` 不受影响；preview 包按新名产出。
- **不改 `Upload APK` artifact 名**（`debug-apk`，3 天内部产物，不给用户下载）。
- **不改 `versionName`**：包内仍是 `0.13.1-dev-<7位SHA>`，设置页显示不变 ——
  文件名短了不代表版本身份变了。
- 未决：无。约定已写入 8.12 并由门禁锁定；将来新增 flavor / 渠道需回 8.12 重新拍板。

### 292.8 判据（给下一轮）

> **「短」是删重复，不是删身份。** 发布物的身份必须能在页面上被用户验证；
> 文件名可以短到只剩「产品名 + 可对应的提交」，前提是页面把版本 / 提交 / 构建 /
> 签名原样列全。约束变化时改约定与门禁**两处一起改**，别给门禁加白名单。
