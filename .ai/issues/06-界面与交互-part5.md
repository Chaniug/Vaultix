## 117. 验证码遮罩字符：`•` → `*`，以及「等宽字体宽度」这条隐形约束（2026-09-23）

- **背景**：用户反馈「验证码界面隐藏验证码的是用圆点不好看」，在给出选项后选择换成 `*`。
- **约束（这是本条真正的知识点）**：`TotpGenerator.mask` 原来**特意**用 `•`（U+2022）
  而不是 `*`，KDoc 里写明了原因。真正的机制比"回"要细：
  - `•` 的东亚宽度属性是 **Ambiguous（A）** —— 中日韩字体常按**全角**渲染，拉丁字体按半角；
  - `*` 是 **Narrow（Na）**，且等宽字体里它的字形盒**普遍比数字窄**（多画成上标状小星号）。
  ⇒ 后果不是"两者都错"，而是**遮罩串与数字列不完全等宽**，
  位数一变（6 位码 ↔ 8 位码、HOTP 计数器进位）整串宽度**会有可见跳动**。
  ⚠️ 验证码每 30 秒刷新，这个跳动会被反复看到，所以它是**观感问题而非功能问题**。
- **处理**：按用户要求改 `MASK_CHAR = '*'`，但**没有删掉原警告** ——
  而是把代价如实改写成"已知代价（用户主动选择接受）"，并留下后路：
  若日后想消抖又不回圆点，可换 `●`（U+25CF，宽度属性与 `•` 相同、观感更实）。
  ⇒ **纪律**：用户推翻一个"有理由的设计"时，**改实现但不要抹掉理由**，
  把它降级成"已知代价"留档 —— 否则下一个人会重新踩同一个坑。
- **范围**：只改验证码（用户指定）。详情页密码 / 卡号 / 逐字段隐藏仍用 `•`。
  `TotpCodesScreen` 侧**零改动** —— 它不含硬编码遮罩字符，全走 `TotpGenerator.mask`，
  这正是"遮罩只在一处实现"的好处。
- **验证**：`core/common` 是纯 JVM 模块（无 Android 依赖），可整份源码 + 整个测试文件
  真编译真运行：36/36 通过；并做**变异测试**（`'*'` → `'#'`）⇒ 5 条失败，
  证明 8 条断言不是空转。这比上一轮 #116 的"片段编译"可靠得多。

## 118. 设置页「网盘账号」：按钮层级倒挂，与只活两秒的断开原因（2026-09-23）

- **背景**：用户反馈「设置页面的优化，尤其是 OneDrive 同步的按钮」。定范围**只动 OneDrive**。
- **发现一：主操作被做成了最弱的样式。**
  账号卡里「登录 Microsoft 账号」是 `TextButton`，**与「注销」同款平级**。
  可它是本页最核心、最难成功、最需要被看见的动作；未连接时它还承载**恢复路径**
  （"我该怎么把它弄回来"）。⇒ `TextButton` 是 M3 最弱的按钮，主路看起来最不重要。
  改法：主操作 `FilledTonalButton` / 破坏性 `TextButton`+error 色且置底。
  ⚠️ **不是重新设计，是向同页已有的正确形态看齐** —— WebDAV 那侧本来就是
  强按钮 + 独立自检 + 4 态状态卡。**WebDAV 一行未改。**
- **发现二（本条真正的知识点）：UI 把一个**已经做好的**语义区分丢掉了。**
  `OneDriveAuthTemporarilyUnavailableException` 的 KDoc 写得清清楚楚：
  临时不可用（打盹期静默刷新被系统掐断，**可自愈**）vs 真失效（**必须重新登录**），
  「混成一句话会让用户白跑一次登录流程」。
  `CloudAccountsViewModel.oneDriveMessage()` **确实做了这个分流** —— 但结果只进
  `error` → snackbar，**两秒就没了**。而账号卡上的「未连接」是**持续状态**：
  用户隔天回来看见"未连接"，想不起当时那句一闪而过的话，只能靠猜。两种错误
  在界面上长得**一模一样**。
  ⇒ 加 `UiState.oneDriveIssues`（按账号存），把原因**挂在状态上**跟着一起显示。
  ⚠️ 教训：**做了分流却没让用户看见，等于没做。** 判定"这个区分实现了没有"，
  要看**最终呈现**，不能只看逻辑层有没有分支。
- **发现三：`connected` 回答不了"现在还能不能用"。**
  它只说明"MSAL 缓存里还有没有这个账户"。而「账户还在、静默刷新已被掐断」
  是 OneDrive 唯一会**悄悄坏掉**的状态 —— 界面一直显示"已连接"，直到用户去读库
  才失败，**那时人已经在另一个页面上了**，看不到任何解释。
  ⇒ 进页面时真去取一次 token（新增 connector 转发 `probeOneDriveToken`）。
  ⚠️ 探测失败**不写成 `error`**：它是**背景探测**、不是用户刚触发的动作，
  弹 snackbar 会让人以为是自己操作出了问题。
  ⚠️ 只在 `connected` 时探：未连接本来就是"需要重新登录"（界面已如实写着），
  再探一次纯属浪费一次网络往返，还会把真正的"未连接"盖成"暂时不可用"。
- **发现四：`key()` 不能省。**
  `LaunchedEffect` 按**调用位置**（而非参数值）与组合树匹配。裸写在 `forEach` 里，
  账号列表一增删，后面每一项的"位置"都前移 ⇒ **A 的探测跑在 B 的槽位上**。
  另：`LaunchedEffect` 的 key **只放探测真正依赖的**（`storedId + connected`），
  **刻意不放 `oneDriveIssues`** —— 放了会形成"结果 → 重组 → key 变 → 再探"的自咬。
- **★ 自造 bug（靠 diff 自查抓到）**：`signInOneDrive` 成功回调我原本写成
  `it.oneDriveIssues - session.accountId`，但**写入侧的键是 `account.storedId`** ——
  两者形状不同（差 `.utid`，正是 `matchesStoredAccountId` 存在的理由），
  按 MSAL id 删会**静默删不掉**，表现为"登录成功了但红字还挂着"。
  ⇒ 改成整表清空。
  ⚠️ 通用陷阱：**同一份数据在"写入"和"删除"两侧用了不同来源的 id**，
  而两者恰好长得很像 —— 只有把 diff 从头读一遍才会发现。
- **验证方式（无 Android SDK 时的诚实做法）**：沙箱跑不了真编译 ⇒
  **不假装能编译**，改写结构化交叉验证脚本（9 组：具名参数双向核对、
  `connector.xxx()` **调用点 ↔ 定义双向**核对、UiState 字段读写一致、行宽、括号配平…）。
  其中「调用点 ↔ 定义双向核对」这一条是**变异测试逼出来的**：
  最初只查了"定义存在"，把调用改成 `probeOneDriveTokenXYZ()` **没被咬出来**
  （定义那边照样好好躺着）⇒ 补成双向。后续三个变异（`issue`→`issueTypo`、
  调用名加后缀、`key` 的 import 包路径改错）**全部被咬出**。
  ⇒ 纪律（同 #104）：**新写的探针，先用变异测试证明它有牙齿**，
  否则"全绿"只是"什么都没查"。
  另：探针第一版还因正则贪婪匹配误报过（跨到了邻接组件），
  再次印证「**探针报了不可能的问题 = 探针坏了**」。
- **detekt 交叉验证的正确姿势**：项目 pin 的 2.0.0-alpha.6 不在 Maven Central，
  1.23.8 只认 1.x 属性名 ⇒ 写映射（`allowedLines`→`threshold`、
  `allowedFunctionParameters`→`functionThreshold`、
  `allowedFunctionsPerClass`→`thresholdInClasses`）**生成 1.x 等价配置**再跑，
  比"只跑默认规则"准得多。用它跑改动文件：**零违规**。
  ⚠️ 反例：拿**默认规则**跑会报一堆 `LongMethod`/`FunctionNaming`/`LongParameterList`，
  但项目配置其实是 `≤150 行` / `≤8 参数`，那些全是假警报 —— **别拿默认阈值吓自己**。

## 120. 「不猜状态」原则只修了一半：同一页 3 个开关用占位、7 个用裸 `Switch`（2026-09-26）

- **现象（代码层）**：设置页「防截屏」「动态取色」在冷启动后快速进入时会先显示占位、
  数据到了才出现；但「OLED 纯黑」「自动复制验证码」「临期复制下一个码」「自动填充保存提示」
  「严格匹配」「允许子域名匹配」「填充辅助」「卡片显示图标」**直接渲染一个开/关**。
- **根因（分两层，第二层才是关键）**：
  1. **UI 层**：后 7 处直接写 `Switch(checked = xxx)`，没走 `SettingsSwitch`。
  2. ⭐ **类型层**：ViewModel 里这些是 `StateFlow<Boolean>` + `initialValue = true/false` ——
     **类型上就禁止表达 `null`**。于是即使 UI 想不猜也拿不到"不知道"这个信息。
     ⇒ 这解释了为什么 #84 那次只修了 3 个开关：**其余 7 个不是"忘了改"，是"改不了"**，
     得先把类型放宽。
- **解法**：8 个流改 `StateFlow<Boolean?>` + `initialValue = null`；
  7 处裸 `Switch` 换 `SettingsSwitch`（含跨包复用的 `DisplayOptionsSheet`）。
  并在 ViewModel 加契约 KDoc：**新加开关初值一律 `null`**。
- **★ 最容易做错的一步**：`FillBehaviorSection(exactDomainOnly: Boolean, ...)` 这个中间层。
  只改 ViewModel 和 UI、漏掉它，调用点就必须写 `?: false` 把 `null` 压回确定答案 ——
  **问题没解决，只是从 UI 挪到了调用点**。改为 `Boolean?` 才算真通。
  ⚠️ 通用教训：**可空性要在整条链路上传递**，任何一层收窄都会让上游的努力白费。
- **附带修正（占位态不可点）**：原 `SettingsSwitch` 占位是一个纯 `Spacer`，**不可点**。
  数据没到的那几百毫秒里，用户手指已落在开关位置，点击被吞 ⇒ 用户感受是
  「这个开关按了没反应（有时）」。改为占位仍接收点击，语义固定为**「打开」**。
  - 为什么不是"取反"：`value == null` 时**根本没有"当前值"可反**，
    硬反只能拿上次会话的旧值猜，又把未定状态换成可能过期的确定值。
  - 为什么"打开"安全：本就开 → 幂等；本就关 → 正是用户意图。
    反方向的"关闭"才危险 —— 用户"从没见过它开，却把它关了"。
- **验证**：detekt 净改善（18→17，删 `passkeyCount` 消掉一个 `MagicNumber`）；
  另建契约片段复刻「可空流 → 收集 → section → SettingsSwitch」整链，
  变异（把 section 或组件参数改回非空）均立即报错。

## 121. ⭐ `checked = x is S.On` 把三态类型压成二值开关 —— **类型检查与 detekt 双双查不出**（2026-09-26）

- **现象（真机）**：快速解锁的指纹/PIN 开关处于「配了一半」状态时，
  用户看到的是一个**关着的开关**；点一下预期"打开"，**实际弹出了配置向导**。
  ⇒ 体感是「点了开关没打开，反而弹了个框」。
- **根因**：`CapabilityState` 是**三态**
  （`Off` 没启用 / `Partial(n)` 还差 n 个 / `On` 全部生效），
  而 UI 写的是 `Switch(checked = state.biometric is CapabilityState.On)` ——
  `is On` 把 `Off` 与 `Partial` **合并成同一个"关"**。
- **★ 为什么它能长期存活**：
  - `checked = x is On` 是**完全合法的 Kotlin**，类型检查不报；
  - 它不是 `when`，**穷尽性检查管不到**；
  - detekt 没有对应规则。
  ⇒ **这个 bug 在现有全部自动化手段下都是不可见的**，只在真机上、
  且只有当用户恰好处于 `Partial` 状态时才暴露。
  - 更讽刺的是：KDoc 里早就写清了"点 Partial = 继续配置，不是关闭" ——
    但**注释不是 UI，用户看不到**。
- **解法**：新增 `CapabilityToggle`，三态 → **两种控件**：
  `On`/`Off` ⇒ 真 `Switch`；`Partial` ⇒ 写着「继续」的 `TextButton`。
  - 为什么不用半开开关：M3 的 `Switch` 只有两态，自绘半开 knob 可读性与无障碍都更差；
  - 更根本的理由：`Partial` 的本质**压根不是"开关的位置"**，而是"一个还没做完的动作"。
    用动作词表达，控件形态与 `toggleBiometric()` 里 `Partial ⇒ showConfigure(...)`
    的实际行为一一对应 —— **界面自己会说话**，不需要靠注释解释。
- **★ 新增探针 `.ai/tools/check_state_flattening.py` 的两次自纠（值得单独记）**：
  1. **第一版只在同文件找 sealed 声明** ⇒ 扫那个 bug **报 0 处**。
     因为 `CapabilityState` 定义在 `QuickUnlockController.kt`、
     误用在 `QuickUnlockDialogs.kt`。⇒ 改为先建**全树**的"多态类型名"表。
  2. **第二版 7/7 自测全绿，扫真实代码仍然报 0 处。**
     根因：正则 `(?:is|==)\s*([A-Za-z_]\w*)\.([A-Za-z_]\w*)` 在
     `Outer.CapabilityState.On` 上把**倒数第二段**当成了类型名；
     而我的自测用例**全写短名** `Cap.On`，恰好能匹配。
     ⇒ **自测只证明了"探针能处理我编的简化输入"，不能证明它有用。**
     修正：正则跳过前缀段取最后一段；自测补**全限定名**正例 + 配对负例。
- **★ 探针有效的唯一证明方式**：把目标文件还原成 bug 版本 →
  全树扫描**精确报出那 2 行**（exit 1）→ 恢复修复版本 → 0 处（exit 0）。
  **只有这个闭环能证明探针有牙齿**；自测全绿不算（第二次自纠就是反例）。
- **⚠️ 探针的已知局限（写进 KDoc 了）**：只认"全部就绪"的约定名 `On`；
  `if (x is On) ... else ...` 里的 `checked` 会被报出（刻意偏严：宁可让作者写清 `when`）。

## 122. 快解锁的三态开关：「注释里写清了语义」不等于「界面表达出来了」（2026-09-26）

- 与 #121 同源，但**问题性质不同**，单列一条：
  `QuickUnlockDialogs` 的 KDoc 里有一段表格，明确写了
  「`Partial(n)` → 开关显示**关** → 副标题『有 n 个库未完成，点此继续』」，
  还有一句「点 `Partial` 的开关 = 继续把没配完的补上（**不是关闭**）」。
- ⇒ 作者**是知道**这个语义的，还专门写了注释。但用户看到的仍是"关着的开关"。
  **注释能防住"下一个人改错"，防不住"用户理解错"。**
- **教训**：当一个交互需要靠注释来解释"这个控件点下去不是你想的那个意思"时，
  **错的是控件，不是注释**。正确做法是换一个语义自明的形态（#121 的「继续」按钮），
  然后把那段解释性注释**删掉** —— 不再需要它了。
- **判据（可复用）**：写完一段"这里要注意：点它是 A 不是 B"的注释时，
  先问一句「**能不能让界面本身不用解释**」。能，就去改界面。

## 123. 设置行副标题不截断：长文案撑高整行，破坏"一组一行"的分组感（2026-09-26）

- **现象**：`setting_manual_fill_tile_desc` 有 60+ 字，在窄屏会把整行撑高，
  同一张卡片里各行高度参差，"一组一行"的分组观感被破坏。
- **解法**：`maxLines = 2` + `TextOverflow.Ellipsis`。
  - **为什么是 2 不是 1**：副标题的价值就是"说清后果"（见本文件 #128 那批文案），
    砍到 1 行会把刚补上的代价说明又截掉；
  - **为什么不能不限**：不限时长副标题会破坏分组感（就是本条的问题）。
- **附带**：删掉 `SettingsRow.showSubtitle` 参数 ——
  它自引入起**全项目无任何调用点传值**（默认 `true`，各行都走默认路径），是纯冗余 API。
  需要"整行不显示副标题"时传 `subtitle = null` 即可，**语义比布尔开关更直接**。
- **★ detekt `LongParameterList` 的阈值勘误（重要）**：
  项目多处注释（`FormValues.kt` / `TotpCodesScreen.kt`）写着"8 个刚好"——**这是错的**。
  `LongParameterList.functionThreshold = 8` 的语义是 **参数个数 ≥ 8 即报**，
  即**实际上限是 7 个**。
  ⇒ 删掉 `showSubtitle` 让本函数从 8 降到 7，顺带消掉一处**既存**违例。
  ⇒ 通用坑：**"阈值"这个词在 detekt 里是"触发点"不是"上限"**。
  验证方式：改完跑 detekt 确认该行消失（等路径比对以排除其它干扰项），
  再**把参数加回去**确认违例重新出现 —— 证明判断是真的，不是探针失效。
