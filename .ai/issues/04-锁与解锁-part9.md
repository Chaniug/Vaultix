## 268. 切库改为「跟随锁定」——#265 宽限期的最终形态（2026-11-10 晚）

### 用户原话（这一轮的全部动机）

> 你说的最有效的其实是不锁，怎么解决，有何优点。

上一轮我给他做的是「60 秒宽限期」。他的追问一针见血：宽限期只是把"慢"推迟了 60 秒，
并没有消除它 —— **只要用户在那个库停留超过 60 秒，切回去仍然要重付一次全流程**。

他选定的方案（原文）：

> 改成「跟随锁定」—— 切库不再锁；任一 KDBX 被锁则全部一起锁；
> 同时解锁上限默认 3 个，超了锁最久没用的那个。

### 判据：从「时间维度」换到「生命周期维度」

| 方案 | 一句话 | 失效方式 |
|---|---|---|
| 切库即锁（2026-11-04 起） | 进新库就锁旧的 | 每次切回都要重解 |
| 60 秒宽限期（当天上午） | 切走后 60 秒才锁 | **60 秒这个数字是猜的** |
| **跟随锁定（本篇）** | 只有"你锁它"才锁 | 明文份数由上限（3）兜住 |

宽限期的根本问题：它把约束押在一个**时间常数**上。常数取小了没用（用户看五分钟），
取大了等于不锁 —— 而任何取值都无法同时满足"我想快点切回去"和"我不想让明文留太久"，
因为这两件事**根本不是时间问题**，是**用户意图问题**。

> **判据：当一条策略需要引入一个"魔法数字"才能成立时，先问这个数字在替谁做决定。**
> 答案如果是"替用户的意图做决定"，那这条策略迟早要重写。

### 为什么"不锁"的代价比直觉小（这一节是全篇最重要的论证）

直觉上"多留一份整库明文"听起来很可怕。但本项目**已经**做了这件事：

`KdbxTransformKeyCache` 把 KDBX 的**派生密钥**（32 字节）常驻内存，并加密落盘，
且**刻意不随 `Kdbx.lock()` 清除**（#247 的决定：清了就等于"锁了再开又变 30 秒"）。

⇒ `Kdbx.lock()` 现在丢掉的**只是解析后的对象图**，不是密钥。
   真正的秘密（派生密钥）本来就一直在内存和磁盘上。

所以"多留一份对象图"的额外暴露面，远小于"整库明文常驻"这个说法给人的直觉。
而 `Kdbx.unlock` 的成本是**全额存在**的：

| 段 | 本地库 | OneDrive 库 |
|---|---|---|
| `read` 读整库 | 磁盘 IO | **stat 往返 + 整库下载** |
| `open` 的 KDF | 命中缓存 ≈ 0 | 同 |
| `open` 的解析 | kotpass 解密 + XML 解析 | 同 |

⇒ 省掉的是第一段和第三段。对网盘库，"切一次库 = 下一次文件"才是用户真正感受到的慢。

⚠️ 这段论证**不是**说"锁没意义"：锁依然是"用户要求立刻停止访问"的唯一表达方式，
而且它同时清掉视图状态、触发导航回根。它只是**不适合用来做日常切库的副作用**。

### 实现：`KdbxUnlockGroup`（替代 `KdbxGraceLocks`）

| 入口 | 行为 |
|---|---|
| `markKdbxActive(id)`（原 `lockOtherKdbxVaults`） | 记 LRU；超 3 个才驱逐最久未用的 |
| `lockVault(KDBX)` | **锁掉整个组**（`Kdbx.lockAll()` + `group.clear()`） |
| `lockAll` / 超时 | 锁全部（组清空） |
| `signOut` / `removeVault` | 只 `forget` 自己（"忘记这个库"不等于"锁一下"） |

三个必须守住的不变量：

1. **`note` 返回的驱逐名单必须被真正执行** —— 返回了不锁，上限就名存实亡，
   整个方案退化成"永不锁"。这是本类唯一的失败模式，也是它存在的唯一理由。
2. **先补记"没见过的库"，再记本次使用的库** —— 顺序反了，本次进入的库会被排成最旧，
   表现为"刚点进去就被挤掉、又提示要解锁"。
3. **与真源对齐**（`Kdbx.unlockedIds()`）—— 只信自己记的集合，会在库被别处锁掉后
   继续占名额，导致上限提前触发（明明只开 2 个，第 3 个却被挤掉）。

### ⚠️ 与 D1「锁单库不影响其它库」的冲突，以及它为什么不是冲突

D1（2026-09-29）写的是：锁单库改为写**每库**「用户主动锁」标记，不再删全局信封，
理由是"用一次单库动作去删全局信封，会掐掉其它库的冷启动恢复能力"。

本轮 `lockVault(KDBX)` 会锁掉**整组的内存会话** —— 字面上违反了 D1。但它**不动**
`markUserLocked` 标记，所以：

- 锁了 A，B 的内存会话没了（切过去要重新解锁）✔ 这是本方案的**预期**；
- 锁了 A，B 的**冷启动恢复信封**还在（下次冷启动仍能被自动恢复）✔ D1 的原始目的没被破坏。

⇒ D1 保的是"信封"，本方案改的是"内存会话"。**两者是不同的东西**，
已在该行代码注释里写死，避免下次有人拿 D1 来"修"它。

### 测试

`KdbxUnlockGroupTest`，**10 条**（纯 JUnit，无协程）：

- 未超上限不驱逐 / 超了驱逐最久未用 / **刚用过的不会被自己驱逐** /
  访问刷新顺序（反复用 a 时挤掉 b）/ 一次超两个按序驱逐 /
  **真源里已锁掉的不占名额** / **没见过的会被补记且排在本次之前** /
  forget / clear / 默认上限是 3。

最后一条是"常数守卫"：调大 `DEFAULT_MAX_UNLOCKED` 等于放宽 `#60` 的份数约束，
必须是一次有意识的改动，不能顺手改。

### 副作用（如实记账）

- 接口 `lockOtherKdbxVaults` → `markKdbxActive`（语义从"锁"变成"记账"，
  名字不改会长期误导后来者）；
- `flushPendingKdbxLocks` 删除：没有排期，就没有"提前执行"；
- `AutoLockController.onStop` 的 flush 调用一并删除（并回退其两条单测）；
- `KdbxGraceLocks` 与其 13 条测试删除 —— **不是被放弃，是被取代**，
  历史在 [`04-锁与解锁-part7.md`](./04-锁与解锁-part7.md) 与 part8。

## 269. 恢复「熄屏/清后台回来自动弹指纹」——#245 的结论是过拟合（2026-11-10 晚）

### 用户原话

> 设置里面的锁与安全，里面的指纹解锁和应用内 PIN 解锁是否都是完善的，
> 尤其是指纹解锁的时机和机制是否都是目前 bitwarden 那种同款的优秀机制。

逐项核对后（见本轮汇报的对照表），**唯一一处**与 Bitwarden 不同：熄屏/清后台回来后
Bitwarden 直接弹指纹，Vaultix 要用户点一下。用户选择「恢复自动弹（Bitwarden 同款）」。

### #245 当时为什么这么改，现在为什么不算数

2026-11-04 真机反馈："锁屏回来弹不出指纹，就在那里转"。当时的结论是
「自动门禁不要抢在用户前面弹，让他自己按主按钮」。

但**转圈的真正原因是 `prewarmCipher` 还不存在** —— 要走完三步：
`localUnlockAvailable` 首帧 → 现备一次 Keystore 往返 → 等 Activity RESUMED。
三件事串起来才有那段空白。当时的修法把**症状**（抢跑导致转圈）当成了**原因**。

现在三件事都解决了（`UnlockViewModel.prewarmCipher` 预暖 + `withResumed` 门禁），
「不弹」就只剩下代价：用户从口袋掏出手机 → 看到一页"验证身份" → 还得点一下。

> **判据：为绕开一个 bug 而加的抑制逻辑，必须写下"它绕的是什么"。**
> 否则那个 bug 修好之后，抑制逻辑会以"这是经过真机验证的决定"的名义永远留下。

### 改动只有一行判据

```kotlin
// 之前
val eligible = ((viewLocked && !viewLockAuto) || localUnlockAvailable) && …
// 现在
val eligible = (viewLocked || localUnlockAvailable) && …
```

安全性**没有任何变化**：

- 自动门禁打的是**查看锁**（密钥从没被它保护过）；
- 用户取消认证时 `clearAutoViewLockIfAny` 仍会放行回主界面 —— 那是 #245 的另一半，
  与本改动不冲突，也不该跟着回退。

⚠️ 被删掉的 `viewLockAuto` 参数只服务于这条抑制逻辑；`UnlockViewModel` 里的
`UiState.viewLockAuto` **仍然存在且必须保留** —— `clearAutoViewLockIfAny` 靠它区分
"自动门禁"与"用户手动锁"，后者取消时**不能**放行。

### 测试

本轮**没有**新增 `AutoPromptQuickUnlock` 的测试：它是 `@Composable`，
验证需要 Compose UI 测试（项目目前没有 instrumentation 用例）。
⇒ 这条改动靠**真机验收**（冷启动 / 熄屏 / 清后台三种场景各看一次是否直接弹）。

如实记账：这是一处**测试盲区**，不是"已经覆盖"。
