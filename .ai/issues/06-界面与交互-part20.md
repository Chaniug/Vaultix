## 282. 第五批界面 / 设置 / 条目 UI 整改（2026-11-12，用户反馈）

### 用户原话

> 1. 通常模式下和液态玻璃下，底栏的外框有点很小的边线出来的，很小很小的，感觉世界效果不太好，液态玻璃开关打开后的透明效果还是不够。
> 2. 另外 kdbx 的小云图标和 bitwarden 的云同步的图标不一样，不是带对勾的云图标。
> 3. 新建条目页面的剪影卡片的颜色偏单调，能稍微多加一两个色系的配色吗，更活泼一点。
> 4. 设置里面的，设置 PIN 页面，继续按钮和另外的按钮有点错位不平衡。自动锁定设置里面的文案过于啰嗦，可以精简优化。剪切板自动清除设置里面，取消按钮没有边框效果。
> 5. 条目显示里面，按域名显示之类的分组还不错，但是 UI 之类的可以稍微做的好看一点吗。密码条目界面的每一条密码条目的 UI 都能做的好看一点吗，参考一下 material3 的设计风格，在不增加太多性能开销的情况下，提升条目的质感，在外观和字体字号，显示效果，条目上的同步，验证码，通行密钥之类的小点缀上下点功夫，让条目看起来更好看一点。

五组反馈、九个落点。**全部改了生产代码**，不是解释也不是只调文案。施工前复核了三处
「用户最新反馈 vs 既有判据」冲突（见下文「三处判据反转」），并明确：**最新反馈优先，
但语义层不跟着形状 / 文案一起合并**。

### 第 1 组：底栏细边线 + 液态玻璃通透度（`ui/glass/`）

**根因**：`LiquidGlass.drawGlass` 末尾原第 ⑧ 层，两档材质**共有一圈**沿 Outline 的
`style.stroke` 1dp 细描边（`InnerStrokeWidth = 1.dp`）。用户说的「很小很小的外框边线」
就是它。它当初的职责是「与背后内容分界」，但 #281 已补了 3dp 内阴影与镜面 rim ——
两者都是**有厚度的受光 / 暗部**，比一条细线更像玻璃，那圈线反而把边界读成「描了一圈框」。

**「透明效果还是不够」不回退 #281**。#281 刚把填充从 0.38 / 0.52 回提到 0.50 / 0.62
来治「薄」，若再一路调淡就是来回摇摆。本轮采用**中心更透、边缘更立**：

| 量 | #281 | #282 | 作用 |
|---|---|---|---|
| Liquid 填充（light / dark） | 0.50 / 0.62 | **0.44 / 0.56** | 中心更透 |
| `INNER_CLARITY_ALPHA` | 0.10 | **0.13** | 中心提亮，避免「透 = 灰」 |
| `INNER_VIGNETTE_ALPHA` | 0.09 | **0.06** | 下沿渐晕减弱 |
| `SHADER_CLARITY` | 0.055 | **0.075** | AGSL 中心通透 |
| 模糊（Liquid / Frosted） | 24 / 30 dp | **不变** | 保住 #281 的「玻璃自身」 |
| 整圈 1dp `style.stroke` | 两档共有 | **真模糊两档删除** | 去细边线 |

- 边界改由 ③ 内阴影 + ⑥ 镜面 rim + 阴影立住；降级实色档（API < 31、无真模糊）
  **仍保留**那圈「`if (!blurAvailable) { … return }` 之前」的描边给不透明板收边。
- AGSL shader 内的 `uLine` 沿轮廓暗线**没动**：它属于 shader 内的边缘厚度、只在
  33+ 液态玻璃档，且 AGSL 运行时编译 CI 覆盖不到，改它收益小于风险。
- `LiquidGlassTest` 的填充下界 `0.45 → 0.42`（#281 的 0.45 是**调参留痕**，不是架构底线），
  但 `LiquidBlurRadius ≥ 20`、`SPECULAR_ALPHA ≥ 0.55`、磨砂比液态更雾等边缘厚度判据一个不动。
- 新增 `LiquidGlassDockRulesTest` **规则 11**：取 `drawGlass` 函数体，降级档 `return`
  之后不得再出现 `style.stroke`。谁把细线加回真模糊路径，立刻红。

### 第 2 组：KDBX 云图标与 Bitwarden 统一（`ui/common/CloudSyncIcon.kt`）

**冲突**：#266 刻意用「裸云 = 地点 / 云+对勾 = 状态」区分语义，KDoc 与
`CloudSyncBadgeTest` 都写着「KDBX 是整文件同步，条目级没有『这一条上了云』」。
真机上两朵不同的云并排出现时，用户读到的是「这个不一样 / 是不是没同步」，
而不是设计者想表达的语义差。

**处理：形状统一，语义不合并**。`VaultSourceCloudIcon()` 改用 `Icons.Filled.CloudDone`，
与 Bitwarden「已同步」同形同色（`onSurfaceVariant` 弱化）；删掉 `Cloud` import。
三条底线**一个没动**，由 `CloudSyncBadgeTest` 钉住：

1. **本地 KDBX 仍不画云** —— 判据始终是 `VaultSummary.origin`；
2. KDBX **不产出条目级同步态** —— `CLOUD_VAULT` / `SYNCED` / `PENDING` 仍是三个枚举值、
   两套数据源、三条读屏文案（`sync_state_cloud_vault` / `sync_state_synced` / `sync_state_pending`）；
3. 「待上传 / 失败」仍由库级 `DetailSyncIndicator` / `SyncBadge` 用 `CloudOff` + error 承担。

旧 KDoc「裸云 = 地点，云+对勾 = 状态」「刻意不画对勾」**即日作废**，历史理由留在 part14，
不要在别处再引用；`.ai/README.md` 的 #266 形状层判据同步反转（语义层保留）。

### 第 3 组：新建条目剪影卡片配色（`ui/shell/AddActionSheet.kt`）

单调有三层叠加原因：① 5 个类型只用到 `primary / secondary / tertiary` 三个 accent，
且 Login = Identity = primary、SecureNote = SshKey = secondary；② 卡底
`tint.copy(alpha = 0.45f)` 被洗淡；③ 内层 `ItemFieldGlyph` 再盖一层
`surface.copy(alpha = 0.78f)`；④ `GlyphNote` 完全用灰线，没有 accent。

`GlyphPalette` 从「accent / tint」两色扩为「**accent / tint / wash**」三色，五种类型在
「卡底 / 剪影底 / 重点形状」上交叉铺开（如 Login = primary / primaryContainer /
secondaryContainer），卡底 alpha `0.45 → 0.68`、内层小卡改 `palette.wash 0.62`、
`GlyphNote` 首行短色块用 accent。**全部继续走 `colorScheme`**：不硬编码品牌色、
不新增 vector、不破坏动态取色。

### 第 4 组：设置页三处（`ui/settings/` + 对话框门禁）

- **PIN 按钮错位**：`DialogActions` 是 `FlowRow`，自带
  `Arrangement.spacedBy(Spacing.sm, Alignment.End)`；`QuickUnlockDialogs.kt` 的 4 个
  `DialogActions` 块里又手写了 5 处 `Spacer(Modifier.width(Spacing.sm))` ⇒
  「spacedBy + Spacer + spacedBy」双份间距，且 Spacer 作为独立 item **参与换行**，
  于是「继续」与「返回」被推得不齐。删掉 5 处 Spacer，间距只由 FlowRow 管。
- **自动锁定文案**：`auto_lock_never_warning` / `auto_lock_on_system_lock_note`
  精简为更短提示，保留关键风险（离开 App 不锁、别人能打开 / 自动填充）与失效场景
  （未设锁屏密码时该档不生效）。**只改内容、不增删字符串资源**，避免孤儿门禁额外风险。
- **剪切板「取消」无边框**：主题 / 剪贴板 / 自动锁定三个「即选即存」的单选项对话框
  统一改用 `DialogOutlinedActionButton`。这与 #275 定的规则 1（单动作对话框退出按钮
  **不许**用 Outlined 强调）直接冲突 ⇒ **反转门禁**：规则 1 改为「单选项对话框的退出按钮
  **必须有边框**」，判据是 `confirmButton` + 无 `dismissButton` + 块内含 `SingleChoiceRow(`
  + 文案为 `action_(close|cancel|done)`。用 Python 复现括号配平后精确圈住 3 个块
  （`SettingsComponents.kt:718`、`SettingsScreen.kt:1286/1347`），全部合规、
  `LongTextInfoDialog` 未被误圈。`DialogActionButtons.kt` 的 KDoc 同步反转留痕。

⚠️ 删除 Spacer 时踩了一次：用 `replace_all` 把 `\n    Spacer(...)` 连前导换行一起吃掉，
导致 5 处相邻 composable 挤在同一行（`)                DialogBackButton(...)`）。
已用 Grep 精确定位逐处恢复换行，并静态确认「同行两语句残留 = 0」。

### 第 5 组：条目列表 M3 质感（`ui/items/ItemsScreen.kt`）

用户点名「外观 / 字体字号 / 显示效果 / 同步 / 验证码 / 通行密钥小点缀」，并明确
**不增加太多性能开销**。取舍是：全部改动落在**绘制与布局阶段**，零新增 State、
零动画、零新增 composable 层级（除副标题把 `Text` 换成已有的 `TypeBadge`）。

| 位置 | 改法 | 为什么 |
|---|---|---|
| `GroupHeader` | 整条铺 `surfaceContainerLow` 低档容器底；计数收进 `tertiaryContainer` 小胶囊；标题 `weight(1f)` 把数字推到行尾；标题色 `primary → onSurface`，箭头保留 `primary` | 此前是透明 Row + 满屏主色小字，与下面有描边的 `EntryCard` 之间没有层次，读成「列表里混进一行正文」 |
| `ItemRowSubtitle` | 两处用户名 `Text` 补 `maxLines = 1` + `TextOverflow.Ellipsis`；非 Login 类型从 `primary` 纯文字改 `TypeBadge(..., BadgeTone.NEUTRAL)` | 长用户名会把卡片撑成两行（一屏条目数跟着变）；**详情页 `ItemDetailScreen:519` 本来就用同一个 `TypeBadge` + NEUTRAL**，列表对齐它不是新花样，是消除 8.4 的「同规格两页长得不一样」 |
| `ItemRow` 标题 | 补 `maxLines = 1` + `Ellipsis` + 统一行高 `EntryCardTitleLineHeight` | ⚠️ **本轮唯一的「显示行为变更」**：密码页长标题原先折行，而 TOTP / 卡包 / 通行密钥三个列表共用的 `EntryCard` 早已单行，密码页是唯一例外。不是「顺手改行为」，是把漏掉的一处**补齐**；要恢复折行必须四页一起改 |
| `ItemRowTrailing` | 四枚行尾图标（云 / 收藏 / TOTP / passkey）**整组装进一个** `surfaceContainerHigh` 胶囊；靠新增纯函数 `hasRowTrailing()` 早退，没有点缀时完全不画容器 | 一个 `Modifier.background` = 一次绘制；四枚圆点各包一层既吵、又违背 `CapabilityIcon` 的克制结论。图标语义色一个不动 |

硬边界（全部守住）：

- **不改字号、不加粗字重**（`TypeBadge` 用 `labelSmall`，比原 `bodySmall` 还轻一档）；
  项目 8.8 §5 明确不采纳更大的 display 字号 / 更重的字重；
- **不换 `ListItem`、不引入每行重组 / 每帧动画 / 渐变阴影**；`GroupHeader` 的箭头旋转
  是既有动画，且分组头数量远少于条目数，不构成「每行开销」，保留；
- **不动共享组件**：`CapabilityIcon` 同时被 `ItemDetailScreen` 调用，`CloudSyncIcon` /
  `VaultSourceCloudIcon` 被详情页与库列表调用 —— 只在列表这一层包容器；
- **不动 `SiteIcon` 缓存链**、**不动 `EntryCard` 的 0.5dp 描边**、**不动 `ItemsGrouping.kt`**
  的 #278 显示层分组逻辑、**不动 `cloudSyncBadgeOrNull`** 的三态判据。

新增 `app/src/test/java/io/vaultix/vaultix/ui/items/ItemsRowStyleTest.kt` **5 条可机检规范**
（扫 `ItemsScreen.kt` 源码，与 `LiquidGlassDockRulesTest` 同一套 `stripComments` /
`functionBody` 写法）：① 副标题恒定一行且类型徽标与详情页一致、不许改字号字重；
② 行尾整组只有一个底 + 无点缀早退 + 三个共享组件不许被替换 + 不许出现每行开销；
③ 分组头成块 + 计数 tonal 胶囊 + 读屏展开态不丢；④ 美化不改显示偏好与点缀判据；
⑤ **标题恒定一行**（把上面那条唯一的行为变更单独钉住，防止有人只把密码页删回去、
让四页规格重新分叉）。
云状态三态 / 分组逻辑的运行时行为仍由 `CloudSyncBadgeTest` / `ItemsGroupingSiteTest` 钉，
本文件不重复，避免两处规则漂移。

⚠️ 第 5 条是收尾复核时补的：规则 1 的 KDoc 原本写「标题**早就** `maxLines = 1`」，
但生产代码 KDoc 明写「这里**新增**了 `maxLines = 1`，是一次行为变更」—— **同一事实两处
互相矛盾**。已订正 KDoc 并补门禁。教训：写「早就如此 / 一直如此」这类断言前先回源码看一眼，
美化轮次里夹带的行为变更最容易在文档里被抹平成「本来就这样」。

### 三处判据反转（**本轮最重要的留痕**）

| # | 旧判据 | #282 起 | 为什么 |
|---|---|---|---|
| 1 | #266：裸云 = 地点、云+对勾 = 状态（形状层也分开） | 形状统一为 `CloudDone`；**语义层不合并**，本地 KDBX 仍不画云、KDBX 仍不产出条目级同步态 | 最新用户反馈优先；两朵不同的云并排被读成「是不是没同步」 |

> 继续绿，也不是把旧结论留在 KDoc 里当现行判据（后者最危险：下一个 AI 会照着错的写）。
> 历史理由留在原分篇，不在别处再引用。
