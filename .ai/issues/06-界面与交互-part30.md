## 302. ⋮ 菜单两段主次 + 状态灯五态五色（2026-11-17，用户连续两轮反馈）

### 用户原话与选择

1. 看到 #301 三块卡片截图后追问：

2. 听完 A/B/C 三案后拍板：

   > 用方案A吧。然后不同颜色的状态灯，你有什么好点子优化的吗

3. 在「理想档（颜色+形状+动效）/ 务实档（推荐）/ 只换一处色」里选择：

⇒ 本轮不是推翻 #301，而是**在 #301 的 Popup + 分组骨架上重排主次**；
`DropdownMenuPopup`、16dp 圆角、8dp 间隙、1dp `outlineVariant` 描边、280dp 固定宽、
intrinsic-safe 中间省略**全部保留**。

### 改前：三张等权白卡为什么还是不够好

#301 已经比「一整块 + 两条线」好很多，但用户仍然觉得可以更精致。问题不再是老套，而是：

| 问题 | 具体表现 |
|---|---|
| **堆** | 三个 `MenuGroup` 视觉权重完全相同，像三张同样的卡片摞在一起 |
| **碎** | 身份 / 导航 / 同步锁定各占一张卡，动作区内又被切成两张卡的信息量 |
| **没主次** | 「我在哪」是背景信息，「去别处」是主操作，「同步/锁定」是次操作，却等量呈现 |

> 判据：**「好看」的第二层不是形态统一，而是权重分配**。第一层（#301）解决
> "和项目语言不一致"；第二层（本轮）解决"三样东西一样响"。

### 方案 A：身份带 + 动作区

给过三个方案：

| 方案 | 做法 | 结论 |
|---|---|---|
| **A（采纳）** | 段 1 身份带用 `surfaceContainerHigh` 淡底，段 2 动作区用默认菜单白卡；动作区内用 `HorizontalDivider` 子分区 | **主次靠底色，不靠再加一张卡** |
| B | 三卡各自加「密码库 / 前往 / 同步」语义标签 | 把 #301 刚删掉的「前往」灰字又请回来，退步 |
| C | 底部 `ModalBottomSheet` | 改动面太大，且失去"贴着 ⋮ 展开"的空间关系 |

落地结构：

```text
DropdownMenuPopup
 ├─ MenuGroup(tinted = true)        ← 身份带：surfaceContainerHigh 淡底
 │    └─ MenuVaultHeader            ← 徽标 / 库名 / 条目数 / 来源 / 状态灯+文案
 ├─ MenuGroupGap()                  ← 8dp 真实间隙
 └─ MenuGroup()                     ← 动作区：默认白卡
      ├─ MenuNavItems               ← 切换库 / 验证码 / 回收站 / 文件夹
      ├─ HorizontalDivider          ← 1dp 子分区（不是第二张卡）
      └─ MenuSyncLockRow            ← 同步 / 锁定，状态灯已去重
```

#### 取证：`DropdownMenuGroup.containerColor` 可直接用

为了不为了淡底自绘一层 `Surface`（会重写 hover / 涟漪 / 无障碍语义），
下载并解压 `material3-1.5.0-alpha16-sources.jar` 核对了签名：

```kotlin
fun DropdownMenuGroup(
    shapes: MenuGroupShapes,
    modifier: Modifier = Modifier,
    containerColor: Color = MenuDefaults.groupStandardContainerColor,
    ...
)
```

⇒ `MenuGroup` 加一个 `tinted: Boolean` 开关即可：

```kotlin
containerColor = if (tinted) {
    MaterialTheme.colorScheme.surfaceContainerHigh
} else {
    MenuDefaults.groupStandardContainerColor
}
```

这也是门禁要钉 `tinted = true` 的原因：**淡底不是"随便换个颜色"，是身份带与动作区的主次契约**。

### 状态灯：为什么务实档不选理想档

#### 改前的编码问题

| 状态 | 改前颜色 | 问题 |
|---|---|---|
| `FAILED` | `colorScheme.error` | 合理 |
| `SUCCESS` | `#2E7D32` 绿 | 合理 |
| `SYNCING` | `#B26A00` 琥珀 | — |
| `UPLOADING` | **同为 `#B26A00`** | 4 色表达 5 态，"正在拉"和"正在推"分不出 |
| `CONFLICT` | **`colorScheme.primary` 品牌蓝** | 蓝色在本项目 = 可点 / 品牌，冲突是要人拍板，语义相反 |

理想档是「颜色 + 形状 + 动效」（冲突加感叹号、上传加旋转），但 6dp 的小圆点放不下形状差异，
动效又会引入新 State 与重组 —— 与 #282「只在绘制 / 布局阶段动、零新增 State」的取舍冲突。
用户选的务实档因此只做**颜色拆开**：

```kotlin
private val SyncDotSyncing   = Color(0xFFB26A00) // 琥珀：正在跑一次同步
private val SyncDotSuccess   = Color(0xFF2E7D32) // 绿：已对齐
private val SyncDotUploading = Color(0xFF1565C0) // 蓝：后台在传本地改动
private val SyncDotConflict  = Color(0xFFC2410C) // 警示橙：要人拍板

fun syncStatusDotColor(dot: SyncStatusDot): Color = when (dot) {
    SyncStatusDot.FAILED    -> MaterialTheme.colorScheme.error
    SyncStatusDot.SYNCING   -> SyncDotSyncing
    SyncStatusDot.UPLOADING -> SyncDotUploading
    SyncStatusDot.CONFLICT  -> SyncDotConflict
    SyncStatusDot.SUCCESS   -> SyncDotSuccess
}
```

⚠️ 只改 `syncStatusDotColor`，**刻意不改** `syncBadgeColor` / `syncLineToneOf`：
状态点、⋮ 角标、文字行在原项目里是刻意独立的三套配色（角标与菜单点共用色函数，
文字行按语气分档），顺手统一会破坏既有语义与门禁。

### 状态去重：一个差一点就造成功能回退的坑

原 `MenuVaultHeader` 把状态灯写在 `card.syncLine?.let { ... }` 分支里，而 **Bitwarden 库的
`syncLine` 恒为 `null`、`syncDot` 有值**。如果只删 `MenuSyncLockRow` 的状态灯、不拆
`MenuVaultHeader`，Bitwarden 库会变成**完全没有状态灯**——不是简化，是功能回退。

修法是把点和行各自独立判断：

```kotlin
val dot = card.syncDot
val lineRes = card.syncLine
if (dot != null || lineRes != null) {
    Row(verticalAlignment = Alignment.CenterVertically) {
        if (dot != null) {
            Icon(
                imageVector = Icons.Filled.Circle,
                contentDescription = syncStatusDotDescription(dot),
                tint = syncStatusDotColor(dot),
                modifier = Modifier.size(SYNC_LINE_DOT_SIZE),
            )
            if (lineRes != null) Spacer(Modifier.width(Spacing.xs))
        }
        if (lineRes != null) {
            Text(text = stringResource(lineRes), maxLines = 1, ...)
        }
    }
}
```

`MenuSyncLockRow` 里的状态点、读屏描述、`syncDot` 引用全部删除，只剩同步 / 锁定两个动作。

> 判据：**"去重"前先问被删的那份是不是唯一渲染路径**。本轮差点把 Bitwarden 的状态灯删没。

### 门禁：从 #301 的 7 条升级到 12 条

`app/src/test/java/io/vaultix/vaultix/ui/items/ItemsMoreMenuGroupingTest.kt` 整文件重写：

| # | 断言 | 防的回退 |
|---|---|---|
| 1 | `DropdownMenuPopup`，不得出现 `DropdownMenu(` | 两段被整块底糊回去 |
| 2 | 正好 2 个 `MenuGroup` + 三个功能入口都在 | 退回三段或漏功能 |
| 3 | 正好 1 个 `MenuGroupGap()` | 间隙丢失 |
| 4 | `MenuGroup` 带 `outlineVariant` 描边 | 浅色下淡底与卡片底糊成一片 |
| 5 | 固定 `MENU_PANEL_WIDTH` | 切库宽度跳变 |
| 6 | `MenuDefaults.itemShape(index, count)` | 组内首/尾圆角漏一处 |
| 7 | 四个入口 + 两个动作一个不少 | "顺手删功能" |
| 8 | `tinted: Boolean` + `surfaceContainerHigh` + 身份带传 `tinted = true` | 主次靠底色这条契约被抹掉 |
| 9 | 动作区内有 `HorizontalDivider` | 退回第二张卡 |
| 10 | 状态灯只画一次（身份带有、动作区无、读屏描述在） | 状态重复 / Bitwarden 无灯 |
| 11 | 五色分支齐全 + `UPLOADING != SYNCING` + `CONFLICT != primary` + 四个常量两两不同 | 退回 4 色表达 5 态 |
| 12 | 菜单内禁止 subcompose；正向钉住 intrinsic-safe 变体 | #301.1 真机闪退复发 |

两个实现细节值得记：

- `bodyOf()` **按花括号配平**截函数体，否则下一段 KDoc 会被算进来；
- 状态灯配色在 common 层是 `@Composable public fun`，`bodyOf()` 要同时认 `private fun` 与 `fun`；
- 测试文件里不能出现字面量 `Icons.Filled.Circle`，否则 `check_compile_smells.py` 会把测试
  自己当成"漏 import 的图标引用"；用 `"Icons.Filled." + "Circle"` 拼出来。
