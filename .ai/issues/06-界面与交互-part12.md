## 259. 「同一张卡里装着两种东西」与「主标识长成了待填字段」（2026-11-09，真机两张截图定案）

> 两条反馈表面上无关（详情页展示 / 表单输入），根因是同一类：
> **同一个容器 / 同一个控件承担了两种语义**，于是读者要靠文字内容去猜。

### ① 关联应用混在「网址」卡里，还带复制按钮

**现象**（用户原话）：「如果关联了应用，那么这个应用在密码条目页中的展示，为什么会有一个
能复制的按钮，另外，展示的时候，关联的应用好像是和网址放在同一区域显示，容易看错吧。」

**根因**：Bitwarden 用 `androidapp://<包名>` 表示"这个条目绑定某个 App"，它和普通网址
一样存在 `item.uris` 里。于是同一张卡、同一条「网址」标题下，既有
`https://xui.ptlogin2.qq.com/…` 又有 `com.tencent.mobileqq`，中间只隔一条分隔线。
两者的区别**只有一行的 label 而已（12sp 小标签"应用"）**，扫视时根本抓不住。

| 问题 | 修法 |
|---|---|
| 两类东西共用一张卡 / 一条标题 | 拆成「网址」与「关联应用」两个分区，各自判空 |
| 应用行有复制按钮 | **去掉** —— 没人需要把包名粘到别处 |
| 应用行形态与网址行几乎一样 | 换 `ListItem`：包名 headline + 状态 supporting + 打开按钮 |

**★ 判据（可直接用于 review）**：
> **复制按钮是给"要拿去用"的值准备的**（用户名 / 密码 / 网址能粘到登录框、浏览器），
> **不是给"标识"准备的**。包名的唯一可用动作是"打开它所属的 App"。
> 问一句「用户复制完这个值能粘到哪？」答不出来就不该有复制按钮。

⚠️ **未安装的应用仍保留整行**，只把按钮去掉、副标题改成「本机未安装该应用」。
隐藏它会让"自动填充为什么没生效"变成谜 —— 用户需要知道"绑了，只是没装"。

⚠️ **不能再在调用处用 `item.uris.isNotEmpty()` 当闸门**：只含应用的条目会渲染出一张
空网址卡。两个分区各自内部判空。

### ② 名称区「太简陋」+ 标题到内容 40dp

**现象**：「这个填写名称是否太简陋啊。另外新建条目的标题与下方内容区块好像也存在了一定的
空隙留白。」

**「简陋」的根因不是缺装饰，是两种语义互相拆台**：上一轮（#258 之后）给名称用了 M3 的
无框 `TextField`，想借下划线表达"可编辑"。但下划线在 M3 里**同时是"未完成的表单字段"
的标准像**，而 `headlineSmall` 想说的是"这是标题"。一个元素同时说两件事 ⇒ 读起来就是
"简陋 / 没做完"。

⇒ 明确主张：**它是标题**。

| 改动 | 理由 |
|---|---|
| 去下划线，改 `BasicTextField` | 下划线是表单字段的语法，标题不需要 |
| 字段名独立成行 `labelLarge` + `primary` | 与表单其它字段名同档字号，靠**颜色**标出"这是主标识" |
| 空值显示「未命名条目」占位 | **空标题也有话说** —— 这是"简陋"的另一半来源 |
| 光标 `SolidColor(primary)` | 没有框和下划线时，聚焦仍需反馈 |
| 星标 `Top` 对齐 | 长标题换行时不会"飘"到中间 |

**间距的量化**（截图实测，不是感觉）：

| 来源 | 高度 |
|---|---|
| 壳的 `CONTENT_BAR_GAP`（栏 → 正文） | 16dp |
| `TextField` 自身容器留白 + 基线 | ~24dp |
| **合计（用户看到的）** | **40dp** |
| 表单里**卡片 ↔ 卡片** | **24dp** |

⇒ **阶梯倒挂**：标题离正文比正文自己内部还远，读者看到的是"标题与内容无关、
卡片之间才是一伙的"。

修法：顶部呼吸位 `16 → 8dp`（栏 → 身份区 ≈ 32dp，与"页大标题 ↔ 第一段内容"的
量级相符），**底部保持 16dp** —— 那里没有元素自身留白叠加，16dp 就是真实值。

**★ 判据**：
> **量"两个元素之间的间距"时，必须量到可见元素的边界，不能只量容器 padding。**
> 组件自身的容器留白（`TextField`、`Card` 的 `contentPadding`）会**叠加**在
> 你写的那条间距上。本项目已因"只看 padding 不看实际占位"翻过两次
> （2026-09-20 的栏高、这次的标题留白）。

## 261. 「返回就取消」被三次拦住：判脏基线取错 / 空段被当成改动 / 新建被当成编辑（2026-11-10，真机截图）

- **现象**：新建**银行卡**条目，什么都不填，直接按返回 → 弹「放弃这次修改？填写的内容还没有保存」。
  新建**登录**条目同样操作 → 直接关掉，没有任何提示。
- **根因（三层，从下往上）**：
  1. **`buildSnapshot` 对 Card / Identity / SshKey 无条件构造对象**（`base.copy(card = buildCard(...))`）。
     新建时 `initial.card == null`，快照里却是 `VaultCard("","","","","","")` ⇒
     `snapshot() != initial` **恒为真**。Login / SecureNote 没有"子对象"这一层，
     所以同一份判据在它们身上恰好不误报 —— 这就是"只有银行卡会弹"的全部原因。
  2. **判脏基线取成了 `initial`**，而表单初始化会做**补全**（空的卡/身份/SSH 段、
     由公钥推导的 SSH 指纹）。补全结果不在 `initial` 里 ⇒ 任何补全都算"用户改动"。
  3. **新建与编辑共用同一道闸门**。新建时没有"已保存的内容"可保护，
     用户点返回的语义本来就是"不要了"。
- **解法**：
  - 基线改成**「打开这一份表单时的首帧快照」**（`remember(initial) { snapshot() }`）。
    这一改同时免疫第 1、2 层 —— 任何初始化补全都自动被算进基线，
    将来新增的推导（比如又给某个类型加默认值）也不需要再改判据。
  - 闸门只对**编辑**生效：`isDirty = { initial.id.isNotBlank() && snapshot() != baseline }`。
  - 顺手删掉两行**解释功能**的副标题（新建面板）：
    「当前页面的默认新建动作」与「只生成并复制，不创建条目」。
- **为什么不全砍**：编辑态误关丢的是**库里已有的数据**，那正是这道闸门存在的理由。
  用户原话也是「新建的时候返回并不会提示，这个也不要提示」——
  他要的是**新建直通**，不是取消整个保护。

### 一并做的版式调整（删字之后必须跟着改）

删掉副标题会留下"卡片还在，但内容只剩一行"的悬空感。高度因此按**内容重算**，
而不是保留旧值：

| 卡 | 改前 | 改后 | 依据 |
|---|---|---|---|
| 主卡（primary 面） | 76dp（图标 + 标题 + 副标题） | **72dp** | 图标 40 + `Spacing.lg` ×2 |
| 生成器卡 | 84dp（剪影 + 标题 + 副标题） | **72dp** | 剪影 20 + `Spacing.sm` + `labelLarge` 行高 20 + `Spacing.md` ×2 |
| 类型网格卡 | 104dp | 104dp（不动） | 画的是"整张条目长什么样"，需要高度 |

⇒ 一屏只剩**两档高度**：通栏动作卡 72 / 类型网格卡 104。
主卡与生成器卡首尾同高，中间四格成组 —— 层级靠**位置与高度**说，不靠文字解释。

**★ 判据**：
> **"有没有改动"不能拿"当前快照 vs 原始入参"来判，要拿"当前快照 vs 打开时快照"。**
> 表单初始化一旦做过任何补全/推导，前一种判法就把补全算成用户行为 ——
> 用户什么都没做却被问"要放弃修改吗"，比不提示更糟：它会让人以为自己误触了什么。

> ⚠️ 另有一条同类误报一并关掉：编辑一个**缺 SSH 指纹**的条目，指纹在初始化时被推导补上，
> 一开一关也弹确认。基线改动同样覆盖它，不需要为它单独写判据。

## 262. 新建本地 KDBX：文件名恒为固定值，与用户填写的库名无关（2026-11-10，真机反馈）

**现象**：新建本地库时填了库名 `unit`，落盘的文件却始终叫 `vaultix.kdbx`。
用户原话：

> 库名一直都是 vaultix.kdbx 保存在本地，我填写的这个是打开 vaultix 才看得到的名称，
> 这样合适吗？就比如我在本地建了好几个 kdbx，结果全是 vaultix.kdbx，也不好找啊。

**根因**（一行）：

```kotlin
// AddKdbxScreen.kt（改前）
createTargetPicker.launch(DEFAULT_KDBX_FILE_NAME)   // private const = "vault.kdbx"
```

`state.vaultName` 只被用作 `createVault(displayName = ...)`（写进 KDBX 根组名），
**从未参与文件名**。系统面板拿到的是一个与用户输入无关的常量。

### 这不只是"名字不好看"，是三件事

| 后果 | 具体表现 |
|---|---|
| **无法从文件名分辨** | 建 3 个库 = 磁盘上 3 个同名文件，只有打开后才知道谁是谁 |
| **同目录自动改名** | `CreateDocument` 遇重名会加 `(1)` ⇒ `vaultix(1).kdbx`、`(2)`… 越建越糊 |
| **直接被拒** | 撞上**非空**同名文件时被 `SafCreatePolicy` 拦下（判据是"有字节"），用户拿到"该位置已存在同名文件"——而他只是想新建 |

⇒ 第三条尤其反直觉：**上一轮刚修好"空文件不算冲突"**，
但如果每次新建都叫同一个名字，第二次撞上的就是**有内容**的那个，照样失败。

### 修法

`KdbxFileName.kt` 新增纯函数 `suggestedKdbxFileName(vaultName)`，Screen 改为：

```kotlin
createTargetPicker.launch(suggestedKdbxFileName(viewModel.state.value.vaultName))
```

清洗规则（按**最严的 Windows/OneDrive** 取交集，否则会出现"本地建得出、传 OneDrive 就失败"）：

| 步骤 | 规则 | 例 |
|---|---|---|
| ① | `trim()`（含 U+3000 全角空格） | `"  unit  "` → `unit` |
| ② | 去掉用户自带的 `.kdbx`（忽略大小写） | `MyVault.KDBX` → `MyVault` |
| ③ | `\ / : * ? " < > \|` 与控制字符 → `_` | `我的/库` → `我的_库` |
| ④ | 去末尾的**空格与点**（Windows 会静默去掉，导致"面板名 ≠ 落盘名"） | `unit . .` → `unit` |
| ⑤ | 截断到 64 **码点** | 见下 |
| ⑥ | 空则兜底 `vaultix.kdbx` | `.kdbx` → 兜底 |

> **★ 判据**：文件名是用户在**文件管理器里**看到的第二身份。
> 凡是由用户命名的东西，落盘名必须跟着它走 —— 否则"命名"这个动作在库外没有任何效果。

### 两个实现坑（都是单测抓到的，不是想出来的）

**1）"防呆守卫"反而制造了 bug**

初版给去后缀加了守卫 `name.length > KDBX_SUFFIX.length`，
想的是"别把 `.kdbx` 去掉后变空串"。结果 `.kdbx`（长度 5）不满足 `5 > 5`
⇒ 后缀原样留下 ⇒ 拼成 **`.kdbx.kdbx`**，还是个隐藏文件。
去守卫、让它变空串、交给兜底，才对。

⇒ 常见模式：**为了防一个边界而加的守卫，会把那个边界变成另一个更隐蔽的错误**。
这里兜底逻辑本来就是为"空"准备的，不需要第二道防线。

**2）截断必须按码点，不能按 `Char`**

`String.take(n)` 数的是 UTF-16 码元。emoji 是代理对（2 个 `Char` / 1 个码点），
`take()` 可能切在中间 ⇒ 产出**孤立代理**，落盘后变 `?`。
用 `offsetByCodePoints` 切在字符边界上。测试里用 `🔐` × 100 钉住。

### 文案同步

`add_kdbx_create_name_helper` 从

> 这个名称会同时作为根组名写进文件，在 KeePassXC / KeePassDX 里显示的也是它。

改为

> 这个名称会**同时用作文件名**和文件内的根组名，在 KeePassXC / KeePassDX 里显示的也是它。

理由：用户之所以觉得"这样不合适"，部分原因是**没有任何地方告诉过他文件名会用它**。
文案先说清，面板里看到的名字才不会像"系统自己起的"。

（面板里的文件名输入框可编辑，想改成别的名字仍然可以 —— 这里只改预填值。）

### 单测

`KdbxFileNameTest`，18 条：主路径 / 后缀不重复 / 九类非法字符 / 首尾空白（含全角）/
末尾点 / 四种空态兜底 / 超长截断 / emoji 不切半 / 恰好等于上限。

## 263. 本地 KDBX 的条目行尾也挂着「已同步」云图标 —— 三条正确代码串成一句假话（2026-11-10，真机反馈）

**现象**：本地 KDBX 库、从未上传过任何云端，条目行尾却有实心云 + 对勾。
用户原话：

> 本地 kdbx，没有上传云端。怎么条目显示上也有小云图标。这样不对。本地和云端应该有所区别。

### 根因：三段各自正确的代码

| # | 位置 | 单独看 | 串起来 |
|---|---|---|---|
| 1 | `ItemRepositoryImpl.observeSyncStates` | KDBX ⇒ `flowOf(emptyMap())` **正确**（文件即存储，没有云端这一层） | 空 map |
| 2 | `ItemsScreen` 读侧 | `syncStates[id] ?: true` **对 Bitwarden 正确**（新建未入队不闪） | 空 map 查不到 ⇒ 每条都 `true` |
| 3 | `ItemRowTrailing` | `CloudSyncIcon(synced = synced)` 无条件画 | 画出一朵「已同步」 |

⇒ 三处都对，结果是在**一个根本没有云端的库**上显示"已同步"。

⚠️ `CloudSyncIcon` 自己的 KDoc 第 47 行早就写着：

> ⚠️ KDBX 库调用方**不要**渲染本组件：KDBX 的文件即存储，没有「云端」这一层，
> 画出来是在编造一个不存在的状态。

**契约写在了被调用方，而违反契约的是调用方** —— 这类保护等于没有。
（`TotpCodesScreen` 反过来是对的：它写的是 `if (!synced) CloudSyncIcon(false)`，
只在"待推送"时才画，KDBX 恒 true 自然不画。）

### 为什么这条比"少画一个图标"严重

**显示「已同步」比显示「未同步」更糟**：用户会据此认为**已经备份好了**。
这正是 `.ai` 里反复出现的「静默欺骗」——界面在陈述一件没发生过的事。

### 修法：`null` 与 `true` 必须分开表达

```kotlin
internal fun cloudSyncBadgeOrNull(vaultKind: VaultKind?, syncedInVault: Boolean?): Boolean? =
    if (vaultKind == VaultKind.BITWARDEN) syncedInVault ?: true else null
```

行尾改成 `synced?.let { CloudSyncIcon(synced = it) }`，
`ItemRow` / `ItemsList` 的参数类型从 `Boolean` 收窄为 `Boolean?`。

| 库类型 | 条目在 `syncStates` 里 | 返回 | 行尾 |
|---|---|---|---|
| KDBX（本地 / 网盘都是） | 永远查不到（空 map） | `null` | **不画** |
| Bitwarden | `false`（待推送） | `false` | 云加斜杠（error 色） |
| Bitwarden | `true` / 查不到（刚建未入队） | `true` | 实心云（弱化色） |
| 未知（`vaultKind == null`） | — | `null` | 不画 |

**★ 判据**：
> **「没有这回事」必须有一个独立的值，不能借用「一切正常」。**
>
> `true` = 有云、且是最新；`null` = 没有云这个概念。两者在 UI 上都是"不报警"，
> 但一个是**确认过**，一个是**不适用**。合并成一个布尔，KDBX 就必然被画上云。

### KDBX 网盘库为什么不画

KDBX 是**整文件**同步，"某一条上云了"这个概念不存在（`observeSyncStates` 对 KDBX
网盘库同样返回空 map，这是刻意的）。库级状态由详情页的 `DetailSyncIndicator` 表达，
条目级云图标在这里一律是假的。

### 类型收窄是这次修复真正的保险

`synced: Boolean` → `synced: Boolean?` **不是**为了少写一个 `if`：
它把"这个库没有云"变成**类型上无法忽略**的事实。今后再往 `ItemRow` 里加调用方，
传 `true` 就得先解释"为什么这个库有云端" —— 编译器会替我们问这一句。

### 单测

`CloudSyncBadgeTest`，6 条。其中一条是**穷举**：

```kotlin
for (kind in VaultKind.entries) { ... 除 BITWARDEN 外必须全是 null ... }
```

新增 `VaultKind` 时它会立刻红，逼后来者先想清楚"这个库有没有云端"。
