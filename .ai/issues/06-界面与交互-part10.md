## 216. ⭐ 图标"每次打开都重新加载、滑动时从空白长出来" —— 三个根因，其中一个是**尺寸算错**（2026-11-01）

**现象**（用户原话）：「密码条目显示里面，条目图标……每次打开都是重新加载的吧，我在滑动的时候，
发现有一些图标是从空白再加载出来的，每次都这样，是否会浪费性能。」并追加要求：
「我要提升性能与美观度。」

**第一步先否掉错误假设**：不是"在下载"，也不是"缓存不够大"。

| 量 | 值 |
|---|---|
| Coil 内存缓存默认上限 | `memoryClass` 的 **20%**（低内存机 15%）≈ 51MB |
| 一张 40dp 图标（3x 屏 120px） | ≈ 56KB |
| 整库几百条合计 | 几 MB |

差两个数量级 ⇒ **容量不是成因**。继续往源码里找，剩下三个真问题：

### 216.1 尺寸从源头就算错（这是「不美观」的根）

```kotlin
private const val ICON_REQUEST_PX = 96     // ← 死写的**像素**值
```

96px 等于假设屏幕密度恒为 2x。而实际使用点是：

| 位置 | dp | 3x 屏实际需要 | 96px 的结果 |
|---|---|---|---|
| 列表卡片 `EntryCardIconSize` | 40.dp | 120px | **放 1.25 倍** |
| 详情页 `DETAIL_HEADER_ICON` | 56.dp | 168px | **放 1.75 倍** |

⇒ 高密度机上图标一律发虚。这不是"不够清晰"，是**解码尺寸从一开始就小于绘制尺寸**。

修法：`with(LocalDensity.current) { size.roundToPx() }`。
⚠️ Coil 2.7 的 `ImageRequest.Builder.size(...)` **没有 Dp 重载**（只有 `Int` / `(Int,Int)` /
`Dimension` / `Size` / `SizeResolver`）—— 必须自己换算，这点在源码里核对过，不是猜的。

### 216.2 卡片重建后第一帧**必然**是空的

`LazyColumn` 里滑出可见区的卡片会被**销毁**，滑回来时重建 composable。
而 `AsyncImage` 无论如何都要先过一次协程调度（`RealImageLoader.execute` 走
`Dispatchers.Main.immediate`）⇒ 重建后的第一帧没有任何内容。60Hz 下 16.7ms，
肉眼正好能捕捉到"白圈闪一下"。再叠上旧代码的 `crossfade`，观感就是**从空白长出来**。

修法：在**组合期同步**查 `ImageLoader.memoryCache`（O(1) LRU 查找）。命中就直接
`BitmapPainter` 绘制 —— 不构造 `ImageRequest`、不启协程、不查磁盘，整条
`RealImageLoader.execute` 都跳过。这是"根治"，而不是"把动画调短掩盖它"。

### 216.3 ⚠️ 显式 `memoryCacheKey` 会**吞掉尺寸**（改 216.2 时踩出来的坑）

为了让同步查缓存能算出一致的键，很自然会写 `.memoryCacheKey(...)`。但 Coil 源码里：

```kotlin
// MemoryCacheService.newCacheKey()
request.memoryCacheKey?.let { return it }      // ← 快路径：直接返回，不再追加 extras
```

而 Coil 默认键是 `MemoryCache.Key(base, extras)`，**尺寸就在 `extras` 里**。
显式给键 ⇒ `extras` 空 ⇒ 40dp 与 56dp 的图标**共用一条缓存**。

后果不是"糊"，而是更隐蔽的**来回重解码**：`isCacheValueValid` 发现尺寸不符 → 判无效 →
重新解码 → 覆盖同一个键 → 下次换个尺寸再判无效……每进一次详情页白跑一轮。
**不崩、不报错、不打日志**，只有一句"图标好像总是在加载"。

修法：`internal fun siteIconCacheKey(url, px) = "site-icon:$px:$url"` —— 尺寸进键，
两种尺寸各存一条，双方都走"精确匹配"的最快路径。抽成纯函数 + 6 例单测钉住
（`SiteIconCacheKeyTest`），因为这个 bug 真机看一天也定位不到，只能靠断言。

> **判据**：**凡是显式覆盖框架给你算好的键/哈希，必须先把"它原本算了什么"列出来，
> 然后把那些维度自己补回去。** 少一维不一定崩，但一定会让缓存静默失效。

### 216.4 失败被永久化

旧 `onError = { failed = true }` 一路带到卡片被回收：一次 DNS 抖动就让某个条目
在本次浏览里**永远**停在首字母（除非用户把它滑出去再滑回来）。

修法：记**失败时刻**（`mutableLongStateOf`，既是状态又是 `LaunchedEffect` 的 key），
30s 后清标志 + 递增 `retries` ⇒ `ImageRequest` 的 `remember` key 变化 ⇒ 重新加载，最多 1 次。
1 次足够覆盖网络抖动 / DNS 超时；再多就是拿用户的电换运气。

### 216.5 观感：任何时刻都不是空白

改成"首字母始终在底层，图标成功后再盖上去"：加载中 / 失败 / 待重试三种状态
**画同一件事**（首字母），且与"根本没有域名可拼 URL"的 `FallbackAvatar` 共用
`FallbackInitial` —— 否则同一个条目会因"有域名但没取到"和"没域名"显示成两种大小。

### 216.6 全局 `respectCacheHeaders(false)`（冷启动重下的最后一环）

`respectCacheHeaders` 是 **loader 级**开关（`ImageRequest` 上有 per-request 版本，
但默认行为由 loader 决定）。Coil 默认 `true` ⇒ 服务端回什么 `Cache-Control` 就照办。
图标端点 `<base>/icons/<host>/icon.png` 一旦返回 `no-cache` / `max-age=0`
（反代与 CDN 的默认行为并不统一），**磁盘缓存完全不写** ⇒ 冷启动 内存空 + 磁盘空 ⇒
一屏图标全部重新联网。

修法：`VaultixApplication : ImageLoaderFactory`，`newImageLoader()` 里关掉它。
代价只有"站点换了 favicon 可能仍是旧图，直到 LRU 淘汰"—— 远小于每次启动重下几十张。

⚠️ 磁盘缓存目录必须保持 Coil 默认的 `cacheDir/image_cache`：`AutofillItemIcon`
**直接按 URL 读这个目录**做填充建议的图标，换目录等于把它废掉。

### 216.7 顺带修两个长期误报的静态门禁

不修的话"门禁红"会变成噪音，真正的错误被淹没。

| 工具 | 误报原因 | 修法 |
|---|---|---|
| `check_import_packages.py` | `material.icons.filled.Image`（图标）与 `foundation.Image`（组件）同名 ⇒ 图标被算进"组件包票数" ⇒ 合法 import 被判违规 | 把 `androidx.compose.material.icons.*` **整体**排除在约定包统计外 + 补反向自测 |
| `check_ui_hardcoded_text.py` | 跨行 `Log.w(...)` 的中文文案在第四行、关键字在第一行 ⇒ 被判"界面硬编码文案"。**这条自 2026-10-30 起一直红着** | 改为按"逻辑行"判断（先合并括号未闭合的续行）+ 补 2 例自测（7/7 PASS） |

> ⚠️ **为什么"一直红着"没人发现**：上一轮跑检查用的是
> `python3 check.py ... | tail -4; exit=$?` —— `$?` 取到的是 **`tail` 的退出码**，
> 永远是 0。**判据：任何被管道接过的命令，退出码都要单独取**，或者干脆不用管道
> （`> /tmp/o.txt 2>&1; code=$?`）。

### 216.8 验收

- 列表上下滑动：滑回来的卡片**第一帧就有图标**，不再有白圈闪烁；
- 3x / 4x 密度机上图标**边缘清晰**（不再被放大绘制）；
- 断网进入：一屏都是首字母（不是白圈），恢复网络后 30s 内自动补上；
- 清后台重进、断网启动：图标仍从磁盘缓存出（离线可见）；
- 自动填充建议列表的图标不受影响（`cacheDir/image_cache` 未变）。

## 217. 🔴 CI 连红 7 次：三个独立问题首尾相接，中间夹着"诊断器自己坏了"（2026-11-01）

#216 的改动推送后，CI **连续红 7 次**（#332–#338）才走到 #339 全绿。
值得单独立条，因为**每一次报错看起来都像下一次的原因**。

### 217.1 三个真问题

| # | 问题 | 伪装成什么 |
|---|---|---|
| A | `assertThat(key).doesNotStartWith("http")` —— Truth 的 `StringSubject` **没有这个方法**（只有 `doesNotContain` / `doesNotContainMatch` / `doesNotMatch`） | **编译期**错误，报在 `compileFullDebugUnitTestKotlin`；CI 顶层只说「exit code 1」，看着像测试挂了 |
| B | `SIGNING_KEY_PASSWORD` 与 `SIGNING_STORE_PASSWORD` 不一致 | 解码步骤用 `keytool -list` 验，**只验 store 密码** ⇒ 打「校验通过」；真失败在 `packageFullDebug` |
| C | `Summarize failed unit tests`（纯读 XML 做汇总）自己 exit 1 | 把「915 例 0 失败」报成了 CI 红 |

### 217.2 「0 失败」与「exit 1」为什么能并存

`assembleFullDebug` 只编译 **main**；`testFullDebugUnitTest` 还要编译 **`src/test`**。
后者编译失败 ⇒ **一个测试都没跑** ⇒ 但 `test-results/` 里有**上一轮遗留的 XML** ⇒
汇总步骤照常数出「915 例、0 失败」。

> **判据：汇总结论不能反证"这一步成功"。**
> "0 失败"只说明"我数到的那些没失败"，不说明"该跑的跑了"。

### 217.3 为什么前四次只能靠猜

| 想要的信息 | 路径 | 结果 |
|---|---|---|
| 编译错误原文 | step 内的 `/tmp/build_log.txt` | step 结束即随 runner 消失 |
| job 完整日志 | `GET /actions/jobs/{id}/logs` | **403**（需 admin） |
| 单测 XML | artifact | **401**（需认证） |

三条路全堵。⇒ **凡是"失败后才知道需要"的信息，必须由 workflow 自己打到 annotation 上。**
新增 `Summarize build errors`（`if: always()`）后，第一次运行就吐出了真因。

### 217.4 ⚠️ 两个"第一版又错了"的地方

1. **`grep` 关键词表漏了 `^e: `** —— 只找了 `OutOfMemoryError`/`crashed`/`FAILED`，
   于是 #338 只能看到 `Task ... FAILED` 看不到具体那行 Kotlin 错误，又白跑一轮。
   > **grep 的关键词表本身就是一种判据，漏一个 = 再猜一次。**
2. **`Build gate diagnostics::build_failed=false`** 名不副实：它只反映它自己那次
   `gradlew` 的退出码，而失败发生在别处。看到这个 `false` **不能**推断"编译没问题"。

### 217.5 判据汇总

1. **诊断步骤的职责是提供信息，不是下判决** —— 它一旦能失败，就会把"真正的失败"
   替换成"诊断器自己坏了"（#336/#337 就是这样）；
2. **`cmd | tee log; exit=$?` 取到的是 tee 的退出码**，必须用 `PIPESTATUS[0]`；
3. **校验要覆盖下一步真正用到的每一个凭据** —— `keytool -list` 能解 store ≠ 能签 APK；
4. **用没见过的 API 前先查文档** —— `doesNotContain` 存在不代表 `doesNotStartWith` 存在，
   名字对称的东西在 Truth 里并不对称。

### 217.6 结果（#339）

| 项 | 值 |
|---|---|
| 步骤 | 21 个，**全部 success** |
| 单测 | **1428 例，失败 0 例**（`gradlew 退出码 = 0`） |
| 产物 | `debug-apk` 34 MB + 预览包 `app-full-debug.apk` 35.8 MB |
| 遗留 | ⚠️ `SIGNING_KEY_PASSWORD` 与 store 密码不一致 ⇒ 本次包用一次性密钥签名，**盖不上旧包** |
