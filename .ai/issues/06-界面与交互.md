## 20. Quick Settings 磁贴「加了不显示 / 空白」（2026-09-09）

- **现象**：声明了 TileService，但快捷设置里找不到，或加进去是空白方块
- **根因**：① 只实现 `onClick`，没有 `onStartListening`（系统拿不到 label/icon/state，
  国产 ROM 尤其明显）；② 没调 `requestListeningState`，系统不保证回调 onClick
- **另注**：磁贴**必须由用户手动添加**，系统没有给应用「开关磁贴」的 API——
  设置页只能做「引导添加」（API 33+ `StatusBarManager.requestAddTileService`），不是开关
- **解法**：`onTileAdded` / `onStartListening` 里写 `tile.label/icon/state` + `updateTile()`，
  并 `requestListeningState(this, ComponentName(this, X::class.java))`

## 21. Android 11+ 查不全已安装应用（「关联应用」列表很短）（2026-09-09）

- **现象**：`queryIntentActivities(ACTION_MAIN + CATEGORY_LAUNCHER)` 只返回很少几个 App
- **根因**：**包可见性限制**（API 30+）——不在「自动可见」白名单的查询需要 `<queries>` 声明
- **解法**：Manifest 加 `<queries><intent><action MAIN/><category LAUNCHER/></intent></queries>`，
  **不要**申请 `QUERY_ALL_PACKAGES`（应用商店审核风险）

## 31. 设置页与 Bastion 的信息架构差距（本轮修复，2026-09-10，be8a5bf）

对 Bastion `AutofillSettingsV2Screen`(1149 行) / `PasskeySettingsScreen`(666 行) /
`SettingsScreen`(1925 行) 逐项比对后补齐：

- **没有状态卡**：用户分不清「没启用」和「启用了但填不出来」→ 新增三态卡
  （未启用 errorContainer / 需注意 tertiaryContainer / 正常 primaryContainer）。
  「需注意」= 密码能填但通行密钥没开（Chromium 半残状态，最常见）。
- **`AutofillStatusChecker` 的两步判定**：`AutofillManager.hasEnabledAutofillServices()`
  只回答「系统有没有启用任何服务」，选的是谁分不出来 → 必须再读
  `Settings.Secure:autofill_service` 按自身类名子串匹配。
  **读不到值（部分 ROM 对第三方 App 隐藏）时按「已启用」处理**——第一步已确认有服务，
  把「读不到」报成「未启用」会误导用户反复去系统设置确认。
- **没有通行密钥入口**：设置页看不到「我到底存了几个通行密钥」，排查 Edge 通行密钥
  问题全靠猜 → 新增分组显示「已解锁库中：N 个」。显示 0 即定位到同步/解析问题。
  口径必须写清「已解锁库中」：锁定库密文读不出来，硬统计得 0 会误导成「没存过」。
- **填充行为无开关**：`MatchConfig` 的两个域匹配参数此前是硬编码默认值 → 提升为用户
  开关（严格匹配 / 允许子域名匹配），在 `VaultixAutofillService.buildResponse` 生效。
  **必须是真开关**：装饰性开关比没有开关更糟。
- **`credential_provider.xml` 的 `settingsSubtitle` 误用标题文案**
  （`@string/setting_credential_provider` = 「凭据提供商（通行密钥）」），
  新增 `setting_credential_provider_subtitle` 专用副标题。

### 明确**不**对齐 Bastion 的三项（有意为之）

1. Bastion CP 文案写「通行密钥**和密码**设置」——与其 `credential_provider_config.xml`
   里「CP 不处理密码」的注释自相矛盾。Vaultix 保持「凭据提供商（通行密钥）」。
2. Bastion 用 `Intent("android.settings.CREDENTIAL_PROVIDER_SETTINGS")` 跳系统设置，
   Vaultix 用 `CredentialManager.createSettingsPendingIntent()`（能直达自家 provider
   的启用开关），不下沉为通用 `ACTION_SETTINGS`。
3. 不搬 Bastion 的「黑名单 / 屏蔽字段 / 智能标题 / 通知时长 / 密码建议 / 影子校验 /
   校验诊断」——Vaultix 无对应能力，搬过来只会是点不动的假开关。
   同理不搬 `PasskeySettingsScreen` 的影子校验/严格校验开关。

## 38. 搜索框「乱跳」——三处顶栏写法不一致（2026-09-11，P1，`a3093e4`）

**现象**：用户反馈「一直在输入框，搜索框乱跳」。

**根因**：三个带搜索的界面**各写各的**，且都不符合 Bitwarden 做法：

| 屏幕 | 旧写法 | 为何会跳 |
| --- | --- | --- |
| `ItemsScreen` | `OutlinedTextField` 挂在 `LargeTopAppBar` **外层** `Column` | 大标题栏滚动变高 → 输入框被反复垫高（最严重） |
| `PasskeysScreen` | 输入框塞进 `LargeTopAppBar.title` | 大标题栏自身可变高度 → 展开/收起时抖 |
| `TotpCodesScreen` | 同上（清除按钮语义还写成「取消」） | 同上 |

**修法（照抄 Bitwarden `BitwardenSearchTopAppBar`）**：

- 新增 `ui/common/SearchTopAppBar.kt`（`VaultixSearchTopAppBar`）：固定高度 `TopAppBar`
  （**绝不用 `LargeTopAppBar`**）+ 搜索态输入框整体占据 `title` 槽 +
  `FocusRequester`/`LaunchedEffect` 主动聚焦 + `ImeAction.Done` + 清除按钮动画。
- 三个屏幕统一 `if (searchActive) 搜索顶栏 else 普通顶栏`（**整体替换，不叠加**）。
- `searchActive` 由 `remember` 改 `rememberSaveable`。
- 删除三个屏幕各自的旧 `SearchField` 与失效 import。

**验证**：Compose API 桩 + kotlin-compiler-embeddable 真实编译新组件 → 0 error；
API 参数名逐字对齐 Bastion；四文件无超 120 字符行（UTF-16 语义）；无未使用 import。

### 教训

同一功能在项目里出现 **3 种不同写法**，是最危险的信号之一 —— 说明没有统一封装。
**优先建一个复用组件、三处统一，再谈“修 bug”**；否则今天修好一处，另两处还在跳。

## 56. 「整行点击 = 复制」与「按住后滑动删除」的手势冲突（2026-09-12，第四十四轮）

**需求（用户原话）**：「验证码界面的点击复制验证码到剪切板的，按住验证码条目，滑动删除」；
密码条目同样要「按住后滑动删除」。

**冲突点**：卡片内层已有 `EntryCard` 的 `clickable`（点击 = 打开详情 / 复制验证码），
删除手势若也用普通拖动，会在松手时**同时**触发点击（变成「删掉又打开详情」）。

**解法**（`ui/common/PressAndSwipeToDelete.kt`）：
1. 用 `detectDragGesturesAfterLongPress` —— **只有长按之后**的拖动才算删除手势，
   与点击互不干扰（点击仍在长按超时前完成）；
2. 拖动事件 `change.consume()` —— 内层 clickable 见到已消费的 move 会放弃这次点击；
3. 只允许向左拖（`minOf(amount.x, 0f)`），红色删除底随位移渐显，未过阈值回弹、过阈值滑出后回调；
4. 删除一律走**软删除**（`ItemRepository.softDeleteItem`，进回收站可恢复），并在列表给一句提示。

**为什么不做普通左滑删除**：密码条目一滑就没，误触代价太高（列表滚动/单手/口袋误碰）。
上游 Bastion 的删除也是「先长按/选择、再动手」的两步语义。

⚠️ 副作用：验证码行点击改成「复制」后**编辑入口必须显式补一个**（否则条目改不了）——
已在行内加「编辑」按钮；密码列表则仍由点击进详情编辑。

## 57. 沉浸式顶栏：必须「浮在内容之上」才成立（2026-09-12，第四十四轮）

**用户要求**：「滑动就左上角的字放大缩小的效果、状态栏沉浸、右上角按钮沉浸」。

**规格**（`ui/common/ExpressiveTopBar.kt`，移植 Bastion `ExpressiveTopBar`）：
标题 32sp→16sp、栏高 72dp→48dp、上下内边距 8dp→4dp、内容下移 8dp→0dp、
**收起后栏背景 alpha→0**、动作胶囊 48dp→40dp + 整组缩放 0.85、内容色向 `onSurfaceVariant` 过渡。
收起判定是**快照式**（首个可见项偏移 > 8dp → 1，否则 0），内部 200ms 补间，
判定值用 `derivedStateOf`（避免每帧重组）。

**三个必须同时满足的条件（缺一个就退化成「顶栏变短了但内容还是被压着」）**：
1. 顶栏必须画在**内容之上**（`Box { 列表; 顶栏 }`），**不能**放 `Scaffold(topBar = …)`
   —— Scaffold 会把内容整体压到顶栏下方，「内容从半透明栏下穿过」就不存在了；
2. 列表顶部留白取 `rememberImmersiveBarPadding(collapse)` = 状态栏内边距 + 当当前栏高
   （随收起动画变短），这样展开时首条不被挡、收起后内容滑到栏下；
3. 外层壳（`AdaptiveMainScaffold` 的 `Scaffold`）必须 `contentWindowInsets = 0`
   —— 否则外层已把内容压到状态栏下方，顶栏再加一次 `statusBarsPadding` 就是双份留白。

搜索态例外：搜索输入框不能塞进会折叠的大标题里，故搜索态仍走固定高度的
`VaultixSearchTopAppBar`（并恢复默认 `contentWindowInsets`）。

## 58. 验证码页「统一进度条」与详情页「去动态验证码」（2026-09-12，第四十四轮）

**① 统一进度条**（`ui/totp/UnifiedProgressBar.kt`，移植 Bastion `UnifiedProgressBar`）：
整页**一条**倒计时（取最快翻转那条条目的周期），进度 = 本周期已过/周期，
剩余 ≤5s 切 `error` 色，右侧固定「Ns」，其后是可选的**尾部插槽**——
「通行密钥」入口就挂在这里（对齐 Bastion，空列表时独立成行兜底，
否则用户在空态下失去进入通行密钥页的路径）。
**行内进度条全部删除**：每行每秒重绘一条进度条是纯浪费，统一到顶部一条即可（用户要求降功耗）。

**② 详情页去动态验证码**：`ItemDetailScreen` 此前每秒重算验证码 + 重绘进度条（页面开着就一直跑），
现改为**只提示**「该条目含有验证码 / 已绑定 N 个通行密钥」，并注明去「验证码」页查看。
⚠️ 点击行 = 复制之后，验证码页的编辑入口必须显式保留（见 #56）。

**③ 2FA 第二步页面完全不响应**：`AutofillFillTargetPolicy.isOtpOnly` →
`VaultixAutofillService.buildResponse` 直接 `return null`。验证码在上一步填账号密码时就已进剪贴板，
这一页既不该列条目、也不该弹「没有匹配的密码」（对齐上游 `Unfillable → onSuccess(null)`）。

## 62. 点库名展开的筛选条必须「浮在内容之上」（2026-09-12，第四十八轮）

**用户要求**：「点左上角库名展开/收起分类筛选」。

**坑**：把筛选条塞进可滚动的 `Column`（列表上方）会让它**随列表滚走**，
而顶栏的箭头还指着「已展开」——用户会以为筛选条坏了。
这与 #57（沉浸式顶栏必须浮在内容之上）是**同一类问题的第二次出现**。

**解法**：筛选条与顶栏同层（`Box` 的另一个子节点），
`topPadding = rememberImmersiveBarPadding(collapse)` 让它正好压在顶栏下方；
另铺一层 `matchParentSize()` 的透明遮罩（点面板外即收起，免去找关闭按钮）。

**另一个刻意的决定：筛选状态不持久化。** 落盘会让用户下次打开 App 对着一个空列表发呆
（条目都在，只是被上次的筛选挡着），而收起状态下那排 chip 是看不见的 ——
这就是「条目莫名其妙不见了」类投诉的来源。`rememberSaveable` 只保证切 Tab 回来仍在。

**还有一处**：有筛选时标题必须拼成「库名 · 筛选名」。
只显示库名的话，用户看到条数明显变少会以为数据丢了。

## 67. 顶部 / 底部「让位」写在外层容器 padding 上 ⇒ 三个症状同一个根因（2026-09-13）

**现象**（用户一次报三个）：① 筛选 chip 行压在第一条条目上；② 顶栏与底栏「不沉浸」
（滚动时两片区域都不是透明的）；③ 搜索态出现巨大黑色横幅，且返回手势**直接退回桌面**。

**根因**
- ①③ 与 ②的顶栏部分：内容顶部让位一律写成
  `Column(modifier = Modifier.padding(top = barPadding))`（密码 / 验证码 / 卡包 / 设置
  **四个 Tab 全是这个写法**）。后果三条：列表视口被整体下压 ⇒ 内容永远画不到顶栏区域，
  「收起后顶栏透明、内容从下方穿过」不成立；不感知筛选行高度 ⇒ chip 压住首条；
  搜索态 `Scaffold` 已按 `contentWindowInsets` 让过位，外层再叠一次 ⇒ **双重留白** = 黑横幅。
- ②的底栏部分：底栏走 `Scaffold(bottomBar = ...)`，内容被让出底栏高度 ⇒
  胶囊周围那圈留白只能露出纯背景，与内容割裂。
- ③的返回：搜索态**没有 `BackHandler`**，而主界面是**根路由**
  （`popUpTo(0) { inclusive = true }`，栈里没有上一层）⇒ 系统返回直接结束 Activity。

**解法**：顶部让位一律改到 **`LazyColumn.contentPadding`**（列表）或
**可滚动的 `Spacer`**（`verticalScroll` 页面），可随动画变化、可叠加，搜索态归零；
底栏改**叠层悬浮**（`Box { content(); Box(align = BottomCenter) { bottomBar() } }`），
各页用 `bottomInset`（`rememberBottomDockInset` = 胶囊 86dp + 系统手势条）自己留位；
搜索态加 `BackHandler`。

**判据**：**「让位」必须做在滚动内容里，不能做在滚动容器外。**
做在外面，内容就永远到不了那片区域 —— 无论顶栏的 alpha 是 0 还是 1。

## 68. 手势有实现但**无可感知反馈** ⇒ 功能等于不存在（2026-09-13）

**现象**：用户要求「按住密码条目 / 验证码条目，然后从右往左滑删除，**分组密码也要**」——
而该手势**三个列表早就接了**（含分组路径：分组只多插一个分组头，行 composable 是同一个）。

**根因**：长按「上膛」后唯一的反馈是 `ARMED_SCALE = 0.02f`（2% 缩放），
红色删除底只在 `offsetX < 0` 之后才显影 ⇒ 用户按住时画面几乎没有变化，
**根本不知道自己已经解锁了这个手势**。参考实现 Bastion 有显式的 armed 态：
`SwipeArmState.arm()` + 静态露出 `hintAlpha = 0.32f` 的红底。

**解法**：armed 用 `animateFloatAsState` 平滑成 0→1；红底显隐取
`max(滑动进度, 0.32 × armedProgress)`；并让内容在 armed 时**额外左移 16dp** ——
删除底被不透明的卡片完全盖住，只调 alpha 是看不见的，必须挤出一条缝。

**判据**：**「功能存在」与「用户知道功能存在」是两件事。**
手势、快捷键这类隐藏交互，没有可见反馈就等于没做。

## 70. Tab 切换闪一下 —— 进出动画不同步造成的「双向半透明」漏光（2026-09-13）

**现象**：密码条目页 → 验证码页（以及反向）切换时屏幕闪一下；**深色模式尤其晃眼**。

**根因**：`TabTransitions` 原为 `fadeIn(220ms)` + `fadeOut(120ms)`，另叠加 `slideInVertically`。
`AnimatedContent` 过渡的**中间帧两页同时在屏幕上**：新页 alpha = a、旧页 alpha = b 时，
与背景 `Bg` 的合成结果是 `新*a + 旧*b*(1-a) + Bg*(1-a)*(1-b)`。
两条**时长不同**的曲线必然在中间某处同时处于「半透明」（a≈b≈0.5），
此时背景占比 `(1-a)(1-b) = 25%` ⇒ 黑底透出四分之一 = **一帧明显的闪光**。
位移动画把这块漏光「抹开」，观感更糟。

**解法**：进出**同时长**（140ms）且 alpha **互为补数**（enter 0.95→1、exit 1→0.05，
`CubicBezierEasing(0.6,0,0.4,1)`），`(1-a)(1-b)` 峰值降到约 1.2%；去掉位移。

**判据**：**任何 cross-fade，进出必须同时长 + alpha 互补。**
「让退出更快一点」这类看着更利落的配置，在深色底上就是一次闪光。

## 71. 长按多选缺失 / 卡片按钮冗余 —— 对齐 Bastion 的「选择模式」规格（2026-09-13）

**现象**：①验证码卡片上「复制 / 编辑 / 移除」三个图标按钮太占地方；
②「按住条目出现选择框 → 从右往左滑删除」没做好。

**根因**：①把「复制」这种**主操作**（Bastion 里点卡片本身即复制）又做成一个图标，
另有编辑 / 移除两个低频动作**常驻**在行内；②列表只有 `onClick` + 左滑删除，
没有「长按进入选择态」这条路径，用户勾不了多条。

**解法**（对齐 Bastion `TotpCodeCard.cardInteractionModifier`）：
- **选择态**：`clickable { onToggleSelect }`，行尾 `Checkbox` 顶掉菜单按钮；
  **非选择态**：`combinedClickable(onClick = 主操作, onLongClick = 进选择)`，
  行尾 `MoreVert` + `DropdownMenu` 收纳「绑定 / 编辑 / 移除」。
- 底部批量操作条（`ui/common/SelectionActionBar`）：已选 N / 全选 / 清空 / 删除所选；
  密码页与验证码页共用，`BackHandler` 优先吃掉返回手势以免白勾一场。
- 左滑删除保留，且**不与长按抢事件**：`PressAndSwipeToDelete` 由
  `detectDragGesturesAfterLongPress` 改为手写 `awaitEachGesture + 
  withTimeoutOrNull(longPressTimeout) + drag`，长按进选择、继续拖才滑删。

**判据**：**列表行的「主操作 / 低频操作 / 批量操作」要分层** ——
主操作 = 点卡片；低频 = 收进菜单；批量 = 长按进选择态。
三者挤在一行里，结果是既不好点也不好看。

## 76. 沉浸式让位**必须写在滚动内容里**，写在滚动容器外的 padding 上就永远不沉浸（2026-09-13，第五十一轮）

**现象**：验证码页下滑时**不沉浸、没有透明**，与密码页处理不一致（密码页正常）。

**根因**：验证码页沿用旧写法 —— `Column(modifier = Modifier.padding(top = barTopInset))`
包住 `LazyColumn`。让位被加在**滚动容器之外** ⇒ 整页被永久下压 `barTopInset`，
列表的可见区域从顶栏下沿才开始，内容**永远画不到顶栏区域**，于是顶栏底下永远是一段纯色，
没有「内容从顶栏之下滑过去」的透明感。密码页早已改成把让位并入列表首项。

**对照**：同一个病在 `ISSUES.md` **#67** 已经写过一次（当时修的是「筛选条压首条 /
上下不沉浸 / 搜索黑横幅」三症）。本轮是**同一根因在另一个页面残留**。

**解法**：删除外层 `Column(padding(top = ...))`，把让位并入
`LazyColumn(contentPadding = PaddingValues(top = barPadding + 8.dp, ...))`；
同时把页面顶部的「统一进度条」从「列表外的固定头」改成**列表首项**（`item(key = "page_progress")`），
让它在滚动时与条目一起滑走 —— 这正是上一轮 #2 想要的「进度条随滚动收起」在沉浸式下的正确形态。

**判据**：**顶栏 / 底栏让位一律做在滚动内容里**（`contentPadding` 或列表首/末项），
**永远不要**加在滚动容器的外层 padding 上。出现「不沉浸」先去看外层有没有 `padding(top)`。

## 77. 手势要**分层**：长按只负责「进选择」，红底与位移只由手指产生（2026-09-13，第五十一轮）

**现象**：长按条目后「删除按钮不显示、不跟手」，但删除**确实生效**；
用户明确只想要「长按出现勾选框」。

**根因**：上一版为了让手势「看得见」（`ISSUES.md` #68 的补救）做了 **armed 态**：
长按瞬间把 `armed` 置 1 ⇒ 立刻画 32% 红底 + 把内容左移 16dp。
但这条手势**同时**还要承载「长按进多选」——「长按」这一个事件被赋予了两种语义：
①进多选（用户要的）②预露删除（上一版加的）。两条在一起就是「一按就红、内容跳一下」，
而且这层静态红底和手指位移**不是同一个驱动源**，滑动起来自然「不跟手」；
更糟的是红底和卡片在同一坐标系里抢视觉，观感就是「和 UI 冲突」。

**解法**（按用户选定口径「长按只勾选，滑动才显红」）：
- **长按只回调 `onLongPress`**（进多选、只勾选），不再改任何视觉状态；
- **位移只由手指产生**：`onDrag` 里 `offsetX = (offsetX + delta).coerceIn(-maxDragPx, 0f)`；
- **红底 alpha 只由位移驱动**：`reveal = (-offsetX / thresholdPx).coerceIn(0f, 1f)`；
- 删除掉 `armed` / `ARMED_SCALE` / `ARMED_HINT_ALPHA` / `hintRevealPx` 整套；
- 阈值判定只发生在 `onDragEnd`：过阈值就 settle 到 `-maxDragPx * 2` 再触发删除。

**顺带**：删除底由「`if (reveal > 0f)` 条件式组合」改为**常驻**节点，只调
`graphicsLayer { alpha = reveal }`。条件式增删 Compose 节点会让「第一个像素的位移」
触发一次重新组合，观感就是起手抖一下。

**判据**：**一个手势事件只承担一种语义。** 「长按 = 进选择」与「滑动 = 危险操作」
必须分在不同手势通道里；危险操作的红底 / 位移**只能由位移一个驱动源**推。

## 80. `PullToRefreshBox` 指示器默认贴容器顶 ⇒ 与「让位后的列表首条」之间露出空隙（2026-09-13，第五十一轮）

**现象**：下拉同步时，下拉处有一块很大的空隙没处理好。

**根因**：`PullToRefreshBox` 的指示器默认贴在**滚动容器顶部**（= 整页最上面），
而列表首条在 `topInset`（状态栏 + 72dp 顶栏）之下。下拉时指示器从上往下走、
列表从上往下走，两者之间就是一段**没有被内容覆盖的纯背景** —— 看起来就是「一大块空隙」。

**解法**：自定义 `indicator`，给 `PullToRefreshDefaults.IndicatorBox` 加
`Modifier.padding(top = topInset)`，让指示器与列表首条**同一个基准线**：

```kotlin
PullToRefreshBox(
    isRefreshing = syncing, onRefresh = onRefresh, state = pullState,
    indicator = {
        PullToRefreshDefaults.IndicatorBox(
            state = pullState, isRefreshing = syncing,
            modifier = Modifier.padding(top = topInset),
            containerColor = MaterialTheme.colorScheme.surfaceContainerHigh,
            content = {},
        )
    },
    content = content,
)
```

**签名坑（javap 实证）**：这个重载**没有** `indicatorAlignment` 参数；
`IndicatorBox` 的 `content: @Composable BoxScope.() -> Unit` 是**必传**的（传 `{}`）。
把这段抽成 `ItemsPullToRefresh` 时，`content` 参数类型必须写
`@Composable BoxScope.() -> Unit`，写成 `@Composable () -> Unit` 会报类型不匹配。

**判据**：**凡是「给滚动容器加顶栏让位」的地方，都要同步检查下拉指示器 / 空的加载态 /
吸顶头这些「不在滚动内容里的元素」有没有跟着让位。**

## 81. 「手势返回时画面缩小 1~2 帧」= Android **预测式返回的预览**，与转场无关（2026-09-13，第五十二轮）

- **现象**：**手势**返回时能看到"当前页缩到约 80%、居中、四周露出下层页面"的 1~2 帧；
  条目详情 / 卡包 / 设置子页**处处都有**。而**返回键**（含 `adb input keyevent 4`）**完全没有**。
- **根因**：那是 **Android 预测式返回（predictive back）的预览**——手势期间系统把当前页缩小、
  露出下层页面。`android:enableOnBackInvokedCallback` 对 **targetSdk 36+ 默认值为 `true`**：
  不声明 ⇒ 预览已开启；**显式写 `true` ⇒ 等于把预览钉死开启**；只有显式 `false` 才关掉。
- **解法**：`AndroidManifest` 的 `<application>` 显式
  `android:enableOnBackInvokedCallback="false"`，把返回交回 App 播自己的转场。
  要保留预测式手感则写 `true` + `PredictiveBackHandler` **自绘**预览。
- ⚠️ **排查教训（最贵的一条）**：这个现象我改了**三次转场**（fade → `sizeTransform` → 位移幅度），
  全都没打中，因为**复现方式本身是错的**——我用"按键返回"去复现"手势返回"的问题。
  ⇒ **先对齐复现路径（哪个手势/哪个入口），再动代码**；
  `input keyevent 4` ≠ 手势返回，复现动效类问题必须用 `input swipe`（从左缘起）。
- ⚠️ 同时**根因不止一个**：另有 `NavHost` 的容器尺寸补间（见 #82 附近的转场铁律）
  与 MainShell 重放 Tab 过渡，都会造成"看着像缩小"的错觉，已一并修掉。

## 84. 「空」有三种状态，塌进一个 `isEmpty()` 分支就出**假空态**（2026-09-13，第五十二轮）

- **现象**：冷启动瞬间点验证码页，有 **1~2 秒**的"还没有验证码"——**假的**，其实是还没加载完。
- **根因**：界面把"加载中 / 真的没有 / 查询无结果"三种状态**塌进了同一个
  `state.items.isEmpty() -> EmptyBody()` 分支**；而 `vaultIdState` 初始为 `""`，
  `observeItems("")` 会**立刻发一个空列表**，正好落进假空态。
- **解法**：`UiState` 单独加 `loading`；数据管线在 id 为空时**发 `null`**（而不是去查空 id），
  下游翻译成 `loading = true`；界面把 `loading` 分支**排在空态之前**，显示居中转圈。
- **判据**：**任何 `isEmpty() -> 空态` 的地方都要问一句"这个空，是真的空，还是还没来？"**
  （同类形状尚存于密码列表 `ItemsScreen` 与卡包页；密码页因活跃库 id 同步解析暂未复现）。

## 86. 同形状的两层圆角矩形叠放，边缘**必漏一条缝**（2026-09-13，第五十二轮）

- **现象**：深色模式下条目卡片周围有一圈**极细的红边**（像删除按钮溢出）。
- **根因**：`PressAndSwipeToDelete` 的卡片与删除底层是**两个各自栅格化的 12dp 圆角矩形**，

- **判据**：**`Box` 里两层"同形状"的矩形永远会有缝**；下层要么 alpha=0，要么别用同形状叠。

## 89. 应用图标：内层图形必须「等比缩放 + 质心对齐」，手工拼曲线会让它**漂移**（2026-09-14）

- **现象**：用户：「**内层的盾和外层的盾没对齐，内层的漂移了位置啊**」——内盾横向偏了，
  且形状看着比外盾"扁"。
- **根因**：为了让「描边缝四边等宽」，内层改成**手工按每条边向外偏移拼曲线**
  （顶边直线段 + Q 角 + 底部 C 曲线）。但拼出来的 **Q 角在纵横方向被非等比拉伸**：

  | | 横占 | 纵占 |
  |---|---|---|
  | 外盾角 r=7 | 0.3500 | 0.1321 |
  | 手工拼的内场角 | **0.4145** | **0.1460** |

  左右角的实际形状与外盾不一致 ⇒ 两条底曲线的对称性被破坏
  ⇒ **内层面积质心横向漂移 -0.29dp**（53.7124 vs 外盾 54.0000）。
- **解法**：**内层一律由外层 path「等比缩放（单一 k）+ 平移」生成**——
  等比 ⇒ 形状严格同构 ⇒ 左右对称是**构造性成立**的；平移量由
  「内层质心 → 外层质心」反解。实测质心偏差 **0.0006**、左右留白差 **-0.0000**。
  ⚠️ 改尺寸只改 k 后重算 path，**不要手改顶点**。
- ★ **核心认识**：外盾是「方肩 + 尖底」，顶边直线、底尖曲线，两种边界的等距偏移
  性质不同 ⇒ **缝宽"四边相等"与"左右对称"几何上不可兼得**。本项目明确**选左右对称**，
  按"最小缝 ≥ 2.0dp"定 k（终选 0.815：缝 左2.10/右2.10/顶2.67/底3.93）。
- ⚠️ **判据教训**：判"整组是否居中"要用**外层图形的面积质心**比画布中心，
  不能拿内层质心去比（我据此误报"偏低 0.73dp"，实际外盾偏差仅 0.089）。
  且**按包围盒中心平移会把顶角推出安全圈**（r=33.20 > 33）——外盾本来就该略偏下。
- **工具**：`~/.workbuddy/skills/android-adaptive-icon-geometry/`
  （`solve_inner()` 求内层、`verify()` 跑四条校验：安全圈 / 质心 / 左右留白 / 越界采样）。

**函数式调用不会订阅 Flow、不参与 Compose 快照**。于是：

1. 首帧渲染时 `state.items` 可能还没到（`observeItems` 的首帧是异步的）⇒ `rows` 算出**空列表**；
2. 渲染空态「还没有通行密钥」；
3. 之后**没有任何机制保证再重组一次** —— 数据到了也不会自动刷新；
4. 点搜索 ⇒ `searchActive` 变化 ⇒ **强制重组** ⇒ 这一次才读到真数据 ⇒ 列表出现。

所以「必须点搜索」**不是玄学，是一次漏订阅**。
`collectAsStateWithLifecycle()` 拿到的 `state` 是**订阅着的**，
但界面**没用它**算派生数据，而是绕回去读了后端的 `_state.value`。

**修法**（照抄验证码页早已修过的同一坑）：

```kotlin
// ViewModel：纯逻辑抽成不碰 _state 的扩展
fun List<VaultItem>.toPasskeyRows(): List<PasskeyRow> = ...

// Screen：绑定到**已收集的 state 快照**
@Composable
private fun rememberPasskeyRows(state: PasskeysViewModel.UiState): List<PasskeyRow> =
    remember(state.items, state.query) {
        state.items.toPasskeyRows().filter { it.matches(state.query) }
    }
```

**这是同一个坑的第二次踩**：验证码页 `TotpCodesScreen.kt` 的 `rememberTotpEntries`
早已修过，KDoc 里写得明明白白 ——

> 必须吃 `state.items` / `state.query` 两个 Compose State（而非
> `viewModel.filteredEntries()` 直读 `_state.value`）—— **后者不感知快照**，
> Tab 切换 / `SaveableStateProvider` 恢复时偶发不刷新
> （用户反馈「密码页新建的含验证码条目，在验证码页搜不到」）。

**⇒ 可复用判据（写代码时自问）**：

> **界面要用的任何派生数据，都必须从「已收集的 state 快照」算出来，
> 不要回 ViewModel 读 `_state.value`。**

ViewModel 里凡是给界面用的 `fun xxx(): List<...>`，只要内部读了 `_state.value`，
就是一个**定时炸弹**：它依赖"碰巧还有别的状态变化触发重组"才正常。
**正确形态**永远是把纯逻辑做成不碰 `_state` 的扩展/顶层函数，
由界面用 `remember(state.a, state.b) { ... }` 绑定输入重算。

**顺带修掉的同源问题**：

| 问题 | 原状 | 现状 |
|---|---|---|
| 空态分支混淆 | `state.items.isEmpty() \|\| rows.isEmpty()` 一个分支 | 拆成 `noPasskeysAtAll` 与 `rows.isEmpty()` 两级（对齐验证码页），搜索无结果不再错报「还没有通行密钥」 |
| loading 文案自相矛盾 | `passkeys_empty_title`（"还没有"）+ 计数硬编码 `0` | `title = null` + 新增 `passkeys_loading_body`「正在读取通行密钥…」 |

**排查手法（值得复用）**：用户描述里出现「**要点一下某个无关按钮才出现**」时，
八成就是这一类**漏订阅 / 少一次重组**，而不是数据或分支错。
先看界面拿数据的那个函数是不是绕开了 `collectAsState*` 的快照。

### ★ 第五轮更正：真根因在**窗口层**，不在栏的形状

**第三轮改成胶囊后，用户反馈黑带更明显了**（「上方下方还有黑色的」）—— 这是最关键的线索：
**胶囊四周留白恰好把 `Dialog` 窗口的黑底露了出来。**

#### 两条真根因（缺一不可）

| # | 根因 | 说明 |
|---|---|---|
| **A** | `targetSdk ≥ 35` 起 `window.statusBarColor` / `navigationBarColor` **是 no-op** | Android 15 强制 edge-to-edge，旧 API 失效。原代码那两行赋值是**死代码**，而 `@Suppress("DEPRECATION")` 把"它已不生效"这个信号也一起压掉了 ⇒ 一直没被发现 |
| **B** | `Dialog` 窗口**不继承** Activity 的 edge-to-edge | 窗口类型是 `TYPE_APPLICATION_PANEL`；其 window background **来自主题 = 黑色**。**只要窗口顶/底留了白，黑色就露出来** ⇒ 满宽栏反而能盖住它 |

#### 定稿方案：满宽薄栏 + 与背景匹配的三档渐变保护层

依据 = 官方 [edge-to-edge 指南](https://developer.android.com/design/ui/mobile/guides/layout-and-content/edge-to-edge)：

| 官方条目 | 落到本壳 |
|---|---|
| **Do** 小顶栏不吸顶时加**与背景匹配的渐变** | `drawBehind { drawRect(Brush.verticalGradient(...)) }` |
| **Do** 系统栏半透明、UI 从下方滚过 | 不透明段只到栏体，之后是过渡尾段，内容从尾段穿过可见 |
| **Don't** 渐变**与各 pane 背景不匹配** | 端点色必须用 `colorScheme.surface`（正文卡片是 `surfaceContainerHighest`，**不同色**） |
| **Don't** **叠加**多层 status bar 保护 | 只有**一层**渐变，**不加** scrim、不加第二层色块 |

#### 修法两条（窗口层，缺一不可）

1. **把窗口背景换成 `surface`** —— ⚠️ **不是 `transparent`**：API 35+ 在三键导航下仍会按
   window background 叠一层 **80% 遮罩**，设透明的结果**还是近黑**。设成 `surface` 后，
   遮罩叠在**与页面同色**的底上 = "同色的加深"，符合官方的"渐变保护必须匹配背景 pane"。
   - 必须用 `window.setBackgroundDrawable(ColorDrawable(...))`：
     资源 id 表达不了**运行时**底色（浅色/深色/OLED/动态取色）；
     `decorView.setBackgroundColor` 只改 DecorView 层、**改不到 Window 层**，遮罩仍按旧色算。
2. **关掉导航栏对比度遮罩**（`isNavigationBarContrastEnforced = false`，默认 `true`）——
   它会在三键导航下把导航栏压暗 20%，在底部制造"半黑带"。
   （`isStatusBarContrastEnforced` 在 API 35+ 已是 no-op，无须碰。）

#### 为什么形状必须回到满宽

- `RoundedCornerShape(Int)` 是**百分比**语义，在「宽满屏 × 高 48~72dp」的扁容器上被高度钳死
  ⇒ 两端半圆、中间长直线 ⇒ **扁椭圆枕头**。M3 无组件用此形状。
- 满宽栏把窗口边缘的黑底**盖住**，配合渐变保护层正好满足官方 Do 的两条。

#### ★ 复现判据（第五轮重写 —— 第四轮那版三问全问错了）

### ★ 第六轮更正（2026-09-21）：渐变本身没错，错的是**渐隐段画在了空白上**

> 用户反馈原文（两轮合并）：
> ① 「最新的预览界面，新建编辑条目界面。**浅色页面，感觉还是不透明**，整体布局不美观，
>   上下的白条显得很大。」
> ② 「这个是新建条目和编辑条目时候，**往下滑动的时候，下方保存和取消占用的空间太大**了，
>   一条很大很宽的白色横条，上方也是一整片的白色横条，**不沉浸，滑动的时候也不透明**。
>   **完全和主界面滑动的时候效果不搭调**。」

⚠️ 第五轮定稿的「满宽薄栏 + 渐变保护层」**方向是对的**（CI 已绿、APK 已发），
但它有两处细节没做到位，用户在真机上看出来了。**不要推翻方向**，只修这两处。

#### 根因 1：栏体高 72dp 里有 24dp 是**纯留白**

`TITLE_BAR_HEIGHT = ACTION_BAR_HEIGHT = 48(触摸目标) + Spacing.md × 2 = 72dp`。
两个 12dp 垂直内边距让按钮上下各多出 12dp 纯白 —— **栏体比内容高 50%**。
截图实测底部白条约 87dp（含 inset），而里面有内容的按钮只有 48dp。

⇒ `BAR_VERTICAL_PADDING`：`Spacing.md`(12dp) → **`Spacing.xs`(4dp)**，栏体 72 → **56dp**。
**触摸目标不缩**（48dp 全保留），只去掉超出留白。与用户自己项目 Bastion 的
`NoteEditorTopBarHeight = 64.dp` 同量级。

#### 根因 2 ★：**渐隐段整段落在"无内容"区 ⇒ 等于没做渐变**

第五轮的底部实现是**倒序写法**：

```kotlin
val tailFraction: Float = GRADIENT_TAIL / layerHeight
val opaqueUntil: Float = GRADIENT_END - tailFraction   // ← 缺陷在这
```

数学上它等价于「不透明段 = `inset + 栏体`」，**看起来没问题**。但逐像素模拟显示：

```
层高 141dp = navBar(45) + 栏体(72) + 尾段(24)
 不透明段 0 ~ 117dp        渐隐段 117 ~ 141dp
                            ↑ 这段全在 navBar inset 的空白里，没有元素会画在那儿
```

⇒ **渐变从 1 → 0 走的是**一片**什么都没有的区域**，肉眼完全看不出来；
而真正有卡片穿过、会露出 `surfaceContainerHighest` 灰的按钮区（12~60dp）反而**全程 1.00 不透明**
⇒ 用户看到的就是**硬边白条**，与他描述的「不透明」「白条很大」**逐字对应**。

⚠️ 更关键的是：**这个 bug 只看代码发现不了** —— 两种写法数学等价，必须**逐像素打印
「alpha + 该处有无内容」**才看得出来（脚本见 `SESSION-2026-09-20.md` §10.4）。

#### 修法：把渐隐段挪到**内容侧**

- 顶部：不透明 `0 ~ (状态栏 + 栏体)`，渐隐 `(状态栏 + 栏体) ~ (状态栏 + 栏体 + 尾段)`。
- 底部（镜像）：层顶全透明 → 到 `尾段` 处已不透明 → 直到屏幕底保持不透明。
  即 `fadeStart = GRADIENT_TAIL / layerHeight`（与 `1 - (inset+栏体)/层高` 是同一个值）。
- **`bottomGradientStops` 必须新增 `navBarInset` 入参**。第五轮 KDoc 曾以
  「倒序写法可以省掉这个参数」为优点 —— 那个"省"**恰恰就是把渐隐钉到错地方的机制**。
  ⇒ 纪律：**当被省掉的信息决定语义时，省它就是错**，不能只看"能不能省"。

#### 不变量（改完必须仍然成立）

| 不变量 | 内容 | 验证方式 |
|---|---|---|
| A | `不透明段长度 ≡ contentClearance(inset, bar)` | `ContentClearanceTest` + 逐像素模拟 |
| B | 渐隐段**整段** ≥ 让位终点（在内容侧）<br>底部：`栏体上沿@层内 == GRADIENT_TAIL` | 逐像素模拟 |
| C | 标题区 / 按钮区逐像素 **alpha 恒 = 1.000** | 逐像素模拟 |
| D | 层顶/层底端点 alpha ∈ {0, 1}（无残余色带） | 逐像素模拟 |

⇒ **A 是"卡片不会透进不透明段"的唯一依据**（`FormGroupCard` 是 `surfaceContainerHighest`，
与渐变端点 `surface` 不同色）；B 是"渐变真的可见"的唯一依据。**两条都不能破。**

#### ⛔ 一条被否掉的猜测（记下来，免得下次再走）

曾怀疑「底部白横条下沿不是屏幕底」是 `WindowInsets.navigationBars` 取到了**手势热区**
（~45dp）而非可视内容区所致。**核对后否掉**：主界面 `VaultixBottomDock.kt:87` 读的是
**同一个** `WindowInsets.navigationBars`。

⚠️ 换 insets 源会让编辑壳与主界面**分叉**，而用户的验收判据恰恰是
「完全和主界面滑动的时候效果不搭调」。⇒ **与主界面保持同源**优先于"理论上更准"。
真正成因是不透明段把这片 inset 空白整个涂满了 —— 改的是**渐变分布**，**不是** insets 源。

#### 本轮明确**不做**的两件事（用户已选项）

- ❌ **不做滚动淡出**：编辑是模态场景，「新建条目」标题与「保存」**必须一直可见**。
  （第五轮的 `barBackgroundAlpha` 式淡出在编辑壳里会让人找不到"保存"。）
- ❌ **不动卡片观感**：用户明确选了"先只修上下白条"。

## 110. 🔴 Compose `Dialog` 里系统栏逻辑**整段静默失效**：`LocalView.current` 取在了 `Dialog { }` 之外（2026-09-21）

**现象**：编辑/新建条目页的**状态栏图标白到看不见**（白图标压白底，看起来像"被一层白盖住"）；
窗口背景、导航栏对比度遮罩同样从未生效。

**根因**：`FullScreenDialogShell` 在**函数体开头**写 `val view = LocalView.current`，
但函数体运行在**外层（Activity）的 composition** 里
⇒ `view` 是 **Activity 的 view**，parent 链里没有 `DialogLayout`
⇒ 窗口查找恒为 `null` ⇒ `SideEffect` 里 `?: return@SideEffect` 直接返回
⇒ **窗口背景 / 导航栏遮罩 / 图标深浅三件事从来没执行过**。

⚠️ 原注释写的是「必须在 Dialog 内容里取 parent（这时 parent 才是这扇 dialog 窗口）」——
**注释说的是对的，代码没照做**。

**真机取证（决定性）**：`dumpsys window windows` 看目标窗口的 `mAttrs`：
```
ty=BASE_APPLICATION   apr=LIGHT_STATUS_BARS LIGHT_NAVIGATION_BARS   ← Activity（正确）
ty=APPLICATION        （apr 整行缺失）                                ← 编辑对话框（错误）
```
修复后对话框窗口出现 `apr=LIGHT_STATUS_BARS LIGHT_NAVIGATION_BARS`；
像素复核（全分辨率截图，状态栏带）主色 `#FAF8FE`、最暗 `#121212`、深色像素 6166。

**修法**：① `LocalView.current` **必须在 `Dialog { }` 内容里取**；
② 拿窗口要**沿 view 树逐级向上找 `DialogWindowProvider`**（`DialogLayout` 实现它），
**不要**赌"直接父级"（`view.parent as? DialogWindowProvider` 一旦中间多一层包装就返回 null）；
③ 拿到窗口后**别只设一次** —— Dialog 在 `show()`/首帧布局会重应用系统栏外观，需幂等补设
（`DisposableEffect` 立即设 + `decorView.post{}` + `OnAttachStateChangeListener`）。

> **可复用纪律**：`?: return@Effect` 这类"拿不到就静默返回"会把整段功能变成
> **不报错的死代码**。排查顺序应是 **先确认"这段有没有执行"，再问"执行了为什么不对"**。
> 判据工具：`dumpsys window windows` 看 `apr=`（有 = 深色图标，无 = 浅色图标）。

## 111. 🔴 **谎报成功**：界面弹「已复制下一个验证码」，剪贴板里什么都没放（2026-09-21）

**现象**：用户以为"临期（剩余 ≤5 秒）会自动复制下一个验证码"，实际**从来没复制过**。

**根因**（`ui/totp/TotpCodesScreen.kt`，加开关时才发现的）：
```kotlin
val codeToCopy = if (isExpiring) nextCode else code              // 算出来了……
val copyNow = { if (isExpiring) onCopyNext() else onCopy(code) } // 却没人用它
```
- `codeToCopy` 是**死变量**（全仓库只有注释引用）；
- 临期分支调的是 `onCopyNext()`，而它的接线**只弹一个 Snackbar**。

**修法**：抽 `copyAction(...)` 纯函数，**先复制 `nextCode`、再提示**，两者由**同一判据**派生
（顺带把 `TotpRow` 的圈复杂度从 17 降回门禁内）。

> **可复用纪律**：「提示成功」的代码必须与「做事」的代码**写在同一条路径上**。
> 只提示不做事 = **谎报**，比不做更糟 —— 用户会以为成功、不再排查。
> 同族纪律（§0 已有一条）：`每个早退分支要么改状态、要么留日志`；
> 本例是它的反向：**"成功提示"也是一个状态，必须有对应的事实支撑它。**
> 排查手段：看到"算了却没人用"的变量，立刻查它本该被谁消费。

  位数一变（6 位码 ↔ 8 位码、HOTP 计数器进位）整串宽度**会有可见跳动**。
  ⚠️ 验证码每 30 秒刷新，这个跳动会被反复看到，所以它是**观感问题而非功能问题**。
- **处理**：按用户要求改 `MASK_CHAR = '*'`，但**没有删掉原警告** ——
  而是把代价如实改写成"已知代价（用户主动选择接受）"，并留下后路：
  若日后想消抖又不回圆点，可换 `●`（U+25CF，宽度属性与 `•` 相同、观感更实）。
  ⇒ **纪律**：用户推翻一个"有理由的设计"时，**改实现但不要抹掉理由**，
  把它降级成"已知代价"留档 —— 否则下一个人会重新踩同一个坑。
- **范围**：只改验证码（用户指定）。详情页密码 / 卡号 / 逐字段隐藏仍用 `•`。
  `TotpCodesScreen` 侧**零改动** —— 它不含硬编码遮罩字符，全走 `TotpGenerator.mask`，
  这正是"遮罩只在一处实现"的好处。
- **验证**：`core/common` 是纯 JVM 模块（无 Android 依赖），可整份源码 + 整个测试文件
  真编译真运行：36/36 通过；并做**变异测试**（`'*'` → `'#'`）⇒ 5 条失败，
  证明 8 条断言不是空转。这比上一轮 #116 的"片段编译"可靠得多。

## 120. 「不猜状态」原则只修了一半：同一页 3 个开关用占位、7 个用裸 `Switch`（2026-09-26）

- **现象（代码层）**：设置页「防截屏」「动态取色」在冷启动后快速进入时会先显示占位、
  数据到了才出现；但「OLED 纯黑」「自动复制验证码」「临期复制下一个码」「自动填充保存提示」
  「严格匹配」「允许子域名匹配」「填充辅助」「卡片显示图标」**直接渲染一个开/关**。
- **根因（分两层，第二层才是关键）**：
  1. **UI 层**：后 7 处直接写 `Switch(checked = xxx)`，没走 `SettingsSwitch`。
  2. ⭐ **类型层**：ViewModel 里这些是 `StateFlow<Boolean>` + `initialValue = true/false` ——
     **类型上就禁止表达 `null`**。于是即使 UI 想不猜也拿不到"不知道"这个信息。
     ⇒ 这解释了为什么 #84 那次只修了 3 个开关：**其余 7 个不是"忘了改"，是"改不了"**，
     得先把类型放宽。
- **解法**：8 个流改 `StateFlow<Boolean?>` + `initialValue = null`；
  7 处裸 `Switch` 换 `SettingsSwitch`（含跨包复用的 `DisplayOptionsSheet`）。
  并在 ViewModel 加契约 KDoc：**新加开关初值一律 `null`**。
- **★ 最容易做错的一步**：`FillBehaviorSection(exactDomainOnly: Boolean, ...)` 这个中间层。
  只改 ViewModel 和 UI、漏掉它，调用点就必须写 `?: false` 把 `null` 压回确定答案 ——
  **问题没解决，只是从 UI 挪到了调用点**。改为 `Boolean?` 才算真通。
  ⚠️ 通用教训：**可空性要在整条链路上传递**，任何一层收窄都会让上游的努力白费。
- **附带修正（占位态不可点）**：原 `SettingsSwitch` 占位是一个纯 `Spacer`，**不可点**。
  数据没到的那几百毫秒里，用户手指已落在开关位置，点击被吞 ⇒ 用户感受是
  「这个开关按了没反应（有时）」。改为占位仍接收点击，语义固定为**「打开」**。
  - 为什么不是"取反"：`value == null` 时**根本没有"当前值"可反**，
    硬反只能拿上次会话的旧值猜，又把未定状态换成可能过期的确定值。
  - 为什么"打开"安全：本就开 → 幂等；本就关 → 正是用户意图。
    反方向的"关闭"才危险 —— 用户"从没见过它开，却把它关了"。
- **验证**：detekt 净改善（18→17，删 `passkeyCount` 消掉一个 `MagicNumber`）；
  另建契约片段复刻「可空流 → 收集 → section → SettingsSwitch」整链，
  变异（把 section 或组件参数改回非空）均立即报错。

## 142. 顶栏标题折两行：`softWrap = false` 会让整件事**静默不发生**（2026-10-01）

1. **固定栏高下两行有字号预算**：栏高写死 72dp，而列表顶部让位高度也按它算

   ⇒ 两行时字号上限压到 **20sp**（48 + 16 = 64dp，留在 72dp 内）。

## 144. 拆行之后，**可压缩项要跟着换**（2026-10-01）

- 状态行原为一行：来源（`weight(1f)`、中间省略）+ 角标 + 条目数（**都不压缩**）。
  压缩压力全部由**来源**承担 —— 这正是它能成立的原因。
- 拆成两行后：第一行只剩来源（独占整行），第二行是角标 + 条目数。
  ⇒ 第二行**没有任何一项可压缩**，窄屏 + 长角标时会**溢出**。
- **解法**：把"可压缩"这个责任转给第二行的**角标**（`weight(1f, fill = false)`），
  条目数继续不压缩（它是锚点信息："有多少条"必须完整可读）。
- **纪律**：⚠️ **布局里"谁来吸收挤压"是一项显式设计，不是默认值**。
  任何"把一行拆成两行 / 把两行并成一行"的改动，都要重新回答一遍这个问题 ——
  否则要么溢出，要么某个关键信息被挤成省略号。

  「空串」出现 8 次、「真 null」出现 5 次。**若只盯着空串那 8 次下结论，会得出
  「补个 `isNotBlank()` 就好了」的错误判断** —— 因为真 null 的那 5 次 `?:` 根本不短路，
  兜底**已经算了、确实算不出来**。⇒ **修掉空串后，那 8 次只会退化成和另外 5 次一样的 null，
  用户症状一点没变。**
  ⇒ **「分布统计」比「挑一个典型样本」更能定性**：同一份日志里 `webDomain=` 与
  `webDomain=null` 的**出现次数对比**，直接决定了「这是一处判据写错」还是
  「整条路在平台层就不通」。
- **外部佐证（不是我们写错了）**：Bitwarden Android 在 Firefox Android 上**同样**
  做不了域名匹配 —— 其 issue [#5720](https://github.com/bitwarden/android/issues/5720)
  「Autofill does not propose correct vault entries」与社区帖
  [#19444](https://community.bitwarden.com/t/compatability-with-android-mobile-browsers-that-arent-chrome/19444)
  都记着这件事。**Firefox 用 GeckoView，第三方 AutofillService 拿不到可用 `webDomain`
  是已知平台限制**，用户搜到的普遍结论是「Firefox 上改用 Bitwarden 的扩展（Add-on）」。
- **修法（两刀，缺一不可）**：
  1. **空白防御**：域名收集与兜底裁决抽成纯函数 [WebDomainResolver](../app/src/main/java/io/vaultix/vaultix/autofill/parser/WebDomainResolver.kt)
     （`ViewNode` 是 `@SystemApi` 抽象类、构造不出实例，逻辑不抽出来就没法 JVM 单测），
     判据与 `inheritWebDomain` 对齐。
  2. **无域名降级**（真正解决用户问题的那一刀）：`webDomain` 为空时**不返回 0 条**，
     改为按「收藏优先 → 名称升序」返回全部候选（`orderWithoutDomain`），
     再由 `MAX_DATASETS` 截断 ⇒ 用户在 Firefox 上仍能看到条目并一键填入，
     而不是面对一个空面板。**对齐 Bitwarden 的搜索兜底语义**：它也没让用户挡在门外。
- **⚠️ 安全边界**：降级**不关闭** `AutofillRequestContextPolicy` 的包名匹配闸门 ——
  浏览器里缺域名时包名是**浏览器自己**的，拿它匹配会弹出「浏览器身份」的无关条目，
  那才是真的错条目。降级只在确实是登录表单时生效（由 `noFillTarget` 闸门保证）。
- **遗留（下次真机验收要盯）**：`AutofillCredential` **没有 `lastUsedAt`** ⇒ 降级只能按
  收藏 + 名称排，不能按「最近使用」。Bitwarden 有这个字段，是本条最大的可改进点。

## 181. 🔴 详情页「条目不存在或已被删除」一闪而过 —— **「未知」借用了「空值」**（2026-10-22，用户真机反馈）

- **现象**：在条目列表里滑动后点进某条详情，会闪过**不到 1 帧**的「条目不存在或已被删除」，
  随后内容正常出现。不崩、不报错、logcat 干净，只有眼睛能抓到。
- **根因**：`ItemDetailViewModel.UiState.item` 的初始值是 `null`，而 UI 用它表达**两件事**：
  「还没解出来」和「确认不存在」。`DetailBodyContent` 的 `when` 里 `item == null` 直接落到
  缺失提示分支 ⇒ **订阅建立之前的那几帧被渲染成"确认不存在"**。
  窗口窄到只剩一两次重组（新 ViewModel 实例、`observeItem` 还在建立订阅、
  或库类型/密钥尚未就绪），所以是"1 帧"，而不是"白屏一秒"。
- **修法**（两层，缺一不可）：
  1. 状态层：`UiState` 新增 `itemLoaded`（**已经收到过一次条目流发射**），
     一旦置真不再回落 —— 流重发时若短暂解不出条目，继续显示上一次的内容，而不是闪回"不存在"；
  2. 呈现层：`DetailBodyContent` 增加 `loading = !itemLoaded`，
     `loading && item == null` 画转圈，`item == null` 才画缺失提示。
- **判据**：**「未知」必须是一种显式状态，不能借用「空值」来表达**。
  `null` 同时表示"没有"和"不知道"时，UI 必然在其中一种情况下撒谎。
- **⚠️ 排查过程中的一个反例（值得记）**：最初怀疑的是 `ItemRepositoryImpl.observeItem`
  的 `vaultDao.observeAll()`（Room 流要先跑一次查询）把 `cipherDao.observe()` 卡在
  `flatMapLatest` 上游，为此加了 `.onStart { emit(null) }`。**实测证伪**：
  撤掉该行，`observeItem(...).first()` 仍然拿到条目（`runTest` 的虚拟时钟会推进上游）。
  该行作为**廉价的前置订阅优化**保留，但**它不是本 bug 的修复点**，
  真正修复上面那两层。教训：**"看起来合理"的链路要先用探针证伪/证实，别照着直觉改**。
- **测试**：`ItemRepositoryImplTest.observeItem_firstEmissionIsNeverNullOrBeforeVaultKindResolves`
  锁住数据层"首值不为 null"；状态层的 `itemLoaded` 属于 Compose 状态机，
  本地无 Compose UI 测试装置，**留待真机验收**（点进条目不应再看到该提示）。

## 182. 🟡 筛选面板贴条目、滚动后展开难看 —— **面板与列表的两条边都没有"落点"**（2026-10-24，用户真机反馈）

- **现象**（用户原话）：
  1. 「展开筛选的时候，全部、验证码、通行密钥这些展开栏目好像和底下的密码条目隔得很近」；
  2. 「在往下滑动的时候点击筛选，好像显示效果很不好看」。
- **根因（两个，表现不同但同源：**没有一条边界被明确画出来**）**：
  1. **面板与列表的缝只有 8dp**，而第一张卡片的底色 `surfaceContainerLow` 与页面背景
     对比度只有 1.049（`EntryCard` KDoc 有推导）⇒ 8dp 的缝在像素上读不出来，
     观感就是「chip 行坐在第一张卡片上」。这正是 `.ai/conventions/8.4` 判据⑨
     「几何上有间距 ≠ 看起来没被遮住」的**第二次**复现（上一次是 2026-10-04 的浮层底色）。
  2. **往下滑之后，顶栏之下是一片空白**：面板靠 `AnimatedVisibility` 自上而下展开，
     只能画出已经滚到顶栏之下的内容 —— 列表滚下去之后那里什么都没有，
     于是面板往空处展开，chip 行像悬在半空。
- **修法**：
  1. chip 行下内边距 8dp → 12dp（`QUICK_FILTER_ROW_PADDING_BOTTOM`），
     并在**让位侧**另加 [QUICK_FILTER_LIST_GAP] = 8dp 的呼吸缝
     —— 「面板多高」与「列表让多少」分开两处，各调各的不互相牵动；
     `QUICK_FILTER_ROW_HEIGHT` 从字面量 48dp 改成**算式**
     （`上下内边距 + FILTER_CHIP_HEIGHT`），内边距再变也不会漏改让位常数。
  2. 新增「面板展开 ⇒ 列表顶端露在面板下方」：面板已展开**且列表已滚离顶部**时，
     主动把列表滚到 `first = 第 0 项、offset = QUICK_FILTER_TOP_ANCHOR(56dp)`，
     同时外壳 `padding(top)` 下移同一个值、列表内各项用 `graphicsLayer(translationY)`
     **反向补偿** ⇒ 可见内容**一像素都不跳**，用户只看到「面板盖住上面几行」。
     列表本就在顶部时这条路径**完全不走**（`reveal = 0`），与改动前逐字节一致。
- **⚠️ 顺序是硬性的：先让位、再滚。** `scrollToItem(0, anchor)` 的上限是
  `contentPadding.top - viewport`，而让位要**下一帧**才生效；先滚的话那一刻
  `padding.top` 还是 0，锚点被夹到 0 ⇒ 滚了等于没滚（`scrollToItem` 只记录目标位，
  不会在让位生效后自己修正）。实现上用两帧：`withFrameNanos { }` 之后再 `scrollToItem`。
- **代价（有意接受）**：滚到下面之后点开面板，列表会跳回顶端一个视图 —— 数据没变，
  只是"看的位置"变了；点面板外收起时停在原位（**不回跳**，避免一次意料之外的位移）。
- **测试**：全部是 Compose 布局/滚动态，本地无 UI 测试装置 ⇒ **留待真机验收**：
  ① 列表在顶部点开面板，首条与 chip 行之间应是明显的一道缝；
  ② 往下滑几屏再点库名，面板下方应立刻能看到列表顶端（而不是一片空）；
  ③ 面板展开期间连点 chip，顶栏标题不应缩一下。

### 182.1 ★ 更正（2026-10-24 当晚）：**"回到顶部"被用户否决，改为默认关闭的选项**

- **用户反馈**（原话）：「现在往下滑动的时候，发现点击筛选，会直接返回最上面。这样设定不友好」。
- **我错在哪**：我把「面板展开时下方不能是空的」当成了**唯一**要满足的约束，
  于是拿"滚到顶端"去满足它 —— 补偿只保证了**不跳**（可见内容一像素不动），
  却没保证**不换位置**。而用户的诉求是**位置连续性本身**：他在看第 30 条，
  点筛选是想在**这个上下文里**换一维，不是从头再看一遍。
  ⇒ **"画面连续" ≠ "位置连续"**。前者能靠 `graphicsLayer` 补偿做到，后者意味着压根不该滚。
- **修法**：`rememberListEdgeHolder` 增加 `jumpToTop` 门控，接偏好项
  `VaultixPreferences.itemsFilterJumpToTop`（**默认 `false`**）。
  关闭时该函数**一个字节都不碰滚动位置** —— 连"切 chip 回第 0 项"也不做，
  因为那也是"换一种方式回顶部"。
- **开关位置**：「条目显示」浮层（顶栏 🔍 旁边那个）最下面新增一组，
  文案 `展开筛选时回到列表顶部` / 说明 `展开分类筛选面板时，把列表拉回最上面（关闭则保持当前位置）`。
  放在这里而不是设置页：它只在**这个列表**上有意义，设置页是全局的，放那儿会让人误以为影响所有页面。
- **⚠️ 代价（如实记）**：关掉之后，往下滑再展开面板时顶栏之下仍是空白 —— 那正是 #182 想解决的"难看"。
  **这个取舍交给用户**：两边诉求都真实，只是优先级不同，不该由我再猜一次。
- **教训**：**当"修好一个现象"需要对用户的浏览上下文动手时，先问这是不是他要的**。
  位置类改动（滚动、分页、折叠）默认应该是"不打扰"，要打扰就必须是用户显式打开的行为。

- **文档与实现的裂缝**：`Docs/08-界面设计规格.md` 第 63 行早就写了

- **🔴 最容易写错的一条：准入条件不是"第一次装 App"，而是「无库」且「没看过」**
  - 只看"没看过" ⇒ 从旧版本升级上来的老用户（那个键**不存在**，读作 false）会被拦一次；
  - 只看"无库" ⇒ 老用户把库删光后每次都要重看一遍；
  - 因此 `RootNavState.Onboarding`（= 无库）**不能**直接当引导条件用。它的语义是
    "没有库可解锁"（见该类 KDoc 的启动死锁说明），第三个条件必须另取偏好位。
- **修法**：
  1. 新增 `core:datastore` 的 `OnboardingPreferences`（**独立类**，不塞进已有 35 个函数的
     `VaultixPreferences` —— 那离 detekt `TooManyFunctions` 的 40 上限只剩 5 格）。
     两把键：`onboarding_seen`、`onboarding_fill_setup_prompted`，都默认 `false`；
  2. `RootNavViewModel.showOnboarding` = `vaults.isEmpty() && !seen`，**初值 `false`**（不拦）；
  3. `VaultixApp` 只在 **`!routedOnce`**（真正冷启动）时落引导 —— 否则"在设置里删掉最后一个库"
     会把人从设置页拽到引导页；
  4. 引导页 `ui/onboarding/OnboardingScreen.kt`：`HorizontalPager` 3 页 + 跳过 + 指示点；
     插画 `OnboardingArtwork.kt` 用 `Canvas` 画（吃主题色，深浅/动态色自动成立，无外链素材）。
- **文案与插画的两条对应纪律**：
  - 第 2 页说"两个库地位一样"，插画里两块石头**就必须等大** —— 画成一朵云 + 一个文件，
    云的视觉重量天然压过文件，图会自己打脸文案；
  - 「去开启自动填充」放在**第 3 页**而不是第 1 页：还没接库的用户去配填充服务是空转。
- **两条行为约定**：
  - **跳过 = 看完**（同一个标记）。区分开就要在"跳过"后再弹一次"真的不看吗"，而这页没有需要补问的东西；
  - 点「去开启自动填充」**不结束引导**，只记 `fill_setup_prompted` 再跳系统页 ——

## 198. 🟢 底栏液态玻璃（Liquid Glass）—— 真模糊只有一条路，且有三处静默失效陷阱（2026-10-27，用户需求）

- **需求原话**：「我想底栏做液态玻璃的通透效果，能做吗，开启底栏的液态玻璃效果，
  需要在设置里面主题模式里面添加液态玻璃开关按钮。」
- **能做，但必须先说清"能做到什么程度"**：
  - ✅ 做：半透明填充 + **实时模糊其后的列表内容** + 上沿高光 + 1px 内描边；
  - ❌ 不做：iOS 26 的**透镜折射**（边缘把背景像素往里挤）。
- **为什么"真模糊"只能这么做**：Compose 没有"模糊背后像素"的 API。
  `Modifier.blur` 模糊的是**自己绘制的内容**，不是身后已画好的像素。
  唯一可行路径是把底栏所在**图层**做成模糊渲染层 ——
  `graphicsLayer { renderEffect = RenderEffect.createBlurEffect(...) }`，
  它作用于该图层的**输入**（= 背后已合成内容）。
- **🔴 三处静默失效陷阱（都不报错，只表现为"开关像坏了"）**：
  1. **顺序陷阱**：模糊必须挂**最外层** Box。挂到内层内容 Box 上 → 模糊的是"内层自己"（近乎空白）；
     先用不透明 `Surface(color=…)` 铺底再模糊 → 模糊的是一块纯色。两者看起来一模一样：没生效。
  2. **填充 alpha 必须是半透明**：`fill.alpha == 1f` 会把模糊结果整块盖掉。
     这条最容易在后续改配色时被顺手改坏 ⇒ 单测 `填充保持半透明且深色更透` 反向锁定。
  3. **降级会静默**：`RenderEffect.createBlurEffect` **只有 API 31+ 有**。低版本若"开关打开、
     什么都不提示"，用户只会认为功能坏了 ⇒ 设置页副标题换成
     「当前系统版本不支持实时模糊，将使用半透明底栏」，**显式降级而不是静默降级**。
- **为什么不做折射（写在这里免得下一棒以为漏做）**：在 `RenderEffect` 之上再叠折射，需要把
  背景内容当**纹理**喂给 AGSL `RuntimeShader`；而 `graphicsLayer` 的 renderEffect
  只能对自己的图层输入生效，拿不到可控采样源。硬做只剩 `PixelCopy` 逐帧回读屏幕 ——
  列表滚动时帧率直接打穿。⇒ 这是**有意的取舍**，不是未完成项。
- **修法（五个改动点，全部收敛到一个实现）**：
  1. 新建 `app/src/main/java/io/vaultix/vaultix/ui/glass/LiquidGlass.kt` ——
     **唯一实现点**：`isLiquidGlassBlurSupported` / `shouldApplyBlur` / `LiquidGlassStyle` /
     `liquidGlassStyle` / `LiquidGlassLayer` / `Modifier.blurBehind` / `DrawScope.drawGlass`。
     所有视觉参数集中在 `object LiquidGlass` 常量里，**避免各处拼参数导致观感漂移**；
  2. `VaultixBottomDock(liquidGlass: Boolean = false)` 分支：真玻璃走 `LiquidGlassLayer`，
     否则保留原 `Surface`；并**抽出 `DockRow`** 让两条分支共用同一份布局；
  3. 偏好链：`VaultixPreferences.liquidGlassDock`（默认 **false**）→
     `SettingsViewModel.liquidGlassDock: StateFlow<Boolean?>`（初值 **null**，遵守"布尔开关
     初值一律 null"契约）→ `SettingsScreen.DisplaySection` 里「主题模式」组中 **OLED 纯黑之后**
     新增一行开关（`BlurOn` 图标）；
  4. 状态穿透：`MainActivity` 收集 → `VaultixApp(liquidGlassDock)` →
     `vaultEntryGraph(..., liquidGlassDock)` → `MainShellScreen(liquidGlassDock = …)` →
     `VaultixBottomDock(liquidGlass = …)`；
  5. 文案：`setting_liquid_glass` / `setting_liquid_glass_desc` / `setting_liquid_glass_unsupported`。
- **⚠️ 本轮又踩了一次"以为已接线其实没接"**：连报三次
  `Unresolved reference 'liquidGlassDock'`，真实原因是参数的实际调用点在
  `VaultixApp.kt` 里的**私有函数 `vaultEntryGraph`**，不是 `VaultixApp` 函数体。
  ⇒ **加"从底到顶"的参数时，先用 grep 找出谁真正构造那个 Composable**，
  不要去猜调用链。命名参数也要认准位置（`MainShellScreen(` 的参数是**紧跟左括号**的第一个）。
- **测试**：`LiquidGlassTest` 8 例 —— API 门槛表驱动（26/29/30/31/33/35）、开关关闭不挂模糊、
  默认参数取真实 `Build.VERSION.SDK_INT`、填充半透明且深色更透、填充只改 alpha 不改色相、
  描边深色更淡 + 高光恒白、降级补偿"接近不透但不越界"、上沿高光带比例合理。
  ⚠️ **不测"画出来好不好看"** —— 那只能在真机上看；这里只锁**会静默出错**的数值约束。
- **待真机验收**：① API 31+ 打开开关 → 列表滚动时底栏后面的文字被糊成色块；
  ② API 30 及以下打开开关 → 底栏实色、设置页副标题为"不支持实时模糊"；

### 198.1 🔴 返工：第一版把图标一起糊掉了（2026-10-27 用户真机截图）

- **用户原话**：「液态玻璃的底栏不对啊，按钮都看不清，参考开源项目是如何实现的？」（附截图：
  整条胶囊连同 4 个 tab 图标、文字、中央「+」全被糊成灰雾）。
- **根因（一句话）**：`graphicsLayer { renderEffect = 模糊 }` 模糊的是**该图层的输出，
  包含它全部子内容**。第一版把它挂在**包住 `DockRow` 的那个 Box** 上 ⇒ 图标文字连同背景
  一起被糊。上面 §198 写的「✅ 对：把 `clip` + `blurBehind` 挂在最外层 Box 上」
  **这条判断是错的**，真机截图直接证伪 —— 已在本轮改写。
- **正确架构 = 源 → 消费 两段分离**（对齐 [chrisbanes/Haze](https://github.com/chrisbanes/haze)
  的 `hazeSource` / `hazeEffect`，Apache-2.0）：
  ```kotlin
  // Haze 的原始范式
  val hazeState = rememberHazeState()
  LazyColumn(Modifier.hazeSource(hazeState)) { … }   // ① 登记"可被模糊的内容"
  TopAppBar(Modifier.hazeEffect(hazeState)) { … }     // ② 浮层采样它，自己不受影响
  ```
  本项目**不引新依赖**，用 Compose 自带的 `rememberGraphicsLayer` + `record` + `drawLayer`
  实现了同一机制：
  | 角色 | 实现 | 关键 API |
  |---|---|---|
  | 源 | `Modifier.liquidGlassSource(source, enabled)` 挂在 Tab 内容区 Box 上 | `drawWithContent { layer.record { drawContent() } }` |
  | 消费 | `Modifier.liquidGlassBackdrop(source, offset, radiusPx)` 挂在浮层的"背景层" | `canvas.translate(-offset); layer.renderEffect = blur; drawLayer(layer)` |
  | 共享 | `rememberLiquidGlassSource()` → `LiquidGlassSource(layer, bounds)` | `boundsInRoot()` 求偏移 |
- **结构必须分两层**（这是本次修复的核心，改错一行就复现 bug）：
  ```
  Box(modifier) {
      Box(matchParentSize().clip(shape).onGloballyPositioned{…}.liquidGlassBackdrop(…))  // 层 A：唯一带模糊
      Box(matchParentSize().clip(shape).drawBehind { drawGlass(…) }) { content() }        // 层 B：图标 + 填充/高光/描边
  }
  ```
  层 A / 层 B 是**兄弟节点**，各画各的层 ⇒ 层 A 的 `renderEffect` 波及不到层 B 的图标。
  这正是 StackOverflow 上「内容放在同一层里也会受效果影响，解法是两个叠加的 Box」所说的做法。
- **四条"不报错、只是不糊/糊错"的约束**（写进 `LiquidGlassSource` KDoc）：
  1. 源的子树里**不能有不透明铺底**（`Surface(color=…)` / `background`）：录到的是"子树自己
     画了什么"，铺底会盖掉底下的一切 ⇒ 录下一块纯色，模糊它等于没做。本项目 Tab 页背景透明
     （`VaultixTheme` 的 `Surface` 在更外层），而**顶栏自己是不透明 `Surface`** ⇒ 若把源挂到
     含顶栏的位置，只会糊到一片灰。
  2. 源与浮层都用 `boundsInRoot()` 描述，跨兄弟层级会对不上。
  3. **每帧重录**：`record` 每帧跑一遍，列表滚动才跟着糊 —— 这是成本所在，所以只挂一个源。
  4. 尺寸为 0 时跳过 `record`（首帧 / 页面切走会分配 0×0 位图）。
- **🔴 顺手修掉的第二个真 bug（视觉）**：源的录制区**比胶囊高得多**，层 A 若不 `clip(shape)`
  就会把一大块糊影画到胶囊外面。第一版没有层 A，所以这个坑当时不存在；分层之后必须补。
- **顺带纠正两处拍脑袋的数值**（数值直接对齐 Haze `HazeMaterials` 五档）：
  | 项 | 第一版 | 现在 | 理由 |
  |---|---|---|---|
  | 填充 alpha（浅/深） | 0.62 / 0.48（**深色更透**） | 0.60 / 0.65（**深色更实**，= Haze `thin`） | Haze 五档全部深色更实（0.55/0.65、0.65/0.80、0.80/0.90…）：深色背景更暗、模糊结果更接近黑，填充再薄就分不清"玻璃"与"背景" |
  | 降级档 | 半透明 + 0.18 补偿（≈0.80） | **全不透明**（`FALLBACK_ALPHA = 1f`） | 半透明底栏浮在滚动列表上，条目会从图标之间透出来 → 读不清，那是"不可用"不是"不好看"。Haze 对无模糊平台同样画 flat scrim |
- **测试**：`LiquidGlassTest` **10 例**（原 8 例，其中 2 例被真机证伪而改写）——
  新增 `降级档直接不透明`、`blurAvailable 默认按真模糊算`、`深浅判定取底色亮度而非系统主题`；
  `真模糊档填充保持半透明且深色更实` 把方向反过来钉住。
  ⚠️ **架构正确性单测测不到**（要 Compose UI 测试 + 真机），只能靠真机看图标清不清晰。
- **待真机验收（本轮重做后）**：① 图标 / 文字 / 中央「+」**必须清晰**（这是本次 bug 的核心）；
  ② 列表滚动时胶囊后面有内容在动、被糊开；③ 糊影**不越出胶囊边界**（不出现方形色块）；
  ④ 深色主题下玻璃与背景能分出边界；⑤ API 30 及以下 → 实色底栏 + 设置页提示"将使用实色底栏"。

## 199. 文件夹 CRUD：整条写路径此前不存在（2026-10-27）

**用户需求**（原话）：「继续开发，完善设置，以及日常的功能」。核对功能盘点后发现：
`FolderRepository` **只有 `observeFolders` 三个读方法**，`FolderDao` 只有整体替换的
`replaceByVault`。⇒ 用户能**看到**文件夹（分组视图、表单下拉框都在用），但**建不了、
改不了、删不了**。Bitwarden 客户端与本项目对标的 KeePassDX 都能建分组 —— 这是一块
「别人有、我们没有」的真空。

### 199.1 三个决策点（用户已选定，别再重议）

| 问题 | 选择 | 为什么 |
|---|---|---|
| 写失败怎么办 | **直连 API，失败当场报错** | 见 199.2 |
| 要不要一并支持 KDBX 分组 | **一并支持** | 只做 Bitwarden 等于给一半用户看一个死页面 |
| 入口放哪 | **条目页 ⋮ 菜单「前往」组** | 文件夹是**数据**（能删），不是"看的方式"；后者归「显示选项」 |

### 199.2 🔴 为什么 Bitwarden 侧**不能**照搬条目的「本地先行 + pending_ops 排队」

条目的写是"本地先落库、`pending_ops` 排队、轻量推送"。文件夹有三条硬理由不能抄：

1. `pending_ops` 的主键语义是 `cipherId` + 五种 **cipher** 操作，没有任何一列能装 folder；
2. **`pruneRemovedRows` 会把本地新行当已删清掉** —— 它判定"服务端没返回的 folder 行 = 已删"。
   用户刚建、还没推上去的文件夹会被**下一次同步静默删除**（用户看到自己建的东西凭空消失，
   比"离线时建不了"严重得多）；
3. `FolderDao` 只有 `replaceByVault` 的整体替换语义，没有单行 upsert。

⇒ **直连：成功才写本地，失败一个字都不改。** 代价写进 KDoc 了：离线时不能建文件夹。
这个取舍是**有意的**，后续"顺手统一成队列"会直接复现第 2 条。

### 199.3 实现结构（四层，每层一处判据）

| 层 | 文件 | 内容 |
|---|---|---|
| 领域 | `domain/FolderNamePolicy.kt` | 名字校验**唯一一处**：trim / 空 / ≤100 字符 / 禁 `/` `\` |
| 领域 | `domain/FolderRepository.kt` | 三个写方法，均 `Result<Unit>` |
| KDBX | `data/kdbx/KdbxItemWriter.kt` | `createGroup` / `renameGroup` / `removeGroup` / `deletionCostOf` |
| KDBX | `data/kdbx/Kdbx.kt` | 门面 + `folderDeletionCostOf`（只读预览） |
| 仓储 | `data/repository/FolderRepositoryImpl.kt` | `resolve(vaultId)` 分流到 `Remote(api)` / `Kdbx` |
| 库 | `core/database/dao/AtomicWriteDao.kt` | `upsertFolder` / `deleteFolder`（`@Transaction`） |
| UI | `ui/folders/` | `FoldersViewModel` + `FoldersScreen` + `FolderNameDialog` |

🔴 **为什么 `/` 和 `\` 必须禁**：KDBX 的 `VaultFolder.name` 存的是**完整路径**
（`KdbxItemMapper` 用 `"$parentPath/${group.name}"` 拼），组名里带 `/` 会让层级
不可解析 —— 建得进去、读出来全是错的。

🔴 **`AtomicWriteDao` 的两个文件夹方法故意写成「非 abstract」**：用 Room `@Upsert`
的**已注册实体**形态（`FolderEntity` 在 `@Database(entities=…)` 里），Room 自己生成实现。
代价是单测里那些手写的 `AtomicWriteDao` 转发子类**一个字都不用改**；
若哪天有人改回 `protected abstract`，那 5 个子类会立刻编译失败 —— **这个失败是想要的**。

### 199.4 删除代价的「数法只能有一处」

`KdbxItemWriter.removeGroup` 递归删子树时要报 `GroupDeletion(subGroups, entries)`，
而 UI 的确认框也要显示"会连带删掉 N 条"。两处各算一遍必然漂移 ⇒
**抽 `deletionCostOf(database, folderId)` 只读预览**，`removeGroup` 内部也改用它。

⚠️ **UI 侧 KDBX 那一支刻意不显示条目数**：`FoldersViewModel` 只统计 `folderId`
**恰好等于该分组完整路径**的条目，**子组里的没算进去** ⇒ 系统性偏小。
给一个偏小的数字比不给更危险（用户会想"才 2 条，删吧"），
而算准它要重走整棵树、为确认框跑一次文件解析不划算。

### 199.5 两种库的删除语义**必须分开写文案**

- **Bitwarden**：文件夹是扁平标签 ⇒ 删掉只让条目变「无文件夹」，**条目不删**；
- **KDBX**：分组是树 ⇒ 删掉是**递归删整棵子树**（子组 + 条目全没，不可撤销）。

用同一句"删除文件夹？"会让 KDBX 用户在毫无预警的情况下丢数据。
这是本页唯一一处"两种库必须长得不一样"的地方（文案键都分开：`folder_delete_*_message`）。

### 199.6 三层测试与两条反证

| 测试 | 例数 | 锁定什么 |
|---|---|---|
| `FolderNamePolicyTest` | 6 | 边界值、trim、禁字符 |
| `KdbxGroupWriteTest` | 11 | 建/改名/删子树、回收站组不许动、代价统计 |
| `FolderRepositoryImplTest`（新增 10） | 共 14 | 双路径分流与失败零写入 |

★★ **两条必留的反证**：
- `新建失败_本地零写入`（`coVerify(exactly = 0) { folderDao.upsertOne(any()) }`）——
  没有它，"先写本地再调远端"的实现也能让其它用例全绿，而那正是 199.2 第 2 条的幽灵行来源；
- `KDBX 库建文件夹转交 KdbxItemRepository` + `coVerify(exactly = 0) { api.createFolder(any()) }`
  —— 两个库的写路径**不能串**，串了就是把 KDBX 分组发去某个 Bitwarden 服务器。
