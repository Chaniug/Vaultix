## 256. 「能力做完了，入口没接」的第三次与第四次 —— 建文件夹 / 扫验证码 / 选条目搜索（2026-11-09，用户真机反馈）

**现象**（用户原话，三条一起报）：

> 1. 新建密码条目的时候，选择文件夹的时候没有新建文件夹的选项。照理说项目应该都支持新建文件的选项。
> 2. 新建验证码条目的时候，没有扫描验证的按钮，项目已经做了扫描的功能，应该在添加验证码的页面增加入口。
> 3. 添加通行密钥的时候，照理说通行密钥是自己会调用 vaultix 添加的，那个步骤已经有搜索条目并保存到条目中，
>    但是单独的添加通行密钥的部分，选择保存条目没有搜索的选项，只能一条一条往下翻找。

三条**症状各不相同**（缺按钮 / 缺按钮 / 缺搜索框），但**根因是同一个**：

| # | 缺口 | 能力其实早就有 | 为什么用户找不到 |
|---|---|---|---|
| 1 | 条目表单的文件夹下拉只有一个只读列表 | `FolderRepository.createFolder` + `FolderNameDialog`（文件夹页一直在用） | 下拉**只接了"读"**，没接"写"。想顺手建一个分类，得退出表单去文件夹页建完再回来重填 |
| 2 | 验证码编辑页的密钥只能手打 | `QrScannerContent`（登录条目的 TOTP 字段一直在用） | 验证码页作为「**专门**录验证码」的页面，反而没有扫的入口 |
| 3 | 通行密钥「选择密码条目」是裸 `ExposedDropdownMenu` | 「通行密钥注册时选条目」那一步**有搜索** | 同一个 App 两个入口，一个能搜一个不能 |

- **这是 #255「资源存在但从未接线」的延续**，也是 `.ai/conventions/8.9` 里反复出现的失败模型：
  写能力 / 组件 / 资源都落地了，也都有调用点，**但不是用户会走的那条路**。
  可复用的判据（review 时可直接问）：
  > **某个能力在 A 处可用，B 处是同一件事的另一个入口 —— B 处接了吗？**
  > 如果 B 处"能用但难用/得绕路"，它算缺陷，不算"设计如此"。

- **#3 尤其值得记**：用户自己给出的推理是「那个步骤**已经**有搜索条目并保存到条目中，但单独的添加通行密钥的部分没有」——
  他用的判据正是上面这条**一致性判据**。用户不需要读代码就能发现这类缺口，
  因为它表现为「同一个 App 里同一个动作，两个地方行为不一样」。

### 修法

**1. 文件夹下拉底部加「新建文件夹」**（`ItemFormDialog.kt` → `FolderPicker`）

- 复用 `FolderNameDialog`（同一个输入框，校验规则来自 `FolderNamePolicy`，不另写一条）；
- 用 `HorizontalDivider()` 与上方文件夹隔开：它是**动作**，不是**选项**。
  混成一排的话用户会把「新建文件夹」当成一个叫这名字的文件夹；
- **新建成功后自动选中**：点「新建文件夹」的意图就是「把这条放进那个还不存在的分类」，
  建完停在「无文件夹」等于让他再点一次。

- **⚠️ 表单不碰仓储**。签名是 `onCreateFolder: ((name, onCreated) -> Unit)?` 而不是 `suspend`：
  Compose 的菜单回调不是挂起上下文，而且 `ItemFormDialog` 要被三个页面复用，
  不该绑死某个 ViewModel。写能力由宿主提供（`ItemsViewModel.createFolder`），
  表单只声明"我需要一个建文件夹的入口"。**默认 null ⇒ 读-only 场景退化成纯选择器**。
- **⚠️ 失败不回调**。`onCreated` 只在真建成功时触发；失败走既有 `SaveEvent.Failed` 通道（Snackbar）。
  如果失败也回调一个空 id，条目会**悄悄归到根组**，用户还以为建好了。

**2. 验证码编辑页的密钥字段加扫码按钮**（`TotpCodesScreen.kt` → `TotpEditDialog`）

- `trailingIcon` 上的 `Icons.Filled.QrCodeScanner`，点了开**全屏 `Dialog` + `QrScannerContent`**，
  结果直接回填 `secret` —— 与登录条目 TOTP 字段**同一个组件、同一种交互**，不另写一套相机逻辑。
- 复用现成组件而不是新写，是因为相机权限流程（`QrScannerContent` 里 `LaunchedEffect` 请求
  `Manifest.permission.CAMERA`）只有一份实现；抄一份出来就变成两处要各自维护权限拒绝分支。

**3. 通行密钥的条目选择器加搜索**（`SavePasskeyDialog.kt` → 新增 `PasskeyLoginPicker`）

- 搜索框放在**菜单里面**而不是表单里：放外面会先多出一整行输入框，用户以为要填什么，
  而它只在挑条目时才有意义。
- 按 `title` **+ `username`** 两个字段匹配（`ignoreCase`）：很多条目标题是「GitHub」而账号是邮箱，
  用户凭记忆输入的往往是**任一个**，只按标题筛会漏。
- 每项显示**标题 + 账号副标题**：标题可能重复（两个 GitHub），账号用来区分。
- 空结果给 `passkey_search_empty` 文案：菜单只剩一个搜索框却不说话，用户会以为卡住了。
- **⚠️ 两个 Compose 陷阱（都已踩过）**：
  - 搜索框**不能**加 `menuAnchor()`。加了它会把这个菜单当成自己的锚点，抢掉外层输入框的位置。
  - 收起时清搜索词**不能**在组合里直接 `query = ""`（那是渲染期间写状态，会同一帧再跑一次组合），
    要用 `LaunchedEffect(expanded) { if (!expanded) query = "" }`。

### 验证

- 门禁：`check_compile_smells` / `check_import_packages` / `check_signature_types` /
  `check_orphan_state` / `check_state_flattening` / `check_experimental_optin` /
  `check_ui_hardcoded_text` / `check_orphan_strings --gate`（1093 条，零引用 114 条 = 基线）/
  `check_md_links` / `check_issues_index` / `verify_sync_fields` 全绿。
- 新增字符串 3 条：`folder_create_new`、`passkey_search_login`、`passkey_search_empty`。
- CI `42562233722`。
- 真机待验：① 新建条目 → 文件夹下拉 → 新建 → 名字确认后**自动选中**；
  ② 新建条目时文件夹列表为空（新库）—— 此时整个下拉**不渲染**（`folders.isNotEmpty()` 闸门），
  **新建入口也跟着没有**（见下方遗留）；③ 验证码新建 → 点扫码 → 扫一个 otpauth:// 二维码 → 密钥回填；
  ④ 通行密钥添加 → 展开条目下拉 → 输入邮箱前缀能筛出条目。

### 遗留（未做，记下来）

- **零文件夹时无法在表单里建第一个文件夹**。`FormHeader` 的闸门是 `if (folders.isNotEmpty())`，
  设计意图是"不显示一个永远无选项的下拉"，但接上「新建文件夹」之后这个闸门就过头了：
  **恰恰是最需要建第一个文件夹**的新库里，入口消失。正确做法是
  `if (folders.isNotEmpty() || onCreateFolder != null)`，即"有选项 **或** 有新建能力"就渲染。
  本轮没改，因为需要同时确认空列表 + 可新建时下拉的视觉（一个只有分隔线和"新建文件夹"的菜单）是否可接受。
- **KDBX 侧建文件夹的语义**：KDBX 没有独立的"文件夹"实体，`createFolder` 落到的是分组。
  表单里建完之后新条目归到该分组是否立即体现在 KDBX 的结构迁移上，未单独验证
  （走的是与文件夹页同一个 `createFolder`，风险低，但没实测过"表单内建 + 立刻保存"这条组合路径）。

## 附：验证码（TOTP）全链路排查 —— 保存 / 修改 / 改位置 / 同步 / 删除（2026-11-09，用户提问）

用户附带的问题是「验证码保存、修改、改位置、同步都是完好的吗？这一点需要排查一下」。
**排查结论：五个环节全部正常**，依据如下（均为读代码确认，非推断）。

| 环节 | 结论 | 依据 |
|---|---|---|
| **保存** | ✅ | `saveTotp` 建的是 `password=""` 的登录条目（Bitwarden 兼容：TOTP 只能挂在 login 上，没有独立 TOTP 类型） |
| **修改** | ✅ | `item.copy(title, totp)` —— 只改这两个字段，`folderId` 与其余全部字段原样保留 |
| **改位置** | ✅ | Bitwarden 写 `folderId = item.folderId`；KDBX 走 `moveFolder` 做结构迁移（不是改个字段） |
| **同步** | ✅ | Bitwarden：`login.totp` 加密后随 cipher 走；KDBX：写 `otp` 字段（`otpauth://`），并通过 `KdbxTotpCodec.isOtpFieldName` 清掉旧的 `TimeOtp-*` |
| **删除** | ✅ | 独立条目 → `softDeleteItem`（Bitwarden 打 `deletedDate` + 入队 `OP_SOFT_DELETE`；KDBX 进回收站）；绑定在登录条目上的 → 只清 TOTP 字段，不删条目 |

**⚠️ 发现一处潜在耦合（已记录，未改）**：

KDBX 的 `applyTotp` 用 `before.totp == item.totp` 来判断"没变就跳过写入"。
这个短路本身是对的，但它的**正确性依赖于 `applyFolder` 是另一条独立路径**：
一旦哪天有人把"改文件夹"也塞进 `applyTotp`，那么"只改文件夹、TOTP 不变"的场景会被这个短路
**整条跳过**，改位置就静默失效。目前两条路径分开，所以没事。
—— 这类"用一个字段的相等来判断整条写不写"的写法，本质上是在**替调用方假设"其他字段不会同时变"**，
与 8.11「多态压成二值开关」同一种味道：把多维状态压成一个布尔。
