### 第 ① 件：自动锁定 — 审查结论是「不动核心」

把整条链路逐段读过，并与 Bitwarden `VaultLockManagerImpl` 逐条对照：

| 环节 | Vaultix 实现 | 与 Bitwarden |
|---|---|---|
| 档位模型 | `VaultTimeout` sealed class 10 档（含 `OnSystemLock` / `OnAppRestart`） | 一一对应，含 2025.11 新增的「系统锁屏时」 |
| 分流 | `checkForVaultTimeoutInternal` 按 `Never / OnAppRestart / OnSystemLock / 分钟档` 四族，`when` 穷尽 | 逐条对齐，负数档位有显式分支（不会被 `coerceAtLeast(0)` 变成「立即锁」） |
| 每库定时器 | `timerJobMap` 按 vaultId，回前台**全撤** | 对齐 `userIdTimerJobMap` |
| 熄屏补偿 | 亮屏按 `elapsedRealtime()` 单调时钟重算剩余 | 对齐 `realtimeManager.elapsedRealtimeMs`，另钳到 `[0, duration]`（比上游更严） |
| 系统锁判定 | `isDeviceLocked`（非 `isKeyguardLocked`）+ 300ms 单次复检 + 可作废 token | 上游相同语义，复检是本项目的加固 |
| 「从不」双层锁 | 密钥层常驻内存（填充直通）+ 界面层 `viewLock`（指纹） | 对齐上游 `Never` 不软锁 + 本项目额外门禁 |
| 界面门禁显示 | 仅「从不」档且指纹可用时显示开关 | 与 `AutoViewGate.quickUnlockReady()` **同源**（都是 `fingerprintLockAvailable()`，经 `lockState()` 投影），无误报 |

⚠️ **刻意不改的地方**（写出来防止接力者又被"看起来像 bug"诱导去改）：

- `checkForVaultTimeout(vaultId)`（`UserChanged` 原因）生产零调用 —— 这是 Bitwarden 的**账号切换**语义，
  Vaultix 是单用户多库、没有账号切换，接口为对齐上游而保留，不是漏接。
- `onAppCreated` 只处理 `activeVaultId` —— 进程刚起来时非活动库本就锁着，无需逐个通知。
- 改档位后不重算当前会话定时器 —— Bitwarden 同样要等下次切后台才按新档位重新计时。
- `devRelaxScreenLock` 只拦 `OnAppRestart` 档 —— 注释明确限定，放开到分钟档会让单测与产品语义分叉。

**真找到一个确凿 bug（已修）**：`vaultTimeoutLabel` 的自定义档显示顺序 ——
`MINUTES_PER_HOUR` 判断写在 `MINUTES_PER_DAY` 之前，而 1440 = 24 × 60，**任何整天的分钟数
必然是整小时** ⇒ `auto_lock_day_fmt` 是死资源，用户填 1440 显示「24 小时」、2880 显示「48 小时」。
与 #297「成功不含证据」同族：写法看着覆盖到了，运行期却走不到。

修法：抽纯函数 `customTimeoutUnit(minutes)`（JVM 可测），判「天」在判「小时」之前；
`vaultTimeoutLabel` 改调它。测试 `CustomTimeoutUnitTest` 4 例（整天 / 整小时非整天 / 分钟 / 上限内 69 天全遍历），
变异反证：把小时判断调回前面 ⇒ 2 例转红，还原复绿。

### 第 ② 件：验证码 ⋮ 偏左 — 反编译取证的 6dp

`TotpRowMenu` 的 ⋮ 按钮 2026-10-19 从 `Modifier.size(36.dp)` 改成
`minimumInteractiveComponentSize()`，注释按「容器 36dp、图标 20dp 居中 ⇒ 左右各 8dp」
推算，声称"贴右距离与改前一致"。

**该前提是错的**。反编译 `material3-android:1.5.0-alpha16` 的
`androidx.compose.material3.IconButtonKt` 证实 `StateLayerSize = 48`（字节码 `bipush 48`）
—— M3 IconButton 容器恒 48dp，20dp 图标居中实际左右各留 **14dp**，比注释假设多缩 6dp。
图标视觉右缘距容器 8dp → 14dp，正是用户看到的「偏左了一点」。

修法（热区与视觉彻底分开）：
- 热区：`minimumInteractiveComponentSize()` **保留** ⇒ ≥48dp 可点（2026-10-19 修好的护墙不能倒）；
- 视觉：图标加 `offset(x = TotpRowMenuIconVisualNudge = 6.dp)` ⇒ 右缘回到距容器 8dp，
  与「36dp 视觉宽度」那版逐像素一致；只 offset 图标不 offset 按钮 ⇒ 点击手感不变。

测试 `TotpRowMenuAlignmentTest` 4 条源码门禁（读原文、**剥掉 `//` 注释**避免 KDoc 里
「36dp」误导断言 —— 同 #296/#297 的「注释与代码用词雷同」坑）：
热区保留 / 20dp 图标 + offset / 常量=6dp / 不得退回 `size(36.dp)`。
两轮变异反证：去掉 offset ⇒ 1 例红；热区退回 size(36) ⇒ 2 例红；均还原复绿。

### 长期判据

- **"看起来有覆盖"不等于"运行期可达"**：`1440 % 60 == 0` 这类整倍数关系会让后写的分支变死码。
  凡「按大小分档」的 `when`，先证明小档不会吃掉大档（按**大单位在前**排）。
- **视觉 dp 判断不能靠注释算术，要取证到框架实现**：M3 IconButton 容器 48dp 是常量，
  注释里"36dp"是臆测。改视觉前先反编译/查源码确认 token 值，否则修一次偏一次。
- **热区与视觉必须拆成两个 modifier 控制**：`minimumInteractiveComponentSize()` 管热区、
  `offset` 管视觉；把它们合并成 `size(36.dp)` 就是把 2026-10-19 修好的护墙推倒。
- **源码门禁读原文要先剥注释**：本仓 KDoc 常把要查的数值写进说明里（"36dp"），
  不剥 `//` 就会「注释命中、代码其实没写」—— 与 #295 `@SerialName("key")`、#297 KDoc 同词同源。
