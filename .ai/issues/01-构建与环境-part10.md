## 186. 🔴 `allowBackup` 默认 true ⇒ 锁库信封被云备份搬走、Keystore 却不跟着走（2026-10-26，对比审计）

- **现象**（审计发现，未在用户设备上观测到 —— 因为一旦发生就在**换机恢复**那一刻）：
  Android 默认 `android:allowBackup="true"`。`shared_prefs/vaultix_secure.xml` 里躺的是
  门锁信封 / KEK 信封 / 房间信封 / WebDAV 凭据 / Bitwarden token，而解封它们要用
  **Android Keystore 里的不可导出密钥** —— Keystore **不参与备份**。
- **后果链**：
  ```
  旧机备份 → 云端（或 device-transfer 直传）→ 新机恢复
  → 信封原样落在新机 → Keystore 里那把密钥不存在
  → 解封必然失败 ⇒ 拿到的是一堆解不开的废纸
  → 但界面上"门锁"这项设置看着还在 ⇒ 用户以为锁还在，实际是一把打不开的假锁
  ```
  比"恢复不了"更糟的是**恢复了一半**：`vaultix.db` 若留下来，用户会看到条目列表
  却打不开任何一条。密码管理器里这属于数据损坏级。
- **修法**：
  1. `AndroidManifest.xml`：`android:allowBackup="false"`；
  2. 同时声明两份规则资源（**保险丝**：将来若有人把 `allowBackup` 改回 true，
     排除表仍然生效，不会一夜之间把信封全搬走）：
     `android:dataExtractionRules="@xml/data_extraction_rules"`（API 31+ 的云备份 + 设备迁移）
     `android:fullBackupContent="@xml/backup_rules"`（API 30- 的老 Autobackup）；
  3. 两份规则都要**同时**排除 `sharedpref/vaultix_secure`、`database/vaultix.db`、
     `file/.`、`cache/.`。
- **⚠️ 四个坑**：
  1. **`data_extraction_rules.xml` 有 `<cloud-backup>` 和 `<device-transfer>` 两段**，
     只写一段 = 另一条通路完全没拦。换机迁移走的正是 `device-transfer`。
  2. **`sharedpref` 的 `path` 不带 `.xml` 后缀**：写 `vaultix_secure.xml` 会**静默不匹配**
     —— 不报错、不警告，规则看起来写了。
  3. **XML 注释里不能出现连续两个短横线**：想画表格分隔线 `---` 会直接编译失败
     `The string "--" is not permitted within comments`。
  4. **`<exclude` 不要跨行写**：单测里是按字符串断言规则内容的，跨行会匹配不到
     （更本质的是跨行写法容易漏掉 `path=`）。
- **验证**：`BackupPolicyConfigTest`（5 条，**直接解析源 XML 文件**，不引 Robolectric）：
  `allowBackup="false"`、两个规则资源都已声明、四条排除在两条通路上都在、
  `sharedpref` 路径不带 `.xml`。
- **判据**：**凡是"加密材料"与"解密密钥"分开存放的地方，备份策略必须按后者决定**
  —— 备份前者只会产出一个「看起来有、实际打不开」的假象。

## 193. 🔴 `release.yml` 仍写死 `gradle-version: 8.11.1` —— **同一条规则只执行了一半**（2026-10-26，对比审计）

- **现象**（尚未发生，属于"下一次发版才会炸"的定时炸弹）：
  `release.yml` 的 `setup-gradle` 仍指定 `gradle-version: 8.11.1`，而
  `gradle/wrapper/gradle-wrapper.properties` 是 **9.5.1**。
- **根因**：`ci-debug.yml` 早在 **2026-10-02** 就修过这件事（#145.3，注释写得很清楚），
  **但 `release.yml` 这条路漏网**。→ 这正是 #120 记的那种失败模式：
  **同一条规则在两个地方各写一遍，只改了一处，看起来"已修"**。
- **三个后果**（前两个是浪费，第三个是事故）：
  1. 8.11.1 白下载白解压（每次约 10s，还占一条缓存条目）；
  2. setup-gradle 的缓存按 Gradle 版本分区 ⇒ provision 的 8.11.1 缓存对实际构建的
     9.5.1 **一点用都没有**（日志里 `Cache hit for: gradle-8.11.1` 看着像命中了，
     其实命中的是个没人用的版本）；
  3. **最危险**：哪天有人把 `./gradlew` 改成 `gradle`，构建会**静默从 9.5.1 掉到 8.11.1**
     —— 一次无声的版本分叉，而 release 这条路出的正是**要发给用户的包**。
- **修法**（与 `ci-debug.yml` 逐字对齐）：
  1. 删掉 `gradle-version:` —— `gradle/actions/setup-gradle` 默认就是
     「用仓库 wrapper 声明的版本」，**版本只有一个来源**，天然不会分叉；
  2. `Ensure gradle wrapper jar` 里那个兜底也把写死的 `8.11.1` 改成**从 properties 读**：
     ```bash
     gwv="$(sed -nE 's#^distributionUrl=.*/gradle-([0-9][0-9.]*)-(bin|all)\.zip$#\1#p' \
       gradle/wrapper/gradle-wrapper.properties)"
     ```
     解析不出来就 `exit 1` 拒绝猜测。
- **⚠️ sed 的分隔符必须用 `#` 不能用 `|`**：正则里的 `(bin|all)` 会让 sed 认为 `s` 命令
  提前结束并报 `unknown option to 's'`（2026-10-02 实测踩到，已写在注释里）。
- **验证**：`python3 -c "import yaml; yaml.safe_load(open('.github/workflows/release.yml'))"` ✅。
- **判据**：**"两处写同一个事实"必然分叉**（这是 `ISSUES.md` 里那个"条数列"问题的同一根因）。
  修法不是"记得两边都改"，而是**让事实只有一个来源**。

## 201. lint fatal **只在发版那天**才暴露（2026-10-28）

> 现象：`main` 上 CI（run 40548140039）**全绿**，push `rele` 触发 stable release 后
> `Build Release APK (stable, minified)` **失败** —— 报的是
> `Execution failed for task ':app:lintVitalFullRelease'` / `Lint found fatal errors`，
> 三处 `Unexpected domain cache`（`backup_rules.xml` 一处、`data_extraction_rules.xml` 两处）。
>
> 🔴 这不是"发布流水线的问题"，是**代码里真有一处非法配置**，只是没人跑过那道检查。

### 201.1 为什么 CI 全绿也照样发不了版

| 环节 | 跑不跑 lint | 后果 |
|---|---|---|
| `ci-debug.yml` 的 `Run lint` | **带 `if: github.event_name != 'push'`** ⇒ push 到 `main` 时**根本不跑**（只有 PR 才跑） | 我们的日常路径（直接 push main）**永远看不到 lint** |
| release 构建 | 默认跑 `lintVital`，且 **fatal 直接中断构建**（不是警告） | 任何 lint fatal 都被推迟到发版那一刻 |

⇒ **"CI 绿"不能推出"能发版"**。这两条路的检查集合并不相同，而缺口正好落在"只影响发版"的那半边。

### 201.2 修法与"为什么那三行本来就该删"

合法 domain 只有 `file` / `database` / `sharedpref` / `external` / `root`
（及 `device_file` / `device_database` / `device_sharedpref` / `device_root`）—— **`cache` 不在其中**。

而 cache 目录（解密后的附件明文 `attachments/`、日志导出 `dev_logs/`）**本来就不参与备份**，
那三行 `<exclude domain="cache" path="." />` 既非法、又多余（#186 当时写它是想"显式声明以防将来改"）。
⇒ 删掉，并在两个 XML 的顶部注释里写明"别再加回来"。

### 201.3 判据

1. **被跳过的步骤就是盲区**：`if:` 让它消失的那一步，等价于"这个检查每年只在发版那天跑一次"。
   写"门禁全绿"时要说清**绿的是哪几条**。
2. `lintVital` 的 **fatal ≠ 普通 lint 警告**：前者中断 release 构建，后者不影响任何构建。
   debug 构建对两者都无感 ⇒ 本地与 debug CI 都对它没有发言权。
3. 资源 XML（`res/xml/*`）的错误**不在 Kotlin 编译里**：`e:` 计数为 0 也不代表没错误 ——
   本次发布日志 `e: 0`、`BUILD FAILED`，失败信息只在 `What went wrong` 与 lint 报告里。

### 201.4 洞补上了，但又踩到一个：单测是**第二道**拦截器

删掉三行之后，调试 CI（run 40554694782）**立刻红了**：
`BackupPolicyConfigTest` 里两条断言失败 —— 因为 #186 写的期望表把
`"cache" to "."` 当成"必须排除的敏感目录"，而 XML 那边刚把这行删了。

⇒ 这是**同一个错误的两个副本**：约束写在两处（XML + 测试），只改一处必然红。
值得记的是**顺序**：先有断言失败，才会有发版失败；如果当时先跑 CI 再发版，
这根本不会变成一次"发版事故"。可接受的顺序只有两种：

1. 改 XML 的同一次提交里改测试（本次没做到）；
2. 或者反过来 —— 先写测试（红），再改 XML（绿）。

顺带补了一条**比原来更值钱**的断言：`排除项里的 domain 必须是 lint 认可的合法值`
（白名单 `root/file/database/sharedpref/external`）。它把"lint 才知道的约束"搬进了
JVM 单测 —— 值 5 分钟的毫秒级检查，替掉一个只有发版日才跑一次的 fatal。

⚠️ 写这条断言时踩到一个自指陷阱：断言扫的是**整份文件文本**，而 XML 顶部注释里
恰好写着"不要给 exclude 标一个 cache 域"这句反例 —— 正则会把它也匹配到，
于是在**代码已经改对**的情况下继续报错。修法是改注释措辞（反例不写成可被解析的标签形式，
改成一句自然语言），而不是给正则开口子。
**注释里写反例，等于给扫描器喂假阳性。**

### 201.5 未做的建议（下一棒可挑）

把 lint 加回 push 路径（或至少在 release 之前单独跑一次 `:app:lintVitalFullRelease`）。
不改的话，这个洞会以同样的方式再出现一次 —— 只是下次换另一个 `res/` 文件。
（本次是靠"用户当场要求发版"才发现的；没有人要求发版的那一周，它会一直躺着。）

## 204. 🟡 发布说明里的「校验和」显示成 shell 命令原文 —— `body:` 是 YAML 字符串，不是 shell（2026-10-28，v0.10.2 实测）

- **现象**：v0.10.2 的 [Release 页面](https://github.com/Chaniug/Vaultix/releases/tag/v0.10.2)
  「校验和 (SHA-256)」区块里显示的是一行**命令原文**：

  ```text
  $(cat "$GITHUB_WORKSPACE/checksums-sha256.txt" 2>/dev/null || echo "见附件 checksums-sha256.txt")
  ```

  附件 `checksums-sha256.txt` 本身是好的，但**正文里等于没给校验和**——
  而"贴校验和"的全部意义就是让人**不必下载就能核对**。
- **根因**：`softprops/action-gh-release` 的 `with.body:` 是 **YAML 字符串**，
  在 job 运行时原样取用；`$( ... )` 只在 `run:` 里才会被 bash 展开。
  **同一个 `$` 符号，在 `run:` 与 `with:` 里含义完全不同。**
- **修法**：把文件内容做成 step output（`checksums<<EOF … EOF`），body 里用
  `${{ steps.apk_meta.outputs.checksums }}` 引用 —— **往 `with:` 里塞动态内容的
  唯一途径是表达式插值**。
- **判据**：**`run:` 是 shell，`with:` 是模板**。凡是 `with:` 里出现 `$(`、
  反引号、`&&`、`||`，都是把 shell 语法写错了地方；这类错误**不会让构建失败**
  （只是内容不对），所以只能靠**打开产物看一眼**发现。
- ⚠️ **修复本身尚未在真实发版路径跑过**：只做了 YAML 解析校验 + 逐行对照。
  下一次发版（`rele` 带上 `c7f8381` 之后）**要打开 Release 页面确认校验和是哈希而不是命令**——
  这类"只影响内容、不影响构建"的改动，**CI 绿与构建成功都不能算验证**。
- **已一并做的事**：v0.10.2 的发布说明已用 API 回填真实校验和；
  并下载 APK 核对 `sha256 = d2c57abc…579a` 与附件一致；
  另比对 v0.10.1 / v0.10.2 的签名证书（v2 签名块）→ **同一张证书**
  （`7e6c8c07…1fd8`，753 字节），v0.10.1 用户可**直接覆盖升级**。

## 207. 「核对校验和」入口：镜像下载之后无处可验（2026-10-29）

**现象**：`UpdateChecker` 的镜像开关打开时，「前往下载」指向 `ghproxy.net`
（`mirrorUrl`）—— 用户**从那儿拿到的 APK 由镜像提供**。而 App 内**没有任何**官方
SHA-256 清单入口 ⇒ 下载完对不对得上，全凭信任镜像。

> #204 之后发版工作流会产出 `checksums-sha256.txt`（Release 说明里的校验和区块就是
> 从它来的），**但那个入口在网页上，App 内拿不到**。产物有了、入口没有。

**修法**：
- `UpdateCheckResult` 增 `checksumsUrl`：从 release 的 `assets` 里挑
  `checksums-sha256.txt`（`pickChecksumsUrl`，名字只此一处，忽略大小写）；
- 更新对话框在**确有更新时**多给一个「核对校验和」动作（M3 对话框上限 3 个动作，恰好够）；
- ⚠️ 该地址**绝不走** `mirrorUrl` —— **拿镜像给的校验和去验镜像给的 APK，等于什么都没验**。

> **判据**：① **"用户可能被引导到第三方源"，就必须同时给出官方的可核验物**；
> ② **校验物的来源必须与被测物独立**（同源校验 = 没校验）；
> ③ 拿不到就**不给入口**，不拼"看起来像"的地址（用户点开 404 只会得出"项目不靠谱"）。
>
> ℹ️ 顺带更正 06 篇「已知未做」里的一条旧账：`UpdateChecker` 走 `ghproxy.net`
> 这一项**已经不是洞** —— 镜像只作用于下载页、且**默认关闭**
> （`VaultixPreferences.updateUseMirror`，KDoc 写明"地址被第三方代理必须用户显式选择"）。
> 真正缺的是"验"，不是"关"。
