## 263. 本地 KDBX 的条目行尾也挂着「已同步」云图标 —— 三条正确代码串成一句假话（2026-11-10，真机反馈）

**现象**：本地 KDBX 库、从未上传过任何云端，条目行尾却有实心云 + 对勾。
用户原话：

> 本地 kdbx，没有上传云端。怎么条目显示上也有小云图标。这样不对。本地和云端应该有所区别。

### 根因：三段各自正确的代码

| # | 位置 | 单独看 | 串起来 |
|---|---|---|---|
| 1 | `ItemRepositoryImpl.observeSyncStates` | KDBX ⇒ `flowOf(emptyMap())` **正确**（文件即存储，没有云端这一层） | 空 map |
| 2 | `ItemsScreen` 读侧 | `syncStates[id] ?: true` **对 Bitwarden 正确**（新建未入队不闪） | 空 map 查不到 ⇒ 每条都 `true` |
| 3 | `ItemRowTrailing` | `CloudSyncIcon(synced = synced)` 无条件画 | 画出一朵「已同步」 |

⇒ 三处都对，结果是在**一个根本没有云端的库**上显示"已同步"。

⚠️ `CloudSyncIcon` 自己的 KDoc 第 47 行早就写着：

> ⚠️ KDBX 库调用方**不要**渲染本组件：KDBX 的文件即存储，没有「云端」这一层，
> 画出来是在编造一个不存在的状态。

**契约写在了被调用方，而违反契约的是调用方** —— 这类保护等于没有。
（`TotpCodesScreen` 反过来是对的：它写的是 `if (!synced) CloudSyncIcon(false)`，
只在"待推送"时才画，KDBX 恒 true 自然不画。）

### 为什么这条比"少画一个图标"严重

**显示「已同步」比显示「未同步」更糟**：用户会据此认为**已经备份好了**。
这正是 `.ai` 里反复出现的「静默欺骗」——界面在陈述一件没发生过的事。

### 修法：`null` 与 `true` 必须分开表达

```kotlin
internal fun cloudSyncBadgeOrNull(vaultKind: VaultKind?, syncedInVault: Boolean?): Boolean? =
    if (vaultKind == VaultKind.BITWARDEN) syncedInVault ?: true else null
```

行尾改成 `synced?.let { CloudSyncIcon(synced = it) }`，
`ItemRow` / `ItemsList` 的参数类型从 `Boolean` 收窄为 `Boolean?`。

| 库类型 | 条目在 `syncStates` 里 | 返回 | 行尾 |
|---|---|---|---|
| KDBX（本地 / 网盘都是） | 永远查不到（空 map） | `null` | **不画** |
| Bitwarden | `false`（待推送） | `false` | 云加斜杠（error 色） |
| Bitwarden | `true` / 查不到（刚建未入队） | `true` | 实心云（弱化色） |
| 未知（`vaultKind == null`） | — | `null` | 不画 |

**★ 判据**：
> **「没有这回事」必须有一个独立的值，不能借用「一切正常」。**
>
> `true` = 有云、且是最新；`null` = 没有云这个概念。两者在 UI 上都是"不报警"，
> 但一个是**确认过**，一个是**不适用**。合并成一个布尔，KDBX 就必然被画上云。

### KDBX 网盘库为什么不画

KDBX 是**整文件**同步，"某一条上云了"这个概念不存在（`observeSyncStates` 对 KDBX
网盘库同样返回空 map，这是刻意的）。库级状态由详情页的 `DetailSyncIndicator` 表达，
条目级云图标在这里一律是假的。

### 类型收窄是这次修复真正的保险

`synced: Boolean` → `synced: Boolean?` **不是**为了少写一个 `if`：
它把"这个库没有云"变成**类型上无法忽略**的事实。今后再往 `ItemRow` 里加调用方，
传 `true` 就得先解释"为什么这个库有云端" —— 编译器会替我们问这一句。

### 单测

`CloudSyncBadgeTest`，6 条。其中一条是**穷举**：

```kotlin
for (kind in VaultKind.entries) { ... 除 BITWARDEN 外必须全是 null ... }
```

新增 `VaultKind` 时它会立刻红，逼后来者先想清楚"这个库有没有云端"。

## 264. 库列表把 OneDrive 上的 KDBX 显示成「本地文件」—— 同一份判据存在两份（2026-11-10，真机反馈）

**现象**：库列表里，OneDrive 上的 KDBX 库 `uit` 副标题是「本地文件 · uit」。
用户原话：

> 库列表，这两个显示是对的，但是处于 onedrive 上的 kdbx，在这里也会显示出本地文件，这样不对吧

（「这两个」，指上面 Bitwarden 显示邮箱、本地库显示本地文件 —— 那两条是对的。）

### 根因：`VaultOriginLabel.kt` 写了一套，列表页又自己写了一套

`ui/common/VaultOriginLabel.kt` 里有完整实现，按 origin 前缀分三种：

```kotlin
fun vaultOriginLabel(vault) = when (vault.kind) {
    BITWARDEN -> serverHostOf(vault.origin)
    KDBX -> kdbxSourceLabel(vault)          // 本地文件 / OneDrive · 路径 / WebDAV · 主机与路径
}
```

而库列表页 `VaultListScreen.vaultSubtitle()` **没有用它**，自己判了一遍：

```kotlin
// 改前
@Composable
private fun vaultSubtitle(vault: VaultSummary): String = when (vault.kind) {
    VaultKind.KDBX -> stringResource(R.string.vault_card_kdbx_subtitle, vault.name)  // 「本地文件 · %s」
    VaultKind.BITWARDEN -> vault.account ?: vault.origin
}
```

**KDBX 这一支是无条件的** —— 不管 origin 是 `content://`、`onedrive:` 还是 `webdav:`，
一律显示「本地文件」。而它的注释还写着：

> ⇒ KDBX 一律取**文件名**，并标注「本地文件」让用户一眼知道它不在云端。

⇒ 对 OneDrive 库来说，这句话**本身就是假话**。

### 为什么这类 bug 特别难发现

| 现成的门禁 | 为什么查不到 |
|---|---|
| 编译 | 语法完全正确 |
| 单测 | `vaultSubtitle` 是 `private @Composable`，纯 JVM 测不到 |
| 资源检查 | `vault_card_kdbx_subtitle` **确实**被引用了，不是孤儿 |
| 页面截图回归 | 需要**恰好在一个 OneDrive 库上**看库列表 |
| 人工 review | 两处都"看起来各说各的合理"，因为**看的是不同的页面** |

而密码页的库状态行走的是 `vaultOriginLabel`，**是对的** ——
同一个库在两个页面叫两个名字，这本身就是 bug 的信号。

### 修法

```kotlin
@Composable
private fun vaultSubtitle(vault: VaultSummary): String = when (vault.kind) {
    VaultKind.KDBX -> vaultOriginLabel(vault)     // ← 复用唯一真值源
    VaultKind.BITWARDEN -> vault.account ?: vault.origin
}
```

Bitwarden 那一支**保持不变**是有意的：库状态行要的是「服务器地址」，
卡片要的是「账号邮箱」，这是两页任务的差异，不是重复判据。

### 新增门禁：`check_kdbx_origin_single_source.py`

静态扫描 `ui/` 下**除 `VaultOriginLabel.kt` 之外**的所有 `.kt`：
`VaultKind.KDBX ->` 分支体内不得出现
`vault_card_kdbx_subtitle` / `vault_origin_onedrive` / `vault_origin_webdav`。

已接进 CI（`android-ci` 的 `Check KDBX origin single source` 步骤）。
**做过反向验证**：把旧写法注入回去，脚本退出码 1 并指出文件行号；还原后通过。

### ★ 判据

> **凡是"某个值该显示成什么"的映射，全项目只能有一份实现。**
>
> 出现第二份时，两份**都不会报错**，只是慢慢地一个页面说 A、另一个页面说 B。
> 这类 bug 的表现永远是"某个特定组合下显示错一个词"，人工回归极难覆盖，
> 所以要么收敛成一份，要么加静态门禁 —— 不能靠"记得两边一起改"。

同族的既有教训：`#95`（`content://` 泄漏给用户）、`261`（判脏基线两份口径）、
`VaultCardInfo` 的 KDoc 里那句「两处共用是刻意的……各拼一遍必然漂移」。

### 一个**没改**的已知问题（记录在此，不在本次范围）

「本地文件 · uit」里的 `uit` 是**库名**，不是**文件名**。
`VaultSummary` 没有"文件名"字段（`name` 就是库名），所以本地库无法显示磁盘上的真实文件名 ——
而上一轮修完 `#262` 之后，文件名已经跟着库名走了，二者通常一致，不一致时（用户在系统面板里改过名）
这里仍会显示库名。

真要修需要给 `VaultSummary` 加字段并在 `addKdbxVault` 落库时保存 SAF 显示名，
涉及数据模型与迁移，且收益有限（多数情况二者相同）。**先记着，不改。**

### 单测
