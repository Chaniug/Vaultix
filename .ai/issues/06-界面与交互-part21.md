## 283. 深色模式光照重构 + 三组 M3 观感整改（2026-11-12，用户反馈）

### 用户原话

> 有几个问题需要继续优化
> 1. 主题模式里面的取消按钮的大小和 ui 与 material3 风格不匹配，同款的取消按钮在其他位置好像也存在问题，修复它们。
> 2. 显示里面按站点分类后，站点分类后面有个数字点，比如 baidu.com 有 2 条，后面就是数字 2 显示，这个数字的 UI 很不好看，给人一种要点击的感觉，强迫症受不了，能优化它吗，不要这么显眼。
> 3. 深色模式下，常态的底栏以及添加条目里面的剪影卡片显示效果不太好，色彩搭配有点怪，很多文案都显示不清晰。你按照深色模式的规范进行优化。底栏是周围的光照与深色模式对比存在问题，感觉深色模式下，常态化底栏和开启液态玻璃后，底栏外围有点脏脏的。仔细看看优秀的项目是如何处理的，完善底栏的效果。

三组反馈，**全部改了生产代码**。第 3 组明确要求「仔细看看优秀的项目是如何处理的」
⇒ 本轮先做规范取证、再动手调参，并把取证结论写进代码 KDoc（不是凭感觉改 alpha）。

### ⚠️ 判据反转 / 不反转对照

延续 #282 的「**判据不是誓言**」：用户最新反馈覆盖旧结论时反转并写明；没覆盖的旧结论
**也不能顺手推翻**，要在文档里记一句「为什么不动」。

| 点 | #282 判据 | #283 | 理由 |
|---|---|---|---|
| 单选项对话框「取消」**必须有边框** | `DialogStyleRulesTest` 规则 1 | **不反转** | 用户只说「大小 / UI 不匹配」，没说不要边框；改的是宽度与 padding |
| 分组计数收进 `tertiaryContainer` 小胶囊 | `ItemsRowStyleTest` 规则 3 | **反转作废** | 高对比彩色圆点在 M3 里读作 chip / badge，凭空造了第二个假点击目标 |

### 第 1 组：主题模式「取消」按钮的 M3 尺寸规格（全项目排查）

**根因**：#273 修的是「两个字逐字竖排」——`AlertDialog` 动作槽传 `indentChar` 导致
裸按钮在 `IntrinsicSize.Max` 下测得 0，被 `ButtonDefaults.MinWidth` 兜到 58dp。当时的修法是
共用组件统一加 `width(IntrinsicSize.Min)`。但那**只解决了撑宽 / 竖排，没解决「太窄」**：
`width(IntrinsicSize.Min)` 把按钮宽压到 `minIntrinsicWidth`（中文按单字断行 ⇒ 只够一个字
+ 内边距），而 M3 按钮的 `MinWidth` 下限在这条链里被 `fixedWidth` 约束吃掉
⇒ 孤零零一个「取消」读起来像贴字小胶囊，不像 M3 按钮。

**修法**（`DialogActionButtons.kt` 一处）：

```kotlin
private fun Modifier.dialogActionWidth(): Modifier =
    this.widthIn(min = ButtonDefaults.MinWidth)   // #283：先把父约束下限抬到 M3 64dp
        .width(IntrinsicSize.Min)                // #273：intrinsic 实现一点没丢
```

⚠️ **顺序不能反**：`IntrinsicSizeModifier` 会把算出的宽度 `coerceIn(minWidth, maxWidth)`，
只有让父约束先带上下限，`width(IntrinsicSize.Min)` 才会被托到标准宽度；反过来写，
前一步产生的 `fixedWidth` 会把后面的 `widthIn` 钳掉。两个按钮另外显式声明
`ButtonDefaults.ContentPadding` / `ButtonDefaults.TextButtonContentPadding`。

**全项目排查结论**：Grep 所有 `AlertDialog` 的 `confirmButton` / `dismissButton`，
**22 个文件、60+ 处动作槽全部**走 `DialogTextButton` / `DialogOutlinedActionButton`，
零裸 `TextButton` / `OutlinedButton` 漏网 ⇒ 改共用组件一次即全量生效，
**不去 20+ 调用点打补丁**（#120/#193/#195 已栽过三次「同一规则写两处」）。

⚠️ **`DialogShell` 家族刻意不动**：它用 M3 原生 `Button` / `OutlinedButton`（自带
`MinWidth`）、走 `FlowRow`，**不吃动作槽的 intrinsic 缩进**，不会复现此问题；它的
`DIALOG_BUTTON_PADDING = 16dp` 是 11-06 真机「三按钮弹窗被挤出可见区」后刻意从
24dp 收的一档，理由写在注释里。⇒ 「同款按钮」= 共用组件的调用点，不是这一套。

门禁：`DialogStyleRulesTest` 新增**规则 4**，扫共用组件源码钉住 `widthIn` 在
`IntrinsicSize.Min` 之前、后者不许删、两种 `contentPadding` 必须显式声明。

### 第 2 组：站点分组计数「不要这么显眼」

**根因**：#282 把计数做成了 `tertiaryContainer` + `CircleShape` + `padding` 的高对比
小圆点。在 M3 里这套视觉语言就是 **chip / badge**，天然带可点击暗示；而分组头唯一的
点击目标是**整条 Row**（箭头与 `stateDescription` 已表达），等于凭空造了第二个假目标。
用户原话「给人一种要点击的感觉」判得很准。

**修法**：计数退回 `onSurfaceVariant` 的纯 `labelSmall` 文字，**无容器底 / 无形状 /
无内边距**；标题 `weight(1f)` 右对齐保留 ⇒ 扫读「这组几条」的能力不变，视觉噪音归零。
整条 `GroupHeader` 的 `surfaceContainerLow` 容器底**保留**（它是「分节」，不是 chip）。
零新增 State / 动画 / 层级，不增加性能开销。

⚠️ **反转门禁**：`ItemsRowStyleTest` 规则 3 从「计数收进 tonal 胶囊」改为
「计数低调无点击暗示」——断言整个 `GroupHeader` 只许有 **1 个** `.background(`，
且 `count.toString()` 之后的块禁止 `.background(` / `CircleShape` / `.padding(` /
`tertiaryContainer`；旧的「必须有 CircleShape」同步作废。KDoc 写明反转理由，
不留旧结论当现行判据。

### 第 3 组 A：深色下「+」剪影卡片色彩怪 / 文案不清晰

**三条根因**（`AddActionSheet.kt`）：

1. `AddTypeTile` 用 `palette.tint`（`primaryContainer` / `secondaryContainer` /
   `tertiaryContainer`）作底，`contentColor` 却是 `onSurface` —— **M3 规定容器底必须配
   `onXxxContainer`**，深色下两者亮度分叉最大，卡上的类型名与剪影线条同时发灰；
   `Surface` 的 `contentColor` 会传给 `LocalContentColor`，`Text` 默认取它 ⇒ 这就是
   「很多文案都显示不清晰」。
2. 卡底 `0.68` + 剪影底 `0.62` 两层半透明叠在近黑 `surface` 上 ⇒ 三个暗色混成浑浊灰，
   五个色系全糊掉（「色彩搭配有点怪」）。M3 深色规范是层次靠**表面色阶**表达，
   不是靠半透明叠色。
3. 剪影线条 `onSurfaceVariant × 0.34` 压在深色 wash 底上对比不足。

**修法**：`GlyphPalette` 从 3 字段扩到 5（`accent / tint / wash / onTint / onWash`）；
`glyphPalette()` 为每种类型给出配对的 `onXxxContainer`；深 / 浅两档叠色强度与线条
alpha 分开取（`TILE_ALPHA 0.68 → 0.94`、`WASH 0.62 → 0.92`、`LINE 0.34 → 0.62`，
生成器卡浅色沿用 `0.58`、深色与类型卡共用 `0.94`）；深色线条改从 `onWash` /
`onTertiaryContainer` 取色。

⚠️ **判深浅复用 `isDarkSurface(surface)` 按实际底色亮度，不用
`isSystemInDarkTheme()`** —— 本 App 有独立「主题模式」（浅 / 深 / 跟随系统）、OLED 纯黑
与动态取色，按系统判会错档。⚠️ **不硬编码任何色值**，全部取自 `colorScheme`。
⚠️ **浅色档 4 个数值一个没动**（#282 刚按用户反馈调活泼，本轮只处理深色）。

门禁：新建 `AddActionSheetStyleTest` 3 条文本规则 —— ① container/onContainer 配对；
② 按底色判深浅 + 深色画纯叠色 + 线条取配对前景；③ 深色档强于浅色且浅色档保持
#282 原值（防「修深色顺手把浅色也调了」）。

### 第 3 组 B：深色底栏「外围脏脏的」—— 优秀项目是怎么处理的

用户要求「仔细看看优秀的项目是如何处理的」，取证三条规范并写进 `LiquidGlass.kt` 文件头：

| 来源 | 结论 |
|---|---|
| Material 官方 **Dark theme** | 深色下 elevation 靠**表面色阶**表达（越高越亮），明确 *"Don't use light glows in place of dark shadows"*；M3 elevation 规则把自定义 `Modifier.shadow(8.dp)` 列为反模式（`Surface(tonalElevation)` 才是正解） |
| iOS 26 / Apple **Liquid Glass** 设计资源 | 深色玻璃 tint / stroke 用 `white 0.10` 一类低强度；specular 高光**从 0.1–0.2 起步**；阴影 keep mild（`shadowOpacity 0.12`）；并直接警告「blur + tint + gloss + shadow + stroke 全开满 ⇒ card turns into muddy gray」 |
| 玻璃拟态深色口径 | 面板白仅 5%–12%；玻璃自身保持中性，亮度来自背后内容；顶边受光 / 底边背光但必须克制 |

**对照本项目，恰好三者全开满**：`sheen = Color.White` 配 `0.48` 上沿高光 / `0.62`
镜面 rim、`Color.Black` 3dp 内阴影与下沿渐晕、外层 `8dp` 黑 elevation 阴影
⇒ 近黑底上白边刺眼，黑外影与黑内阴影连成一圈灰黑脏晕。而且它**同时命中常态磨砂
（`Frosted`）与液态玻璃（`Liquid`）** —— 因为三种装饰是两档共用的，这解释了用户为什么
说「常态化底栏和开启液态玻璃后」都脏。

**修法：引入深色光照档，一处定义、全链路一致**（不是逐处调 alpha）：

```kotlin
private fun glassLighting(darkTheme: Boolean): GlassLighting = if (darkTheme) {
    GlassLighting(DARK_SHEEN_SCALE, DARK_SHADE_SCALE, DarkShadowElevation)
} else {
    GlassLighting(1f, 1f, ShadowElevation)   // 浅色档一个数值没动
}
```

| 量 | 浅色（不变） | #283 深色 | 依据 |
|---|---|---|---|
| `sheenScale` | 1.0 | **0.35** | 0.48 → 0.17、0.62 → 0.22，落进 Apple 建议的 0.1–0.2 起步区间 |
| `shadeScale` | 1.0 | **0.45** | 3dp 黑内阴影 / 下沿渐晕 / `RIM_LINE_ALPHA` 统一收敛，保留「上淡下暗」方向感 |
| `shadowElevation` | 8dp | **2dp** | Material「深色 elevation 靠表面色阶」；本项目已用 `surfaceContainerHigh` |
| `style.sheen` 色相 | `Color.White` | **`Color.White`** | 收敛强度不改色相，既有单测继续钉住 |

- 所有白色高光改走 `style.sheenAt(...)`、所有黑色暗部改走 `style.shadeAt(...)`，
  **8 处白 + 3 处黑**全部接线（6 个绘制函数 + 布局层），不留一处绕开缩放的死常量；
  `RimLineColor`（Color）改成 `RIM_LINE_ALPHA`（标量）正是为此。
- `VaultixBottomDock.kt` 的 `.shadow(elevation = LiquidGlass.ShadowElevation, …)` 改成
  `glassStyle.shadowElevation` ⇒ 绘制层与布局层读**同一个值**。
- ⚠️ **不回退 #282**：真模糊两档仍不画整圈 `style.stroke`；填充 / 描边 / 模糊半径 /
  内阴影**宽度** / `SHADER_CLARITY` 一个没动；改的只是颜色 alpha 与外圈阴影高度。
- ⚠️ **不新增第三套材质**：仍走 #281 的 `Frosted` / `Liquid` 两档与同一条
  `LiquidGlassLayer` 采样链路，只在 `LiquidGlassStyle` 上多带三个绘制参数。

门禁：`LiquidGlassTest` +2 条数值用例（色相不变 / 强度收敛 / 落在规范区间 / 阴影档位），
`LiquidGlassDockRulesTest` +**规则 12**（绘制层禁止 `style.sheen.copy` /
`Color.Black.copy` / `RimLineColor`，必须走 `sheenAt` / `shadeAt`；三档必须经
`glassLighting` 一处定义并全接进 style；底栏阴影不许写死 8dp）。

### 本轮踩的坑（别记成代码红）

1. **常量类型变更必须全链路同步**：把 `RimLineColor: Color` 改成
   `RIM_LINE_ALPHA: Float` 后，`drawSpecularRim()` 里旧引用会让代码**编译不过**。
   接力时一度停在「常量已加、绘制函数没接」的半成品状态 —— 这类「先改定义后改调用」
   的中间态不要留到下班，先让编译绿再继续。
2. **`functionBody()` 从 `{` 起，不含参数列表**：新门禁里写
   `glyph.contains("dark: Boolean")` 必然失败（那是**测试自己写错**，不是生产代码问题）。
   补了 `functionSignature()` 单独查签名。同类坑见 `DialogStyleRulesTest` 的
   `stripComments()` 说明。
3. **管道会吞掉 Gradle 退出码**：`./gradlew … 2>&1 | tail -N` 失败时整体 rc 仍是 0
   （tail 成功），后台任务显示 `exit code 0` 但日志里是 `BUILD FAILED`。
   ⇒ 一律 `set -o pipefail; … | tail -N`。
4. **detekt `CyclomaticComplexMethod ≤14` 撞了两次**：
   - 生产侧 `liquidGlassStyle` 原已两组 `when`，再塞三个 `if (darkTheme)` ⇒ 复杂度 15；
     抽出 `glassLighting()` 一次性返回三档（顺带满足「一处定义」的设计意图）。
   - 测试侧规则 12 的 `buildList { … }` 堆了 12 个 `if` ⇒ 复杂度 18，把**用例本身**判红；
     拆成 `lightingDrawIssues()` / `lightingWiringIssues()` 两个小 helper。
   ⚠️ 与本文件 `stripComments()` 拆小函数是同一条纪律：**门禁代码自己也要过门禁**。
