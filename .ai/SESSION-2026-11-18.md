## 0. 一句话结论

**Vaultix 与 Bitwarden 的自动填充差距不在打分算法，在「不匹配时怎么办」的默认值。**
打分五项分数、包名 120 分抄得已经接近；真正的差距是四层默认值：分区（先判表单类型）、
焦点窗口（只出当前那一屏）、`uri == null` 不给密码候选、blocked URIs。
一句话：**Bitwarden 的默认值是「少给」，Vaultix 是「多给」**——误弹全从这取向差出来。
通行密钥侧则是一个纯格式缺口：Bitwarden SDK 的 credentialId 有 `b64.` 前缀形态，全仓零处理。

## 2. 根因 / 约束

### 2.1 包名匹配被两道闸门挡住（这章回答：为什么 androidapp 条目命中不了）

`AutofillRequestContextPolicy.allowPackageMatching` 第二行 `if (isWebView) return false`
一刀切禁掉 WebView 场景的包名匹配；而 Bastion 原实现有 `allowExactPackageMatching(...,
webScheme)`——`file://` 的 WebView 且非已知浏览器时**重新放行**精确包名。Vaultix 只搬了前者，
且 `ParsedStructure.webScheme` 恒 null（从未读 `ViewNode.getWebScheme()`）⇒ App 内嵌 H5
（X5 / System WebView）登录页永远匹配不到自己的 `androidapp://` 条目。

第二条断点：包名只从 `activityComponent` 取，Bitwarden 是三级兜底
（`ViewNode.idPackage` → window title 的 `pkg/Activity` → `activityComponent`）；
`activityComponent` 为 null 时整条包名链失效。

⚠️ `AutofillRequestContextPolicyTest` 曾把这条缺陷写成规格
（`com.unknown.app` + WebView + 无域名也断言 false），修它必须先改测试。

### 2.2 误弹是「多给」取向（这章回答：为什么面板会列出整库别人的密码）

`AutofillCandidateSource.matchLogins` 的 `orderWithoutDomain` 降级本为 Firefox 设计，
但判据只有「没有域名」，没区分「浏览器拿不到域名」与「原生 App 本来就没有域名」
⇒ 任何没存 `androidapp://` 条目的 App 里都会按收藏/名称列出整库登录项。
Bitwarden 在 `uri == null` 时直接返回 0 条。

放大因素：包名又被 2.1 挡掉 ⇒ 在 App 内 H5 登录页时，**自己的条目不在列表里，
列表里全是别的站点密码**。另两个入口：解析全部 window 而 `isFocused` 采集后零消费；
页面出现 NAME/PHONE_NUMBER/POSTAL_CODE 就无条件列全库身份。

### 2.3 实测：内网 IP 互填与非域名规则失效（这章回答：哪些是量化可证的错）

本地无 Gradle，但用 JDK 把纯函数照原样复刻（非项目编译，只验算法）：

- `baseDomain("192.168.1.1") == "1.1"`、`baseDomain("172.16.1.1") == "1.1"`
  ⇒ 两个不同内网 IP 被判成同站。Bitwarden（IP 直接返回 host）/ Bastion
  （`AutofillHostPolicy.isIp` 守卫）都防了，只有 Vaultix 没有。
- `hostOf` 丢端口 ⇒ `localhost:8080` 与 `:9090` hostMatch 为真。
- 比对串硬编码 `https://<host>`：存 `https://example.com/login` 的 StartsWith = false；
  存 `http://example.com` 的 Exact = false；正则 `^https://.*` 永不命中。
- 等价域比原串，`www.google.com` 与组里的 `google.com` 不等价。

### 2.4 credentialId 的两种存储形态（这章回答：为什么 Bitwarden 同步来的通行密钥登不上）

Bitwarden `802427a`（PM-44191）暴露 SDK 约定：`b64.<base64url>`（新）或 `<uuid>`（旧）。
Vaultix `WebAuthn.rawIdFromStored` 只识别 UUID 与合法 Base64，全仓 grep `b64.` 零命中。
遇到带前缀的 ID：不是 UUID → 跳过；含 `.` 解不了 Base64 → 跳过；
落到兜底 `base64Url(text.toByteArray())` ⇒ 把整串文本当字节发出去，RP 必然拒绝。

同源问题：`allowCredentials` 解码成字节比较，`excludeCredentials` 走原串相等
（`PasskeyExcludePolicy.firstConflict`）⇒ UUID 存储形态永远排除不中，
用户在同一 RP 重复注册时挡不住。

## 3. 做法

### 3.1 自动填充七处（commit `3f1eff36`，11 文件 +424/−53）

1. `AutofillRequestContextPolicy`：新增 `isKnownBrowser` / `allowExactPackageMatching`
   （`file://` 本地 H5 的精确包名例外，照搬 Bastion 语义）/ `allowDomainlessFallback`
   （仅已知浏览器）。
2. `AutofillCandidateSource`：包名闸改「宽松 ∪ file:// 例外」；降级加浏览器白名单。
3. `AssistStructureParser`：包名三级兜底（activityComponent → idPackage → window title，
   标题要求含 `/` 且前缀含 `.`）；`webScheme` 真正采集；按 window 分开解析 +
   `chooseWindow` 只取「有焦点且有凭据字段」的窗口；删 `firstWebDomainOf/findWebDomain`。
4. `BitwardenLikeAutofillMatcher`：`match()` 增 `webScheme`（默认 null = https）；
   内部 `MatchTarget` 收参；`exactDomainOnly` 关掉 StartsWith/Exact/Regex（包名 URI 不受影响）。
5. `UriMatcher.pageUri()`：`scheme://host` 唯一真源（匹配器 + 解析器共用）。
6. `EquivalentDomains`：先归一基域再查组表（修 `www.` 失效），同基域不冒充等价域。
7. `PublicSuffixList`：IPv4 字面量原样返回（修两个内网 IP 互填）。

测试 +12 例（policy 4 / matcher 3 / equiv 2 / psl 3，含畸形 IP 回落）。

**刻意没做**：`EXACT_APP_TITLE` 应用名模糊匹配（与「精准」相反）；端口区分（目标侧无端口）；
保存链路（compat 掩码 / 空密码覆盖，属数据完整性另开一批）；manifest
`supportsInlineSuggestions` 改 false（会污染这轮真机判读）；屏蔽列表（另批）。

### 3.2 通行密钥统一 codec（commit `99cb459e` + `b83bd9d2`）

- `WebAuthn.rawIdFromStored` 增 `b64.` 前缀分支；`describeStoredIdForm` 增 `b64` 档
  （日志 `storedIdForm=b64` 可取证）。
- allow / exclude / 断言三处统一按字节比较；`parseAllowedCredentialIds` /
  `excludedIds` 共用 `credentialDescriptorIdOrNull`，都校验 `type=public-key`（缺失宽容）。
- detekt 插曲：循环内两个 `continue` 触发 `LoopWithTooManyJumpStatements`，重构成
  单出口的 descriptor 解析函数后过。
