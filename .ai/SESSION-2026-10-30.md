## 1. 先把「从不」这件事说清楚（这是本轮的认知核心）

用户说「我感觉 app 清掉后台或者锁屏后，指纹解锁是正确的方案」—— **这个判断是对的**，
但它对应的档位**不是「从不」**：

| 想要的效果 | 档位 | 代码依据 |
|---|---|---|
| 清后台 / 熄屏回来要指纹 | **`OnAppRestart`（重启 App 时）** | `checkForVaultTimeoutInternal` → `AppCreated(firstTime)` 分支锁 |
| 进程被清掉也不用验证（免交互恢复） | **「从不」`Never`** | 同上 → `Never -> return@launch`，且 `AutoRestoreTrigger` 用免认证信封开回 |
| 连切一下后台回来都要验证 | `Immediately` | `AppBackgrounded` → 延迟 0 分钟 |

`screens` 里能看出区别：`设置 → 锁与安全 → 自动锁定` 那行的**副标题**就是当前生效档位。

⇒ 所以「两个包都是「从不」，却一个锁一个不锁」**按代码不可能**（同一条
`VaultTimeoutPreferences`，同一份 `AutoRestoreTrigger`）。判断只能是这两类之一：

1. **实际档位不同**（覆盖安装后偏好没跟过来，或某一包停在「重启 App 时」/「立即」）；
2. **那一次不是超时锁**：主页锁按钮 = 查看层锁（解锁页只剩指纹按钮），
   或指纹门锁待重装（解锁页报"需要重新启用"）。

**没有改 `Never` 的语义。** 那是 2026-09-29 二次定稿（用户三次拍板对齐 Bitwarden），
`VaultLockManagerImpl` 的 KDoc「为什么推翻」写了整整一屏。

## 2. 日志两问的答案

### 2.1 内容要不要优化

**上一轮（#206）已经做了**：抽了 `LogScrubber`，把脱敏从"只挂在导出出口"改成**采集即脱敏**，
并把 `E/F` 兜底收窄为「**且**含 `vaultix`」——原先那个 `|| level in "EF"` 等于把白名单架空
（logcat 里 E/F 绝大多数是系统噪声，全部放行）。本轮只补了一处语义（通行密钥 type 串，见 §3）。

真要再优化，方向**不是脱敏**，是**过滤范围**：`shouldKeep` 的 tag 白名单还可以更精确地
"只留自己的 + 崩溃"，代价是跨进程排查时线索更少。当前取舍（留 `Vaultix|Credential|KeyStore|
Biometric|AndroidRuntime|FATAL`）是刻意偏宽的，没动。

### 2.2 会不会拖性能

| 构建 | 结论 | 依据 |
|---|---|---|
| release | **零开销** | `VaultixLog.install(enabled = BuildConfig.DEBUG)`；`enabled=false` 时 `emit()` 在**拼字符串之前**返回（消息是 `() -> String`）。`AutofillLogger.d` 也是 `if (BuildConfig.DEBUG) Log.d(...)` |
| debug | 每次调用 = 一条 `Log.d` | 系统环形缓冲，**不写文件、无同步 IO、无磁盘配额**；`VaultixLog` 另有每 tag 60s/50 条的限频 |
| 打开日志对话框 | 一次 `logcat -d -t 1200` | 在 `Dispatchers.IO`，只在**点开/刷新/清空**时跑；`-d` 是 dump 后立即退出，不常驻 |

⇒ 真正会拖慢的写法只有两种，项目里都没有：① 常驻 `logcat` 进程流式读；
② 往自己存储写文件日志（还占盘、还要清理）。

### `OnAppRestart` 分支的最终形态

```kotlin
VaultTimeout.OnAppRestart -> {
    if (reason is CheckTimeoutReason.AppCreated) {
        if (reason.firstTimeCreation || !reason.createdForAutofill) {
            if (devRelaxScreenLockEnabled()) handleTimeoutAction(vaultId)
        }
    }
}
```

**只**拦这一档。`Never`（本来就 return）与 `N 分钟`（走定时器）都不碰 —— 否则会造出
"开发者开关把 5 分钟档也关掉了"这种只在 debug 出现的分叉，且单测和产品语义会分家。

### 为什么偏好写口是 `var` 而不是 `suspend fun`

`VaultixPreferences` 已经 **40 个函数**（detekt `TooManyFunctions` 硬上限，`OnboardingPreferences`
的 KDoc 记着这条）。所以：

```kotlin
val devRelaxScreenLock: Flow<Boolean> = safeData.map { it[DEV_RELAX_SCREEN_LOCK] ?: true }

@set:JvmName("setDevRelaxScreenLock")
var writeDevRelaxScreenLock: Boolean
    get() = error("write-only，只用于写")
    set(value) { writeScope.launch { dataStore.edit { it[DEV_RELAX_SCREEN_LOCK] = value } } }
```

代价：写是异步的（`writeScope` = 应用级 `SupervisorJob + Dispatchers.IO`）。对这个键无所谓
（只影响"下次锁不锁"）。**但别再往这个类加函数** —— 下一把要么抽子类，要么用同样手法。

## 4. 两个 CI 编译错误（`41033038640` ❌）—— 都是我的想当然

| 报错 | 我的错误假设 | 真相 |
|---|---|---|
| `SettingsViewModel:457 Unresolved reference 'setDevRelaxScreenLock'` | 以为 `@set:JvmName("setDevRelaxScreenLock")` 之后就能用 `prefs.setDevRelaxScreenLock = …` | **Kotlin 的成员解析永远用属性名**，注解只改 JVM 方法名（给 Java / 反射看）⇒ 必须写 `prefs.writeDevRelaxScreenLock = …` |
| `PasskeyCreateActivity:406 Cannot access 'TYPE_CREATE_PUBLIC_KEY_CREDENTIAL_INVALID_STATE_ERROR': it is internal` | 以为 `javap` 看到 `public static final` 就是公开 API | **`javap` 的 `public` ≠ Kotlin 的 `public`** —— Kotlin 侧声明是 `internal`，编译期就拒 |

修法：① 改用属性名；② type 串改成文件私有常量 `INVALID_STATE_ERROR_TYPE =
"androidx.credentials.TYPE_INVALID_STATE_ERROR"`（值不变，仍不是裸写的类名 `"InvalidStateError"`）。

**新判据（进 MEMORY §9）**：
- `@get:/@set:JvmName` 只影响 Java/反射，Kotlin 侧调用永远用属性名；
- 依赖里的常量"能不能用"要看**Kotlin 可见性**，`javap` 只证明 JVM 签名；
- **relaxed mock 的 `Boolean` 恒 `false`** —— 新开关 `true`=安全侧时，正向用例会**静默变绿**
  （`OnAppRestart` 那条"锁没发生"被测成"没锁"，正好也是绿）。必须显式 stub。

## 6. 第三轮（同日晚）：#210 的开关"点了没反应"（#212）

### 用户原话

> 「保持不锁的按钮无法点击」（附截图，1256px 宽 ≈ 393dp）

### 排查顺序（这次没走弯路，值得记）

1. **先排数据流**：`setDevRelaxScreenLock` → `writeDevRelaxScreenLock` → DataStore →
   `devRelaxScreenLock` 回流，链路上一轮已由 3 条单测钉住 ⇒ 不是数据问题。
2. **再看这一行有没有别的热区**：`SettingsRow` 这一行**没传 `onClick`**（有意为之，
   改锁的开关不该"点哪都生效"）⇒ 整个行只有行尾开关能点。
3. **最后量开关本身**：M3 `Switch` 画出来 52×32dp，`toggleable` 的命中框**就是**这 52×32dp。
   Material 要 ≥48dp，`Switch` 自己不补。

### 第一版修法错了（这次没进 CI，靠读源码拦下来的）

第一版写的是 `Box(...).pointerInput { detectTapGestures(onTap = {}) }` 再套
`Modifier.minimumInteractiveComponentSize()`。两个问题：

- `pointerInput { detectTapGestures }` 那层**什么都不做** —— 它既不吃事件也不放大热区；
- `minimumInteractiveComponentSize()` 对 `Switch` **完全无效**：它只是**提供**
  `LocalMinimumInteractiveComponentSize`，而 `Switch` 的实现里**没读**这个 Local
  （读它的是 `Checkbox` / `RadioButton` / `Slider`）。⇒ 写了等于没写，真机照样点不中。

**判据**：给任何组件补触摸目标前，先去它的源码里确认它**读不读**
`LocalMinimumInteractiveComponentSize`。不读的（`Switch` 就是），只能靠**占更大的布局格子**。

### 最终修法

| 文件 | 改动 |
|---|---|
| `SettingsComponents.kt` | 新增 `SwitchWithTouchTarget`：`BoxWithConstraints(width = 52dp)` → 内层 `Box(width=52dp, height = 48dp或行高)` 居中放内容；`SettingsSwitch` 内置调用它（13 个调用点一次修好）；文件头补"上游漏了触摸目标"一条 |
| `QuickUnlockDialogs.kt` | `CapabilityToggle` 的"未知 / 开 / 关"三分支都套同一外壳；删掉 KDoc 里那句错的"[Switch] 自带最小触摸尺寸"；顺手删两个确认未使用的 import |
| `DisplayOptionsSheet.kt` | 两个开关行 `Spacing.sm` → `Spacing.md`（内容 22dp ⇒ 行高恰好 48dp，装得下热区） |

### 几个刻意的取舍

- **不做整行可点**：误触代价太高（这行改的是锁行为）；只把开关那一处做大。
- **热区上限 48dp**：`InteractiveComponentSize.kt` 的注释明说更大的可点区域会抢相邻组件的手势。
- **不做"外壳 clickable 再调一次 onCheckedChange"**：内外都收到点击 ⇒ 切两次弹回原样，
  症状还是"没反应"（这正是本 bug 最像的伪装）。
- **矮行不硬撑 48dp**：`BoxWithConstraints` 量到行高不够就按行高封顶 + `Log.w` **一次**
  （用 `remember` 挡住重复刷屏）。这条日志是"下一个人看到就知道自己那行 padding 给少了"的路标。

## 7. 第四轮（同日晚）：命中框修完仍然点不动 —— 双重取反（#213）

### 用户原话

> 「好像还是无法点击这个按钮，按钮始终是打开状态的」

**"始终是打开状态"这半句是关键线索**：如果事件根本没落到控件上，人会说"点不动"；
说"始终是打开"，说明他看到一个**确定但不变**的状态 —— 那是状态机问题，不是命中框问题。

### 真因：`f(!x) = x`

第一版把偏好写成反义（`true` = 仍需验证），UI 又取反一次：

| 步 | 值 |
|---|---|
| 偏好 | `true` |
| `Switch(checked = true)` | ON |
| 点一下 → `toggleable` 回调 `!checked` | 收到 `false` |
| 调用点 `setXxx(!false)` | 写入 `true` |
| 回流 | 仍 ON |

每次点击都把**当前值**写回去。写盘是成功的（所以偏好层单测全绿），只是写的是旧值。
而且这是**双向不动点**：初始 `false` 时同样写回 `false`。

### 为什么上一轮的命中框修复没解决问题（但也不是白做）

两个 bug **同时存在**：
1. 命中框 52×32dp < Material 要求的 48dp（#212，真实存在，`SettingsSwitch` 那 13 个调用点都受影响）；
2. 状态机恒等映射（#213，本轮的）。

修完 1 之后 2 才显形，且症状一模一样 ⇒ 很容易被读成"上轮的修复没生效"。
**教训：同一症状要多层排查，修完第一层必须重新复测，而不是假设后面没有第二层。**

### 这一轮的改法（把语义彻底翻正，不留"再补一个 `!`"的空间）

| 层 | 改动 |
|---|---|
| `VaultixPreferences` | 键改名 `dev_relax_screen_lock_v2`；语义与键名同向（`true` = 保持不锁）；默认 `false` |
| `VaultLockManagerImpl` | `if (!devRelaxScreenLockEnabled()) handleTimeoutAction(vaultId)`；读失败默认 `false`（不放松 = 锁） |
| `SettingsViewModel` | `setDevRelaxScreenLock(true)` 直接写 `true`（KDoc 写明"入参与 StateFlow 的值完全一致"） |
| `SettingsScreen` | `onCheckedChange = viewModel::setDevRelaxScreenLock`（方法引用，**没有 lambda、没有取反**）；文案换名 `desc_normal` / `desc_relaxed` |
| 测试 | 3 条锁管理用例按新语义改（`OnAppRestart` 正向用 `false`、放松用例用 `true`）；新增 `VaultixPreferencesDevRelaxTest` 3 条 |

### 为什么换键而不是沿用 `dev_relax_screen_lock`

旧键里可能有一条 `true`（用户点过、但每次写的都是旧值）。沿用旧键 + 翻转语义 ⇒
那条 `true` 升级后会突然变成"不锁" —— **一次静默的安全降级**。
换键 ⇒ 旧值被忽略，所有机器升级后一律回到 `false`（= 与正式版一致）。

### 新增的三条偏好层用例

1. 默认值必须是 `false`（写成 `true` = 给所有 debug 包静默关掉验证）；
2. 写口往返（`writeDevRelaxScreenLock` 是 fire-and-forget 的属性 setter，最容易坏成"发了没落盘"，
   UI 只表现为"开关自己弹回去"）；
3. **旧键必须被忽略**：直接往 `dev_relax_screen_lock` 塞 `true`，断言读出来仍是 `false`。

### 顺带修正的一处文档错误（我自己上一轮引入的）

上一轮我把 03 篇条数改成 25 —— 错了。真实规则见 `check_issues_index.py`：
`^## (\d+)\.(?!\d)`，`## 50.1`（更正子条）**不计入**。我的临时脚本用了 `^## (\d+)\.`，
把子条算成独立一条，于是"三处一致"其实是**三处一起错**。已回退为 24 并在篇内留了勘误。
**教训：计数的口径必须与探针一致，否则自制的"三方核对"只是自我确认。**

## 8. 第五轮（同日晚）：对齐 Bitwarden —— 「从不」档要的是**两层锁**（#214）

### 用户原话

> 「感觉这一块的逻辑可以直接参考 bitwarden 的，它的保护效果很不错，另外开启了从不锁定的设置，
> 屏幕熄屏或者清除后台后，bitwarden 好像还是会需要指纹解锁生物验证解锁。但是好像填充并不会受影响，
> 意思是开启了从不锁定，自动填充依然是生效的，只是进入 bitwarden 这个软件的时候需要验证指纹，
> 其他的不变。你仔细看一下相关的代码就知道我说的了」

### 用户说对了：读代码就看见两个洞

按用户提示去读，`Never` 档确实有**两处**"不用验证就能进去"：

1. `AutoRestoreTrigger`：`Never` + 密钥在内存 ⇒ 注册信封；进程被杀后 `Never` + 有信封 ⇒
   **`restore()` 不要求生物识别**（信封用的 Keystore 密钥不带 `setUserAuthenticationRequired`）。
   ⇒ 清后台再打开 = 一声不响地开回来。
2. `VaultixApplication` / `AutoLockController` 只调 `onAppCreated` / `onAppBackgrounded`，
   而 `Never` 分支对两者都直接 `return`。⇒ 熄屏/回前台**没有任何东西挡界面**。

### 但"熄屏就锁库"是错的解法

用户的描述里有半句最容易被忽略：**「其他的不变」**。如果按直觉加狠锁：

| 做法 | 熄屏要指纹 | 清后台要指纹 | 填充 | 要主密码 |
|---|---|---|---|---|
| 熄屏就真锁库 | ✅ | ✅ | ❌ 要重新认证 | ❌ 密钥清零 |
| **两层锁（本轮）** | ✅ | ✅ | ✅ | ✅ 不要求 |

所以缺的不是更强的锁，而是**把"密钥可见性"和"界面可见性"拆成两个开关**。

### 第二层项目里本来就有 —— 只是没人自动拉它

`viewLockedIds`（#61「查看锁」）就是"只挡界面、不动密钥"，`UnlockScreen` 已经有
`ViewLockedContent`（只画一个指纹按钮）。它一直是**手动**的（长按"锁此库"），
没有任何地方在熄屏/恢复后自动置位 ⇒ 本轮只是给它补了一个**自动入口** `AutoViewGate`，
**没有新增锁类型、没有新增"软锁"**。

### 关键设计：自动标记必须是**可区分的子集**

`viewLock(id, automatic)` 写入 `viewLockedIdsState` 的同时，把 id 记进
`autoViewLockedIdsState`（子集）。这一步不是为了好看 —— 它决定下游能不能同时满足两件事：

| 下游 | 要的行为 | 靠什么判 |
|---|---|---|
| 界面 | 自动 + 手动 **都挡** | `isViewLocked(id)` |
| 自动填充 | 只能**看穿自动**、但要**尊重手动** | `anyManualViewLocked()` + `isAutoViewLocked(id)` |

如果两者共用一个标志，自动填充只能二选一：一律认证（违反"填充不受影响"）或
一律放行（把用户手动锁的库也放行 —— **安全倒退**）。所以子集是必需的，不是冗余。

自动标记还**可被手动升级**：先自动挡、再手动锁，`automatic=false` 会把 id 从子集里减掉。
有单测钉这一个方向。

### `AutoViewGate` 的两个触发点与五个前置条件

只在这两处调用：`onScreenOff()`、`AutoRestoreTrigger` 恢复且 `opened > 0` 之后。
**普通切后台不触发** —— 复制密码→粘到别的 App 是最高频路径，在 `onAppBackgrounded` 挡界面
等于把 `Never` 变成 `Immediately`，违背本轮全部前提。

前置条件：已解锁库 → 产品开关 → 该库档位 == `Never` → **指纹可用** → 开发者不锁。
其中"指纹可用"是**硬要求**：没有指纹时"门禁"= 每次回来输主密码，比不做门禁更糟，
而且一定会被当成 bug 报回来。

⚠️ 这里的读失败**全部 fail-open**，方向与 `devRelaxScreenLockEnabled()` 的 fail-closed **相反**。
理由写在 KDoc 里：这一层管的是"要不要挡界面"（可用性），不是"要不要清密钥"（安全）；
读不到偏好就挡人 = 把人关在门外。

### 顺手补齐 Bitwarden 的档位：`OnSystemLock`

用户说"直接参考 Bitwarden"。核实后 Bitwarden **2025.11.0** 的档位里有 `On system lock`
（Android 先行，2025.12.1 全客户端）—— 也就是说 `.ai/decisions/` 里
「❌ 仍不做：锁屏即锁」这条**外部前提已经变了**，本轮补上并在决策文件里标注作废。

实现上三个坑：

1. **用 `isDeviceLocked()` 不用 `isKeyguardLocked()`**：后者在"只滑动解锁"的设备上熄屏即为
   `true`，这档会变成"熄屏即锁"，与"锁屏时"三个字不符。
2. **熄屏瞬间设备还没被标记 locked** ⇒ 300ms 后复查一次。
3. **复查要能取消**：`screenOffToken` 在 `onScreenOff` / `onScreenOn` 都自增，
   亮屏了就作废那次复查（否则刚亮屏又被锁上）。
4. **`-3` 与"负数 = 旧键的 Never"冲突**：`fromLegacyMinutes(-3)` 保留返回 `Never`，
   配一个 `assertNotEquals` 钉死；只有新键 `fromStorageValue` 认 `-3`。

## 9. 第六轮（2026-10-31）：一次指纹够所有库 —— 认证粒度对齐全局（#215）

### 用户原话

> 「进入 app 时候验证指纹怎么需要两次，两个密码库？两个密码库不应该是同一个指纹吗，
> 指纹检验一次就够了啊」

用户有两个密码库。熄屏后重进：验一次 → 进第一个库 → **切到第二个库又弹一次**。
用户的判断是对的，这是 #214 的直接后果，不是"设计如此"。

### 三个环节串起来就是"验几次 = 有几个库"

| # | 位置 | 行为 | 后果 |
|---|---|---|---|
| ① | `AutoViewGate.gateUnlockedVaults()` | 熄屏给**每个**已解锁的「从不」库各打一个 `automatic = true` | 两库 ⇒ 两个标记 |
| ② | `RootNavViewModel` | 「**任一**库带查看锁 ⇒ 收回解锁页」 | 只要剩**一个**标记，整个 UI 就停在解锁页 |
| ③ | `UnlockViewModel.completeLocalUnlock(forViewLock = true)` | 只调 `clearViewLock(vaultId)` | 只清当前库 ⇒ 剩下的标记让下一个库再验一次 |

②是"放大"环节，不是原因：它本来就是"任一库锁了就先别让人看"，这个判据没错。
错的是**③的清除范围**——它按库清，而认证本身是全局的。

> **Bitwarden 为什么没有这个 bug**：锁定态是**账号级**的（一个账号一次认证），
> 门禁与认证天然同粒度。#214 把**门禁**细化到库、却没同步细化**认证**，错位就出现了。

### 修法：新增一个更精确的方法，而不是放宽已有的那个

```kotlin
// VaultSessionManager
suspend fun clearAutoViewLocks() {
    mutex.withLock {
        viewLockedIdsState.value = viewLockedIdsState.value - autoViewLockedIdsState.value
        autoViewLockedIdsState.value = emptySet()
    }
}
```

UI 侧只改一行：`sessionRepository.clearViewLock(vaultId)` → `sessionRepository.clearAutoViewLocks()`。

两个刻意**没**选的写法（写在 commit message 和 #215 正文里，防止被后人"优化"回去）：

| 候选 | 为什么不行 |
|---|---|
| `clearAllViewLocks()` | 顺手，但会把手动查看锁一起抹掉 —— 用户锁了 A、验个指纹 A 也开了，**安全倒退** |
| `for (id in ids) clearViewLock(id)` | 还是逐库清，且**漏掉之后才出现的库**；等于把粒度错位固化进 UI |

一个额外收获：`mutex.withLock` 里是一次读-改-写，两个集合在**同一个临界区**里改，
不会出现"自动集合已清空但主集合还没减"的中间态被观察者读到。

### 判据（沉淀进 #215）

1. **认证的粒度必须与门禁的粒度对齐**。要么都全局，要么都按主体；
   一全局一按主体，立刻退化成"每个主体各认证一次"。
2. **"存储方式"不许升格成"语义"**。按库存标记是为了知道"锁哪几个库"，
   不是为了让用户按库出认证。
3. **要扩大清除范围时，正确解通常是"新增一个更精确的方法"**，而不是放宽已有的那个。
   `clearAllViewLocks()` 就在旁边、一行就能调，但它带着"连手动一起清"的语义。
4. **子集标志的第二次回报**。#214 引入 `autoViewLockedIdsState` 时，用途只是让自动填充
   "看穿自动门禁、仍尊重手动锁"；本轮它又正好是"只清自动、不动手动"的现成工具。
   ⇒ 把一个当下"看起来多余"的区分做出来，往往下一轮就还回来。
