## 二、本轮的定案（**已落代码，但真机未验**）

### 症状
锁 Bitwarden 库 → 切 OneDrive 的 KDBX 库 → 指纹 → 等 1.3–8 秒。

### 实测（Honor BKQ-AN00，`d221713` debug，5 轮）

```
read = 7692 / 1636 / 2598 / 2793 / 1177 ms     ← 读文件
open =  344 /  115 /  252 /  289 /  122 ms     ← KDF + 解析
```

| 环节 | 占比 |
|---|---|
| **read** | **≈90%+** |
| open（Argon2 + 解析） | <10% |

### 根因（逐段核实，勿再推翻）
缓存**一直是命中的**（日志「命中，不下载」；缓存文件 30701 B / meta 一致 / eTag 非空 / mtime 10-01）。
瓶颈是**判定之前那次 `stat()` 的 Graph 元数据往返**：
判定日志时间戳与 `unlock` 完成只差 **0.1–0.3 s**，而 `read` 报 1.1–2.8 s
⇒ **95% 的 read 花在 stat 上**。OneDrive 的 `/me/drive` 往返与下载 30 KB 差不多慢。

⇒ **B1 的原设计假设「stat 很快，只省带宽不省时间」在 OneDrive 上不成立**，
「保新鲜」本身成了瓶颈，**取舍反转**。

### 已落地的改法（`fa7d0bc`）
「折中」= 解锁不等 stat + 让过期**可见**：

- `CachedKdbxFileSource.read()`：**有缓存即返回**，`stat()` 丢后台
- 后台发现令牌变了 ⇒ 换缓存 + 置 `Freshness.STALE` + 上报 `KdbxSyncStatus.REMOTE_CHANGED`
  （**复用已有 `SyncBadge` 与文案 ⇒ UI 侧零改动**）
- 写入侧安全网**不动**（`write(expectedVersion)` 带 eTag ⇒ 冲突抛异常，**绝不静默覆盖远端**）
- 无缓存时仍走同步 stat（没有可牺牲的东西，失败如实抛）

**门禁五关分开单跑全绿** + **变异验证**（改回同步 stat ⇒ `HangingStatSource` 那条测试超时红）。
**CI `37219227984` = success**（`fa7d0bc`）。

### ★ 未验事项（**新会话第一件事**）
**真机从未跑过这个包。** 验收清单：
- [ ] `read` 是否降到 ~0ms（预期总耗时 0.1–0.4 s）
- [ ] 「远端有改动」角标**真的会亮**（折中的第二半，代码里有但从未真机跑过）
- [ ] 离线解锁仍可用
- [ ] 远端被改过时，保存会**报冲突**而不是静默覆盖

## 四、本轮被推翻的结论（**别再照抄**）

| 我先前的判断 | 实测 |
|---|---|
| 「KDBX 不支持通行密钥」 | ❌ KDBX 用 `KPEX_PASSKEY_*` 自定义字段承载，**本项目读侧早已实现**。真正缺的是**写回** |
| 「与项目无关，是格式限制」 | ❌ 把因果说反了：格式完全支持，是**我们没做写回** |
| 「自定义字段 `Title` 只能显示乱」 | ❌ kotpass 探针实测**真覆盖** ⇒ 库名被毁，是数据毁不是显示乱 |
| 「Argon2 每次重跑是主因，Keyguard 方案只省 4% 不值」 | ⚠️ 占比对（4–10%），但**结论错**：BW 33 ms vs KDBX 344 ms 是**用户能感觉到的差距** ⇒ B2 该做 |
| 「缓存没被调用，是挂载盲区」 | ❌ 缓存一直命中，慢在 `stat()`（见 §一） |
