## 1. 施工主线（8 刀 —— 见接力文档清单，这里只记取舍）

### 取舍 1：`isHouseKeyReady` 为什么是**非 suspend**

它是给控制器「在问主密码**之前**做前置判断」用的：那一步在 `Dialog.Configure` 提交后的
同步判定期，读内存字段即可，**不该为它开一次协程或 IO 切换**。
KDoc 里写明「读内存字段、不落盘」—— 免得后来有人把它改成「去读一次信封再解密」，
那就把房钥匙的明文化危机又造了一遍。

### 取舍 2：清理时机**不放在** `LegacyQuickUnlockCleanup` 里

一开始想让它自己判「能不能清」。否掉：**它没法知道本次会话有没有建成房间**
（那是控制器的编排信息）。让它只提供 `hasLegacyRemains` / `clearLegacyRemains`，
判定权留给 `QuickUnlockController.finish()` —— 「新体系真站起来才清」。
这也让清理器**可单测**（8 用例无需任何编排上下文）。

### 取舍 3：`finish()` 里三件事的顺序 = 「不半新半旧」的落点

```
回退（若需要）→ 出报告 → 清旧残留（若本次建成了房间）
```

- 报告必须在回退**之后**出，否则会谎报「门锁已开」；
- `_legacyRemains` 清完**重新查一次**而不是直接置 `false`：
  清没清干净是**事实问题**，置 `false` 就是把「其实没删掉」演成「已清理」（谎报状态那一族）。

### 取舍 4：`removeLegacyQuickUnlockKeys(emptySet())` 不该调（被测试逼出来的真问题）

单测「只删旧前缀下的键」红了一次。查下来不是测试写错了，是**生产代码无条件调了一次
空集删除**：白开一次 DataStore 写事务（改文件、跑 fsync，一个字节没变），
且让「没有残留」和「清掉了残留」在调用轨迹上**无法区分**。
⇒ 加 `if (prefKeys.isEmpty()) 0 else …` 守卫。**这条属于「测试逼出了设计问题」，不是「改测试迁就代码」。**

### 取舍 5：40 函数卡线（第三次撞上）

加 cleanup 后 `QuickUnlockController` 41 > 40。纪律不变：
`anyRoomSealed` 挪文件级（与批次 1 的 `normalizeServer` 同款先例）。
**再次确认：新逻辑进新类，别往老类身上堆。**

## 1. 最大的一件事：把**判定逻辑**从编排里剥出来

批次 2 收工时我留了一条诚实遗留：动作表没有单测覆盖，因为控制器内部硬编码
`Dispatchers.IO`，纯 JVM 下 `runTest` 无法确定性推进那次线程跳转 ⇒ 强写会得到
**间歇性红**的测试（比没有更糟）。

本轮的解法不是给控制器打洞（把 dispatcher 注入化会让构造参数再涨一个，且
`LongParameterList` 已逼近阈值），而是**把判定挪到文件级纯函数**：

| 函数 | 钉住的是什么 |
|---|---|
| `lockState(exists)` | 开关 = 门锁存在性（二值）—— #93 的复发点 |
| `locksToOpen(methods, ui)` | 只开**还没装**的门锁（动作表第 2 条） |
| `roomSealingBlocker(...)` | 封房间前的两道闸（定稿 §5 顺序约束） |
| `assemble(...)` | 范围语义（默认全勾 / 房间存在性单维度） |

四个都改 `internal` ⇒ 单测直接钉，不必 mock 全套依赖；
顺带给 `QuickUnlockController` 的函数数腾了位（detekt `TooManyFunctions` 40）。
`QuickUnlockControllerTest` 7 条 → **17 条**。

**代价必须说清**（写进了测试类 KDoc，别让人误读）：这批用例证明的是
「判定逻辑正确」，**不是**「整条编排流程正确」。后者仍要靠批次 5 真机验收。

## 2. 删 `Partial` 时的一段取舍

`Partial` 是 2026-09-26 刚改对的东西（#121：从"关着的开关"改成「继续」按钮）。
删它会不会是把修好的又改坏？判据是**它是否还可能被产出**：
房子化后 `assemble` 用 `lockState(门锁存在性)` 推开关，永远产不出 `Partial`
⇒ 它是**死状态**。留着它：① 每个渲染点多一个不可能走到的分支；
② 一旦有人又把按库进度接回来，#93 会原样复发。

那段 2026-09-26 的设计说明**没删**，而是保留在 `QuickUnlockDialogs` 的 KDoc 里
（写明"针对的是旧模型，新模型下整体作废"）—— 它解释的是
「**为什么不能再按范围进度推导开关**」，那正是防复发的关键。

## 3. 结果页的一个判断（工作单没写细）

工作单只说「结果页逐库成败分类 → 改『已纳入 N / 跳过 M』」。
我把它读成**成功/跳过报数、失败仍逐条列**，理由写进了 KDoc：
失败必须**可行动** —— 只知道"有 2 个失败了"但不知道是哪两个、为什么，
用户唯一的出路是全部重来一遍。数量给结论、逐条给出路，
两者不是同一种信息，不该用同一种呈现。

## 4. 副标题文案的一处"顺手改对"

PIN 副标题原本要写「6 位数字；连续输错 5 次将锁定」。
**没有写死 5**，改成由 `PIN_MAX_ATTEMPTS` 传入。理由：文案里的数字一旦与
代码阈值分叉，就是一句**不成立的承诺**（谎报状态那一族），
而这类分叉在改阈值时几乎必然发生。
