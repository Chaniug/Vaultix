## 1. #186 备份策略：`allowBackup` 默认 true

**这是本轮唯一"用户看不见、但一旦发生就是数据损坏"的一条。**

`shared_prefs/vaultix_secure.xml` 里存的是门锁信封 / KEK 信封 / 房间信封 / WebDAV 凭据 /
Bitwarden token，而解封它们要用 **Android Keystore 里的不可导出密钥** —— Keystore **不参与备份**。

```
旧机备份 → 云端 / device-transfer → 新机恢复
→ 信封原样落在新机 → Keystore 里那把密钥不存在 → 解封必然失败
→ 拿到的是一堆解不开的废纸
→ 但界面上"门锁"这项设置看着还在 ⇒ 用户以为锁还在，实际是一把打不开的假锁
```

修法两条并行：

1. `allowBackup="false"`；
2. 同时声明两份规则资源（**保险丝**）：`dataExtractionRules`（API 31+ 的云备份 + 设备迁移）
   与 `fullBackupContent`（API 30- 的老 Autobackup），四条路径在**两条通路**上都排。

### 四个坑

| 坑 | 说明 |
|---|---|
| `<cloud-backup>` 与 `<device-transfer>` 是**两段** | 只写一段 = 另一条通路完全没拦。换机迁移走的正是后者 |
| `sharedpref` 的 `path` **不带 `.xml`** | 写 `vaultix_secure.xml` 会**静默不匹配** —— 不报错、不警告，规则看起来写了 |
| XML 注释里不能出现连续两个短横线 | 想画表格分隔线 `---` 直接编译失败 `The string "--" is not permitted within comments` |
| `<exclude` 不要跨行写 | 单测按字符串断言，跨行匹配不到（更本质的是跨行容易漏掉 `path=`） |

验证：`BackupPolicyConfigTest`（5 条，**直接解析源 XML**，不引 Robolectric）。

## 2. #187 自动填充保存链：四处断裂

四个独立缺陷落在同一条链上，任一都足以让「保存」失败：

| 子问题 | 根因 | 修法 |
|---|---|---|
| 首次在锁态登录**永不提示保存** | 锁定态分支构造响应时**漏挂 `saveInfo`** ⇒ 系统不知道可以保存 ⇒ `onSaveRequest` 压根不会被调用 | 补 `saveInfo = AutofillSaveInfo.build(parsed)` |
| 保存的是**第一个框**的值（可能是隐藏框/空框） | `parse(...)` 的 `fillAssistRules` 用方法引用传参时**丢了实参**；字段选取不跳 `isVisible=false` 与空值 | 显式传参 + 新增 `saveValueOf(parsed, hint)` |
| 点**第 2 行**填进第 1 条密码 | `requestCode = id.hashCode()` + `FLAG_UPDATE_CURRENT` ⇒ 同 id 覆盖前一个 PendingIntent | 新增 `RequestCodes.next()`：`AtomicInteger` CAS 自增，**8000 起**（让开手写区间 `1..7999`） |
| 明文密码进 `Intent` extras | 保存链直接把 `username`/`password` 塞 extras 与 `SavedStateHandle` | 新增 `PendingSaveStore`：一次票据 + 60s TTL，只带 `EXTRA_TOKEN` |

### 三个坑

1. **`FLAG_UPDATE_CURRENT` + 值当 key 是经典撞号**，症状是"填错密码"而不是崩溃，极易被当成用户记错密码；
2. **票据 `consume` 必须原子且一次性** —— `SavedStateHandle` 在进程重建后会重放，允许二次消费就等于
   重放路径能拿到一份本该作废的明文；
3. **TTL 用 `SystemClock.elapsedRealtime`**，用 `currentTimeMillis` 的话改系统时间能把过期票据"复活"。

界面上，票据失效时画 `ExpiredBody`（"保存窗口已过期"），**不是**画一个永远转圈的加载态。

验证：`PendingSaveStoreTest`（7 条，TTL 用的是反射把 `stagedAtElapsedMs` 往前推 61 秒，不真等）+
`RequestCodesTest`（2 条：2 万次发号无重复、首号 ≥ 8000）。

## 3. #188 / #189 剪贴板与锁定

**#188**：锁库时 `setVaultToLocked()` 里没有任何剪贴板动作，密码留在剪贴板里任何 App 都能粘出来。
修法 = `VaultixClipboard.clearNow()`：先取消定时任务，再**只在确认剪贴板里就是自己放的东西**时才清
（判据 `EXTRA_IS_SENSITIVE`（API 33+）或 `label == "Vaultix"`），**读不到就什么都不做**
—— 清掉用户从别处复制的验证码是同样的伤害。

顺带修了反面：复制**网址**也被当成敏感内容，30 秒后粘出来是空的。`doCopy` 改 `sensitive = !isUri`。

⚠️ 还有个隐藏问题：`clipboardScope` 是 `Dispatchers.Main.immediate`，`delay` 挂在主线程上，
界面忙 / Doze 时定时器整体推迟，"30 秒清空"可能变成几分钟。改 `Dispatchers.Default`。

**#189**：设成"离开 5 分钟锁定"，熄屏放一夜，第二天点亮发现还开着。根因是 `ACTION_SCREEN_OFF`
没被监听 —— **熄屏不保证触发 `onStop`**（媒体播放 / 画中画 / `showWhenLocked` 下 Activity 仍 resumed）。
修法 = 同时注册 `SCREEN_ON`/`SCREEN_OFF` 并按 action 分流，新增 `onScreenOff()` 复用
`onAppBackgrounded()` 那套（`Never` / `OnAppRestart` 档位不变）。

⚠️ **测试坑**：`onScreenOff()` 之后直接推进虚拟时间是**假红** —— 定时器在协程里挂上，
只 `runCurrent()` 一次跳不够。要 `settle(m)`（反复 `runCurrent()` 到定时器计数稳定）再推。

## 4. #190 两半：409 弃单 + 内容指纹漏字段

### 4.1 同步：409 Conflict 被当成"确定性失败"弃单

`flushPending` 把 `(400..499)` 一律当"确定性失败" ⇒ 删队列行、不重试。而 **409 Conflict**
恰恰是"这不是我的错，重来一次可能就成"的语义。后果：**远端那条改动永久丢失**，
没有报错、没有冲突提示、队列里也没有残留。

修法：`HTTP_CONFLICT` 从 `DEFINITIVE_HTTP_CODES` 剔除，409 走 `incrementRetry`。

⚠️ detekt 直接红：`flushPending` 圈复杂度 **16 > 14**。拆出 `handleOperationFailure(op, error): Boolean`。
**踩过的雷**：降复杂度时"提前 return"也算分支。

⚠️ 测试**假红**：`BitwardenSyncPendingOpFailureTest` 的 404 用例本该弃单却留在队列。
真相是夹具 `payload = "{}"` 缺 `CipherRequest.type` 必填项，`executeOperation` 在**发请求之前**
就抛了 `MissingFieldException`，被归到"网络类"。改成合法 JSON `{"type":1,"name":"2.xxx"}`。
定位手段：临时 `System.err` + 读测试 XML 的 `<system-err>`（`VaultixLog` 默认 sink 丢弃，logcat 什么都看不到）。

### 4.2 KDBX：内容指纹只摘 5 个字段

**这是本轮最值钱的一条。** #185 的写回基线防线靠 `contentFingerprint` 判断"我手里这份是不是远端那一版"，
而它最初只摘 `id / title / username / password / notes`。

> 用户改**网址、TOTP 密钥、自定义字段、卡片号、SSH 私钥、身份、收藏、文件夹归属**后保存
> —— 指纹**不变** ⇒ 基线判为"内容没动过" ⇒ 落盘放行 ⇒ **基于旧版本覆盖远端**。

而且**不报错、不降级、零日志**。比"没有防线"更难发现，因为审查时**看着它是有的**。

修法：全字段进摘要（`type`/`folderId`/`favorite`/`reprompt`/`uris`/`totp`/`fido2Credentials` 11 字段/
`card`/`sshKey`/`identity`/`customFields`/`secureNote`/`passwordHistory`）。

| 坑 | 说明 |
|---|---|
| Map 顺序不稳 = 假阳性 | `binaryNames` 是 `Map`，直接遍历两次可能不同 ⇒ "所有库永远算变过" ⇒ **按 hash 排序**后再参与 |
| 无分隔符可构造碰撞 | 「标题 `ab` + 用户名 `c`」与「标题 `a` + 用户名 `bc`」摘要相同 ⇒ 新增 `update(digest, vararg)`，逐串前写 `FIELD_SEPARATOR` |
| `null` 与 `""` 要能区分 | 前者是"字段缺席"，落盘语义不同 ⇒ `ABSENT_MARK` / `PRESENT_MARK` |

验证：`KdbxFingerprintCoverageTest`（6 条）—— **表驱动** `FIELD_MUTATORS` 覆盖 21 个字段，
每个字段改一次断言指纹**必变**。KDoc 里写死纪律：**给 `VaultItem` 加字段必须往表里加一条**，
否则"全字段"会随模型演进慢慢退化回"部分字段"。

## 7. 本轮踩到的工程坑（与业务无关，但会重复踩）

1. **Kotlin 块注释可以嵌套**：注释里写 `res/xml/*.xml` 会被当成新注释的起点 ⇒ `Unclosed comment`。
   改写措辞避开 `/*`。
2. **`org.junit.Assert.assertTrue(message, condition)` 与 `kotlin.test` 参数顺序相反**，
   且 `kotlin.test.Test` 在 `app` 模块不可用（依赖里只有 junit4/truth/turbine/mockk）。
3. **用 python 批量改 .kt 时把 `\x00` 写进了源码** ⇒ `file` 报 `data`、grep 报 `binary file matches`。
   用 `open(p,'rb').read().replace(b'\x00', b'')` 清。
4. **heredoc 写 Markdown 时，命令正文本身会被写进文件**（连续两次 `cat >> … <<'EOF'` 时第二段的
   `python3 - <<'EOF'` 也会进文件）。本轮 `.ai/issues/05` 与 `06` 各被污染一次，已清理。
   教训：**批量写文件用独立的 .py 脚本 + `Write` 工具，不要在 heredoc 里嵌 heredoc。**
