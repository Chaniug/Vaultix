# SESSION 2026-11-01 · 图标空帧与尺寸算错（#216）

> 用户两句话：「条目图标好像现在每次打开都是重新加载的吧，我在滑动的时候，发现有一些图标是
> 从空白再加载出来的，每次都这样，是否会浪费性能」→「你认为该怎么做，**我要提升性能与美观度**」。
>
> 第二句是关键：用户不是在提问，是在**授权动手**。所以本轮不做"要不要优化"的论证，
> 只做"优化什么、为什么是这三个"的取证。

---

## 1. 先算量级，否掉最顺手的那个假设

第一反应是"缓存太小了 / 每次都在下载"。先把它证伪，否则后面所有工作都建立在错的前提上。

| 量 | 值 | 出处 |
|---|---|---|
| Coil 内存缓存默认上限 | `memoryClass` 的 **20%**（低内存机 15%）≈ 51MB | `MemoryCache.Builder` 的 `defaultMemoryCacheSizePercent` |
| 一张 40dp 图标（3x 屏 120px） | ≈ 120×120×4 B ≈ 56KB | 算出来的 |
| 整库几百条合计 | 几 MB | 56KB × 300 |

**差两个数量级。** 再叠加一点：`RealImageLoader` 里**没有任何"首次加载清缓存"的逻辑**，
`onTrimMemory` 也只做 `trimMemory`。⇒ 缓存容量与失效策略都不是成因。

这条否证很重要 —— 它把排查方向从"调大缓存 / 加预加载"直接推到了**渲染路径**上。

## 2. 三个真因

### 2.1 尺寸从源头就算错（这是「不美观」的根）

```kotlin
private const val ICON_REQUEST_PX = 96     // 死写的**像素**值
```

注释还写着「统一按 2 倍密度请求」—— 但**屏幕密度不是 2x**。实际使用点：

| 位置 | dp | 3x 屏需要 | 请求 96px 的结果 |
|---|---|---|---|
| `EntryCardIconSize`（列表卡片） | 40.dp | 120px | **放大 1.25 倍** |
| `DETAIL_HEADER_ICON`（详情页） | 56.dp | 168px | **放大 1.75 倍** |

⇒ 高密度机上图标一律发虚。这不是"不够清晰"，是**解码尺寸从一开始就小于绘制尺寸**。

修法只有一行，但有一个坑要先确认：

```kotlin
val targetPx = remember(size, density) { with(density) { size.roundToPx() } }
```

⚠️ 原本想写 `.size(size)` 直接传 `Dp` —— **Coil 2.7 没有这个重载**。`ImageRequest.Builder.size`
只有 `(Int)` / `(Int, Int)` / `(Dimension, Dimension)` / `(Size)` / `(SizeResolver)` 五种。
这点是去源码里核对过的（`ImageRequest.kt`），不是凭印象。

### 2.2 卡片重建后第一帧**必然**是空的

`LazyColumn` 里滑出可见区的卡片会被**销毁**，滑回来时**重建 composable**。
而 `AsyncImage` 无论如何都要先过一次协程调度（`RealImageLoader.execute` 走
`Dispatchers.Main.immediate`）⇒ 重建后的第一帧没有任何内容。

60Hz 下 16.7ms —— 肉眼正好能捕捉到"白圈闪一下"。再叠上旧代码的 `crossfade`（每张卡片
进出场都白播一次 ~100ms 的 alpha 渐变），观感就是用户说的「**从空白长出来**」。

修法：**在组合期同步查 `ImageLoader.memoryCache`**。

```kotlin
val cachedBitmap = remember(iconUrl, targetPx) {
    imageLoader.memoryCache?.get(MemoryCache.Key(siteIconCacheKey(iconUrl, targetPx)))?.bitmap
}
if (cachedBitmap != null) CachedSiteIcon(...) else RemoteSiteIcon(...)
```

命中就直接 `BitmapPainter` 绘制 —— **不构造 `ImageRequest`、不启协程、不查磁盘**，
整条 `RealImageLoader.execute` 都跳过。这是"根治"，不是"把动画调短去掩盖它"。

### 2.3 ⚠️ 显式 `memoryCacheKey` 会**吞掉尺寸**（改 2.2 时踩出来的坑）

为了让"同步查缓存"能算出一个稳定的键，很自然会写 `.memoryCacheKey(...)`。
但 Coil 源码里：

```kotlin
// MemoryCacheService.newCacheKey()
request.memoryCacheKey?.let { return it }      // ← 快路径：直接返回，不再追加 extras
```

而 Coil 默认键是 `MemoryCache.Key(base, extras)`，**尺寸就在 `extras` 里**。
显式给键 ⇒ `extras` 空 ⇒ 40dp 与 56dp 的图标**共用一条缓存**。

后果不是"糊"，而是更隐蔽的**来回重解码**：`MemoryCache.Value.isCacheValueValid` 发现
缓存里的尺寸与本次请求不符 → 判无效 → 重新解码 → 覆盖同一个键 → 下次换个尺寸再判无效……
**每进一次详情页白跑一轮。不崩、不报错、不打日志**，只有一句"图标好像总是在加载"。

修法：键自带尺寸。

```kotlin
internal fun siteIconCacheKey(url: String, px: Int): String = "site-icon:$px:$url"
```

抽成纯函数 + `SiteIconCacheKeyTest`（6 例）钉死。**因为这个 bug 真机看一天也定位不到，
只能靠断言。** 六例分别是：同键稳定 / 尺寸不同必须不同 / URL 不同必须不同 /
库不同必须不同 / 带命名空间前缀 / 尺寸段可读（便于 dump 排查"糊不糊"）。

> **判据**：**凡是显式覆盖框架给你算好的键或哈希，必须先把"它原本算了什么"列出来，
> 然后把那些维度自己补回去。** 少一维不一定崩，但一定会让缓存静默失效。

### 2.4 失败被永久化

旧 `onError = { failed = true }` 会一路带到卡片被回收：一次 DNS 抖动就让某个条目
在本次浏览里**永远**停在首字母（除非用户把它滑出去再滑回来重建）。

修法：记**失败时刻**而不是布尔 —— 它既是状态，又能当 `LaunchedEffect` 的 key，
让每次失败都重新计时；30s 后清标志 + 递增 `retries` ⇒ `ImageRequest` 的 `remember` key
变化 ⇒ 重新加载，最多 1 次。

```kotlin
var failedAt by remember(iconUrl) { mutableLongStateOf(0L) }   // 0 = 未失败
var retries by remember(iconUrl) { mutableIntStateOf(0) }
```

1 次足够覆盖网络抖动 / DNS 超时；再多就是拿用户的电换运气。

### 2.5 观感：任何时刻都不是空白

旧实现在"加载中"时 `AsyncImage` 什么都没画、底色又是白圆 ⇒ 用户看到的就是**一个白圈**。
现在改成"首字母始终在底层，图标成功后再盖上去"：加载中 / 失败 / 待重试三种状态
**画同一件事**。

而且与"根本没有域名可拼 URL"（KDBX 库、未填网址）的 `FallbackAvatar` **共用**
`FallbackInitial` —— 否则同一个条目会因"有域名但没取到"和"没域名"显示成两种大小。

## 3. 编译期才知道的两件事

1. **`rememberAsyncImagePainter(model, onError)` 编译不过** —— `onError` 属于另一个重载，
   而那个重载的 `imageLoader` 参数**没有默认值**。必须显式传
   `imageLoader = context.imageLoader`，并在代码里写清原因，否则下一个人会把这个
   "看起来多余"的参数"清理"掉。
2. **`ImageRequest.Builder.size(Dp)` 不存在**（见 2.1）。

## 4. 全局 `respectCacheHeaders(false)`（冷启动重下的最后一环）

`respectCacheHeaders` 是 **loader 级**开关 —— `ImageRequest` 上有 per-request 版本，
但默认行为由 loader 决定。Coil 默认 `true`：服务端回什么 `Cache-Control` 就照办。

图标端点 `<base>/icons/<host>/icon.png` 一旦返回 `no-cache` / `max-age=0`
（反向代理与 CDN 的默认行为并不统一），**磁盘缓存完全不写** ⇒ 冷启动 内存空 + 磁盘空 ⇒
一屏图标全部重新联网。这正是用户说的「每次打开都重新加载」。

修法：`VaultixApplication : ImageLoaderFactory`，`newImageLoader()` 里关掉它。
代价只有"站点换了 favicon 可能仍是旧图，直到 LRU 淘汰"—— 远小于每次启动重下几十张。

⚠️ **磁盘缓存目录必须保持 Coil 默认的 `cacheDir/image_cache`**：`AutofillItemIcon`
**直接按 URL 读这个目录**给填充建议取图标，换目录等于把它废掉。

内存 / 磁盘缓存**大小一个都不收紧**（理由见 §1）：收紧只会降低命中率、把空帧放回来。

## 5. 顺带修两个长期误报的静态门禁

不修的话"门禁红"会变成噪音，真正的错误被淹没。本轮两处都是**工具判据错**，
不是代码错 —— 所以改的是工具，**没有**去"改对"那几行合法代码。

### 5.1 `check_import_packages.py`：图标与组件同名

`SiteIcon.kt` 新增 `import androidx.compose.foundation.Image` 后，`foundation.Image`
票数变 2 —— 而 `DisplayOptionsSheet.kt:35` 的 `import androidx.compose.material.icons.filled.Image`
是**图标**，被算成了"组件包票数"的异议票 ⇒ 合法 import 被判违规。

修法：把 `androidx.compose.material.icons.*` **整体**排除在约定包统计之外
（图标不是 UI 组件，不该参与"本项目该用哪个包"的投票），并在
`selftest_import_packages.py` 补一条反向用例（4/4 PASS）。

### 5.2 `check_ui_hardcoded_text.py`：跨行调用被切成两半

`SettingsComponents.kt:439/440` 是一个跨行的 `Log.w(...)`：关键字在第一行、
中文文案在第四行 ⇒ 被判成"界面硬编码文案"。

**这条自 2026-10-30 起就一直红着，没人知道。** 原因是我上一轮跑检查时写的是：

```bash
python3 check.py ... | tail -4; exit=$?      # ← $? 是 tail 的退出码，永远 0
```

修法两层：
- 工具改为按**逻辑行**判断（先合并括号未闭合的续行，行号取起始行）+ 2 例自测（7/7 PASS）；
- 流程改为 `python3 ... > /tmp/o.txt 2>&1; code=$?`，**不用管道**。

> **判据：任何被管道接过的命令，退出码都要单独取。** 这条比上面任何一条都更容易再犯。

## 8. 追记：CI #332 —— 我自己写的断言假红了一次

首轮推送 `809d824` 后 CI 红：**1428 例，失败 1 例**，恰好是我新加的
`SiteIconCacheKeyTest.键带命名空间前缀_不与其它Coil缓存撞车`。

```kotlin
assertThat(siteIconCacheKey(url, 120)).doesNotContain("://")   // ← 假红
```

键的实现是 `site-icon:$px:$url` —— **刻意保留原始 URL**（dump 时一眼看出是哪张图），
而 URL 自身就带 `://`。所以这条断言**必然**失败。

**问题不在实现，在断言与注释里写的意图不一致**：

| | 内容 |
|---|---|
| 注释想说的 | 「不许**冒充** URL / 不许与 Coil 默认键（`UriKeyer` 的裸 URL）撞车」 |
| 实际断言的 | 「不许出现 URL 的**特征字符** `://`」 |

后者是个**过强的代理指标**。改为三条直接对应意图的断言：

- `startsWith("site-icon:")` —— 有命名空间前缀；
- `doesNotStartWith("http")` —— 不以 URL 形状开头；
- `isNotEqualTo(url)` —— 整条键不等于裸 URL ⇒ 不会与默认键同格。

> ⚠️ **判据：否定式断言（`doesNotContain` / `doesNotStartWith`）最容易写成过强。**
> 因为它只需要脑子里想出一个反例就能"说得通"。
> 写完回头读一遍自己的注释：**若注释说的是"必须是 X 形状"，就直接断 `startsWith(X)`，
> 不要绕过去断"不含 Y"**。

顺带说明：这次是**真红**（不是误报），CI 该红 —— 它抓到的是"测试代码的意图与断言不一致"，
而这类问题在本地 `./gradlew test` 里同样会红，不存在"CI 才有的怪问题"。

## 9. 追记：CI 连红 7 次的完整链条（#332–#338）

这一段值得完整记下来 —— 因为**每一次报错看起来都像下一次的原因**，实际是三个独立问题
首尾相接，中间还夹着一个"诊断器自己坏了"的假象。

```
#332  ① 我写的断言假红（doesNotContain("://")）        ← 真
#333  ② 同 ① 修完仍红：签名密码错（被伪装成"915 例 0 失败"）
#334  ③ 猜 Compose 提前 return（猜错，但重构本身无害）
#335  ④ 加"打印编译错误"的 step → 终于看到真因：签名密码
#336  ⑤ 加 key 密码校验 → APK 打出来了，但红在报告 step
#337  ⑥ 报告 step 设 continue-on-error 仍红（锚点仍在 19）
#338  ⑦ 打印单测真实退出码 → 真因：compileFullDebugUnitTestKotlin FAILED
#339  ⑧ 修 doesNotStartWith（该 API 不存在）→ 全绿 · 1428 例 · 0 失败
```

### 9.1 三个真问题

| # | 问题 | 为什么难看出来 |
|---|---|---|
| A | **`doesNotStartWith` 在 Truth 的 `StringSubject` 里不存在** | 它是**编译期**错误，报在 `compileFullDebugUnitTestKotlin`；而 CI 顶层只说「exit code 1」 |
| B | **key 密码与 store 密码不一致** | 解码步骤用 `keytool -list` 校验，**只验 store 密码**，打着"校验通过"；真正失败在 `packageFullDebug` |
| C | **诊断步骤自己会失败** | 一个只读 XML 做汇总的 step，把「915 例 0 失败」报成了 CI 红 |

### 9.2 为什么"915 例 0 失败"会与 "exit 1" 并存

`assembleFullDebug` 只编译 **main**；`testFullDebugUnitTest` 还要编译 **`src/test`**。
后者编译失败 ⇒ 一个测试都没跑 ⇒ 但 `test-results/` 里有**上一轮遗留的 XML** ⇒
汇总步骤照常统计出「915 例、0 失败」。

> **判据：汇总结论不能反证"这一步成功"。**
> "0 失败"只说明"我数到的那些没失败"，不说明"该跑的跑了"。

### 9.3 为什么前四次完全查不到

| 想要的信息 | 拿到它的路径 | 结果 |
|---|---|---|
| 编译错误原文 | 在 step 的 `/tmp/build_log.txt` | step 结束即随 runner 消失 |
| job 完整日志 | `GET /actions/jobs/{id}/logs` | **403**（需 admin 权限） |
| 单测 XML | run 的 artifact | **401**（需认证） |

三条路全堵。⇒ **凡是"失败后才知道需要"的信息，必须由 workflow 自己打到 annotation 上。**
这就是 #335 那个 `Summarize build errors` step 存在的理由 —— 它一上线就结束了盲猜。

### 9.4 顺带修好的三处 CI 机制

1. **`Summarize build errors`**（`if: always()` + `continue-on-error`）：
   把 `^e: ` / `FAILURE:` / `Caused by:` 逐行打成 notice；
2. **单测步骤打印真实退出码**：`PIPESTATUS[0]` + `^e: ` 关键词（第一版漏了 `e:`，又白跑一轮）；
3. **签名校验升级为 `keytool -certreq`**：真的解一次私钥，与打包等效；验不过就降级一次性密钥
   并打 `::warning` 明确告知"本包无法覆盖安装"。

### 9.5 ⚠️ 留给维护者的待办

`SIGNING_KEY_PASSWORD` 与 `SIGNING_STORE_PASSWORD` **不一致**（`keytool -certreq` 实测解不开）。
现在的行为是**自动降级一次性密钥** → 预览包能装、但**盖不上旧包**（会因签名不同而安装失败）。
请把 `SIGNING_KEY_PASSWORD` 改成与 keystore 里那把 key 的实际密码一致；
改好后 CI 会打出 `store 密码与 key 密码均已验证通过`。
