## 2. R-2 + R-3：开关「不猜状态」（`06bd5a4`）—— 本轮最大的一块

### 症状

同一个设置页上，**两种开关行为并存**：3 个开关首帧是灰占位（点了才变），
7 个是裸 `Switch`（首帧直接显示 `true`）。

### 根因在类型层，不在 UI 层

```kotlin
private val oledPureBlack = repository.observePrefs()
    .map { it.oledPureBlack }
    .stateIn(scope, SharingStarted.Eagerly, initialValue = true)   // ← 病在这里
    .asStateFlow()                                                  //   StateFlow<Boolean>
```

`StateFlow<Boolean>` **不允许 null** ⟹ 磁盘还没读出来时，只能用 `true`/`false` **猜**一个。
猜 `true` 就把「偏好还没读出来」**伪装成「明确开着」**。

这违背项目自己的纪律（`SettingsScreen.kt:1316-1329`）：
> **不认识就什么都不说。**

### 改法

8 个流 `StateFlow<Boolean>` → **`StateFlow<Boolean?>`**，`initialValue = null`：

`oledPureBlack` / `autofillSavePrompt` / `autoCopyTotp` / `totpCopyNextOnExpiring` /
`autofillBaseDomainMatch` / `autofillExactDomainOnly` / `fillAssistEnabled` / `itemsShowIcon`

并在 `SettingsViewModel.kt` 加一段**契约 KDoc**（因为这条约定只能靠人守住）：

```kotlin
// ---- 布尔型设置项：**一律是 `Boolean?`，初值 `null`** ----------------------
//
//   null  = 「偏好还没从磁盘读出来」（.ai/ISSUES.md #84「三种空」）
//   true  = 明确的"开"
//   false = 明确的"关"
//
// ⚠️ **不要把 `initialValue` 改回 `true`/`false`**……
```

### ★ 泄漏点：`FillBehaviorSection`

`Boolean?` 到了这一层**又降回 `Boolean`**：

```kotlin
private fun FillBehaviorSection(
    exactDomainOnly: Boolean,      // ← 这里收窄，下面的 null 语义全丢
    baseDomainMatch: Boolean,
    fillAssistEnabled: Boolean,
)
```

⟹ 改 `Boolean?` 并在 KDoc 里写明**别"修"回去**。
**这条是本轮最值钱的发现形式**：类型改造最容易死在「中途某一层收窄」上，
而收窄处**编译不会报**（把 `Boolean?` 传进 `Boolean` 参数才报；反过来是隐式的）。

### `SettingsSwitch` 收口

原先是 `SettingsScreen.kt` 里的 `private fun`，二级页用不了 ⇒ 各写各的。
搬到 `SettingsComponents.kt` 改 **`internal`**，全仓**一处定义**。

占位态（`value == null`）的可点语义**定稿为「打开」（`true`）**，并写清**为什么不是「取反」**：

> `value == null` 意味着**根本没有当前值**，取反没有意义。

⚠️ 这里我**自己纠正过一次**：初版加了个 `onToggleUnknown` 回调想表达"点了到底该怎样"，
写完后 grep 发现**零调用点** ⇒ 删掉，API 停在 2 参。
**过度设计的判据就是"没人用"。**

### 验证

detekt **净 18 → 17**（无新增违例）。
类型检查：`SettingsComponents.kt` 干净产出 `SettingsComponentsKt.class`。
另写一个**契约片段**覆盖「可空流 → 收集 → section → SettingsSwitch」整条链，
并在**两个方向**做变异：

| 变异 | 结果 |
|---|---|
| `SettingsSwitch(value = autoCopyTotp!!, …)` | **没抓到 —— 但我的前提是错的**：`Boolean` 传进 `Boolean?` 本来合法 |
| 把 `SettingsSwitch` 参数收窄回非空 | ✅ 抓到 |
| 把 `if (value != null)` 改成 `if (true)` | ✅ 抓到 |

⇒ 再次印证 #104：**变异测试先要证明"这个变异本该被抓"**，否则是自己在演自己。

> ⚠️ **上面那句「无新增违例」当时是错的** —— 见 §8。收工复核才抓出来。

## 3. R-4：快解三态开关（`561bf11`）

### 症状

`QuickUnlockDialogs` 里两处：

```kotlin
Switch(checked = state.x is CapabilityState.On, onCheckedChange = { … })
```

`CapabilityState` 是**三态**（`On` / `Off` / `Partial`）。
`Partial` 表示**「已开启，但只覆盖一部分应用」** —— 显示成一个**关着的开关**。
用户点它：是「打开」还是「补齐」？**无从判断。**（这正是 #120 那条"不猜状态"的另一面。）

### ★ 为什么所有现有手段都查不出

- **类型检查**：`is On` 是合法 Kotlin，返回 `Boolean`，没毛病；
- **detekt**：不管语义；
- **`when` 穷尽性**：压根没有 `when`，是包在 `Switch` 参数里的一行布尔表达式。

> **压扁发生在「类型 → 界面」的缝里。**

### 改法：两种控件，而不是给开关写注释

```kotlin
@Composable
private fun CapabilityToggle(capability, enabled, onToggle) {
    when (capability) {
        is CapabilityState.Partial -> TextButton(onClick = onToggle, enabled) {
            Text(stringResource(R.string.quick_unlock_partial_action))   // 「继续」
        }
        is CapabilityState.On -> Switch(checked = true, …)
        CapabilityState.Off   -> Switch(checked = false, …)
    }
}
```

**判据（可复用，已进 #122）**：

> 当**注释不得不解释**「点这个按钮是 A 不是 B」时，**错的是控件，不是注释。**

### 新探针 `check_state_flattening.py`（#124）

4 条判据，抓 `checked = x is S.On` 这类形态，且**要求 `S` 是 ≥3 分支的 sealed**，
且该表达式**不在 `when` 派发内**（`when` 内是正当用法，必须放行）。

### ★★ 这个探针坏了两次，两次都是「假绿」

**第一版**：只扫**当前文件**里有没有 sealed 声明。
而真 bug 的 `CapabilityState` 声明在 `QuickUnlockController.kt`、误用在 `QuickUnlockDialogs.kt`
⟹ **报 0 findings，全绿。**

修：建**全仓**多态类型名表（`collect_polyadic_names`）。

**第二版**：自测 7/7 全绿，真代码上**还是报 0**。

根因：`READY_TEST` 正则**贪婪地吃到了倒数第二段**：

```
QuickUnlockController.CapabilityState.On
                     ↑ 匹配成 ("QuickUnlockController", "CapabilityState")
                        而不是 ("CapabilityState", "On")
```

我所有自测用例都写短名（`Cap.On`），**所以抓不到自己这个 bug**。

> **教训（已写进代码注释）**：**自测只证明"探针能处理我编的简化输入"，不能证明它有用。**

修：正则跳过包前缀段；补**全限定名**正例 + 配对的负例 ⇒ 自测 **9 例**。

### ★★ 闭环证明（这才是探针的验收标准）

把 `QuickUnlockDialogs.kt` **还原成 HEAD 的版本**：

```
全树扫描 ⇒ 精确报出那 2 行，exit 1     ✅
还原修复  ⇒ 0 findings，exit 0         ✅
```

> **探针的闭环证明 = 「把代码还原成出 bug 的版本，看它是否恰好报那几行」**，
> **不是「自测全绿」。** 这条已进 #124。

用户问「设置的文案是否模糊」。逐条审完（**不是扫印象**）：

  > **对齐上游的文案不叫"模糊"，叫"保持一致"。**

### 新探针 `check_orphan_strings.py`（#126）

`strings.xml` 共 834 条，**126 条零引用**。

**关键定位：这是报告器，不是删除器。**

因为按项目自己的判断规则「**被"搬走"的留，被"取代"的删**」——
留档的字符串**本身就是零引用的**（它的用途是被后人对照，不是被代码引用）
⟹ **这个数字不可能归零。**

所以 `--gate` 用基线做**只减不增**约束（基线 126 条）。

**方向性取舍**：探针**刻意偏向少报**。
- 误报（把在用的判成孤儿）⇒ 编译期/人工可见，代价低；
- 误删（真删了在用的）⇒ **运行时才炸**，代价高。

> **宁可少报几条孤儿，也不能误删在用的。**

自测 7 例，含两个经典误判：
- `prefix_names_not_confused`：`a_head` vs `a_header`（前缀撞名）；
- `ignores_non_string_resources`：`<string-array>` 不该被计入。

闭环：注入一个新孤儿 ⇒ 点名报出 exit 1；还原 ⇒ 通过。

### ⚠️ 一次作业事故（已修）

用 Python heredoc 改 `README.md` 时，**中文引号进了字符串字面量** ⇒ `SyntaxError`：
**注册没成功，但后面的 `git commit` 照跑**，于是提交了一个「只有代码、没有登记」的状态。

⇒ 用 Edit 工具重做，另起一个 `docs(.ai):` 提交（`1493f9e`）。

**教训**：`&&` 串联的脚本里，**前一步失败不一定拦住后一步** ——
把「改文档」和「提交」串在一条命令里，失败了会静默产出一个半成品提交。

### ⚠️ 本地 detekt 的**正确口径**（我一开始说错了一版）

**先说结论**：项目自带的 `config/detekt/detekt.yml` **本来就是旧属性名**
（`threshold` / `functionThreshold` / `max`），可以直接喂给沙箱里的 detekt 1.23.8。

我中途一度以为"项目配置用新属性名、必须另写一份"——**那是我看错了**，
`config/detekt/detekt.yml` 里写的确实是 `threshold: 150` 这种旧名。
`/tmp/detekt-1x.yml` 只是它的**镜像**（内容等价），留着是为了避免误改真源。

**真正要注意的是另一件事 —— 两边的默认规则集不同**：

| | 违例数 |
|---|---|
| 沙箱 detekt 1.23.8（`--build-upon-default-config`） | **175 条**（多出大量 `MagicNumber`） |
| CI `./gradlew detekt`（2.0.0-alpha.6，项目配置） | **全绿** |

⇒ **本地这套不能用来判"是否绿"，只能用来做「相对基线的差值」。**

### ★ 正确用法：拿 `origin/main` 开一个 worktree 做集合差（这是本轮真正学到的东西）

```bash
git worktree add /tmp/base origin/main -f
# 两边用同一份配置、同一个 --input 各跑一次，抓「文件:行:列: 消息」行
java -jar /tmp/detekt-all.jar --config /tmp/detekt-1x.yml --build-upon-default-config \
     --input app/src/main/java,core,data,domain 2>&1 \
  | grep -E '^\S+\.kt:[0-9]+' | sed 's|/workspace/Vaultix/||' | sort > /tmp/now.txt
# ⚠️ 归一化必须掐掉行号（行号会随改动漂移，带着比会把"挪了几行"误判成"消一条+增一条"）
comm -13 <(sed 's/:[0-9]*:[0-9]*:/::/' /tmp/base.txt | sort -u) \
         <(sed 's/:[0-9]*:[0-9]*:/::/' /tmp/now.txt  | sort -u)
```

> **判据：`comm -13` 的输出必须为空。只看总数等于没看** —— 见 §8。

### Compose stub 的踩坑记录（供后人复用）

`/tmp/kcheck.sh` 已是可用脚本。踩过的坑：

- `Modifier` 必须是 `object`；
- `@Composable` 的 `AnnotationTarget` **要含 `TYPE`**；
- ★ **`provides` 是 `ProvidableCompositionLocal<T>` 的 `infix` 成员函数**，不是扩展函数
  （靠对真 AAR 跑 `javap` 定的：`maven.aliyun.com/.../runtime-android-1.7.0.aar`）；
- `Icons` 需要**两个独立的顶层声明**（`...material.icons.Icons` 与 `...icons.filled.ChevronRight`）；
- `Box` 的 `content` 必须有默认值 `{}`。

## 7. ★ 收工复核抓出的自造回归（#127）—— 本轮第二值钱的一课

推送前按规矩跑一遍门禁，顺手把违例清单与 `origin/main` 做了**逐条集合差**，结果：

```
基线(origin/main) = 175 条
本轮修复前         = 174 条   ← 我当时以为"消 1 条，无新增"
```

**逐条比之后**：

| | |
|---|---|
| 消除 | 1 条（`SettingsRow` 的 `LongParameterList`，预期之中）|
| **新增** | **2 条** —— `SettingsViewModel.itemRepository` 的 `UnusedPrivateProperty`、以及另一条 |

净数 **17 → 19**，但**只看"174 vs 175"是看不出来的**。

**真因**：删 `passkeyCount`（缺陷 4）时，它订阅用的 `itemRepository`
**唯一用途随之消失** —— 变成构造上一个没人用的属性。
这是**删除代码的典型副产品**：删掉 A，只被 A 用的 B 就成了死代码，
