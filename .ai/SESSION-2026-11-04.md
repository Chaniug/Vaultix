## 二、#243：纳入挂在认证之前 ⇒ 条件恒假

### 2.1 定位

截图那句话的来源是 `RoomOpen.NotEnrolled → RoomUnlockOutcome.Unavailable(该库未纳入快速解锁)`。
也就是说：**用户按到了门锁、房钥匙已经进内存、但该库没有房间信封**。

把冷启动的时序摊开就明白为什么：

```
① 主密码解开 valk.kdbx → autoEnrollNewVault
                         └─ houseKeyStore.isUnlocked == false ⇒ 静默 false
② 用户按指纹 → 门锁开了、房钥匙进内存
                         └─ 但**没有任何人再来封这个库的房间**
③ 解锁页：valk 不在 quickUnlockScope
   ⇒ fingerprintQuickUnlockAvailable(valk) == false
   ⇒ 自动弹认证不触发
   ⇒ 用户按下去 ⇒「该库未纳入快速解锁」
```

更要命的是**入口可见性当初也用同一个判据**：
`fingerprintQuickUnlockAvailable(id) = fingerprintLockAvailable() && id in scope`。
于是形成一个闭环：没有信封 ⇒ 没有入口 ⇒ 用户没法触发补建 ⇒ 永远没有信封。

### 2.2 修法（四处）

| # | 改点 | 为什么必须 |
|---|---|---|
| 1 | 入口判据改成 `quickUnlockEntryAvailable()` = **装过任意一把门锁** | 入口不能以"能力已就绪"为前提，否则用户永远无法第一次让它就绪 |
| 2 | `LocalUnlockFanout.RoomEnroller` 接缝：门锁刚开、首库 `Unavailable` ⇒ 补建 ⇒ **原地重试一次** | 不重试的话用户会看到"已纳入却仍然开不了"，下次还得输密码 |
| 3 | 主密码路径改走 `enrollJustAuthenticated`（**带**房钥匙守卫） | 房钥匙不在时 KDBX 备料要白跑一次 `Kdbx.verify`，再在 `sealRoom` 抛异常 |
| 4 | `autoEnrollUnlocked` 加 `hasRoom` 短路 | 方法现在每次主密码解锁后都会跑；没有短路就是**每输一次密码多烧一遍 Argon2**（真机 64 MiB / 46 轮） |

`RoomUnlockOutcome` 仍是四态（`Opened` / `StaleCredentials` / `Unavailable` / 门锁失败），
只是 `Unavailable` 不再等于"死路"——它在这次按压内会被消化掉。

### 2.3 顺带修掉的第二道死锁

`autoEnrollUnlocked` 旧守卫是「范围为空集 ⇒ 不做」。但 `QUICK_UNLOCK_SCOPE` 的空集有
**两种**含义（见 `VaultixPreferences.QUICK_UNLOCK_SCOPE_CONFIRMED` 的 KDoc）：
未确认 = 默认全部库；已确认 = 一个都不要。旧写法把前者也当成后者 ⇒
**只有单个 KDBX 库的用户永远纳不进来**（他没有别的库可纳入，范围就永远是空集）。
现在改为同时判 `isQuickUnlockScopeConfirmed()`。

### 2.4 测试

- `LocalUnlockEnrollmentAutoEnrollTest` 补 3 条：`范围为空集但从未确认过_默认全部库_该封`、
  `已经有房间信封_直接短路_不再烧一次KDF`、原「空集」用例改名并补 `CONFIRMED = true`；
- `LocalUnlockFanoutTest` 补「补建成功 ⇒ 重试一次 ⇒ 结论以重试为准」与
  「`Opened` 不触发补建」。

## 三、#244：误报冲突的三层根因

### 3.1 根因 ①：令牌字段混用

`OneDriveGraphClient.toEntry()` 写的是 `versionToken = eTag ?: cTag`。
Graph 里两者语义不同：

| 字段 | 覆盖范围 | 什么时候变 |
|---|---|---|
| `eTag` | 整个 item（**元数据 + 内容**） | 改权限、服务端处理、挪目录…… |
| `cTag` | **只有内容** | 内容变了（官方口径，已知在 SPO 上会被重命名影响） |

上层拿它回答的是「远端**内容**变了没有」，答的却是"这个 item 动过没有" ⇒
用户什么都没改，也会判 `remoteChanged = true`。

修法：**cTag 优先、eTag 只在 cTag 缺失时兜底**，并把来源编码成前缀
（`ctag:` / `etag:`）—— 否则一次 `stat` 拿到 cTag、一次拿到 eTag，两者永不相等。

两个配套细节不能漏：
- `normalizeVersionToken` 必须先剥前缀**再**剥引号（`ctag:"abc"` 否则被剥成 `ctag:"abc`，
  既不等于旧值也不等于新值 ⇒ 每次同步都判"远端变了"）；
- 条件写（`If-Match`）前要剥前缀但**保留引号**，且**不能**复用 `normalizeVersionToken`
  （它剥引号，会把请求改成必 412）。`ctag:/etag:` 是内部格式，服务端只认字段原值。

迁移：`isSameVersionToken` 允许"只有一边带前缀"时去前缀再比；两边前缀不同则判为不同版，
不做"差不多就算一样"的猜测。旧库第一次同步仍可能不相等，由下面第 ③ 条兜住。

### 3.2 根因 ②：内容对账放错位置

`adoptRemoteIfSameContent` 只在 `localChanged == false` 那一支跑；真机局面是
**两个布尔都判 true** ⇒ 直接 `NeedsUserDecision`，**从来没有人验过内容**。

新增 `resolveConflictByContent`：冲突落锤前先对账一次 ——
字节逐字相同 ⇒ 对齐基线、返回 `AlreadyInSync`；不同（或读不到/解不开）⇒ 原样报冲突，
**一个字都不写**。它只消假冲突，不把真冲突判成没事。代价是真冲突时多下载一次整库，
换掉的是"用户明明没改却被拦下来赌自己删过什么"。

### 3.3 根因 ③：同步跑在主线程

`KdbxSyncRepositoryImpl` 的每个方法都直接在调用方上下文执行，而调用方全是
`viewModelScope.launch { … }` —— 默认 **Main**。`stat` + 整库上传 + AES 编解码
全在主线程 ⇒ 用户说的「覆盖点完就会卡死」就是主线程被钉住。

修法：仓库层全体 `withContext(Dispatchers.IO)`。调度器归**知道自己在做 IO 的那一层**，
不能指望每个调用点都记得套 —— 一处漏了就是一次卡死。

### 3.4 测试

- `VersionTokenEqualityTest`（新文件，7 例）：前缀剥离、跨格式迁移、两边前缀不同判不同版、
  空值语义、引号处理；
- `KdbxSyncOrchestratorTest` 补 3 例：两边都判 true 但内容相同 ⇒ `AlreadyInSync`；
  内容不同 ⇒ 仍报冲突；读不到远端 ⇒ 退回保守（报冲突）。

## 五、判据（写给下一个人）

1. **"先认证再授权"的流程里，依赖授权的副作用必须挂在认证之后** —— 挂在之前，条件恒假。
2. **入口不能以"能力已就绪"为前提**，否则用户永远无法第一次让它就绪。正确形状：
   入口常开，能力按需补建（`RoomEnroller` + 原地重试）。
3. **`suspend` 不等于不阻塞**。`viewModelScope.launch` 默认 Main；任何秒级 IO 都要
   由数据层自己切线程。
4. **令牌回答"动过没有"，回答不了"是不是同一份"**。凡是会让用户做有损决策的按钮，
   落锤前必须用内容再验一遍。
5. **空集/空值要连同"确认标记"一起读**。一个值两种含义时只取一种，必然挡住一类用户。
6. **同一个 bug 被报第二次，先问"上次修的是哪条路径"**。#241/#242 都只修了报障者
   走的那一条，另一条（KDBX 主密码路径 / 冲突的"两边都改"分支）原样留着。

> 「onedrive 上的 kdbx，解锁速度很慢很慢，我输入了密码，或者指纹解锁，依然很慢很慢。」

### 7.1 #245：查看锁页面的三件事叠在一起

截图里那句「正在派生密钥并解锁…（约需 1–3 秒）」是 `add_vault_working` 被 **复用**到了
查看锁分支 —— 而这一页**不做任何派生**（密钥已在内存，只等一次生物识别）。

| # | 问题 | 修法 |
|---|---|---|
| ① | 文案说谎 | 新增 `unlock_view_lock_verifying`（「正在等待身份验证…」），如实描述 |
| ② | 自动弹认证首帧抢跑（cipher 现备 + 等 RESUMED ⇒ 用户只看到转圈） | 自动弹**排除自动门禁**（`viewLockAuto`），只保留手动查看锁与快速解锁入口 |
| ③ | 自动门禁被取消后仍被钉在认证页 | 用户取消（非系统侧终止）⇒ `clearAutoViewLocks()` + 放行回库列表 |

`UiState.viewLockAuto` 与 `viewLocked` 必须**同一次** `copy` 写入 —— 自动弹认证的判据
正好读它们，分两次写会留下一帧"锁着但不知来源"的中间态。

### 7.2 #246：慢在哪里，先把 KDF 次数数清

KDF（Argon2d，用户实测 64 MiB / 46 轮）在这个项目里出现在三处：主解锁、
房间信封备料（`prepareKdbx` 的 `Kdbx.verify`）、每次改动后的保存。**任何一处多做一次就是翻倍**。

#243 引入的风险：主密码解锁成功后补建房间信封 —— 信封早就在的那些用户，
每次解锁都要多跑一遍 KDF。已加 `hasRoom` 短路。本轮又发现短路排在
`hasAnyLock()`（Keystore 往返）与 `quickUnlockScope().first()`（DataStore 读，冷启动可达数百毫秒）
**之后** ⇒ 绝大多数情况下仍白付这两笔。已把 `hasRoom` 提到方法**第一行**。

⚠️ 仍可能慢的两件事需要真机日志才能定，**不猜**：
- OneDrive 上每次解锁是否重新下载整库（缓存是否命中）；
- 指纹路径（`LocalUnlockFanout`）里 `rest` 是串行循环，库多时是 O(库数) 次 KDF。

排查命令：`adb logcat -s VaultixKdbxSync VaultixUnlock VaultixAutoViewGate`。

## 八、追加：切库/退后台就锁定，每次解锁都很慢（#246 第三批）

用户第二轮描述把方向彻底改了：

> 「切换密码库后，或者 vaultix 退出后台后，kdbx 就会锁定，虽然可以指纹解锁打开，但每次解锁都很慢。」

前一节还在查「网络往返」，这两句指向的是**会话被无谓销毁**。

### 8.1 三个真根因（全部静默：不报错、不崩溃，只让用户多等）

| # | 位置 | 缺陷形状 | 为什么一直没被发现 |
|---|---|---|---|
| ① | `lockOtherKdbxVaults` | 判据 `filter { it != keepVaultId }` 是**按「不是这个」筛**，不是按「是那个」筛。进 Bitwarden 库时所有 KDBX 都不等于它 ⇒ 全锁。而 `ItemsViewModel.init` **每次进任意库的条目页**都调它 | 不报错；而且**这条方法此前没有任何测试** |
| ② | `enrollJustAuthenticated` | `force` 写死 `true` ⇒ 跳过 `hasRoom` 短路。而它唯一"成功路径"调用点（`unlockKdbxInternal`）是**每次主密码解锁必走**的 | 表现是"慢"，没人会怀疑到"补建信封"这段逻辑上 |
| ③ | `FileKdbxFileCache` | 内容/令牌分两个文件写，中间被杀 ⇒ 新内容配旧尺寸 ⇒ 判成半截 ⇒ **删掉一份完好的缓存** ⇒ 重下整库 | 时好时坏，取决于有没有被杀在那个几毫秒的窗口里 |

> **判据**：① 属于 #215 那一族 ——「判据按"不是这个"筛」会把所有无关情况算进目标集合。
> ②③ 是同一个病的两面：**该省的 KDF 没省，不该丢的缓存丢了**。

### 8.2 「缓存到本地就快了」这个直觉不成立

Vaultix 早就有 `CachedKdbxFileSource`（命中时 `read()` 直接返回、`stat()` 丢后台），
比 KeePass2Android 还激进。缺的不是"加缓存"，是"别误删"（③）与"别多跑一次 KDF"（②）。

用用户自己的日志对照：

```
unlock 耗时分解：read=2837ms（30701B）+ open(KDF+解析)=334ms
```

⇒ 慢 8.5 倍的是网络；这个库的 KDF 只要 334ms，一点都不慢。

KeePass2Android 系感觉更快，真正的差别是**锁屏语义**：它们的 `QuickLock` 只锁 UI、
数据库对象留在内存；Vaultix 的 `lockAll()` → `Kdbx.lock()` 会销毁会话 ⇒ 必重跑一次 KDF。
这条**未做**，因为它是安全取舍（锁屏期间整库明文留内存），留给用户拍板。

另：kotpass 的 `Credentials` 只收 `passphrase` + `keyfile`，
`KeyTransform.transformedKey(kdfProvider, header, credentials)` 是唯一入口
⇒「信封直接存派生密钥、彻底跳过 KDF」走不通，除非 fork。

### 8.3 一个被测试当场抓住的设计错误

单文件缓存第一版把「剩余字节就是内容」当作 payload 长度 —— 于是**尾部截断无法发现**
（砍 3 字节照样解析出更短的 payload，交给 KDBX 就是"文件损坏 / 密码错"）。
`文件被截断_当作未命中并清掉` 直接报红，随后补了显式 `payloadLen` 字段。
**旧实现靠侧车尺寸做到的那道防线，不能在换格式时悄悄丢掉。**
