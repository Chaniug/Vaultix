## 2. 通行密钥注册：两层解析者，缺一不可

见 `issues/03` **#108**（RP 层）与 **#109**（浏览器层）。摘要：

| 层 | 谁在解析 | 失败表现 | 条目 |
|---|---|---|---|
| **浏览器** | Chromium `fido2credentialrequest_native_android.cc` → Mojo | `MojoClassFromJSON … field missing or invalid: publicKeyAlgorithm`，**整份响应丢弃** | #109 |
| **RP（服务端）** | 解析 `attestationObject`（CBOR） | 注册校验失败 | #108 |

### 决定性的取证顺序

`.ai/conventions/8.5` 的「**先证伪『自己失败了』**」直接救场 —— 系统侧两句
`Final credential received from: …VaultixCredentialProviderService` /
`finishing session with propagateCancellation false` 证明**我方全对**，
于是嫌疑只能落在"交给对方的形态"，直接压到字段级，不必再猜密码学。

### 验收（同一判据、前后对比）

| 判据 | 修复前 `dev-4edf866` | 修复后 `dev-924dd85` |
|---|---|---|
| `MojoClassFromJSON … publicKeyAlgorithm` | **2 次** | **0 次** |
| `Failed to convert response from CredMan` | **2 次** | **0 次** |
| `Final credential received from …VaultixCredentialProviderService` | 在 | 仍在 |

用户确认（Edge + `console.cloud.tencent.com`）：**注册成功**。

### 修法要点

`WebAuthn.buildCreateResponseJson` 的 `response` 补齐四项（对齐 Bastion 的响应构造）：
`publicKeyAlgorithm`(int, ES256=-7) / `publicKey`(DER SPKI) / `authenticatorData` / `transports`。
★ **新增的三个入参刻意不给默认值** —— 少任何一个都在**调用方看不见的另一侧**失败，
让编译器强迫调用点显式提供，是防"静默不完整"的唯一可靠手段。

### 6.1 ★★ 施工中发现并修掉一处**谎报成功**

`TotpCodesScreen` 原代码：

```kotlin
val codeToCopy = if (isExpiring) nextCode else code              // 算出来了……
val copyNow = { if (isExpiring) onCopyNext() else onCopy(code) } // 却没人用它
```

- `codeToCopy` 是**死变量**（全仓库只有注释引用）；
- 临期分支调的是 `onCopyNext()`，其接线**只弹一个 Snackbar**；
- ⇒ **剪贴板里什么都没放，界面却弹「已复制下一个验证码」。**

用户一直以为"临期会自动复制下一个码"——**实际只弹了提示，没有复制**。
改法：`copyAction(...)` 纯函数，**先复制（nextCode）、再提示**，两者由同一判据派生。

> **可复用纪律**：「提示成功」的代码必须与「做事」的代码**写在同一条路径上**。
> 只写提示不做事 = 谎报，比不做更糟（用户会以为成功、不再排查）。

### 6.3 ★★ §4 的能力边界（别误判）

**应用内只能读本进程 logcat**（Android 4.1+ 无 `READ_LOGS` 时只能读自己的 UID）。
⇒ 定位通行密钥时那句救命证据 `cr_ChromiumWebauthn: [CredManHelper] Failed to convert…`
**在应用内看不到**（那是浏览器进程）。**「应用内没报错」≠「没问题」**，跨进程仍须 `adb logcat`。
已写进 `DeveloperLogsDialog` 的文件头 + 界面提示文案。

### 6.4 「清空」的设计（不需依赖系统权限）

清空 = 尽力 `logcat -c` + **把时间下界推到"现在"**。
⚠️ 应用无 `READ_LOGS` 时清全局缓冲**可能被静默拒绝**（拿不到反馈）⇒ 若只靠它，清空就是假的。
⇒ 保证效果的是**时间下界过滤**；为此采集从 `-v time` 改为 `-v epoch`（时间戳可直接比较），
显示时格式化回 `HH:mm:ss.SSS`。

### 6.7 ★★ Actions 缓存：手动清理**效果远小于预期**

- 现状：长期贴 10 GB 上限（`gradle-transforms` 25 条 6.0 GiB + `gradle-build-cache` 27 条 2.1 GiB）。
- 新增 `.github/workflows/cache-cleanup.yml`：每周一自动 + 可手动触发；
  删「未访问 >7 天」且「不在该族最近 3 条内」的；
  **刻意不删全部**（清完全冷启动反而更慢）。
- ⚠️ **手动清理只释放约 0.5 GB**（100→98 条 / 10.42→9.92 GB），远低于按条数估算的 8 GB。

- ⇒ 教训：**清缓存要"先删再数"，别"先数后删"（快照会过期）**；
  占用真正的驱动是**每次 push 新增约 300 MB**（12 + 240 + 51 MiB 三块切片），不是陈年堆积。

### 6.8 ★★ 当天新踩的 Windows 陷阱（跨工具传行式数据）

Windows 版 Python 用 `open(p,'w')` 写文件会把 `\n` 变成 `\r\n` ⇒ 读回时每行尾部带 `\r`
⇒ **80 次 `gh cache delete` 全部因 id 非法失败**（且第一轮我把 stderr 吞了，看起来像"跑完了"）。
⇒ 修法：`tr -d '\r\n'`，或写入用 `newline=''` / 二进制模式。
⇒ 纪律：**跨 Linux 工具与 Windows Python 传行式数据时，先剥 `\r`；且别吞 stderr。**
