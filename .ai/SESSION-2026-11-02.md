## 二、三次运行，两个真缺陷

### 2.1 第一次（run 41368877377）— 嵌套 `cd`（→ #226）

**构建完全成功**，签名也验证通过，死在 `Collect APK + SHA-256`：

```
Detected release APKs:
 - full/release/app-full-release.apk
##[error]Invalid value. Matching delimiter not found 'EOF'
```

**「找不到 EOF 分隔符」** 看起来像 `$GITHUB_OUTPUT` 写法坏了，与真实原因毫无关系。

根因：#218（`5ec3189`）往这一步加了一行 `(cd app/build/outputs/apk && ...)`，
而该步骤**开头早就 cd 到同一目录**。从 apk 目录再往下找同名子目录 ⇒ `cd` 必然失败；
`shell: bash -e` 下失败即退出 ⇒ heredoc 的 EOF 没写完 ⇒ 报"分隔符找不到"。
真实原因 `cd: app/build/outputs/apk: No such file or directory` 就在上一行。

v0.10.4 没炸是因为 #218 在 v0.10.4 之后才进 main —— 这条回归从 `5ec3189` 起就躺着，
**下一次发版必炸**，而且 `release.yml` 在 main 上永远不会被 CI 验证。

### 2.2 第二次（run 41369516243）— 成功，但校验和不可用（→ #227）

发布成功，2 个附件都在。按用户视角验收时发现：

```
$ sha256sum -c checksums-sha256.txt
sha256sum: ./full/release/app-full-release.apk: No such file or directory
```

校验和文件里写的是 `./full/release/app-full-release.apk`（`find .` 的产物），
用户下载后文件名是 `app-full-release.apk` ⇒ **给了校验和却验不了**。

哈希值本身是对的（用 GitHub 服务端独立算的 `digest` 交叉验证过：`626dfaa0…` 完全一致），
问题纯粹在路径语义：生成端用构建目录结构，消费端用下载目录。

### 2.3 第三次（run 41371740088）— 成功

删掉嵌套 cd + checksums 改 `basename` 后重发，全绿。

> ⚠️ 重发是幂等的：`release.yml` 有「删除同版本既有 release/tag」步骤，
> 会先删再建。所以每次 `push rele` 都是"重建这个版本"，不是"新增一个"。

## 五、这轮的三条通用教训

1. **「构建成功」≠「发布成功」，而报错信息可能完全指向错误的方向。**
   `Matching delimiter not found 'EOF'` 让人去查 YAML / output 写法，
   真实原因在它上一行。读 CI 日志要从**第一条** `##[error]` 往上找。
   同时：`bash -e` 下任何一步失败都会让后面的 heredoc 一起烂掉，
   "分隔符没闭合"几乎总是**上游某条命令失败**的马甲。

2. **「有校验和」≠「校验和能用」。**
   生成端看到文件里有哈希就以为完事，而消费端的路径语义完全不同。
   验收要在**用户的场景**里做（下载到同一目录、照文档执行），不是在生成端 `cat` 一眼。

3. **只验"通过"是不够的，要验"能失败"。**
   哈希校验、签名校验、断言这类东西，恒真与正确在成功路径上长得一模一样。
   改坏一个字节看它红不红，成本几秒 —— #227 的本地验证第三步就是干这个。

另有一条环境坑：**zsh 里 `path` 是 `PATH` 的数组别名**。
`while read -r hash path` 会把 `PATH` 覆盖成 APK 路径，之后 `basename`/`cat` 全部找不到。
CI 用 `bash` 不会炸，所以这类问题**只在本地跑才暴露** ——
"CI 绿了"不能替代"本地跑过一遍"。

[`issues/05-KDBX本地库-part6.md`](./issues/05-KDBX本地库-part6.md)。

| # | 一句话 | 属用户点名的哪一块 |
|---|---|---|

| 229 | 新建 / 加入的网盘库 `syncStatus` 留 null ⇒「立即同步」入口消失、**首次改动漏推** | onedrive 同步 |

### 同时完成的前置修复（上一轮尾巴，本次一并验证）

- OneDrive 分片重试与服务端真实进度对齐（`OneDriveGraphClientChunkRetryTest`，3 例 + 变异验证）
- WebDAV origin 改 base64url，避开 SQLite 的 `LIKE` 通配 `%`/`_` 与 `trim()` 语义
  （`WebDavVaultOriginTest`，5 例）
- 云盘建库时 origin 不得被 `remoteId`（OneDrive 那是 **itemId**）顶掉
  （`KdbxCreateRepositoryTest`，1 例；顶掉后建库"成功"、下次解锁报"没有可用的文件来源"，**不可恢复**）

### 三个值得记住的教训

1. **`runCatching` + `isSuccess` 是一个能把"失败"整段吞掉的组合**。
   凡是"这个结果决定要不要记成功"的地方，`Result` 必须**三个分支都写出来**，
   `getOrNull()` 为 null 时必须有显式的失败路径。#228 就是这个组合的直接产物。
2. **`null` 在一个可空列上往往有语义**。`vaults.syncStatus` 的 null 是
   「**该库不适用**网盘同步」，不是"还没同步过"。#229 把两件事混成了一个 null，
   后果是入口消失 + 首次改动漏推，而且**没有任何报错**。
   给可空列补值时，顺手**用整行 `upsert`** 又是一个坑：漏抄一列 = 静默清空一列。
3. **"写了" ≠ "用得到"**。`AddKdbxScreen` 一直支持"选文件 → 输密码 → 入库"，
   但没有任何外部入口能把文件递给它 ⇒ 用户在文件管理器里只看到「没有可打开此文件的应用」。
   验收要站在**用户的起点**（他是从哪点下去的），而不是从我们的 Activity 往里看。

## 五之三、KDBX 库加固轮 · 第二批（同日第三节）：保障本身成了代价 · #232–#233

上一批的形态是"某个分支的结局写反了"；这一批**正好相反** —— 两道防线都正确，
但都**无条件**用了最重的手段。所以验收标准不是"能不能省"，而是
**「省掉这一步有没有精确报红的用例」**。

| # | 一句话 | 用户点名的哪一块 |
|---|---|---|
| 232 | OneDrive 每次保存都把远端整库重下一次做读回校验 | onedrive 同步 |
| 233 | 上传成功后远端缓存里的版本令牌被永远留成旧值 ⇒ 每次解锁都挂**假的**「远端有更新」角标 | 同步（用户可感知） |

### 232 的关键取舍：元数据只能证明"不一致"，永远证明不了"一致"

第一版加了"远端 `lastModifiedDateTime` 明显早于本次写入 ⇒ 判不一致"。
写完一跑，`写成功后必须读回一次并比对内容` 立刻红 —— 假条目时间是 2026-10-17、
"现在"是 2026-11-02，于是**每一次正常保存**都被判成"远端回滚"。

⇒ 时间戳**降级为诊断线索**（`suspiciousTimestamp`，只在报错文案里追加一句"远端时间戳可疑"），
**永不参与结论**。判据只留一条：远端记录的大小 ≠ 写入字节数 ⇒ 内容不可能相同 ⇒ 直接判冲突。

⚠️ **反向绝不成立**：大小相符 ⇒ 仍然必须下载逐字节比对。所以 `readBackPlan()`
没有"证明一致"这一档，只有 `MISMATCH_PROVEN` 与 `NEEDS_BYTE_CHECK`。
把"元数据相符"当"内容一致"，是这条路上最容易犯、也最难查的错。

### 233 的关键：两份真相必须有收敛机制

`vaults.remoteVersionToken`（服务端给的最新版）与缓存里的 `versionToken`（这份字节对应哪一版）
各存一份，而成功路径只更新前者。于是：上传成功 → 缓存仍是旧令牌 → 下次解锁 stat 到新 eTag
与旧令牌不等 → 判"远端已变" → 重下一次（内容完全相同）+ 置 `STALE` + 标 `REMOTE_CHANGED`。
用户什么都没改，界面上一直挂着「远端有更新」。

修法是 `CachedKdbxFileSource.recordUploaded(bytes, newVersionToken)`：上传成功后把两个真相
**一起**刷新，并把新鲜度直接置 `VERIFIED`（这不是猜 —— 刚写完的字节与刚拿到的令牌本就对应）。

### 这一轮踩到的两个"工具坑"（都比 bug 本身更值得记）

1. **测试是假绿**：第一版断言"缓存令牌变成新值"——但 `CachedKdbxFileSource.write` **自己**
   就会用写入结果刷新缓存（#172 时代的行为），有没有收敛回调都成立。
   变异验证（删掉接线仍然全绿）当场抓到 ⇒ 改成断言**只有收敛才能做到的事**：`freshness` 变 `VERIFIED`。
2. **变异后仍然全绿，先怀疑"没编译"**：把 `onUploaded = { … }` 整行删掉后测试还绿，
   `javap` 一看，增量编译根本没重编译那个 class。⇒ 变异要选编译器**看得见**的形态。

### 验证

- `:data:kdbx:test` 绿；`:data:repository:testDebugUnitTest` **244 例 0 失败**；
  `:app:testFullDebugUnitTest` **533 例 0 失败**；`detekt` 绿（`ThrowsCount` 红过一次，
  按"按结局种类拆函数"解决，**没有**放宽阈值）

## 五之四、KDBX 库加固轮 · 第三批（同日第四节）：本地 SAF 也别每次都整份读 · #234

第 7 篇那条线的延续。`SafKdbxFileSource` 的版本令牌是**内容 SHA-256**（这个选择对：
`lastModified` 只到秒，同秒内改两次看不出差异），但实现把"算令牌"与"读完整份文件"绑死了
⇒ 解锁、每一次后台校验、每一次同步都要把本地库完整读一遍。

修法是**先证明，再省**：记住上一次整份读的摘要**与那次读的时间区间**，下次只查元数据，
"修改时间早于区间起点 + 大小一致" ⇒ 那段区间里文件没被动过 ⇒ 摘要就是现在这一版。
证据另加两根支柱：库变更序号（本进程每次成功写 `++`）与 #185 的写侧内容指纹。

### 这一轮最值得记的对照

| | 比的是什么 | 时间戳能不能当结论 |
|---|---|---|
| #232（OneDrive 读回） | 服务端时钟 vs 本机时钟 | ❌ 只能当诊断 |
| #234（本地 SAF） | 同一个时钟源的两次读数 | ✅ 可以 |

⇒ 差别从来不是"时间戳准不准"，而是**谁的时钟**。

### 两个自己撞出来的问题

1. **区间判据只判"里面"**：第一版写 `window.covers(modified)`，于是"读完之后又被改"
   被放行 —— 而那不是理论漏洞（`stat()` 到 `write()` 之间别的 App 完全可能改一笔）。
   用例 `修改时间晚于读区间 必须重读` 当场抓红，改成 `modified >= window.startedAt`。
2. **状态挂在短命对象上，等于没挂**（与 #233 同一个坑）：`generation` 只在同一实例内有效，
   而 `fileSourceFor` 每次新建 SAF 实例 ⇒ 序号恒为 0，保护静默失效。改为按 origin 复用。

### 验证

- `SafCachePolicyTest` 14 例；四组变异全部精确报红后还原
- `:data:repository:testDebugUnitTest` **258 例 0 失败**；`:app:testFullDebugUnitTest` **533 例 0 失败**
- `detekt` 绿；全部脚本门禁绿（`check_issues_index` 33 条一致 / `check_md_links` 186 文件）
- ⚠️ **诚实记录**：判据是纯函数，单测覆盖的是**判定**；"一次 stat 实际少读多少 IO"只能靠真机
  `VaultixKdbxSaf` 日志验收，本轮未取证。
