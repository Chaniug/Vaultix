## 一、这一轮在做什么、为什么

用户此时在睡觉，留下的线索是"KDBX 与 Bitwarden 两条链都自称完成"。
我给自己出的题不是"还有几个功能没做"，而是：**两条腿各自健康吗** ——
尤其是那些"用户下一个动作才知道"的地方。

⇒ 审计方法就一句：**对每个「成功」的返回点，问它凭什么说是成功的**。
后来发现这一问值七个坑 —— 它们的共同点是：**全都向用户报了"成功"**。

其中最值得留存的**判据**（已写进对应分篇）：

- **#153**：`catch` 之后返回兜底值 ≠ 有保护。`catch (_: Exception) { "0".repeat(digits) }`
  把异常**美化成一个假的有效结果** —— 用户拿着 `000000` 只会怀疑自己。
- **#154**：畸形输入的"能解析成功"不等于"能用"。`toIntOrNull` 认 `0`。
  ⚠️ 更要命的是"边上有保护的那条路径看起来正常"（`generateTotp` 有 catch 所以不崩），
  **它会掩盖紧邻的真崩溃**（`remainingSeconds` 是无 catch 的纯计算，跑在 Composable 里）。
- **#155**："从请求体反推本地快照"这个方向**天然有信息缺口**。要认真逐个回答"哪些字段请求体里根本没有"。
- **#156**：id 会被服务端替换的流程，**同一事实存两份**（内存 op 列表 + 库里队列行）⇒ 修一处等于修一半。
- **#157**：`applied` 默认 `true` ⇔ 把"没做存在性校验"这条缺省路径**变成了成功**。
  ⇒ 凡表达"改动是否真的发生"的标志位，默认必须是"没发生"。
- **#158**：注释里写"由某某兜底"时，**当场确认那个调用点存在**（#147 的第二次发作，同一出错形状）。
- **#159**：安全属性要"跟着载体走"（生命周期级），不能是"每个页面记得写一行"。

## 三、几个实现上的取舍（留给下次改同一处的人）

- **#153 归一化放在哪**：只放 `generateHmac` **一个咽点**（不放每个入口）——
  URI / KDBX 独立字段 / 位置式 `30;6;SHA1` 三条路径最终都要过它，**不可能有"某个入口忘了"这种漏法**。
- **#155 顺延而不是"塞进请求体"**：把 `organizationId` 等塞进 `CipherRequest` 会改变**提交语义**
  （尤其 `attachments`，server 侧会当成"要更新附件"）⇒ 只在本地落库时从 `previous` 顺延。
- **#158 只解码不重编码**：原本一次写要付两遍 KDF（`mutate` 编一次、`verify` 再编一次）。
  ⇒ 新加 `verifyEncoded` 只做反向那一半。**"太贵所以被跳过"从来不该是一场正确性保障的下场。**
- **#158 顺手把五个写动作统一 `withContext(Dispatchers.IO)`**：`mutate` 的 KDoc 早就要求调用方切调度器，
  而 ViewModel 是在主线程协程里调它们的 ⇒ 每次保存同步跑一遍 Argon2。
  ⇒ **调度责任收在 public 层一次做完**，而不是指望每个调用点各自记得切。
- **#159 不抽 `SecureActivity` 基类**：抽基类要改 10 个文件的继承关系，且每加一个 Activity 仍需**记得继承**；
  生命周期回调反过来：**新 Activity 默认被保护**。
- **#159 覆盖 `onActivityCreated` 而非只 `PreCreated`**：前者全版本回调（只在 `Activity.onCreate()` 之后，
  但**远在第一帧呈现之前**，对 `FLAG_SECURE` 不构成问题）；后者补 API 29+ 的更早时机。两者幂等。

## 五、副产品：ISSUES 索引**第四次**漂移（#160）

补 #153–#159 时顺手核对索引，发现的是同一件事再犯一遍：**"改哪篇顺手改那个数字"这条约定已失效四次**。
四种形态各留一个实例：

1. **标题层级写错 ⇒ 从未被计入**：01 篇 #102–#105 是 `###` 三级标题，被埋在 #101 的层级下。
2. **增量式改法**：06 篇题注 33 → 34（应 +4），**上一轮刚加的 #142–#144 从来没进过名单**。
3. **数字与名单互不可证**：03 篇写「18 条」却只列 **16 个号**。
4. **跨表错位与重复行**：#88 正文在 04 却列在 06 表；#128 在 01 表重复两行；#83 两表都列、正文里没有。

七篇差额（实际 − 索引列）= **12 / 0 / 1 / 0 / 4 / 4 / 13** 条。
⚠️ 02、04 这次**恰好为 0** —— 这不能当作"不用查"的依据（与 #145「卡片颜色既不能证明也不能否证」同构）。

**解法**：`.ai/tools/check_issues_index.py` 全量重数（查三处相等）+ `tests/selftest_issues_index.py`
**6 例正反用例**（反向要求"报错必须落到被改坏的那一处"——只看有没有输出，看不出它抓错了东西）。
现在七篇的状态是：**索引 = 题注 = 正文**。

⚠️ **重号不修**：#50（02 vs 03）、#103（01 vs 06）是历史上两个坑共用一号。改编号会让代码注释里
`见 .ai/ISSUES.md #NN` 全部失真 ⇒ 维持编号 + 登记到 `KNOWN_DUPLICATES` + **要求引用处带分篇名**。

**三条可迁移的判据**（写在 #160 末尾）：
① 数字不许用增量算，必须从源头重数；② 同一事实的两处表达要同时校；
③ 人的注意力落在自己刚碰过的东西上 ⇒ 漏的永远是别人的（或上个月的自己）。

## 七、CI 实证：绿卡片说谎的一次（记进 01 篇 #145.1）

第一轮 CI（run `36949293837`，head `ccd2e22`）**job 卡片是 success**，但拉日志后：

```
> Task :core:common:compileDebugUnitTestKotlin FAILED
e: …TotpTest.kt:471:40 Unresolved reference 'parse'      （共 6 处）
BUILD FAILED in 51s
```

- 根因：`TotpGenerator.parse` 不存在 —— 解析入口是 `OtpUriParser.parse`。
  修法：把这 6 处改正确的 receiver（`f2a9438`）。
- ⚠️ 更值得记的是**我是怎么差点漏掉它的**：
  ① **卡片是绿的**（单测步 `continue-on-error: true`）；
  ② 我按惯例跑 `grep -c '^e: '` 得到 **0** —— 因为 GitHub 日志每行带时间戳前缀，
     `e:` 不在行首 ⇒ **这个 0 是"没匹配上"而不是"没有"**；
  ③ **其余四个模块的单测照常跑完**（bitwarden/repository/kdbx/app 都出现且无 FAILED）
     ⇒ "别的都正常"很容易让人以为挂的那个不重要。
  三条合起来 ⇒ 我把要下的那句话写进了 #145.1：**计数为 0 时，先确认这个 0 是真的、
  还是检查本身有一条静默的假通过路径。**
- ⇒ 修复后我**没有再信一轮 CI**：先做本地定向自检（把 `<类型>.<成员>()` 的调用
  逐个核对成员是否存在），并**做了变异测试**（把修复处改回 `TotpGenerator.parse`
  ⇒ 精确报出 471 行），才推第二轮（run `36950743186`）：`e:` **0**（这次用 `(^|Z )e: ` 查的）·
  三个 BUILD SUCCESSFUL · `:core:common:testDebugUnitTest` 真执行 ⇒ **13 条新断言真的跑了**。

## 八、收口后用 token 复核 CI（2026-10-02 深夜，记进 01 篇 #145.2）

用户给了 GitHub token ⇒ 把上面那轮"真绿"复核了一遍，顺带发现**另一种没有证据的情形**。

### 复核结论：run `36950743186` 确认真绿

```
e:                                       0        （(^|Z )e: 计数）
BUILD SUCCESSFUL                         3        （"BUILD FAILED" 那行是脚本里的 grep 匹配串）
FAILURE: / FAILED:                       0
:core:common:compileDebugUnitTestKotlin  通过
:core:common:testDebugUnitTest           无后缀 ⇒ 真执行
```

⚠️ **复核时差点误读的两处**：
1. 日志里确实有一行 `BUILD FAILED` —— 那是 workflow 里的一句
   `grep "BUILD FAILED" /tmp/build_log.txt | head -40`，**是匹配串不是构建结果**。
   按 `BUILD (SUCCESSFUL|FAILED)` 计数会把它混进来。实际 3 SUCCESSFUL / 0 FAILED。
2. **不能说"六个模块单测都跑了"** —— 只有 `:core:common:testDebugUnitTest` 真执行，
   其余五个（crypto / model / bitwarden / kdbx / repository）全是 `FROM-CACHE`
   （它们没改，命中缓存是正常的）。
   ⇒ **改了哪个模块就只看哪个模块的任务行**，别拿总数当证据。

### 新发现：最近两次推送压根没触发 CI（#145.2）

`actions/runs` 列表里最新仍是 `36950743186`（head `f2a9438`），
而我们已经推了 `81abaa2` 和 `4d9bfc5` ⇒ **没有新 run**。

根因：`ci-debug.yml` 的 `on.push.paths` 是**白名单**，只认
`.kt/.java/.xml/.json/.gradle/.gradle.kts/.kts/.toml/.sh/gradle/**/.github/scripts/**/config/**`，
**`.md` 与 `.py` 都不在列**。

⇒ 与 #145.1 是**两种相反成因的"没有证据"**：
- 145.1 = **有 run，结论是假的**（卡片绿、日志红）；
- 145.2 = **根本没有 run**（没变化 ≠ 没问题，只是没被测）。

**共同判据**：「CI 没报错」四个字本身不构成证据。
且 **`.ai/tools/check_*.py` 六个探针永远只靠本地跑** —— 改完探针说"CI 是绿的"等于什么都没说。
