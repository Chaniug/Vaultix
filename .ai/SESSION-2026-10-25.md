## 2. 真正的问题和审计写的不一样

审计的推演是「token 被提前推进到 v2，会话还停在 v1 ⇒ 下次同步会算错」。
但实际危险更直接，**token 根本不需要被提前推进**：

```
远端 v1 → v2（另一台设备改的）
→ 同步报 REMOTE_CHANGED（基线令牌仍是 v1 ⇒ 这个判断是对的）
→ 用户在旧会话上编辑并保存
→ 主写路径 saveVia(expectedVersion = 缓存里的 v1)
→ 服务端说"还是 v1" ⇒ 条件写**通过** ⇒ 远端 v2 被基于 v1 的内容静默覆盖
```

主写路径带的就是**缓存里的旧令牌**，它天生不满足"内容与令牌配套"这条乐观并发前提。
⇒ **令牌回答的是"远端动过没"，回答不了"我手里这份是不是它"。**

## 3. 两道防线

| 层 | 位置 | 做什么 |
|---|---|---|
| 令牌层 | `KdbxSyncOrchestrator` | 「只有远端变」分支**不推进 token**；改做**内容对账**（`adoptRemoteIfSameContent`）：内容相同则降级 `IN_SYNC`，不同则保持 `REMOTE_CHANGED` 且一个字节都不写 |
| 内容指纹层 | `KdbxBaseStore` + `Kdbx` + `KdbxItemRepository` | 每库记「写回基线」内容指纹；`mutateLocked` 在**改动之前**取指纹比对，结论随 `KdbxPendingWrite.baselineAligned` 上浮；`persist` 落字节前抛 `StaleBaseline` |

新状态 `KdbxWriteFailure.StaleBaseline` 一路贯通：
`KdbxSyncResult` → `KdbxSyncReport` → `VaultActionsController.Outcome.SyncStaleBaseline`
→ 两处 toast（设置页 `vault_result_sync_stale_baseline` / 列表页 `kdbx_sync_stale_baseline`）。

## 4. 四个坑（全部是本轮实测踩到的）

### 4.1 不能拿 `encode` 的字节哈希当指纹

`KdbxEncoder.encode` 内部 `regenerateVectors` **每次重派生内容密钥 + 重生成 IV/随机流**
⇒ 同一份库编两次字节**必然不同**。拿它当"内容变没变"的判据，等于**所有库永远算变过**。

这条是我写完第一版之后在 `KdbxEncoder` 类头读到的（类头早就写了这件事），
立刻推翻重做。⇒ 指纹改为对**明文映射内容**（`KdbxMappedContent`）做 SHA-256。

### 4.2 不能为了比指纹再 `encode` 一遍

一次编码 = 一次 KDF（真机数百毫秒）。为比较而多编一遍，这种代价迟早被人关掉，
而关掉的那一刻防线就没了（与 `verifyWrite` 那套"太贵所以被跳过"是同一类教训）。
⇒ 顺带给 `KdbxRoundTrip.verify` 加了 `encoded` 重载，避免"判指纹的字节"与"写出去的字节"不是同一份。

### 4.3 不能把 `updatedAt` 算进指纹

首次实现把 `updatedAt` 一起喂进摘要，结果**连"同一份内容编两次"都对不上**：
远端那份是别的设备重编码的，`<Times>` 与本地完全是两回事 ⇒
"远端只是重新编码、内容一模一样"被判成"内容变了"，本该省掉的一次「请先同步」照样弹。

更要命的是**它挡不住真正的危险**：覆盖远端丢的是"别人改的字段值"，而字段值已经逐字进摘要。
⇒ 取舍：**宁可在时间戳上宽一点，也不能在字段值上漏一点。**

### 4.4 🔴 `saveVia` 里不能"现查会话内容"比基线

这是本轮最贵的一个坑。天然想法是在 `saveVia` 里写：

```kotlin
if (baseline != null && baseline != KdbxEncoder.contentFingerprint(session.content)) reject()
```

**这是错的**：走到 `saveVia` 时 `session.content` 已经是**改完之后**的内容
（`mutateLocked` 在写锁里就把会话换成了新那一份），而基线记的是**改之前**那一版
⇒ 两者必然不等 ⇒ **每一次正常保存都被判成"内容过期"**。

实测表现：14 条用例红了 4 条，日志里 `bl=f05aa5… sn=64bf63… eq=false`，
而会话里的条目标题已经是"本机改过"。

"基线对不对"只能在**改动之前**判断，而 `mutateLocked` 已经在做 ⇒
结论随 `KdbxPendingWrite.baselineAligned` 递上来，`saveVia` 只负责**执行**这个结论
（`baselineAligned: Boolean?` 三态：`true` 放行 / `false` 拒写 / `null` 不表态）。

## 5. 两条"只对某条路径"的边界（也是实测逼出来的）

1. **闸门只对"有云端来源"的库生效**。本地 SAF 库没有"远端那一版"这个概念，
   基线永远不会登记 ⇒ 无条件判它等于把所有本地保存拦住。
   实测后果：`KdbxItemRepositoryTest.登录与安全笔记照常放行并落盘` 直接红了。
2. **同步编排器那条写路径传 `baselineAligned = null`（不表态）**。
   它推的是"会话里的全部改动"，可能是"上次编辑后一直没推上去"的旧货 —— 那时基线本来就对不上。
   这条路径的正解是**条件写**（`lastKnownVersion`）：远端真在期间变过，服务端会拒写并转 `CONFLICT`。

## 6. 顺带修掉的一个真 bug（不是本轮引入的）

`if (error is KdbxStaleBaselineException) return Result.failure(...)` 这段写在
`source.write(...)` 的 `getOrElse` 里 —— 但基线闸门在**写之前**就返回了，
那段翻译**永远走不到**。它不会报错，只会让人以为"翻译过了"。
⇒ 删掉，闸门处直接返回 `KdbxWriteFailure.StaleBaseline()`。
