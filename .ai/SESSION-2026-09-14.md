### ★★ 两条最重要的方法论沉淀

**1. 「照抄配置」比「照抄代码」更危险 —— #90**

`noHistory="true"` 是从 Bitwarden **照抄配置**来的（`.ai/issues/02-自动填充.md` #82 的
注释里甚至列了它），但**两家回灌架构不同**：Bitwarden 走 NEW_TASK + 独立进程回灌，
本项目走「**留在栈上等 `onResume`**」。⇒ 同一个属性在两种架构下**语义相反**
（`noHistory` = 不可见即销毁，与「留在栈上」物理互斥）⇒ `onResume` 永不触发 ⇒
解锁返回后回灌静默丢失。

⇒ **照抄配置前必须先问"对方为什么要这么配"**。已记入 `#90`。

**2. detekt 挂了会「掩盖编译错误」—— 又一次实证**

CI run `34812174915` 失败根因是 **detekt（13 处）**，而 detekt 跑在 **compile 之前**
⇒ **编译阶段的 bug 根本没机会暴露**。实测：修完 detekt 后真跑编译，才发现
`ImportExportScreen.kt` **缺 `android.net.Uri` 的 import**（提交时就漏了，从未被编译过）。

⇒ **「修完 detekt 必须再真跑一次 compile」这条纪律再次被验证，务必遵守。**

### Passkey「使用次数」仪式感（bastion 原实现已查清）

**bastion 做法极简，完全可复刻**：

| 项 | 实现 |
|---|---|
| 数据 | Room 表 `passkeys`：`last_used_at: Long`、`use_count: Int` |
| 更新时机 | **签名成功后**（非保存时）+1 |
| SQL | `UPDATE passkeys SET last_used_at=?, use_count=use_count+1, sign_count=? WHERE credential_id=?` |
| UI | 详情页「活动」分区：创建时间 / 最近使用 / 使用次数 |
| 代码 | `PasskeyAuthActivity.kt:540-555`（更新）· `PasskeyDetailPanes.kt:124-182`（展示） |

⚠️ **关键细节**：bastion 是**异步更新、不阻塞签名返回**——不能因统计拖慢登录。

**Vaultix 落地条件良好**：
- `SettingsViewModel.passkeyCount` **现成可用**（口径注释很到位，只是 UI 未消费）；
- `PasskeyGetActivity` / `PasskeyCreateActivity` 链路完整，**埋点位置现成**；
- `VaultFido2Credential` 已有 `counter` 字段可复用为 `useCount` 近亲。

⚠️ **风险（与 bastion 的最大差异）**：`VaultFido2Credential` **参与 Bitwarden 导入导出**
（bastion 那张是纯本地表）⇒ 新增统计字段**必须做序列化兼容测试**
（官方 DTO 无此二字段，导出时应跳过），否则可能污染导出文件或破坏往返一致性。
项目已有 `CipherMapperTotpUriFido2Test` 可扩展。
