## 一、bug 现象与根因

**现象**（两件，一起在"给写路径补单测"时暴露）：

1. `OneDriveKdbxFileSource.write` 在 `expectedVersion = null`（无基线）时，
   `simpleUpload` **一个条件头都不发** ⇒ Graph 直接覆盖同名文件。
2. 更严重：`createUploadSession` 的请求体是**手拼字符串**，
   `append(if (forceReplace) "replace" else "fail")` **值没加引号**，
   实际发出的是 `{"item":{"@microsoft.graph.conflictBehavior":fail}}` —— **非法 JSON**。
   Graph 回 400 ⇒ **任何 > 2MiB 的库在 OneDrive 上从来没存进去过**。
   小库走简单上传，根本不经过这段代码，所以长期无人发现。

**根因**：

- ①「`expectedVersion = null`」被当成了"随便写"的许可。而 `KdbxFileSource.write`
  的契约是**无基线 ⇒ 退化为最严保障**（`SafKdbxFileSource` / `WebDavKdbxFileSource`
  都做了写前预检 + 写后读回，**只有 OneDrive 两样都没有**）。
  一直没炸，是因为唯一的无基线调用方 `Kdbx.createVault` 恰好先 `stat` 过 ——
  **那是调用方的自觉，不是来源层的保证**。一旦新增一条无基线写入路径，就是静默数据丢失。
- ② 手拼 JSON。少一对引号，编译器一声不吭。

## 二、修法

### 2.1 接口加独立参数，不靠 null 推断

```kotlin
suspend fun write(
    bytes: ByteArray,
    expectedVersion: String? = null,
    force: Boolean = false,
    failIfExists: Boolean = false,   // ← 新增
): KdbxFileWriteResult
```

⚠️ **为什么是独立参数而不是"`expectedVersion == null` 就当只创建"**：
null 表示"没有基线"，`failIfExists` 表示"文件存在就是错"，**两者不是同一件事**。
`force` 也是独立参数，同构。靠 null 推断等于把一个语义塞进另一个语义的空值里，
下一个人加第五种组合时必然读错。

四个象限（KDoc 里有完整表）：`failIfExists`（只创建）/ `expectedVersion != null`
（条件写）/ `force = true`（无条件强写）/ 全默认（无基线 ⇒ 写前预检 + 写后读回）。

### 2.2 三个来源各自对齐

| 来源 | 落点 |
|---|---|
| SAF | 在 `openOutputStream(uri, "wt")` **之前**先读一次，存在就抛 `KdbxFileConflictException` |
| WebDAV | 强制丢弃基线（`if (failIfExists) null else normalizeVersionToken(...)`），改发 `If-None-Match: *` |
| OneDrive | 简单上传发 `If-None-Match: *`；分片上传改用 uploadSession 请求体的 `conflictBehavior: "fail"` + **不带 `ifMatch`**；并补**写后读回校验** |

`Kdbx.createVault` 传 `failIfExists = true`；`CachedKdbxFileSource` 原样透传。

### 2.3 OneDrive 写后读回（`verifyReadBack`）

先比 size 做廉价预筛（大小都不对就别浪费一次完整下载），再下载逐字节比对。
**读不回来也算冲突** —— "以为存好了其实没有"是这类同步最坏的失败模式。

顺带**复用 `write` 已取到的 token**（原先 `token()` 再取一次 = 多一个网络往返 +
两次可能不是同一个 token，排查时对不上）。

### 2.4 请求体改由序列化器生成

```kotlin
val sessionBody = json.encodeToString(
    OneDriveUploadSessionRequestDto(
        item = OneDriveUploadSessionItemDto(
            conflictBehavior = if (forceReplace) "replace" else "fail",
            ifMatch = expectedETag?.takeIf { !forceReplace && !failIfExists && it.isNotBlank() },
        ),
    ),
)
```

`Json` 显式打开 `explicitNulls = false`（否则 `"ifMatch": null` 会一起发出去）。

## 四、四个"顺带踩出"的坑（都写进 #172 了）

1. **`Uri.encode` 是 Android 桩方法**：`unitTests.isReturnDefaultValues = true`
   让它返回 `null` ⇒ `encode(...) must not be null` 的 NPE，**任何**走 Graph 的
   JVM 单测都跑不起来。⇒ 换纯 Kotlin `percentEncodePathSegment`（顺带消掉一个
   没必要的平台依赖）。**注意**：这是"测试环境暴露了生产代码的一个平台耦合"，
   不是测试写错了。
2. **`runTest` 测不了真线程**：裸 `runTest` 用虚拟时间，而 `upload` 是
   `withContext(Dispatchers.IO)` ⇒ 断言抢在拦截器之前执行；
   改 `runTest(Dispatchers.Default)` 直接抛 `Dispatcher must implement TestDispatcher`。
   ⇒ 这类"要验真实请求长什么样"的用例用 `runBlocking`（本来就不需要虚拟时间）。
3. **Hilt 不接受"带默认值参数的 `@Inject constructor`"**：Kotlin 为默认值生成的
   合成构造与 `@Inject` 那个撞车 ⇒ `may only contain one injected constructor`。
   ⇒ 改 `@Provides`；类还要 `open`（mockk 给 final 类打桩要挂 inline agent）。
4. **detekt `ThrowsCount` 的守卫子句规则**：`excludeGuardClauses: true` 只把
   **"第一条非声明语句之前的 throw"** 当守卫放行，**前面出现一次 suspend 调用后
   就不再算守卫**。实测三步才收敛（详见第五节）——**没有放宽阈值，也没有加 `@Suppress`**。

## 五、detekt 那一小时的收敛过程（值得记）

`verifyReadBack` 里有三个失败分支（大小不符 / 读不回 / 读回不一致），
而 `ThrowsCount` 上限是 **2**。三次改写，每次实测：

| 版本 | 报数 | 原因 |
|---|---|---|
| `getOrElse { throw ... }` | 3 | lambda 里的 throw **也算一条** |
| `?: throw f(error ?: Default)` | 3 | 嵌套 `?:` 的另一支**同样被计数** |
| 先把异常算成局部变量 | 3 | —— 说明问题根本不在括号形状 |
| 抽 `verifySize`，预筛挪出本函数 | **2 ✅** | 本函数只剩两条 throw |

关键认识来自反编译 `detekt-rules-style` 的 `JunkKt.isGuardClause`：
`guard` = **序列里第一条既不是 guard、也不是 super 调用、也不是局部变量声明**的语句。
所以 `runCatching { suspend() }` 这条语句会先把 guard 位"用掉"，
后面再多的 throw 一律计数。**而这把钥匙刚好解开锁**：大小预筛语义上本来
就不该和"读回"挤在一个函数里——它是一次**廉价预判**，失败模式与后面的
"下载失败/内容不符"不同。**门禁逼出来的形状，恰好是更好的形状。**

## 八、⚠️ 本轮最贵的一课：本地"1155 例全绿"是**假的**

推到 CI 后 run `39042480023`（commit `75ae07f`）的 `Run unit tests (hard gate)` **红**，
其余步骤（detekt / 编码 / Build APK / preview 发布）全绿 ⇒ 不是编译错误，是**测试真的挂了**。
而我本地同款命令 `--rerun-tasks` 跑了 1155 例 0 失败。

**用 A/B 实验隔离（而不是猜）**：

| 实验 | 改动 | CI 结果 | 结论 |
|---|---|---|---|
| A | 把 18 个改动 `.kt` 移出构建路径 + `strings.xml` 还原基线 | **全绿** | 红与本次改动相关，环境/配额无关 |
| B | 注入一条 `fail("CI 探针")` | `Run unit tests (hard gate)` **红** | 该步骤在 push 链路**确实执行且无 `continue-on-error`** ⇒ **红是真的，本地绿是假的** |

**本地为什么绿**：沙箱 `~/.gradle`（2.5 GB）里早就有 10-17 上午那一批构建的
`gradle-build-cache` 记录 ⇒ 任务是 `FROM-CACHE`，**执行用例被跳过、但 test-results
从缓存里被"恢复"回来**。所以我上一轮立的"XML mtime 晚于启动时刻"这条判据，
在这个场景下**完全失效**——XML 确实是新的，里面的结果却是旧的。

⇒ 新判据（已写进 #173）：**只有任务行是 `> Task :x:test…` 而不是 `FROM-CACHE` /
`UP-TO-DATE` 的执行才算数**。`--rerun-tasks` 能治 `UP-TO-DATE`，**治不了 build-cache**。

⚠️ 另外两件事：
1. **不要**为了"消毒"去 `gh cache delete` 清 CI 侧缓存——若清了之后 CI 再红，
   本来清晰的"与改动相关"会退化成"与冷缓存相关"，**把一次隔离实验变成两次未知**。
   要清只清本地。
2. 加取证步骤时踩了 YAML 坑：`- name: [TEMP PROBE] …` 里的方括号**被当成流序列**
   ⇒ workflow 解析失败 ⇒ run 0 秒 `failure` 且 `jobs: []` 是空的。
   **步骤名别用方括号开头。**（取证探针与其后的 A/B 提交已全部 revert，
   `git diff 75ae07f 8c365dd` 为空。）

**待办**：单测到底红了哪几例，仍未取证（CI 日志与工件下载都需要 token，匿名 401；
已备好临时取证步骤的做法与踩坑记录，下一轮拿到 token 或换手段再取）。
