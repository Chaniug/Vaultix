## 一、bug 现象与根因

**现象**：KDBX 库新建一条**空备注的安全笔记**（表单备注字段可空，只填标题 +
自定义字段完全合法），保存时看着正常；退出再进 / 下次解锁，条目**变成登录**——
用户名/密码两行空字段杵在详情页，条目落进「登录」分类与筛选。

**根因**：KDBX **没有条目类型概念**（KeePass 标准五键里没有"这是安全笔记"），
`KdbxItemMapper.toVaultItem` 靠纯启发式推导：

```
无用户名 && 无密码 && 有笔记 ⇒ SecureNote，否则 Login
```

空笔记的安全笔记三个标准字段全空 ⇒ `isNote=false` ⇒ **类型静默翻转**。
写入侧从未把类型信息落盘，读侧自然无从恢复。
Bitwarden 侧类型是服务端显式存储字段，无此问题 —— 又是「两个库两种命运」。

## 二、修法：沿用 A1 的 `VPX_` 工具区模式，读侧三态

| 文件 | 改动 |
|---|---|
| `KdbxToolFields.kt` | 新增 `SECURE_NOTE` / `SECURE_NOTE_TRUE`；`isSecureNoteTrue` 与 `isFavoriteTrue` 共走私有 `isTruthyFlag`（宽松真值 `true`/`1`/`yes` 唯一口径） |
| `KdbxItemMapper.kt` | `isNote = fields.secureNoteMarker() ?: 启发式`；新增文件级私有扩展 `secureNoteMarker()`（大小写不敏感查键，同 `favoriteFlag`） |
| `KdbxItemWriter.kt` | 链上插入 `applySecureNote`：类型未变一字不动 / SecureNote 写 `"true"`（已是则不碰）/ 离开 SecureNote 删键（含大小写变体） |
| `KdbxItemWriterTest.kt` | 9 条新用例（见下） |

**两个刻意的设计决策**（KDoc 有完整论证，ISSUES #169 有摘要）：

1. **读侧三态，不压布尔**：`secureNoteMarker()` 的 `null` = 「没有标记」
   （第三方条目 ⇒ 回落启发式），`false` = 「标记显式为假值」（用户把安全笔记
   改成了登录型 ⇒ 信标记）。压成布尔就等于宣布「没有标记的条目都不是笔记」——
   第三方库里的安全笔记会一夜之间全部变成登录，**比原 bug 波及面更大**。
   这是 #121「三态压二值」的同款事故，本篇第二次撞同一堵墙。
2. **只写 `"true"` 不写 `"false"`**：收藏「缺失即假」是对的（没星就是没星），
   而类型**缺失不等于登录**——第三方工具写的笔记型条目靠启发式判安全笔记，
   KeePass 生态就是这个 convention。给每条登录镶一个恒假字段纯属噪音。
   代价：「Vaultix 自建的、只有笔记的登录条目」仍会被启发式判成安全笔记——
   该内容形态本身歧义，且与第三方工具的解释一致，可接受。

## 六、A6：标准字段受保护属性丢失（`d50463f`，ISSUES #170）

承接「还有哪些明显的 bug」继续对拍 KDBX 读写两侧，发现 `applyDomainFields`
里 Title / UserName / Notes **无条件写 `EntryValue.Plain`**，只有密码走
`passwordValue` 保留 `Protected="True"`。

- **实锤位置在编码器**：kotpass 的 `marshalFields` 只对 `EntryValue.Encrypted`
  写 `Protected="True"` 属性 ⇒ 我们把第三方受保护字段降级成 Plain 之后，
  **落盘即丢保护属性**。值不丢（读侧 `.content` 两种都解密），
  但「内存保护」这种安全属性静默翻面，用户无从察觉。
- **修法**：`protectedAware(existing, key, value)` 泛化原 `passwordValue`，
  四个标准字段一律走它。语义与 typed accessor 逐字等价（都是
  `fields[BasicField.X.key]` 的 Map.get，大小写敏感的已知坑不变）。
- **测试 2 条 + 反证**：受保护的用户名/备注更新后保护不丢值不丢（主用例）；
  未受保护的不被无端加密（反证——把用户没标的字段升级成 Encrypted
  同样是一种改坏用户库）。变异验证（`protectedAware` 恒 Plain）精确 2 红：
  主用例 + **既有的密码用例**，反证保持绿。

## 七、A5 提案被自己的测试推翻（查证后驳回，本轮最贵的一小时）

接着想修「KDBX 条目时间戳」：读 `createEntry` / `updateEntry` 都没写 times，
mapper 却消费 `times?.`，看着像"新建不设时间戳、编辑不刷最近修改"。
**先写了测试再动手** —— 然后测试接连打脸：

1. 「新建条目带时间戳」用例**没有我的改动也绿**：kotpass 的 `Entry` 数据类
   默认 `times = TimeData.create()`（创建/访问/修改/位置四个时间全填 now）。
   空转测试，删。
2. 「第三方条目没有 Times」用例**红**：`times` 为 null 的条目经
   `modifyEntry` 后 creationTime 变成了带纳秒的 now。
3. 读 kotpass 0.13.0 源码（`database/modifiers/Entry.kt`）找到答案：
   私有的 `Group.modifyEntry` 内部就会
   `times?.copy(lastAccessTime = now, lastModificationTime = now) ?: TimeData.create()`，
   `moveEntry` 刷 `locationChanged`。**时间戳全链路上游已经包了**，
   我们自己写不仅多余，还会被上游用**原条目的** times 重算后整个盖掉。

**⇒ A5 不是 bug，整段撤销。** 留下的资产：
- `updateEntry` / `createEntry` 注释里的查证记录（防下一个人再"修"一遍）；
- 一条**契约护栏测试**（`更新条目刷新最近修改时间且不碰创建时间`）钉住上游
  行为——kotpass 升级后若它变红，先查上游改了没有，别下意识在我们的
  writer 里再写一遍刷新逻辑。

**两条教训**（比 A6 本身更值钱）：
1. **「代码里没写」≠「没发生」** —— 数据类默认值、上游修饰器都是隐形写点。
   读第三方库的行为不能只看调用点，要读它的源码/字节码。
2. **空转测试比没有测试更糟** —— 它给人"这里有守护"的错觉。
   判别标准：**把修复回退掉，测试必须变红**（本轮 A6 就是这么验的）。
