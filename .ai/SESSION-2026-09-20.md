## 2. 两个独立成因（都改了）

### 2.1 让位少算了一个系统栏内边距 ★ 主因

`FullScreenDialogShell` 是「叠加式」全屏壳：正文铺满，标题栏/底栏用 `Box` 叠在上面，
正文靠 padding 让位。两条栏的 modifier 链是

```
.background(surface)  →  .statusBarsPadding() / .navigationBarsPadding()  →  自身 padding
```

⇒ 它们**实际占位 = 系统栏内边距 + 栏自身高度**。而正文此前只让了**栏自身高度**这一个常量：

| | 栏实际占位 | 正文让位 | 差额 |
|---|---|---|---|
| 顶部 | 状态栏 24 + 56 | `TITLE_BAR_HEIGHT` = 56 | **少让 24dp** |
| 底部 | 手势条 24 + 80 | `ACTION_BAR_HEIGHT` = 80 | **少让 24dp** |

状态栏高的机型（36 / 48dp）少让更多。正文首/末元素因此正好落在那条不透明色带底下。

**修法**：改成 `contentClearance(inset, barHeight) = maxOf(barHeight, inset + barHeight)`。

- 取**实测** `WindowInsets`（与两条栏同一份）而不是再加一个常量 —— 常量只是把
  "少让"换成"多让"，换个机型仍然偏；
- `maxOf` 兜底：insets 读到 0（全屏 / 桌面模式 / 尚未分发）时不能退化成"零让位"。

抽成 `internal` 纯函数并加单测 `ContentClearanceTest`（5 例，含不变式"让位 ≥ insets + 栏高"）。

### 2.2 卡片底色与栏同色，看不出"穿越" ★ 观感成因

`ItemFormDialog.FormGroupCard` 用的是 `surfaceContainerLow`，而两条栏是 `surface`。
M3 亮色基线实测对比度（我算的）：

| 色 | hex | vs `surface` 对比度 |
|---|---|---|
| `surfaceContainerLow` | `#F7F2FA` | **1.049** |
| `surfaceContainerHigh` | `#ECE6F0` | 1.164 |
| `surfaceContainerHighest` | `#E6E0E9` | **1.232** |

1.049 肉眼等同同色 ⇒ 卡片滑到栏下面时，用户看到的是"被遮住"而不是"从下面穿过"。
**修法**：改用 `surfaceContainerHighest`（1.232），给卡片一个真实的边界。

> ⚠️ 卡片自己加描边**不是**解法 —— 那会让"穿越"变成"一堵墙从标题下钻出来"。

`ItemFormDialog` 是「新建条目」与「卡包」共用的 ⇒ 这一处改动同时覆盖用户报的两个页面。

### 2.3 验证码编辑页：字段从来没有分组卡片

`TotpEditDialog` 的字段是**平铺的裸 `OutlinedTextField`**（`Spacer` 相连），
没有 `FormGroupCard` ⇒ 滚动时输入框描边直接切在栏下面，看起来就是"被遮住"。

**修法**：把 `FormGroupCard` 从 `private` 提为 `internal`，验证码页也用它分两张卡
（基本字段一张、类型参数一张；Steam 无可调参数 ⇒ 不出第二张）。顺带删掉四个
`TotpXxxFields` 开头那个现在多余的 `Spacer(Spacing.sm)`。

## 5. 第二轮反馈：尺寸对了，但**不沉浸**

> 「大小现在确实合适了，但是页面不沉浸，滑动的时候上下也不是透明，
> 跟密码条目页面、验证码条目页面的效果不一样。」

### 5.1 根因：栏底色写死成不透明，恒不淡出

§2.1 只修了**让位**（内容不再被遮），但两条栏的底色仍是写死的
`.background(MaterialTheme.colorScheme.surface)` —— **恒 alpha = 1** ⇒ 内容滑到栏下
就被盖住，"穿过"看不见。而列表页顶栏走的是 `VaultixExpressiveTopBar`：

```kotlin
val barBackgroundAlpha by animateFloatAsState(
    targetValue = if (collapseFraction < 0.5f) 1f else 0f,   // ← 滚了就透明
    animationSpec = tween(ANIM_MS),
)
```

⇒ **一边会淡出、一边不会**，这就是"效果不一样"的全部原因。

### 5.2 修法：把列表页那套口径搬过来（不是新发明）

| 参数 | 取值 | 来源 |
|---|---|---|
| 收起判定 | 滚动偏移 > `Spacing.sm` | 同 `COLLAPSE_THRESHOLD` |
| 过渡 | `tween(200ms)` 快照式 | 同 `ANIM_MS` |
| 淡出对象 | **只有底色**；文字/按钮不淡 | 同顶栏（图标与标题也不淡出） |

两条栏都改成 `surface.copy(alpha = barAlpha)`，并**保留原来的 modifier 顺序**
（`background` 在 `statusBarsPadding()` 之前）—— 顺序反了状态栏那一条会永远留着底色。

### 5.3 ★ 一处**有意保留的差异**：底部条不做成悬浮胶囊

> ## ⛔ 本条已于本轮（§7，2026-09-20 第四轮）被**推翻**，仅作"一次走错的判断"的样本保留。
>
> **原文（保持不变）：**
>
> 列表页底部是 `VaultixBottomDock`（**悬浮胶囊**，四周留白、底部透出内容），
> 所以它的"沉浸"来得更容易。而本页是同一扇 `Dialog` 窗口里的**满宽操作条**，
> 底部必须一直可点 ⇒ 只做到"淡出底色"这一档，**不**改成胶囊。
> 已写进代码注释：若哪天要做成胶囊，改的是那里，不是在外面再叠一层。
>
> **为什么错**：「可点」与「满宽」是**两件无关的事** —— 我把它俩当成了同一件。
> 列表页底栏就是胶囊，且恒在最上层、从不挡点击。§5.3 真正想防的是
> "**半透明**、看不出能点"，而胶囊是**不透明**的，从一开始就不违反这个诉求。
> 更关键的是：**满宽 + 与页面同色**这个组合本身就是两条黑带的来源（见 §7）——
> 本轮用户报的就是它。
>
> **正确表述**（已并入 `conventions/8.4`）：
> **可点性由"不透明 + 恒定在最上层"保证，与"是否满宽"无关。**
> 底部条**应当**做成胶囊，与顶部、与列表页底栏同规格。

> 顺带说明为什么**不**给按钮加 scrim：加了就是一条恒定的灰带，
> 等于把刚去掉的不透明底色换个颜色装回来。

### 6.1 胶囊阴影闪动（`475ac2a`）

**两个成因叠在一起**，只修一个不够：

| # | 成因 | 机理 |
|---|---|---|
| ① | **判据不一致** | 底色的判据是补间**之后**的值（`barBackgroundAlpha`），阴影却用**原始**的 `collapseFraction`。手指一越过阈值 `collapseFraction` 立刻跳变、阴影当场翻，而底色还要等 200ms 补间走完 ⇒ 那 200ms 里"阴影没了底色还在"，看起来就是**阴影在闪** |
| ② | **`shadowElevation` 一变就重建渲染层** | M3 的 `Surface` 用 `graphicsLayer{ shadowElevation }` + 阴影轮廓实现，高度值一动，阴影几何要重算、图层轮廓缓存作废 ⇒ **掉帧** |

**改法**：阴影固定为 `PILL_SHADOW = 1.dp`（恒定，不参与动画）。

为什么不只统一判据（①）就够：统一了判据只是让两者**同步**变，但 ② 的
"变一次重建一次"依然存在 —— 只有**恒定值**才能让这层阴影在整个动画期间一次都不用重算。

> 对照：`VaultixBottomDock` 的 6dp 阴影本来就是恒定的，从不参与动画，
> 所以那里一直没有这个问题。**这里才是那个例外。**

### 6.2 「配色单一」—— 排查结论是**强调色缺语义**，不是缺颜色

先做了用量普查（`MaterialTheme.colorScheme.*` 全仓计数）：

| 角色 | 次数 | | 角色 | 次数 |
|---|---|---|---|---|
| `onSurfaceVariant` | **110** | | `primaryContainer` | 3 |
| `primary` | 48 | | `secondaryContainer` | 3 |
| `error` | 48 | | `surfaceVariant` | 3 |
| `surfaceContainerHigh` | 11 | | `tertiaryContainer` | 2 |
| `tertiary` | 4 | | `secondary` | **0** |

`primary` 有 48 处，说明**不是没在用强调色**。真正的问题是两处**语义缺失**：

**a) 同一个概念在不同页面各挑各的色（`capabilityTint`）**

修正前 `ItemsScreen.kt` 与 `ItemDetailScreen.kt` **各写一遍**
`tint = MaterialTheme.colorScheme.tertiary`。想调通行密钥的色相就得记得改两处，
忘一处就又制造出一组不一致。现在收进唯一出处：

```kotlin
enum class Capability { TOTP, PASSKEY }
@Composable fun capabilityTint(capability: Capability): Color  // TOTP→primary, PASSKEY→tertiary
```

**b) 首字母头像全是灰的（`fallbackAvatar`）—— 这才是"单一"的主因**

三个列表页左端那个 40dp 头像，取不到站点图标时**原本恒为 `surfaceContainerHigh`
+ `onSurfaceVariant`**。而**兜底才是常态**：自建 Vaultwarden 不开图标代理、
局域网地址、KDBX 库（origin 是 `content://`）全都走兜底。
一屏几十条里最显眼的一列元素全是灰的 ⇒ 观感自然"单色"。

改为按**标题哈希**取 12 档色相之一。三个设计约束：

1. **用哈希，不用随机/下标**：颜色必须对同一条目**恒定**。随机的话滚动一遍颜色就变，
   用户会把"颜色"误读成"状态"（以为条目变了）。
2. **明度 0.32，不是直觉上的 0.45**（★ 实测调出来的）：
   白字要求对比度 ≥ 4.5:1，而**青黄两色的相对亮度远高于红蓝**——
   | 明度 | 12 档中最差的白字对比度 | |
   |---|---|---|
   | 0.45 | **2.57** | ❌ 青黄区完全读不清 |
   | 0.32 | **4.75** | ✅ 全部达标 |
   二分求解的实际上限是 0.331，取 0.32 留余量。
3. **避开 `Int.MIN_VALUE`**：`seed.hashCode().absoluteValue` 对它是**负数**
   （32 位补码没有对应的正数），会算出负色相 ⇒ `Color.hsl` 行为未定义。
   改用修正式 `(x % n + n) % n`。

> ⚠️ 别把"配色单一"理解成"要加更多颜色"。M3 的**大面积容器**（页面底、卡片、对话框）
> 本就该低饱和，那里加色即是反模式。着力点是**小面积、语义明确**的元素。

新增 `AvatarHueTest` 5 项钉住上述性质（色相范围 / 12 档 / 同种子恒定 /
不塌缩 / `Int.MIN_VALUE` 不炸）。纯算术，不需要 Compose。

## 7. 第四轮 · 反馈 A：通行密钥「网页端保存后校验不出」（★ 协议结构 bug）

> 用户原话：「app 好像无法正常通过网页保存通行密钥。这是怎么回事」
> 追问确认现象：**「能弹出，能保存，但是网页端校验不出来已保存的」**

### 7.1 根因：`attestationObject` 的 CBOR 键名写成了 `attestationStatement`

`core/common/.../WebAuthn.kt` 的 `buildNoneAttestationObject`（手工拼 canonical CBOR）。
W3C WebAuthn L2 §6.5.4 规定顶层 **3 个键、键名逐字固定**：`fmt` / `attStmt` / `authData`，
且 `fmt = "none"` 时 **`attStmt` 仍须存在、值为空 map**。

我写成了 `attestationStatement`（20 字节文本）⇒ RP 按规范读 `attStmt` 取不到键
⇒ attestation statement 缺失 ⇒ 注册校验失败。**客户端全程无异常**（它只是往 map 里塞键，
从不校验键名）⇒ 症状正好是"能保存、但校验不出"。

字节级证据（纯 Python 独立复现）：

```
修正前： … 0x74 "attestationStatement"   ← 74 = text(20)
修正后： 0x67 "attStmt" 0xA0             ← 67 = text(7)，A0 = 空 map（必须存在）
```

修法：改键名 + 补 KDoc 规范依据 + 给 `writeText` 加防御性 `require`
（它只支持短头 `< 24` 字节，长键名会**静默写坏长度头**，比键名写错更难查）。
已核实现有 4 处调用（3/4/7/8 字节）全部 < 24。

### 7.2 ★ 单测把错误行为**锁死**了 —— 比 bug 本身更值得记

`WebAuthnTest.kt` 原本有 `assertThat(text).contains("attestationStatement")`
⇒ 测试**永远绿**、且**反向保护了 bug**（谁改对反而红）。这就是它能活到真机反馈的原因。

修复：断言升到**字节级 + 反向锁**（`attStmt` 必须存在 / `attestationStatement` 必须不存在 /
`0x67` 文本头 / `0xA0` 空 map / `0x58` 长度头 / 嵌入 authData 相等）。

## 9. 第五轮 · 反馈 B 再更正：黑带的**真根因在窗口层**，胶囊方案作废

> ⛔ **§8 的结论（"改悬浮胶囊"）已被本轮推翻。** 本节是这条链路的**终点**，也是第四次返工。
> 四轮的用户反馈依次是：
> ① 「上边标题部分和下方部分遮住了显示内容」（真 bug：让位少算 insets）
> ② 「页面不沉浸，上下也不是透明」
> ③ 「上方下方还有黑色的…造型不好看」⇒ 我改胶囊，**把问题弄严重了**
> ④ 「上下胶囊都好长，太碍眼了」⇒ 缩短胶囊
> ⑤ 「上下胶囊不好看，太碍眼了。而且上下滑动的透明效果也没做好。能有更好的方案吗 material3 里面有什么好的实现方案吗」

### 9.1 ★ 第三轮为什么"越改越糟"（本节最重要的一句）

**胶囊四周留白，恰好把 `Dialog` 窗口的黑色露了出来。**
—— 黑带从来**不是**栏的形状问题。**满宽栏反而能盖住它**，
这就是"改成胶囊后黑带更明显"的**全部**原因。四轮里前三次都改错了地方。

### 9.2 两条真根因

| # | 根因 | 说明 |
|---|---|---|
| **A** | `window.statusBarColor` / `navigationBarColor` 在 **`targetSdk ≥ 35` 上是 no-op** | Android 15 强制 edge-to-edge，旧 API 失效。原代码两行赋值是**死代码**，而 `@Suppress("DEPRECATION")` 把"它已不生效"这个信号一起压掉了 ⇒ 一直没被发现 |
| **B** | `Dialog` 窗口**不继承** Activity 的 edge-to-edge | 窗口类型 `TYPE_APPLICATION_PANEL`；window background **来自主题 = 黑色**。窗口顶/底**一旦留白，黑色就露出来** |

### 9.3 定稿：满宽薄栏 + 与 `surface` 匹配的三档渐变保护层

依据 = 官方 edge-to-edge 指南（`developer.android.com/design/ui/mobile/guides/layout-and-content/edge-to-edge`）：
**Do** 栏不吸顶时加**与背景匹配的渐变**；**Do** 系统栏半透明、UI 从下方滚过；
**Don't** 渐变与各 pane 背景**不匹配**；**Don't** **叠加**多层 status bar 保护。

**窗口层修法两条（缺一不可）**：

1. `window.setBackgroundDrawable(ColorDrawable(surface.toArgb()))`
   ⚠️ 设 **`surface` 而非 `transparent`** —— API 35+ 在三键导航下仍会按 window background
   叠 **80% 遮罩**，设透明的结果**还是近黑**。设 `surface` 后遮罩叠在同色底上 = "同色加深"，
   符合官方的"渐变保护必须匹配背景 pane"。
   ⚠️ 必须用 `setBackgroundDrawable`：资源 id 表达不了**运行时**底色（浅色/深色/OLED/取色）；
   `decorView.setBackgroundColor` 只改 DecorView 层、**改不到 Window 层**。
2. `dialogWindow.isNavigationBarContrastEnforced = false`（默认 `true`）——
   它会在三键导航下把导航栏压暗 20%，正是底部那条"半黑带"。
   （`isStatusBarContrastEnforced` 在 API 35+ 已是 no-op，无须碰。）

**形状回到满宽的理由**：`RoundedCornerShape(Int)` 是**百分比**语义，在「宽满屏 × 高 48~72dp」
的扁容器上被**高度钳死** ⇒ 两端半圆、中间长直线 ⇒ **扁椭圆枕头**（用户："好长""太碍眼"）。
M3 无组件用此形状。满宽栏把窗口边缘的黑底**盖住**，配合渐变层正好满足官方 Do 的两条。

### 9.4 落地数值（`FullScreenDialogShell.kt`）

| 常量 | 值 | 口径 |
|---|---|---|
| `BUTTON_MIN_HEIGHT` | `48.dp` | M3 触摸目标下限（**必须声明在最前**，见 §9.5） |
| `BAR_VERTICAL_PADDING` | `Spacing.md` = 12dp | 两栏**共用同值** |
| `TITLE_BAR_HEIGHT` | `48 + 12×2` = **72dp** | 顶部**栏体**高（不含状态栏） |
| `ACTION_BAR_HEIGHT` | `48 + 12×2` = **72dp** | 底部**栏体**高（不含手势条） |
| `GRADIENT_TAIL` | `Spacing.xl` = 24dp | 渐变过渡尾段 |

- `contentClearance(inset, barHeight) = maxOf(barHeight, inset + barHeight)` —— **公式与签名不变**，
  口径**退回"栏体自身高"**（§8 那个"含胶囊留白"的 `68/84dp` 已作废）。
- 新增 `layerHeight(inset, barHeight) = inset + barHeight + GRADIENT_TAIL`；
  `TitleBar` / `ActionBar` 的 `.height(...)` 与 `topGradientStops` 的分母**共用它**。

### 9.5 ★ 不透明段 ≡ 正文让位（纯算术验证 PASS）

| inset | 顶部不透明比例 | 顶部不透明长 | 顶部让位 | 恒等 |
|---|---|---|---|---|
| 0dp | 0.750000 | 72.000000 | 72.0 | ✅ |
| 24dp | 0.800000 | 96.000000 | 96.0 | ✅ |
| 36dp | 0.818182 | 108.000000 | 108.0 | ✅ |
| 48dp | 0.833333 | 120.000000 | 120.0 | ✅ |

底部同表（镜像算法，`1f - 尾段占比`），**互差 1e-9 以内**。

**这条恒等式是"`FormGroupCard`（`surfaceContainerHighest`，与 `surface` 不同色）不会透进
不透明段"的全部依据** ⇒ 不需要额外机制（**不改**卡片色、**不加** scrim）。
⚠️ 反过来说：若哪天改了让位公式而没同步渐变，卡片就会开始从栏底透出来。

⚠️ 比例**必须按实测 inset 算**：写死 0.7 时，24dp 机型栏体上沿实际要在 0.80 ⇒ 标题区提前变透明。
