## 一、§2.2 + §3.7：第四张表 `UiSize`（为什么是"第四张"而不是"扩充 `Spacing`"）

### 问题不是"18 不在标尺上"

审计原话是「`Spacing` 标尺被大面积绕过，且**已经事实上出现了新档位**」。这句里的两个分句
指向两件不同的事，混在一起做就会做错：

| 分句 | 真问题 | 不是问题 |
|---|---|---|
| 「被绕过」 | 同一语义在不同页面取了不同值（同为"列表行"，设置页 20dp / 条目卡 16dp / 删除确认行 16dp） | 字面量本身 ——`Spacing` 纪律第 2 条「不在标尺上的值保持字面量」在**独立版式决定**上仍然成立 |
| 「事实上出现了新档位」 | `18.dp` 出现 26 次 / 12 文件，它已经是"行内小图标"这个**语义**了 | 值本身不对 —— 改成 16 或 20 都是**设计变更** |

⇒ 所以本轮**只抽语义，不动数值**。一个 `.dp` 数字都没改，改的是"它有没有名字"。

### 三张表变四张，分工写死在 KDoc 里

| 表 | 回答的问题 | 判据 | 文件 |
|---|---|---|---|
| `Spacing` | 两个元素**之间**留多少 | 它在两个东西**中间** | `theme/Spacing.kt`（既有） |
| `VaultixCorner` | 元素**外轮廓**有多圆 | 看它有多高（分档不按组件） | `theme/VaultixCorner.kt`（2026-10-19 建） |
| **`UiSize`** | 元素**自己**有多大 | 它是**独立存在**的图标 / 进度圈 / 触摸目标 | `theme/UiSize.kt`（**本轮新建**） |

`UiSize` 九个成员，每个都带着"谁在用"的说明：

```kotlin
object UiSize {
    val InlineIcon: Dp = 18.dp            // TextButton 图标槽 / 字段尾部复制·眼睛
    val SecondaryIcon: Dp = 20.dp         // 标题旁箭头 / 选中勾 / 拖动手柄
    val MicroIcon: Dp = 16.dp             // 只读角标（⚠️ 这一档不扩散）
    val InlineProgress: Dp = 18.dp        // 按钮里 / 字段尾部的小转圈
    val InlineProgressStroke: Dp = 2.dp   // 配合上一项
    val TouchTarget: Dp = 48.dp           // 只给 minimumInteractiveComponentSize / heightIn(min)
    val HairGap: Dp = 2.dp                // 同一块信息内部的两行
    val TightGap: Dp = 6.dp               // 徽章横内边距：4 太挤、8 太松
    val RowVerticalPadding: Dp = 10.dp    // 可点整行的上下内边距
}
```

### 🔴 本轮最值钱的一条判据：**18 与 20 并存不是重复，判据是"它和谁并排"**

这是全轮唯一一个"看起来该合并、实际不能合并"的地方。想当然的做法是"统一到 18"或
"统一到 20"，**两边都会改版式**：

| 值 | 用在哪 | 合并的后果 |
|---|---|---|
| 18dp | `TextButton` 的默认图标槽内 | 改 20 ⇒ **把按钮顶高**（图标槽撑开行高） |
| 20dp | 标题旁的箭头、独立图形、勾选标记 | 改 18 ⇒ **视觉上比正文细一档，显小** |

⇒ **判据：并排的是 `bodyMedium`/`labelLarge` 正文 ⇒ 18；并排的是 `titleMedium` 或作为独立图形 ⇒ 20。**

### 四类 `Res / Detail` 密封类型，封的是同一个判据

不是"抽一个公共抽象"，而是**四处各自一个**：

| 类型 | 用在哪 | 为什么另起一个 |
|---|---|---|
| `UnlockUiError.Validation` + `validationTextRes` | 解锁 / 添加库 | **复用既有范式**，扩枚举 6 项即可 |
| `CloudError`（新建） | 网盘账号 | `Res` 映射的资源集合不同 |
| `QuickUnlockText`（新建） | 快速解锁对话框 | 需要**格式化参数**（剩余次数、PIN 位数） |
| `SyncNotice`（新建） | 同步 / 删除结果提示 | 跨 `vaultlist` 与 `settings` **两包复用** |

> 🔴 **判据**：**这句话是不是我们自己写的？** 是 ⇒ `Res`（必须进 `strings.xml`）；
> 来源层已翻译 ⇒ `Detail`（原样透传，**不套前缀** —— 套了会变成「操作失败：主密码不正确」）。
>
> 🔴 **想抽公共抽象前先问**：除了"有 `Res` 和 `Detail` 两个分支"，它们还有共同行为吗？
> **目前没有。** 硬抽一个 `UiText<T>` 只会让四个包的依赖关系变怪。

`QuickUnlockText` 的形状（`data class` 里不能 `vararg` —— 会退化成数组引用比较，`copy()` 后判不相等）：

```kotlin
sealed interface QuickUnlockText {
    data class Res(@StringRes val id: Int, val args: List<Any> = emptyList()) : QuickUnlockText
    data class Detail(val message: String) : QuickUnlockText
}
internal fun quickUnlockText(@StringRes id: Int, vararg args: Any): QuickUnlockText =
    QuickUnlockText.Res(id, args.toList())
```

### 三处"顺手"的架构修正（都不大，但都是同类病）

**① 兜底文案归 UI 层，不归 ViewModel**

三个 ViewModel 各自写 `error.message ?: "未知错误"`。改成事件字段 `message: String?`，
**原样传 null**，由 UI 拼模板时换成 `error_unknown_no_detail`。
理由：「异常没细节时说什么」是**呈现决定**，而文案只能有一个家。

**② `LocalUnlockFanout` 拿不到 `Context` ≠ 可以写死中文**

它原来"镜像"了 5 个中文字面量常量，KDoc 写着「与另一处措辞必须一致，**靠 review 守**」——
那就是靠人守的双源，而且一行 `grep` 就能证明它已经漂移过。
改成产出 `LocalUnlockMessage` 枚举（只带资源 id），解析交给有 `Context` 的调用方
（`UnlockViewModel` 注入了 `@ApplicationContext`）。

**③ 内部标识串不上屏 —— 用枚举名当交接凭据**

`LocalUnlockFanout` 产出的消息要跨 `RoomUnlockOutcome.Unavailable.detail: String` 这道
**类型是 String 的缝**。做法是拿枚举的 `name` 当交接凭据，解析方认回来：

```kotlin
private fun lockMessageOf(detail: String): LocalUnlockMessage? =
    LocalUnlockMessage.entries.firstOrNull { it.name == detail }   // 不用 valueOf：失败路径不能再抛
```

同款还用在 `SEAL_NO_HOUSE_KEY = "seal:no_house_key"`：`LocalUnlockFanout` 拿不到房钥匙时
抛这个串，`QuickUnlockController` 认出后映射到 `quick_unlock_need_unlock_first`。

**④ 新增语义状态 `PinEnrollOutcome.HouseKeyMissing`**

原来是 `PinEnrollOutcome.Failed("pin_lock_needs_house_key")` —— 一个**给开发者看的串**被
当成用户文案透传了。新增枚举项，KDoc 写清为何不与 `SessionUnavailable` 合并：
会话在但房钥匙不在内存（解锁某个库即可）vs 会话没了（需重新登录）—— 合并会让用户
按错方向补救。

## 四、§2.5 顶栏四套收敛：**不做，理由与 §2.7 不擅自实现三档是同一个**

审计自己在建议里写着「需真机看折叠手感」。这句话决定了它的性质：

> **"折叠手感"是这一项唯一的效果指标，而它本地量不出来。**

本地能做的只有：改数值 → 编译通过 → Preview 里看一眼静态帧 → 结论"看起来还行"。
那不是验证，那是把"我猜"写成"已改"。所以本项**零改动**，留在真机清单里。

> 这条与 §2.7 是同一条纪律的两个应用面：
> **凡是"效果只在真机上可判"的改动，本地不做，宁可留着。**
> 空写一段无法验证的逻辑，比不写更糟 —— 因为它会伪装成"已完成"。

## 六、本轮踩坑（6 条，都能复现）

### ① 哨兵基线：特征串匹配的是「**引号之间的内容**」，不是整行

第一次登记写成 `FALLBACK_TITLE =` —— 那串在引号**外面**，`needle in text` 永远不命中。
而基线三列齐全、脚本也不报错 ⇒ 表现为"登记了但没用"，**极难自查**。
正确写法是 `验证码`。已把这条写进脚本 KDoc 与 §8.4 新纪律 6。

顺带：同一文件里若两处字面量内容相同，**一条特征串同时放行两处** —— 原因列要把两处都写清。

### ② 给 ViewModel 注入 `Context` 会连带炸两处直接构造它的单测

`UnlockViewModel` 加了 `@ApplicationContext context` 后，`StaleRoomResealTest` /
`UnlockViewModelTest` 报 `No value passed for parameter 'context'`。
补 `textContext()`：`mockk<Context>` + 反射把资源 id 映回符号名 ——
这样断言看的是"**用了哪条资源**"，而不是"中文写了什么"，比改断言更耐改。

### ③ 把 `when` 内联进已有大 `when` 的参数会顶爆圈复杂度

detekt 当场抓住（16 > 14）。想省一个函数的代价是拆两次才过。

### ④ 替换顺序踩坑：断言改到一半，残留的 `assertThat(detail).doesNotContain(...)` 编译不过

修的时候顺手发现一条测试**原本就没接返回值**（只 `verify` 副作用），
换成枚举断言后它退化成"半截测试"。补了 `isEqualTo(Degraded)` ——
**这类"改着改着发现原测试本来就虚"的情况，改断言时必须顺手补上，否则等于把洞带进下一轮。**

### ⑤ `check_compile_smells.py` 把 KDoc 里的 `R.string.xxx` 示例当成悬空引用

修法是**改文档写法**（去掉 `R.string.` 前缀），**不放宽脚本** —— 脚本是对的，
KDoc 里出现一个看起来像真引用的符号本来就该避免。

### ⑥ 🔴 **最阴的一条：daemon 崩溃会产生一份"看起来全绿"的测试报告**

本轮收尾时 `:app:testFullDebugUnitTest --rerun-tasks` 报了 `BUILD FAILED`，但
`test-results/*.xml` 里是 `tests=367 failures=0 errors=0` —— **零失败**。
只看 XML 的人会得出"测试全过、构建挂了是环境问题"的结论，然后放行。

真实情况是：**daemon 在跑到第 39 个套件时被杀**，剩下 3 个套件**根本没生成 XML**。
`failures=0` 不是"通过了"，是"没跑到"。

| 信号 | 骗人的说法 | 真实含义 |
|---|---|---|
| `failures=0 errors=0` | 全过 | 只覆盖**已生成 XML 的那部分** |
| `套数 = 39`（应 42） | — | **3 个套件被跳过，且没有任何报错** |

**⇒ 核数必须同时核「套数」。** 只看 `failures=0` 是不够的，必须
`tests=388` **和** `套数=42` 两个数都对上，才叫全绿。这一步不能省。

判据修正（已写进 `.ai/conventions/8.6-工程质量.md` 的核数纪律）：
> **测试门禁要核三个数：套数、用例数、失败数。** 少一个数都可能是"没跑到"伪装成"全过"。

本轮的处置：`gradle --stop` + `--no-daemon --max-workers=2 --rerun-tasks` 重跑，
得 `套数=42 tests=388 failures=0 errors=0`、`185 actionable tasks: 185 executed`、
XML 时间戳全落在当次运行窗口内。
