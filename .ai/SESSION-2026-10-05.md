## 二、KDBX 快速解锁 —— 三轮诊断，两次翻案

### 用户症状
锁 Bitwarden 库 → 切 OneDrive 的 KDBX 库 → 指纹 → 等很久。「这不是缓存在本地吗？」

### ★★ 翻案一：我错判「KDBX 不支持通行密钥」

我先说「KDBX 不支持，这是硬伤」。用户纠正后去读代码 —— **本项目 `KdbxPasskeyCodec.kt`
读侧早就实现了**（`KPEX_PASSKEY_*`，KeePassDX 插件约定，7 字段 + BE/BS 备份态）。
我甚至已经看到那个文件名却没读内容就下结论。

⇒ 正确的因果是：**格式完全支持，是本项目写回没做**（`KdbxPasskeyCodec:48` 自标
「只读映射，写回要等阶段 B」）。**把因果说反了。**

### ★ 查 Keyguard 用了什么方案

`AChep/keyguard-app` ★3360（D 盘有源码 `/d/Vaultix-refs/keyguard-app`，比 clone 新）：

| | Keyguard | Vaultix 当时 |
|---|---|---|
| 锁粒度 | **全局单锁**（`VaultState` 只有 Create/Unlock/Main，无 per-vault 态） | 一栋房子 N 个房间 |
| KDBX 信封 | **派生密钥**：`KeePassToken.Key.passwordBase64` + `EncryptedValue.fromBase64`（跳过 KDF） | 主密码（每次跑 Argon2） |
| 密文缓存 | **没有** | 有 |
| 实测 | 33 ms | 3.58 s |

⚠️ 关键对照：`DbUtils.kt` 里 `Key.toPassphraseOrNull()` 走 `fromBase64`（**跳 KDF**）
与 `String.toPassphraseOrNull()` 走 `fromString`（**跑 KDF**）是**故意成对**的。

### 翻案二：Argon2 不是主因

我说过「Argon2 每次重跑 ⇒ B2 最多省 4%，不值得」。
**占比对**（4–10%），**结论错**：BW 33 ms vs KDBX 344 ms 是**用户能感觉到的差距** ⇒ B2 该做。

### ★★★ 翻案三：缓存一直命中，慢在 `stat()` —— 我编了假根因

第 80 轮我断言「`CachedKdbxFileSource.read()` 压根没被调用，因为日志里没有『缓存判定』那行」，
并据此推出「进程死后 `extraFactory` 为 null → `?.let` 短路 → 缓存挂不上」。

**全错。** 那行 TAG 是 **`VaultixKdbxCache`**（`CachedKdbxFileSource.kt:142`），
我 logcat 只过滤了 `VaultixKdbx`（`Kdbx.kt:137`）⇒ **它一直在打印**。
且 `VaultixApplication.kt:49-50` 是 `@Inject lateinit var`（字段注入期构造），注册时机正确。

⇒ **纪律：断言「某段代码没执行」前，必须先核对 TAG / 通道 / 过滤条件。**
logcat 抓不到有三种成因（没执行 / TAG 写错 / 被过滤），**结论相反**。
`VaultixLog.d` 还被 `BuildConfig.DEBUG` 门控 ⇒ 只有 debug 包有日志。

### 第三次抓包（带对 TAG）—— 真凶

```
00:47:35.008 D/VaultixKdbxCache: 缓存判定：cached=true(30701B,token=#32d46eea) 远端token=#32d46eea ⇒ 命中，不下载
00:47:35.342 D/VaultixKdbx:      unlock 耗时分解：read=2837ms（30701B）+ open=344ms
```

⇒ **B1 功能完全正常**。而**判定行到 unlock 完成只隔 0.1–0.3 s，`read` 却报 2837 ms**
⇒ **95% 花在判定之前那次 `stat()` 的 Graph 元数据往返**。
OneDrive 的 `/me/drive` 往返与下载 30 KB 差不多慢。

⇒ **B1 的原假设「stat 很快，只省带宽不省时间」在 OneDrive 上不成立，取舍反转。**

### 落地（`fa7d0bc`，用户拍板「折中」）

- 有缓存即解密，`stat()` 丢后台
- 后台发现令牌变了 ⇒ 换缓存 + `Freshness.STALE` + 上报 `KdbxSyncStatus.REMOTE_CHANGED`
  （**复用已有 `SyncBadge` + 文案 ⇒ UI 零改动**）
- 写入侧 eTag 条件写**不动** ⇒ 绝不静默覆盖远端
- 无缓存时仍走同步 stat（没有可牺牲的东西，失败如实抛）

**门禁五关全绿 + 变异验证**（改回同步 stat ⇒ `HangingStatSource` 那条测试超时红）。

⚠️ **真机未验** —— 验收清单在接力文档第二节。

## 三、JSON ⇄ KDBX 无损互转（已立单，未动手）

施工单：`Docs/progress/json-kdbx-lossless-conversion.md`（W1–W6）。

**用户拍板**：转换结果 = 生成 `.kdbx` 文件；保真度 = 先平铺；**先补写回**（否则通行密钥静默丢失）。

### ★ 探针实测：kotpass 标准键是**真覆盖**

`data:kdbx` 临时探针（跑完即删）：

| 探针 | 实测 |
|---|---|
| `+ ("Title" to X)` | `.title` **变成 X** ⇒ 真覆盖 |
| `+ ("title" to X)` | `.title` **不变**，并存两条 ⇒ **大小写敏感** |
| `+ ("Url" to X)` | `.url` = **空** ⇒ 写 `Url` 读不出 `url` |

⇒ **现网 bug 坐实**：`KdbxItemWriter.applyCustomFields:269` 无条件 `result + (name to …)`
⇒ 用户一个叫 `Title` 的自定义字段**直接毁掉库名**。
且 `KdbxItemMapper:213` 白名单写 `"URL"` 而写侧写 `"Url"` ⇒ **读侧漏 URL**（同根因第二处）。

### bw2keepass 的血泪（直接抄结论）

- **保留键**：`converter.py:310-316` —— pykeepass 的 `UserName`/`otp` 是保留键，
  `set_custom_property` **抛 AssertionError 崩掉整个转换**。kotpass 不抛但**静默覆盖**。
- **多 URL**：`engine.js:261-266` 主 URL 进标准 `URL`，其余进 `KP2A_URL_1/_2` ⇒ 照搬。
- **标准字段优先**：`engine.js:285` 的 `if (!fields[cf.name])` ⇒ 这条规则必须搬到 Vaultix。
- **字段集是互补**：它有 `RP_NAME`/`USER_DISPLAY_NAME`/`CREATION_DATE`，
  我们有 `FLAG_BE`/`FLAG_BS` ⇒ 写回要取**并集**（10 键）。
- ⚠️ 它靠 `_1`/`_2` 后缀区分多凭证（`engine.js:290`），
  而 `KdbxPasskeyCodec` 只有**单个** `KdbxPasskeyFields` ⇒ 读侧需补拆解。

### 方案要点
命名空间三级键区（标准 / `VPX_` 工具区 / `KPEX_` 通行区 / 外来区原样保留），
三条铁律 R1 标准键不可被覆盖（大小写折叠后判）· R2 工具字段加前缀（**可逆**）· R3 外来字段原样保留。
**不用抄 `KP2A_`**：`KPEX_` 已被通行密钥占用，且要能识别"谁写的"。

## 四、架构讨论：要不要改成 Keyguard 的全局单锁

用户问「Keyguard 更简洁，你认为呢」。**我不同意**，理由三条：

1. per-vault 状态散在 **9 个文件**（`house_user_locked` / `vault_timeout::` / `house_room::`），
   Keyguard 的 `VaultState` **没有任何地方能表达"锁了 A 但 B 开着"** ——
   **它的简洁来自能力上的放弃**。
2. **#131**（P0-结构，用户原话「两个库互相解锁/加锁逻辑混乱」）的解法 D1–D3
   **已建成并经变异验证**（405 测试）。那份定稿开头写得很准：「修的是违反模型的行为，
   不推翻既有架构」。#132（KDBX 慢）与锁模型**无关** —— 砍掉 per-vault 锁，KDBX 依然 7.7 秒。
3. 复杂度的**成本已经付过了**，现在砍是纯亏。

⇒ 路线：`① 修 stat 阻塞（已做）→ ② B2 信封装派生密钥 → ③ 补可预测性 UI（不是砍模型）`。

## 九、W3 TOTP 往返验证（2026-10-06 续做）

**结论先行：往返本来就是通的，`KdbxTotpCodec` 一行未改。** 施工单 §1.2 缺口表把
「`applyTotp` 从未做过往返验证」列为缺口 —— 验证之后发现**缺口在知识层面，不在代码层面**。
新增 `KdbxTotpRoundTripTest`（9 条用例 / 11 种 otpauth 形态），把这个「不知道」变成「已钉死」。

### 为什么这类往返必须测，即使它本来就是通的

写侧 `applyTotp` 把 `VaultItem.totp` 整串塞进 `otp` 字段，读侧 `toOtpAuthUri` 认得
「`otp` 字段里直接躺着一条完整 URI」⇒ 往返**本该**恒等。但中间隔着
`EntryFields` 键名大小写敏感、`Plain`/`Encrypted` 两种取值、一次 URI 解析 ——
**任一环出错都不报错**，只是让用户的验证码从此算错（界面上仍是 6 位数字，照常刷新）。
「不报错」正是这类 bug 能活到今天的原因：单测全绿 ≠ 用户能用。

### 断的是语义，不是字面串

断言一律落在 `OtpUriParser.parse` 之后的 `TotpConfig` 各分量（secret/period/digits/
algorithm/type/counter/pin），**不比字面串**。理由：`otpauth://totp/X?secret=Y` 与
`...?secret=Y&issuer=X` 是同一个配置，比字符串会误报；而真正的数据丢失
（`digits` 从 8 掉回 6）反倒可能被放过。

覆盖维度：SHA1/256/512 × 6/8 位 × 15/30/60 秒 step × HOTP counter × Steam × Yandex
× label 含空格；另有 Steam base64 密钥（`+/=` 三类 URL 不安全字符）、`counter=42`、
`digits=8`/`period=60` 不被默认兜底、幂等（未改 TOTP 不重写）、otp 不泄漏进
`customFields`、清空会真删字段。

### ⚠️ 返工一：没有证据就不改解析语义

我一度认为「位置式 `TOTP Settings` 里的 HOTP counter 被静默丢弃」是真 bug
（`KdbxTotpCodec.parsePositionalSettings` 里 `HOTP` 之后的裸数字既落不到 `periodFilled`
分支也落不到 `digitsFilled` 分支），并动手改了。**动手前该查的没查**：

1. 项目内`reference/` 只有 bastion，没有 KeePass 格式的一手依据；
2. KeePassXC 实际只写 `period;digits`，算法另存 `TimeOtp-Algorithm`，
   `30;6;SHA1;HOTP;5` 这种写法**并无来源佐证**；
3. 既有测试 `KdbxTotpCodecTest.positional hotp settings carry counter` **明确断言**
   `counter == 0L`，注释写着「位置式里的 counter 由独立字段承载时才生效」——

## 十、W4 · `VPX_` 工具字段 + 多 URL 无损降级（2026-10-07 续做）

### 1. W4 解决的是一类"不报错的丢数据"

W4 之前 `KdbxItemWriter.applyDomainFields` 写 URI 只有一行：

```kotlin
fields + (BasicField.Url.key to EntryValue.Plain(item.uris.firstOrNull()?.uri.orEmpty()))
```

KDBX 的 `Url` 字段**只装一条**，`VaultItem.uris` 是 `List` ⇒ 第 2 条起**无处可存**。
症状：一条挂 3 个网址的登录，**改一次标题**就被抹掉 2 个网址 ——
文件能正常打开、库能正常解锁、没有任何报错。

⇒ 这类缺陷只能靠**往返计数相等**判定。断言字段值逐个相等反而抓不到
（少掉的那几个压根没有"错值"可比）。`KdbxToolFieldsRoundTripTest` 的主判据因此是
**数量 + 内容 + 顺序**三者同时相等。

### 2. 落法（写侧）

| 来源 | KDBX 落法 | 反向还原 |
|---|---|---|
| 第 1 条 URI | 标准 `Url` | 原样 |
| 第 2 条起 | `VPX_URL_n`（下标从 1 起） | 按 n 升序拼回 |
| 每条的 `match` | `VPX_MATCH_n` | `UriMatch.entries` 匹配 |
| `androidapp://` | `App Package Name` | `androidapp://<pkg>` |

### 3. ⚠️ 施工单的一处转述错误（依实证纠正）

施工单 §2.2 写 `androidapp://` → `AndroidApp` 字段对。
**实际是 `App Package Name` / `App Name`** —— Bastion（GPL-3.0）
`reference/bastion/.../KeePassKdbxService.kt:364-365` 的常量字面值，
且它用 `getFieldValueIgnoreCase` 兼容**七个**别名（`AppPackageName` /
`AndroidAppPackageName` / `PackageName` / `KP2A_APP` / 两个Monica 自有字段 …）。

⇒ 写侧只写 `App Package Name` 一个键；**读侧必须吃别名且大小写不敏感**，
否则读不出 KeePassDX / bw2keepass 写的库（等于单向丢数据）。
别名清单直接取自 Bastion 的实参列表，**只读不写**。

### 4. ⚠️ 三处靠实证抓出来的 bug（都不是推理出来的）

| # | bug | 抓法 |
|---|---|---|
| 1 | `typeOf` 类型码**整段错位一位**（2→Card / 3→Identity / 4→SshKey） | grep `BitwardenCipherTypeCode.kt`：官方是 `LOGIN=1 … SSH_KEY=5`，**0 不分配**。错位不报错，只让"卡片"往返后变成"身份" |
| 2 | `extras()` / `appUriOf()` 键名比对**大小写敏感** | `javap` kotpass 0.13.0：`EntryFields.get(String)` 就是 `Map.get`（字节码只有 `invokeinterface Map.get`）⇒ 大小写敏感。只认自己写的键名 ⇒ **读不出第三方库** |
| 3 | `fromUris` 过滤后再回头索引**原列表**取 `match` | 过滤掉空串/应用 URI 后两个列表下标已错位 ⇒ 取到的是**另一条 URI 的匹配档位**，症状是"自动填充档位莫名变了"，几乎无法归因 |

⇒ 铁律补充：**涉及"某库怎么存"的判断，一律 `javap` / grep 一手实现或权威常量，
不靠记忆**。bug 1 和 2 都是"看起来完全合理"的写法，错得毫无征兆。

### 5. ⚠️ 一个刻意做的设计：整段替换而非按键名增删

用户把 3 条 URI 删到 2 条时，若按键名增删，旧 `VPX_URL_2`(=c) 会留在原地，
而新 `VPX_URL_1` 也= c ⇒ **b 消失、c 出现两次**。
症状比丢数据更坏：**网址还在，但对应关系错了**，用户看不出来。

⇒ `applyUris` 走 `previousToolKeys(before)` **整段删除**再重写。
且 `previousToolKeys` 走 `fromUris`/`appFieldsOf` **重算**键名，
不另抄一份清单（抄一份必然与写侧漂移 —— 那正是 `KdbxFieldKeys` 单一真源要治的病）。

### 6. ⚠️ `VPX_` 不混进自定义字段（差点漏掉的设计）

读方向 `customFieldsOf` 原先只排除 `isReserved`（标准/OTP/通行密钥）。
加上 `VPX_` 后 `VPX_URL_1` 会**同时**出现在 `uris` 和 `customFields` 里：

1. 详情页同一个网址出现两次（网址区 + 自定义字段区）；
2. **两条写通道抢同一个键** —— `applyUris` 产出 `VPX_URL_1`，
   `applyCustomFields` 若也把它当自定义字段写一遍，两边各自判"值没变就不动"，
   **谁先跑谁说了算**，后跑的还会用错误的类型（Text/Hidden）覆盖前一个。
   而 R1铁律只挡"标准/OTP/通行密钥"，**挡不住工具字段自己撞自己**。

⇒ `customFieldsOf` 额外判 `!isToolFieldName(key)`。
用户仍能在 KeePassXC 编辑器里看到 `VPX_URL_1` —— W1 里"工具字段要可见"
指的是**用户的库文件**不是 Vaultix 自己的 UI。
`isReserved` 的 KDoc 已补上"这不是漏加"，防止后人"顺手修回去"。

### 7. ⚠️ 已知取舍：多个应用 URI 只保留第一个

`App Package Name` 是**单个**字段位（KeePassDX 约定就是一条一个包名），
没有 `_2` 那种落法 ⇒ 第 2 个应用 URI 在 KDBX 侧无处可存。

**为什么不改成"全塞进 `VPX_URL_n`"**：那些 `androidapp://` 会被 KeePassXC 当域名匹配
（必然匹配不上）⇒ 等于**为了多存一条而让所有应用 URI 的匹配全失效**。宁可少一条。

⇒ 该行为由单测`多个应用 URI 时只保留第一个` **钉死**，并在
`KdbxToolFields.appFieldsOf` 的 KDoc 里写明"改前先读这段"。

### 8. 刻意不做 `VPX_PW_HISTORY`

施工单 §2.2 列了它，但 `VaultItem` **没有** `passwordHistory` 字段
（`BitwardenExportModels` 注释也写着"暂不承载，恒为 `null`"）。
此刻加这个键会造出「**写进去就再也读不出来**」的字段：没有承载者，
转换时写进去、下次读出来无处安放 ⇒ 数据在往返中凭空消失，用户看不到任何提示。

⇒ **等领域模型真建模了再补**，届时的正确做法是加常量 + 两侧接入，而不是现在写空壳。

### 9. ⚠️ 返工：CI 假绿第二次（单测编译失败）

- `37609359341`：run 顶部 `✓ success`，detekt 与 APK 构建门禁都绿，

### 11. ⚠️⚠️ 返工二：假绿第二次 —— 6 条用例失败，两个都是**真 bug**

`37610581524` 顶层依旧 `success`，但 `:data:kdbx:testDebugUnitTest FAILED`，
`138 tests completed, 6 failed`。取报告（`gh api .../artifacts` 里的
`debug-unit-test-reports`，比翻日志快）拿到 expected/actual，两个根因：

#### bug 1：读侧恒为 null —— 把自己写的字段按"别人的格式"去解析

写侧 `appFieldsOf` 往 `App Package Name` 里存的是**裸包名** `com.example.mail`
（这才是 KeePassDX 约定，Bastion 读的也是裸包名）；
而读侧 `appUriOf` 却把它交给 `androidAppPackage` —— 而那个函数**只认
`androidapp://` 开头**，裸包名直接被判否返回 null。

```
写入: App Package Name = "com.example.mail"   ← 断言字段存在是绿的
读取: appUriOf(...) = null                     ← 应用条目整体消失
日志: 没有任何错误
```

**为什么这条单测没能更早抓住**：写侧断言"字段写进去了"，
读侧断言"URI 读回来了"，两条都成立才叫往返 ——
**只验写侧或只验读侧，都会漏**。这类"两侧各自都对、接起来不对"的缺陷
只有**完整往返**才暴露。

**修法**：新增 `normalizeAppPackage(raw)`，**裸包名 / 完整 URI 两种形态都认**
（有的工具直接写完整 URI）。绝不能图省事直接调 `androidAppPackage`。

#### bug 2：第 0 条 URI 的匹配档位无处可存

写侧设计是「第 0 条进标准 `Url`，第 2 条起进 `VPX_URL_n`」，
配套的 `VPX_MATCH_n` 也从下标 1 起 ⇒ **第 0 条的 `match` 没有落点**：
标准 `Url` 字段只装 URI 字符串、不装匹配规则。

症状是「那条唯一网址的匹配档位退回默认基域匹配」——
用户会发现自动填充**匹配得比之前松**，但完全无从追溯。

**修法**：写 `VPX_MATCH_0`，读侧 `toUris` 用同一下标口径取回；**不论几条都存**
（单条时它是唯一那条的规则，两条时它是第 1 条的规则）。

⇒ 这类是**降级设计里的覆盖盲区**：`n` 从 1 起这个决定本身没错，
  但配套字段必须**覆盖同一个下标空间**。加 `VPX_MATCH_n` 时就该问一句
  "n=0 怎么办"，而不是等单测失败才发现。


### 1. 三处实证缺陷（都不是"审美问题"）

### 2. ★ 紫调的量化签名（本次最有价值的发现）

基线三档 surface 的 RGB：

```
surfaceContainerLow     #F7F2FA   G-R = -3
surfaceContainerHigh    #ECE6F0   G-R = -6
surfaceContainerHighest #E6E0E9   G-R = -3
```

**紫 ≠ "蓝比绿高"，紫 = 绿通道凹陷。** 纯度低到看起来像中性灰
⇒ 这就是为什么没人发现、为什么每次"整体调色"都压不住。

⇒ 判据因此定为 **`G-R >= -2`**（允许轻微冷调，钉死绿凹陷）。
   品牌色板实测 `G-R ∈ {0, -1}`。这比"看着不像紫"可靠得多。

### 3. 色板怎么定的：不手搓色彩科学

**先说失败的两条路**（都别重走）：

- 用 HSL 插值推 tone：符号写反导致 `tone10` 比 `tone40` 还亮，且 90/100 撞色；
- 自己实现 Lab/LCH + 色域裁剪：**D65 白点归一化写错**，算出的 `L*=260`（Lab 只到 100），
  全盘输出 `#00FF00`。

⇒ 改为**只取公开常量**（Open Color 9 的 indigo/green/blue），**不调不猜**，
  再用 WCAG 公式逐对实测验证。

### 4. WCAG 算式必须先自校验

拿 `ItemFormDialog.kt` KDoc 里**此前独立实测**的 M3 基线值反向核对：

```
#E6E0E9 vs #FEF7FF  算得 1.232 / 文档记 1.232  ✓
```

## 十二、品牌色板降饱和（2026-10-08 续做，同一轮反馈的第二段）

### 1. 用户反馈与拍板

- 反馈：「这个蓝色太亮了一点。适合人眼舒适度的配色吧」+ 截图（设置页分组标题 / FAB / 选中态呈高饱和亮蓝）；
- `AskUserQuestion` 拍板：**降饱和为主**（而非降明度）+ **保留蓝**（而非换色相）。

⚠️ 注意这是**同一天的第二次返工**。第一轮（§十一）修的是"发紫"，
这一轮用户说"太亮"—— 两次是**不同的病因**，不能用同一刀解决。

### 2. ★ "太亮"的分层拆解：主因是饱和度，不是明度

直觉会把"太亮"当成明度高。实测 HSL 后发现它其实是两层，**且主因是饱和度**：

| 角色 | 上一版 | 饱和度 | 明度 | 性质 |
|---|---|---|---|---|
| `primary` | `#3B5BDB`（indigo-7） | **69.0%** | 54.5% | 偏"荧光" |
| `primaryContainer` | `#DBE4FF`（blue-1） | **100%** | 92.9% | ★ **刺眼大头** |
| `secondaryContainer` | `#E6ECF9`（blue-1） | 61.3% | 93.9% | 同类 |

⇒ **`primaryContainer` 才是病灶**：它是 FAB / 选中态底 / 分组底的来源，
**一次出现就是成片面积**，而人眼对**大面积高饱和**的敏感度远高于小面积高饱和。
`#DBE4FF` 是Open Color 的 `blue-1` —— 一个**完全饱和**的色，
看着"干净"，铺开却晃眼。

⇒ 这也解释了"为什么只调 `primary` 不够"：用户截图里扎眼的根本不是主色，是那大片浅蓝。

### 3. 色值来源：Open Color 的淡蓝档**帮不上忙**，只能生成

`primaryContainer` 想要"淡蓝"，但 Open Color 9 的 `blue-0/1/2`
实测饱和度**全都是 100%**（明度 96.5% / 92.9% / 87.5% 三档）⇒ 正是要消除的那一类。

⇒ 改为**固定色相 228° 下按目标饱和度生成**。实测色相落在 225.0°~231.3°。

⚠️ **一个必须写清的量化事实**：生成值只能落在 8bit 网格上，
所以相对 228° 有最多 **±3.3°** 的**量化偏差**（不是色相漂移）。
我一度把它写成"≤ 0.3°"，复核后发现不成立，已改正 ——
**注释里的实测数字同样会骗人，不复核就会把错的传下去。**

### 4. ★ 降饱和没有牺牲可读性（本次的底线）

| |上一版 | 本版 |
|---|---|---|
| 浅色 文本级最低 | 5.67 | **6.04** |
| 浅色 非文本级最低 | 3.77 | 3.77（持平） |
| 深色 文本级最低 | 6.79 | 6.77 |
| 深色 非文本级最低 | 4.51 | **4.57** |

⇒ 无任何一对跌破 4.5 / 3.0。**"护眼"不等于"牺牲可读性"**，这是本次的硬底线。
⚠️ 其中"UI 余量变宽"是我最初写错的（实际持平），已在 KDoc 与本文改正。

### 5. 新增 3 条判据（单测 9 → 12 例）

| 判据 | 钉住什么 | 本版实测 / 余量 |
|---|---|---|
| `accentSlotsStayBelowSaturationCeiling` | 品牌主色 `S ≤ 58%` | 最高 55.56% / 余 2.44 |
| `largeAreaContainersStayMuted` | 大面积容器 `S ≤ 40%` 且 `L ≤ 96%` | 39.13% / 余 0.87；L 94.51% |
| `primaryKeepsBlueHue` | `primary` 色相留在 **200°~250°** | 226.0° / 221.7° |

**反向验证**（判据必须能抓住上一版）：上一版 `primary` S=68.97% > 58%、
`primaryContainer` S=100% > 40% ⇒ **两条都会红**。色相那条对上一版**通过**
（228.0° 仍是蓝相）—— 这是**正确的**，用户要保留的正是蓝相。

💡 **色相判据为什么必须有**：降饱和是**无方向**的 ——
朝"灰"降和朝"柔和的蓝"降，在代码上都只是改两个数字。
用户明确说"保留蓝"，而**光有饱和度上限会把品牌色降成毫无个性的灰蓝**。
⇒ 必须"低饱和"与"还是蓝"**同时**钉住。

⚠️ **判据刻意不管 `error` 家族**：危险红是语义色不是品牌色（`Docs/07` §9.3），
实测 S≈60%~65% 本就超上限。判据越界去压它，等于为了配色好看而**削弱"危险"的辨识度**。

### 6. ★ 又一次差点栽在"符号存在性"上（这次靠反编译挡住）

写判据时想用 `assertWithMessage(...).that(hue).isIn(ClosedFloatingPointRange(200f, 250f))`
—— 读起来最自然。**反编译 `/tmp/truth.jar`（Truth 1.4.4）后：**

```
FloatSubject:  isGreaterThan(int) / isLessThan(int) / isAtMost(int) / isAtLeast(int)
Subject:       isIn(java.lang.Iterable<?>)          ← 没有 Range 重载
FloatSubject extends ComparableSubject<Float>        ← 父类有 isAtMost(T)/isAtLeast(T)
```

⇒ `isIn(Range)` **不存在**，会直接编译失败（而单测步骤是 non-blocking 的）。
同时查清：`Float` 实测值走的是**父类 `ComparableSubject<Float>` 的浮点重载**。

⚠️ 由此发现一个**静默失效**的陷阱：若把上限常量从 `Float` 改成 `Int`，
`Float` 实测值会改走 `isAtMost(int)` 重载而**截断小数**（55.56 → 55），
判据会**比预期更宽松**且不报错。已在判据 KDoc 里写死这条注意事项。

⇒ **铁律再确认一次**：不赌任何未实证的符号存在性。
  本轮沙箱无 Gradle 缓存、查不到 Compose 的 `Color.hsl` ⇒ 测试里
  **用已实证的 `red/green/blue` 通道自己算 HSL**，不赌那个 API。
