## §1 权限管理页：乱码 + 字符没对齐

**回答「为什么权限没开时顶部会出现乱码」**

| 现象 | 根因 | 改法 |
|---|---|---|
| 状态卡标题显示字面量 `有 %1$d 项待允许` | `permission_status_pending` 带 `%1$d`，但 `PermissionStatusCard` 的 `stringResource(...)` **没传** `pendingCount`；实参反倒错传给了**不需要参数**的副标题 | 两处各归各位：标题传参数、副标题不传 |
| 四行右侧「已允许 / 去设置」既比标题低一截、左缘也不齐 | ① `SettingsRow.trailing` 垂直居中于「标题 + 两行副标题」整体 ⇒ 状态落在两行之间；② `TextButton` 自带 24dp 内边距，裸 `Text` 没有 ⇒ 两种行尾各贴各的左缘 | 自绘 `PermissionRow`：**状态与标题同一行**、用途说明落到下一行且不再截断；行尾**弃用 `TextButton`**，纯文本与可点项共用同一个 `TrailingSlot` 外框（固定宽 / 48dp / 统一内边距 / `labelLarge`） |
| 顶部「一切就绪」与某行「设备不支持」同屏 | `pendingCount` 只数 `Denied`，`Unavailable` 不计 ⇒ `allGood` 仍为真 | 拆成**两个计数 + 三态状态卡**：有待办 → 「有 N 项待允许」；只有不支持 → 「有 N 项设备不支持」；都为 0 → 「一切就绪」 |

⚠️ **不能把 `Unavailable` 混进 `Denied` 的计数**：单测
`PermissionStatusCheckerTest.待办计数只数 Denied 不数 Unavailable` 明确钉过口径 ——
硬件决定的项用户永远消不掉，混进去会让没有指纹的设备**永远到不了「一切就绪」**。
所以第三条路才是「第三态」，不是「把两态并成一态」。

尺寸常量 `PERMISSION_ROW_PADDING_H`(20dp) / `PERMISSION_ICON_BOX`(28dp) /
`PERMISSION_ICON_GAP`(`UiSize.InlineIcon`) 刻意与 `SettingsRow` 逐字一致：
自绘行布局改的是**对齐关系**，不是另起一套尺寸规格；`SettingsDivider` 的缩进
因此仍精确落在文字左缘。

**文件**：`ui/permissions/PermissionsScreen.kt`、`res/values/strings.xml`

## §2 锁与安全：弹框、档位顺序、对话框风格

**回答「既然默认对所有库生效，为什么还要弹框」**

- 查证结论：**「选库 / 配置向导」早在 2026-09-30 就删了**，`toggleBiometric` /
  `togglePin` 现在直接进 `startEnrollment(范围恒 = 全部库)`。用户仍看到的弹框是
  **输 PIN / 输 KDBX 主密码 / 系统 BiometricPrompt / 结果页**这四类。
- 前三样是**安全链条**，不能删：PIN 只在输入那一刻存在、房间信封必须在认证之后
  才能封装（#243 就是「挂在认证之前 ⇒ 条件恒假」栽过的）。删掉会得到
  **一个永远解不开的信封**。
- 真正该砍的误触源：**整行可点**。`onClick = onToggleXxx` 让点行任意位置都启动
  一串对话框，而 `SettingsComponents` 里既有纪律写的是「改锁的开关不该点哪都生效」。
  ⇒ 去掉两行的 `onClick`，只留开关（本身已有 48dp 触控目标）。相关 5 处历史注释
  已同步更正，避免下一轮又被读回去。

**回答「『从不』怎么放到最下面了」**

`AutoLockPresets.VALUES` 照抄 Bitwarden 菜单「从严到松」，`Never` 排第 9，
且那段 100 字风险警告也压在列表底部 ⇒ 整张对话框又长又杂。
改法：`Never` **提到第一位**（它回答的是「要不要自动锁定」这层决策，不是时长序列末端），
紧跟一张 `errorContainer` 风险卡，再用留白与其余档位分段。

**回答「UI 没匹配整体风格」**

| 缺口 | 改法 |
|---|---|
| `AlertDialog.text` 槽**自身不滚动**，10 档位 + 2 段说明小屏被裁 | `Column` 挂 `verticalScroll(rememberScrollState())` |
| 两段说明是裸 `Text` 堆在单选行之间 | 统一收进 `AutoLockHintCard`：风险用 `errorContainer`、普通说明用 `surfaceContainerLow`，圆角取 `VaultixCorner.Panel` |
| 单选对话框按钮写「取消」，但点选项即选中并关闭、根本没有可取消的操作 | 三处（`AutoLockDialog` / `ThemeModeDialog` / `ClipboardClearDialog`）统一为 `action_close`「关闭」，对齐 `UpdateCheckDialog` 的定稿口径 |
| PIN 两行没有副标题、末尾多一根分隔线 | 补 `pin_change_desc` / `pin_forgot_desc`；末尾分隔线归调用方（`UnlockMethodScreen` 已画一根），消除重复粗线 |

**文件**：`ui/settings/SettingsComponents.kt` / `QuickUnlockDialogs.kt` /
`QuickUnlockController.kt` / `UnlockMethodScreen.kt` / `SettingsScreen.kt`、`strings.xml`

## §4 判据（可复用）

1. **带 `%1$d` 的字符串，参数与字符串要成对核对**：静态门禁只查 `R.string` 是否存在，
   查不出「漏传实参」——它会安静地把占位符原样显示给用户，看起来像乱码。
2. **「未就绪」≠「待办」**：硬件决定的不可用项既不能算待办、也不能算就绪，
   需要**第三种状态**，而不是把两类计数合并。
3. **`AlertDialog.text` 槽不滚动**；内容一多必须自己挂 `verticalScroll`（本仓第二次踩）。
4. **「只需要开关」的正确解法是砍掉整行点击**，不是砍安全链条；
   也别把「选范围」和「做认证」混为一谈。
5. **chip 折行先看标签字数再调布局**：`weight(1f)` 平分后宽度是固定的，
   与其缩字号 / 改间距，不如把冗余信息移到下面的说明里。
6. **一屏两套规格是廉价感首要来源**：圆角、容器色阶、按钮强调级别都要先统一再谈美化。

### 6.1 四个 P0 / P1

| # | 缺口 | 改法 |
|---|---|---|
| 1 | `SelectionActionBar` 批量删除无确认，绕过单条删除的「长按→左滑→确认」三重闸门 | 确认层放进**共用组件**而不是四个调用点，一处覆盖密码 / 验证码 / 通行密钥 / 卡包；文案带条数并写明「部分可恢复、绑定信息不可恢复」 |
| 2 | 通行密钥「详情」框右下角唯一主按钮就是删除，文案还是借来的「移除」 | 详情框只留「关闭」；删除改左侧 error 色按钮 + 二次确认，写明不可撤销 |
| 3 | 验证码编辑框的「移除」后果随 `entry.bound` 变化（清配置 / 删整条），文案却只有一个词 | **编辑框 + ⋮ 菜单两条入口**都接同一套分支文案与确认框 |
| 4 | 全屏表单按 ✕ / 返回 / 点外部 / 取消直接丢弃全部输入 | 新增 `rememberDiscardGate`：调用点判脏、两个表单共用确认框 |

### 6.2 同族补齐

- **回收站自动清理档位**：从「即选即存」改为**暂存 + 保存才提交**；hint 补「永久删除、无法恢复、缩短天数会立即清掉已超期的」。它是 UI 里唯一会批量永久删除回收站内容的入口。
- **关闭 PIN 解锁**：复用 `BasicAlertDialog + DialogSurface` 形态加确认；同一动作的另一个入口（忘记 PIN）早有确认框，两条入口现在一致。
- **确认导入**：`onApply` 前加确认框，与导出侧对称；正文写明不可撤销。
- **防截屏开关**：关闭态换成后果文案，`null`（未读出）不猜状态。

### 6.3 快速解锁结果页收敛

`finish()` 在**全成功**时把 `Dialog.Report` 换成 `Dialog.Idle`：开关变 On +
副标题「已对 N 个库生效」就是反馈，不必再点一次「完成」。
⚠️ 四类结论**仍必须弹**：任何失败 / 有跳过 / `scopeOnly` / `lockOnly`
（后两者两个数字都是 0，不给一句话用户会以为开关拨了却没生效）。
PIN 输入、KDBX 主密码、系统指纹认证仍保留（#243）。

### 6.4 三条设计判据

1. **确认框放共用组件，不要放每个调用点** —— 四个列表共用一个 `SelectionActionBar`，
   逐个改必然漏一个；两条「移除」入口共用同一套字符串才不会口径漂移。
2. **判脏与保存必须用同一个快照构造** —— 两套判据必然出现「明明没改却拦着不让走」
   或「改了却不拦」。`ItemFormDialog` 的 `snapshot()` 既供 `isDirty` 比较也供 `onSave`；
   同时它还替掉了 `onConfirm` 里那段重复的 `buildSnapshot`，净增行数几乎为零。
3. **沉默的结果页可以省，沉默的失败不行** —— `silent` 条件必须把「需要用户读一句」的
   分支全部排除；「全成功且零跳过」是唯一可以省略报告的场景。

⚠️ 工程约束：`ItemFormDialog` 贴着 detekt `LongMethod ≤150`，所以把状态与确认框
抽到 `rememberDiscardGate`（返回回调的 composable，按 Compose 惯例用 `remember` 前缀），
调用点只多一行；顺带让两个全屏表单共用一套闸门。
