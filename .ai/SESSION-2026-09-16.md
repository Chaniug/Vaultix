## 1. bug：主密码解锁变成了「重新登录」（`bfb0179`）

### 1.1 用户判断是对的

用户的推理："已经登录上了，用密码只是校验解开密码库，而不是重新登录" ——
这就是 Bitwarden 的两层语义，用户比当时的代码更懂协议。

- **登录**（`connect/token`）= 向服务器要一个 access token，**只有**首次添加库、
  会话被吊销、或本地凭据缺失时才该发生；
- **解锁** = 用主密码派生主密钥 → 解开本地已保存的 account symmetric key，**纯本地**。

服务端 2FA 只在「登录」这一步索要。把它掺进解锁，等于每次冷启动都强制联网 + 2FA。

### 1.2 根因

`VaultRepositoryImpl.doUnlock` **无条件**走 `authRepository.login(...)`（一次全新的
`connect/token`）。只要账号开了 2FA，服务器必然回 `two_factor_required` ⇒
`UnlockResult.TwoFactorRequired` ⇒ UI 弹验证码框。

> ⚠️ 顺带一个反直觉的点（排查时容易误判方向）：`two_factor_required` **只在密码校验通过之后**
> 才返回。所以「输错主密码」得到的是 `invalid_grant`，**不会**弹 2FA 框 ——
> 用户看到 2FA 框，恰恰说明密码是对的，只是走错了路径。

### 1.3 修法：本地解锁优先，失败才回退登录

```
doUnlock(…, preferLocalUnlock = true)
  └ 若 twoFactor == null && preferLocalUnlock
      └ authRepository.unlockWithMasterKey(server, email, password)
          ├ 有本地 account key？没有 ⇒ 返回 null（走登录）
          ├ 读持久化的 KDF 快照 ⇒ 派生 masterKey ⇒ 解 account key
          └ 成功 ⇒ registerServer(server) + sessions.unlock(server, key) ⇒ Success
      └ 返回 null ⇒ 落回原来的 login 流程（行为不变）
```

**新增 `KdfProfile`**（`data/bitwarden/.../auth/KdfProfile.kt`）：把 `preLogin` 的
KDF 参数（type / iterations / memory / parallelism）持久化到凭据库
（`CredentialKeys.kdfProfile(server)`，管道分隔、`-1` 表示缺省）。

**为什么要持久化 KDF**：不存的话，每次解锁都要先打一次 `preLogin` ——
那就还是"解锁依赖网络"，用户飞行模式下依然开不了库。存下来之后
**冷启动解锁完全离线**。`parse()` 遇到脏数据返回 `null`（不抛），
取不到就回退到联网 `preLogin` 再存一次。

**一个容易漏的连带修复**：本地解锁路径上必须补 `authRepository.registerServer(server)`。
原登录流程里服务器是在 `login` 内部注册的；本地路径绕过了它，
401 刷新拦截器会**找不到该 server 的凭据** ⇒ 解锁后同步静默失败。

`logout` 同步删除 KDF 快照。单测 `KdfProfileTest`（PBKDF2 / Argon2id 往返 + 脏数据 → null）。

## 3. 设置页：搬运 + 合并精简 + M3（`a56da7c`）

### 3.1 从 Bastion 还能搬什么：逐项过了一遍，只有一项值得搬

Bastion 设置页的条目与判定：

| Bastion 项 | 判定 | 理由 |
|---|---|---|
| **检查更新**（`update_check_title`） | ✅ **搬** | Vaultix 的分发渠道就是 GitHub Release，用户本来就得去那下载，App 内给一个"有没有新构建"的答案顺理成章 |
| 安全分析 / 密码泄露报告 | ❌ | 需要 Bitwarden 服务端 HIBP 接口，Vaultix 未打通 |
| 同步与备份 | ❌ | Vaultix 已有「导入与导出」（加密 JSON 备份 + 增量恢复），语义已被覆盖 |
| 扩展 / 页面自定义 / 预览功能 / 开发者设置 | ❌ | Bastion 特有 |
| 安全问答 / 重置主密码 | ❌ | Bitwarden 网页端流程，客户端做不到 |

### 3.2 搬来的「检查更新」刻意没搬哪部分（边界要写清）

上游 `UpdateChecker.kt` 里最大的一块是 **`downloadApk` + `validateDownloadedApk` + 拉起安装**。
**不搬**，两个理由：

1. Vaultix 的预览包每次 CI 都**覆盖同一个 `preview` release 的同一个附件名**
   （`app-full-debug.apk`），版本无从在文件名里体现，用户下载到本地就是一堆同名文件；
2. 对一个**密码管理器**来说，"自动下载并静默安装"是比"多两步"严重得多的风险面 ——
   装错来源 = 把主密码交给了一个来路不明的 APK。

⇒ 只回答「有没有新构建」+ 给**发布页链接**，下载与安装仍由用户在浏览器里完成。

**渠道自动判定**（与上游的最大差异）：

- 版本名含 `-dev-`（CI debug 包形如 `0.3.0-dev-78db0ed`）⇒ **预览渠道**：
  取最新 prerelease，**比对 release 标题里的 commit SHA 与本机短 SHA**（前缀匹配即同一构建）；
- 否则 ⇒ **正式渠道**：`compareVersionTags(latestTag, currentVersion)`（移植自上游）。

> ⚠️ **不能用 `published_at` 判定预览版**：`preview` 是**同一条 release 反复覆盖附件**，
> `published_at` 停在首次创建那天。拿它跟本机比会得到「你比远端新」这种荒谬结论。
> commit SHA 才是构建身份。

### 3.3 已有的内容里能合并什么

原「密码库」组**只剩一个入口行**（密码库管理）却独占一个组标题，而它旁边的
「解锁与隐私」讲的是同一件事：**库怎么开、开了怎么锁**。
⇒ 并为 **「密码库与解锁」**（新 `group_vault_unlock`），首页 **5 组 → 4 组**：

| 组 | 内容 |
|---|---|
| 密码库与解锁 | 密码库管理 · 自动锁定 · 防截屏 · 剪贴板清除 |
| 显示与填充 | 主题模式 · 动态取色 · 纯黑背景 · 条目显示 · 自动填充设置 |
| 数据 | 导入与导出 · 回收站清理 · **退出数据库**（error 色，置底） |
| 关于 | 权限管理 · 版本 · **检查更新** · 源码与反馈 · 开源许可 |

**没有**继续合并的理由（别为了少而少）：「显示与填充」是"界面怎么呈现"、
「数据」是"数据怎么进出"、破坏性动作必须单独成组置底 —— 三条语义互不重叠。

### 3.4 M3 观感：一组一张卡，不是一行一张卡

上游 Bastion 的 `SettingsItem` 是**每一行各自一张 `Card`**（20dp 圆角 + 72dp 最小高）。
18 行 = 18 张漂浮的小药丸，页面被切成一堆碎片，**读不出"这几行是一组"**。
加上它的容器底是 `surfaceContainerHigh.copy(alpha = 0.55f)` —— **同色叠 alpha**
（8.4 已记：卡片边界会彻底消失）。

⇒ 新增两个组件（`SettingsComponents.kt`，文件头有 2026-09-16 的**勘误段**，
明确"上游这两处是缺陷、不要照抄"）：

```kotlin
SettingsGroupCard { … }   // 一组一张 surfaceContainerLow 卡片（20dp 圆角）
SettingsDivider()          // 行间分隔线，起点缩进到文字左边缘
```

`SettingsRow` **不再自带卡片外壳**，降级为纯行；`clickable` 提到 `padding` **之前**
（否则水波纹只覆盖内边距以内那一小块，改成整组卡片后"只有中间能点"会特别明显）。

已应用到：设置首页（4 组 17 行）、自动填充页（5 组 9 行）、密码库管理页（2 组 3 行）、
导入导出页（1 行）。

## 4. 🔴 抓到两处「detekt 全绿、CI 编译才炸」的错误

新增的 `DetailCard` / `SettingsGroupCard` 都用了 `@Composable ColumnScope.() -> Unit`，
**两个文件都只写用法、没补 `import androidx.compose.foundation.layout.ColumnScope`**。

由 `.ai/tools/check_signature_types.py` 抓到（它专门管这一类）。
**同族文件有导入 ≠ 本文件有**（`036c8ff` 已栽过一次，见 `SESSION-2026-09-15.md` §14.2）。

### 4.1 顺手修了脚本的两个盲区

1. 🔴 **默认只查 `HEAD~1..HEAD`** ⇒ 只要上一条提交改过文件（几乎总是），
   **工作区里未提交的改动永远不被检查**。而"正在改的东西"恰恰是最该查的。
   改为 **「上次提交 ∪ 工作区改动 ∪ 未跟踪文件」**。
2. 类型定义表只有 `class/interface/object/typealias` ⇒ `const val`（SCREAMING_CASE）
   出现在**参数默认值**里时被误报成"找不到定义的类型名"（本轮 2 处假报）。
   补 `CONST_DEF_RE`。

> **校验工具的误报比漏报更致命**（09-15 的教训）：误报会让人不再看输出，
> 而这类工具唯一的价值就是"报了就该改"。


### 4.2 🔴 第四道门禁：源码编码（本地漏跑，CI 立刻红）

推送后 CI run `34999960527` 在 **`Check source encoding (UTF-8 / mojibake gate)`** 失败：

```
data/bitwarden/.../auth/BitwardenAuthRepository.kt
    'utf-8' codec can't decode bytes in position 14-15
```

全文件 **656 处**非法 UTF-8 序列：每个三字节字符（汉字 / 全角标点 / 破折号）
的**末字节都被换成 `?`**（`\xe3\x80\x8d` → `\xe3\x80?`，`——` → `—?`）。

**根因**：该文件里有两个**历史遗留的控制字符**（BEL `\x07` 顶替了 `accounts` 的 a、
ESC `\x1b` 顶替了 `email` 的 e）。文件编辑工具据此**把编码猜错**，回写时按错误编码
重新编码 ⇒ 中文全部损毁。**只坏这一个文件**（仓库里只有它含控制字符）——
这解释了为什么"上一轮明明通过、这一轮改几个字就全烂"。

**修法**：`git checkout 0bdf78e -- <file>` 取回干净版本 → 用**字节级** Python 脚本
（`open(...,'rb')` / `write_bytes`，中文显式 `.encode('utf-8')`）重新应用改动 →
顺手修掉那两个控制字符。全仓扫描又发现同类残留一处：
`SecureCredentialStore.kt` 的 `\x07ndroidx` ⇒ `Androidx`。

> **可复用纪律**：
> 1. **CI 有第四道门禁**（`.github/scripts/check-encoding.py`），
>    detekt 与三个 `.ai/tools/check_*.py` **都不覆盖它**。推送前必须本地跑：
>    `python3 .github/scripts/check-encoding.py .`
> 2. **改含控制字符的文件，别用会做编码猜测的编辑器**，直接字节操作。
> 3. 字节级损坏**不可还原**（同一个前缀对应多个汉字），只能从 git 取回重写 ——
>    所以损坏要**尽早发现**，别指望事后修。


### 4.3 🔴 CI 编译红：漏 import + 顶层常量前向引用（两处）

| # | 错误 | 原因 |

| B 顶层常量前向引用 | 初始化器里引用在其**之后**声明的顶层常量（本轮 `SETTINGS_ICON_BOX`） |

遇空行 / 顶格即止；且初始化器含 `{`（lambda，延迟求值）时跳过。

### 3.5 检查更新对话框的两个状态缺陷（旋转屏幕）

写完「检查更新」后自查发现的，都不是崩溃，是**状态错乱**：

1. 结论对象 `UpdateCheckResult` 不可序列化 ⇒ 旋转后丢失 ⇒ 对话框只剩
   「暂时无法确定」，用户得关掉重开。**修法**：把结论放进 `LaunchedEffect` 的 key，
   丢了就自动重查；已有结论则跳过（故点击入口必须先清结论，否则看到旧答案）。
2. 连带陷阱：**写结论会改变 LaunchedEffect 的 key ⇒ 协程随即被取消**。
   ⇒ `updateChecking = false` 必须写在**赋值结论之前**，否则永远执行不到，
   对话框会一直停在「正在检查…」。

> 这类「key 变化取消协程」的坑，detekt 与所有自检脚本都查不出，只能靠推理。

## 8. 第二轮反馈的后续：快速解锁设置「简单点」（`0b99c68`）

> 用户原话：「设置里面的快速解锁设置还是不太好看，有没有让设置简单点的方案」

### 8.1 先归因：不简单的**不是元素数量**，是"判断题"数量

改前形态（2026-09-15 三改的产物）：**每库一张卡、卡内两行**（指纹 / 应用内 PIN），
每行 = 图标 + 标题 + 状态徽标 + 副标题 + 动作栏（最多 2 个按钮）。

真正的病灶有三层，**都不是"东西太多"**：

| # | 病灶 | 说明 |
|---|---|---|
| 1 | **两个并列开关 = 两道判断题** | 用户得先自己回答"这俩冲突吗、要不要都开"，才能动手设置 |
| 2 | **同一件事说三遍** | 状态徽标说「已启用」+ 副标题也讲状态 + 按钮写「关闭」 |
| 3 | **副标题是说明书口气** | "点此处启用"讲的是**怎么点**，而用户要判断的是**选了会怎样** |

⇒ 结论：**"简单"= 减少用户要做的判断**，判据是"把用户要做的判断列出来数一遍"。

### 8.2 改法：三选一（`UnlockChoice`）

**指纹解锁 / 应用内 PIN / 每次输主密码** —— 用户只需回答"这个库怎么进？"

三个设计决定，每个都有理由：

1. **第三个选项「每次输主密码」必须显式列出**。改前两个开关都关掉时，界面只有
   两个「未启用」，用户**看不出这等于他想要的状态**，且要表达"我就想每次输主密码"
   只能做**否定式操作**（把开关全关掉）。⇒ 永远给用户一个**肯定的退出方式**。
2. **自绘圆点指示器（20dp），不用 M3 `RadioButton`**。后者带 48dp 最小触达尺寸
   与额外内边距，三个选项叠起来把卡片撑高 —— 而"简单"的一大来源就是**看得完**。
   整行可点反而让触达区域更大；无障碍语义照给（`selectable` + `Role.RadioButton`）。
3. **砍掉状态徽标 / 操作指引 / 独立动作栏**。单选控件的选中态**本身就是状态**；
   副标题只留"选中后会怎样"（"用系统指纹验证，免输主密码"）。

### 8.3 ⚠️ 关键约定：单选是**呈现层**的，数据模型一行未改

底层 `enabled` / `pinEnabled` 仍是**两个独立布尔**、**可以同时为真**
（两条解锁路径互不依赖，这是既有能力，本次刻意保留）。做法：

- **显示时按优先级取一个**（指纹 > PIN）⇒ 两个都开的历史数据不会出现"两个都选中"；
- **互斥由动作实现**（点某项时关掉同库另一种）；
- ⚠️ **优先级顺序在"显示"与"点击"两处必须一致**，否则会出现
  "卡片显示指纹选中、点一下 PIN 却把指纹关了"的错乱。已写进 `UnlockChoice` 的 KDoc。

### 8.4 🔴 顺带修掉一个**静默数据丢失**（本轮最值得记的一条）

按 8.3 的"点某项关掉另一种"直接实现时，第一版写成了
**"点 PIN ⇒ 立刻关指纹 → 再弹 PIN 设置框"**。

漏洞：**PIN 设置是独立流程，用户可能中途取消** ⇒ 取消后就成了
**"指纹没了、PIN 也没设成"** —— 白白丢掉一种已配好的解锁方式，**且没有任何提示**。

修法（`SettingsViewModel`）：
- 新增 `dismissBiometricAfterPinEnroll: String?`，**登记意图**；
- 只在 `PinEnrollOutcome.Enrolled`（**真正落盘后**）才执行 `disableQuickUnlock`；
- `dismissPinDialog()`（取消路径）**清掉意图** —— 否则下次成功时会误关指纹；
- **"修改"与"换用"拆成两个入口**：`openPinDialog`（修改，不动指纹）/
  `openPinDialogSwitchingFromBiometric`（换用，成功后关指纹）。
  修改 PIN 时用户可能指纹与 PIN 同时开着，顺手关掉就是破坏配置。

> 教训：**互斥切换绝不能"先拆旧的、再建新的"** —— 新配置未落地前拆掉旧的，
> 就是把"用户取消"变成"用户配置被删"。**静默的数据丢失比 UI 难看严重得多。**

### 8.5 顺带修掉的误导

`biometricSummaryRes` 的 `when` 顺序错了：KDBX 库**已建好指纹钥匙**时，
副标题仍显示"需再输一次该库的主密码以建立钥匙" ⇒ 用户以为要重来一遍。
⇒ 判断顺序改为 **"已生效状态优先"**（`vault.enabled` 排最前）。

## 9. 「一个 PIN 打开 bitwarden 和 kdbx」（诉求 B）

用户原话：**"对了pin码指纹解锁可以让bitwarden和kdbx用同一个吗"**
→ 澄清后最终原话：**"我想要的是app一个PIN能够打开bitwarden和kdbx。"**

### 9.1 两次理解偏差（教训）

| 我的理解 | 用户反馈 |
| --- | --- |
| ①"设置一个 PIN，自动**同步**到其它库（仅可复制的库）" | ❌ 用户："**如果选同一个PIN呢**" |
| ②"仅可复制的库可开，其余**置灰注明**" | ❌ 用户直接点明真实意图 |
| ③ ✅ **"设置时一次配齐，以后一个 PIN 开所有库"** | ✔️ 用户认可 |

**教训：用户在说"省事"时，别自作聪明加限制条件。**
我两次都把"安全边界"当成了设计自由度，实际上用户要的是**结果**（一个 PIN 能开两个库），
而不是我替他决定"哪些库允许被覆盖"。安全边界应该体现在**实现方式**上
（每库独立信封 + 独立失败计数），而不是体现在**砍功能**上。

### 9.2 技术真相：PIN 值相同 ≠ KDBX 免掉主密码

这是本轮最重要的一条认知，**必须写进长期约定**：

```
差别不在 PIN 值，而在「包进信封的东西」：

  Bitwarden → buildFullKey(sessions.keyOf(vaultId))        ← 会话里有，无需任何密码
  KDBX      → KdbxUnlockPayload.encode(masterPassword, kf) ← 会话里【没有】主密码
```

KDBX 解锁后内存里只有「解出来的数据 + 派生密钥」，**没有原始主密码**。
⇒ 想给 KDBX 设 PIN，主密码早晚要在某个时刻被收集一次。
⇒ **唯一可行路径是"设置时一次配齐"**（用户当场输一次主密码，逐个库拿去校验）。

**好消息**：配齐之后**解锁链路一行都不用改** —— 每个库本来就有自己的信封，
输入同一个 PIN 自然各开各的。这一条决定了整个改动是"设置侧"的事，不碰解锁侧。

### 9.3 安全边界靠"每库独立"，不靠砍功能

- 信封按 `vaultId` 分存（`local_pin_key::<vaultId>`），**密文各不同**（各库密钥不同）；
- 失败计数按 `vaultId` 独立（`local_pin_attempts::<vaultId>`）⇒ 一个库锁住**不牵连**其它库；
- 某库在别处重设 PIN ⇒ **只影响那个库**。

### 9.4 自查发现的越权缺陷（已修）

初版写了 `enrollPinForAllVaults(pin, ...)` —— **自己遍历全表**给所有库设 PIN。
用户有 5 个库但只想给 1 个设 PIN 时，程序会**静默改掉另外 4 个库的配置**。
这与上一轮刚写进 8.4 的"静默改配置"是同一类错误。

⇒ 改为 `enrollPinForVaults(vaultIds, pin, masterPassword)`，**由调用方传入用户勾选的目标**；
`pinCandidateVaultIds()` 返回**全部**库（含 KDBX，由 UI 默认全选但可取消）。

⚠️ **`pinCandidateVaultIds` 必须返回全部库含 KDBX**：KDBX 并非不可设（只是要多输一次密码）。
在数据层过滤掉 = 用户以为"KDBX 不支持 PIN" = **假状态**。

### 9.5 状态迁移不能丢信息（本轮新踩的坑）

`PinDialogState.Entering` → `AskingKdbxPassword` 时，我一度只带了 `vaultId/vaultName`，
把用户勾选的目标留在一个**未定义的** `pendingPinTargets` 里。
后果：配齐时取不到勾选 ⇒ 只能退化成"全部库" ⇒ **静默越权**（同 9.4）。

⇒ 修法：让 `AskingKdbxPassword` **自己带 `targets`**，`confirmKdbxPassword()` 从本状态自取。
**规矩：状态迁移必须把下一步需要的信息一起搬过去，不能指望外部缓存。**

同理修了 `open()` 的异步回填：候选列表是异步取的，
初版无条件 `selected = candidates.map{id}`，会**覆盖用户已点的勾选**。
⇒ 改为只在"用户还没动过"（`selected.isEmpty() && pin.isEmpty()`）时才默认全选。

### 9.6 `TooManyFunctions` 触发的三次抽取

加完本功能后两个类都到了 43 个函数（detekt 上限 40）。**抽取路径**：

| # | 抽出的类 | 从哪抽 | 抽出去的是什么 |
| --- | --- | --- | --- |
| 1 | `PinEnrollmentCoordinator` | `VaultRepositoryImpl` | **编排**：给哪些库设、缺主密码怎么报 |
| 2 | `PinEnrollment` | `VaultRepositoryImpl` | **落盘动作**：包什么明文进信封 |
| 3 | `PinSettingsController` | `SettingsViewModel` | **交互**：勾选 / 输 PIN / 输主密码 / 结果汇报 |

抽完后 `VaultRepositoryImpl` **42 → 仍超限**（58 行注释让函数数涨得比预期慢）。
最终**删掉了 `enrollPin` / `enrollPinKdbx` 两个接口方法**（已无外部调用者，
`enrollPinForVaults` 完全覆盖它们），从**接口层**减 2 个函数 ⇒ 40 达标。

⚠️ **`enrollPin` / `enrollPinKdbx` 已从 `VaultRepository` 删除**（2026-09-16）。
新代码一律走 `enrollPinForVaults(vaultIds, pin, masterPassword)`，单库传一个元素的列表即可。

### 9.7 `Kdbx.verify`：只验不开库（新入口）

`PinEnrollment.enrollKdbx` 需要"确认这组凭据能开库"，但**不能真的去开库**：

1. 会把明文内容拉进内存（用户没要求，页面也没准备展示）；
2. 会**覆盖该库可能已存在的会话**（用户可能正开着，却在为另一个库设 PIN）；
3. 多库配齐时每个 KDBX 库各开一次，成本与副作用都白付。

⇒ 在 `data/kdbx` 新增 `Kdbx.verify(sourceUri, password, keyFileUri, source): Boolean`：
只做「读文件 → 尝试凭据」两步，**完全不碰 `KdbxSessionStore`**。
⚠️ 别把它实现成 `unlock()` 包一层 try —— 那正是第 2 条要避免的副作用泄漏。

另外：**keyfile 读不出来时拒绝，而不是降级成"仅主密码"**。
keyfile 不是可选装饰，少它一个字节就是开不了；静默降级会让信封里躺一组
永远解不开的凭据，用户只会看到"PIN 不对"，无从得知真因。

1. 设置 → 密码库管理 → 快速解锁 → 某库选「应用内 PIN」：
   弹框里应能看到**目标库勾选列表**（默认全选），下方是两格 PIN 输入。
2. **重点验**：同时勾选一个 Bitwarden 库 + 一个 KDBX 库 → 输 PIN → 会**多弹一步

### 10.2 第二段：凭据服务说「本空间没有配置」🔴 根因

|---|---|
| `git-credential-helper` 谁提供的 | 平台预置二进制，`~/.gitconfig` 里 `credential.helper = /usr/local/bin/git-credential-helper` |

**旁证**：环境变量里**没有** `GH_TOKEN` / `GITHUB_TOKEN`；`gh auth status` 报未登录。

## 11. 「一个指纹解锁所有的库」（诉求 C）

用户原话：

> 「默认一个生物验证的指纹，管理解锁所有的库也可以吗」

四轮确认（AskUserQuestion）：① KDBX 也能勾、当场收**一次**主密码；② KEK 失效后

先静默验完所有库**；④ **解锁页一并改**。

### 11.1 🔴 我先给过错误结论，必须记住这个教训

我最初告诉用户「指纹这条路**现在就已经是**一个指纹开所有库了」。**这是错的。**

真相：只有 `AutofillActivity.unlockAll`（自动填充入口）才遍历多库；
**解锁页**的 `UnlockViewModel.resolveTargetVaultId` **只解析出一个库**，
`completeLocalUnlock` 也只解封那一个。用户平时点的正是解锁页 ⇒ 他感受到的
"每库按一次指纹"是**真实存在**的。

> **教训**：说"现在已经是 X 了"之前，必须把**每一条**用户可触及的路径都走一遍。
> 只看其中一条（自动填充那条恰好支持多库）就下结论，等于用一个角落的行为
> 代表了整个功能。**"某处支持" ≠ "功能支持"。**

### 11.2 三条硬约束（决定了实现形态）

| 约束 | 后果 |
|---|---|
| KEK 是 **auth-per-use**（`setUserAuthenticationParameters(0, …)`） | 一个 cipher 只对一次认证有效 ⇒ **必须**"先静默验全部 → 弹一次指纹 → 连续逐库 wrap"；绝不能每库各准备一个 cipher（2026-09-14 闪退同源） |
| `stagedKdbxPayload` 是**单槽**（一个 `ByteArray?`，不按库分） | 多库会互相覆盖 ⇒ 新建 `LocalUnlockEnrollment` **完全绕开那个槽**，备料列表由控制器自己持有 |
| `VaultRepositoryImpl` 函数数**顶格 40**（detekt `TooManyFunctions`） | 加一个必须等量删一个 ⇒ 把单库 KDBX 三件套 + `stagedKdbxPayload` 迁入 `LocalUnlockEnrollment`，再内联 `wrappedPayload` 私有 helper |

### 11.3 🔴 模块分层：`domain` 不依赖 `data`（本轮踩到并修正）

### 13.7 同一份 CI 日志里的第二个编译错：`when` 对非 sealed 类型不算穷尽

CI 那次红还报了第 8 行错误（与 `VaultKind` 无关，是独立的第二个 bug）：

```
e: LocalUnlockEnrollment.kt:268:17 'when' expression must be exhaustive. Add an 'else' branch.
```

代码是：

```kotlin
// 注释还写着"万一将来有第二个实现，这里会**编译期**提醒"
when (unit) {
    is Prepared -> commitOneSafely(unit, cipher)
}
```

**注释里的说法是错的。** `LocalUnlockPreparedEnrollment` 是**普通 interface**，
不是 `sealed` —— 而且**在跨模块的前提下根本没法 sealed**：
实现 `Prepared` 在 `data` 模块、接口在 `domain` 模块，
sealed 层级要求实现同模块。

⇒ Kotlin 对非 sealed 类型的 `when` **不认为单分支是穷尽的**，
所以它既不会"提醒你有第二个实现"，也通不过编译。

**修法**：改回强转 —— `val target = unit as Prepared`，并在注释里写清为什么。
强转是这里**更诚实**的选择：唯一的构造入口是 `prepareForVaults`，
真出现第二个实现会**立刻** `ClassCastException`（响亮地失败），
而加个 `else -> ...` 只会把类型错误静默吞掉。

> **一般化教训**：`when` 想获得"编译期穷尽性保护"，前提是类型**真的** sealed。
> 不要在一个普通 interface 上写单分支 `when` 并指望编译器帮你守门 ——
> 它只会要求你加 `else`，而那个 `else` 恰恰抹掉了你想要的保护。

⚠️ 顺带一条：**CI 一次红可能同时含多个独立编译错**（本次 8 行里，
7 行同源、1 行独立）。`gh run view --repo ... ` 的 `ANNOTATIONS` 段
**要读全**，别只修第一条就重推 —— 那会多跑一轮 CI。
