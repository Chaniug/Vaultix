> **状态**：2026-09-29 深夜定稿（用户逐项拍板）。

> **性质**：**修订既有行为，不推翻既有架构** —— 三层钥匙（房子化定稿 2026-09-28）不变，
> 修的是**违反模型的行为**。与既有定稿的关系见 §7。

## 1. 一句话模型（锚点）

> **一栋房子，一扇门，N 个房间；任何「锁」只动自己那一层。**

```
门锁层（全局，各只有一把，各只有一个信封）
┌──────────────────────┐ ┌──────────────────────┐ ┌──────────────────────┐
│ 指纹锁 · Keystore KEK │ │ PIN 锁 · Argon2id    │ │ 自动恢复锁（仅 Never）│
│ auth-per-use         │ │ 全局 5 次熔断         │ │ 免认证               │
└──────────┬───────────┘ └──────────┬───────────┘ └──────────┬───────────┘
           └───────────┬────────────┴───────────────┬─────────┘
                       ▼
        ┌───────────────────────────────┐
        │ 房子钥匙（随机 256-bit，明文仅存内存）│ ← lock() = 清零 = 全屋失效
        └───────────────┬───────────────┘
            ┌───────────┼───────────┐
            ▼           ▼           ▼
   house_room::<vaultId>（每库一份，纯软件 AES-GCM）
   BW 房间包派生 64B key ／ KDBX 房间包主密码+keyfile（待改，§5 批次 B）
```

**三行记住全部**：

| 层 | 归属 | 一句话 |
|---|---|---|
| 门锁 + 房钥匙 | **全局** | 锁门 = 钥匙清零 = 全锁；只有「用户点全部锁定」和「进程死亡」两个场合 |
| 房间 | **每库** | 锁房间 = 只关那间 + 记状态；**每间自己的计时器与档位**，到点自己锁 |
| 解锁 | **两个入口** | 用户过门锁（指纹/PIN/主密码）；冷启动（仅 Never 档）免认证开部分房间（细则见 §3） |

**铁律**：任何「锁」不得跨层、跨库产生副作用。现状七处不一致（§4）全部是违反铁律的越界行为。

## 3. 解锁/恢复语义细则（施工按此，避免实现时再猜）

### 3.1 进入流程（用户视角）

```
打开 Vaultix
 ├─ 房门锁着（到点/进程被杀/主动全锁）→ 指纹 或 PIN（二选一）→ 落在星标库
 ├─ Never 档 + auto 信封完好 → 免验证静默恢复（细则见 3.2）
 └─ 没登记任何门锁 → 各库主密码兜底（每库自己的，互不相干）
之后：房钥匙在内存期间，库间切换 = 秒切，零验证（已实测）
```

对照：Keyguard 同模式（`common/.../unlock/UnlockRoute.kt:12-14`，进门三方式过门才谈库）。
Vaultix 差异：门锁包**钥匙本体**（锁着 = 钥匙密码学上不在内存）；门后可容纳异构库。

### 3.2 冷启动恢复（autoRestore）规则 —— **只开「该开」的房间**

对齐 Bitwarden（`autoUnlockKey` 仅 Never 档存在，`VaultLockManagerImpl.kt:521-529`）：

auto 信封解出的房钥匙是全局的，但**开哪些房间按每库判定**：

| 房间状态 | 冷启动是否恢复 |
|---|---|
| 档位 = Never 且无「用户主动锁」标记 | ✅ 恢复 |
| 档位 = Never 但有「用户主动锁」标记（D1） | ❌ 跳过（尊重"锁"的意图） |
| 档位 ≠ Never（含 OnAppRestart / 立即 / N 分钟） | ❌ 不恢复（超时语义 = 离开期间可能已到期；对齐 Bitwarden：非 Never 无 auto 恢复） |

### 3.3 到点锁房间的重开

- 到点（D2）锁的房间：重开**必须过一次门锁认证**（即使钥匙还在内存 —— 认证即"验一次"，
  与用户期待的 Bitwarden 行为一致）；一次认证后 fanout 可把**所有**已登记房间一起开
  （「一次认证开多库」语义不变，D5 修好后可靠）。
- 用户主动锁（D1）的房间：同上走认证重开（重开成功即清标记）。

### 3.4 ★ 多 KDBX 例外（既有产品决策，**维持不变**）

`#60` 的内存约束保留：**进入一个 KDBX 库 ⇒ 锁其它 KDBX 库**（KDBX 的"密钥"是整库明文，
多库同时解锁违反「同时只能进一个」的内存约束；执行点仍在 `ItemsViewModel.init` 的
`lockOtherKdbxVaults`）。**Bitwarden 云库不参与此约束**（BW+KDBX 可同时开 —— 用户现状）。
⚠️ 本条是对早期草案「`lockOtherKdbxVaults` 随铁律死亡」的**修正**：它不死，
只是其定位被收窄为「#60 内存约束的执行者」，不再被当作普适的"切库即锁"规则。

### 批次 B 的施工细则（**2026-09-30 改版**，原「信封包派生密钥」方案前提被推翻）

**⚠️ 前提更正（有双重证据，别再照原方案做）**：
原方案假定 3.58 s 里 KDF 占大头。回看代码与日志后**推翻**：

1. **代码结构**：`Kdbx.unlock()` 是「**先 `source.read()`（读文件）→ 再 `KdbxOpener.open(bytes, …)`（KDF + 解密 + 解析）」**
   （`data/kdbx/.../Kdbx.kt:117-148`）。所以「读文件」在 KDF **之前**，且是唯一在它之前的耗时步骤。
2. **实测时序**（`.workbuddy/vx-unlock.log`，run 1）：
   `fanout start` `22:42:40.633` → **`heap expand` `22:42:44.087`（空白 3.45 s）** → `Opened` `22:42:45.274`（+1.19 s）。
   而那 3.45 s 恰好落在 `source.read()` 上。
3. **旁证**：该 4.6 s 窗口内**网络栈日志 54 条**（http/tcp/socket/dns）。

⇒ 估算：**下载 ≈ 3.4 s（94%）**，KDF + 解析 ≈ 1.2 s（6%）。库源是 OneDrive，而设备上**没有本地 kdbx 缓存**
（app 私有目录实测无 kdbx；`files` 仅 51K）。
⇒ 只改 payload（跳过 KDF）**达不到「≤100 ms」的验收标准**（最多到 ~2.4 s）——**原方案作废**。

#### 改版方案（两步，先大后小）

| # | 事项 | 做法 | 预期收益 |
|---|---|---|---|
| **B1** | **本地 kdbx 文件缓存 + 条件回源**（**已落地 2026-09-30**） | 装饰 `KdbxFileSource`：`read()` 先看缓存，用 `stat().versionToken` 判定是否仍是最新（**只发一次元数据请求，不下载**）；token 变了才重下并更新缓存；`write()` 成功后同步更新缓存；**离线时回退缓存**（顺带获得离线解锁能力）。**只包远端来源**（SAF 本地无需缓存，其 token = 内容 SHA-256，缓存反而多做一次读） | 3.4 s → ~0.1–0.3 s（一次元数据往返） |
| **B2** | **信封包派生密钥**（原方案的 B，**降级为第二步**，未做） | 原 B1–B4（payload 升版 / 惰性升级 / 校验失败回退 / 与 #60 交互）**保留不变**，只是**不再指望它解决大头** | 剩余 ~1.2 s → 数十 ms |

**B1 落地清单（2026-09-30）**：
`KdbxFileCache`（接口）· `FileKdbxFileCache`（文件实现，**带字节数校验**防半截文件 ——
本设备被 Honor 杀进程是常态）· `CachedKdbxFileSource`（装饰器）·
挂载点 `KdbxCloudSyncCoordinator.withRemoteCache`（`fileSourceFor` 是唯一闸口 ⇒ 解锁/校验/keyfile/同步全覆盖）·
DI 在 `KdbxCloudSyncModule`（`noBackupFilesDir/kdbx_cache`，不进系统备份）·
清理在 `VaultRepositoryImpl` 的 `signOut` / `removeVault`（**按 origin 清，必须早于删行**；
文件级函数 `evictKdbxFileCache` —— 该类函数数卡在 detekt 40 上限）。

**门禁（2026-09-30，三关分开单跑）**：detekt ✅ · `:app:compileFullDebugKotlin` ✅ ·
app **289** + `data:repository` **127** = **416 / 0 失败**（+= 本批新增 11 条）。
**变异验证**：④ 漏掉 `token != null`（无令牌误命中）⇒ 1 红；⑤ 命中分支忘了 `return`（每次仍下载）⇒ 1 红。

⚠️ **B1 的收益尚未真机实测**（单测证明的是"逻辑对"，不是"真机上快了"）：
验收标准是「真机 KDBX 解锁从 3.58 s 落到 ≈1.2–1.5 s」，需要**装新包 + 解锁一次**。

**验收标准（改版）**：B1 完成后实测 KDBX 解锁应落到 **≈1.2–1.5 s**（= KDF + 解析）；
若要继续追 **≤100 ms**，再做 B2 —— **用 B1 后的真数字决定 B2 值不值**。

**B1 的安全取舍（须复核）**：缓存的是**已加密**的 kdbx（KDBX 本就是「文件可放任意位置」的格式；
其威胁模型已假定攻击者可能拿到文件）。**比现有的「从不」档免认证信封（包房钥匙）更不敏感**。
约束：① 只缓存**远端**来源；② 只存**密文**；③ **删库 / 退出登录 / 移除房间信封时一并清缓存**；
④ 缓存目录在 app 私有存储（`files/kdbx_cache/`），不进备份（`noBackupFilesDir` 更佳）。
**B2 原有的四条**（B1 线格式升版 / B2 惰性升级 / B3 校验失败回退 / B4 与 #60 交互）沿用，
编号改为 **B2.1–B2.4**。

## 8. 设置 · 密码库管理页目标形态（批次 C 施工图）

```
密码库管理
├─ 浏览的库（显式单选 radio）「条目、验证码、卡包页显示这个库的内容」
│    ○ Bitwarden   ← 当前
│    ○ valkjin.kdbx
```
