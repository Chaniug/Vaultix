## §11 第三轮修订（2026-09-17 · 密码库管理：按库卡片 + 三动作分级）

> **触发**：用户原话「退出密码库的设置应该再优化一下，能不能在设置里面的每一个密码库上增加退出的按钮…
> 管理页参考 bastion…分为两类 bitwarden 和 kdbx，每一个库相当于一个卡片，卡片上有同步、备份、退出」。
>
> ⚠️ **本轮的直接起因是一次真实事故**：用户测试 OneDrive 时误点「退出数据库」，
> 它清掉了**所有库**的本地缓存 + token，界面只显示「还没有保存的密码」⇒ **用户以为数据丢了**。
> （数据其实在服务端，重新登录即回；但**界面上无法推断这一点** —— 详见 `../README.md` 里的
> 「要么改状态、要么留日志」约定。）

### 11.1 改了什么（相对 §10 的二级页）

1. 「当前密码库」单行 → **按两类分组的库卡片**：`Bitwarden` / `KDBX`（用户拍板的两类）。
2. ★ **「锁定 / 退出 / 移除」下沉到每个库卡片**，并**分级**：

   | 动作 | 后果 | 界面表达 |
   |---|---|---|
   | 锁定 | 丢弃内存密钥，秒解 | 普通按钮 |
   | 退出 | 清**该库**本地缓存 + token（需重新登录），**远程不动** | 二次确认，文案写明"需重新登录" |
   | 移除库 | 只删本地那一行，**远程不动** | 收进 ⋮，红色 + 确认 |

3. ★ **全局「退出数据库」移除**（建议）—— 它正是本轮事故的入口：**范围不可见**。
   「清本地缓存」必须**逐个库做**，让范围与后果都看得见。
4. ★ **新建「网盘账号」区**（账号级，与库分开）：NAS(WebDAV) 凭据 / OneDrive 登录态 + 换号 / 注销 / 自检。
   理由：**凭据是账号级的、且被多个库共用**（同一 NAS 的 `credentialId`；OneDrive 同账号下的多个库）
   ⇒ 挂到单库卡片上会**连带废掉同账号的其他库，而用户看不见**。
5. ★ **按钮按能力显示**（本地 KDBX 与网盘 KDBX 的能力矩阵不同）：

   | 能力 | 本地 KDBX（`content://`） | 网盘 KDBX（`webdav:`/`onedrive:`） |
   |---|---|---|
   | 同步 | ❌ **无此概念** | ✅ |
   | 备份 | ✅ | ✅（云端历史 **≤3 份**） |
   | 离线 | ✅ | ❌ 需网络 |

   ⇒ 本地 KDBX 卡片**不显示「同步」**（否则用户以为它有云端副本）。
   判据用现成的 `origin` 前缀；⚠️ **不要新加 `sourceType` 列**（方案 §2：一加就有两处真相）。

### 11.2 ★ KDBX 卡片**不要「退出」**（与 11.1.5 同源）

对 KDBX，「退出」与「锁定」**同义**：条目**不在 Room**（在内存会话）、无 token、无待推送队列
⇒ 没有"本地缓存"可清；不解锁本来就读不到、条目也不落盘。
放一个语义重复的按钮只会让用户更分不清"哪个安全" —— 而这正是事故的病根。

### 11.3 与 §2 / §7 边界的关系（**没有被推翻**）

- §7「不要在首页摊开」**继续有效**：本轮改的是**二级页内部**的结构，不是把内容搬回首页。
- §2③「消灭单行组」**继续有效**：库卡片是"每库一张卡"，不是"每库一行设置项"。
- §4 文案三规则**继续有效**，本轮**新增一条硬约束**：
  ★ **破坏性动作的文案必须写清"对远程有没有影响"**（今天的事故就是范围不可见造成的）。

### 11.4 备份（≤3 份）与「导出 ≠ 备份」

- 备份**最多保留 3 份**（用户拍板），超出自动删最旧。
- ⚠️ **导出 ≠ 备份**：导出是**一次性格式转换**（一个文件，通常立刻拿走）；
  备份是**时间序列**（带时间戳、可列出/还原/删）。
  把"导出到网盘"当成备份 ⇒ 用户以为有历史版本、而实际只有一个最新文件 = **"看起来有保障"型危险**。

### 11.5 装机验收（在 §8.1 / §10.5 基础上补）

- [ ] 每个库卡片上只有它**该有**的按钮（**本地 KDBX 没有「同步」**）
- [ ] 「退出」只影响**那一个库**（另一个库的条目仍在），且文案写明"需重新登录"
- [ ] 「移除库」之后远程数据仍在（用另一设备 / 网页端确认）
- [ ] 「网盘账号」区能注销账号；注销后同账号的**多个**库都表现为"需重新连接"（而不是静默失败）
- [ ] 全局「退出数据库」已移除

### 11.10 修订：库**不用卡片**，用「行 + trailing ⋮」（2026-09-17 21:21 用户提出、我同意）

**用户提问**：「设置界面的密码库管理界面的，库的卡片形式展示有实现的必要吗」。

★ **这是个好问题，而且它推翻了我自己前面的设计（§11.1）** —— §11.1 的"卡片"是照
用户最初的说法（"每个库相当于一个卡片一样"）定下的，**但当时没有回头验证它是否真需要**。

**回到病因**：
| | |
|---|---|
| 真病根 | 「退出数据库」是**全局动作**、**范围不可见** ⇒ 误点后以为数据丢了 |
| 修它需要什么 | **每个库有自己的动作** —— 只此一条 |
| 卡片多给什么 | 只多一件事：让**多个动作常驻可见**（同步/备份/退出 全摊在卡面上） |

⇒ **决定：**
1. 库用 **「行 + 右侧 ⋮」**（⋮ 里放 锁定 / 同步 / 退出 / 移除）；
2. **状态放副标题**（已锁定 / 已连接 / 同步失败）—— 那才是真正要"看得见"的信息；
3. **不为卡片而卡片**：若将来某个库确实需要 3–4 个常驻动作，再升级成卡片 ——
   那时卡片是**被需要的**，不是默认。另：卡片会让列表迅速变长（5 个库 = 5 张大卡），
   与设置页其余"紧凑行"的形态也**不一致**。

⚠️ 本节是对 §11.1 的**修订**（同 §11.3 的写法：说明"谁没有被推翻"，此处 §11.1 的
**动作分级**继续有效，只换承载形式）。

### 11.11 修订：「解锁方式」合并精简（用户："逻辑很麻烦、操作很复杂"）

**先把"复杂"拆成四条，区分"可优化"与"硬约束"**：

| # | 现状 | 性质 |
|---|---|---|
| 1 | **逐库一行**，要逐个点开 | 可优化 |
| 2 | **两步对话框**（先选库 → 再确认） | 可优化 |
| 3 | ★「一个 PIN 打开多个库」**必须一次配齐** | ⚠️ **硬约束**（PIN 只在输入那一刻存在，包裹只能同流程完成） |
| 4 | 指纹与 PIN 是**两条独立路径**，用户得先搞清"我在配哪种" | 可优化 |

**目标形态（按我的方案，用户已同意"按你的意思改"）**：
```
设置 → 密码库管理 → 「解锁方式」
  ┌───────────────────────────────────┐
  │ 快速解锁（指纹）         [开关]    │
  │ ● 3 个库已启用                     │  ← 一行汇总，不再逐库列行
  │ 应用内 PIN                [开关]   │
  │ [管理解锁方式]                     │
  └───────────────────────────────────┘
                ↓ 一次流程
  ① 列出所有库（★**默认全勾**）→ ② 需要主密码的就地填 → ③ 一次认证/PIN → 全部完成
```
1. ★ **默认全勾** —— 用户 99% 想要"所有库都能快速解锁"，"逐个勾选"是纯负担（**最大的省事点**）；
2. ★ **硬约束要如实告知**：PIN 场景必须**一次做完** ⇒ UI **不能**让用户以为"可以事后再给某个库补 PIN"
   （那会得到一个**永远解不开的信封** —— 与今天那类"看起来配好了、实际打不开"同族）；
3. ★ **指纹与 PIN 合成一个「解锁方式」入口**：它们是同一问题的两种答案，
   不该让用户先去理解二者关系。

### 11.12 新需求（待定，未开工）：新建 SSH 条目时「自己生成公钥/私钥」

**用户原话**：「新建 SSH 的时候，能不能增加一个自己生成公钥和私钥的按钮呀，方便我添加和管理」。

**⚠️ 三个必须先定的点（成本差别很大）**：
1. **算法**：Ed25519（现代、短、KeePassXC 默认）vs RSA（老服务器兼容）。建议 **Ed25519 优先、RSA 可选**。
2. ★★ **私钥导出格式 —— 这才是工作量所在**：
   - 「**生成密钥对**」本身很便宜（Android `KeyPairGenerator` / API 33+ 的 `Ed25519`）；
   - 但 **OpenSSH 新格式私钥**（`-----BEGIN OPENSSH PRIVATE KEY-----`）**不是标准 PKCS#8**，
     它需要 bcrypt-kdf + chacha20-poly1305 自己封装 ⇒ **是一块独立实现**；
   - 若只需「PKCS#8 PEM」，则几乎零成本，但**很多 SSH 客户端与老工具不认**。
   ⇒ **必须先定"导出成哪种格式"**，否则会做出一个"生成了但用不上"的按钮。
3. **存哪 / 与 KeePassXC 对齐**：KeePassXC 把 SSH 密钥放在条目的自定义字段里
   （`publicKey` / `privateKey`）。**字段名必须逐字对齐**，否则在 KeePassXC 里看不到。
   ⚠️ 私钥字段必须是**受保护（Hidden）**类型。

**安全提示（必须做，不是可选）**：生成的私钥**不可再生** ⇒ 生成后要明确提示
"立即备份 / 立刻用一次"；这一点与今天"passkey 私钥是唯一不可再生的东西"是同一类。

#### 11.13.1 ★ 一处设计修正：「默认全勾」不能用"范围为空"来表达

§11.11 要求"默认全勾"，但 `quickUnlockScope()` 的空集**已经有确定含义** ——「一个库都不要」。
一个值背两种含义的后果是：用户主动全部取消勾选之后，界面会反过来告诉他"全都勾上了"。
这正是「空有三态」那条纪律要防的塌缩（同族：读路径解密失败被渲染成空列表）。

⇒ 拆成两个事实，新增独立标记 `quick_unlock_scope_confirmed`：

- `false`（从未配置）⇒ **所有库都在范围内**，向导默认全勾；
- `true` ⇒ 范围就是存储值，空集如实表示"一个都不要"。

这个拆法顺带修掉一个新库的坑：新加的库在"未确认"阶段**天然就在范围内**，
不必等用户回来手动勾一次。

#### 11.13.2 ★ 为什么"两法一次配完"不是修饰性的合并

KDBX 的主密码**两种方式都要用**（代码里的两处 `passwordFor`）：

```
enrollment.prepareForVaults(targets) { id -> passwordFor(id) }             // 指纹要
vaultRepository.enrollPinForVaults(targets, pin) { id -> passwordFor(id) } // PIN 也要
```

⇒ 分开跑 = **每个 KDBX 库的主密码要输两遍**。把两者合进一次流程（主密码只收一次）
才是真正砍掉那个重复次数的做法；只把"选库"那一步缩短，重复次数一点都不会少。

#### 11.13.3 顺手修掉的两处"沉默 / 假状态"（今天反复出现的同族病根）

1. **旧 `Notice` 通道**根本没人消费 —— `notices` / `noticeShown()` 在整个 `app/src/main` 里
   **零引用**，「库被移出生效范围」那条提示**从来没有显示过**。⇒ 删掉该通道，
   把"取消勾选会清掉该库凭据"改成**动手之前**写在向导里
   （事后的提示追不回已经删掉的东西）。
2. **指纹被取消、但 PIN 段已落盘却不报** —— PIN 段先执行；若用户随后取消指纹验证，
   旧逻辑直接回设置界面，用户以为"什么都没配成"，实际 PIN 已经可用
   （与"看起来没配好、实际能打开"同族）。⇒ 现在只要 PIN 段有结论就照样出结果页，
   如实写「已取消指纹验证，指纹未启用」。
