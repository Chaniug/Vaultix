# 快速解锁「能力级」重构 —— 逻辑定稿（2026-09-16）

> **背景**：2026-09-16 四改把「快速解锁」做成了**每库独占的三选一**（指纹 / PIN / 主密码）。
> 那是**基于"每个库单独选一种方式"的假设**，与用户原本在
> `库选择与快速解锁-逻辑定稿.md` §4.7 提出的「增加一个**生效范围**，

> ⇒ 本次把「快速解锁」从**每库独占**改回**能力级**。

## §2 新模型：两个顶层开关 + 一份统一范围

```
快速解锁
┌────────────────────────────────────────┐
│  [开关] 生物识别指纹                     │
│         用系统指纹验证，免输主密码         │
│  [开关] 应用内 PIN（6 位）                │
│         输入 6 位数字即可打开              │
├────────────────────────────────────────┤
│  生效范围                                │
│   [✓] 我的 Bitwarden                    │
│   [✓] 家庭 KDBX                         │
│   [ ] 工作 KDBX                         │
└────────────────────────────────────────┘
```

**「每次输主密码」不再需要单独做第三个选项** —— 把库移出范围（或关掉两个开关）
就是那个状态。这正是四改想要的「肯定的退出方式」，但用的是**正确**的实现途径。

## §3 真源（★ 防漂移，本节最关键）

| 状态 | 存放 | 说明 |
|---|---|---|
| 每库 `enabled` | 既有偏好（不动） | **指纹信封是否已建立** —— 唯一真源 |
| 每库 `pinEnabled` | 既有偏好（不动） | **PIN 信封是否已建立** —— 唯一真源 |
| `quickUnlockScope` | **新增** `Set<String>` | 统一生效范围（哪些库纳入快速解锁） |

**刻意不新增「全局开关」字段。** 开关的状态由「范围 + 执行结果」**推导**：

```
指纹开关 ON  ⟺  scope 非空  且  scope 中每个库都 enabled
PIN 开关 ON  ⟺  scope 非空  且  scope 中每个库都 pinEnabled
```

- 不新增字段 ⇒ **不会出现"开关说开着、信封却没有"的双源漂移**
  （这正是 #93「谎报状态的开关」的成因，别再造一个）。
- **部分未完成**（如密码打错、用户中途取消）⇒ 开关显示 **OFF**，
  副标题如实提示「有 N 个库未完成，点此继续」。
  ⚠️ **宁可显示未完成，也绝不谎报 ON** —— 本项目「假状态」纪律。

## §4 动作表（每个操作的副作用，实现照此写）

| 用户操作 | 副作用 | 需要认证？ |
|---|---|---|
| 打开「指纹」开关 | scope 为空 ⇒ 默认取**全部库**；对 scope 中**尚未 enabled** 的库走指纹登记 | 是（一次指纹覆盖全部） |
| 关闭「指纹」开关 | 删除 scope 中**所有库**的指纹信封 | 否 |
| 打开「PIN」开关 | 同上，但走 PIN 路径（需先输 PIN + 两次确认） | 否（PIN 不走系统认证） |
| 关闭「PIN」开关 | 删除 scope 中所有库的 PIN 信封与失败计数 | 否 |
| 勾选库 C 进范围 | 若**任一**开关当前为 ON ⇒ 立即为 C 补建对应信封 | 按能力定 |
| 取消勾选库 C | 删除 C 的**两个**信封，并移出 scope | 否 |
| 新库接入 | **默认不进 scope**（不静默给新库开快速解锁） | — |

⚠️ **登记失败不清除其它库**：逐库独立成败（既有纪律，本次保持）。
⚠️ **互斥切换一律不做**：四改那套「选指纹就关 PIN」**整体删除** —— 那正是本轮要纠正的错误。
（`dismissBiometricAfterEnroll` 那个"登记意图"机制随之失去用途，一并移除。）

## §5 逐库主密码：本次改动最重的一处

**现状**（要改）：一个**共用**主密码打天下
- `LocalUnlockEnrollment.prepareForVaults(vaultIds, masterPassword)`
- `PinEnrollmentCoordinator.enrollForVaults(vaultIds, pin, masterPassword)`

**改为**：逐库取密码

```kotlin
// 方案：调用方提供"逐库取密码"的能力，控制器逐库询问
prepareForVaults(vaultIds: List<String>, passwordOf: (vaultId: String) -> String?)
enrollForVaults(vaultIds: List<String>, pin: String, passwordOf: (vaultId: String) -> String?)
```

- 顺序：**逐个 KDBX 库**弹一次密码框（Bitwarden 库不问）
- 每个框都要有「跳过此库」出口 —— 用户可能确实不知道某个库的密码，
  不该被一个库卡死整批登记
- 跳过的库如实计入结果页的未完成项
- ⚠️ 传 `Map<String,String>` 也可以，但回调更好：
  密码**用完即弃**，不必在内存里攒一整份 Map

## §11 真机验收清单（交给用户）

1. 设置 → 密码库管理 → 快速解锁：应是**两个开关 + 一份范围列表**（不再是每库三选一）。
2. 勾 2 个 Bitwarden 库 → 打开「指纹」→ **只弹一次**指纹 → 两个库都出现「指纹」标记。
3. 勾 1 个 KDBX 库 → 打开「指纹」→ **先弹主密码框**，输对 → 再弹指纹。
4. **重点**：勾 2 个 KDBX 且主密码**不同** ⇒ 应**逐个弹两次**密码框，各输各的。
5. 在密码框点「跳过」⇒ 结果页把它列进**「已跳过」**，**不是**「未成功」。
6. 关闭「指纹」开关 ⇒ 范围保留、标记消失；**不应**出现"有 N 个库未完成"
   （那是 `Partial` 与 `Off` 混淆的症状）。
7. 取消勾选某库 ⇒ Snackbar 提示已移除，该库标记清空。
8. 两个开关**同时打开** ⇒ 解锁页应同时出现指纹图标与 PIN 按钮（**并列，不互斥**）。
9. 库列表页的引导横幅点「启用」⇒ 应正常走一次指纹登记（不再是自己一套实现）。
