## §0 一句话总结

> 库选择：**首次平等挑选**（选中的即默认库）→ 默认库可随时改（**唯一写入点 = 设置**）
> → 临时切库只改活跃库 → **冷启动默认库优先**，为空则按 `createdAt` 最早
> → 解锁页有**换库出口** → 快速解锁**一把 KEK 管多库**
> （KDBX 需包裹「主密码 + keyfile」，**首次接入时登记**）。

## §1 六条定稿（用户逐条认可 ✅）

| # | 条目 | 关键约束 |
|---|---|---|
| ① | **首次打开：平等问「接入哪个库」** | Bitwarden / KDBX **地位完全平等**，不预设、不建库。判据 = `vaults.isEmpty()`（已有逻辑，见 `RootNavViewModel.kt:118`） |
| ② | **接入 KDBX**：选文件（SAF）→ 输主密码 → 打开 | 是「**输入**」不是「设置」；选文件天然含选目录，**不额外做「选文件夹」步骤** |
| ③ | **快速解锁：首次接入时顺手登记** | **一把指纹（KEK）管多个库**；KDBX 侧包裹「主密码 + keyfile」 |
| ④ | **默认库：设置里可改；临时切库不写默认库** | ⚠️ **当前代码违反此条** —— `ActiveVaultStore.select()` 会写 `defaultVaultId`（见 §3） |
| ⑤ | **冷启动：默认库优先；解锁页有换库出口** | 默认库为空 ⇒ 走原有逻辑（`createdAt` 最早），**老用户行为零变化** |
| ⑥ | **App 目录：只做导入导出中转，不托管库文件** | 库文件靠 SAF `takePersistableUriPermission` 持久化，**不搬进 App 目录**（否则断同步） |

## §2 用户放弃「迁移老用户」（重要！）

**问**：这些改动会不会影响已在用 Bitwarden 的老用户？
**答**：不受影响（引导页只在 `vaults.isEmpty()` 出现；默认库为空走原逻辑）。

我原本给出 A/B 两个选项（保留旧 `defaultVaultId` 值 / 加「已显式设置」标记）。
**用户选择：「我选择让用户重新装」。**

⇒ **取消迁移逻辑**。A/B 选择题**不存在了**。
⇒ 后续可直接用**新键名**，旧值自然失效，**不需写任何迁移代码**。

⚠️ **但这不能免除 §3 的修复** —— 共键冲突是**新装用户同样会踩**的独立 bug。

## §3 ⚠️ 本轮发现的结构性冲突（**必修**，与迁移无关）

**现象**：`ActiveVaultStore.select(vaultId)`（切库）**已经会写** `preferences.setDefaultVaultId(vaultId)`。

证据（`app/.../session/ActiveVaultStore.kt:105-109`）：

```kotlin
fun select(vaultId: String) {
    _activeVaultId.value = vaultId
    scope.launch { preferences.setDefaultVaultId(vaultId) }   // ← 切库即覆盖默认库
}
```

**后果**：用户「临时切去看一眼另一个库」，会**静默永久改掉默认库**。
下次冷启动进的就是那个临时看的库 ⇒ 违反用户第 ④ 条，且**新老用户都会踩**。

**正解：拆成两个键**

| 键 | 语义 | 写入时机 |
|---|---|---|
| `activeVaultId` | 本次会话当前看哪个 | 切库时（`select()`） |
| `defaultVaultId` | 冷启动先开哪个 | **仅用户在设置里明确改时** |

⚠️ 注意：`VaultixPreferences.defaultVaultId` / `setDefaultVaultId` **已存在**
（`core/datastore/.../VaultixPreferences.kt:225` 与 `:348`）——
**不是「待新增」，是「待拆分」**。同时 `ActiveVaultStoreTest.kt:91` 有一条
`coVerify { preferences.setDefaultVaultId("vault-b") }` 固化着**当前（错误）行为**，改后必须同步修。

## §4 快速解锁：KDBX 方案定稿

### 4.1 为什么「开关点了必然失败」（#93 的精确性质）

用户原问：「为什么是无效的，照理说是生效的吧？」

**答**：它**不是「没生效的开关」，是「谎报状态的开关」**。
开关值**真写入了** `preferences`，但**保险箱里是空的**。

根因（`VaultRepositoryImpl.kt:380-381`）：

```kotlin
override suspend fun enrollLocalUnlock(vaultId: String, cipher: Cipher): Boolean {
    val key = sessions.keyOf(vaultId) ?: return false   // ← KDBX 恒 false
```

`VaultSessionManager.keyOf()` 要的是「会话里在手的**对称密钥**」；
而 KDBX 会话（`KdbxSessionStore`）持的是**整库明文**、**没有可包裹的密钥**
（`KdbxOpener.kt:28-33` 的 `KdbxSession` 不含主密码、不含 keyfile 字节）。

### 4.2 传播路径（两处 UI 行为不一致）

| 位置 | 行为 |
|---|---|
| 设置页 `quickUnlockVaults` | **遍历所有库（含 KDBX）** ⇒ 渲染出开关（谎报） |
| 库列表横幅 `QuickUnlockBanner` | 走 `enrollLocalUnlock` ⇒ **恒 false** ⇒ 指纹按钮永不渲染 |

⇒ 用户看到「设置里勾选有效、实际用不了」。

### 4.3 定稿方案：包裹「主密码 + keyfile」

**技术可行性（已验证）**：

- `LocalUnlockKeyStore.wrap(cipher, bytes: ByteArray)` / `unwrap()` ——
  **对 `ByteArray` 一视同仁**，可直接包裹任意字节（`LocalUnlockKeyStore.kt:158-174`）；
- `KdbxOpener.open(bytes, password, keyFileBytes)` —— 三输入，主密码 + keyfile 齐全即可开库。

**为什么不能包裹「整库明文」**：与 `Kdbx.kt:18`「明文绝不落盘」**直接冲突**，
且需重构会话模型 ⇒ **不可取**。

### 4.4 用户拍板的两条流程决策 ✅

**D3（失效处理）= B「明确提示 + 自动重包」**：
> 指纹过了但打不开 ⇒ 提示「主密码可能已变更」⇒ 用户输新密码成功后**自动重新包裹**
> ⇒ 下次指纹又能用。

**校验失败处理 = B「宽松」**（用户原话「宽松一点」）：
> 输错密码 ⇒ 提示「主密码不正确」，**输入框保留、就地重输**，不掉出流程。

⚠️ **新增一步「校验」是必须的**：`wrap` 只管包裹字节、**不管字节对不对**。
若用户输错密码照样 wrap 成功 ⇒ 下次指纹解出错密码 ⇒ 打开失败。
⇒ **wrap 之前必须用这组凭据实际解一次库**（复用现有校验路径）。

### 4.5 ⚠️ 「启用时当场输密码」的必然性（重要推理）

用户在设置页勾选时，KDBX 会话**已在内存**，但：

- `KdbxSession` **不持主密码**（`KdbxOpener.kt:28-33`）；
- `Kdbx.unlock()` **用完即弃**、不落盘（`Kdbx.kt:90-120`）。

⇒ **无法从当前会话取到可包裹的东西** ⇒ 必须**再问用户要一次主密码**。
⇒ 「勾选只是登记意愿、真正包裹等下次输密码」**不如「当场输密码即时闭环」**——后者
用户每个动作都有立刻可见的结果，且状态与现实立即对齐（**用户直觉优于原方案**）。

### 4.6 安全等级提醒（写给将来的自己）

| | Bitwarden | KDBX |
|---|---|---|
| 包裹物 | **对称密钥** | **主密码**（全权限） |
| 泄露后果 | 只够到本地缓存，可改密码止损 | **整个库失守，无远程撤销** |

⇒ Android 上「指纹 + Keystore 用户认证 KEK，密文绑设备」是**标准且足够强**的做法
（KeePassDX / KeePass2Android 同款）。**支持做**，但将来若加用户提示，措辞须更慎重。

### 4.7 用户提出的 UI 方案（**采纳，优于原方案**）

原方案「分两个入口」→ 用户提出：

> 「在快速解锁的设置里面增加一个**快速解锁的生效范围**，可以选取哪些库生效的。
> 相当于**指纹解锁管理多个密码库**。」

**为何更优**：一个用户只有**一把** Keystore 密钥 ⇒「快速解锁是一个**能力**，
作用于哪些库由用户勾选」是**正确的心智模型**。
⇒ 勾选 = 决定「这把钥匙串上挂几把钥匙」。

## §5 三个被推过的边界情形（定稿）

### 边界一：默认库 = KDBX 时，冷启动必须先输密码 / 指纹

**做不到「直接进库内容」** —— 那等于把明文落盘，违反 `Kdbx.kt:18`。

| 场景 | 冷启动要什么 |
|---|---|
| KDBX **未启用**快速解锁 | **必须输主密码** |
| KDBX **已启用**快速解锁 | **只需指纹** |

**关键澄清**：「首次输密码」是**一次性成本**（库的钥匙必须来自用户），
**不是每次都要付**。启用快速解锁后，两个库体验**完全对齐**：

```
Bitwarden：输主密码登录 → 启用快速解锁 → 以后只按指纹
KDBX     ：输主密码开库 → 启用快速解锁 → 以后只按指纹
```

### 边界二：「共用一个快速解锁」的精确含义

**共用 = 一把 KEK（全局唯一）**；
**不共用 = 每个库各自被包裹的东西**（Bitwarden 包对称密钥 / KDBX 包主密码 + keyfile，**必须两份**）。

心智模型：**一把钥匙串，上面挂两把不同的房门钥匙，开哪扇门用哪把。**

### 边界三：指纹的语义 = **打开「当前屏上显示的那个库」**（方案 B）

用户按指纹时：

| 方案 | 语义 | 取舍 |
|---|---|---|
| A | 开**默认库** | 想开另一个库时，最便捷的动作反而用不上 |
| **B ✅** | 开**当前屏上显示的那个库** | **指纹 = 身份确认，不带库的语义**。所见即所得 |
| C | 指纹后弹「选哪个库」 | 过度设计 |

**定稿 = B**。理由：**「默认库」决定第一屏显示谁；「指纹」只负责打开你正在看的那一个。**
两个机制职责**完全不重叠**，不会打架。

### 边界补充：两个库的「持久状态」**不对称**（勿被表面措辞骗）

用户说「bitwarden 的登录不会掉，kdbx 的密码不会变」——**听似对称，实现完全不对称**：

| | Bitwarden | KDBX |
|---|---|---|
| 背后 | **服务器**账号 | **本地文件** |
| 「登录」状态 | 令牌 + 账号信息，**可落盘** | —— |
| 关了 App 再开 | 仍「已登录、锁着」 | **会话彻底没了**（内存明文丢弃） |
| 开库要什么 | 生物识别 或 主密码 | **必须**主密码（或指纹包裹） |

⇒ 用户的「不预设 / 可灵活切换」意图**成立**，但要理解 KDBX 那侧的「状态」本质是
**「没有状态」**（文件在，但每次冷启动都是未打开）。

## §6 被否掉的方案（连同理由，避免新会话重复提议）

| 方案 | 否决理由 |
|---|---|
| 首次打开就「选文件夹 + 设密码」（KeePass 系 App 式） | ① 违反第 ① 条「平等挑选」（等于预设用户要 KDBX）；② KDBX 是「输入」已有库的密码，不是「设置」；③ 选文件天然含选目录，**多余的步骤** |
| 把 KDBX 库文件搬进 App 专属目录 | **会断同步**（用户在电脑端/网盘有同一份）⇒ 两个库各自演变，数据灾难。SAF `takePersistableUriPermission` 已解决「不用每次找文件」 |
| 「勾选 = 登记意愿，下次输密码时顺手包裹」 | 用户当场输密码**即时闭环**更优（见 §4.5） |
| 包裹「整库明文」以省掉主密码 | 与 `Kdbx.kt:18` 直接冲突 |
| 为「默认库」给老用户做迁移（A/B） | 用户选择「重新装」⇒ **取消迁移**，用新键名即可 |
| 「App 数据文件夹」托管库文件 | 同第 2 行；目录只做**导入导出中转** |
