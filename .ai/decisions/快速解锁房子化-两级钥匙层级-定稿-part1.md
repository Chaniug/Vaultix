## §0 一句话

> 把「需要过 Keystore / Argon2id 的东西」从 **N 个每库信封**压到 **1 把房子钥匙**：
> 指纹锁和 PIN 锁各包同一把随机软件密钥（全 app 仅此两把门锁信封），
> 每个库的凭据改用这把钥匙**纯软件**封装。
> **一次生物识别授权 = 一次 Keystore 操作** —— H1/H2 从结构上消失，不是被修掉的。

## §2 为什么要改：P0 的两个候选根因都是「钥匙串」形状自带的

| 候选根因 | 机制（现状代码） | 房子模型下 |
|---|---|---|
| **H1** | 多库登记 `commitForVaults` 用**一把 cipher 连续 wrap** N 个信封（`LocalUnlockKeyStore.wrap` 先读 `iv` 再 `doFinal`，无重新初始化）⇒ 第二库起 IV/密文错位；或 KEK 换代后未重包 | 登记只 wrap **1 样东西**（房子钥匙）⇒ 该代码路径整体不存在 |
| **H2** | 解锁扇出时 rest 库走 `prepareLocalUnlock` **现取新解密 cipher**；而 KEK 是 auth-per-use（`setUserAuthenticationParameters(0, AUTH_BIOMETRIC_STRONG or AUTH_DEVICE_CREDENTIAL)`），一次授权只保一次使用 ⇒ 新 cipher 的 `doFinal` 无人授权 | 解锁只做 **1 次** Keystore 解密（解房子钥匙），其余全是软件解密 ⇒ 「新 cipher」这条路不存在 |

**关键认知**：auth-per-use 的平台语义就是「一次授权 = 一次密钥使用」。钥匙串模型在把
一次授权拉伸成 N 次解包 —— **P0 不是实现失误，是在跟平台契约较劲**。
（真机 4 次 fanout 失败日志与 ~50ms 本地密码学层时序分析：报告 §3.1/§3.2。）

## §3 新模型：两级钥匙层级

```
门锁层（各只有一把，各只有一个信封）
┌──────────────────────┐    ┌──────────────────────┐
│ 指纹锁 · Keystore KEK │    │ PIN 锁 · Argon2id    │
│ 一次授权一次使用      │    │ 全局 5 次熔断        │
└──────────┬───────────┘    └──────────┬───────────┘
           └───────────┬───────────────┘
                       ▼
       ┌───────────────────────────────┐
       │ 房子钥匙（随机 256-bit 软件密钥）│
       │ 全 app 唯一被门锁包裹之物      │
       │ 明文仅存内存（硬约束 #1）       │
       │ （Never 档另有加密恢复信封*）  │
       └───────────────┬───────────────┘
           ┌───────────┼───────────┐
           ▼           ▼           ▼
      房间信封①     房间信封②     房间信封③ …（纯软件封装）
      Bitwarden     本地 KDBX     OneDrive KDBX
      64B 对称密钥  主密码+keyfile 主密码+keyfile
```

| 组件 | 定义 | 数量 |
|---|---|---|
| 门锁信封 | 指纹：KEK 直包房子钥匙（唯一过 Keystore 的 wrap）；PIN：Argon2id 派生密钥包房子钥匙 | 各 1 |
| 房子钥匙 | 随机生成；明文仅内存；进程死亡即消失（Never 档除外，见下） | 1 |
| 自动恢复信封* | **仅 `vaultTimeout = Never` 时存在**：免认证 Keystore 密钥（`setUserAuthenticationRequired(false)`）包房子钥匙；用户主动锁库即删（真锁）；对齐 Bitwarden `userAutoUnlockKey` | 0 或 1 |
| 房间信封 | 每库一份，**纯软件 AES-GCM** 封装（复用 `KdbxUnlockPayload` 长度前缀编解码；AEAD 自带完整性校验，损坏可检测） | = 库数 |

## §4 硬约束（不可妥协，逐条有出处）

| # | 约束 | 出处 |
|---|---|---|
| 1 | **房子钥匙绝不以明文落盘**（2026-09-29 修订；原文「绝不落盘」） | 用户 23:39 拍板「杀后台=自然锁定」+ 2026-09-29 用户拍板「从不档对齐 Bitwarden（userAutoUnlockKey）」。允许的落盘形态仅 Keystore 密文信封：指纹 auth-per-use / PIN Argon2id / **Never 档免认证恢复锁**（仅用户显式选「从不」时创建；主动锁库即删）。⚠️ Keyguard 的 `Origin.Persisted` 是**无条件**持久会话——仍然不学；Vaultix 的恢复信封是**档位条件 + 可被用户锁库撤销**的。⚠️ 本约束**只约束「落盘」**，不约束「内存驻留时长」——Never 档下**房钥匙在进程存活期间常驻内存**是**有意设计**（对齐 Bitwarden，见 §6.3），**不是违反本约束** |
| 2 | 一次生物识别授权 = 一次 Keystore 操作 | 平台契约（auth-per-use 语义），H2 的结构性免疫 |
| 3 | 登记只 wrap 1 次（房子钥匙） | H1 的结构性免疫 |
| 4 | 锁 = 密钥清零 | 沿用 `8.2`「真锁」定义；锁的门锁一刀切全屋 |
| 5 | 门锁失效 → **优雅降级**：禁用该锁 + 回退主密码 + 明确文案，绝不静默「本地解锁凭据不可用」 | 学 Keyguard `disableBiometricQuietly`；同时解决排查报告 P0.5（KDBX 侧「勿删登记」永不自愈 vs Bitwarden 侧清登记的**策略不一致**——新模型下两类失效分开处理，见 §6） |
| 6 | 先校验后包裹 / 明文用完即擦 | 沿用钥匙串定稿第 6 项的两条纪律，不变 |

## §5 保留什么（两篇定稿的不变部分）

- **能力级 UI 骨架**：两个并列开关 + 生效范围（能力级定稿 §2）——语义微调见 §5.1；
- 逐库问 KDBX 主密码、每框可跳过（能力级定稿 §5）；
- 每库独立成败、部分完成如实显示「绝不谎报 ON」（能力级定稿 §3 纪律）；
- 开关状态由「范围 + 执行结果」推导，**不新增双源真值**（同上，防漂移原则）；
- D3 失效自愈精神（钥匙串定稿 §4.4）——措辞升级为 §6 的失效矩阵；
- 生效范围的动作含义变化：**勾选/取消某库 = 建/删该库的房间信封（纯软件），
  不再触碰门锁、不再触发指纹**；两个总开关 = 建/删对应门锁信封（各一次 wrap）。
- ⚠️ **顺序约束：房间信封只在至少一把门锁已存在时创建**——否则房钥匙从未被任何
  门锁包裹过，进程一死房间信封即成孤儿（房钥匙无从恢复）。首启流程 = 先包门锁、再建房间。

### §5.1 设置页同步简化（用户 2026-09-28 23:48 追加拍板）

目标形态：

```
快速解锁
├── [开关] 指纹解锁 —— 副标题「用系统指纹打开所有已纳入的库」
├── [开关] PIN 解锁 —— 副标题「6 位数字；连续输错 5 次将锁定」
└── 生效范围 —— 纯复选框列表（勾 = 该库房间信封已建）
```

**删除清单**（「多余」的精确定义——五类）：

| 删什么 | 为什么变多余 |
|---|---|
| 每库「指纹 / PIN」方法标记 | 两把锁包**同一把**房钥匙 ⇒ 「这个库用哪种方式解锁」不再存在；库要么在范围内要么不在 |
| Partial 态与「有 N 个库未完成，点此继续」 | 门锁开关 = 一次 wrap，要么成功要么不变；「部分完成」结构上不可能（#121 三态开关失联的整个类别随之消失） |
| 勾库的两步登记（主密码框 → 指纹） | 勾库只建**软件**信封，不碰指纹；指纹只在开「指纹开关」时弹一次 |
| 每库 `enabled` / `pinEnabled` 双键（真源） | 真源收敛：门锁信封存在性（全局各一）+ 房间信封存在性（每库一个） |
| 结果页逐库成败分类 | 简化为「已纳入 N / 跳过 M」（跳过 = 未建房间信封，不是失败） |

**保留**：范围列表本身（安全价值：把高价值库排除在快解外，呼应钥匙串定稿 §4.6 的
安全等级提醒）、KDBX「纳入时需输一次主密码」的如实标注、「修改 PIN = 关掉再开」（既有决策）。
孤儿串：按 `check_orphan_strings --gate` 处理，**被取代的删**。
