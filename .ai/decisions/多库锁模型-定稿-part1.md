## 1. 一句话模型（锚点）

> **一栋房子，一扇门，N 个房间；任何「锁」只动自己那一层。**

```
门锁层（全局，各只有一把，各只有一个信封）
┌──────────────────────┐ ┌──────────────────────┐ ┌──────────────────────┐
│ 指纹锁 · Keystore KEK │ │ PIN 锁 · Argon2id    │ │ 自动恢复锁（仅 Never）│
│ auth-per-use         │ │ 全局 5 次熔断         │ │ 免认证               │
└──────────┬───────────┘ └──────────┬───────────┘ └──────────┬───────────┘
           └───────────┬────────────┴───────────────┬─────────┘
                       ▼
        ┌───────────────────────────────┐
        │ 房子钥匙（随机 256-bit，明文仅存内存）│ ← lock() = 清零 = 全屋失效
        └───────────────┬───────────────┘
            ┌───────────┼───────────┐
            ▼           ▼           ▼
   house_room::<vaultId>（每库一份，纯软件 AES-GCM）
   BW 房间包派生 64B key ／ KDBX 房间包主密码+keyfile（待改，§5 批次 B）
```

**三行记住全部**：

| 层 | 归属 | 一句话 |
|---|---|---|
| 门锁 + 房钥匙 | **全局** | 锁门 = 钥匙清零 = 全锁；只有「用户点全部锁定」和「进程死亡」两个场合 |
| 房间 | **每库** | 锁房间 = 只关那间 + 记状态；**每间自己的计时器与档位**，到点自己锁 |
| 解锁 | **两个入口** | 用户过门锁（指纹/PIN/主密码）；冷启动（仅 Never 档）免认证开部分房间（细则见 §3） |

**铁律**：任何「锁」不得跨层、跨库产生副作用。现状七处不一致（§4）全部是违反铁律的越界行为。

## 3. 解锁/恢复语义细则（施工按此，避免实现时再猜）

### 3.1 进入流程（用户视角）

```
打开 Vaultix
 ├─ 房门锁着（到点/进程被杀/主动全锁）→ 指纹 或 PIN（二选一）→ 落在星标库
 ├─ Never 档 + auto 信封完好 → 免验证静默恢复（细则见 3.2）
 └─ 没登记任何门锁 → 各库主密码兜底（每库自己的，互不相干）
之后：房钥匙在内存期间，库间切换 = 秒切，零验证（已实测）
```

对照：Keyguard 同模式（`common/.../unlock/UnlockRoute.kt:12-14`，进门三方式过门才谈库）。
Vaultix 差异：门锁包**钥匙本体**（锁着 = 钥匙密码学上不在内存）；门后可容纳异构库。

### 3.2 冷启动恢复（autoRestore）规则 —— **只开「该开」的房间**

对齐 Bitwarden（`autoUnlockKey` 仅 Never 档存在，`VaultLockManagerImpl.kt:521-529`）：

auto 信封解出的房钥匙是全局的，但**开哪些房间按每库判定**：

| 房间状态 | 冷启动是否恢复 |
|---|---|
| 档位 = Never 且无「用户主动锁」标记 | ✅ 恢复 |
| 档位 = Never 但有「用户主动锁」标记（D1） | ❌ 跳过（尊重"锁"的意图） |
| 档位 ≠ Never（含 OnAppRestart / 立即 / N 分钟） | ❌ 不恢复（超时语义 = 离开期间可能已到期；对齐 Bitwarden：非 Never 无 auto 恢复） |

### 3.3 到点锁房间的重开

- 到点（D2）锁的房间：重开**必须过一次门锁认证**（即使钥匙还在内存 —— 认证即"验一次"，
  与用户期待的 Bitwarden 行为一致）；一次认证后 fanout 可把**所有**已登记房间一起开
  （「一次认证开多库」语义不变，D5 修好后可靠）。
- 用户主动锁（D1）的房间：同上走认证重开（重开成功即清标记）。

### 3.4 ★ 多 KDBX：**跟随锁定**（2026-11-10 晚定稿，第三次也是最终形态）

`#60` 的内存约束保留，但**判据换了两次**，现在是：

> **同时解锁的 KDBX 份数有硬上限（3）；上限靠"用户锁它"来兑现，不靠切库、也不靠计时器。**
> **锁任意一个 KDBX ⇒ 整组失效。**

**Bitwarden 云库不参与此约束**（BW + KDBX 可同时开 —— 用户现状，且进 BW 库不影响组）。

#### 演进史（别只看结论，看每次为什么被推翻）

| 版本 | 判据 | 为什么不行 |
|---|---|---|
| 2026-11-04 起：切库即锁 | 动作（进新库就锁旧的） | "来回对比两个库"每次切回都重付 `read` + 解析 |
| 2026-11-10 上午：60 秒宽限期 | **时间**（60 秒后锁） | 常数是猜的：取小了没用（用户看五分钟），取大了等于不锁 |
| **2026-11-10 晚：跟随锁定** | **生命周期**（你锁它才锁） | — |

#### 关键论证：为什么"不锁"的代价比直觉小

`KdbxTransformKeyCache` 把派生密钥（32 字节）常驻内存 + 加密落盘，且**不随
`Kdbx.lock()` 清除**（#247：清了就等于"锁了再开又 30 秒"）。
因此 `Kdbx.lock()` 丢掉的**只是解析后的对象图**，不是密钥 —— 真正的秘密本来就一直在。

⇒「多留一份对象图」的额外暴露面，远小于"整库明文常驻"这个说法给人的直觉；
而省掉的是 `read`（网盘库是**整库下载 + stat 往返**）与**解析**两整段。

#### 实现与不变量

`KdbxUnlockGroup`（原 `KdbxGraceLocks` 已删除）：

| 入口 | 行为 |
|---|---|
| `markKdbxActive(id)`（原 `lockOtherKdbxVaults`） | 记 LRU；超 3 个才驱逐最久未用的 |
| `lockVault(KDBX)` | **锁整个组** |
| `lockAll` / 超时 | 锁全部 |
| `signOut` / `removeVault` | 只 `forget` 自己（"忘记"≠"锁一下"） |

1. **`note` 返回的驱逐名单必须被真正执行** —— 否则上限名存实亡，方案退化成"永不锁"。
2. **先补记"没见过的库"，再记本次使用的** —— 反了会让"刚点进去的库"被排成最旧。
3. **与真源对齐**（`Kdbx.unlockedIds()`）—— 否则已被锁掉的库继续占名额，上限提前触发。

#### ⚠️ 与 D1 的关系（别拿 D1 来"修"它）

D1（2026-09-29）说"锁单库不影响其它库"，保的是**冷启动恢复信封**
（`markUserLocked` 仍是每库的，本方案**不碰**）。
本方案改的是**内存会话**。锁 A ⇒ B 的会话没了、但 B 的信封还在 ⇒ 下次冷启动仍能自动恢复。
**两者是不同的东西。**

#### 不要再做的事

- ❌ 改回「切库即锁」：那是 #265 修掉的问题。
- ❌ 加回「N 秒宽限期」：任何时间常数都在替用户的意图做决定。
- ❌ 调大 `DEFAULT_MAX_UNLOCKED`：每加 1 就多一份常驻对象图，第 3 个之后收益基本为零。
- ❌ 让 `KdbxUnlockGroup` 自己执行 `Kdbx.lock`：那会形成"谁负责锁"两个来源，
  且它就不再是纯逻辑、无法用普通 JUnit 钉住 LRU 顺序。
