## 2. ★★ 两处改判（**接力者最容易照着旧文档做错的地方**）

### 2.1 §3：私钥导出格式 —— 从 PKCS#8 改为 **OpenSSH 新格式**

施工单 §3 白纸黑字建议「先做 PKCS#8 + ssh-ed25519，OpenSSH 新格式列第二期」。
**实测推翻**（OpenSSH 9.6p1 / Ubuntu，`ssh-keygen -y -f key.pem`）：

| 私钥形态 | 结果 |
|---|---|
| PKCS#8 的 **RSA** | ✅ 能读，`-y` 导出的公钥与本实现逐位一致 |
| PKCS#8 的 **Ed25519** | 🔴 **`Load key: invalid format`** |

⇒ 照原建议做，就会撞上它自己点名的失败模式「**生成了但用不上**的按钮」。
最终产出 OpenSSH 新格式（`cipher=none` / `kdf=none`）；无口令变体不需要 bcrypt-kdf，
成本比定稿估计的低一个量级。**已用真 `ssh-keygen` 交叉验证**：`-y` 与 `-lf` 全部逐位一致
（Ed25519 与 RSA 各一组）。

⇒ **教训（与 §0-2 同类）**：导出格式这种"外部契约"性质的事，**先拿真工具验一次**再写代码，
比读完文档再写省事得多。

### 2.2 §4：云表单 —— **没有**整段摘掉

施工单 §4 要求摘掉添加页的服务器/账号/密码表单，改成就地引导去「网盘账号」。
**照做会造出死路**，两个事实同时成立：

1. `CloudAccountInventory` **按设计从库的 origin 反推**账号（不另存注册表）
   ⇒ "配了但还没建库"的账号**列不出来**；
2. 「网盘账号」页是**只读清单**（只有 `refresh()`，没有"添加账号"）；
   而 `WebDavCredentialStore.save()` 全仓库**只有 `AddCloudVaultViewModel.connectWebDav()` 一处**在调。

⇒ 摘掉 = **首次使用网盘的人再也加不了网盘库**，引导去的页面同样加不了。

实际做法：表单保留但**退居「连接其他账号」之后**（无账号直接展开；有账号时默认只给
"选账号 + 去网盘账号管理"）。顺带修掉原实现的真 bug：**账号列表非空时是早退 `return`**，
表单被整块跳过 ⇒ **已配过一个账号的人永远连不上第二个账号**。

## 4. 原生化评估（Rust / Go）—— 结论

完整文档在 [`Docs/progress/native-rewrite-eval.md`](../Docs/progress/native-rewrite-eval.md)。
核心结论三条：

1. **现在别动**。`perf-plan.md` 里唯一未达标项是 **P6 切 Tab 掉帧（3.97~4.28%）**，
   性质是 **Compose 重组范围** ⇒ **换成任何语言都治不了**。
2. **唯一被量化的热点是 KDF**。同一台机器、Bitwarden 默认 600k 次、32 字节：
   | 实现 | 耗时 |
   |---|---|
   | **BouncyCastle 纯 Java（项目当前）** | **353 ms** |
   | JCE `PBKDF2WithHmacSHA256` | 133 ms |
   | OpenSSL 3.0（C） | ≈127 ms |
   | Go 标准库 | 97 ms |
   ⇒ 纯 Java : 原生 ≈ **2.7 ~ 3.6 倍**。但它在 `Dispatchers.IO` 上，**主线程不卡**，
   所以它是"解锁要等"问题而不是"卡顿"问题 ⇒ **必须先在真机上量，再决定值不值**。
3. **要引就引 Rust，不要 Go**。`gomobile bind` 会把 Go runtime 整包打进 APK（数 MB ~ 十 MB / ABI），
   而 `cargo-ndk` + UniFFI 产出的是普通 `.so`（百 KB 级）。
   ★ Rust 在本项目的真正卖点**不是"更快"**：BC 是为**跨设备确定性**才被选中的（JCE 有 provider
   编码差异史），Rust 能**同时**拿到确定性与原生速度；另外 Argon2 的 JVM 回退会在
   **Android 堆上**分配 64MiB（代码里已写明是"实打实的线上崩溃点"），原生实现把这个风险整个移走。

> ⚠️ 文档里那组基准是 **x86 + HotSpot JIT** 的，**不是 ART**。只用于判量级与方向，
> **不能当真机结论** —— 照 `perf-plan.md` §0 的铁律：不换 release 包就不下结论。

## 5.1 `check_compile_smells.py` 的 3 处误报（**别再查第二遍**）

报的是 `data/kdbx/.../KdbxCredentialCandidate.kt:160` 的文件级 `private fun sha256Hex`
被 `SafKdbxFileSource.kt:80/111/134` 调用。**是误报**，全模块编译通过。

⚠️ **理由在 2026-09-18 下半场被重新厘清过 —— 旧说法有一处是错的，别照抄。**

| | 说法 | 判定 |
|---|---|---|
| 旧（本文件原版） | 「`SafKdbxFileSource.kt:195` 在**自己 companion object 里另有一份同名实现**」 | 🔴 **错**。那一份是 `private companion object` 的成员，**从实例方法根本看不见**，不可能成为解析目标 |
| 新（已实测） | **两个模块的同名函数被脚本混为一谈** | ✅ |

真正原因是**模块边界**：`data/kdbx` 与 `data/repository` 是**两个独立 Gradle 模块**。
脚本跨文件按名字匹配 `private fun`，看到 `data/kdbx/...` 里有个 `private fun sha256Hex`
就直接认定"提供者"是它 —— 而它**根本不参与** `data/repository` 的解析。

**"是误报"这个结论怎么证出来的（可复现）**：把 `SafKdbxFileSource.kt` 整个还原到改动前，
然后**强制重编译**（`--rerun-tasks`，绕开增量缓存）：

```
gw :data:repository:compileDebugKotlin --rerun-tasks   # BUILD SUCCESSFUL
```

顺带证伪了一个我自己的错误猜想：Kotlin 里实例体**可以**解析到 companion object 的成员，
`private companion object` 也照常可见 —— 所以那句"跨作用域 unresolved reference"**不成立**。

⇒ 若将来要修脚本：让「跨文件 private」检查先按 **Gradle 模块**分组，只在同模块内匹配。
在那之前，这 3 处输出**直接忽略**。

### 9.2 第 2 次是 WebAuthn 的 User Verification，**去不掉**

`PasskeyGetActivity.kt:358-370` 的 `sign()` 首行就是防御性断言：
```kotlin
// 照抄 Bitwarden 的调用契约：签名只在「设备验证已完成」之后发生

    AutofillLogger.d("PK aborted: sign() called while not user-verified")

```
`isUserVerified` **只能**由 `BiometricPrompt.AuthenticationCallback.onAuthenticationSucceeded`
置真（`:315-319`），全文件无第二处写点。签名要用的私钥来自**已解密的内存仓储**
（`itemRepository.observeItem(vaultId, itemId)` → `cred.keyValue`，`:219-220`）——
**解锁库是拿到私钥的前提，不是可以省的步骤**。这条链路顺序是硬约束：

```
解锁库（第 1 次） → 内存里有 keyValue → verifyUser()（第 2 次） → sign()
```

### 9.3 第 1 次为什么会弹：库在「候选被点中」之前就锁着

链路（全部有源码依据）：

1. `CredentialProviderEntryBuilder.buildGetResponse():133` 查 `observeUnlockedVaultIds()`
2. `:136-163` 空 ⇒ `log("GET locked → authenticationActions")` + 暂存请求 + 只回 `unlockAction()`
3. `unlockAction():221-238` 建 `AutofillIntents.MODE_UNLOCK` 的 `PendingIntent`
4. `AutofillActivity:199` `MODE_UNLOCK -> maybeBiometricUnlock(...)`
5. `:402-445` `outcome is Prompt` ⇒ `BiometricPrompter.authenticate(...)` ← **第 1 次弹窗在这里**
6. `unlockAllAndFinish():473-505` 解封成功 → `finishCredentialFlowUnlocked()`
7. `finishWithRefreshedEntries():332-352` 重建候选塞进结果 Intent + `RESULT_OK`

⚠️ **关键：这是一次「认证动作」，不是「候选点击」。** 第 1、2 次之间隔着一次
系统的请求往返，所以**它们不可能是同一个 `BiometricPrompt` 实例**。

### 9.4 ★ 为什么不能「合并成一次」——两处独立的源码注释都在警告

`UnlockViewModel.kt:43-44` 明确了两种锁的语义差别：

| 锁型 | 密钥状态 | 恢复方式 |
|---|---|---|
| 真锁（超时 / 冷启动 / 退出数据库）| 已清零 | 主密码（+2FA）**+ 联网重登** |
| 查看层锁（主页锁按钮）| **仍在内存** | **只有生物识别**，一次认证 |

⇒ 要变成一次指纹，第 1 次弹窗必须**消失**，而那要求库在候选被点中时**根本没锁**。
可以做到这一点的只有 `VaultTimeout.OnAppRestart` 的**结构性豁免**
（`VaultLockManagerImpl:196-204`）：
```kotlin

        if (reason.firstTimeCreation || !reason.createdForAutofill) {
            handleTimeoutAction(vaultId)   // ← 只有这里会真锁
        }
    }
}
```
豁免要生效，需要**两个条件同时成立**：
1. 档位恰为 `OnAppRestart`（更严的档位走 `else` 分支，`firstTimeCreation` 时照样锁，`:207-213`）；
2. `CredentialProviderActivity.onCreate:90` 的 `markCreatedForAutofill()` 在
   `VaultixApplication.onCreate` 判定**之前**执行（`VaultixApplication.kt:59-67` 的
   KDoc 专门写了这个顺序要求）。

⚠️ 而且 `markCreatedForAutofill` **全项目只有 `CredentialProviderActivity` 一处调用**
（已 grep 确认，`autofill/` 下没有）—— AutofillService 路径不打这个标记。
用户报的场景是「通行密钥登录」，所以走的是 CP 通道，标记应该在。

### 10.2 ★ 真根因：**第 1 次给的指纹只"解锁"，但收尾时库仍是锁定态**

关键代码 `AutofillActivity.maybeBiometricUnlock():448-470`（`prepareBiometricUnlock`）：

```kotlin
private suspend fun prepareBiometricUnlock(): BiometricUnlockOutcome {
    // ① 有任意库已解锁 → 直接 Ready（不弹窗）
    if (vaultRepository.observeUnlockedVaultIds().first().isNotEmpty()) {
        return BiometricUnlockOutcome.Ready
    }
    val vaults = ...
    val lockedIds = vaults.filterNot { it.unlocked }.map { it.id }
    // ② 只挑「启用了本地快速解锁」的锁定库
    val unlockable = lockedIds.filter { id ->
        runCatching { vaultRepository.localUnlockAvailable(id).first() }.getOrDefault(false)
    }
    val first = unlockable.firstOrNull() ?: return BiometricUnlockOutcome.Fallback   // ③
    val cipher = runCatching { vaultRepository.prepareLocalUnlock(first) }.getOrNull()
        ?: return BiometricUnlockOutcome.Fallback
    return BiometricUnlockOutcome.Prompt(...)
}
```

而 §12.3 的真机日志（已修的那一轮）里有一行**当时被当成"附带目标"而放过**的证据：

```
fanout first=https://pwd.vv1234.cn → Success               ← Bitwarden 库解锁成功
fanout rest=…valkjin.kdbx → Unknown(本地解锁凭据不可用)      ← KDBX 库没解开
fanout done first=Success opened=0 failed=1
```

★ **`rest` 里那个库解不开，但 `first` 是 Success** ⇒ `unlockAllAndFinish():489` 判定
`credentialFlow && result.first == UnlockResult.Success` **成立** ⇒ 回 `RESULT_OK` 收工。

⚠️ **这里就是漏洞**：`finishCredentialFlowUnlocked()` 用 `pendingUnlockRequest` 重建候选，
而 `CredentialProviderEntryBuilder.buildGetResponse():133` 的**第一条判据**是
`observeUnlockedVaultIds().first()`——只要**还有任何库锁着**（那个 KDBX 库），
它算出来就**非空**（因为 `first` 那个 Bitwarden 库开了），于是**会正常列候选**。

**等等 —— 那为什么还是弹了 ①？** 关键在于 `PasskeyGetActivity:233-236` 的**判据更严**：

```kotlin
val vaultUnlocked = vaultRepository.isVaultUnlocked(vaultId)      // ← 单库！
val anyUnlocked   = vaultRepository.observeUnlockedVaultIds()...  // ← 任意库
...
if (!vaultUnlocked || !anyUnlocked) { unlockAndFinish() }         // ← 两个都要真
```

`EXTRA_VAULT_ID` 由**候选条目**决定（`CredentialProviderEntryBuilder:366`
`vaultId = m.vaultId`，来自 `PasskeyMatch.vaultId`）。
⇒ **若通行密钥那条记录属于「本地快速解锁不可用」的那个库**（正是 KDBX 库，
或那个 `rest` 里 `Unknown(本地解锁凭据不可用)` 的库），则：

1. `buildGetResponse` 列候选时：`unlocked` 非空 ⇒ **列出候选**（含那条通行密钥）
2. 用户点候选项 ⇒ `PasskeyGetActivity` 收到 `vaultId = 那个库`
3. `isVaultUnlocked(那个库)` = **false** ⇒ **`unlockAndFinish()`** ⇒ 回取消
4. 取消 ⇒ 走 `unlockAction()` ⇒ `AutofillActivity` ⇒ **① 弹指纹**
5. 指纹只解 KDBX 库的 `first`（Bitwarden 那个），**那个特定的库仍锁着** ⇒ 回到第 3 步

**⇒ 这是一个自我维持的环：列得出来 → 点进去说锁定 → 去解锁 → 解的不是它 → 再点还是它。**

### 10.3 与「从不加锁」的矛盾正好对上

这也解释了**为什么「从不加锁」还会弹**：这个环**完全不经过超时引擎**——
它是「候选列表的解锁判据是『任意库』，而凭据校验的判据是『该库』」这**两个口径不一致**造成的。
`Never` 档位只是让"本该早就解锁的库一直锁着"这件事没有被超时锁定掩盖掉。

## 11. ★★★ §10 的结论**被证伪**，真根因在别处：`isUserPreVerified` **只写不读**

### 11.1 真根因：UV 豁免标志写进了三处，**没有任何一处读它**

`isUserPreVerified` 这套机制**存在、且注释写得完全正确**，但**链路断了**：

| 环节 | 代码 | 状态 |
|---|---|---|
| 定义语义 | `CredentialProviderIntentUtils.isUserPreVerified()`（`:60-79`） | ✅ 实现正确 |
| 契约说明 | 同上 KDoc：「第二条来源是本 App 自己的解锁流程（用户在解锁时刚做过生物识别，**无需再弹一次**）」 | ✅ 意图明确 |
| 写进管理器 | `CredentialProviderRequestManager.setGetCredentialRequest/setCreateCredentialRequest(…, preVerified)` | ✅ |
| trampoline 透传 | `CredentialProviderActivity:135` `.putExtra(EXTRA_KEY_UV_PERFORMED_DURING_UNLOCK, …)` | ⚠️ **但这条只传给 MainActivity** |
| **候选条目的 PendingIntent** | `CredentialProviderEntryBuilder.publicKeyEntry():362-377` | ❌ **完全没带这个 extra** |
| **`PasskeyGetActivity` 读取** | `verifyUser()` | ❌ **0 处引用**（`grep -c` 结果 = 0） |
| **`PasskeyCreateActivity` 读取** | `verifyUser()` | ❌ **0 处引用** |

**⇒ 两处断裂，缺一不可：**

1. **候选条目的 Intent 里没有这个 extra** ⇒ `PasskeyGetActivity` 就算想读也读不到；
2. **`PasskeyGetActivity` / `PasskeyCreateActivity` 压根没读** ⇒ `verifyUser()` 无条件弹窗。

### 11.2 为什么这正好解释「两次指纹」

```
① CP 列候选时库锁定 → authenticationActions → AutofillActivity 弹指纹（解锁）
② 解锁成功 → RESULT_OK + 候选列表
③ 用户点候选 → PasskeyGetActivity
④ verifyUser() 无条件弹指纹  ← 即使第 ① 步刚在同一流程里做过生物识别
```

★ 第 ④ 步的验证与第 ① 步的**是同一次用户意图、同一个流程**，
`isUserPreVerified` 这套机制**本来就是为消除它而设计的**（注释原文：
「用户在解锁时刚做过生物识别，无需再弹一次」）。

⚠️ 但注意：**解锁在另一个 Activity、且经系统往返**——
所以「解锁时的认证能不能算作 WebAuthn UV」在**协议层面需要慎重**：
- WebAuthn 的 UV 要求"本次断言前有过设备验证"，同一个流程内的验证**通常可接受**
  （Bitwarden 就是这么做的：解锁后 `isUserPreVerified = true` ⇒ 断言不再弹）；
- 但**不变量是「验证必须发生在签名之前且未被撤销」**——
  `sign()` 的 `isUserVerified` 断言必须**由这个标志合法地置真**，
  而不是被绕过（那会让"没验证也能签名"，是**安全缺陷**，不是优化）。

### 11.3 所以「只弹一次」是**可达的**，但必须修对

§9.6 说的「② 去不掉」需要修正：**② 在这一条流程里能省**，省的方式是
**把第 ① 步的验证结论合法地传下去**，而不是删掉 UV 检查。

正确修法（三处，缺一不可）：

| # | 位置 | 改动 |
|---|---|---|
| 1 | `CredentialProviderEntryBuilder.publicKeyEntry()` | 建 `PasskeyProviderIntents.getIntent(...)` 时补上 UV 已完成的 extra |
| 2 | `PasskeyGetActivity.verifyUser()` 调用点 | 若 `isUserPreVerified` ⇒ **跳过弹窗**，直接 `isUserVerified = true` 后 `sign()` |
| 3 | `PasskeyCreateActivity.verifyUser()` 调用点 | 同上（注册侧） |
| ⚠️ | **解锁→候选 的标记来源** | `AutofillActivity` 解锁成功、且本次是 CP 流程时，要把「刚做过生物识别」写进管理器，否则第 1 步传下去的值恒为 `false` |

**第 ⚠️ 条是关键**：`CredentialProviderRequestManager.isUserPreVerified` 目前在
`setGetCredentialRequest/setCreateCredentialRequest` 里被赋值，而
**解锁成功后没有任何地方把它置为 true** ⇒ 即使补了 1~3，值仍是 `false`，弹窗照旧。

### 11.4 安全边界（**动手前必须定死**）

「解锁用的生物识别」能否充当「WebAuthn UV」，必须满足：
1. **同一次流程**（不能被"上一次会话的解锁"顶用）—— 所以标记要有**时效/流程绑定**，
   不能做成进程级持久标志；
2. **验证对象一致**：Android 的 `BiometricPrompt` 只证明"设备用户在场"，
   与 WebAuthn UV 的语义在规范上**是可以对齐的**（都是 user verification）；
3. **`sign()` 的断言不能删、不能放宽** —— 只允许"合法地提前置真"。

⚠️ 这三条要在实现前写成决策记录（`.ai/decisions/`），
**不要**在代码里凭"看起来能省一次"就跳过。

### 11.5 与 §9 的关系（哪些结论仍然有效）

| §9 结论 | 是否仍成立 |
|---|---|
| 两次弹窗分属两个不同的 Credential Manager 请求 | ✅ 成立（解锁动作 ≠ 候选点击） |
| ② 属于 WebAuthn UV、不能"删掉" | ✅ 成立（**但可以"合法跳过"**，见 11.3） |
