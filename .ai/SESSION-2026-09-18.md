## 2. ★★ 两处改判（**接力者最容易照着旧文档做错的地方**）

### 2.1 §3：私钥导出格式 —— 从 PKCS#8 改为 **OpenSSH 新格式**

施工单 §3 白纸黑字建议「先做 PKCS#8 + ssh-ed25519，OpenSSH 新格式列第二期」。
**实测推翻**（OpenSSH 9.6p1 / Ubuntu，`ssh-keygen -y -f key.pem`）：

| 私钥形态 | 结果 |
|---|---|
| PKCS#8 的 **RSA** | ✅ 能读，`-y` 导出的公钥与本实现逐位一致 |
| PKCS#8 的 **Ed25519** | 🔴 **`Load key: invalid format`** |

⇒ 照原建议做，就会撞上它自己点名的失败模式「**生成了但用不上**的按钮」。
最终产出 OpenSSH 新格式（`cipher=none` / `kdf=none`）；无口令变体不需要 bcrypt-kdf，
成本比定稿估计的低一个量级。**已用真 `ssh-keygen` 交叉验证**：`-y` 与 `-lf` 全部逐位一致
（Ed25519 与 RSA 各一组）。

⇒ **教训（与 §0-2 同类）**：导出格式这种"外部契约"性质的事，**先拿真工具验一次**再写代码，
比读完文档再写省事得多。

### 2.2 §4：云表单 —— **没有**整段摘掉

施工单 §4 要求摘掉添加页的服务器/账号/密码表单，改成就地引导去「网盘账号」。
**照做会造出死路**，两个事实同时成立：

1. `CloudAccountInventory` **按设计从库的 origin 反推**账号（不另存注册表）
   ⇒ "配了但还没建库"的账号**列不出来**；
2. 「网盘账号」页是**只读清单**（只有 `refresh()`，没有"添加账号"）；
   而 `WebDavCredentialStore.save()` 全仓库**只有 `AddCloudVaultViewModel.connectWebDav()` 一处**在调。

⇒ 摘掉 = **首次使用网盘的人再也加不了网盘库**，引导去的页面同样加不了。

实际做法：表单保留但**退居「连接其他账号」之后**（无账号直接展开；有账号时默认只给
"选账号 + 去网盘账号管理"）。顺带修掉原实现的真 bug：**账号列表非空时是早退 `return`**，
表单被整块跳过 ⇒ **已配过一个账号的人永远连不上第二个账号**。

## 4. 原生化评估（Rust / Go）—— 结论

完整文档在 [`Docs/progress/native-rewrite-eval.md`](../Docs/progress/native-rewrite-eval.md)。
核心结论三条：

1. **现在别动**。`perf-plan.md` 里唯一未达标项是 **P6 切 Tab 掉帧（3.97~4.28%）**，
   性质是 **Compose 重组范围** ⇒ **换成任何语言都治不了**。
2. **唯一被量化的热点是 KDF**。同一台机器、Bitwarden 默认 600k 次、32 字节：
   | 实现 | 耗时 |
   |---|---|
   | **BouncyCastle 纯 Java（项目当前）** | **353 ms** |
   | JCE `PBKDF2WithHmacSHA256` | 133 ms |
   | OpenSSL 3.0（C） | ≈127 ms |
   | Go 标准库 | 97 ms |
   ⇒ 纯 Java : 原生 ≈ **2.7 ~ 3.6 倍**。但它在 `Dispatchers.IO` 上，**主线程不卡**，
   所以它是"解锁要等"问题而不是"卡顿"问题 ⇒ **必须先在真机上量，再决定值不值**。
3. **要引就引 Rust，不要 Go**。`gomobile bind` 会把 Go runtime 整包打进 APK（数 MB ~ 十 MB / ABI），
   而 `cargo-ndk` + UniFFI 产出的是普通 `.so`（百 KB 级）。
   ★ Rust 在本项目的真正卖点**不是"更快"**：BC 是为**跨设备确定性**才被选中的（JCE 有 provider
   编码差异史），Rust 能**同时**拿到确定性与原生速度；另外 Argon2 的 JVM 回退会在
   **Android 堆上**分配 64MiB（代码里已写明是"实打实的线上崩溃点"），原生实现把这个风险整个移走。

> ⚠️ 文档里那组基准是 **x86 + HotSpot JIT** 的，**不是 ART**。只用于判量级与方向，
> **不能当真机结论** —— 照 `perf-plan.md` §0 的铁律：不换 release 包就不下结论。

## 5.1 `check_compile_smells.py` 的 3 处误报（**别再查第二遍**）

报的是 `data/kdbx/.../KdbxCredentialCandidate.kt:160` 的文件级 `private fun sha256Hex`
被 `SafKdbxFileSource.kt:80/111/134` 调用。**是误报**，全模块编译通过。

⚠️ **理由在 2026-09-18 下半场被重新厘清过 —— 旧说法有一处是错的，别照抄。**

| | 说法 | 判定 |
|---|---|---|
| 旧（本文件原版） | 「`SafKdbxFileSource.kt:195` 在**自己 companion object 里另有一份同名实现**」 | 🔴 **错**。那一份是 `private companion object` 的成员，**从实例方法根本看不见**，不可能成为解析目标 |
| 新（已实测） | **两个模块的同名函数被脚本混为一谈** | ✅ |

真正原因是**模块边界**：`data/kdbx` 与 `data/repository` 是**两个独立 Gradle 模块**。
脚本跨文件按名字匹配 `private fun`，看到 `data/kdbx/...` 里有个 `private fun sha256Hex`
就直接认定"提供者"是它 —— 而它**根本不参与** `data/repository` 的解析。

**"是误报"这个结论怎么证出来的（可复现）**：把 `SafKdbxFileSource.kt` 整个还原到改动前，
然后**强制重编译**（`--rerun-tasks`，绕开增量缓存）：

```
gw :data:repository:compileDebugKotlin --rerun-tasks   # BUILD SUCCESSFUL
```

顺带证伪了一个我自己的错误猜想：Kotlin 里实例体**可以**解析到 companion object 的成员，
`private companion object` 也照常可见 —— 所以那句"跨作用域 unresolved reference"**不成立**。

⇒ 若将来要修脚本：让「跨文件 private」检查先按 **Gradle 模块**分组，只在同模块内匹配。
在那之前，这 3 处输出**直接忽略**。

### 8.1 验证码页：临期自动换码 + 行内 Next 预览

用户原话两条：「**只剩 5 秒的时候自动复制下一个验证码**」「**在验证码条目上也显示下一个
验证码，比较小字的那种**」。落点 `ui/totp/TotpCodesScreen.kt`。

| 决定 | 依据 |
|---|---|
| 阈值**复用** `TOTP_HOT_WARNING_SECONDS`（=5），**不新开一个常量** | 码转警示色与"临期换码"是**同一个「快过期了」概念**。两处各写一个数 ⇒ 迟早出现「码变红了但复制到的还是它」的错位 |
| 临期时复制 `nextCode`，非临期照旧复制当前码 | 对齐 Bastion `TotpCodeCard.codeToCopy`（`reference/bastion/.../TotpCodeCard.kt`） |
| HOTP **不参与**（`isExpiring = !isHotp && …`） | HOTP 基于计数器、没有时间衰减，"下一个码"这个概念对它不成立 |
| 行内 Next 预览用 `labelSmall` + `Monospace`，**不给 `SelectionContainer`** | 等宽 ⇒ 每秒刷新宽度不抖（与大码同因）；包上选择容器会把长按选择吸到小码上、**抢走整行点击**手势 |
| ⚠️ **临期换码时补一句 Snackbar**（`totp_copied_next`），普通复制仍然安静 | 这是对 2026-09-13「复制不要提示」的**定向例外**。理由：换码时用户**看得见的是大码、进剪贴板的是下一个** —— 不说明就只能是"复制错了"。提示的不是"复制成功"，而是"你复制的和屏幕上显示的不是同一个" |

> ★ **这条例外不要顺手推广成"复制都提示"。** 2026-09-13 去掉提示的理由依然成立
> （`Snackbar` 会在悬浮胶囊底栏上方压出一块自带 surface 底板的方块，观感很脏）。
> 例外只限"复制内容与屏幕所示不一致"这一种情况。

### 8.2 权限引导页（新增 `ui/permissions/`）

用户原话：「**权限管理界面能优化一下。加一点规范的引导，打开什么权限之类的**」。

理由：系统页只列权限名与开关，**不解释为什么要** —— 而用户对密码管理器的权限恰恰最戒心，
不解释就等于心虚。

**另外两处必须记住的口径**：

1. **`LongParameterList` 之外还有个隐藏的 8 参限制**：`SettingsScreen` 的
