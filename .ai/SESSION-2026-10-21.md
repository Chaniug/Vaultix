### P0 · Bitwarden 附件下载链路（完整）
| 层 | 文件 | 内容 |
|---|---|---|
| 模型 | `VaultAttachment` | 加 `wrappedKey`（EncString **密文**，明文不进模型） |
| DTO | `AttachmentDownloadResponse` | `GET /ciphers/{id}/attachment/{aid}` 的 `url` |
| API | `BitwardenVaultApi.attachmentDownload` | 端点 |
| DI | `@AttachmentHttpClient` + `NetworkModule.provideAttachmentOkHttpClient` | **无鉴权** client |
| 编排 | `BitwardenAttachmentDownloader` | 拿 URL → 下载密文 → 解包附件密钥 → 验 MAC → 解密写 sink |
| 仓储 | `ItemRepository.downloadAttachment` / `ItemRepositoryImpl` | 解锁校验 + 库类型分流 + 密钥候选（条目密钥→账号密钥） |
| UI | `AttachmentsSection` / `AttachmentRow` | 下载按钮（下载中全局禁用）、`ACTION_VIEW` 打开，打不开提示"已下载但没有能打开的应用" |

### P1 · KDBX 附件：只做"可见"
`KdbxItemMapper` 把 `Entry.binaries` 映射为 `VaultAttachment`（hash 为 id）。
**导出不做**：kotpass 0.13.0 的 `Meta.binaries` 是 `@PublishedApi internal`
（已用 `javap` 核对字节码），没有按 hash 取字节的公开入口；反射不可接受（密码库纪律）。
UI 对 KDBX 来源只显示文件名 + "暂不支持导出"说明，不给按钮。

## 二、两个安全设计（必须保持）

1. **先验 MAC、再解密**（`BitwardenAttachmentCrypto`）：参考实现（Bastion）是流式边解边验，
   MAC 失败时明文已落盘；本实现先整份校验 HMAC（下载密文先全进内存），通过后才写 sink ——
   **写出去的一定是认证过的明文**。11 条测试含 4 条反证 + 已做过变异验证。
2. **附件下载必须用无鉴权 client**（`@AttachmentHttpClient`）：签名 URL 指向第三方对象存储
   （Azure/S3），默认 client 的 `BitwardenAuthInterceptor` 会把 Bearer 发给第三方域名 =
   令牌进别人的访问日志。新增网络请求时**不要**图省事复用默认 client 下载附件。
