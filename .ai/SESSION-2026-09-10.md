## 第二十六轮（CI 编译门禁闭环 + getOrigin 语义纠正）

### 背景
第二十五轮推 `de6ad9e`（credentials 1.3.0→1.6.0 + 全面对齐 Bitwarden）后：
- run `34495082792` 挂在 detekt（`RomCompat.kt` 常量返回 + 超长行）→ `3e23740` 清理，
- run `34495532104`：detekt ✓，但 **Build Debug APK ✗**：
  ```
  e: CallingAppOrigin.kt:51:44 No value passed for parameter 'privilegedAllowlist'
  > Task :app:compileFullDebugKotlin FAILED
  ```
  本轮专门解决这一条。

### 做法：反编译真源，而非猜签名
下载 `maven.google.com` 上的 **credentials-1.6.0.aar**（634 KB）→ `unzip classes.jar`
→ `javap -c -p` 逐条读 `CallingAppInfo` / `PrivilegedApp` / `SignatureVerifier` / `RequestValidationUtil`。

**关键事实（纠正上一轮的错误认知）**：
`getOrigin(privilegedAllowlist)` 的 allowList **不是可选占位参数，而是签名背书名单**：
| 分支 | 条件 | 结果 |
|---|---|---|
| 1 | `!isValidJSON(allowList)` | 抛 `IllegalArgumentException` |
| 2 | `origin == null` | `return null`（不校验） |
| 3 | 包名命中且 `intersect(调用方指纹, 名单指纹)` 非空 | `return origin` |
| 4 | 其余 | 抛 `IllegalStateException` |

且 `signatures` 是**必填**且元素为**对象**（`getJSONObject(i).getString("cert_fingerprint_sha256")`）。
→ 空名单 / `[]` / `["FP"]` 三种写法**全部必抛异常**，必须填调用方**自己的真实指纹**。

### 修复（`d082e63`）
`CallingAppOrigin` 改为**自证式读取**：
1. `ALLOW_LIST_TEMPLATE`：`{"apps":[{"type":"android","info":{"package_name":"%s","signatures":[{"cert_fingerprint_sha256":"%s"}]}}]}`；
2. `signingFingerprintOrNull(info)`：`info.signingInfo`，多签名者→null，否则
   `SHA-256(apkContentsSigners[0])` 大写冒号分隔（对齐 Bitwarden `getSignatureFingerprintAsHexString`）；
3. `originOrNull` = 守卫 → 算指纹 → 拼只含自己的名单 → `getOrigin` → 规整空串；
4. `trustedOriginOrNull(allowList)` 保留给将来接用户信任名单（对应 next-steps ⑦ 的正解路径）。
头部注释按反编译事实重写。

### 验证
- 静态：非注释代码行全 ≤120；ReturnCount 全守卫子句；object 内 6 函数 ≤40；JSON 模板 `json.loads` 结构合法。
- **CI run `34496366032` 全绿**：detekt ✓ / 编码门禁 ✓ / 签名解码 ✓ / Build Debug APK ✓ / 单测（非阻塞）✓。
- 预览包已发布：`app-full-debug.apk`（`dev-d082e63`，31.09 MB，sha256 `76d5afd3…`）。

### 教训
**读第三方 API 不能只看方法签名猜语义，要反编译看实现。** 上一轮的「传个空名单就能拿 origin」
是纯猜想，本轮 5 分钟的 `javap` 直接给出了确定答案，省掉一轮 CI 试错。

## 第二十八轮（2026-09-11）· 通行密钥验签失败根因

用户：「在edge使用通行密钥登陆的时候，会报错，验证失败的」

### 定位过程
先问清了三个关键事实（这一步决定了后面不用瞎猜）：
- 报错时机 → **指纹验证通过了**，网站才报错
- 影响范围 → **所有网站**都失败
- 报错原文 → **验签失败 / 无法验证**

三条合起来只有一个解释：**签名数据的密码学校验不通过**。候选展示、CP 通道、
生物识别、credentialId 匹配全都是通的（前几轮反复修的就是这些，它们早就通了）。

### 排查：先实测排除，再下结论
写了 JVM 压测脚本（`/tmp/wv/T*.java`）逐个排除疑似项，**没有靠推理**：
1. **密钥编解码往返**：200 组随机 P-256 密钥走
   `base64Url(PKCS8)` → `decodeBase64UrlOrStandard` → `parseEcPrivateKey` → 签名 →
   原公钥验签，**200/200 通过**（DER 分支命中 200/200）。→ 排除。
2. **PKCS8 分支顺序**：PKCS8 长 67 字节，`normalizeScalar` 正确返回 null 交给 DER
   分支，不会被误当 32 字节裸标量。→ 排除。
3. **clientDataHash 反选**：模拟 Chromium 含 `crossOrigin` 的原文，验证「无 crossOrigin
   候选不命中、含 crossOrigin 候选命中」。→ 反选逻辑有效，排除。
4. **PendingIntent flag**：`requestCode = credentialId.hashCode()` +
   `FLAG_UPDATE_CURRENT` 组合正确（同一 credential 多次请求会更新 extras）。→ 排除。

### 根因（`8afac3d`）
`buildAuthenticatorData` 只设 UP(0x01)+UV(0x04)，**缺 BE(0x08)/BS(0x10)**。
Vaultix 私钥存库 + 随服务端同步 ⇒ 语义上是**可备份凭证**，必须声明 BE + BS。
对齐 Bastion（两边基线都是 `0x1D`，注册额外加 AT）：
- 断言 `0x05` → `0x1D`
- 注册 `0x45` → `0x5D`

连带修复：
- **signCount** 硬编码 0 → 读库非零值原样发送不递增（Keyguard 口径，避免跨设备分叉）；
- **响应 JSON** 补 `clientExtensionResults:{}`（部分 RP 解析器直接读该键）+
  `authenticatorAttachment:"platform"`。

### ⚠️ 关键：修复前注册的 passkey 必须重新注册
RP 记的是**注册时**的 BE/BS 语义。改代码只能让**新注册**的凭证正确，旧凭证的断言
仍会因基线不符而失败。用户需在被拒的网站删除旧通行密钥后重新创建。

### 教训
**把「功能不通」拆成阶段，别笼统当成一个问题。** 前几轮一直在修「能不能弹出来」，
而那一步早就通了；真正的故障点在「弹出来之后的数据是否正确」。
用户给出的「指纹通过 + 全站失败 + 验签失败」这个组合，本可以一步定位到数据层。

**能在本地跑的实验就不要靠推理排除** —— 三个疑似项用一轮脚本 10 分钟排掉，
比推三轮 CI 试错便宜得多。
