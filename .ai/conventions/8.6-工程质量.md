### 8.6.0 本地 vs GitHub CI 的编译分工（2026-10-28 拍板）

> 用户原话：「大型的编译可以放到 github 上进行，感觉更能够提升编程效率」
> ⇒ **固化，不再每轮口头指定。**

| 场景 | 在哪跑 | 跑什么 |
|---|---|---|
| 改完一个模块，想抓语法 / 签名错 | **本地** | **只跑改动模块的增量编译**：`:data:repository:compileDebugKotlin`、`:core:xxx:compileDebugKotlin`；改到 app 才跑 `:app:compileFullDebugKotlin` |
| 全量门禁（detekt + 全模块单测 + app 编译/打包） | **GitHub Actions** | push `main` → `ci-debug.yml`；用 `gh run watch` / check-run annotations 看结果 |
| 发版 / 需要真机包 | 本地（必要时） | 按 8.6 三关**分开单跑**；发版仍走 `rele` |
| 只改文档 / 注释 | 不编译 | 跑 `.ai/tools/check_*.py` + `check-encoding.py` 即可 |

**硬规则**：

1. **本地不做全量 `test` / `assemble` / 全模块 detekt**（除非发版、或 CI 不可用）。
   日常开发的「全量门禁结论」以 CI 为准 —— 这与「必须含 test」不矛盾：
   那条约束的是**收口/发版**，不是每次改一个文件都本地跑一遍。
2. **本地编译只跑「改动模块 + 它的上游」**；一次命令不要串多个大任务
   （daemon 会崩，见下文的三关分开单跑）。
3. **全量结果以 CI 为准**；本地绿不等于 CI 绿，反之亦然。
4. **看 CI 失败用 annotations**（文件:行:列 + 消息），不要反复本地重跑整条链。
5. **绝不 push `rele`**（= 直接发版）；日常只 push `main`。
6. **不要为了「干净」删 `~/.gradle` / 项目 `.gradle`**；删 `build/` 只在下一次
   确实需要全量重编时做（否则只是把成本从 CI 挪回本地）。

### 8.6 工程质量
- **detekt 两个必须知道的坑**：① `CyclomaticComplexMethod` 会把**同文件**被调私有函数的
  复杂度**累加**进调用方（实测拆同文件 helper：19 → 41，阈值 14）；本版本
  `ignoreNestingFunctions` 默认 **false** ⇒ 作用域函数（`let`/`run`/`apply`/`also`/`forEach`）
  每个 +1。**唯一规避 = 把 helper 拆到「独立文件」**（detekt 逐文件分析）。
  实证法：把可疑函数体 stub 成 `return emptyList()` 再跑。
  ② detekt **只做静态检查、不做类型检查**，且 **CI 里 detekt 先于 compile** ⇒
  **编译错误被掩盖**（现象：CI 1 分钟就红）。**改完 detekt 必须真跑一次 compile。**
- 🔴 **本地 detekt CLI 不报 `CyclomaticComplexMethod`**（2026-09-16 踩到，代价一次 CI 往返）：
  用 `detekt-cli --config config/detekt/detekt.yml` 跑，**永远 0 findings** ——
  因为该规则依赖 `buildUponDefaultConfig`，而那是 **gradle 侧的参数**，CLI 传不进去
  （配置文件里写 `buildUponDefaultConfig` 会直接报 "misspelled or does not exist"）。
  ⇒ 本地 CLI 只能覆盖 `LongMethod` / `LongParameterList` / `MagicNumber` 这类纯语法规则；
  **圈复杂度只有 CI（gradle 任务）会判**。
  ⇒ **本地复现办法**（已验证有效）：另写一份探针配置，**只**显式打开该规则：
  ```yaml
  # /tmp/detekt-probe.yml
  complexity:
    CyclomaticComplexMethod:
      active: true
      allowedComplexity: 14
      ignoreNestingFunctions: false
  ```
  `detekt-cli --config /tmp/detekt-probe.yml --input <目录>`。
  ⚠️ 探针必须先用一个故意超标的样例函数验证"真的会报"，否则等于没验证
  （实测：15 个 `if` 的样例报 `complexity: 16`）。
  实测两处超标都是**给 Compose 主函数加分支**造成的（`CardWalletScreen` 16、
  `UnlockScreen` 15，上限 14）⇒ 修法是**把新增分支收进 holder / 抽成 composable**，
  而不是删注释（见下条实测勘误）。
- **重构后必重跑 detekt**：编译/测试全绿也不会报新违例
- **注释里的「斜杠 + 星号」**：Kotlin 块注释**支持嵌套**，注释文案里出现「星号紧跟斜杠」会
  **提前结束注释**（报一堆 `Expecting a top level declaration`，位置全在同一行 —— 看到这个
  形态先去看注释）。写完注释 5 秒自检 `grep -n '\*/\|\/\*'`。
  **KDoc 里禁止字面 `/**`**（如 `/api/**`），块注释嵌套到 EOF 不闭合，KSP 报误导性连锁错
- **源码编码门禁** `.github/scripts/check-encoding.py`（CI push/PR）：
  判据必须是「**GBK 编码 → UTF-8 解码后全部落在 CJK 区**」；
  朴素的「encode gbk + decode utf-8 成功即乱码」会**大量误报**（「为」「状态」「值」「只」等）
  ⚠️ **2026-09-16 补：这道门禁必须本地先跑一遍**（`python3 .github/scripts/check-encoding.py .`）。
  本轮本地只跑了 detekt + 三个 `.ai/tools/check_*.py` 就推送，CI 立刻红在这一步
  （run `34999960527`）。它是 CI 里的**第四道**门禁，前面的都不覆盖它。
  ⚠️ **改含控制字符的文件要先清掉控制字符**：`BitwardenAuthRepository.kt` 里有两个
  历史遗留的 BEL / ESC（`\x07ccounts` / `\x1bmail`），文件编辑工具据此**把编码猜错**，
  回写时把每个三字节字符的末字节换成 `?` ⇒ **656 处**非法 UTF-8。
  ⇒ 修这类文件：`git checkout <rev> -- <path>` 取回干净版本，
  再用**字节级**脚本（`open(...,'rb')` / `write_bytes`，中文显式 `.encode('utf-8')`）改。
- ⚠️ `git add -A` 会把工作区任何损坏一并提交（曾造成 139 处 U+FFFD 的注释损坏静默入库）；
  用 `git cat-file blob <rev>:<path>` 取**原始字节**比对（**不要**用 `git show > file`，会转码）
- **类型陷阱**：`retrieveProviderCreateCredentialRequest(intent).callingRequest` 是**客户端侧**
  `androidx.credentials.CreateCredentialRequest`，与**服务端侧**
  `androidx.credentials.provider.BeginCreateCredentialRequest` **互不相关**（无继承）；
  `BeginCreatePublicKeyCredentialRequest` **自带** `clientDataHash`
- **Hilt 断环**：`OkHttpClient ↔ Retrofit.Builder` 构造期环 → 注入 `Provider<TokenRefresher>`，
  401 回调时才 `get()`（**懒断环；eager 会死锁**）
- `@Inject` 构造只能含可绑定参数；测试注入口走 `internal` 次构造
- **单测是回归标尺**（数字随轮次涨，**以最新 SESSION 记的为准**）：
  2026-10-27 基线 **131 套 / 1301 例 / 0 失败**（全部 8 个有测试的模块 +
  `:app:testOfflineDebugUnitTest`）+ 全模块 detekt 全绿 + full/offline 两个 flavor 都编译通过。
  报数字时**必须同时给"套数 / 例数 / 失败数"三项**，只报 tests 会掩盖"整套没跑"。
  ⚠️ 统计口径：`app` 有 `offline` / `full` 两个 flavor，`gradlew test` 会**各跑一遍**，
  直接累加 XML 会把 app 的 51 套算两遍 ⇒ 取其中一个 flavor 计数。
  🔴 **2026-10-27 发现历史数字（174/1706、180/1744）口径有误**：当时的统计脚本用了
  `glob('**/build/test-results/**/TEST-*.xml')`，`**` 会匹配到 `composeApp/` 之类的
  **非 Gradle 模块目录**，且 `if 'offline' in f or 'full' in f` 这种字符串包含判断
  把路径里含 `full` 的其他目录也一起保留了下来 ⇒ **数字虚高约 40%**。
  正确做法：**按 `settings.gradle.kts` 里的模块清单逐个取**
  （`app` 取 `testOfflineDebugUnitTest/`，其余取 `testDebugUnitTest/`），不要用通配符。
  当前 8 个有测试的模块：`app` 51 · `core/common` 13 · `core/crypto` 9 · `core/datastore` 3 ·
  `core/model` 1 · `data/bitwarden` 12 · `data/kdbx` 18 · `data/repository` 24（`domain` / `core/database` 无测试）。
- 🔴 **JVM 单测里的 `org.json` 是空壳**（2026-10-26 踩到，代价一整轮调试）：
  AGP 的 `mockable-android.jar` 把 `org.json.JSONObject` 的**每个方法**都替换成"返回默认值"
  （`has` → `ireturn 0`、`getJSONObject` → `aconst_null`、`isNull` → `ireturn 0`），
  **连 `JSONObject(String)` 构造器都是空实现**。⇒ 任何"解析 JSON"的被测代码在单测里
  只会走解析失败分支；更危险的是"恒返回默认值"会让**本该失败的用例通过**。
  - 定位：`javap -c -p -classpath <android.jar> org.json.JSONObject`，方法体只有
    `iconst_0; ireturn` 就是空壳；
  - 修法：`testRuntimeOnly(libs.org.json)`（app 模块已加）。测试 fork 的 classpath 里
    **测试运行时依赖排在 mockable jar 之前**，真实实现胜出；
  - 守卫：`app` 模块的 `UnitTestEnvironmentTest` 断言这一点，依赖被删时它先红。
  - ⚠️ 连带教训：环境可疑时**先修环境，再写业务代码**。本项目一度用"子对象再序列化再解析"
    绕这层，结果把显式 `null` 变成字面量 `"null"`，把环境问题变成了业务 bug。
- **新增入口先画一遍「从冷启动到该入口」的可达路径**：KDBX 添加入口曾挂在
  `VaultListRoute` 后面，而该路由在「已有 ≥1 个库」时**不可达**（根导航落在解锁页 / 主界面）
  ⇒ 集成交付了却用不到（`ISSUES.md` #69）。功能挂在不可达路由后面，测试通过也没意义。
- **全局形状杠杆**：`MaterialTheme.shapes.extraSmall` 是 M3 `OutlinedTextField` 的默认圆角
  （基线只有 4dp）⇒ 改这一处 = 全 App 输入框一次性变圆，比逐个字段加 `shape` 稳妥
- ⚠️ **`Spacing.x` 比 `16.dp` 长 ⇒ 批量替换会撞 `MaxLineLength(120)`**：
  2026-09-15 用脚本替换 369 处标尺值后，两行 `PaddingValues(...)` / `Modifier.padding(...)`
  从 118/120 涨到 121/123 而变红。替换类改动**必须**在跑完 detekt 后单独确认行长——
  这类问题不会在本地"看着像没问题"时被发现（值明明没变）。
- **detekt 行数门禁会随改动"涨"到临界**：主 composable 贴着 `LongMethod ≤150` 时，
  加几行就红。拆法：把「与主流程无耦合的一段」抽成独立 composable / 私有函数
  （本轮抽了 `rememberItemsTopInset` / `SearchBackHandler` / `TotpPageProgress`）；
  文件里**唯一的类形声明**必须与文件名同名（`MatchingDeclarationName`）——
  枚举与 composable 同文件时会被判违规，需拆文件（`BadgeTone.kt`）

  > ⚠️ **2026-09-15 实测勘误：上面说的"加几行就红"指的是加【代码】行。**
  > `LongMethod` **不计注释行与空行** —— 探针实验：函数体 45 行 `println` + 45 行 `//` 注释
  > + 6 行 KDoc（肉眼约 96 行），detekt 报的却是 **47**（= 45 代码 + `fun` 行 + 结束 `}`）。
  > 阈值设 150 不报、设 40 才报，与"只数代码行"完全吻合。
  > ⇒ 两条推论：①**写详细注释不会吃掉行数额度**，别为了省行数把注释写短；
  > ②反过来，**精简注释救不了超长函数**（本轮试过：删 3 行注释，151 仍是 151），
  > 只能抽代码。⇒ 项目里多处「为了守 ≤150 才拆出去」的注释是对的，
  > 但"注释占额度"这个隐含理由**不成立**，真实理由只是代码本身长。
- ⚠️ **抽 composable 时不能凭记忆写参数类型**：2026-09-15 把 `ItemsScreen` 一大段抽成
  `ItemsBody`，签名里我按记忆写了 `ItemGroup` / `ItemsDisplayMode` ——
  **这两个类型在本仓库根本不存在**（真名是 `ItemsGroup` / `ItemsCardDisplayMode`），
  同包内所以"不需要 import" ⇒ 直到 CI 编译才炸（detekt 不做类型检查，本地全绿）。
  **正确做法**：照抄原调用点的实参类型，或直接 `grep` 类型定义确认。
  **自检脚本**（改完抽函数就跑）：扫 `app/src/main/java` 全部顶层类型定义建集合，
  再校验新签名里每个类型名「有定义 或 有 import 或 在 kotlin/java 默认包」——
  这类错误本可本地一次揪出。
- 🔴 **新写的 `Modifier.xxx(...)` 扩展必须立刻确认 import 存在**（2026-10-04 又踩一次，
  代价一次 CI 往返）：本轮给 `DialogActions` 加 `Spacer(Modifier.weight(1f))` +
  `Spacer(Modifier.width(Spacing.sm))`，`weight` 已在 import 里、**`width` 没有**
  ⇒ CI `37201428105` 在 `:app:compileFullDebugKotlin` 报
  `Unresolved reference 'width'`（`QuickUnlockDialogs.kt:470`）。
  **detekt 对此完全无感**（它不做类型/引用解析）⇒ 本地 detekt 绿得毫无帮助。
  ⇒ **纪律：每写一个第一次在本文件出现的 `Modifier.<扩展>`，
  立刻 `grep -n 'import androidx.compose.foundation.layout.<扩展>$'` 核一遍**，
  比等 CI 快两个数量级。同类高危符号：`weight` / `width` / `height` / `background` /
  `clip` / `clickable` / `combinedClickable` / `imePadding`。
- ⚠️ **判断 CI 结果必须看 `conclusion`，不能看管道退出码**：
  后台跑 `gh run watch ... | grep ...; echo $?` 拿到的是**管道最后一环（grep）的退出码**，
  不是 `gh run watch` 的 ⇒ 上一轮我据此**误报过"CI 通过"**，实际 run 是 failed。
  ⚠️ **`--exit-status` 也救不了你**：`gh run watch --exit-status | grep …; echo $?`
  里 `$?` 仍是 `grep` 的。**唯一可靠做法**：
  `gh run view <id> --json conclusion,status --jq '"\(.conclusion) \(.status)"'`。
  **唯一可信判据**：`gh run view <id> --json conclusion`。
- **CI 日志下载会被沙箱网络挡住**（`gh api .../logs` 返回 blob 存储直链，沙箱不可达）：
  改用 **check-run annotations** API 能直接拿到**编译器报错文本**（文件:行:列 + 消息），
  这是沙箱里定位编译错误的**最省事路径**：
  `gh api repos/<o>/<r>/commits/<sha>/check-runs` → 取 `id` →
  `gh api repos/<o>/<r>/check-runs/<id>/annotations`。
  另：`gh run view --json jobs --jq '.jobs[0].id'` 可能返回 null（jobs 未展开），
  用 `gh api repos/<o>/<r>/actions/runs/<id>/jobs` 取 job id 更稳。
- ⚠️ **「另一个文件有同名 import」≠「这个文件也有」**（2026-09-15，CI `34965536847`）：
  给 `UnlockOptionRow` 加图标槽时用了 `CompositionLocalProvider` / `LocalContentColor`，
  **只写用法、没补导入**，`SettingsScreen.kt` 一直到 CI 编译才报
  `Unresolved reference`。三个自检脚本**全放过了它**，因为：
  `check_signature_types` 只看**签名**里的类型名（用法在函数体里）；
  `check_import_packages` 只校验**已写出的 import 行**对不对 ——
  **「漏写的 import」它结构上看不见**（这是它的固有边界，不是 bug）；
  `check_experimental_optin` 只管注解作用域。
  **我核对时错在哪**：去看的是 `DialogShell.kt`（那个文件两个 import 都在）⇒
  把「同族文件有」当成了「本文件有」。
  **纪律**：核对导入**必须在本文件内**把「用法」与「import」做差集，别拿别的文件当参照。
  一行即可：
  ```bash
  # 在本文件里找"用了但没导入"的候选（按需替换符号名）
  grep -o 'CompositionLocalProvider\|LocalContentColor' <file> | sort -u   # 用法
  grep -c 'import androidx.compose.runtime.CompositionLocalProvider' <file> # import
  ```
  **另**：此类「一行未解析」会**连带**报出
  `@Composable invocations can only happen from the context of a @Composable function`
  （外层符号没解析 ⇒ 其尾随 lambda 不再算 @Composable 作用域）
  ⇒ **看到多行报错先找"第一行未解析"，别当多个问题修。**
- ⚠️ **2026-09-16：上面那条「漏 import」第二轮又犯了**（`Icons.Filled.Tune`），
  并新增一类 **「顶层常量前向引用」**：`SETTINGS_DIVIDER_INSET = PADDING_H + ICON_BOX + ICON_GAP`
  写在了 `SETTINGS_ICON_BOX` **声明之前** ⇒ `Variable 'SETTINGS_ICON_BOX' must be initialized`
  （顶层属性**按声明顺序**初始化；报的不是"未定义"，名字明明存在，所以极难自查）。
  两者都是 **detekt 不查 + 本地没有编译器** ⇒ 只在 CI `compileFullDebugKotlin` 炸
  （run `35000941371`，一次 CI 约 4 分钟）。
  ⇒ **已固化为脚本** `.ai/tools/check_compile_smells.py`（三条规则：图标引用/导入差集、
  顶层常量初始化前向引用、`R.string.*` 悬空），**推送前跑一遍**（默认全扫 161 个 .kt）。
  ⚠️ 写它时踩的坑：初始化器范围**不能**取到"下一个顶层声明"——那中间夹的是**函数体**，
  函数体内引用后声明的常量完全合法（调用在运行时）⇒ 首版误报 16 处（`UnlockScreen`
  的 PIN_* 背了 6 处）。正确取法：声明行 `=` 之后 + 紧随的**缩进续行**，遇空行/顶格即止；
  初始化器含 `{`（lambda，延迟求值）时跳过。修正后全仓 **0 误报**。
  ⇒ **纪律：同一类坑犯第二次 = 该有脚本了，别再靠手工 grep。**

- 🔴 **`TooManyFunctions`（单类 ≤40）是"该抽类了"的信号，不是"该压注释"的信号**（2026-09-16 九改）。
  本轮加完「一个 PIN 打开多个库」后，`VaultRepositoryImpl` 与 `SettingsViewModel`
  **同时**到 43（上限 40）。路径：

  | 抽出的类 | 从哪抽 | 抽出去的是什么 |
  | --- | --- | --- |
  | `PinEnrollmentCoordinator` | `VaultRepositoryImpl` | **编排**：给哪些库设、缺主密码怎么报 |
  | `PinEnrollment` | `VaultRepositoryImpl` | **落盘动作**：包什么明文进信封 |
  | `PinSettingsController` | `SettingsViewModel` | **交互**：勾选 / 输 PIN / 输主密码 / 结果汇报 |

  ⚠️ **踩坑：抽类对"函数数"的减益比预期小。**
  `VaultRepositoryImpl` 抽完两个类后仍是 **42**（只减 1）—— 因为它拥有
  **33 个 interface override**：抽走的私有辅助函数会以"更薄的 override"回来，
  真正减少的只有删除的私有函数数。**58 行注释也让函数数量级判断失真。**
