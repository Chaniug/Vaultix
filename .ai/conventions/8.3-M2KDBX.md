### 8.3 M2 KDBX
- **引擎选型定案**：直接用 **`app.keemobile:kotpass:0.13.0`**（Maven Central，**MIT**，
  纯 Kotlin/JVM，唯一传递依赖 okio）。**不搬 Keyguard**：其本体 `All Rights Reserved`；
  其 `util/kdbx/` 只是 vendored kotpass 且被改过（换成 Keyguard 自己的 crypto）；GPL 兼容性有问题
- **KDBX 与 Bitwarden 是两套会话模型**（第 4 批全部复杂度来源）：

  | | Bitwarden | KDBX |
  |---|---|---|
  | 内存会话 | 一把对称密钥（`VaultSessionManager`） | **整库明文**（`data:kdbx` 会话） |
  | 条目存储 | Room `ciphers`（密文） | **只在内存**（不写 ciphers 表） |
  | 解锁 | 联网 + 可能 2FA | 离线（文件 + 主密码 + 可选 keyfile） |

- **门面** `io.vaultix.data.kdbx.Kdbx`（`unlock / contentOf / isUnlocked / unlockedIds /
  lock / lockAll`）+ `KdbxSource`（`(uri) -> ByteArray?`，由 `data:repository` 用 `ContentResolver` 实现）。
  `KdbxSession / KdbxOpener / KdbxSessionStore` **永远保持 `internal`** —— 它们握着 kotpass 的
  `KeePassDatabase`（明文整库），绝不能进跨模块签名（一次 `println` 就可能把明文写进日志）
- **读路径分流**在 `ItemRepositoryImpl.observeItems / observeTrash / observeItem`，UI 与
  自动填充侧零改动。⚠️ 库种类是**挂起**查询（`vaultDao.get`）⇒ 必须放 `flatMapLatest`，
  不能写在方法体里
- **会话变化通知** = `KdbxSessionFlow`（**只带一个代次计数**）。任何改变会话集合的动作
  （解锁 / 锁定 / 移除 / 退出数据库 / 切库）都要 `bump()`，**漏一处就「解锁了但列表还是空」**。
  给明文会话挂 `MutableStateFlow` 是**反模式**
- **切库即锁旧库**在 `ItemsViewModel.init`（`lockOtherKdbxVaults`）：KDBX 那把「密钥」是整库明文，
  多库同时解锁会让「同时只能进一个库」的内存约束失效。
  ⚠️ **2026-11-10 起是「60 秒宽限期」而不是立刻锁**（`KdbxGraceLocks`，#265）：
  切走立刻锁会让「来回对比两个库」反复付一次 `stat` 往返 + Argon2 + 整库解析。
  宽限期内切回免解锁，超时必锁，**手动锁 / 退出 / 删库仍立即生效**。
  **宽限期只属于前台**：`AutoLockController.onStop` 会调 `flushPendingKdbxLocks()`
  把排期当场执行（后台没有"秒切回去"的场景，只剩多留 60 秒整库明文）。
  不要改回立刻锁，也不要改成不锁（后者会让约束消失）
- **keyfile 只存 URI**（`VaultixPreferences.kdbxKeyFileUri`），内容现读；
  UI 必须 `takePersistableUriPermission`（否则「今天能解锁、明天说读不到文件」）
- **失败必须分类**：`SourceUnavailable`（读不到文件）≠ `InvalidCredentials`（密码错）——
  一律报「密码错误」会让人反复重输正确的密码
- **两个 codec**（`KdbxTotpCodec` / `KdbxPasskeyCodec`）都提供 `isXxxFieldName`，
  `customFieldsOf` 用它排除专属字段 —— 否则详情页会把**私钥 PEM / TOTP 密钥**当
  「隐藏自定义字段」展示。最易错两点：位置式 `TOTP Settings` 按**出现顺序**填；
  `TimeOtp-Secret-Hex|Base64` 必须**真解码再转 base32**（当 base32 解析会**静默算错码**）
- **阶段 B（写回）已于 2026-09 起落地**（本行原写「未做」，2026-10-02 更正）：
  **插件字段（`KPEX_*`）与不认识的自定义字段一律原样保留**
  （丢一个 = 用户通行密钥失效）；写回走**整体重建 + 原子替换**（先写临时文件再 rename）+
  `.kdbx.bak` 备份；往返测试**逐字段相等**。目标格式 **KDBX 4.1**。
  ⚠️ SAF 路径**拿不到兄弟文件写权限** ⇒ `.kdbx.bak` 只在 `File` 路径成立，
  SAF 侧靠「写后读回」兜底（见 `SafKdbxFileSource` KDoc）。
  2026-10-02 起主写路径还多一道**写回自检**：`Kdbx.verifyWrite` 只解码不重编码
  （见 01 篇 #158）
- 写回钩子已就位：`Kdbx.save(vaultId, target)`（`Kdbx.kt:541`）+ `saveVia`（`:653`）；
  `KdbxSessionStore` 已持 `KeePassDatabase`；
  `KdbxMappedContent.groupPaths`（uuid → 路径）就是为写回预留的
- KDBX 快速解锁（KEK 包裹，免每次输主密码）与 KDBX 回收站映射**均已落地**
  （本行原写「未做」，2026-10-02 更正）：
  快速解锁见 `LocalUnlockEnrollment.kt` + `VaultixPreferences.kdbxKeyFileUri`；
  回收站见 `ItemRepositoryImpl.kdbxTrash`（`6397de1`，S5 —— 原先只 `recycleBinCount` 计数、
  `observeTrash` 对 KDBX 返回空列表的占位已撤）
- **标准键铁律（R1–R3，2026-10-16 W5 补录）**：`KdbxFieldKeys.kt` 的
  `KdbxFieldKeys.STANDARD`（`Title`/`UserName`/`Password`/`Url`/`Notes`）
  是**全库唯一真源** —— 判「是不是标准键」只许用它，**不许再抄一份集合**，
  更不许在调用点写裸字符串字面量（历史事故：写 `"URL"` 读不出 `url`、
  自定义字段 `Title` 直接覆盖库名）。三条推论：R1 标准键**大小写折叠后**
  不可被自定义字段覆盖；R2 工具字段一律 `VPX_` 前缀（保可逆，读侧靠前缀
  与用户字段分区）；R3 外来（第三方工具写的）字段**原样保留**，
  丢一个 = 用户数据丢失

## 2026-11-09 增补：写回链路的四条硬判据（0.11.3 批次定稿）

这一批不是新功能，是把「改了却传不上去」这条链修通。四条判据都不许回退：

### ① 写前闸门必须**在 mutate 之前**，不能长在 persist 里

`mutateLocked` 会先把新会话换进内存，`persist` 才落盘。闸门如果只在 `persist` 里判，
拒写时就是"内存已删、磁盘没动" ⇒ 列表 / 详情 / 回收站读到**三份不同的真相**。
⇒ 判据要能**只读地取**（`Kdbx.baselineStateOf()`：`known` / `aligned` / 内容指纹），
九个写动作入口统一 `assertWritable()`；`persist` 用 `finally` **无条件** bump。

### ② `!aligned` 的两种成因必须分开，否则必然死锁

| 成因 | 处理 |
|---|---|
| 远端真变过（`REMOTE_CHANGED` / `CONFLICT`） | 拒写，抛 `StaleBaseline` |
| 本机连续编辑、基线没跟着推进 | `rebaseBaselineOnSession()` 就地重对齐后放行 |

一律当"远端变过"的后果是：「保存被拦 → 点同步判两边都没变 → 仍被拦」成环，
状态还被洗成绿色 `IN_SYNC`，只能靠锁库 / 冷启动清内存基线解开。
⚠️ **远端是否变过最终由条件写兜底**（`If-Match` → 412 → `CONFLICT`），
内容指纹只是辅助判据，**不是唯一防线** —— 放宽它不等于放松安全。

### ③ 落盘失败必须**回滚会话**，且失败路径不许静默

真机症状「删除后搜索看得到、点不开、回收站有、XC 没删」= 内存与磁盘不一致。
⇒ `KdbxSessionStore` 按令牌留旧会话快照（每库只留最新一个，锁库即清），
`persist` 成功 `commitMutation` / 失败 `rollbackMutation`；
`try` 要包住整个函数体（否则 `finally` 的 bump 不执行，列表停在旧快照）；
`mutate` 的 `applied=false` 与 `persist` 异常都必须打日志，
否则下次只能靠猜区分「目标不存在」与「自检失败 / 落盘 IO 失败」。

### ④ 网络失败要自己重试，但**冲突不许重试**

- `KdbxAutoUploader`：`Failed` 按 **3s → 8s → 20s** 退避，最多 3 次；
  一次 `enqueue` 最多 6 轮（正常 1 轮收敛，额外轮次服务"上传期间又改了一笔"）。
- `Conflict` / `StaleBaseline` / `NeedsReload` / `NoCloudSource` **一次收工** ——
  这些需要用户决策，重试解决不了，重试只会把状态搅浑。

### ⑤ 读路径不要挂在 KDF 车道上

`kdbxItems` / `kdbxTrash` 曾误挂 `@CryptoDispatcher`（`limitedParallelism(2)` 的 KDF 车道），
写回一占用、读就排队 ⇒ 真机「点删除等 1–2 秒」。纯内存读必须用 `Dispatchers.Default`，
并且**会话在 `mutateLocked` 里提交时就推 UI**，不要等 `persist` 末尾的 bump。
