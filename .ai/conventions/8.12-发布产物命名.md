# 8.12 发布产物命名（2026-11-14）

> 用户原话拍板：「`Vaultix-v0.13.1-dev-fcb77f9-preview.apk` 最终生成包的名字偏长了，
> release 名字也偏长了吧，你看看如何优化。**以后这种名字短一点，简洁一点**。」
>
> 这是**长期约定**，不是一次改名。形状由
> [`../tools/check_release_naming.py`](../tools/check_release_naming.py) 钉住，
> 自测见 [`../tools/tests/selftest_release_naming.py`](../tools/tests/selftest_release_naming.py)，
> 施工记录见 [`../issues/01-构建与环境-part15.md`](../issues/01-构建与环境-part15.md)（#292）。
> 分篇规则见 [`8.9-文档分篇.md`](./8.9-文档分篇.md)。

## 0 一句话结论

**身份由 Release 页承载，APK 文件名只留「产品名 + 可对应的提交」。**
短，不等于把身份信息删掉 —— 删掉的版本号与 SHA 必须能在页面上原样查到。

## 1 现象

| 项 | 改前 | 字符数 |
|---|---|---|
| preview APK | `Vaultix-v0.13.1-dev-fcb77f9-preview.apk` | 39 |
| preview Release 标题 | `Vaultix v0.13.1-dev-fcb77f9 · Preview` | 37 |

APK 名把**版本 + `dev` + 短 SHA + 渠道**四段全堆在一起，而版本与 SHA 在
Release 标题、正文表里已经各写了一遍。下载列表里长到要横向滚动。

## 2 约束：短不能突破 #218 的身份硬约束

> 判据原文（[`../issues/01-构建与环境-part11.md`](../issues/01-构建与环境-part11.md) #218）：
> **「能被用户验证的，才叫『发布物的身份』—— 只写 SHA 等于没写身份」**。

这条是同一位用户 2026-11-01 拍的板，起因正是当时标题只有一长串 SHA
（`Development Preview (dev-341be3a58fb…)`），在 Releases 列表里被截断、
看不出是哪个版本。所以：

- **Release 标题里的「版本 + 7 位短 SHA」一个字都不能砍**，也不许把 `-` 换回 `+`
  （`+` 在语义化版本里是 build metadata，不参与版本比较）。
- **APK 名不能叫 `Vaultix-preview.apk`**：没有提交标识，多个预览包下载到本机
  会互相覆盖，用户也无从把手里那个包对应回某次构建 —— 等于把 #218 刚补上的
  身份又丢了。7 位 SHA 是短名与可验证之间唯一的连接点。
- **`-preview` 后缀是纯冗余**：tag 就叫 `preview`、Release 有 prerelease 徽标、
  标题带 `· Preview`，三处已经说清渠道。
- **`Vaultix ` 前缀在标题里冗余**：Release 页面本身在 Vaultix 仓库下，面包屑
  已经有产品名；但 APK 文件名要保留产品名（脱离页面后仍要认得出是什么）。

⇒ 可删的是**重复**，不是**身份**。这也是「短」与「能自查」两头都保住的切分。

## 3 约定形状（唯一真源）

| 产物 | 模板 | 最坏渲染 | 长度 |
|---|---|---|---|
| preview APK | `Vaultix-${short_sha}.apk` | `Vaultix-fcb77f9.apk` | 18 |
| preview Release 标题 | `v${{ …version_name }} · Preview` | `v0.13.1-dev-fcb77f9 · Preview` | 29 |
| stable APK | `Vaultix-v${{ …version }}.apk` | `Vaultix-v0.13.1.apk` | 17 |
| stable Release 标题 | `Vaultix v${{ …version }}` | `Vaultix v0.13.1` | 15 |

**稳定侧不动**：`Vaultix-v0.13.1.apk` / `Vaultix v0.13.1` 本就够短，版本号是稳定版
唯一身份，没有 `dev` / SHA / 渠道后缀可删。别为了「两边统一」把它改长，也别为了
更短去掉产品名（`v0.13.1` 会和 tag 混淆）。

落地文件：

| 位置 | 作用 |
|---|---|
| `.github/workflows/ci-debug.yml` → `Collect debug APK metadata` | preview APK 改名（`short_sha` 有落盘 + `GITHUB_SHA` 双重兜底） |
| `.github/workflows/ci-debug.yml` → `Publish Debug APK to preview Release` | preview 标题、正文身份表 |
| `.github/workflows/release.yml` → `Collect APK + SHA-256` / `Publish Stable Release` | stable 两个模板（保持原样） |

### 3.1 机器可校验的三条不变量

1. **一个模板只带一个变量** —— 从结构上挡住「版本 + SHA + 渠道」重新堆叠。
2. **渲染长度预算**：APK ≤ 24 字符、Release 标题 ≤ 34 字符（按最坏版本样本估）。
3. **找不到被检查的步骤 / 改名语句一律报红** —— 静默放过等于门禁失效
   （#218.7：改了门禁却没触发 CI，给的是**假绿灯**，比没有门禁更贵）。

门禁必须挂在 **`ci-debug.yml` 的 `android-ci` job**：它的 `paths` 含
`.github/workflows/**` 与 `.ai/tools/**`，改命名或改门禁都会触发；
`ci-docs.yml` 的 `paths` 不含前者，挂那边会出现「改了 workflow 却没跑检查」。

## 4 验证

- `python3 .ai/tools/check_release_naming.py .` —— 4 个模板 + 变量数 + 长度 + #218 身份。
- `python3 .ai/tools/tests/selftest_release_naming.py .` —— 拿**真实 workflow** 做
  11 组变异（长名 / 无 SHA / 无版本 / 删提交行 / 步骤改名 / 缺文件…），逐组判红判绿。
  每个变异都断言「原文里确实有这个子串」，替换失效即自检失败 —— 不给假绿留口子。
- 施工当轮先在**长名**上跑门禁拿到 rc=1（5 条违规），改完再跑转绿；这一步本身就是
  第一轮变异反证。

## 5 边界：什么不算「改短」

- 版本号升到 `0.14.0`、提交 SHA 变了 —— 模板不变，门禁不应红。
- 新增 flavor / 构建渠道 —— 先回来改本篇，再改门禁与自测；**不要给门禁加白名单**。
  门禁红的意思是「形状变了，需要重新拍板」，不是「检查器太严」。
- `Upload APK` artifact 内仍是 Gradle 原名（`debug-apk`，3 天保留期的内部产物），
  不是给用户下载的东西，不纳入本约定。
