## 三条可复用的一般化教训

1. **判据正确 ≠ 门禁有效。** 门禁还得**真的扫到**那些文件。
   写/改门禁时先问：**"它扫的是不是全部？报数对不对得上？"**
   （164 vs 293 就是一眼能看出的信号 —— **验收时看数字，不只看 OK**。）

2. **当心"自证伪"的门禁。** 若门禁的参照系是从**被检查的语料本身**统计出来的，
   那么**制造错误会污染参照系**，使其恰好查不出这个错误。
   凡是"用仓库当基准"的统计型判据，都要问一句：
   **"我把错写进去之后，它还能报出来吗？"**

3. **统计型判据必有例外，例外要显式登记。** 多数派不是真理：
   同名不同包有时**两边都对**。用"另一个包是否根本不导出该符号"来区分，
   合法的一律进豁免表并写清理由 —— **不要为了压误报而放宽判据**
   （那样会把 ① 的漏报重新引回来）。

## 对应新增的自测

| 文件 | 覆盖 |
|---|---|
| `.ai/tools/tests/selftest_duplicate_declarations.py` | 7 用例：真重复必报 / 合法重载 / 扩展函数同接收者 / 不同接收者 / 跨接口同名 不报 |
| `.ai/tools/tests/selftest_import_packages.py` | **端到端**：真的把 import 改错、跑脚本、看退出码，再还原 |

⚠️ 第二个必须是端到端：坏法 ① 与 ② **都测不出来单元测试** ——
① 是"函数从没被喂到那个输入"，② 是"喂到之前输入已被错误本身污染"。
**只有在真实仓库里制造那个错误，才能证明门禁拦得住它。**

## 🔴 一个缺失的 import 可以制造一大片「看似无关」的类型错误（2026-09-16）

`UnlockViewModel.kt` 里 CI 一次报了 **7 行**错，长这样：

```
e: UnlockViewModel.kt:441:13  Cannot infer type for type parameter 'R'.
e: UnlockViewModel.kt:441:25  Cannot infer type for type parameter 'R'.
e: UnlockViewModel.kt:442:49  Unresolved reference 'first'.
e: UnlockViewModel.kt:443:22  Cannot infer type for type parameter 'T'.
e: UnlockViewModel.kt:443:29  Cannot infer type for type parameter 'T'.
e: UnlockViewModel.kt:443:34  Unresolved reference 'id'.
e: UnlockViewModel.kt:443:54  Unresolved reference 'unlocked'.
```

看着像"这条链到处都写错了"，**实际只要补一行**
`import kotlinx.coroutines.flow.first`。

机制：`observeVaults().first()` 解析不了 ⇒ 表达式类型变成"未解析"
⇒ `filter{}` 的 lambda 参数类型无从推断 ⇒ `it.id` / `it.unlocked` 全 unresolved
⇒ 编译器对每一步再报一次 `Cannot infer type`。**一个根因，七行症状。**

### 为什么特别难发现

该文件**已经**导入了：

```kotlin
import kotlinx.coroutines.flow.distinctUntilChanged
import kotlinx.coroutines.flow.filter
import kotlinx.coroutines.flow.map          // ← 挨着，很像"都导了"
import kotlinx.coroutines.flow.receiveAsFlow
import kotlinx.coroutines.flow.update
```

一眼扫过去"flow 操作符都导齐了"。**独独缺 `first`**，
而它恰恰是链头第一个被调用的。

### 规矩

> **看到"同一个文件里多行 unresolved + `Cannot infer type`"，
> 先去看 import，不要动逻辑。**
> 语法正确的代码不会平白冒出一堆类型推断错误 ——
> 那种"雪崩式"报错几乎总有一个**上游的解析失败**。

⚠️ 反之也要注意：**别把 7 行当成 7 个 bug 去逐个修** ——
那会改出真 bug 来。**先找那个共同的根。**

## 🔴 写正则解析函数名时，别忘了「可选接收者」——我犯了第二次（2026-09-16）

同一个错误，一天内犯了**两次**，两次都是探针误报：

| # | 探针 | 写错的地方 | 后果 |
|---|---|---|---|
| 1 | `check_duplicate_declarations` | `fun\s+(\w+)` 把 `fun JsonElement?.asObject()` 的**接收者**当成函数名 | **5 处误报** |
| 2 | `check_cross_file_private` | `private\s+...fun\s+(\w+)` 把 `private fun Entry.toVaultItem()` 的**接收者**当成函数名 | **103 处误报** |

两次的机制**完全相同**：Kotlin 扩展函数的写法是
`fun <接收者>.<函数名>(...)` —— 紧跟 `fun` 的那个标识符是**接收者**，不是函数名。

**正确的正则形态**（两个探针现在都用这个）：

```python
r"fun\s+"
r"(?:<[^>]*>\s*)?"                                  # 泛型参数 fun <T> f()
r"(?:[A-Za-z_][\w.]*(?:<[^<>]*>)?\??\s*\.\s*)?"      # 可选接收者 Intent. / JsonElement?.
r"(\w+)"                                            # ← 第 1 组才是函数名
```

> **教训**：**写正则之前先想清楚"我要抓的那个 token，它前面可能有什么"。**
> 而且，**同一个坑犯第二次说明上次只修了现场、没提炼成规则。**
> 所以这条才写进 conventions，而不是留在 session 里。

⚠️ 还有一条：**接收者必须进"重复判定"的 key**
（`fun Intent.foo(x)` 与 `fun Bundle.foo(x)` 是两个签名），
但**不能**让接收者被当成函数名 —— 这两件事都要做对。

## 🔴 「状态变量只写不读」是本项目第三次让本地门禁全绿的事故（2026-09-30）

真机实录（我自己引入的）：给设置首页加回「自动锁定」行时，

```kotlin
var showAutoLockDialog by rememberSaveable { mutableStateOf(false) }   // 声明 ✅
...
onAutoLock = { showAutoLockDialog = true },                            // 写入 ✅
// ❌ 漏了 if (showAutoLockDialog) { AutoLockDialog(...) }
```

症状：**点那一行毫无反应**（用户原话「自动锁定选项不能选取」）。

### 为什么当时**五道门禁全都没拦住**

| 门禁 | 为什么看不见 |
|---|---|
| Kotlin 编译器 | **`by` 委托的局部变量不触发 "variable is never used"** —— 实测 `--rerun-tasks` 全量重编**零条 warning**（`by` 生成的 getter 不被"未使用"检查覆盖） |
| detekt | unused 规则面向 private 属性 / 参数，不解析局部委托变量 |
| 增量编译 | 无输出；任务 UP-TO-DATE 也照样"绿" |
| `check_orphan_strings` | 那些字符串（`setting_auto_lock` 等）**在别处仍被引用** ⇒ 不是孤儿 |
| 单测 | 本项目没有 Compose UI 测试 |

### 新增第 5 类门禁：`check_orphan_state.py`

判据：**标识符是否只出现在"声明"与"赋值左侧"**（去掉声明与写入后，一次读取都不剩 ⇒ 报）。
覆盖 `var x by remember…` 与 `val x = remember { mutableStateOf(…) }` 两种形态；
阈值是**零容忍**（不存在"合理的不读"，所以不做基线制）。

⚠️ **已知局限（刻意宁可漏报也不误报）**：同名变量在同一文件出现多次时计数**按名字合并**
（两个同名状态里只有一个被读会放过）；只扫 `app/src/main/java`；只判"有没有读"、
判不了"读得对不对"。`--verbose` 会列出计数明细供人核对。

### ★ 写探针的代价（与本文上一节同一条教训，24 小时内又重演一次）

这个探针**自己先坏了三处**，全靠自测与全仓首跑暴露：

| 版本 | 症状 | 怎么坏的 |
|---|---|---|
| 第 1 版 | **一个都匹配不到 ⇒ 静默"全绿"** | 声明正则写成"先匹配 `by remember` 再要求一个 `remember`" —— `by rememberSaveable` 后面当然没有第二个 `remember` |
| 同时 | `AttributeError` 直接抛 | `re.Pattern` 上用 `.format()` 填占位符 |
| 第 2 版 | **全仓 22 处误报** | `val barPadding = remember…` 这种**声明自带的 `=`** 被我又算了一次"赋值" ⇒ `x` + 一处 `x.属性` 就判成"只写不读" |

⇒ 教训与上一节完全相同：**启发式探针必须配正反用例**（`tests/selftest_orphan_state.py`，5 例），
**并且首跑必须核对误报**（"探针报了一个我不可能引入的问题" = 探针坏了，先去核对真实代码，
别急着改源码）。修好后：自测 5/5 过、全仓 **0 命中**、且它**确实**能报出上面那个 bug 的形状。

⚠️ **另一条同族教训**：本地门禁三关跑的是**编译**，而 `by` 委托局部变量的这条缝
**连编译都报不出** —— 所以"三关全绿"不等于"点得动"。UI 交互的连接处
（状态 → 渲染）属于**必须真机/或探针**覆盖的一类，别只用编译背书。

## 🔴🔴 「`failures=0` 不等于全过」—— daemon 崩溃会产出一份**看起来全绿**的报告（2026-10-20 踩）

> 这条与本文开头两条（门禁前置项红 ⇒ 后面一个没跑、探针自证伪）属同一族：
> **检查没跑完，但报告长得像跑完了。**

### 现象

`:app:testFullDebugUnitTest --rerun-tasks` 报 `BUILD FAILED`，而数 `test-results/*.xml`：

```
tests=367  skipped=0  failures=0  errors=0      ← 零失败！
```

只看这三个数的人会得出「测试全过，构建挂了是环境问题」然后放行。
**真实情况：daemon 跑到第 39 个套件时被杀，剩下 3 个套件根本没生成 XML。**

| 信号 | 骗人的读法 | 真实含义 |
|---|---|---|
| `failures=0 errors=0` | 全过 | 只覆盖**已生成 XML 的那部分** |
| 套数 39（应 42） | — | **3 个套件被跳过，且没有任何报错** |
| `BUILD FAILED` | "测试没问题，是环境" | 可能是**测试根本没跑完** |

### 判据：测试门禁必须核**三个数**

```
套数 = 42      tests = 388      failures = 0      ← 三个都对上才叫全绿
```

少核一个「套数」，就会把「没跑到」读成「全过」。这是本项目核数纪律里**唯一**
一个"漏一个数就会得出相反结论"的地方 —— 其它门禁漏一个数只是证据不足，这里漏了是**结论错误**。

### 顺带三条可复用的

1. **`up-to-date` 在 `rm -rf test-results/` 之后仍可能出现**：Gradle 会把结果从
   `build/` 缓存重新复制，任务行是 `1 executed, 1 from cache, 183 up-to-date` ——
   **看起来跑了，其实没跑**。判据永远是「任务行是不是 `executed`」，不是「目录里有没有文件」。
2. **daemon 崩溃 ≠ OOM**：本轮内存 123G / 可用 92G，仍被杀。处置是
   `gradle --stop` 后 `--no-daemon --max-workers=2 --rerun-tasks`，跑完两次对照确认。
3. **偶发失败必须复现一次再定性**。本轮第一次 `BUILD FAILED` 时日志被 `tail` 截掉，
   我当时判为"偶发"就往下走了 —— 这是错的。第二次强制重跑并把输出**落盘到文件**，
   才拿到 `Gradle build daemon disappeared unexpectedly` 这句话。
   ⇒ **"偶发"是结论，不是借口；下结论前先留日志。**
