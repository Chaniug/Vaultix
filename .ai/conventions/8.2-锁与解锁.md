### 8.2 锁与解锁 —— **两层语义，代码里是两条独立路径（勿合并）**

| | 真锁（加密门禁） | 查看锁（界面门禁） |
|---|---|---|
| 入口 | 超时到期 / 冷启动 / 退出数据库 / `lockVault` | 主页锁按钮 → `viewLock` |
| 密钥 | **清零** | **原样留着** |
| 恢复 | 主密码（+2FA）+ 联网 | **一次生物识别**，离线 |
| 载体 | `VaultSessionManager` | `VaultSessionManager.viewLockedIds` |
| 根导航 | `RootNavState.VaultLocked(null)` | `RootNavState.VaultLocked(vaultId)` |

三条不变量（破坏必然出「点了没反应」或「解锁完又要验证」）：
1. `viewLocked` 在 `RootNavViewModel` 判定里**必须排在「已解锁」之前**（查看锁的库在 `unlockedIds` 里）
2. 解锁页自动选库**先看 `isViewLocked`**，再看 `!unlocked`
3. 真锁路径（`lock / lockAll`）要**一并清查看锁标记**，否则标记残留把用户死锁在
   「只需认证、但密钥已不在内存」的页面

成功分支靠**显式参数**区分（`completeLocalUnlock(cipher, forViewLock)`），
**不要**读调用时刻的状态（认证对话框期间可能被别的流改写）。

其他：
- **锁态模型按 Bitwarden 重写**：`VaultTimeout` sealed class（10 档位）+ 后台
  `launch { delay(t); lock() }` / 前台 `cancel` job；CP 侧由 `RootNavViewModel` 集中判据，
  锁定只给 `authenticationActions`；`CredentialProviderActivity` 作 trampoline（`exported=false`）
- ⚠️ **迁移陷阱**：旧 `auto_lock_minutes = -1` = 「**从不**」；新 `VaultTimeout` `-1` =
  `OnAppRestart`「**重启即锁**」—— 语义正好相反，已做一次性迁移 + 标记
- **Android 16+ `Settings.Secure` 对第三方 App 受限** ⇒ 凡读系统设置判状态的检测，
  取向一律「**读不到 = 已启用**」（⚠️ `adb shell settings get` 有值 ≠ App 内读得到）
- **快速解锁四铁律**：① `submitting` 必须由「成功 / 失败 / **任何**弹窗错误」三路复位
  （只处理「用户取消」会整页死锁）；② `UserNotAuthenticatedException` **不是**「密钥已废」，
  不得据此清用户注册；③ **解密路径绝不新建 KEK**（`loadKey()` 只读，只有启用路径
  `obtainOrCreateKey()`）；④ 判 KEK 健康用 `getKey`（三态 `kekStatus`），
  **不要用 `containsAlias`**（失效时静默返回 false）
- 快速解锁模型：账号对称密钥 64B 用 Keystore user-auth KEK（AES-GCM）包裹落盘
  （`local_unlock_key::<vaultId>`），锁库只清内存；指纹增删自动 invalidate KEK → 回退主密码
- **敏感存储未用** `androidx.security.crypto`（1.1.0 已整体废弃），改用
  **Android Keystore + AES-256-GCM**（密钥不可导出、每值随机 IV）

- 🔴 **一个 PIN 打开多个库：必须"设置时一次配齐"，不能"设一次自动通用"**（2026-09-16 九改）。
  ⚠️ **最容易误解的一点：PIN 值相同 ≠ KDBX 免掉主密码。**
  差别不在 PIN，而在**包进信封的东西**：

  | 库类型 | 信封里包什么 | 为什么 |
  | --- | --- | --- |
  | Bitwarden | `buildFullKey(sessions.keyOf(vaultId))` | 对称密钥在**会话里** ⇒ 当场取，无需任何密码 |
  | KDBX | `KdbxUnlockPayload.encode(masterPassword, keyFileBytes)` | 会话里**只有**解密后的数据与派生密钥，**没有原始主密码** |

  ⇒ 想给 KDBX 设 PIN，主密码**早晚要在某个时刻被收集一次**；
    最省事的收法就是"设置 PIN 时一次问清"。
  ⇒ **配齐之后解锁链路一行都不用改**：每个库本来就有自己的信封，输入同一个 PIN 各开各的。

- **安全边界靠"每库独立"，不靠砍功能**（同上）：
  信封按 `vaultId` 分存（密文各不同，各库密钥不同）、**失败计数按 `vaultId` 独立**
  ⇒ 一个库输错锁住**不牵连**其它库；某库在别处重设 PIN 也只影响它自己。
  ⚠️ 别用"只允许可复制的库"这类限制去换安全 —— 那是砍功能，不是边界。

- 🔴 **KDBX 校验必须"只验不开库"**（同上）：`Kdbx.verify(...)` 是 2026-09-16 新增的
  **无副作用**入口（只做「读文件 → 尝试凭据」，**完全不碰 `KdbxSessionStore`**）。
  为什么不能复用 `unlock()`：
  ① 会把明文内容拉进内存（用户没要求，页面也没准备展示）；
  ② 会**覆盖该库可能已存在的会话**（用户可能正开着，却在为另一个库设 PIN）；
  ③ 多库配齐时每个 KDBX 库各开一次，成本与副作用都白付。
  ⚠️ **别把它实现成 `unlock()` 包一层 try** —— 那正是 ② 要避免的副作用泄漏。
  ⚠️ **keyfile 读不出来时拒绝，而不是降级成"仅主密码"**：keyfile 不是可选装饰，
  少它一个字节就是开不了；静默降级会让信封里躺一组永远解不开的凭据，
  用户只会看到"PIN 不对"，无从得知真因。

- **「先校验、后包裹」是 PIN 登记的铁律**（与 `prepareKdbxEnroll` 同源）：
  `PinKeyWrapper.wrap` 只负责封字节、不管字节对不对。先包后校会得到
  「启用成功、但躺的是错密码」，用户要到下次解锁才发现，那时已分不清是 PIN 错还是密码错。
  ⚠️ 但 PIN 路径**可以当场 wrap**（与生物识别不同）：它的保护器不需要系统认证，
  不存在「cipher 还没被授权」的问题（生物识别那侧的 KEK 是 auth-per-use）。

- **`enrollPin` / `enrollPinKdbx` 已从 `VaultRepository` 删除**（2026-09-16）。
  新代码一律走 `enrollPinForVaults(vaultIds, pin, masterPassword)`；单库传一个元素的列表即可。
  ⚠️ `pinCandidateVaultIds()` **返回全部库（含 KDBX）**，不在数据层过滤 ——
  KDBX 并非不可设（只是要多输一次主密码），过滤掉 = 用户以为"KDBX 不支持 PIN" = **假状态**。

- **生物识别快解是「一次认证 → 一把 cipher」**（2026-09-16，诉求 C 转正）。
  保护器 KEK 用 `setUserAuthenticationParameters(0, …)` ⇒ **auth-per-use**：
  只有被 `BiometricPrompt` 授权过的**那一个 `Cipher` 实例**能 `doFinal`。
  这决定了多库场景的**唯一正确顺序**：

  | 顺序 | 结果 |
  |---|---|
  | ❌ 每库各准备一个 cipher、逐个弹指纹 | 第 2 个 cipher 未被授权 ⇒ `UserNotAuthenticatedException`（2026-09-14 闪退同源） |
  | ❌ 先 `wrap` 再弹指纹 | 同上，`doFinal` 抛异常 |
  | ✅ 认证前只**校验 + 备料**，认证后用**同一个** cipher **连续** wrap 完 | 正确，且用户只被问一次 |

  ⚠️ **登记（写信封）与解锁（读信封）的方向不同，别互相套**：

  | 场景 | cipher 来源 | 覆盖多个库的方式 |
  |---|---|---|
  | 登记 | 一次认证（`prepareLocalEnroll`） | **同一个** cipher 连续 wrap |
  | 解锁 | 首个用认证 cipher，其余各自 `prepareLocalUnlock` | 每个库**各取一把**解密 cipher（auth-per-use 下认证窗口内可用） |

  ⚠️ 解锁侧"其余库取不到 cipher"（该库 KEK 也失效）⇒ **跳过该库**，
  绝不能因此回滚首个库 —— 首个库的成功才是用户点指纹的目的。

- **多库备料必须绕开单槽暂存**（2026-09-16）。
  `VaultRepositoryImpl` 原有的 `stagedKdbxPayload` 是**一个 `ByteArray?`，不按库分**；
  多库用它会让后一个库**覆盖**前一个，于是前者的信封里躺着别人的密码，
  用户要到解锁时才发现打不开。⇒ 新建 `LocalUnlockEnrollment`，
  备料列表由调用方（控制器）自己持有，**完全不碰那个槽**。
  （与 `PinEnrollment.enrollKdbx` 绕开暂存槽是同一条纪律。）

- **「一次认证开多库」只有一份实现**：`LocalUnlockFanout`（2026-09-16）。
  在此之前 `UnlockViewModel.completeLocalUnlock` 与 `AutofillActivity.completeLocalUnlockByKind`
  **各写了一份**"按库类型分流"，而那条分流写错**不报错、只静默失效**
  （KDBX 的包裹物走 Bitwarden 那条路会解出完全错误的语义）—— 两份 = 同一个坑埋两次，
  且很可能只修好一处。**`localUnlock` 相关的分流逻辑今后只允许有一个实现。**

- **`localUnlock` 的"其余库"必须过滤成「已启用快解」的锁定库**（2026-09-16）。
  对只走主密码的库调 `prepareLocalUnlock` 必然返回 null（没有信封），
  白跑一趟还会被记成一次"失败"，结果里冒出莫名其妙的"未打开" —— 而用户根本没打算开它们。
  解锁页 `candidateVaultIds()` 与自动填充 `prepareBiometricUnlock()` 用的是同一口径。
