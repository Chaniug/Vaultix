### 8.4 UI / 观感
- **站点图标**：端点 `<服务器>/icons/<域名>/icon.png`（同 Vaultwarden）。三条取舍：
  **剥掉服务器路径**（反代下端点在站点根）、**只收 https**（cleartext 会被静默拦）、
  **保留 `www.`**。⚠️ **域名必须过白名单**（仅字母/数字/`.`/`-`）—— 它会被拼进 URL 路径，
  不设防就能改写请求目标。纯字符串实现放 `core:common/SiteIconUrl`（零 Android/零网络）
- **顶栏**：动作收敛为 **🔍 + ⋮**（低频动作进 overflow）；
  **筛选条必须浮在内容之上**（与顶栏同层 + `matchParentSize()` 透明遮罩）——
  塞进可滚动 `Column` 会随列表滚走而箭头还指着「已展开」；
  **筛选状态刻意不持久化**（落盘会让用户下次对着空列表发呆）；有筛选时标题必须拼
  「**库名 · 筛选名**」（只显示库名，用户会以为数据丢了）
- **让位必须做在滚动内容里**（`LazyColumn.contentPadding` / 可滚动的 `Spacer`），
  **绝不**做外层容器 `padding`：做在外面，内容就永远到不了那片区域 ⇒ 顶栏透明了也不沉浸、
  筛选条压住首条、搜索态「Scaffold 让位 + 外层 padding」双重留白成黑横幅（`ISSUES.md` #67）。
  搜索态还必须自己 `BackHandler` —— 主界面是**根路由**（栈里没有上一层），不拦就退桌面。
- **底栏是叠层悬浮**（不是 `Scaffold(bottomBar)`）：内容铺到屏幕底，各页用 `bottomInset`
  （`rememberBottomDockInset` = 胶囊 86dp + 系统手势条）自己留位。
- **隐藏手势必须有可见反馈**：长按滑删的 armed 态要给 32% 红底 **+ 让出 16dp 缝**
  （只调 alpha 看不见 —— 删除底被不透明卡片完全盖住）。功能存在 ≠ 用户知道它存在（#68）。
- **沉浸式顶栏三个前置条件缺一不可**：Box 叠加 + 列表顶部让位 + 外层 insets 归零
  （少一个就退化成「顶栏变短但内容仍被压着」）
- **Tab 动效规格**（Bastion 移植）：进入 `fadeIn + slideInVertically(1/16 屏高)` 220ms，
  退出 `fadeOut` 120ms，缓动 `CubicBezierEasing(0.6f, 0f, 0.4f, 1f)`；
  配 `AnimatedContent(contentKey = tab)` + `SaveableStateHolder`（**切 Tab 不丢滚动/搜索词**）；
  验证码倒计时用 `rememberTotpSmoothProgress`（秒级数据 + 绘制层 1s 线性动画，翻转 `snap()`）
- **条目卡片**（`ui/common/EntryCard.kt`，照 Bastion `PasswordEntryCard`）：M3 默认 Card +
  **12dp 圆角** + **16dp 内边距** + 标题 SemiBold + 6dp 行距；三个列表（密码/验证码/卡包）统一。
  ⚠️ 「外框」是**组件级卡片样式**，与「壳」（导航/容器/转场）无关
- **搜索输入框绝不能放进 `LargeTopAppBar`**（高度随滚动变化 ⇒ 输入框被反复垫高、焦点漂移）；
  Bitwarden 做法 = 固定高度 `TopAppBar` + 搜索态**整体占据 `title` 槽**（与标题二选一，
  调用方写 `if (searchActive) 搜索顶栏 else 普通顶栏`，**整体替换不叠加**）；
  `searchActive` 用 `rememberSaveable`
- **改点击语义必须补回被挤掉的入口**：整行点击从「编辑」改成「复制」后，编辑入口若不显式补
  一个，条目就再也改不了
- 详情页**不做动态验证码**（降功耗），只提示「含验证码 / 已绑定 N 个通行密钥」
- 同一功能在项目里出现 3 种不同写法 = 高危信号，先统一再修
- **容器色阶：嵌套必须换档，禁止同色叠 alpha**（2026-09-15 快速解锁对话框「毛坯房」的根因）。
  `DialogSurface` 面板底是 `surfaceContainerHigh`，卡片底若也写
  `surfaceContainerHigh.copy(alpha = …)`，**卡片边界会彻底消失**、整屏糊成一片灰。
  ⇒ 卡片/行底一律用 **`surfaceContainerLowest`**（M3 阶梯 `Lowest < Low < Base < High`，
  嵌套内容往**低**走）。**「加了 Card 就算有层级」是错的 —— 必须核对与父容器是否同色。**
- **一个元素只该说一件事**（同上轮）：状态归徽标、身份归标题、补充信息归副标题。
  同一行里出现两个说同一件事的元素（徽标"已启用" + 副标题"已启用"）就会显得廉价 ——
  它暴露的是"没人在做信息归属决策"。判据：**副标题若与徽标/标题语义重复，就删掉它**。
- **动作区两端对齐**：行内只有一个按钮时别让它孤零零贴左（`RowScope.ActionSpacer()`
  = `weight(1f)` 占位推右）；有两个（如「关闭 / 修改」）时一左一右，主次立现。
- **分组维度选「实体」不选「属性」**（2026-09-15 快速解锁对话框合并的判据）：
  「按手段分组」（指纹段列全部库 → PIN 段再列全部库）会让**同一个实体名反复出现**，
  用户读到第二个时必须回头确认"这是同一个吗"，且跨段操作要滚动来回找。
  ⇒ 改成**按实体分组**（一库一卡，卡内按手段分行）。
  适用条件：实体数量 ≤ 属性数量时收益最明显（库里 2 个、手段 2 个 ⇒ 卡数 = 库数）。
  ⚠️ 合并的是**分组维度**，不是把并列项合成一个开关 ——
  同一卡内各行的**独立状态徽标**必须保留。
- **设置类列表：一组一张卡，不是一行一张卡**（2026-09-16）。
  上游 Bastion 的 `SettingsItem` 是**每行各自一张 Card** —— 18 行 = 18 张漂浮的小药丸，
  页面被切成一堆碎片，**读不出"这几行是一组"**。改为 `SettingsGroupCard { … }`
  （一组一张 `surfaceContainerLow`）+ 行间 `SettingsDivider()`（起点缩进到文字左边缘）。
  ⚠️ 连带两条：`SettingsRow` **不再自带卡片外壳**（降级为纯行）；
  `clickable` 必须排在 `padding` **之前**（否则水波纹只覆盖内边距以内那一小块，
  改成整组卡片后"只有中间能点"会特别明显）。
- **「上游有」不等于「该抄」**：搬运前先判定**边界**。本轮搬 Bastion「检查更新」时
  **刻意没搬**它的「下载 APK + 校验签名 + 拉起安装」：预览包每次覆盖同一附件名
  （版本无从在文件名体现），且对**密码管理器**来说"自动安装"是比"多两步"重得多的风险面。
  ⇒ 只回答「有没有新构建」+ 给发布页链接。**搬运清单必须写明"没搬什么、为什么"**。
- **一屏里出现两套规格 = 观感廉价的首要来源**（2026-09-16 详情页）：
  9 张分区卡片 `surfaceContainerHigh` 与 `surfaceContainerLow` **混用**、
  两套字段行布局并存、部分分区有标题部分没有 —— 都是"没人做过统一决策"的指纹。
  ⇒ 改观感**先做减法（统一规格），再做加法（图标 / 间距）**。
- **分隔线的取舍看"两侧是什么关系"**：两个**段落**之间用留白 + 图标锚点（不用线）；
  同一容器内两条**并列项**之间用 `HorizontalDivider`（M3 的 list divider 正用于此，
  它表达"这是两件独立的事"）。**不要**用一句"某某之间不该有分隔线"通杀。
- 🔴 **列表滑动删除：必须"先选中，再滑动"，且未选中时手势完全不挂**（2026-09-16 定稿）。
  这条是**四轮反复**换来的，别再把门槛删掉：
  | 轮次 | 手势 | 为什么改 |
  |---|---|---|
  | ① 09-13 | 长按成立后才接管位移 | 初版 |
  | ② 09-13 | 长按进多选后才可左滑 | 用户为防误触所选 |
  | ③ 09-14 | **去掉门槛**，任意条目直接左滑 | 用户反馈"不跟手、还要点按钮" |
  | ④ **09-16** | **门槛拿回来**（选中后才可左滑） | 用户反馈"直接滑动就删除"误触太多 |
  ⇒ **「防误触」与「跟手」此消彼长，别一次拍死一边**。两个诉求都真实，
  最终形态 = **长按（选中）+ 左滑 + 确认框** 三重闸门。
  ⚠️ 实现纪律：门槛参数用 `selectable`（**语义**是"该条目已选中"），
  为 `false` 时 **`pointerInput` 完全不挂**（不是"挂上再忽略"）——
  否则会有"滑了但没反应"的诡异手感，还要和滚动抢事件。
  ⚠️ **取消选中时位移必须归零**：否则卡片停在半开位，而那时手势已不挂、用户滑不回去。
  ⚠️ 卡包页这类**没有多选机制**的列表，补一个**轻量单值选中态**即可
  （长按选中/取消 + 点任意处取消 + 返回键取消 + 选中时隐藏 FAB），
  **不要**为此复刻整套多选工具条。
- **头像类元素别用"名称首字母"糊弄**（2026-09-16）：解锁页此前是
  `vault.name.take(1).uppercase()`，Bitwarden 库恒显示一个「B」——
  **不携带任何信息**（一个字母分不出库类型），而解锁页恰恰最需要确认"我开的是哪个库"。
  ⇒ 改成按类型渲染矢量图标。⚠️ 两个连带点：
  ① **自绘单色矢量**（可 tint），别打包位图 —— 否则深色主题要另配一套、
     且容易出现"深色底上一个死白方块"；
  ② 用第三方 logo 必须写清**归属与边界**（商标归属方 + 只在"标识所连接服务"
     的指示性用途下使用），且**优先独立复刻**而非复制上游源文件；
  ③ **必须补 `contentDescription`** —— 字母/文本方案下读屏读得出来，换成图片后
     不显式给就是一个无声的无障碍回归。
- **纵向留白：让位量要封顶，别用"贴底"公式**（2026-09-16 PIN 页）：
  「按容器高度反推让位、让内容底边贴屏幕底」听着精确，实际后果是
  **把全部剩余空间塞进某一处** —— 屏越大空白越大（800dp 机型头部与键盘间空了 220dp，
  用户截图圈出来）。⇒ `让位 = min(贴底所需, 屏高 × 1/6)`，
  再把富余空间交给 `Arrangement.Center` **均分到上下**。
  小屏自然仍走"贴底"分支（值本来就小），大屏留白被收掉 —— 一份公式覆盖两端。

- **「让设置简单点」的正确解法是减少"判断题"，不是减少元素**（2026-09-16 快速解锁设置四改）。
  用户说「还是不太好看，有没有让设置简单点的方案」，真实诉求不是"东西太多"，
  而是**决策成本没被收敛**：改前每库卡内两行（指纹 / 应用内 PIN）各带一个开关，
  用户得先自己回答"这两个冲突吗、要不要都开"，才能动手设置。
  ⇒ 改成**一次单选**（指纹 / 应用内 PIN / 每次输主密码），用户只需回答一个问题：
  "这个库怎么进？"。判据：**把"用户要做的判断"列出来数一遍** ——
  并列开关 = N 个独立判断，单选组 = 1 个判断，后者才是"简单"。
  ⚠️ **必须为"不用任何快速解锁"补一个显式选项**：否则用户要表达"我就想每次输主密码"
  时只能**把开关全关掉**（否定式操作），且界面上只留两个「未启用」，
  看不出这**就等于**他想要的状态。**永远给用户一个肯定的退出方式。**

- **互斥呈现 = 呈现层收敛，别动数据模型**（同上）。底层 `enabled` / `pinEnabled`
  两个独立布尔**可以同时为真**（两条解锁路径互不依赖），本次一行未改 ViewModel 存储。
  做法是：**显示时按优先级取一个**（指纹 > PIN），**互斥由动作实现**（点某项时关掉另一种）。
  ⚠️ 两个纪律：
  ① **优先级顺序在"显示"与"点击"两处必须一致** —— 不一致会出现
     "卡片显示指纹被选中、点一下 PIN 却把指纹关了"的错乱；
  ② 枚举顺序即优先级时，要把它写进 KDoc，别让下一个人靠读 `when` 反推。

- 🔴 **互斥切换绝不能"先拆旧的、再建新的"**（同上，本轮的静默数据丢失）：
  原实现"点 PIN ⇒ 立刻关指纹 → 再弹 PIN 设置框"。**PIN 设置是独立流程，用户可能中途取消**
  ⇒ 取消后就成了"指纹没了、PIN 也没设成"，**白白丢掉一种已配好的解锁方式**，
  且用户不会收到任何提示（静默，比 UI 难看严重得多）。
  ⇒ 改为**登记意图、等新配置真正落盘后**再执行拆除（`dismissBiometricAfterPinEnroll`
  + `PinEnrollOutcome.Enrolled` 分支），并在**取消路径上清掉意图**（否则下次成功会误拆）。
  ⚠️ **"修改"与"换用"必须是两个入口**：修改 PIN 时用户可能指纹与 PIN 同时开着，
  顺手关掉指纹就是破坏配置 ⇒ `openPinDialog`（修改，不动指纹）与
  `openPinDialogSwitchingFromBiometric`（换用，成功后关指纹）分开。

- **副标题只讲"选中后会怎样"，不讲"怎么操作"**（同上）。
  "点此处启用"这类**说明书口气**是廉价感的来源之一 —— 用户要的不是操作步骤，
  是**后果**（"用系统指纹验证，免输主密码"）。同理，**控件本身就是状态**时
  （单选/开关的选中态），就别再配一个「已启用」文字徽标 —— 同一件事说三遍。
  ⚠️ 但**不可用行仍要完整可读**：`enabled = false` 只降对比度（`alpha 0.38`），
  因为"本设备不支持"是**要传达的信息**，不是该藏起来的东西。
  ⚠️ 副标题判断要**"已生效状态优先"**：KDBX 库若已建好指纹钥匙，就
  不能再显示"需再输一次主密码以建立钥匙"（误导用户以为要重来）。

- 🔴 **「便利」类配置的默认值要朝"省事"走，但选择权必须在用户手上**（2026-09-16 九改）。
  用户要「一个 PIN 打开 bitwarden 和 kdbx」时的两条具体落法：
  ① 目标库列表**默认全选**（多数人的诉求就是"全开"，别让多数人多点一次），
     但列表**可见、可取消** —— 库表里有几个库 ≠ 用户想设几个（例如只读的共享库、别人的库）。
  ② ⚠️ **绝不能在数据层替用户决定**：早期版本写了"遍历全表给所有库设 PIN"，
     用户有 5 个库只想给 1 个设时会**静默改掉另外 4 个的配置** —— 越权，
     与 8.4 上面那条"静默改配置"是同一类错误。
  ⇒ 由 **UI 收集勾选、接口接收 `vaultIds`**；接口自己遍历全表是错的。

- **状态迁移必须把下一步需要的信息一起搬过去**（同上，本轮新踩）。
  `Entering` → `AskingKdbxPassword` 时若只带库名、把"勾选了哪些库"留在外部缓存，
  一旦取值失败就会退化成"全部库" ⇒ **静默越权**（同上一条）。
  ⚠️ 同理适用于**异步回填**：候选列表是异步取回来的，无条件写 `selected = 全部`
  会**覆盖用户已经点的勾选**（表现是"我点的那个勾又跳回来了"）。
  ⇒ 只在"用户还没动过"时才给默认值。
  **一句话：UI 状态是单一事实来源，别在它之外再存一份影子副本。**

- **`pinEnabled` 这类"已有状态"标注是必要的**（同上）：用户可能只想给**新库**补一个 PIN，
  看不到既有状态就无从判断"这一勾会不会把现有 PIN 覆盖掉"。

- ⛔ **（已推翻，勿再照做）** ~~沉浸式"栏"一律做悬浮胶囊，不做满宽条~~
  —— 2026-09-20 第四轮写给自己的规矩，**第五轮被用户否掉并已更正**。
  保留在此**仅为记录这个坑**，正确口径见下一条。

  **为什么错**：`RoundedCornerShape(50)` 的语义是**百分比**，它在"宽满屏 × 高 48~72dp"的
  扁容器上会被**高度钳死** ⇒ 两端半圆、中间一大段直线 ⇒ 观感是**扁椭圆枕头**
  （用户原话：「上下胶囊都好长，太碍眼了」）。M3 里没有任何组件用这种形状。
  更严重的是**第三轮我把问题弄大了**：胶囊四周留白恰好把 `Dialog` 窗口的**黑色背景**
  露出来 —— 黑带从来不是形状问题，它在**窗口层**。满宽栏反而能盖住它。

- 🔴 **正确口径：沉浸式"栏"做满宽薄栏 + 与背景匹配的渐变保护层**（2026-09-20 第五轮定稿，
  2026-09-21 第六轮修正，`FullScreenDialogShell`；`ISSUES.md` #107；官方 edge-to-edge 指南的 Do 项）。
  **沉浸感的来源是"内容从栏下方穿过"**，不是"栏透明"、也不是"栏变形状"。
  - **形状**：**满宽**、**无圆角**。一端贴屏幕边，一端做渐变过渡。
  - **✓ 栏体要薄**：栏体高 = `触摸目标 48dp + Spacing.xs × 2 = **56dp**`。
    ⚠️ 第六轮用户反馈的判据是「**下方保存和取消占用的空间太大**，一条很大很宽的白色横条」
    —— 逐像素核对（截图 + 代码模拟）后确认：白条 **87dp** 里真正有内容的按钮只有 **48dp**，
    多出的 **24dp 是纯留白**（上下各 `Spacing.md` = 12dp），栏体因此比内容高 **50%**。
    ⇒ 把垂直内边距从 `Spacing.md`(12dp) 收到 `Spacing.xs`(4dp)，**触摸目标不缩**。
    对照：用户自己项目 Bastion 的 `NoteEditorTopBarHeight = 64.dp` 也在同一量级。
  - **渐变保护层**：`Modifier.drawBehind { drawRect(Brush.verticalGradient(...)) }`，
    **零额外布局节点**、渐变天然跟随宿主尺寸（不需手算端点坐标）。
    端点色**必须是 `colorScheme.surface`** —— 官方 Don't：「渐变保护与各 pane 背景**不匹配**」
    （正文里 `FormGroupCard` 用 `surfaceContainerHighest`，与 `surface` **不同色**）。
  - **必须三档，不能两档**：`不透明段 = 系统栏 inset + 栏体高`，之后才是过渡尾段。
    两档会让栏体上半段就变半透明 ⇒ 标题读不清。
    ⚠️ 比例**必须按实测 inset 算**，不能写死（24/36/48dp 三种机型下各不相同 ——
    写死一个数会让某类机型的标题区提前变透明）。
  - **★ 渐隐段的"位置"是设计要点，不是实现细节**（第六轮新增纪律，本轮核心缺陷）：
    **渐隐段必须落在内容侧** —— 顶部在「栏体下沿」之下、底部在「栏体上沿」之上。
    ⚠️ 把渐隐段放在**系统栏 inset 的空白区**等于**没做渐变**：那片区域本来就没有任何元素，
    渐变画在空白上肉眼不可见；而真正有卡片穿过的栏体区反而全程 1.00 不透明 ⇒ 仍是**硬边**。
    ⚠️ 反模式（第五轮的写法）：底部用 `opaqueUntil = 1f - 尾段/层高` 把渐隐**钉死在层底**
    —— 层底正是 inset 空白区。**"能省参数" ≠ "该省参数"**：当被省掉的信息（这里是 `navBarInset`）
    决定语义时，省它就是错。
    ⚠️ 验证方法：逐像素模拟打印每个 dp 的 alpha + 该处有无内容（见
    `SESSION-2026-09-20.md` §10.4）。**只看代码是看不出这个 bug 的** —— 两个写法数学等价。
  - **官方 Don't：绝不叠加多层保护** —— 只有**一层**渐变，**不加** scrim、不加第二层色块。
  - **`shadowElevation` 恒定**，绝不出自 `animateXxxAsState`：阴影几何参与动画
    会重建渲染层 ⇒ 掉帧（`SESSION-2026-09-20.md` §6.1 踩过）。
  - ⚠️ **不用 `Modifier.blur`**：minSdk 26 的 API 31- 是 no-op（设备分叉）、离屏渲染掉帧耗电、
    且 OLED 下模糊纯黑仍是纯黑。渐变不需要采样本层之外的内容，本来就不该用 blur。

  **"黑带/白条"的诊断顺序（四问，第四轮全问错了、第六轮补第 ④ 问）**：
  ① 黑带是在**栏内**还是**栏外的窗口背景**？（第三轮的教训：胶囊四周留白露出的就是窗口的黑）
  ② 宿主是 `Activity` 还是 **`Dialog`**？`Dialog` 窗口类型是 `TYPE_APPLICATION_PANEL`，
  **不继承** Activity 的 edge-to-edge，其 window background 来自主题（= 黑）。
  ③ 是否还在用 `window.statusBarColor` / `navigationBarColor`？
  `targetSdk ≥ 35` 起**它们是 no-op**（Android 15 强制 edge-to-edge）。
  ④ **（第六轮新增）白条的"高"里，有多少是内容、多少是纯留白？渐隐段落在哪？**
  —— 把截图量出的高度拆成「触摸目标 / 内边距 / inset / 尾段」四份，再逐像素模拟 alpha。
  ⚠️ 用户说"白条很大"时，**先量再改**；本轮量出来是"24dp 留白 + 渐隐画在空白区"两件事，
  和"栏透明没做"（用户原话）**都不是**同一回事。
  ⇒ **先查窗口层，再量尺寸，最后才是渐变分布；栏的形状是最后才动的东西。**

  ⚠️ **不要"顺手修正" `navigationBars` 这个 insets 源**：第六轮曾怀疑底部白条下沿不是屏幕底
  是取到了手势热区（~45dp）所致，核对后**否掉** —— 主界面
  `VaultixBottomDock.kt:87` 读的是**同一个** `WindowInsets.navigationBars`。
  换 insets 源会让编辑壳与主界面**分叉**，而用户的验收判据恰恰是
  「完全和主界面滑动的时候效果不搭调」。**与主界面保持同源**优先于"理论上更准"。

- **全屏壳的"让位"口径 = 系统栏内边距 + 栏体高**（同上）。`contentClearance(inset, barHeight)`
  的公式与语义**不变**（`maxOf(barHeight, inset + barHeight)`，`maxOf` 兜底理由见函数 KDoc）。
  第五轮栏回到满宽后口径**简单化了**：第二入参从"该侧总垂直占位（含胶囊留白）"
  退回"**栏体自身高**"。`FullScreenDialogShell` 当前取值：顶部 `48 + 4 × 2 = **56dp**`、
  底部 `48 + 4 × 2 = **56dp**`（顶部与底部同档；第六轮由 72dp 收到 56dp）。
  ⚠️ **常量必须与栏体 modifier 的内边距严格对齐**（`56 = 触摸目标 48 + Spacing.xs × 2`
  对应 `Row(vertical = Spacing.xs)`）—— 两处不同步，让位就会偏，退化成"内容被遮住"老 bug。
  ⚠️ **让位长度必须与渐变不透明段长度恒等**（都是 `inset + barHeight`）——
  这不是巧合，而是"卡片不会透进不透明段"的**全部依据**（见文件内 `topGradientStops` KDoc）。
  ⚠️ 改栏体高时**三处联动铁三角**必须同步：① 常量 ② `Row(vertical = ...)` ③ 渐变比例分母
  （`layerHeight`）。单测 `ContentClearanceTest` 已按 56dp 重算，改错会立刻红。

- **"必须一直可点"不等于"必须满宽"**（同上，更正 `SESSION-2026-09-20.md` §5.3）。
  那条曾以"底部必须一直可点"为由决定不做胶囊，第四轮复核**不成立**：
  胶囊同样一直可点（列表页底栏就是胶囊且恒在最上层）。
  §5.3 真正要防的是"**半透明**、看不出能点"。
  ⇒ 表述统一为：**可点性由"不透明 + 恒定在最上层"保证，与"是否满宽"无关。**
  ⚠️ 第五轮加注：这条只说明"可点性不是选择形状的理由"，
  **不能**反过来当成"所以该做胶囊"的依据 —— 胶囊已被否掉，理由是形状与窗口背景，见上两条。

## 2026-10-01（第 67 轮）：KDBX 页与条目卡左栏的排版纪律

用户原话：「新建 kdbx 和打开 kdbx 库的 ui 不好看，要符合 material3 最新的风格，
另外密码条目界面的左边标题部分也要注意排版。」本轮从**具体改了哪几行**里，
提炼出四条可复用的判据 —— 它们不是这一页的私事，凡"表单 + 卡片列表"都适用。

### ① 「布局间距」与「视觉间距」必须分开算（本轮的核心发现）

`EntryCard` 的标题用 `titleMedium`（16sp / **24sp 行高**），副标题在其下 6dp。
**代码里是"隔 6dp"，屏幕上却是"隔 13dp"** —— 因为：

| 贡献者 | 量 |
|---|---|
| `spacedBy` 字面值 | 6dp |
| 标题自身行高余量（24 − 16）/2 | ~4dp |
| 副标题 `bodyMedium` 行高余量（20 − 14）/2 | ~3dp |
| **屏幕上的实际空隙** | **≈ 13dp** |

⇒ **改动**：间距取 `Spacing.xs`(4dp)、同时把标题 `lineHeight` 显式收到 21sp，
两者相抵后视觉间距落回 ~8dp（正好是标尺 `sm` 档）。
**光调 `spacedBy` 调不准** —— 行高也在间距里参与运算。

> ⚠️ 纪律：**调文本间距前先问"这里的行高余量是多少"**。
> 行高 > 字号的组件（M3 的 `title*` / `body*` 全部如此）天然自带隐形间距，
> 直接照搬设计稿的 `spacedBy` 数值必然偏大。

### ② 一个共用组件改了规格，**所有调用点一起改**（本轮差点漏掉）

`EntryCard` 被 **4 个列表页**共用（密码条目 / 验证码 / 卡包 / 通行密钥），
其 KDoc 明写"三处列表自动统一"就是为了防不一致。
本轮只给密码页的标题加 `lineHeight` 时，**另外三页没跟上** ⇒ 等于把
「一屏两套规格」平移成**「四个页面两套规格」**，更隐蔽（要跨页截图才看得出）。

⇒ **纪律**：动 `ui/common/` 里的共用组件或它的共享常量时，
先 `grep` 它的**全部调用点**（`grep -rn "EntryCard(" app/src/main | grep -v EntryCard.kt`），
**要么全改、要么不改**。本轮已统一到 4 页。

> ⚠️ 顺带记一笔**行为变更**（不是纯视觉）：密码页的标题此前**没有** `maxLines`
> （长标题会折行），另外三页早已是 `maxLines = 1`。本轮把密码页补齐成 `maxLines = 1`
> ⇒ **长标题从"折行"变成"省略号"**。理由：留一个例外就是留一套规格；
> 且 `ListEntry` 的标题语义上就是单行标识。
> 这正是 `8.8` §6④「别为 M3E 改行为」要求**显式声明**的那类改动 —— 已在此备案。

### ③ 别用 `enabled = false` 表达"已选中"

`AddKdbxScreen` 的模式切换器原写 `enabled = enabled && mode != entry`，
本意是"别重复点已选项"。但 `enabled = false` 的语义是**不可用**，M3 会：
文字降到 `alpha 0.38` + **去掉选中态的容器色** ⇒ 选中的那半看起来像**坏掉的按钮**，
没选中的那半反而更亮、更像能点。用户看到的就是"选中态反了"。

⇒ **纪律**：「已选中」只该由**选中容器色**表达。防重复点应做在**幂等**里
（重复点同值 = 无副作用），不是做在 `enabled` 上。
**一个属性只表达一件事** —— 这条与上面「一个元素只该说一件事」是同一原则的不同层。

### ④ `material3` 组件的 `icon` 槽**不要**占掉默认值

`SegmentedButton` 的 `icon` 槽默认是 `SegmentedButtonDefaults.Icon(selected)`
（选中时 `fadeIn + scaleIn` 淡入一个勾）—— 那是 M3 表达"选中"的标准手段。
本轮初版把类型图标（文件夹 / 加号）塞进 `icon` 槽，等于**丢掉组件自带的选中反馈**。
⇒ 正确做法：`icon` 槽留默认值，类型图标放进 **`label` 行内**。
两者各司其职：`icon` 槽说"选没选中"，label 内图标说"这是什么选项"。

> ⚠️ 该默认动效是**组件自带**的 M3 规范动效，不是我们手加的
> ⇒ 与 `ISSUES #87`「不要花里胡哨的动画」**不冲突**（那条针对页面转场与自造动效）。

## 2026-10-04（第 74 轮）：表单的**四级间距阶梯**与「字段名不许比分区标题大」

对象：`ItemFormDialog`（「编辑条目」，三个调用方）+ `QuickUnlockDialogs`（「锁与安全」）。

### ① 「三层间距一个值」= 层级坍塌（本轮根因）

改前`ItemFormDialog` 里所有纵向间距几乎都是 `Spacing.md`(12dp) / `Spacing.sm`(8dp)：

| 关系 | 改前 | 改后 |
|---|---|---|
| 分区标题 ↔ 它的首个字段 | 8 | **8**（不动） |
| 字段 ↔ 字段 | 8 / 12 混用 | **12** |
| 卡内小节 ↔ 小节（「登录信息」↔「网址」↔「TOTP」） | 12 | **16** |
| 卡片 ↔ 卡片 | 12 | **24** |

⇒ 12dp 同时表达「两个输入框之间」和「两个分组之间」。
**眼睛无法区分"这里换了个控件"和"这里换了个话题"** —— 这就是用户说的
「信息块之间间距过窄、视觉层级不清晰、观感拥挤」的机制性原因，
不是"某几个地方间距调小了"。

⇒ **纪律：任何多分组表单，先把纵向关系列成表并分配互不相同的值，再动代码。**
`Spacing` 标尺的 8/12/16/24 正好够四档用；**档数多于标尺档数时不要新增常量**，
先合并关系（哪两档其实是同一档）。

> ⚠️ **反例要记住**：身份证 18 个字段的 `LabeledFields` **保持 12dp 不变**。
> 那一处的KDoc 已论证「8dp 会挤成一堵输入框墙」—— 12dp 在「字段↔字段」这一档
> 是对的。把阶梯拉开的目的是让**其它三档**有地方落，不是把所有值都推大。

### ② 字段名不许比分区标题更显眼（本轮的字号倒挂）

`OutlinedTextField` 的 `label` 槽默认走 M3 `bodyLarge`(16sp)，
而分区标题 `SectionLabel` 是 `labelLarge`(14sp)
⇒ **二十来个字段名全都比它们的分组标题大一号**，扫视时先看到一排字段、
看不到结构。

⇒ 抽出私有 `FormFieldLabel(labelRes, required = false)`（`ItemFormDialog`），
全表**11 处**字段名统一降到 `bodyMedium`(14sp)，与分区标题同档；
标题靠**图标 + 主色**赢层级，不靠字号。

> ⚠️ **`FormFieldLabel` 只设 `style`、绝不设 `color`** ——
> M3 要靠label 的颜色表达状态（有焦点=primary / 出错=error / 常态=onSurfaceVariant）。
> 在这里写死颜色会把这套状态提示（可访问性的一部分）全部弄丢。
> 这与 ① 里的「一个属性只表达一件事」同源。

### ③ 关键字段用「换色档的淡底」，不用「加粗字号」

密码是全表单唯一「填错会出事」的字段，但它与用户名/网址**结构完全同类**（都是文本框）
⇒ 不能靠改结构来区分（那会让表单长出一节专用布局）。
新增私有 `EmphasisBlock`：`primaryContainer.copy(alpha = 0.30f)` + 12dp圆角 + 12dp 内边距，
包住密码框与强度条。

> ⚠️ **必须换色档**：卡片底是 `surfaceContainerHighest`，强调块用 `primaryContainer`
> （与 surface 档不同色相）再压 alpha。若用 `surfaceContainerHighest.copy(alpha=…)`，
> 那正是本文档禁止的「同色叠 alpha」—— 边界糊掉，等于没做。
> ⚠️ **alpha ≤ 0.30**：它是背景提示，过深就会与分区标题抢注意力。

### ④ 必填项要「常态强调」，不能只在报错时提示

此前名称字段只有保存失败后才出红字+「名称不能为空」，用户已经白填了整张表。
现在 `FormFieldLabel(required = true)` 在 label 后加 `*`：**常态告知规则** + **出错变红**两层。

### ⑤ 动作区：主操作必须是 filled，破坏性操作必须推到另一端

- `FullScreenDialogShell` 底部此前「取消」「保存」**同为 `TextButton`** ——
  两个等重按钮里，用户每次都得重读一遍哪个是主操作。现 `onConfirm` 改filled `Button`。
- `QuickUnlockDialogs` 的「关闭 PIN 解锁」破坏性动作此前紧贴「返回」，
  现用 `Spacer(Modifier.weight(1f))` 推到**最左**并染`error` 色
  ⇒ 动作区两端对齐，破坏性与常规不混在一堆。

> ⚠️ **给 filled `Button` 加 `heightIn(min = 48.dp)` 是错的**：
> M3 `Button` 视觉高 40dp，但 `minimumInteractiveComponentSize` 已把触摸目标撑到 48dp，
> 栏体 `ACTION_BAR_HEIGHT`(56dp) 放得下。强行再拉高只会让同栏「取消」相对更矮、
> 显得像次要残件 —— **别把"触摸目标"和"视觉高度"混为一谈**（呼应 ①）。

### ⑥ 弹窗内的输入框也要给彼此留白

`DialogSurface` 的 `Column` **没有 `verticalArrangement`**，`PinField` 也无外边距
⇒ PIN 弹窗里三个 `OutlinedTextField` 的描边**贴合成一个长框**，看起来像个密码输入区。
已补 `Spacing.md`(12dp)。`DialogErrorText` 的 `top` 由 4dp 提到 8dp
（错误文案贴字段太近会被读成"描边外的第四个框"）。

> ⚠️ **系统 `BiometricPrompt` 内部不可控** —— 指纹弹窗的圆角/间距/配色属于平台，
> 我们**能**优化的只有承载页（`AuthenticatingDialog`）与设置页的指纹行。
> 不要向用户承诺能改系统弹窗内部。

## 2026-10-04 补充：浮层与让位**必须共用同一 animationSpec**（用户实测「点筛选按钮遮住条目」）

### ⑦ 两个动画不同源 ⇒ 动画进行中必然错位一帧

`ItemsScreen` 的快捷筛选面板浮在列表之上，让位走 `LazyColumn.contentPadding`。两者：

| | 高度/让位 | 规格 |
|---|---|---|
| 面板 | `AnimatedVisibility` 的 `expandVertically` | **默认 spring** |
| 列表让位 | `animateDpAsState` | `tween(GROUP_ANIM_MS=200)` |

spring 与 tween 的**时长与曲线都不同** ⇒ 展开过程中面板比让位高，
多出来的那一截**压在第一条条目上**，动画结束才落回正确位置。

⇒ **纪律：凡「浮层尺寸」与「内容让位」都由动画驱动，两个动画必须写同一个
`animationSpec`常量。** 且那个常量必须**只定义一处**、两端都引它
（这里是 `GROUP_ANIM_MS`；改动画时长时只改它，不会漏掉另一端）。

> ⚠️ **这类 bug 静止时抓不到**：动画结束后的位置是正确的 ⇒ 真机截图**永远是好的**。
> 只有"盯着展开过程"才看得见。⇒ 怀疑遮挡类问题时，先问"**是动画期间还是稳定后**"，
> 若是动画期间就去查两个动画的规格是否同源，不要去调 contentPadding 的数值。

### ⑧ 往「子元素自备内边距」的容器里加新元素，必须照抄兄弟的 padding 约定

`DialogShell.DialogSurface` 的 Column **只给 `padding(vertical)`**，水平内边距靠
每个子元素**各自**带（`DialogHeader`/`DialogSectionTitle`/`DialogActions` 都是
`start/end = Spacing.xl`）。

新增的 `PinField` 若写成裸 `fillMaxWidth()` ⇒ 它成了**唯一贴到面板边缘的元素**，
与上下元素内缘对不上 —— 用户看到的就是「输入框顶到弹窗边缘」。

⇒ **纪律：加子元素时先读两个兄弟元素的 padding，照抄。** 一屏里出现两套内边距
与两套字号同源（见本文件②），都是"廉价感"的头号来源。

> ⚠️ **反面做法**：不动调用点、给 `DialogSurface` 统一加水平 padding。

## 第 76 轮：像素取证的**横向扫描**——量间距证明不了「没遮挡」

### ⑨ 「几何上有间距」≠「看起来没被遮住」

2026-10-04 用户三轮反馈「筛选面板遮住下方密码条目」。前两轮我都在**量几何间距**：

| 轮次 | 量出来的 | 结论 | 结局 |
|---|---|---|---|
| 74（读代码） | `expandVertically` 默认 spring ≠ 让位的 `tween(200)` | 动画不同源 | ❌ 提交 `4c3aa72` 后仍复现 |
| 75（纵向扫） | chip 行底 y=343 → 卡片顶 y=595，**间隙 72.5dp 确实存在** | 「没有遮挡，是我误读」 | ❌ 只看了**收起态** |
| 76（**也横扫**） | 间隙那一行**整行同色** `(13,14,17)` | **两侧同色 ⇒ 边界不可见** | ✅ |

`QuickFilterChips` 的 `Surface(color = colorScheme.surface)` **与页面背景同值**。
于是「chip 行底边」和「间隙的开头」在像素层面是**同一块颜色**，人眼读不出边界，
卡片顶部圆角就像被 chip 行吃掉了一半。

⇒ **调 `contentPadding` 数值、改 `animationSpec` 都修不好这个**：
它们只能保证「不重叠」，而这里**本来就没重叠**。

### 纪律：判断「遮挡 / 挤在一起 / 糊成一片」必须**双向扫描**

纵向扫（固定 x，逐行 y）只能回答「**有没有重叠**」。
必须**再横扫一次**（固定 y，逐列 x）回答「**边界看不看得出来**」：

```bash
# 纵向：卡片在哪开始、浮层在哪结束
python scan.py e1.png --col 628 --range 0:760
# ★ 横向：在「两者之间那道间隙」上横着扫一遍
python scan.py e1.png --row 520 --range 0:1256
```

判据：**间隙内那一行的颜色若全段只有一个值 ⇒ 边界不可见 ⇒ 观感必然是「遮住」。**
