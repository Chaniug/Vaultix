# 8.8 M3 Expressive（2026）—— 采纳范围与顺序

> **用户提问**（2026-09-15）：「M3 / M3 Expressive（2026）能借鉴什么？我感觉能帮项目提升很多。」
> **本文档的用途**：把"借哪一半、按什么顺序、每步怎么验"定下来，供 AI 接力直接开工。
>
> **交接状态**：盘点完成 ✅ / **P0-1 间距标尺 ✅ 已落地** / **P0-2 表达式搜索 ✅ 已落地**
> / **P1 起未动** ❌（原因见 §4 各条的「沙箱限制」）
> 结论是**分会采纳、不整体切换**（§0），从 §4 的 P0 开工。
>
> **2026-09-15 更新**：P0 两项已在第六十六轮完成，实测数据见 §4 各条。
> ⚠️ **本轮是在沙箱内完成的，没有编译验证**（沙箱拿不到 Android SDK）——
> detekt 全量已真跑通过，但**编译与真机必须在本机补验**，见 §7。

## §0 结论（先记住这三句）

1. **借"理性的一半"**：间距标尺、表达式搜索、新进度指示器、按钮组的单选语义、
   tonal elevation、Styles API。
2. **不借"情绪的一半"**：形状变形、夸张动效、大字重 —— 与本项目已拍板的纪律
   **直接冲突**（`.ai/ISSUES.md` #87：转场只允许 `translationX`，用户明确"不要花里胡哨的动画"）。
   密码管理器的信任感来自**可预测**，情绪化动效在这里是负资产。
3. **成本几乎为零**：本项目 `material3 = 1.5.0-alpha16` **已经带了 M3E 全套 API**（§2 实测），
   所以这不是"要不要升依赖"，而是"要不要改 + 怎么验"。

## §2 本项目**已有**的 API（实测，别再怀疑要不要升级）

解 `~/.gradle/caches/.../androidx.compose.material3/material3-android/1.5.0-alpha16/*.aar`
里的 `classes.jar`，按类名计数：

| API | 类数 | API | 类数 |
|---|---|---|---|
| `LoadingIndicator` | 8 | `SplitButton` | 9 |
| `MaterialShapes` | 5 | `ToggleButton` | 6 |
| `MotionScheme` | 7 | `FloatingActionButtonMenu` | 10 |
| `WavyProgressIndicator` | 2 | `FloatingToolbar` / `HorizontalFloatingToolbar` | 38 / 9 |

⚠️ **但项目里一个都没用**（grep `MotionScheme|LoadingIndicator|WavyProgress|ButtonGroup|SplitButton` = 0 处）。
⇒ 现状是"手写实现 M3E 的精神"：`VaultixExpressiveTopBar` 的"滚动快照收起 + 胶囊 spring"
就是表达力顶栏，而底层 API 是自己写的。

## §3 现状的两个量化依据（决定优先级）

| 指标 | 实测 | 意味着 |
|---|---|---|
| 手写 `.dp` 字面量 | **540 处**（`app/src/main`） | 没有间距标尺 ⇒ 数值靠感觉 ⇒ 必出"隔太近/多一条缝"这类 bug |
| `Circular/LinearProgressIndicator` 用法 | **32 处** | 进度态全是老指示器，替换收益面大 |

> 佐证：2026-09-14 的「顶栏标题与三个图标隔太近」，根因就是
> `ACTIONS_RESERVE = 144.dp` 恰好等于胶囊宽度（余量 0）——典型"数值没有标尺"的病。

## §4 采纳清单（按顺序做，一步一验）

### P0-1 间距标尺（8dp scale tokens） —— ✅ **已完成（2026-09-15）**

- **做什么**：新建 `ui/theme/Spacing.kt`（`xs=4 / sm=8 / md=12 / lg=16 / xl=24 / xxl=32`），
  然后**按文件**替换 540 处字面量。
- **为什么先做**：零视觉风险（值不变或只对齐到标尺）、直接消掉一类 bug、后续所有 UI 工作都受益。
- **注意**：替换时**只对齐到最近的标尺值**，不要顺手改版式 —— 换版式是"设计变更"，
  会与"零行为变化"的验收标准打架。
- **验证**：`detekt` + 编译 + 真机逐页目视（尤其设置页与条目页）。

**实测结果（第六十六轮）**

| 项 | 数字 |
|---|---|
| 手写 `.dp` 字面量总数 | **539** 处 / 43 个文件 |
| 其中**正好落在 8dp 标尺**上 | **373** 处（69%）→ 已替换 |
| 不在标尺上、保持原样 | 166 处（`0/2/3/6/10/18/20/22/28/36/40/44/48/72` 等） |
| 实际替换 | **369** 处 / 41 个文件（373 减去 `Spacing.kt` 自身 6 处定义值） |

- ⚠️ **`0.dp` 不进标尺**：它是"没有间距"这个语义本身，写成 `Spacing.zero` 反而绕。
- ⚠️ **替换后撞了 2 处 `MaxLineLength`**：`Spacing.lg` 比 `16.dp` 长，两行
  `PaddingValues(...)` / `Modifier.padding(...)` 撑到 121/123 字符 ⇒ 已拆成多行。
  **以后再做批量替换，跑完 detekt 要单独确认行长。**
- ✅ **等价性已用反演法证明**：把改后文件里的 `Spacing.*` 展开回数值 `.dp`，
  与 HEAD 版本逐行比对 —— **41 个文件全部逐字符一致**（`SettingsScreen.kt` 的差异
  经核验全部来自同轮的设置页重组，含 `.dp` 的差异行为 **0**）。
  ⇒ 这次是**纯等价替换，版式一个像素都没变**。

### P0-2 表达式搜索栏（contained search） —— ✅ **已完成（2026-09-15，只做观感）**

- **做什么**：把 `ItemsScreen` 的 `ItemsSearchBar` / `VaultixSearchTopAppBar` 换成 2026 的
  contained search 样式（常驻填充容器 + 尾部图标位）。
- **顺带好处**：**尾部图标位正好是"筛选入口"该待的地方** —— 可以顺手解掉
  「筛选入口放哪」的历史纠结（目前是点库名展开 + 顶栏胶囊）。
- **风险**：中（涉及搜索态与列表 inset 的联动，参考 `itemsTopInset` 的注释）。
- **验证**：搜索态的 inset 与"沉浸"效果不能退化（`ISSUES.md` #67 / #76 是这一带的坑）。

**实测结果（第六十六轮）**

- 改造点只有 `ui/common/SearchTopAppBar.kt` 的 `title` 槽：
  透明裸输入框 → `surfaceContainerHigh` **胶囊容器**（`RoundedCornerShape(28.dp)`）
  + 左侧搜索图标（`Icons.Filled.Search`）。
- ⚠️ **刻意没换成 alpha 的 `SearchBar` 组件** —— 本文档 §6① 明确要求
  「交互框架（AppBar / 搜索）等 beta/stable 再换」。这里用**稳定的 `TextField` 自绘同样的观感**，
  零 alpha API 依赖（`shape` 是 `TextField` 自 1.2 起的稳定参数）。
- ✅ **inset 一行没动**：容器高度固定 `56.dp`、外层仍是同一个 `TopAppBar`（64dp）
  ⇒ 调用方（`ItemsScreen.itemsTopInset` 等）的让位计算**完全不受影响**。
  这正是刻意的设计 —— #67 / #76 都是"让位算错"的坑，为换个样式去动 inset 不值得。
- ⏳ **"尾部图标位放筛选入口"没做**：那会引入一个新交互（属于**产品变更**），
  §6④ 写明"别为 M3E 改行为"。留在 §7 待用户拍板。
- ⚠️ 本组件被 **4 个页面**共用（`ItemsScreen` / `CardWalletScreen` / `PasskeysScreen` /
  `TotpCodesScreen`）⇒ 真机验收要**四个页面各进一次搜索态**确认。

> ⚠️ **P1 起为什么没接着做**：这三项都要引入 **material3 1.5.0-alpha16 的新 API**，
> alpha 会改名、会改语义。本轮**沙箱内无编译环境**，不宜凭记忆写不确定的 API。
> ⇒ P0 两项（只用稳定 API）已落地；P1/P2 留到下一轮。
>
> ✅ **但 API 已经查清了**（2026-09-15 解 `material3-android-1.5.0-alpha16.aar` 的
> `classes.jar` + `javap` 实测，不是凭记忆）⇒ **下一轮可以直接照抄下面的签名开工**，
> 不必重新调研。查法：腾讯 maven 下 aar → `unzip` → `javap -public -classpath classes.jar <类名>`。

### P1-1 新进度指示器 —— ❌ **未开工（需本机编译验证，勿在沙箱做）**

- **做什么**：解锁页（现在只有一个光转圈）+ 同步横幅（`SyncNoteBanner`）换成
  `LoadingIndicator` / `LinearWavyProgressIndicator`。
- **⚠️ 例外**：**验证码倒计时不要换**（`UnifiedProgressBar`）—— 那一处需要**精确读数**，
  波浪动效会干扰判断。
- **验证**：真机看解锁页与同步横幅；确认没有引入额外的主线程开销（`gfxinfo` 对比）。

**实测 API（1.5.0-alpha16，javap 提取）**

```kotlin
// 波浪进度条 —— ✅ 可直接用，无额外依赖
fun LinearWavyProgressIndicator(
    progress: () -> Float,          // 确定进度；不确定循环用下面那个重载
    modifier: Modifier = Modifier,
    color: Color,                   // 进度色
    trackColor: Color,              // 轨道色
    stroke: Stroke,                 // 进度线宽
    trackStroke: Stroke,            // 轨道线宽
    wavelength: Float, amplitude: Float,   // 波长 / 振幅（波浪形状）
    waveSpeed: ... , wavePhase: ...,
)
fun LinearWavyProgressIndicator(modifier = ..., color = ..., trackColor = ...,
    stroke = ..., trackStroke = ..., wavelength = ..., amplitude = ...,
    waveSpeed = ..., wavePhase = ...)          // 不确定态（无 progress）
// CircularWavyProgressIndicator 同理（少一个 stroke 维度）

// 新版加载指示器 —— ⚠️ 见下方依赖提醒
fun LoadingIndicator(modifier = ..., color: Color, polygons: List<RoundedPolygon>)
fun ContainedLoadingIndicator(modifier = ..., color: Color,
    containerColor: Color, shape: Shape, polygons: List<RoundedPolygon>)
```

⚠️ **依赖提醒**：`LoadingIndicator` / `ContainedLoadingIndicator` 的 `polygons` 参数类型是
`androidx.graphics.shapes.RoundedPolygon` ⇒ **需要新增 `androidx.graphics:graphics-shapes` 依赖**
（已在 `libs.versions.toml` / `app/build.gradle.kts` 中确认**当前没有**）。
⇒ **想省事就只用 `LinearWavyProgressIndicator`**（纯 ` Stroke`/`Float` 参数，零新依赖）；
确要用 `LoadingIndicator`，先加依赖再写。

### P1-2 ButtonGroup / ToggleButton（快捷筛选行）—— ❌ **未开工（同上）**

- **做什么**：条目页的快捷筛选 chip 行本质是**单选**，用 `ButtonGroup` 表达最贴切。
- **⚠️ 克制**：形状联动只保留"选中态变化"，**不要**开启夸张的 bump/形变
  （见 §5 的红线）。

**实测 API（1.5.0-alpha16，javap 提取）**：`ButtonGroupKt.ButtonGroup` 有 **3 个重载**，
最通用的一个是
```kotlin
fun ButtonGroup(
    overflowIndicator: @Composable ButtonGroupMenuState.() -> Unit,
    modifier: Modifier = Modifier,
    horizontalArrangement: Arrangement.Horizontal,
    verticalAlignment: Alignment.Vertical,
    content: ButtonGroupScope.() -> Unit,
)
```
⇒ 无 `graphics-shapes` 依赖问题，但**签名与 1.4/1.5 早期版本不同**（多/少了
`overflowIndicator` 与 `verticalAlignment` 的位置）⇒ 照抄上面这份，别照抄网上旧示例。

### P1-3 tonal elevation + Styles API —— ❌ **未开工（同上）**

- **做什么**：用**表面色调**表达层级，替掉零散的 `Modifier.shadow` / `shadowElevation`
  （例：`VaultixExpressiveTopBar` 的动作胶囊 `shadowElevation = 1.dp`）；用 Styles API
  做组件变体，而不是 fork 一份组件。

### P2 表达力 AppBar DSL（**最后做**，单独一批）

- **做什么**：用官方的 `AppBarRow`/`AppBarItem`/`AppBarMenuState` 替掉手写的
  `VaultixExpressiveTopBar`（含 2026-09-14 刚调的 26sp 标题 / 156dp 动作预留 /
  滚动快照收起 + 200ms 补间 + 胶囊 spring）。
- **为什么最后**：**收益最大、回归风险也最高**（那套行为是用户反复提过意见的地方：
  `ISSUES.md` #62 筛选条必须浮在内容之上、#76 让位必须写在 contentPadding 里、
  #87 转场只允许 translationX）。
- **前置条件**：等 `material3` 到 **beta/stable**（见 §6），且**逐帧录屏比对**新旧行为。

## §5 明确**不采纳**（连同理由，避免接力者重新提议）

| 不采纳 | 理由 |
|---|---|
| 形状变形（`MaterialShapes` 的 cookie/clover 等装饰性用法） | 与本项目"克制、可预测"的观感取向冲突；密码管理器里是噪音 |
| 强调排印（更大的 display 字号、更重的字重） | 顶栏标题刚从 32sp 收到 **26sp**（2026-09-14 用户要求"缩小、让开右侧三图标"），方向相反 |
| 夸张动效 / bump 形变 / 弹性过冲 | **硬冲突**：`ISSUES.md` #87「转场只允许 `translationX`」+ 用户原话"不要花里胡哨的动画" |
| watch / XR 相关（arc text、spatial panel、depth elevation） | 目标平台是手机（§MEMORY.md §6），无落地场景 |
| Material Web Components / Glimmer | 与 Android 端无关 |

## §6 坑与边界（写之前先看）

1. **它是 alpha16**：建议**只用于叶子组件**（进度指示器、间距 token、Styles API），
   **交互框架**（AppBar / 搜索）等 beta/stable 再换。理由：alpha 的 API 会改名/改语义，
   而 AppBar 这种"框架级"替换的成本随 API 变动线性上升。
2. **动态取色 ≠ 品牌色**：本项目 UI 走 Material You（跟随壁纸），**品牌色只允许出现在
   两个地方** —— 应用图标（`res/values/colors.xml` 的 `ic_launcher_*`）与首启页的两个
   入口按钮（`VaultListScreen` 的 `BITWARDEN_BRAND_BLUE` / `KDBX_BRAND_GOLD`，
   2026-09-14 加）。**不要**为了"M3E 的鲜艳配色"把品牌色铺进普通 UI。
3. **M3E 是 Android 16 才成为默认的**，但本项目 `targetSdk = 37`：系统侧已在按新口径
   渲染。Compose 组件自带样式，受影响的主要是**XML/View 形态的部分**
   （`res/layout/autofill_*.xml` 等自动填充行）—— 如果将来做视觉回归，先查这几处。
4. **别为"M3E"改行为**：采纳清单里的每一项都应当是"等价替换"或"纯视觉增强"，
   任何需要改交互逻辑的（例如"改成 FAB 菜单"）属于**产品变更**，需用户单独拍板。
