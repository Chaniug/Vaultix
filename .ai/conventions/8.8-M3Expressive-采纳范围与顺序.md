## §0 结论（先记住这三句）

1. **借"理性的一半"**：间距标尺、表达式搜索、新进度指示器、按钮组的单选语义、
   tonal elevation、Styles API。
2. **不借"情绪的一半"**：形状变形、夸张动效、大字重 —— 与本项目已拍板的纪律
   **直接冲突**（`.ai/ISSUES.md` #87：转场只允许 `translationX`，用户明确"不要花里胡哨的动画"）。
   密码管理器的信任感来自**可预测**，情绪化动效在这里是负资产。
3. **成本几乎为零**：本项目 `material3 = 1.5.0-alpha16` **已经带了 M3E 全套 API**（§2 实测），
   所以这不是"要不要升依赖"，而是"要不要改 + 怎么验"。

## §4 采纳清单（按顺序做，一步一验）

### P0-1 间距标尺（8dp scale tokens） —— ✅ **已完成（2026-09-15）**

- **做什么**：新建 `ui/theme/Spacing.kt`（`xs=4 / sm=8 / md=12 / lg=16 / xl=24 / xxl=32`），
  然后**按文件**替换 540 处字面量。
- **为什么先做**：零视觉风险（值不变或只对齐到标尺）、直接消掉一类 bug、后续所有 UI 工作都受益。
- **注意**：替换时**只对齐到最近的标尺值**，不要顺手改版式 —— 换版式是"设计变更"，
  会与"零行为变化"的验收标准打架。
- **验证**：`detekt` + 编译 + 真机逐页目视（尤其设置页与条目页）。

**实测结果（第六十六轮）**

| 项 | 数字 |
|---|---|
| 手写 `.dp` 字面量总数 | **539** 处 / 43 个文件 |
| 其中**正好落在 8dp 标尺**上 | **373** 处（69%）→ 已替换 |
| 不在标尺上、保持原样 | 166 处（`0/2/3/6/10/18/20/22/28/36/40/44/48/72` 等） |
| 实际替换 | **369** 处 / 41 个文件（373 减去 `Spacing.kt` 自身 6 处定义值） |

- ⚠️ **`0.dp` 不进标尺**：它是"没有间距"这个语义本身，写成 `Spacing.zero` 反而绕。
- ⚠️ **替换后撞了 2 处 `MaxLineLength`**：`Spacing.lg` 比 `16.dp` 长，两行
  `PaddingValues(...)` / `Modifier.padding(...)` 撑到 121/123 字符 ⇒ 已拆成多行。
  **以后再做批量替换，跑完 detekt 要单独确认行长。**
- ✅ **等价性已用反演法证明**：把改后文件里的 `Spacing.*` 展开回数值 `.dp`，
  与 HEAD 版本逐行比对 —— **41 个文件全部逐字符一致**（`SettingsScreen.kt` 的差异
  经核验全部来自同轮的设置页重组，含 `.dp` 的差异行为 **0**）。
  ⇒ 这次是**纯等价替换，版式一个像素都没变**。

### P0-2 表达式搜索栏（contained search） —— ✅ **已完成（2026-09-15，只做观感）**

- **做什么**：把 `ItemsScreen` 的 `ItemsSearchBar` / `VaultixSearchTopAppBar` 换成 2026 的
  contained search 样式（常驻填充容器 + 尾部图标位）。
- **顺带好处**：**尾部图标位正好是"筛选入口"该待的地方** —— 可以顺手解掉
  「筛选入口放哪」的历史纠结（目前是点库名展开 + 顶栏胶囊）。
- **风险**：中（涉及搜索态与列表 inset 的联动，参考 `itemsTopInset` 的注释）。
- **验证**：搜索态的 inset 与"沉浸"效果不能退化（`ISSUES.md` #67 / #76 是这一带的坑）。

**实测结果（第六十六轮）**

- 改造点只有 `ui/common/SearchTopAppBar.kt` 的 `title` 槽：
  透明裸输入框 → `surfaceContainerHigh` **胶囊容器**（`RoundedCornerShape(28.dp)`）
  + 左侧搜索图标（`Icons.Filled.Search`）。
- ⚠️ **刻意没换成 alpha 的 `SearchBar` 组件** —— 本文档 §6① 明确要求
  「交互框架（AppBar / 搜索）等 beta/stable 再换」。这里用**稳定的 `TextField` 自绘同样的观感**，
  零 alpha API 依赖（`shape` 是 `TextField` 自 1.2 起的稳定参数）。
- ✅ **inset 一行没动**：容器高度固定 `56.dp`、外层仍是同一个 `TopAppBar`（64dp）
  ⇒ 调用方（`ItemsScreen.itemsTopInset` 等）的让位计算**完全不受影响**。
  这正是刻意的设计 —— #67 / #76 都是"让位算错"的坑，为换个样式去动 inset 不值得。
- ⏳ **"尾部图标位放筛选入口"没做**：那会引入一个新交互（属于**产品变更**），
  §6④ 写明"别为 M3E 改行为"。留在 §7 待用户拍板。

### P1-1 波浪进度指示器 —— ✅ **已完成（2026-09-15，落地 9 处）**

- **做了什么**：新建 `ui/common/ExpressiveProgress.kt` 作**唯一封装点**
  （`VaultixWavyProgress` / `VaultixWavyProgressBar`），替换全部**不确定态等待**语义：
  - 圆形 6 处：`UnlockScreen` 首帧 loading / `VaultixApp` SplashScreen / `TotpCodesScreen`
    / `AppPickerDialog` / `AutofillSaveActivity` / `ItemDetailScreen` 的 busy；
  - 线性 3 处：`ItemsScreen` 同步横幅（`SyncNote.InProgress`）/ `AddVaultScreen` /
    `AddKdbxScreen` 的提交中。
- **为什么封装而不是各处直调**：alpha API 的 `@OptIn` 只写两处；真机若不认可波浪，
  **改这两个函数体即可全部回退**，9 个调用点一行不用动。

**⚠️ 最重要的发现：尺寸是写死的，可替换范围远小于"32 处"**

解 sources 实测（不是推测）：波浪组件内部硬写 `.size(...)`，
**调用方传 `fillMaxWidth()` / `size(18.dp)` 都不会改变最终尺寸** ——
modifier 作用于外层 Box/Spacer，内部那次 `.size()` 覆盖了约束。

| | 老组件（同样写死） | 新波浪组件 | 差异 |
|---|---|---|---|
| Linear | `240.dp × 4.dp` | `240.dp × 10.dp` | **宽不变**，高 4→10（波浪需垂直空间） |
| Circular | `40.dp` | `48.dp` | +8dp |

⇒ 老 Linear 本来就写死 240dp，所以 `fillMaxWidth()` 对两者都无效、**替换是宽度等价的**；
但下列 3 类**不能换**（换了会坏，已实测排除）：

| 不换 | 原因 |
|---|---|
| 18dp / 20dp 内联小转圈（`UnlockScreen` ×2、`AddVault`、`AddKdbx`、`ImportExport`） | 会被撑到 **48dp**，把按钮与文案挤开 |
| 密码强度条（`ItemFormDialog`，`weight(1f)` 撑宽） | 波浪固定 240dp，`weight` 失效；且需读数 |
| TOTP 倒计时（`UnifiedProgressBar`） | 需**精确读数**（§4 原条目已排除） |

**准确签名（1.5.0-alpha16 sources，非 javap 推断）**

```kotlin
// 都带 @ExperimentalMaterial3ExpressiveApi ⇒ 调用方需 @OptIn
fun LinearWavyProgressIndicator(                 // 确定态
    progress: () -> Float, modifier: Modifier = Modifier,
    color: Color = ..., trackColor: Color = ...,
    stroke: Stroke = ..., trackStroke: Stroke = ...,
    gapSize: Dp = ..., stopSize: Dp = ...,
    amplitude: (progress: Float) -> Float = ...,  // 振幅可随进度变化
    wavelength: Dp = ..., waveSpeed: Dp = wavelength,
)
fun LinearWavyProgressIndicator(                 // 不确定态（本项目用的这个）
    modifier: Modifier = Modifier, color: Color = ..., trackColor: Color = ...,
    stroke: Stroke = ..., trackStroke: Stroke = ..., gapSize: Dp = ...,
    amplitude: Float = 1f, wavelength: Dp = ..., waveSpeed: Dp = wavelength,
)
// CircularWavyProgressIndicator 同构（无 stopSize）；容器固定 48.dp
```

- 两个重载**不会歧义**：确定态的 `progress` 是必需参数，只传 `modifier` 只会命中不确定态。
- ⚠️ 旧笔记里写的 `wavePhase` 参数**在 alpha16 里不存在**（javap 时凭 `...` 猜错了），
  以本表为准。
- 未用 `LoadingIndicator` / `ContainedLoadingIndicator`：其 `polygons: List<RoundedPolygon>` 需
  新增 `androidx.graphics:graphics-shapes` 依赖（当前没有）⇒ 性价比不如 Wavy。

**验证**：detekt 全量真跑通过（用 `LongMethod.allowedLines=30` 探针确认它真在扫描，129 条）；
编译由 CI 兜底；**真机目视待用户验收**（尤其解锁页冷启动那个转圈）。

## §6 坑与边界（写之前先看）

1. **它是 alpha16**：建议**只用于叶子组件**（进度指示器、间距 token、Styles API），
   **交互框架**（AppBar / 搜索）等 beta/stable 再换。理由：alpha 的 API 会改名/改语义，
   而 AppBar 这种"框架级"替换的成本随 API 变动线性上升。
2. **动态取色 ≠ 品牌色**：本项目 UI 走 Material You（跟随壁纸），**品牌色只允许出现在
   两个地方** —— 应用图标（`res/values/colors.xml` 的 `ic_launcher_*`）与首启页的两个
   入口按钮（`VaultListScreen` 的 `BITWARDEN_BRAND_BLUE` / `KDBX_BRAND_GOLD`，
   2026-09-14 加）。**不要**为了"M3E 的鲜艳配色"把品牌色铺进普通 UI。
3. **M3E 是 Android 16 才成为默认的**，但本项目 `targetSdk = 37`：系统侧已在按新口径
   渲染。Compose 组件自带样式，受影响的主要是**XML/View 形态的部分**
   （`res/layout/autofill_*.xml` 等自动填充行）—— 如果将来做视觉回归，先查这几处。
4. **别为"M3E"改行为**：采纳清单里的每一项都应当是"等价替换"或"纯视觉增强"，
   任何需要改交互逻辑的（例如"改成 FAB 菜单"）属于**产品变更**，需用户单独拍板。
5. ★ **edge-to-edge 的"渐变保护层"（2026-09-20 第五轮，`FullScreenDialogShell`）** ——
   M3 并没有给"沉浸式栏"提供现成组件，官方给的是**布局指南**，不是 API。两条要记住的：
   - **Do**：栏不吸顶时加**与背景匹配的渐变**保护层；系统栏半透明，UI 从下方滚过。
     Compose 里的写法就是 `Modifier.drawBehind { drawRect(Brush.verticalGradient(...)) }` ——
     **零额外布局节点**、渐变天然跟随宿主尺寸，比嵌一个 `Box(Modifier.background(brush))` 干净。
   - **Don't**：① 渐变**与各 pane 背景不匹配**（端点色必须用 `colorScheme.surface`，
     而正文卡片常是 `surfaceContainerHighest`，**不同色**）；
     ② **叠加**多层 status bar 保护（只有**一层**渐变，不加 scrim、不加第二层色块）。
   - ⚠️ **三档 ≠ 两档**：`不透明段 = 系统栏 inset + 栏体高`，之后才是过渡尾段。
     两档会让栏体上半段就半透明 ⇒ 标题读不清。比例**必须按实测 inset 算**（写死会翻车）。
   - ⚠️ **别用 `Modifier.blur` 当保护层**：minSdk 26 的 API 31- 是 no-op；离屏渲染掉帧耗电；
     OLED 下模糊纯黑**仍是纯黑**。渐变不需要采样本层之外的内容。
   - ⚠️ **M3 的 `BottomAppBarDefaults.exitAlwaysScrollBehavior()` 可以只借状态机**：
     取它的 `nestedScrollConnection` + `heightOffset`，**不用** `BottomAppBar` 组件本体
     （组件默认 `containerColor = surfaceContainer` 与渐变端点不匹配、自带 `windowInsets`
     会与自建让位体系双重叠加）。这是"用 M3 的机制、不用 M3 的外观"的一个可用范式。
   - ⚠️ **`Dialog` 里的系统栏是另一套**：`Dialog` 窗口类型是 `TYPE_APPLICATION_PANEL`，
     **不继承** Activity 的 edge-to-edge；其 window background 来自主题（= 黑）。
     且 `targetSdk ≥ 35` 起 `window.statusBarColor` / `navigationBarColor` **是 no-op**。
     `Dialog` 里要改窗口层只能用 `window.setBackgroundDrawable(...)`，
     `decorView.setBackgroundColor` 改不到。详见 `issues/06-界面与交互.md` #107。
