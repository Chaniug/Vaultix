#### 🔴★ 沙箱 GitHub 通道的完整修法（2026-09-17 排查定案，已固化为脚本）

> 症状：`kex_exchange_identification: Connection closed by remote host`，
> 而且**时通时不通**，很容易被误判成「网络抖动」而反复重试。
> 实际是**两层独立的坑叠在一起**，缺一不可。脚本在 `tools/ci/`：
> `github-channel-check.sh`（通道自愈 + 自检）、`ghp.sh`（推送封装）、
> `ssh-config.sample`、`README.md`（症状对照表）。

**坑 1：`/etc/hosts` 会被重置。** 重置后 `ssh.github.com` 解析到 `198.18.0.39`。
⇒ `github-channel-check` 会从阿里 DoH 查真实 IP 并写回。

**坑 2（★ 真正的根因，最反直觉）：`HostName` 写域名会绕过 hosts。**
即使 hosts 里已经写对 `20.205.243.160 ssh.github.com`，
只要 ssh config 里是 `HostName ssh.github.com`，openSSH 仍会**自己解析这个名字**
⇒ 绕过 hosts ⇒ 又回到 `198.18.0.39`。`ssh -v` 会把目标 IP 打出来，
**这是唯一能看出差别的地方**（只看报错完全看不出）。
⇒ **`HostName` 必须写 IP**：`github.com` = `20.205.243.166`，
`ssh.github.com` = `20.205.243.160`。改完后 **22 与 443 两个端口都能认证通过**。

**坑 3：不要在命令行堆 `-o HostName=...`。**
它会**覆盖** config 里 `Host github.com` 的 `HostName`，把修好的配置换回域名
⇒ 立刻复现坑 2。既然 config 写好了，命令行什么都别传。

**坑 4（第二个独立故障）：`~/.gitconfig` 的 URL 重写劫持 SSH。**
```ini
[url "https://github.com/"]
    insteadOf = git@github.com:
```
它把 `git@github.com:Chaniug/Vaultix.git` 改写成 HTTPS，而 HTTPS 在沙箱里依赖
`git-credential-helper` —— 该端点返回 `404 {"msg":"git credentials not found in space labels"}`，
**沙箱环境未适配** ⇒ 必然失败。这与坑 1–3 是两个**完全独立**的故障，
但症状都是「push 不动」，极易混淆。
⇒ `ghp` 的做法：临时 `--unset-all` 掉重写 → 用 SSH 推 → **无论成败都还原**（`trap EXIT`）。

**坑 5：`api.github.com` 有间歇性封锁，但它不该拦推送。**
实测：同一命令 `curl https://api.github.com/rate_limit` **6/6 全 200**，
两分钟后**稳定全 000**（`curl: (35) SSL_connect: SSL_ERROR_SYSCALL`），
再等一会儿又恢复。这是**环境策略**，不是配置问题，重试只能过滤瞬时抖动。
⇒ **依赖分层**：`ghp` 只把 **SSH 认证**当硬门槛（那才是 push 真正走的通路），
REST API 只服务「读 CI 状态」这类可选增强，失败**只警告不退出**。
`github-channel-check` 同理。验证：API 完全不可用期间 `ghp` 仍成功推送。

**坑 6（脚本自身的写法坑，连续栽了三次）**：
`ssh -T git@host | grep -q "..."` 这种写法**会丢状态** ——
`grep -q` 匹配到就退出，`ssh` 收到 **SIGPIPE** 返回非 0 ⇒ `if` 判失败。
实测 443 备用通道的 banner 明明是 `Hi Chaniug! ... successfully authenticated`，
却被报成「不可用」。**一律改成 `out=$(ssh ... 2>&1)` 再 `grep`**。
（同类坑：`curl | grep` 也会丢 `curl` 的退出码。）

**自检脚本必须能自证可用**：`github-channel-check` 全绿时输出
「hosts 已修复 / SSH 认证通过 / 443 备用通道可用 / REST API 额度」，
`-q` 静默模式返回 0 且无输出（供 `ghp` 内部调用）。

#### 🔴★ HTTPS 与 SSH 是**两条独立通路**，限流只打 HTTPS（2026-09-17 实测）

> **这是本轮最容易误判的一点：`git push` 能成，不代表 HTTPS 能下东西；
> 反过来 HTTPS 全红，也不代表推送有问题。** 排查时务必先分清是哪条通路。

| 通路 | 目标 | 实测状态 |
|---|---|---|
| **SSH** | `git@github.com`（22 或 ssh.github.com:443） | ✅ **稳定可用**，`ghp` 全程没失败过 |
| HTTPS | `github.com:443`（release 资产下载） | ❌ **强限流**：连打 8 次只有 3 次 206 |
| HTTPS | `api.github.com` | ⚠️ 间歇性：6/6 全 200 ↔ 稳定全 000 |
| HTTPS | `codeload.github.com` | ✅ 301（正常） |
| HTTPS | `raw.githubusercontent.com` | ✅ 301（正常） |

失败形态一律是 `curl: (35) OpenSSL SSL_connect: SSL_ERROR_SYSCALL`，
**且成功率随时间衰减**（前 4 次约 2 成、后 4 次约 1 成）。

⇒ **应对：`tools/ci/fetch-release-asset.sh`**（断点续传下载器）。
核心设计：
- **不探长度**。探长度本身也是碰运气的请求，而且有两个陷阱：
  1. 重定向链产生**两段 header** —— 第 1 段是 `github.com` 的 302
     （`content-length: 0`，**无 `content-range`**），第 2 段才有
     `content-range: bytes 0-0/35883835`。⇒ 必须取**最后一段**。
  2. ★ `curl -D - | grep | tail | sed` 这种**一行式管道会偶发返回空串**。
     完全相同的命令分步执行能拿到值，写成一行就拿到空 ——
     `grep` 匹配后提前退出，`curl` 写 header 时收到 **SIGPIPE**。
     ⇒ 若要探长度，必须 `-D <文件>` 落盘再读，**彻底不用管道**。
- 小分块（256KB）+ 每块重试 25 次 + 断点续存，用概率熬过成功窗口。
- **完整性与「字节数吻合」是两件事**：限流下的一次半截写入可能凑巧凑够长度，
  所以必须用 `zipfile.testzip()` 做全量校验（APK 本质是 zip），
  **不许因为 `stat` 字节数对就宣布「已验证可下载」**。

`github-channel-check` 的另一种自身缺陷（也踩了）：**删除旧 hosts 记录与
写入新记录不原子**。旧实现里 `release-assets` / `objects` / `raw.githubusercontent`
的新 IP 依赖 DoH，DoH 一挂 ⇒ 新记录为空 ⇒ 旧记录被删掉且没补上 ⇒
域名回落 `198.18.x`。实测症状：跑完 `github-channel-check -q` 后，
`release-assets` 反而**从可用变成 `198.18.0.43`**，导致下载「探不到总长度」。
⇒ 修法：这三个 fastly 域名的 IP 改用公开稳定常量 `185.199.108-111.133`（不走 DoH），
且替换条件收紧为「新记录非空才写」。

### 8.7 沙箱内跑 detekt 门禁（2026-09-15 打通，**无 Android SDK 也能跑**）

> 场景：沙箱/Linux 里 `dl.google.com` 与 `services.gradle.org` **都不通** ⇒
> 拿不到 Android SDK、也无法 gradle 构建（**编译这一环节只能留给用户本机**）。
> 但 **detekt 是可以真跑的**，这已经能挡住 LongMethod / MaxLineLength /
> LargeClass / TooManyFunctions / NoUnusedImports 这几类门禁问题。

- **取 detekt CLI**（官方 zip，含全部依赖；走 ghfast 镜像，约 76MB）：
  ```bash
  curl -sSL -o detekt.zip \
    https://ghfast.top/https://github.com/detekt/detekt/releases/download/v2.0.0-alpha.6/detekt-cli-2.0.0-alpha.6.zip
  unzip -q detekt.zip && chmod +x detekt-cli-2.0.0-alpha.6/bin/detekt-cli
  ```
  ⚠️ 腾讯 maven 上的 `detekt-cli-*-all.jar` 是 **404**，别在那儿找；release 的 tag 必须带 `v` 前缀。
- **跑法**（`--build-upon-default-config` 必须与 CI 一致，否则阈值口径不同）：
  ```bash
  ./bin/detekt-cli -c config/detekt/detekt.yml --build-upon-default-config \
    -i app/src/main/java
  ```
  无输出 = 全绿；有问题会打印 `e: <路径>:<行> ... [规则名]` 并以非 0 退出。
- **它查不了什么**：`light` 模式下不做类型解析 ⇒ **编译错误、API 签名错误一律查不出**。
  别把 detekt 全绿当成"能编译"（`8.6` 那条「detekt 先于 compile 会掩盖编译错误」同理）。
- **验证它真的扫到了文件**（避免"空跑全绿"的假象）：临时把 `allowedLines: 150` 改成 `30`
  再跑一次，应当报上百处 —— 报得出来才说明输入是对的。

  - 密码：同目录 `vaultix-signing-passwords.txt`（`STORE_PASSWORD` / `ALIAS`；`JKS` 是路径）
  - base64 备份：`vaultix-keystore-b64.txt`
  - 证书 SHA-256：`7e6c8c073d0c1a3b8fd8acf6e5d070acd73fdaf2986ca717de27183f395c1fd8`
- ⚠️ ★ **密码文件里的 `KEY_PASSWORD` 是错的**：实测 **key 密码 == `STORE_PASSWORD`**。
  照文件里的值填会报
  `UnrecoverableKeyException: ... Given final block not properly padded / Wrong password?`
- 流程（用 `build-tools/37.0.0`）：

  ```bash
  BT="/c/AndroidSDK/build-tools/37.0.0"
  # 1) 对齐
  "$BT/zipalign.exe" -p -f 4 app-full-debug.apk aligned.apk
  # 2) 重签（密码走 env，别落在命令行里）
  export KS_PW='<STORE_PASSWORD 的值>'
  "$BT/apksigner.bat" sign --ks "D:/vaultix-release.jks" --ks-key-alias vaultix \
    --ks-pass env:KS_PW --key-pass env:KS_PW --out signed.apk aligned.apk
  # 3) 核证签名
  "$BT/apksigner.bat" verify --print-certs signed.apk   # 应见 CN=Vaultix
  ```

- ⚠️ ★ **git-bash 的 `/d/...` 路径对 Windows 原生工具无效**：
  `keytool -keystore /d/vaultix-release.jks` 会报「密钥库文件不存在」——
  必须传 `D:/vaultix-release.jks`。**与 `adb pull` 那条是同一个坑**。
- ★ **装完必须核证，别只信 `install` 的 "Success"**：
  `pm path` 拉回设备上的 APK，与本地签名产物**比 SHA-256**（一致才算装上）。
- 装前先确认 `isKeyguardShowing=false`（**锁屏时 install 会被拒**，
  且重跑时输出可能只剩空白行，看着像成功 —— 这个坑踩过）。
- `versionCode` 相同即可覆盖安装：`applicationIdSuffix` 被**刻意去掉**
  （见 `app/build.gradle.kts`），保证 debug 与 release 能互相覆盖。
- ⚠️ 装机后 `am start` 若提示「intent has been delivered to currently running
  top-most instance」⇒ 旧进程还在，**先 `am force-stop` 再冷启动**，
  否则验的不是新代码。
