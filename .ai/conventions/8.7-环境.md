### 8.7 环境
- **本机（Windows / WorkBuddy）**：JDK 17 + Android SDK（`C:\AndroidSDK`）+ `gh` CLI **全部可用**
  ⇒ 可本地 gradle 构建、可直接 `git push`、可 `gh run view` 查 CI
- Git Bash 下 `./gradlew` 报「找不到主类 GradleWrapperMain」⇒ 用
  `java -classpath "D:/Vaultix/gradle/wrapper/gradle-wrapper.jar" org.gradle.wrapper.GradleWrapperMain <task>`
  或直接 `~/.gradle/wrapper/dists/gradle-9.5.1-bin/*/gradle-9.5.1/bin/gradle`；
  daemon 配额耗尽先 `--stop`
- **本地验证链（≈ CI push 门禁）**：`detekt`（全模块）→ `:app:compileFullDebugKotlin` →
  `:app:assembleFullDebug` → 相关模块单测
- ⚠️ 沙箱**缺 NDK** ⇒ `assembleFullDebug` 的 native 符号剥离会失败（与代码无关，CI 正常）
  ⇒ 替代验证用 `:app:compileFullDebugKotlin`
- 沙箱内 GitHub 推送（**仅供沙箱参考**）：GitHub 被解析到 `198.18.0.x` ⇒ 用阿里 DoH
  （`https://223.5.5.5/resolve?name=github.com&type=A`）写 hosts + `~/.user_hosts`；
  SSH over 443（`HostName ssh.github.com` / `Port 443`）；HTTPS 推送不可行
- ⚠️ 沙箱查 CI：`api.github.com` 直连可用（匿名额度够用），`runs` / `jobs`
  端点都能读 ⇒ 能拿到 status / conclusion / 每个 step 的成败。
  **但 `/actions/jobs/<id>/logs` 拿不到**（2026-09-17 实测）：
  返回 `403 {"message":"Must have admin rights to Repository."}` ——
  沙箱既没登录 `gh`，也没有 GitHub token（`git-credential-helper` 的端点
  `http://git.auth-proxy.local/api/v1/git/credentials?host=<host>` 返回
  `{"code":404,"msg":"git credentials not found in space labels"}`）。
- ★ **拿不到原始日志时的替代办法（2026-09-17 实测有效）**：
  用 **WebFetch 读 CI 运行页** `https://github.com/<owner>/<repo>/actions/runs/<id>`。
  GitHub 会把每条 Kotlin `e:` 编译错、每个 `Caused by:`、以及 Gradle 的
  `What went wrong` 都放进页面的 **"Annotations"** 区块 ⇒ 实测两次都靠它
  拿到了完整、逐字的错误文本。**别因为 `/logs` 是 403 就放弃诊断而盲目重推。**
  精度提示：`annotations` 里的 `Caused by` 是**倒序**的（最外层在最下面），
  读的时候从下往上才是真正的因果链。
- ⚠️ 沙箱查 CI 的旧记录（保留）：`api.github.com` 曾会 EOF 或被 301 到 `github.com`
  ⇒ 那时要 **hosts 写 `140.82.121.6 api.github.com`**（`140.82.112.4 github.com`），
  之后 `GH_TOKEN=... gh run list/watch/view --repo Chaniug/Vaultix` 即可
  （remote 是 ghfast 镜像，`gh` 认不出 host，必须带 `--repo`）。
  2026-09-17 实测 `20.205.243.168 api.github.com` 亦可。
- ⚠️ **沙箱拿不到 Android SDK（2026-09-17 复核，仍然是死路）**：
  `dl.google.com` / `maven.google.com` / `services.gradle.org` 全被解析到
  `198.18.0.x`（保留网段占位）⇒ `SSL_ERROR_SYSCALL`、`http=000`。
  **即使按本文 §18 的做法用阿里 DoH 查出真实 IP 写进 hosts，也仍然不通**
  （这几个域名的真实 IP 在本沙箱网络下不可达，与 GitHub 的情况不同）。
  ⇒ `app` 模块的编译**只能留在 CI**，别在沙箱里耗时间。
  替代手段见下一条。
- ★ **无 Android SDK 时查「缺失 import」的常备手段（2026-09-17 新建）**：
  脚本 `/tmp/kc/checkrefs.py`。原理：扫描 Kotlin 文件的**未限定** CamelCase 引用
  （前面不是 `.`），与本仓 `io.vaultix.*` 的顶层/嵌套声明索引对照，
  排除 KDoc / 行注释 / 字符串字面量 / 本文件自身声明 / 同包 / `import x.*` / Kotlin 内建名。
  用法：`python3 /tmp/kc/checkrefs.py`（只查本轮改动）或 `--all`（全仓）。
  ⚠️ **它不查签名不匹配、泛型、重载解析** —— 那些仍然只能靠 CI。
  ⚠️ 三引号字符串 `"""..."""` 会漏过（行级正则只处理单引号对）⇒ 有误报是正常的，
  看到可疑项**必须人工确认那行是代码还是字符串**。
  为什么需要它：`910b571` 里 `VaultListViewModel` 新增了 `KdbxSyncRepository`
  构造参数却没 import，而 KSP/Hilt 的报错是
  `could not be resolved` —— 读起来像依赖图问题，实际只是少了 import。
- ⚠️ **下 release 资产（APK）是第三个被劫持的域名，2026-09-15 踩到**：
  `gh release download` 会 302 到 `release-assets.githubusercontent.com`，
  而该域名被解析到 `198.18.0.22`（**保留网段，实为代理占位**）⇒ 连接 EOF，
  `curl` 直接 `http=000`。`gh release view` 却正常（它只走 API，不碰 CDN）
  ⇒ **「资产大小对得上」不等于「能下下来」**，别用前者替代后者。
  修法（已写入 `/etc/hosts`）：真实 IP 是 `185.199.108~111.133`，
  `release-assets.githubusercontent.com` 与 `objects.githubusercontent.com`
  **共用这一组**：
  ```bash
  # 查真实 IP（阿里 DoH，沙箱可用）
  curl -s "https://dns.alidns.com/resolve?name=release-assets.githubusercontent.com&type=A"
  # 然后写入 /etc/hosts：185.199.108.133 / .109 / .110 / .111 各一行，两个域名都给
  ```
  `objects.githubusercontent.com` 也要写 —— 它是 GitHub 各类
  用户内容（LFS、附件）的同一套 CDN，迟早会遇到。
  ⚠️ **2026-09-16 复现：这条 hosts 记录会丢**（沙箱重置 / 换 session 后没了），
  症状与上次一模一样（`getent hosts release-assets...` 又是 `198.18.0.x`）。
  ⇒ **每次要下 APK 前先 `getent hosts release-assets.githubusercontent.com` 确认一次**，
  别默认它还在。检查口径：看到 `198.18.0.x` 就是丢了。
- 🔴 **即使 hosts 正确，沙箱也未必能完整下到 APK（2026-09-16 新证据）**：
  hosts 修好后仍然三次失败 ——
  ① 240s 只到 3.4MB（超时截断）；② 900s 超时那次直接 `http=000`（0 字节）。
  **但同一 URL 用 range 请求 `curl -r 0-0` 拿得到 `http=206` + 正确 1 字节**
  ⇒ **CDN 可达且有数据，是「整文件连续传输」在沙箱网络下不可靠**。
  应对：**1MB 分块 + 每次 5 重试 + 失败 `truncate -s <已确认偏移>` 回滚**
  （脚本形态见 `/tmp/fetch_apk.sh` 的写法：探 `Content-Range` 拿总长 →
  逐块 `-r off-end` 追加 → 每块后校验 `stat -c%s`）。
  ⚠️ 若分块仍拿不到完整 zip，**结论只能写「release 已发布，沙箱未能完整验证」**，
  **不许因为 `gh release view` 看得到资产就写成「已验证可下载」**
  （issues #102：`gh release view` 只走 API，不过 CDN，两者必须分开验证）。
- ⚠️ 沙箱 `assembleFullDebug` 的 **dex 阶段会偶发「Gradle daemon disappeared」**
  （并发越高越易触发，与代码无关）⇒ 用 `--max-workers=1` 稳定跑通
- 沙箱无 Android SDK 时，可用 Gradle 自带的 `kotlin-compiler-embeddable-2.2.21.jar`
  真实编译纯 JVM 模块的 `.kt` 并跑断言 —— **验证真正会编译进 App 的那份代码**，
  胜过「内联逻辑副本」；Compose 文件可用 API 桩（`Modifier` 桩必须写成
  `interface Modifier { companion object : Modifier }`）
- **能在本地跑的实验就不要靠推理排除** —— 一轮脚本胜过三轮 CI 试错

### 8.7 沙箱内跑 detekt 门禁（2026-09-15 打通，**无 Android SDK 也能跑**）

> 场景：沙箱/Linux 里 `dl.google.com` 与 `services.gradle.org` **都不通** ⇒
> 拿不到 Android SDK、也无法 gradle 构建（**编译这一环节只能留给用户本机**）。
> 但 **detekt 是可以真跑的**，这已经能挡住 LongMethod / MaxLineLength /
> LargeClass / TooManyFunctions / NoUnusedImports 这几类门禁问题。

- **取 detekt CLI**（官方 zip，含全部依赖；走 ghfast 镜像，约 76MB）：
  ```bash
  curl -sSL -o detekt.zip \
    https://ghfast.top/https://github.com/detekt/detekt/releases/download/v2.0.0-alpha.6/detekt-cli-2.0.0-alpha.6.zip
  unzip -q detekt.zip && chmod +x detekt-cli-2.0.0-alpha.6/bin/detekt-cli
  ```
  ⚠️ 腾讯 maven 上的 `detekt-cli-*-all.jar` 是 **404**，别在那儿找；release 的 tag 必须带 `v` 前缀。
- **跑法**（`--build-upon-default-config` 必须与 CI 一致，否则阈值口径不同）：
  ```bash
  ./bin/detekt-cli -c config/detekt/detekt.yml --build-upon-default-config \
    -i app/src/main/java
  ```
  无输出 = 全绿；有问题会打印 `e: <路径>:<行> ... [规则名]` 并以非 0 退出。
- **它查不了什么**：`light` 模式下不做类型解析 ⇒ **编译错误、API 签名错误一律查不出**。
  别把 detekt 全绿当成"能编译"（`8.6` 那条「detekt 先于 compile 会掩盖编译错误」同理）。
- **验证它真的扫到了文件**（避免"空跑全绿"的假象）：临时把 `allowedLines: 150` 改成 `30`
  再跑一次，应当报上百处 —— 报得出来才说明输入是对的。

### 8.7 本地出包 + 重签 + 装机（2026-09-16 打通）

> ⚠️ **签名不一致 = 数据全丢**（系统会拒绝覆盖安装，只能卸载重装）。
> 设备上装的是**项目自有签名**，而 `assembleFullDebug` 产出的是 **debug 签名**
> ⇒ **每次装机都必须重签**。

- ★ **签名密钥不在仓库里**（这是有意的：仓库公开）：
  - keystore：`D:\vaultix-release.jks`，别名 `vaultix`
  - 密码：同目录 `vaultix-signing-passwords.txt`（`STORE_PASSWORD` / `ALIAS`；`JKS` 是路径）
  - base64 备份：`vaultix-keystore-b64.txt`
  - 证书 SHA-256：`7e6c8c073d0c1a3b8fd8acf6e5d070acd73fdaf2986ca717de27183f395c1fd8`
- ⚠️ ★ **密码文件里的 `KEY_PASSWORD` 是错的**：实测 **key 密码 == `STORE_PASSWORD`**。
  照文件里的值填会报
  `UnrecoverableKeyException: ... Given final block not properly padded / Wrong password?`
- 流程（用 `build-tools/37.0.0`）：

  ```bash
  BT="/c/AndroidSDK/build-tools/37.0.0"
  # 1) 对齐
  "$BT/zipalign.exe" -p -f 4 app-full-debug.apk aligned.apk
  # 2) 重签（密码走 env，别落在命令行里）
  export KS_PW='<STORE_PASSWORD 的值>'
  "$BT/apksigner.bat" sign --ks "D:/vaultix-release.jks" --ks-key-alias vaultix \
    --ks-pass env:KS_PW --key-pass env:KS_PW --out signed.apk aligned.apk
  # 3) 核证签名
  "$BT/apksigner.bat" verify --print-certs signed.apk   # 应见 CN=Vaultix
  ```

- ⚠️ ★ **git-bash 的 `/d/...` 路径对 Windows 原生工具无效**：
  `keytool -keystore /d/vaultix-release.jks` 会报「密钥库文件不存在」——
  必须传 `D:/vaultix-release.jks`。**与 `adb pull` 那条是同一个坑**。
- ★ **装完必须核证，别只信 `install` 的 "Success"**：
  `pm path` 拉回设备上的 APK，与本地签名产物**比 SHA-256**（一致才算装上）。
- 装前先确认 `isKeyguardShowing=false`（**锁屏时 install 会被拒**，
  且重跑时输出可能只剩空白行，看着像成功 —— 这个坑踩过）。
- `versionCode` 相同即可覆盖安装：`applicationIdSuffix` 被**刻意去掉**
  （见 `app/build.gradle.kts`），保证 debug 与 release 能互相覆盖。
- ⚠️ 装机后 `am start` 若提示「intent has been delivered to currently running
  top-most instance」⇒ 旧进程还在，**先 `am force-stop` 再冷启动**，
  否则验的不是新代码。
