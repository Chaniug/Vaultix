## §1 金标联盟 SharedView Kit 适配评估（未落地）

**回答「一镜到底达成度多少、兼容代价多大、为什么没接」**

标准本体：2026-10 金标联盟（ITGSA）发布 **SharedView Kit**，荣耀 / OPPO / vivo / 小米联合推动；
不是认证条款，是一套 Kit。官网 `itgsa.com/home/union/openness`，Demo `gitee.com/itgsa_sharedviewkit/SharedViewDemo`。

| Kit 事实（读 README 实证） | 值 |
|---|---|
| 依赖 | `gsai.sdk:sharedview-kit:+`，`http://` 明文 Nexus（官方注明内测、正式前升 HTTPS） |
| 产物 | **闭源 aar**，编译期给类型、运行时由设备 ROM 提供实现 |
| 核心 API | `makeViewAnimationOptions(View / Bitmap, …)` → `startActivity(intent, ActivityOptions)`；返回前 `overrideViewAnimationTransition()` + `finish()` |
| 硬要求 | 运行时能力检测（返回 0 回退普通启动）、bounds 的 SCREEN / WINDOW 坐标系读设备 metadata、`color` 取落点列表底色、目标丢失兜底 |
| 要求 minSdk | ≥ 26（项目 26，满足） |

⇒ **它是 Activity 间 / View 快照模型，不是 Compose Navigation 的共享元素。**

项目现状：`MainActivity` 单 Activity + `NavHost`（24 条类型安全路由，navigation-compose 2.10.2）；
另 10 个 Activity 全是 autofill / passkey / MSAL OAuth 回调，没有 UI 详情页；
全仓 `SharedTransitionLayout` / `sharedElement` / `sharedBounds` **零命中**；
`NavHost` 四向转场统一 `tabSwitchEnter/Exit`（140ms 高起步 fade）、`sizeTransform = null`。

**达成度**：按 Kit 的六项验收口径约 **0–1 成**（仅「降级意识」可迁移）；
按「转场不闪、不卡、不缩小、尊重减少动效」的体验口径约 **7 成**。两者不矛盾，是目标不同。

三条路线：

| 路线 | 阻力 | 结论 |
|---|---|---|
| A 忠实接 Kit：拆详情为独立 Activity | 碰「认证 Activity 必须留在默认 task」保命纪律；闭源二进制 + HTTP + 动态版本 `+` 破坏可复现构建；Kit 自动截卡片 View 的图而列表是密码条目；仅四家部分 ROM 生效 | ★★★★★ 不建议 |
| B 只用 Bitmap 源、不拆 Activity | `makeViewAnimationOptions` 仍返回 `ActivityOptions`，**绕不开 `startActivity`** | 收益近零 |
| C 不接 Kit，用 Compose 原生共享元素 | 版本够；但须先由用户解除 #87，并复核 `sizeTransform = null`（为修「返回缩小 1~2 帧」禁容器尺寸补间，与共享元素的边界补间方向相反） | ★★★★ 若只想要手感，走这条 |

**两条容易高估达成度的地方**：`Docs/07` §5 与 `Docs/16` **写了**「页面切换用共享元素」，
实现从未落地（设计期蓝图滞后）；`VaultixApp.kt:180` 注释仍写「`fadeIn + slideInVertically(1/16)`」，
而 `TabTransitions.kt` 早已删掉位移只留 fade —— 注释漂移，别照注释判断现状。

## §2 第六批取证：短板在哪

**回答「用户说『美观度』『表现形式』『点击没区别』，代码里对应什么」**

| 反馈 | 实证 | 性质 |
|---|---|---|
| 新建/编辑页输入框表现形式单调 | `ItemFormDialog.kt` 共 **16 个 `OutlinedTextField` 全同规格**，除密码有 `EmphasisBlock` 淡底外无任何区分；字段名统一走 `FormFieldLabel` | 结构性 |
| 各参数输入框 | `UriListEditor` 的 label 是**多行 `Text(stringResource(...))`**，没走 `FormFieldLabel` ⇒ 默认 `bodyLarge`(16sp)，是 8.4 §74「全表字段名 14sp」**漏掉的一处层级倒挂** | 真 bug（漏网） |

（会重现「点一个、旁边跟着闪」），不是「单个 tab 按下期间的即时反馈」。当年被一刀切掉了。

## §4 底栏按压反馈（解除搁置的范围）

**回答「怎么让玻璃态下看得见按下，又不重现『旁边跟着闪』」**

- `DockTabItem` 订阅 `interactionSource.collectIsPressedAsState()`；
  `animateFloatAsState(0.94f, tween(90ms))` 驱动 `graphicsLayer { scaleX/scaleY }`。
- press 时 pill 换**具名实色档**：选中 → `primaryContainer`、未选中 → `surfaceContainerHigh`；
  松手即回。玻璃态下 ripple 会被半透明层吃掉，实色 pill 才看得见。
- **选中色仍瞬切**、保持 `indication = null`、`clickable` 复用同一个 `interactionSource`；
  `key(item)` 保证组合槽稳定 ⇒ press 只改被按的那一个，不扩散到兄弟节点。
- 常量收进 `const val`（`DOCK_PRESS_SCALE` / `DOCK_PRESS_DURATION_MS`），避免 `MagicNumber` 门禁。

**搁置解除的边界**：11-06 §5「明确搁置液态玻璃点击动效（按压反馈 / lens / 弹性）」，
本日用户反馈「点击没什么区别，尤其液态玻璃下」⇒ **放行按压反馈一项**；
lens 拖动、jelly 弹性、goo 融合、页面转场仍属搁置，且后两类与 #87 直接冲突。
这是**组件内按压反馈**，8.4 part1 已判「M3 组件自带动效与 #87 不冲突」。

## §5 可复用判据

**回答「下轮遇到同类问题该先问什么」**

1. 「点击没反应」先查 `indication` 与 `MutableInteractionSource` 是否被订阅，别急着加动画。
2. 「禁动画」的结论要分清**作用域**：选中态跨项渐变 ≠ 单项按压反馈，一刀切会误伤。
3. 玻璃 / 半透明层上，ripple 与 alpha 叠加都可疑 ⇒ 用**具名色档换色**做瞬时状态。
4. 「表现形式单调」优先找已存在的共用槽位（`leadingIcon` / `trailingIcon` / `supportingText`）加增量。
5. 批量替换必须**先断言匹配次数**：本日第一次脚本因 `UriListEditor` 的多行 label 少匹配 1 处而停下，
   正是断言挡住了静默漏改；第二次因 `ContentCopy` 有 4 处写法而停下，同样靠断言定位。
6. 本机不能编译（AGP 9.5.0 / Gradle 9.8.2 缺口）⇒ 静态核对 + push `main` 交 CI，不跑 `./gradlew`。

## §7 KDBX 同步死锁：显示「已同步」却永远保存不了

**回答「为什么点同步也没用、怎么修才不会覆盖另一台设备的改动」**

- 真机取证：电脑 KeePassXC 与手机连**同一个 OneDrive KDBX**（用户提供 ADB
  `192.168.1.113:40131`，BKQ-AN00）。手机显示已同步 → 改条目 → 保存提示
  「云端有更新还没拉下来，请先同步」→ 同步后再改仍一样。
  脱离会话录 logcat：17:47:54 有「派生密钥写入缓存（保存路径）」，
  之后**无任何落盘 / 上传日志** ⇒ 在写回闸门被拒，改动未落盘，**数据没丢**。

- 根因三连：
  ① `KdbxBaseStore` 文件头契约「基线 null = 不知道 ⇒ 放行，交给版本令牌兜底」，
     但 `mutateLocked` 里 `null == fingerprint` 得 `false`，
     旧闸门 `if (!write.baselineAligned) throw StaleBaseline` 见 false 就拦；
  ② 基线是纯内存 `ConcurrentHashMap`（锁库 / 冷启动即清），
     而 UI 的「已同步」来自持久化 `vaults.syncStatus` ⇒ **两者不同源**；
  ③ `KdbxSyncOrchestrator` 判定「两边都没改」走 `AlreadyInSync` 捷径，

     **不调** `adoptRemoteIfSameContent` ⇒ 基线永远补不回来 ⇒ 死循环。

- 已有单测 183 行的注释早写明「没记录时必须由上层显式表态」，
  测试里手工传 `baselineAligned = null` 模拟了它；但生产主写路径
  `KdbxItemRepository.persist` **根本不调 `saveVia`**，这句表态从未落地

  ⇒ 契约与生产实现脱节，单测测错了层。

- 修法：A 给 `KdbxPendingWrite` 加 `baselineKnown`（与 `baselineAligned`
  同一写锁、同一时刻的快照），闸门只在「确实登记过且对不上」时拒写；
  B `AlreadyInSync` 分支仅在「会话已解锁且基线缺失」时补一次内容对账
  （无会话时跳过，编排器原有单测行为不变，也不每次同步都下载整库）；
  C 补 4 处 `baselineKnown` 断言 + `hasBaseline` 门面用例 +

  `KdbxItemRepositoryTest` 云端库无基线端到端放行。

- ⚠️ **安全底线**：放行「不知道」≠ 放松防线。条件写仍带 DB 里的旧令牌，
  远端真被 XC 改过会 412 → CONFLICT，不会静默覆盖；两端都改仍弹三选项。
  `KdbxWriteBaselineTest` 的「远端变过没拉就保存」用例加了

  `baselineKnown == true` 断言，钉住这条不能被修复顺手放宽。

- **认知边界**（用户提问）：KDBX 是**加密文件**不是服务，OneDrive 只同步整文件。
  双向 = 「A 保存 → B 触发一次 stat / pull」，没有条目级 merge、没有实时推送；
  密码一致只解决解密，不解决同步。修完后 B 能保存并自动上传，
  但 A 改了 B **仍不会自动变**，需要 B 有一次同步动作。
  `onResume` 自动 stat 是另一个功能，本批未做。

- **验证**：`6929a1f3` 的 `Android CI (Debug)` `42362653664` 全链路绿
  （3m32s、单测 **1639 例 0 失败**，比修复前 1637 多出的 2 条正是本批新增用例）、
  编译通过；文档门禁 `42362211563` 绿，preview `v0.11.2-dev-6929a1f`。
  首轮 `42362211526` 红在单测编译漏 `io.vaultix.model.KdbxCloudSyncStatus` 的 import
  ⇒ 静态核对能查多余 import、查不出**少** import，只能靠编译门禁。

- **真机仍待验**：装机后按原路径复现（显示已同步 → 改条目 → 保存），
  并在 XC 端确认「手机保存能自动上传 / 电脑改后手机同步能拉下来」两个方向都收敛。

## §9 保存反馈与同步入口的新发现

**回答「保存转圈能否后台化、条目页同步为何没反应、拉取为何慢」**

- 取证：数据层**早已异步**——`persist()` 写完本地缓存即返回 `VaultSaveOutcome.Queued`，
  上传由 `autoUploader.enqueue()` 后台跑；表单 `onSave` 也立即关闭。
  唯一把结果藏起来的是 `DetailBodyContent` 的 `busy -> WavyProgress` 整页转圈，
  而 `saving` 等的是本地 KDF 编码 / 往返自检，**不是网络**。

- 本批改动：详情页整页遮罩只由 `deleting` 触发；`SyncStatusDot` 新增 `UPLOADING`，
  映射 `PENDING_UPLOAD` / `PENDING_UPLOAD_WITH_LOCAL_CHANGES`，补「正在上传改动」
  文案、读屏描述与琥珀色。列表角标 `SyncBadge.of` 早已映射 `PENDING`，
  这里补的是 ⋮ 菜单那个点原先落到 `else -> null` 的空白。

- 用户追加「详情页里直接看到转动 → 小云」：新增 `DetailSyncIndicator`
  （`ui/common/CloudSyncIcon.kt`），挂详情页顶栏 actions 最左，数据源是库级
  `vaults.syncStatus`（`ItemDetailViewModel` 已有的 `observeVaults()` 订阅里带出）。
  `PENDING_UPLOAD* / SYNCING` → M3 `CircularProgressIndicator`；
  `IN_SYNC` → `CloudDone`；`FAILED / CONFLICT` → `CloudOff` + error；
  本地 SAF 库不画。文案全复用已有资源，零新增字符串。

- ⚠️ 别复用条目级 `observeSyncStates`：它对 KDBX 恒返回空 map
  （文件即存储，没有「某一条上云」的概念），画出来是在编造状态。
  顶栏位置也刻意避开给 `DetailBodyContent` 加参数（它已贴参数上限）。

- ⚠️ 已知边界：本地会话是**乐观更新**（`mutateLocked` 在写锁里就换成新内容），
  去掉遮罩后若本地写入失败，页面会短暂显示新值；失败仍由 `SaveFailed` Snackbar
  「保存失败：…」兜底。要做严格回滚需让失败路径重读会话，本批未做。

- **未决 B（真机反馈：条目页 ⋮ 菜单「同步」点了没反应）**：
  `ItemsViewModel.retrySync()` 只调 `BitwardenSyncOrchestrator.requestSync()`，
  **未注入** `KdbxSyncRepository`；`VaultRepository.syncVault` 对非 Bitwarden
  直接返回 `Unsupported` ⇒ 拿 OneDrive KDBX 的 id 跑 Bitwarden 链路是空转，
  `syncNote` 也不更新，界面毫无反应。用户因此必须回首页切库再点同步。

- B 的修法（下一批）：给 `ItemsViewModel` 注入 `KdbxSyncRepository`，按
  `vault.kind` 分流；KDBX 分支现查 `localChangedSinceLastSync` 后 `sync()`，
  `NeedsReload` 时**自动 `pull()`**（不用回首页），并让 `syncNote` 显示
  进行中 / 结果。注意 `syncNote` 现在由 Bitwarden 编排器的 flow 持续覆盖，
  分流时要加守卫，否则手动设的进度会被冲掉。
