# 附件完善实施方案（2026-11-27）

> 用户诉求：`密码条目/普通条目的附件功能如何解决完善`；确认「**先出可落地方案** +
> **Bitwarden / KDBX 两者均衡**」。本文件是**规划真源**，本轮**未改任何生产代码**。
> 开工某阶段前先读本文件对应章节；每阶段完成后回填结论。

## 1. 一句话结论

附件不是「一个功能没做」，而是**三个不同层面的缺口**，必须分开解决：
① Bitwarden **只读**（下载已通、上传/删除缺）；② KDBX **只显示文件名**（读写都缺）；
③ 明文缓存清理（#194，`SensitiveCache` 已建、需覆盖验证）。
**关键技术验证推翻旧结论**：kotpass 0.13.0 **已有公开的 binary 读写 API**，
KDBX 附件不再是「等上游 / 只能反射」的死局——见 §3。

## 2. 现状盘点（代码级，2026-11-27 实测）

| 库类型 | 已实现 | 缺口 | 证据 |
|---|---|---|---|
| Bitwarden | 详情页列出附件；下载→验 MAC→解密→`ACTION_VIEW` 打开（2026-10-21 交付） | **无上传、无删除、无编辑入口**；API 只有 `GET attachment/{aid}` | `BitwardenVaultApi.kt:70`；`ItemDetailScreen.kt:1787` `AttachmentsSection` |
| KDBX | 条目级列出附件名 +「暂不支持导出」文案 | **既不能导出也不能新增**；注释称受 kotpass 限制 | `KdbxItemMapper.kt:200-225`；`strings.xml:1391` |
| 本地条目 | 无附件概念 | 设计上不补（Vaultix 走 Bitwarden 路线，本地角色由 KDBX 承担） | `.ai/MEMORY.md:389-391` |

模型/接口现状：
- `VaultAttachment(id, fileName, size, source, wrappedKey)`（id 不透明：BW 附件 id / KDBX hash），
  `VaultAttachmentSource = Bitwarden | Kdbx`；**所有 5 种条目类型通用**（Login/SecureNote/Card/Identity/SshKey）。
- `ItemRepository` 附件只有 `downloadAttachment()`，无 add/remove。
- `KdbxItemWriter`（960 行）**完全不碰 binaries**；写入统一走 `Kdbx.mutate(vaultId){ db -> ... }`
  （持锁 + 改前指纹 + `KdbxPendingWrite` 落盘），是新增附件写入的正确切入点。

## 3. 关键技术验证结论（本轮实测，最重要）

### 3.1 kotpass 0.13.0 已有公开 binary API —— 旧注释过时

上游核对（Maven Central `latest/release = 0.13.0`，2025-09-28，项目已在此版本）：

| API（0.13.0 tag 源码，均 **public**） | 用途 |
|---|---|
| `val KeePassDatabase.binaries: Map<ByteString, BinaryData>` | 按 hash 取库内二进制 |
| `inline fun KeePassDatabase.modifyBinaries(block: (Map) -> Map): KeePassDatabase` | 增/删库内二进制 |
| `fun KeePassDatabase.removeUnusedBinaries(): KeePassDatabase` | 清理无引用二进制（删除附件后用） |
| `BinaryData.getContent(): ByteArray` / `inputStream()` | 取明文（自动处理 GZIP 压缩态） |
| `BinaryData.Uncompressed(memoryProtection, raw)` / `.Compressed(...)` | 构造新二进制 |
| `BinaryReference(hash: ByteString, name: String)` | 条目上的引用（KDBX4 按内容哈希去重） |

**结论**：`Kdbx.binaryOf()` 无需等升版、无需反射，直接用 `db.binaries[hash]?.getContent()` 即可实现；
`KdbxItemMapper.kt:200-225` 的「只能反射、密码库不可接受」注释在 0.13.0 上**已不成立**，
实施时须一并订正，否则下一位接手者会再次被误导。
⚠️ `Meta.binaries` 仍是 `@PublishedApi internal`，但**无需访问它**——用 `db.binaries` 公开扩展即可。

### 3.2 Bitwarden 上传/删除协议清晰，加密基元齐备

bastion（仓内 vendored、GPL 同源合法、只读参考）核对：

- **拿上传 URL**：`POST /ciphers/{id}/attachment/v2`，body `{key, fileName, fileSize}`
  （`key` = 包裹后的附件密钥 EncString，`fileName` = 加密文件名，`fileSize` = **密文**长度）
- **响应** `AttachmentUploadResponse{fileUploadType:Int, url:String?, cipherResponse, attachmentId}`
- **上传分派**：`fileUploadType=0` → Direct Multipart（同源 API、带 Bearer，两个 part：`key` + `data`）；
  `=1` → Azure Blob PUT（第三方签名 URL、带 `x-ms-blob-type: BlockBlob`、**无** Bearer）
  〔2026-11-28 订正：早期版本把 0/1 写反了；以 bastion 常量 `FILE_UPLOAD_TYPE_DIRECT=0`
  与 `AttachmentUploadResponse` 注释为准〕
- **删除**：`DELETE /ciphers/{id}/attachment/{aid}`
- **加密流程**：生成附件独立密钥→用条目/账号密钥包裹→加密文件（Bitwarden 格式）→加密文件名

Vaultix 已有可复用基元：`SymmetricCryptoKey.random()`、`VaultixCrypto.encrypt()/encryptString()`。
需补：附件格式写方向封装（对齐现有 `BitwardenAttachmentCrypto.decrypt` 的读格式）、
3 个 API 端点 + 2 个 DTO、编排器、仓储接口、UI 入口。
⚠️ **安全红线（继承 2026-10-21）**：上传/下载附件必须用**无鉴权 client**（`@AttachmentHttpClient`），
签名 URL 指向第三方对象存储，默认 client 的 Bearer interceptor 会把令牌泄露给第三方域名。

### 3.3 写回条目的附件语义（Bitwarden 侧的坑）

`.ai/issues/07-part1:103` 与 `CipherMapper.kt:331` 明确指出：附件在常规条目更新里**刻意不透传**
（服务端 `ToCipher` 不带 attachments 时原样保留；带了是整体替换语义，透传有覆盖风险）。
⇒ 上传/删除**必须走专用附件端点**，完成后用响应里的 `cipherResponse` 更新本地条目附件列表，
**不要**把附件塞进普通 `toUpdateRequest()` 回写。

## 4. 分阶段实施计划（两者均衡）

> 每阶段都是独立可发版增量，含测试 + 门禁 + CI；顺序按「风险低、收益高、可验证」排。

### P0 · Bitwarden 附件上传 + 删除（先做，收益最高）

**目标**：详情页能对 Bitwarden 条目「添加附件」「删除附件」，与现有下载链路闭环。

**改动清单（文件级）**
| 层 | 文件 | 动作 |
|---|---|---|
| crypto | `data/bitwarden/.../BitwardenAttachmentCrypto.kt` | 补 `generateAndWrapAttachmentKey()`、`encrypt()`（写方向，对齐现有 decrypt 格式）、`encryptStringForAttachment()` |
| API | `data/bitwarden/.../BitwardenVaultApi.kt` | 补 `createAttachmentUploadUrl`、`uploadAttachmentDirect`、`deleteAttachment` 三个端点 |
| DTO | `data/bitwarden/.../model/BitwardenDto.kt` | 补 `AttachmentUploadRequest`、`AttachmentUploadResponse`（fileUploadType/url/cipherResponse/attachmentId） |
| 编排 | 新增 `BitwardenAttachmentUploader.kt`（与 Downloader 并列） | 生成密钥→加密→拿 URL→按 type 上传→返回新 attachments |
| 仓储 | `domain/ItemRepository.kt` + `data/repository/ItemRepositoryImpl.kt` | 补 `addAttachment()`、`removeAttachment()`；用 `cipherResponse` 更新本地列表 |
| UI | `ItemDetailScreen.kt` `AttachmentsSection` + `ItemDetailViewModel.kt` | 加「添加附件」（`ActivityResultContracts.GetContent`）与删除确认；上传中禁用按钮、错误文案复用现有 `attachment_*` 系列 |
| 文案 | `strings.xml` | 新增上传/删除相关 string（注意硬编码中文门禁） |

**测试门禁**
- `BitwardenAttachmentCryptoTest`：新增写方向向量——**往返**（encrypt→decrypt 明文一致）、
  MAC 篡改反证、包裹密钥解包一致；加密文件名往返。
- `BitwardenAttachmentUploaderTest`：MockWebServer 回放 200/401/500、`fileUploadType` 两种分派、
  AES key 清理（异常路径也清）。
- 门禁脚本 `check_bitwarden_attachment_write.py`（剥注释）：钉住「上传用无鉴权 client」
  「附件不进 toUpdateRequest」「异常路径 clear 密钥」三条，带变异自测，接 `ci-debug.yml` 两步。

**风险点**：① 密钥材料清理（每个异常分支都要 `clear()`）；② 密文长度 vs 明文长度别搞混；
③ Direct Multipart 的 `key` part 用 EncString 文本、`data` part 用密文字节，别对调；
④ 免费账户 Premium 限制（对齐 bastion `PremiumRequired`，Vaultix 需决定提示还是硬拦）。

**验收**：真机对自建 Vaultwarden 上传一个小附件→重新同步→另一设备能下载打开；删除→同步→两端一致。

### P2 · KDBX 附件新增/删除 + 安全收尾

**目标**：KDBX 条目附件可新增、可删除；锁库清理明文附件缓存纳入门禁。

**改动清单**
| 层 | 文件 | 动作 |
|---|---|---|
| 写库 | `data/kdbx/.../KdbxItemWriter.kt` + `Kdbx.kt` | 新增 `addAttachment` / `removeAttachment`：在**同一次 `mutate`** 里
  `modifyBinaries{}` + 更新 `entry.binaries`（`BinaryReference`）→ 复用现有落盘/指纹门禁 |
| 仓储/UI | `ItemRepository` / `Impl`、`ItemDetailScreen` / `ViewModel` | 接通新增（系统文件选择器）/删除，与 P0 UI 合并成一套通用附件操作 |
| 安全 | `SensitiveCache.kt` + 清理调用点 | 确认附件明文缓存（#194）在锁库/删条目时都清；加门禁 `check_sensitive_cache_clear.py` |

**测试门禁**
- `KdbxItemWriter` 附件用例：新增后往返（重开库取回字节一致）、删除后 `removeUnusedBinaries()`
  生效、库指纹/保真门禁不退化（尤其自定义图标与历史条目不被误改）。
- 缓存清理测试（已有 `SensitiveCacheTest` 扩展）：锁库路径覆盖附件 kind。

**风险点**：① KDBX4 内容哈希去重——同名不同内容/同内容多引用要正确处理，删除时只清无引用；
② `mutate` 的「改前指纹」必须在改动 binaries **之前**取（照抄现有注释 #185）；
③ 文件大小软上限（对齐 bastion `AttachmentSizeValidator`，避免大文件拖垮库解锁）。

**验收**：真机新增附件→保存→KeePassXC 打开可见且内容一致；删除→保存→二进制被清理、库无残留。

## 5. 跨阶段不变量（任何阶段都不得破坏）

1. **不引入反射**访问 kotpass internal（密码库纪律）；公开 API 已够用（§3.1）。
2. **附件字节不进 `VaultItem` 常驻内存**（只存元信息），取字节按需现取。
3. **Bitwarden 附件走专用端点**，不塞进普通 `toUpdateRequest()`（§3.3）。
4. **第三方对象存储请求用无鉴权 client**，Bearer 不外泄（§3.2）。
5. **密钥材料所有路径都 `clear()`**（含异常分支）。
6. **只推 `main`**，合 `rele` 需用户每次明确授权；每阶段出 preview 真机验收后再考虑发布。
