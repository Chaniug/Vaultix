## 0. 为什么挑这一条

## 3. 五个有意的设计决定

### 3.1 Bitwarden 侧**直连**，不进离线队列

条目走「本地先行 + `pending_ops` + 轻量推送」，文件夹**不能**照搬：

1. `pending_ops` 主键是 `cipherId` + 五种 cipher 操作，装不进 folder；
2. 🔴 **`pruneRemovedRows` 会把本地新行当已删清掉** —— "服务端没返回的 folder 行 = 已删"。
   刚建未推的文件夹会被**下一次同步静默删除**；
3. `FolderDao` 只有整体替换语义。

⇒ 成功才写本地，失败一个字不改。**代价（离线时不能建文件夹）是买来的**，
KDoc 里写清了，后续别"顺手统一成队列"。

### 3.2 名字禁 `/` 与 `\`

KDBX 的 `VaultFolder.name` 是**完整路径**（`KdbxItemMapper` 用 `"$parentPath/${group.name}"` 拼）。
组名带分隔符 ⇒ 层级不可解析，建得进去、读出来全错。

上限 100 字符：Bitwarden 服务端未明说，取一个既够用又不会把 UI 撑破的值，并写进策略常量。

### 3.3 `AtomicWriteDao` 的文件夹方法是**非 abstract**

用 Room `@Upsert` 的"已注册实体"形态（`FolderEntity` 在 `@Database(entities=…)` 里），
Room 自己生成实现。副产品：测试里 5 个手写的 `AtomicWriteDao` 转发子类**一个字都不用改**。

若哪天有人改回 `protected abstract`，那 5 个子类会立刻编译失败 —— **这个失败是想要的**。

### 3.4 删除代价「数法只能有一处」

`removeGroup` 已知要报 `GroupDeletion(subGroups, entries)`，UI 确认框也要显示这个数。
⇒ 抽 `deletionCostOf(database, folderId)` 只读预览，`removeGroup` 内部复用它。

⚠️ **UI 侧 KDBX 那支刻意不显示条目数**：`FoldersViewModel` 只统计 `folderId`
恰好等于**完整路径**的条目，子组没算进去 ⇒ 系统性偏小。
给偏小的数字比不给更危险（"才 2 条，删吧"）；而为确认框跑一次文件解析不划算。

### 3.5 两种库的删除文案**必须分开**

- Bitwarden：扁平标签 ⇒ 只让条目变「无文件夹」，**条目不删**；
- KDBX：树 ⇒ **递归删整棵子树**，不可撤销。

同一句话会让 KDBX 用户在无预警下丢数据。

## 4. 本轮踩的坑（编号建议：#200）

### 4.1 🔴 「读报错要看行号指向哪个符号，不要看自己最可疑的那段」

`FolderRepositoryImplTest` 连报 10 条：

```
Suspension functions can only be called within coroutine body.
  at FolderRepositoryImplTest.kt:182:26 …:211:26 …
```

我第一反应是"`coVerify` 写到了 `runTest` 块外面"（之前确实犯过这类错），于是去翻块结构。
**错了。** 报错行是 `every { vaultDao.get(vaultId) }` —— `VaultDao.get` 是 **`suspend`**，
挂起函数必须用 `coEvery`。其它测试文件里全都写的 `coEvery`，只有我新写的这 10 处用了 `every`。

教训：`Suspension functions…` 这条报错**只说明"这个符号是挂起函数"**，
它有两种成因 —— 位置错（在协程外）或**包装函数选错**（`every` / `coEvery`）。
判据是**看列号指向的是哪个标识符**，不是回忆自己上一轮犯了什么错。

### 4.2 detekt `LongMethod ≤150` 是**有效行**，不是总行数

`ItemsScreen` 报 `151`，但我数它的函数体是 228 行 —— 差得远，说明 detekt 排除注释与空行。
踩了三次才定论：
1. 压缩 `onOpenFolders` 的 KDoc（3 行 → 1 行）→ 仍 151；
2. 删掉那行注释 → **仍 151**（说明参数多出的那 1 行是实打实的）；
3. 最终把 `CreateItemDialog` 的宿主接线抽成 `NewItemDialogHost`（12 行）→ 过。

⚠️ **别用"压注释"去凑门禁**：注释是解释设计意图的唯一地方，为过门禁删注释是净损失。
既有先例（`ItemDisplayOptionsHost` 的 KDoc 写的就是同一件事）说明了正确做法：
**把一组完整接线抽成有独立含义的私有函数**。

### 4.3 `every {}` vs `coEvery {}`、`ExpressiveProgress` 并不存在

后一个是纯记忆错误 —— 项目里叫 `VaultixWavyProgress` / `VaultixWavyProgressBar`。
`VaultixExpressiveTopBar` 的 `title` 参数类型是 **`TopBarTitle`**（不是 `String`）。
这类"名字差一点"的错误编译期就能抓，代价只是多跑一次 gradle；**不要靠猜名字省时间**。

## 6. 待真机验收

1. Bitwarden 库 ⋮ →「文件夹管理」→ 新建 → 出现在分组视图里；
2. 重命名 → 分组视图标题跟着变（同一行 id，非新建行）；
3. 删除 → 确认框写「条目不会被删」→ 删完条目仍在、变成「无文件夹」；
4. **断网**新建 → 当场一句错误提示，**本地不出现幽灵行**（这是最重要的一条）；
5. KDBX 库建子组 → 保存 → 用桌面 KeePass 打开，层级正确；
6. KDBX 删父组 → 确认框写「连同条目一起删除」→ 子组与条目一起消失且**不能撤销**；
7. 名字输入 `/` → 输入框当场变红、按钮置灰；
8. 未解锁库进入该页 → 空态说"解锁后才能查看"，而不是"还没有文件夹"。

## 7. 「完善设置与日常功能」的剩余积压（下一棒起点）

按"会不会伤到用户"排序，前三条比功能更能影响信任：

1. `excludeCredentials` 不读（注册时不提示"这个站点已有这把密钥"）；
2. PIN 熔断无冷却 + 忘记 PIN 绕过；「从不」档 KEK 不绑认证；
3. 自动拉取零接线（`SyncTrigger.PAGE_ENTER/APP_RESUME/PERIODIC` 全仓零调用）；
4. 导出丢密码历史 / 时间戳、`passwordRevisionDate` 从不更新、CSV 导入、passphrase UI、
   安全中心（M3 整块为空）；
5. `UpdateChecker` 走 `ghproxy.net` 且不校验 SHA-256；`FillAssistRepository` 默认联网拉规则；
   `DeveloperLogsDialog` 的 E/F 兜底不脱敏；
6. `KdbxRoundTrip.verify` 只比字段名不比值；`KdbxFidelity.NON_DEFAULT_CIPHER` 从不产生。
