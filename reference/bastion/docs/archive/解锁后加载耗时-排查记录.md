# 解锁后 3~5 秒加载 —— 排查记录（2026-08-30）

## 一、症状

用**指纹**解锁后，要等 3~5 秒才能看到密码库内容。

## 二、先说结论（推断，待真机数据确认）

**主要嫌疑：渲染密码列表时对每一行都做了一次解密。**

`PasswordViewModel` 的列表数据源（`passwordEntriesSource` / `allPasswordsSource`）在 map 里：

```kotlin
entries.map { entry ->
    entry.copy(password = inspectSecretState(entry).plainValueOrEmpty())
}
```

而 `inspectSecretState` → `PasswordProviderRegistry.inspectSecret` →
`BitwardenPasswordProvider.inspectSecret()`（对 Bitwarden 条目）：

```kotlin
val decoded = decodePassword(entry.password)      // 解密
...
rememberOfflineCachedSecret(entry, decoded)       // 加密 + SharedPreferences.apply() 写盘
```

也就是说，为了在列表上显示一个「有没有密码」的小指示，每条都要：
**1 次解密 + 1 次加密 + 1 次 `apply()` 写盘**。
100~500 条 → 这就是 3~5 秒。

`PasswordEntryListItem.kt` 的注释也印证了这一点：

> `inspectSecretState(entry).plainValueOrEmpty()` 解密以驱动「是否有密码」指示与隐藏态显示。

对齐官方 Bitwarden / Keyguard：两者列表渲染都**只吃密文**，解密只发生在
用户点开某一条、或批量解密结果共享流里，**绝不会为了「有没有密码」去解密**。

## 三、已排除的假设

| 假设 | 结论 |
|------|------|
| Bitwarden 主密码 KDF（PBKDF2 600k） | ❌ 用户用**指纹**解锁，不跑 KDF。且 `BitwardenRepository.unlock()` 只在主密码解锁时调用 |
| 解锁后触发网络同步 | ❌ 静默同步有 **8 秒**冷启动宽限（`COLD_START_AUTO_SYNC_GRACE_MS`），刚开 App 就解锁时同步被推迟 |
| `restoreUnlockStateFromVault()` 慢 | ❌ 它内部的 `decryptFromStorage()` 只是 **Base64 解码**，没有 Keystore 操作，微秒级 |
| `unlockVaultWithBiometric()` 慢 | ⚠️ 内部只有 1 次 Keystore 解包，理论上毫秒级。**但它由 Compose 直接同步调用**（`AuthComponents.kt`、`PasswordListTopSection.kt`），跑在**主线程**，Keystore 是跨进程 Binder —— 需实测确认 |
| 冷启动修复引入的 | ❌ 那次改的是「隔夜后打开 App」路径，方向是**减少**解密 |

## 四、插桩（统一 tag `BASTION-PROFILE`）

真机一行看全：

```bash
adb logcat -c
# 锁屏 → 指纹解锁 → 看到列表
adb logcat | grep BASTION-PROFILE
```

| 日志 | 含义 | 关注点 |
|------|------|--------|
| `biometricUnlock.total` | 指纹解锁总耗时 | **看 `thread=` 是不是 main** |
| `biometricUnlock.ensureMdkKeystoreWrapper` | MDK 包装初始化 | 正常应极快 |
| `biometricUnlock.getMdkForCrypto` | Keystore 解包 MDK | 正常应极快 |
| `passwordUnlock.hashMasterPassword` | 主密码 PBKDF2（带 `iterations=`） | 走指纹时不该出现 |
| `passwordUnlock.upgradePbkdf2ParamsIfNeeded` | 存量 100k→600k 升级，**会再跑 1~2 次 PBKDF2** | 若反复出现说明升级没持久化 |
| `bitwardenUnlock.deriveMasterKey` | Bitwarden KDF（带 `kdf=` `iterations=`） | 走指纹时不该出现 |
| `bitwardenUnlock.total` | Bitwarden Vault 解锁总耗时 | |
| **`passwordEntriesSource.decryptAll`** | **列表逐条解密（主要嫌疑）** | **看 `costMs` 与 `entries`** |
| **`allPasswordsSource.decryptAll`** | 同上，另一条数据源 | |
| `loadVaultData` / `loadVaults` | Bitwarden 侧数据加载 | |
| `Startup maintenance done` | 启动维护（不含解密） | |
| `restoreUnlockedVaults done` | 恢复解锁态 | |

### 怎么读

- 若 `decryptAll` 的 `costMs` 是 **3000~5000** 且 `entries` 接近你的条目数 → **确认是列表解密**，按第五节方案 ① 修。
- 若 `decryptAll` 很快，但 `biometricUnlock.total` 慢且 `thread=main` → 是指纹解锁在主线程堵 Keystore，按方案 ② 修。
- 若都快，但端到端仍 3~5 秒 → 把完整 `BASTION-PROFILE` 输出贴出来，继续往下挖（可能是 UI 层重组或 Room 查询）。

## 五、静态审计：解密出来的明文，列表根本没用（2026-08-30 完成）

在等真机数据的同时，把「列表解密的产出物到底被谁消费」完整追了一遍。
结论比预想的更干净：**逐行解密的结果，在首屏路径上是零消费的纯浪费。**

### 5.1 列表渲染路径：零处读取 `entry.password`

逐个 grep 了 9 个列表文件，`entry.password` **一次都没被读**：

| 文件 | `.password` 命中 |
|------|------------------|
| `ui/password/PasswordEntryCard.kt` | 0（命中的全是 `com.bastion.app.ui.password.` 包名导入） |
| `ui/password/MultiPasswordEntryCard.kt` | 0 |
| `ui/password/PasswordListRows.kt` | 0 |
| `ui/password/PasswordListContent.kt` | 0 |
| `ui/password/PasswordListContentSupport.kt` | 0 |
| `ui/password/PasswordListScrollableContent.kt` | 0 |
| `ui/password/PasswordListMainPane.kt` | 0 |
| `ui/password/PasswordAggregateListContent.kt` | 0 |
| `ui/password/PasswordListDisplaySupport.kt` | 0 |

卡片展示行由 `resolvePasswordCardDisplayLines()`（`PasswordCardDisplayContent.kt:33`）生成，
它只读 `username` / `website` / `notes` / `updatedAt`，**字段枚举里就没有 password**。

### 5.2 点击进详情：明文被直接丢弃

```kotlin
// PasswordListRows.kt:172
passwordEntries.firstOrNull { it.id == passwordId }?.let(onPasswordClick)

// ui/PasswordTabPane.kt:120
onPasswordClick = { password -> onPasswordOpen(password.id) }   // ← 只用 id
```

整个 entry 传出去，但**只取 `.id`**，详情页自己按 id 查库并解密。解密结果在传递途中被扔掉。

### 5.3 三个真实消费点（都不在首屏）

| 消费点 | 是否依赖明文 | 是否在解锁后首屏 |
|--------|-------------|-----------------|
| `ui/screens/GeneratorScreen.kt:2380` 生成器历史「已存在」去重 | ✅ **真依赖**（`entry.password == historyItem.password`） | ❌ 用户主动打开生成器页 |
| `viewmodel` 内 `filterGhostEntriesForDisplay()`（:736）幽灵条目过滤 | ⚠️ 读 `password.isBlank()`，但**密文也非空**，语义见下 | ✅ 在主列表流里 |
| `ui/password/BitwardenSyncSnapshotSection.kt:371` 同步快照预览 | ❌ 用的是 preview 快照，非主列表流 | ❌ 独立页面 |

顺带排除了两个看着像、其实不是的：
`PasswordBatchMoveSupport.kt:623 buildPasswordDecryptSnapshot()` 自己调 `securityManager.decryptData()`，
**不依赖列表流的解密结果**；安全分析走独立的 `SecurityViewModel.analysisData`，不在主列表路径。

### 5.4 移除解密会带来的 3 处行为差异（必须先处理）

**A. Bitwarden 离线缓存不再被「顺手」预热**
`inspectSecret()` 里的 `rememberOfflineCachedSecret()` 是唯一"有用"的副作用。移除后首屏不再写离线缓存。
→ 兜底已存在：同步后有 `warmBitwardenOfflineSecretCacheForVault()`；且上一轮冷启动修复已删过预热。

**B. `filterGhostEntriesForDisplay()` 的判空语义会变**
当前：`解密失败 → plainValueOrEmpty() 返回 "" → isBlank() 为真 → 被当幽灵条目过滤掉`。
移除解密后：密文非空 → 不过滤。
差异只在一个场景暴露：**MDK 包装丢失（需重输主密码）时**，这些条目会从「被隐藏」变成「显示但读不出密码」。
→ 需要显式决策：用 `shouldSkipDecryptAttempt()` 保持原行为，还是认为「显示出来 + 提示不可读」更正确。

**C. 生成器去重会失效**
`entry.password`（密文）永远不等于 `historyItem.password`（明文），按钮会永远显示「保存」。
→ 需改成按需查询（ViewModel 提供 `isPasswordAlreadyUsed(...)`，点击保存时校验一次）。

### 5.5 对方案 ① 的影响

静态审计把方案 ① 的风险从「中」下调到**中低**：不是"要逐一梳理不确定的读点"，
而是读点已经全部枚举完毕、且只有上面 3 处需要处理。剩下的不确定性只剩
「3~5 秒是否真的花在这里」——仍需真机数据确认。

## 六、待数据确认后的修复方向

### 方案 ①：列表不再解密（推荐，收益最大）

主列表流（`passwordEntriesSource` / `allPasswordsSource`）不再逐行 `inspectSecretState()`，
直接用密文；真正的解密留给详情页与复制操作（按需）。

- 收益：列表首屏延迟从秒级降到毫秒级；顺带消掉 N 次「加密 + `apply()` 写盘」。
- 风险：**中低**（原估「中」，静态审计后下调）—— 读点已全部枚举，
  仅需处理 5.4 节的 A / B / C 三处。
- 对齐：这正是官方 Bitwarden / Keyguard 的做法（列表只吃密文）。
- 先例：**仓库里已有** `allPasswordsForUiSource`，注释写明
  "Keep password blank to avoid redundant decrypt work"—— 同一套思路已经用过了。

### 方案 ②：指纹解锁挪到后台线程

`unlockVaultWithBiometric()` 由 Compose 同步调用，Keystore 是跨进程 Binder。
改成 `withContext(Dispatchers.IO)`，UI 显示解锁中状态。

- 收益：只在 `biometricUnlock` 确实慢且主线程时才有效。
- 风险：低。但要改调用点的回调结构。

### 方案 ③：PBKDF2 换原生实现

`BitwardenCrypto.deriveMasterKeyPbkdf2` 走 BouncyCastle 纯 Java，
而同文件的 Argon2id 走 native（`Argon2Kt`）——实现选型不对称。

- 收益：只对**主密码**解锁有效，且需真机验证非 ASCII 主密码的编码一致性。
- 风险：中高（解不开已登录的库）。**指纹解锁场景下收益为零**，故优先级最低。

## 八、负面影响与残留风险

改动已上线，以下是需要知道（但都不严重）的代价。

### 1. Bitwarden 离线兜底覆盖率下降 —— 唯一的实质性影响

**机制**：`BitwardenPasswordProvider.inspectSecret()` 里的
`rememberOfflineCachedSecret()` 原本会在首屏把每条 Bitwarden 明文加密写盘。
删掉列表解密后，只在这些时机写入：

- 用户点开详情 / 复制某条
- 同步成功后 `warmBitwardenOfflineSecretCacheForVault()`
- 延迟静默 warm（`SILENT_SYNC_CACHE_WARM_DELAY_MS = 12s`）

**何时会痛**：某条目**从未打开过**，之后 MDK 包装失效（需重输主密码）
→ 该条显示「不可读」；改动前可能有缓存兜底。

**为什么不严重**：

- MDK 正常时能直接解密，**根本用不到离线缓存**；
- 同步一次即补上（warm 自动跑）；
- 上一轮冷启动修复已删过一次预热，覆盖率本来就已在下降。

**可选缓解**（未做，属新改动）：把 warm 触发时机从「仅同步成功」扩展到
「解锁后空闲时批量补」。

### 2. 生成器历史「已存在」判定有一帧延迟

改动前 `remember` 同步计算，改动后 `produceState` 异步。
打开生成器历史时，按钮可能瞬时显示「保存」再变「已存在」。

- 影响面：仅生成器历史页，通常几十~几百毫秒。
- 若刺眼，可加 loading 态或首帧先禁用按钮。

### 3. 个别损坏条目的行为变化（边角）

| 场景 | 行为 | 与改动前 |
|------|------|---------|
| MDK 包装丢失（需重输主密码） | 全部视为无可读密码 | ✅ 一致（`hasReadablePassword` 已保持） |
| 个别条目密文损坏 / 密钥不匹配 | 条目**显示出来**但密码不可读 | ⚠️ 改动前会被当幽灵条目过滤掉 |

第二条属异常数据路径，且「显示出来」比「静默丢一条」更正确，故接受该差异。

### 4. 附带收益（正面）

- 内存不再驻留全库明文，进一步对齐官方 Bitwarden「锁定即清」模型；
- 消掉 N 次 `SharedPreferences.apply()` 写盘 —— `QueuedWork` 是主线程阻塞的常见来源；
- 大幅减少 Keystore 跨进程 Binder 调用。

### 5. 建议真机补测的功能点

代码路径已逐一确认安全，但以下场景建议实机点一遍（均未依赖列表流明文）：

| 功能 | 数据来源 | 结论 |
|------|---------|------|
| 复制密码 | 详情页 `getRawPasswordEntryById` + `inspectSecretState` 重新解密 | 安全 |
| 自动填充 | `repository.getAllPasswordEntries()` 直接取数 | 安全 |
| 导出 CSV / Bitwarden JSON | `DataExportImportViewModel` 直接取数 + 自己 `decryptData` | 安全 |
| 批量移动 | `buildPasswordDecryptSnapshot` 自己 `decryptData` | 安全 |
| 安全分析 | 独立 `SecurityViewModel.analysisData` | 安全 |
| 同步快照预览 | 用 Bitwarden `symmetricKey` 独立解密 | 安全 |
| TOTP / Passkey 屏 | 只用 `entry.id` 建绑定 | 安全 |
