## 一、结论先行：可以照着做，但有两条**不能照搬**

Bitwarden 官方与 Keyguard 的设计有 4 条架构原则值得直接吸收，
但它们最有名的那两招——**全库批量解密**和**加密下沉 native**——在 Bastion 这里是**过度设计**，照搬反而没用。

### 为什么不能照搬：问题性质根本不同

| | 官方 Bitwarden / Keyguard | **Bastion** |
|---|---|---|
| cipher 的 `name`/`username` 是否加密 | ✅ **加密**（Bitwarden 协议里 cipher 整体加密） | ❌ **明文列**（本地 `PasswordEntry` 表直接存） |
| 列表要显示标题，是否需要解密 | ✅ **必须全量解密**，否则连标题都渲染不出来 | ❌ **完全不需要** |
| 因此必须付出的代价 | 全量解密 → 才需要 Rust SDK 批量 + 共享流 + native 摊薄 | 无 |

**所以**：官方和 Keyguard 的「批量解密 + 共享 StateFlow + native 加密」是一整套
**为"字段全加密"付出的成本补偿机制**。Bastion 没有这个前提，
照搬等于把 500 次解密从一个地方搬到另一个地方——**总量没变，3~5 秒照旧**。

Bastion 的正解是**从 N 次降到 0 次**，而不是把 N 次搬快一点。这比两者都简单。

## 二、要吸收的 4 条原则（逐条映射到 Bastion）

### 原则 1：仓库层只提供密文，解密在上层按需进行

> Keyguard：`BitwardenCipherRepositoryImpl.get()` 返回 SQLDelight reactive Flow，
> 仓库层只提供**密文领域对象**，解密在上层管道按需进行。

Bastion 的仓库层**本来就是对的**（Room Flow 返回密文），
坏在 `PasswordViewModel` 的列表流提前把解密做掉了：

```kotlin
// viewmodel/PasswordViewModel.kt:548（passwordEntriesSource）
val decrypted = exactDeduped.map { entry ->
    entry.copy(password = inspectSecretState(entry).plainValueOrEmpty())   // ← 要删掉
}
// :586 allPasswordsSource 同样问题
```

**改动**：删掉这两个 map，列表直接吃密文。

**为什么零成本**：`resolvePasswordCardDisplayLines()` 只读
`username` / `website` / `notes` / `updatedAt`，字段枚举里就没有 password
（静态审计已确认 9 个列表文件 `entry.password` 命中数为 0）。
官方/Keyguard 做不到这一点——它们不解密连标题都没有。

### 原则 2：解密结果共享，同一份数据只解一次

> 官方：`vaultDataStateFlow` 单一共享流，UI 全部 `map`/`find`/`filter` 派生，
> **解密只发生一次**。

Bastion **已经有现成的共享缓存**，不用新建：
`BitwardenOfflineSecretCache`（`bitwarden/cache/`）

- 内存 LRU（`MAX_ENTRIES = 1000`）+ 磁盘加密兜底
- `remember(entry, plain)` / `recall(entry)` / `clear(entryId)`
- `clearMemoryCache()` —— 锁定即清，对齐官方「锁定即清空内存明文」

**改动**：把按需解密路径（详情 / 复制 / 批量操作 / 自动填充）统一收敛为：

```
recall(entry) 命中? ── 是 ──> 直接用
       │
       否
       ▼
   解密一次 ──> remember(entry, plain) 回写共享缓存 ──> 返回
```

顺带一个发现：`PasswordViewModel.getSecretValueStates(ids: List<Long>)`
**已经是批量解密入口，但目前零调用方（死代码）**。改造后可直接启用，
不必新增 API。

### 原则 3：解锁门控——未就绪时挂起或跳过，**绝不逐条触发重认证**

> 官方：`vaultLockManager.waitUntilUnlocked(userId)` 未解锁则**挂起等待**，
> 解锁后自动继续；**不抛异常、不触发全局重认证**。

**现状**：上一轮已加 `shouldSkipDecryptAttempt()` 短路，
避免逐条击穿会话（`PasswordViewModel`）+ `cachedDataKey` 复用密钥句柄（`SecurityManager`）。✅ 已对齐主干。

**残留差距（本次不做，记档）**：官方是**挂起等待**（解锁后自动继续），
Bastion 是**短路返回 null**。语义差异在于：解密请求若早于解锁到达，
官方会自动补上，Bastion 会返回空且不会重试。改动面较大，单开一条线。

### 原则 4：单条失败不影响整体

> 官方：`decryptCipherListWithFailures` 返回 `DecryptCipherListResult(successes, failures)`，
> 部分失败仍返回成功的那部分。

**现状**：Bastion 单条解密失败会走进重认证判定，最坏 N 次。❌

**改动**：批量入口返回成功/失败分离的结果结构，失败条目降级为
「离线缓存兜底 → 标记不可读」，不中断整批、不触发全局重认证。

## 四、顺带发现的安全差距（不阻塞本次，建议单开）

| 维度 | 官方 Bitwarden | **Bastion** |
|------|---------------|-------------|
| 磁盘内容 | **只存密文** | 密文 + `title`/`username`/`website`/`notes` **明文列**（Bitwarden 同步后解密落盘） |
| 明文生命周期 | 解锁后在内存，**锁定即清**（含 account encryption key） | 内存 LRU 有 `clearMemoryCache()`；但 `remember()` 会把密码明文的**加密副本**写入 SharedPreferences 持久化 |
| 解锁是否需网络 | 否 | 否 ✅ |

`remember()` 写的是 `encryptDataLegacyCompat()` 加密副本而非明文，风险可控，
但与官方「锁定即清、不落盘」的模型仍有偏离。建议作为独立议题评估。
