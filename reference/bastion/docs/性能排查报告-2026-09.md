## 二、🔴 第 1 项：378 处 `collectAsState`，0 处生命周期感知

### 证据

```bash
cd Bastion/app/src/main/java/com/bastion
grep -rn --include="*.kt" -E "\.collectAsState\("   . | wc -l   # 378
grep -rn --include="*.kt" "collectAsStateWithLifecycle" . | wc -l # 0
```

其中 **62 处**直接收集 Room Flow（`*Flow().collectAsState(initial=...)`），分布在：

| 文件 | `collectAsState` 数 |
|---|---|
| `ui/screens/GeneratorScreen.kt` | 41 |
| `ui/screens/AutofillSettingsV2Screen.kt` | 27 |
| `ui/password/PasswordListContent.kt` | 23 |
| `ui/SimpleMainScreen.kt` | 19 |
| `MainActivity.kt` | 19 |
| `ui/vaultv2/VaultV2Pane.kt` | 16 |
| `ui/screens/TimelineScreen.kt` | 14 |

典型（`PasswordDetailScreen.kt:237`）：

```kotlin
val passwordHistory by viewModel.getPasswordHistoryFlow(passwordId)
    .collectAsState(initial = emptyList())
```

### 为什么耗电

`collectAsState` 内部用 `LaunchedEffect` 启动协程收集，**生命周期只跟 Composition 绑定**。
App 退到后台（Activity `onStop`）时 Activity 不被销毁、Composition 保留 ⇒ **Flow 继续收集**。

代价分两类：

- **Room Flow**：Room 的 `InvalidationTracker` 会持续监听数据库变更，任何写入都会重新执行查询
  —— 后台同步写库时，前台这些查询会跟着重跑。
- **高频 Flow**：如 TOTP ticker，后台仍按原频率唤醒。

`collectAsStateWithLifecycle` 会在生命周期低于 `STARTED` 时停止收集，是 Google 官方推荐做法。

### 修法

```kotlin
val passwordHistory by viewModel.getPasswordHistoryFlow(passwordId)
    .collectAsStateWithLifecycle(initialValue = emptyList())
```

依赖**已具备**：`app/build.gradle:357` 已有 `libs.androidx.lifecycle.runtime.compose`。

### 建议推进顺序

1. 先改 **62 处 Room Flow**（收益最实锤）；
2. 再改 Top 7 文件里的其余部分；
3. 低频 `StateFlow`（ViewModel 的 `_xxx.value`）收益很小，可最后做或不动。

> ⚠️ 注意：`collectAsStateWithLifecycle` 的默认值语义是 `minActiveState = STARTED`，
> 与 `collectAsState` 行为差异仅在后台。逐个替换后需回归验证「回到前台数据是最新的」。

## 三、🟡 第 2 项：TOTP ticker 后台不停 + 冗余双 ticker

### 现状

`TotpListContent.kt` 验证器主页面**同时跑了两个 ticker**：

| 行号 | 实现 | 后台是否停止 |
|---|---|---|
| `419-424` | `produceState { while(true) { value = now; delay(1000) } }` | ❌ **不停**（只跟 Composition 绑定） |
| `425` | `rememberTotpTickerMillis(...)` → `TotpTicker.kt` 的 `stateIn(WhileSubscribed(5s))` | ✅ 5 秒无订阅自动停 |

```kotlin
// TotpListContent.kt:419
val sharedTickSeconds by produceState(initialValue = System.currentTimeMillis() / 1000) {
    while (true) {
        value = System.currentTimeMillis() / 1000
        delay(1000)
    }
}
val sharedProgressTimeMillis = rememberTotpTickerMillis(appSettings.validatorSmoothProgress)
```

### 好消息：高频问题已修过

`TotpTicker.kt:26-32` 的注释记录了 2026-09-05 的架构升级 C.4.4：

> 数据层统一为「秒级对齐发射」（此前 smooth 为 50ms 高频发射）：50ms tick 会驱动
> 整个 TOTP 列表每秒 20×N 次重组，是长列表滑动掉帧主因。

所以**掉帧主因已经解决**，现在只剩 1Hz 的后台空转 + 冗余。

### 建议

1. **删除 `TotpListContent.kt:419-424` 的 produceState ticker**，统一用 `rememberTotpTickerMillis`
   —— 后者有 `WhileSubscribed(5s)` 自停，且语义已覆盖秒级对齐。
   ⚠️ 改前先确认 `sharedTickSeconds` 的下游消费方是否与 `sharedProgressTimeMillis` 重复。
2. 编辑页 2 处同款 produceState（`AddEditPasswordScreen.kt:440/451`、`AddEditTotpScreen.kt:527/538`）
   只在用户停留编辑页时运行，优先级低。

## 四、🟡 第 3 项：手写补间动画 `delay(8)` ≈ 125fps

`ui/components/DraggableBottomNav.kt:141-161`：

```kotlin
fun animateTo(targetOffset: Float) {
    scope.launch {
        val startTime = System.currentTimeMillis()          // ← ①用墙钟时间计时
        while (true) {
            val elapsed = System.currentTimeMillis() - startTime
            if (elapsed >= duration) { offsetValue = targetOffset; break }
            val eased = 1f - (1f - progress) * (1f - progress)
            offsetValue = startValue + distance * eased      // ← ②每次都写 State
            delay(8)                                        // ← ③125Hz
        }
    }
}
```

三个问题：

1. **`delay(8)` = 125Hz**，比 60Hz 屏幕快一倍、比 120Hz 略快 ⇒ 约一半的重组纯属浪费；
2. **`System.currentTimeMillis()`** 受系统时间调整 / NTP 校时影响会跳变，动画可能突跳；
   应用 `SystemClock.uptimeMillis()`；
3. 手写缓动而非 Compose 动画 API，不走 Choreographer / vsync 对齐。

**修法**：改用 `Animatable` 或 `animateFloatAsState`（帧对齐 + 可取消 + 生命周期安全）。

影响面：只在用户拖动底部导航时触发 200ms，非常驻 —— 等级中，但属于明确反模式。

## 九、排查手法沉淀

- **Compose 报告要看 restartable，不能只看 skippable**：
  本次第一次筛 `skippable=0` 得到 93 个，但它们 `restartable=0`（是格式化/取色辅助函数，
  不参与重组）——**不是热点**。真正指标是 `restartable=1 且 skippable=0`，本项目为 0。
- **debug 变体的 Compose 报告需要全量重编才有内容**：增量编译时 CSV 只有表头，
  必须 `cleanCompileDebugKotlin` + `compileDebugKotlin`。
- **看到 `while(true)` 先判断是有界还是常驻**：本次 13 处里只有 TOTP 心跳是常驻，
  其余都是流拷贝 / 手势追踪（有 `break` 或 `awaitPointerEvent`）。
- **别急着下结论，先读注释**：`TotpTicker.kt` / `BitwardenOfflineSecretCache` 的优化
  都在注释里写了前因后果，读了才知道哪些坑已填。
