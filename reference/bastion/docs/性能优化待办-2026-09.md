## 二、✅ 第 1 项：手动同步整库预热后台化（已修）

**提交**：`63f5bbc7`（dev）

**根因**：两条同步路径不对称 ——

| 路径 | 原预热方式 |
|---|---|
| 静默自动同步 | 后台异步（`viewModelScope` + `delay(12s)` + `Dispatchers.IO` + 可取消 job） |
| 手动点同步 | **同步阻塞**，直接写在 `SyncResult.Success` 分支里 |

手动路径把 N 条 ×（最多 3 轮 `decryptData` + 1 次 `encryptDataLegacyCompat`
+ 1 次 `prefs.apply()`）压在同步完成回调上，库越大越卡。

**当初卡住改动的点**（已排除）：同步摘要的 `offlineReadyCount` 看起来依赖预热返回值。
核算口径后确认 `warmedCount ≤ availableOfflineCount` 恒成立 ——

- `availableOfflineCount` = `getAvailableOfflineSecretCount()`
  = `SELECT COUNT(*) FROM password_entries WHERE bitwarden_vault_id=? AND isDeleted=0 AND isArchived=0`
- `warmedCount` = 其中「已绑定 cipher 且解密成功」的条数（前者的子集）

⇒ `maxOf` 恒取 DAO 计数，**同步预热对显示数字零贡献**，唯一产出是副作用（填充离线缓存）。

**改法**：抽出 `scheduleOfflineCacheWarm(vaultId, delayMs)`，静默 12s / 手动 1.5s，
共用同一套可取消后台任务。守卫测试增补正向 + 反向断言防止回退。

**验证**：`:app:compileDebugKotlin` 无新增警告；`BiometricUnlockRegressionGuardTest` 16/16 通过。
**待真机**：手动下拉同步，确认同步完成提示即时出现、完成后滚动不掉帧。

## 四、第 4 项：`scudo` 长时采样

出处：`docs/省电与内存优化计划-2026-09.md` §2.3。22 MB（T0）→ 68 MB（6 分钟）。

```bash
snap() { P=$(adb shell pidof com.bastion.app | tr -d '\r'); \
  adb shell run-as com.bastion.app showmap "$P" | \
  awk '$NF=="[anon]"{a+=$3} /scudo/{s+=$3} END{printf "anon=%dKB scudo=%dKB", a+0, s+0}'; }
for i in $(seq 1 20); do echo "t=${i}min $(snap)"; sleep 60; done
```

判据：**趋平 = 缓存，线性增长 = 泄漏**。

## 六、第 8 项：预热写盘的 N 次 `apply()` 与 O(N²)

位置：`BitwardenOfflineSecretCache.kt`

```kotlin
fun remember(entry: PasswordEntry, plainSecret: String) {
    ...
    prefs.edit().putString(...).putString(...).apply()   // 每条一次 apply()
    putMemory(entryId, cipherId, plainSecret)
}

private fun putMemory(...) {
    val next = memoryCache.toMutableMap()   // 每次全量拷贝
    ...
}
```

- **N 次 `apply()`**：每条一次 `SharedPreferences` 提交，1000 条就是 1000 个磁盘写任务，
  连续 `apply()` 还会在 `QueuedWork.waitToFinish()` 时拖慢主线程（Activity stop 路径）。
- **O(N²)**：`putMemory()` 每次 `toMutableMap()` 全量拷贝，上限 1000 条时冷启动首轮
  约 100 万次拷贝操作。

> 缓解因素：`remember()` 开头有去重短路（`existing.cipherId == cipherId && existing.secret == plainSecret`），
> 热路径重复预热会跳过；只有冷启动首轮 / 变更条目才全量走一遍。

**修法方向**：新增批量 API `rememberAll(entries)` —— 单次 `prefs.edit()` 提交 +
单次构建 map。代价是要动 `BitwardenOfflineSecretCache` 的公开接口。

**优先级**：第 1 项背景化后，这条已从「卡 UI」降级为「缩短后台窗口」，中低。

## 七、复用手法

- **改性能前先找对称性**：本次根因是「静默路径已异步、手动路径还是同步」的不对称。
  同一功能的两条代码路径写法不一致，往往是历史遗留 bug 的高发区。
- **先算清"返回值到底有没有人用"**：很多"不敢改"的性能改动，卡点是误以为返回值被依赖。
  把口径算清楚（子集/全集关系），经常能发现零语义损失。
- **改完加反向守卫断言**：正向断言（必须有 X）容易随重构失效，
  反向断言（禁止出现 Y）能真正防住回退。
